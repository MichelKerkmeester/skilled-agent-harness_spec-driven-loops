## Focus

Investigate direct push operations whose local worktree, effective destination, autosync environment, GitHub account, destructive refspec, or multi-ref shape creates a useful pre-execution coordination fact. The narrow boundary is a direct shell-visible `git`/`git -C` or `gh` command. Positive local facts can justify a neutral advisory; authentication, server policy, push acceptance, and the state remaining unchanged through execution cannot be promised.

## Advisory/Enforcement Boundary

- **Keep silent because the blocking hook already owns it:** new-branch owner grammar, wrapper-branch remote publication, and fresh permission for each non-allowlisted `origin` branch push. Do not spend a second line restating the same block/retry. [SOURCE: .opencode/scripts/git-hooks/pre-push:95-159]
- **Retain because the hook does not own it:** detached/linked destination checked out elsewhere; manual wrapper push that bypasses `git-sync.sh`; unconditional/broad force semantics on allowlisted branches; branch deletion of allowlisted refs; tag force/delete; destructive multi-ref or multi-remote partial-outcome risk; and positive `gh` owner/account mismatch. ## Ruled Out

- Generic warnings for every push, every detached HEAD, every linked worktree, every account/owner comparison, or every multi-ref push.
- Claims that matching `gh` identity proves Git transport identity or that API `push=true` proves branch-protection/server-hook acceptance.
- A duplicate one-line advisory for non-allowlisted branch permission or new-branch naming already owned by pre-push.
- Treating a successful `ls-remote`/API snapshot, local remote-tracking SHA, or preflight force lease as authoritative through remote execution.
- Warnings for ordinary first-time tag publication or normal non-destructive multi-ref pushes.

## Dead Ends

- Ordinary Git history still cannot recover force/delete/tag options, failed/blocked pushes, remote-group partial outcomes, or exact advisory matches. This approach remains exhausted; no additional reflog pass can produce push-argv noise rates.
- A network preflight cannot eliminate the race: it adds latency and yields another snapshot, while server authorization, protection, hooks, and leases are decided during receive.

## Edge Cases

- Ambiguous input: “active account” could mean `gh` API identity, HTTPS credential-helper identity, or SSH key identity. This iteration treats `gh` identity as authoritative only for `gh` commands and requires transport evidence before relating it to `git push`.
- Contradictory evidence: policy and briefing assign blocking ownership to pre-push, but the current configured hook path has no installed `pre-push`. Both facts are preserved; the missing install is a hook-health problem, not evidence for duplicating blockers in advisories.
- Missing dependencies: normalized PreToolUse/push-attempt telemetry is absent, so option-specific historical fire rates remain unmeasured.
- Partial success: no remote mutation was permitted, so actual push authorization/protection outcomes were intentionally not tested; current authenticated repository permission was gathered read-only and labeled as a snapshot.

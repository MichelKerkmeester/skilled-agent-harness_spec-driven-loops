## What Was Built

The Skilled framework has a release line of its own. Every note that a GitHub release carries now lives in `.skilled/changelog/skilled/`, byte for byte, and system-spec-kit's changelog describes the skill again, from 4.0.0.0 to 4.1.1.0.

### Phase 1: release-line-split

You write a framework release entry with `/create:changelog skilled`, and only that line can tag and publish a GitHub release, titled with the tag and the entry's editorial title. A component changelog resolves by whole path segment, so the `.skilled/` prefix every path carries can never send a change to the release line. The version reader now sees generation folders, so a folder whose newest entries were grouped into `v3+/` still resolves its latest version instead of returning a folder name. Gate 1 keeps finding the release notes, because their folder joined the trigger index's corpus roots.

## How It Was Delivered

The orchestrator moved the notes with `mv -n` from a fixed list and hashed them before and after. DeepSeek V4.1 Flash Max lanes on cli-devin made one change each in three chains: matching, the release step, the version reader, the exemplar, the playbook and the mode entry in one chain, the three spec-kit entries in another, and the corpus root, the root docs, sk-git and the README in parallel. After every lane, the orchestrator confirmed the process had exited, read the diff and reran the validators before the next lane in that chain started. It then ran the version bumps, the Hermes sync and the gates itself. Nothing is committed or pushed until the operator asks.

Deviations from the plan, each recorded here because the plan named something else:
- `PUBLIC-RELEASE.md` section 8 keeps the framework's own `MAJOR.MINOR.SERIES.PATCH` scheme and gains a `--bump` mapping, rather than pointing at the mode's bump rules, whose names mean different positions.
- `finish-workflows.md` needed four more re-pointed lines than line 725. The retrieval `README.md`, `retrieval-repo-root.vitest.ts`, `create-changelog-presentation.txt` and more lines of the mode's `SKILL.md` and `README.md` changed than the plan listed. The exemplar count was 13, not 12.
- system-spec-kit's `README.md` carries 4.1.0.99, the value the frontmatter-versioning standard derives for a child document, not the 4.1.1.0 the plan assumed.
- The playbook states no numeric scenario count, and its validator warns on a hand-typed census, so the count update became the new section and its ID range.
- The operator added phase 2 mid-work, so the packet became a phase parent and this phase's documents moved into `001-release-line-split/`.

## Key Decisions

| Decision | Why |
|----------|-----|
| A note joins the release line when a GitHub release carries its number, plus v4.0.0.1 and v4.0.0.2 | The operator set this rule. It matches what GitHub already publishes for each tag, since sampled release bodies carry the note's text |
| system-spec-kit restarts its own line at 4.0.0.0 by the bump rules | The operator chose it. The rebuild moved the skill's paths and retired its database, which the rules call a major change |
| Only `skilled` publishes a release | Component versions share the `vX.X.X.X` shape with release tags, so a component version would otherwise claim a release number |
| Moved notes stay unedited | A byte-identical move reads as a clean rename, which keeps each note's history followable |
| Only `.skilled/changelog/skilled` joins the corpus | The rest of `.skilled/changelog` is symlinks onto skill folders, which the walker does not follow and already reaches through `.skilled/skills` |

## Known Limitations

1. **The committed trigger index is stale until the last commit.** It still maps "v4.0.0.0 release notes" to the old path, which now holds spec-kit's own entry. The planned final commit rebuilds it from committed content.
2. **sk-doc serves legacy routing until its manifest is re-minted.** The pre-commit gate does this when the commit stages the mode's `SKILL.md` in full and does not narrow by pathspec.
3. **spec-kit's component 4.0.0.0 shares its number with Skilled v4.0.0.0.** Only `skilled` publishes, so the component version never becomes a tag, but a reader can confuse the two.
4. **v4.0.0.2 is still a draft.** If the operator adds spec-kit changes to it, spec-kit's 4.1.1.0 entry needs the same additions.
5. **Adjacent defects, recorded and not fixed:** `.skilled/commands/create/README.txt:156` shows the old spec path `specs/01--system-spec-kit/042-memory-upgrade`. `.opencode/SYNC.md:35` documents a `.opencode/changelog` link that does not exist. Playbook CHG-001 (`route-global-component.md:29`) expects `.skilled/changelog/sk-doc/vX.Y.Z.B.md`, but `sk-doc` is a hub whose folder holds only symlinks, and its own entries live under `parent/`. The old reader returned the folder name `parent` there, and the new one returns nothing, so neither resolves a hub component. The fix is to resolve a hub to its `parent/` folder, or to ask. Playbook CHG-006 (`prepare-release-notes.md`) says the tag format and the release command are not defined, which stopped being true when the release step landed in the command YAMLs. The moved v4.0.0.1 note still names `.skilled/changelog/system-spec-kit/v3+/` at lines 187 and 210, and stays unedited by design.

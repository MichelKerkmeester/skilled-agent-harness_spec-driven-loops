## What Was Built

The hubs that get a compiled route are now named in one data file instead of five code lists. A consumer such as Barter adds its own hub with one json-entry overlay entry, where it used to overlay four or five upstream code files.

### Phase 25: data-driven hub registry

`.skilled/bin/lib/compiled-routing/hub-registry.json`, with its authored twin at the program root, is schemaVersion `V1`. Its `hubs` list holds `{id, rolloutChild, defaultOn}` for the eight current hubs in today's order. `014-runtime-engine/lib/hub-registry.cjs`, in both trees, validates it: a canonical id, a `rolloutChild` matching `^009-parent-hub-rollout/\d{3}-<id>$`, a boolean `defaultOn`, and no duplicate. The engine's `HUB_CHILD`, the resolver's `DEFAULT_ON_HUBS`, the guard and the sync tool read their sets from it. The advisor reads the same file without a dependency and falls back to empty sets on any error. Sync reads each root's registry with the reader beside it, and the regenerated serving closure grew from 61 to 63 files.

A consumer adds its hub with this entry set, beside a json-entry manifest entry whose destination is `.skilled/bin/lib/compiled-routing/hub-registry.json`:

```json
{"target":".skilled/bin/lib/compiled-routing/hub-registry.json","style":{"indent":2},"operations":[{"op":"appendItems","path":["hubs"],"identityKey":"id","items":[{"id":"sk-git","rolloutChild":"009-parent-hub-rollout/011-sk-git","defaultOn":true}]}]}
```

The consumer still keeps its own rollout folder and activation manifest.

<!-- ANCHOR:decisions -->
## Key Decisions

| Decision | Why |
|----------|-----|
| A data file, not a code list a consumer overlays | A json-entry `appendItems` can add one entry, and a re-pin carries no rebase of upstream code |
| A reader copy in each tree, and sync reads each root with its own | The promoted tree must read no spec path, and a missing or older promoted tree must not break a build of the authored one |
| The advisor fails closed to empty sets | A malformed registry then turns compiled routing off rather than on for hubs nobody chose |
| Keep the eight hubs in today's order | Every hard-coded list carried that order, so the before-and-after diffs can show that nothing a reader produces moved |

<!-- ANCHOR:limitations -->
## Known Limitations

1. **A consumer's closure manifest will not list its hub.** Barter's `serving-closure.manifest.json` `hubs` field will not name sk-git, because consumers do not run sync and nothing validates that field.
2. **`leaf-route-replay.cjs` keeps its own parent-hub list.** It is not the compiled-route set, and the architecture doc says so.
3. **The rollout canary harnesses still fail.** They fail the same way before and after this change, for reasons unrelated to it.
4. **The branch is not merged.** The commits sit on `worktrees/544-upstream-overlay-mechanisms`.

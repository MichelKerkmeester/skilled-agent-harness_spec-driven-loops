# Iteration 003 - Runtime feasibility (Q4) and runner-contract fit (Q5)

## Focus

Final iteration of three. Q4 and Q5 were the two remaining key questions, so both are covered here:

- **Q4** - are the per-runtime feasibility claims in 002 `plan.md`'s adapter table supported by the `cli-*` skills and each CLI's `--help`, and what does a scratch project outside the repository lose from the repo-local runtime config (`.pi/`, `.claude/`, `.opencode/`, `.codex/`, `.devin/`)?
- **Q5** - does 002's runner contract fit its first consumer, `043-decision-capture/006-live-conversation-test`: stage marks, retry-once on DEVIATION, later stages after a failure, S0 with no human turn, S8 compact plus a send in one stage, S9 restart with `--continue`, S12 kill switch in a fresh scratch project inside one scenario file, randomized think-time pauses, nudge lines in a turn's pane, and whether REQ-008's `git status --ignored` snapshot detects appends to an existing ignored queue file.

## Actions Taken

1. Read the run config, strategy, and both reviewed packets' requirement and plan text (`002/spec.md`, `002/plan.md`, `006/spec.md`, `006/plan.md`, `006/goal.md`).
2. Ran `--help` for all five CLIs (read-only, no interactive sessions), grepping for exactly the flags 002's adapter table claims. `timeout(1)` is absent on this machine, so a `perl -e 'alarm'` wrapper bounded each call.
3. Listed the repository's repo-local runtime config directories and their top-level contents, to establish what a scratch project outside the repository inherits and loses.
4. Verified the git-snapshot claim empirically: `git status --porcelain --ignored -- .skilled/skills/.state` and `--ignored=matching` against the live state tree, plus `git check-ignore -v`.

No files outside this lineage directory were modified. No live interactive session was started.

## Findings

### Q4 - Runtime feasibility, checked against `--help`

The 002 adapter table's launch flags are almost entirely real. That is the good news, and it is worth stating plainly, because the plan hedges harder than the evidence requires.

**Claude Code: every claim confirmed, feasibility "High" is right.**

`claude --help` exposes `--session-id <uuid>` ("Use a specific session ID for the session"), `-r, --resume [value]` ("Resume a conversation by session ID or open a picker"), `-c, --continue` ("Continue the most recent conversation in the current directory"), `--dangerously-skip-permissions` ("Bypass all permission checks"), and `--ax-screen-reader` ("Render screen-reader friendly output"). All five flags named in [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/plan.md:94] exist. Two extras the adapter does not mention are also available and may be better than what is planned: `--permission-mode <mode>` accepts `bypassPermissions` (`claude --help`), which is the documented route, and `--allow-dangerously-skip-permissions` is the separate allow-list gate that precedes it. A probe that reaches for `--dangerously-skip-permissions` first should know `--permission-mode bypassPermissions` exists as the supported spelling.

**OpenCode: every claim confirmed.** `opencode --help` gives `--standalone` ("Run with a private server instead of the background service"), `--auto` ("Auto-approve permissions that are not explicitly denied"), and `--session, -s string` ("Session ID to continue, or to create if it does not exist"). That is exactly the launch line in [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/plan.md:95], including the create-or-continue semantics the plan relies on. One caveat the plan should carry: `--auto` auto-approves what is *not explicitly denied*, so an explicit deny in OpenCode's permissions config still surfaces a prompt, which R-002 would read as an unexpected question. The scratch project has no `.opencode/` permissions config, which makes this unlikely and also makes the point in the config finding below matter.

**Codex: every claim confirmed, and one new risk the plan does not weigh.** `codex --help` has `--no-alt-screen`, `--no-daemon`, and `--dangerously-bypass-approvals-and-sandbox`, and it has **no** `--session-id`, which independently supports the plan's statement that "the session id is not fixed at launch" [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/plan.md:96]. The "Low for tool questions" rating is also supported by the measured behavior recorded in 002: `codex features list` prints `default_mode_request_user_input    under development  false` [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/spec.md:111]. What the plan misses is that `codex --help` also offers `--dangerously-bypass-hook-trust` and `--approve-for-me`. A dedicated *hook-trust* bypass is evidence that Codex gates hooks behind a trust decision — and the consumer that matters here (006) depends on hooks firing inside the subject: the decision-capture append and the Stop-hook nudge are the whole observable surface of S1 to S11 [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/plan.md:86]. An untrusted-hook prompt would land as a question the adapter does not expect, and a silently skipped hook would leave 006 with an all-N/A matrix row and no explanation. The adapter table should name the hook-trust flag as a probe item, and 002's R-002 ("a permission or workspace-trust prompt is read as a question") should be extended from workspace trust to hook trust.

**Pi: every claim confirmed.** `pi --help` lists `--session-id <id>` ("Use exact project session ID, creating it if missing"), `--approve, -a` ("Trust project-local files for this run"), and `--tui-mode <mode>` ("fullscreen (default) or regular"). All three are what [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/plan.md:97] claims. Note `--session <path|id>` is the *partial*-UUID variant and `--session-dir <dir>` also exists; the adapter should stay on `--session-id`, which the plan already names.

**Devin: flags confirmed, resume mechanism unverified.** `devin --help` gives `--permission-mode <PERMISSION_MODE>` with `"dangerous"` documented in the modes list, plus `-r, --resume [<SESSION_ID>]` and `-c, --continue`. So `devin --permission-mode dangerous` is real. What is *not* supported by anything read this iteration is the resume half of the adapter: [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/plan.md:98] says the restart uses "the id from `devin list` in the project folder". `devin list` is a subcommand (its surface was not checked) and `--resume` takes an **optional** id — which means `devin --resume` with no id plausibly opens an interactive session picker, itself a question surface the adapter would have to detect or avoid. Both belong on the T001 probe list, and the Devin row should say so rather than "Medium" as a closed judgment.

**What a scratch project outside the repository loses.** All five repo-local runtime directories exist and carry real configuration: `.claude/` (`agents`, `commands`, `hooks`, `skills`, `settings.json`, `settings.local.json`, `mcp.json`, `repo-rules`), `.pi/` (`agents`, `extensions`, `npm`, `models.json`, `mcp.json`, `pi-blackhole-config.json`), `.opencode/` (`agents`, `commands`, `hooks`, `plugins`, `bin`), `.codex/` (`agents`, `hooks`, `hooks.json`, `prompts`, `config.toml`, `repo-rules`), and `.devin/` (`agents`, `hooks`, `hooks.v1.json`, `skills`, `config.json`, `mcp_config.json`, `repo-rules`). A scratch project made by `mktemp -d` plus `git init` outside the repository inherits **none** of it: no hooks, no agents, no slash commands, no skills, no MCP servers, no model or provider config. 002's scratch guard creates `<scratch>/<runtime>/`, writes the `.conversation-scratch` marker and runs `setup` there [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/plan.md:79] — and `setup` is the *only* channel by which any of that config can reach the project. Two consequences. First, 002 has no requirement that `setup` exist for a runtime that needs project-local config, and no post-setup check that the config arrived; a runtime that starts without its hooks will still report PASS on a scenario that only types text. Second, this is not hypothetical for the first consumer: 006's S0 has to hand-build `.claude/settings.json`, hook links, `AGENTS.md`, `CLAUDE.md`, a demo packet and a real `.skilled/skills/.state/` [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/plan.md:63], and S12 has to build a second such project. A `setup` failure is a `REQ-001` refusal today (exit 2, nothing starts), which is right for a broken setup and wrong for a *missing* one.

One runtime survives the loss: Pi's `ask_user_question` comes from `@juicesharp/rpiv-ask-user-question` installed both repo-locally, at `.pi/npm/node_modules/@juicesharp`, and user-globally, at `~/.pi/agent/npm/node_modules/@juicesharp` — both paths appear in the packet's own measured output [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/spec.md:113]. So Pi keeps its question tool outside the repository; the other four lose their project-level plumbing. That asymmetry is worth one line in the adapter table, because it means Pi's matrix row can pass while a harness fault is present.

### Q5 - The runner contract against its first consumer

**Stage marks have no carrier.** 002 is explicit: "Verdicts are PASS, FAIL or SKIP only" [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/spec.md:180]. 006 needs `PASS, FAIL, DEVIATION or N/A` [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/spec.md:101]. 002's plan asserts "Stage marks map onto PASS, FAIL and SKIP" [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/plan.md:114] — but SKIP is a *runtime-level* blocker ("the runtime's binary is missing, the scenario's `runtimes` list leaves it out, or the script needs a question tool the adapter does not have" [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/spec.md:180]), not a stage outcome, and neither DEVIATION nor N/A has any producer. DEVIATION is load-bearing for 006: the plan's matrix columns make the nudge cells on four of five runtimes read N/A [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/plan.md:90]. And 006's `checkpoints.tsv` has four columns — stage, status, evidence path, observed value [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/plan.md:64] — while 002 emits per-turn pass/fail plus a per-runtime verdict and a matrix row [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/plan.md:83]. Nothing in either packet's requirements produces a per-stage status file. The crosswalk is asserted in one plan line and carried by no requirement on either side.

**Retry-once on DEVIATION is forbidden by the contract it needs.** 006 sets NFR-R02: "A stage is retried once only for a subject DEVIATION, never for a capture FAIL" [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/spec.md:199], and its risk row says "the runner resends the instruction once, and a second miss is FAIL with the pane capture" [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/spec.md:174]. 002 says the opposite: "The first failed turn ends that runtime's run" [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/spec.md:171]. There is no retry, no attempt counter and no re-send in 002's requirement set. This is a direct contradiction, not a gap: implementing 002 as written makes 006's mitigation impossible.

**Later stages after a failure: partial fit.** 006's failure path "kills that tmux server and marks the later stages SKIPPED" [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/spec.md:209]. 002 ends the runtime at the first failed turn and records "first failure" in the matrix row, but has no per-stage SKIPPED rows and no reason field [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/plan.md:83]. 006 would have to derive the 12 remaining rows itself.

**S0 has no human turn, so it has no turn and therefore no check.** 006's S0 is "Build the scratch project, record baselines" with "none" as the human turn [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/plan.md:72]. 002's turn model is exactly one of `send`, `restart` or `compact` [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/spec.md:168], and `check` runs only "after each settled turn" [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/spec.md:171]. A turn `id` is what names the evidence folder [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/plan.md:113], so a stage with no turn has nowhere to put an evidence path. The format needs a check-only stage. Note also that 002's own baseline is the *repository* snapshot [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/spec.md:173], whereas 006's S0 baseline is `git -C "$R" status --short` plus `ls "$Q"` in the scratch project — two different things being called a baseline, and only one of them is written where 006 expects it.

**S8 compact plus a send in one stage does not fit one turn.** 006's S8 is `/compact`, *then* "Ask me with the tool which size the badge uses", with "queue sha before and after `/compact`" as a checkpoint [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/plan.md:80]. 002 gives a turn a single action [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/spec.md:168] and runs the check only at the end of a settled turn [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/spec.md:171]. So the sha comparison *between* the compact and the next send has no slot: either S8 becomes two turns (two evidence ids, and the checkpoint count breaks 006's 13-row requirement, SC-001 at [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/spec.md:159]) or the scenario keeps one dump plus a `check` on the pre-checkpoint it needs.

**S9 restart: `--resume <uuid>` is not `--continue`.** 006's S9 is `/exit`, relaunch with `claude --continue` [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/plan.md:81], and 006 carries an open question about whether that keeps the session id [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/spec.md:232]. Under 002, restart means "exit, then relaunch into the same session" [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/spec.md:168] via the adapter's `resume`, which for Claude is `claude --resume <uuid>` with a `--session-id <uuid>` fixed at launch [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/plan.md:94]. Both flags exist, and they are different operations: `--continue` takes the most recent session in the working directory, `--resume <uuid>` takes a specific one. So by construction the session id *cannot* change under 002, 006's open question disappears, and S9's "session id recorded" expected value stops being informative. If 006 wants the human-realistic `/continue` path, the adapter must not fix the session id at launch. One of the two docs has to own that decision; today both assume their own.

**S12 in one scenario file contradicts 002's own guidance.** 006 needs S12 — "New scratch project `$K`, subject launched with `SYSTEM_DECISION_CAPTURE_DISABLED=1`" — as the thirteenth row of the *same* scenario [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/plan.md:84], and its completion criteria require all 13 rows in one `checkpoints.tsv` [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/goal.md:56]. 002's guidance table says the way to express a kill-switch run is "A second scenario whose `env` sets the switch" [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/plan.md:112]. And 002's scratch guard creates exactly one project per runtime, `<scratch>/<runtime>/` [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/plan.md:79], so a mid-scenario second project is not representable at all. This is the sharpest contradiction found this iteration: the consumer cannot write its own completion criterion against the producer's documented mechanism.

**Randomized think time has no expressible form.** 006 specifies "5 to 15 s of think time after each turn ends and 3 to 8 s after a question widget renders, from a seed it records" [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/plan.md:68] — the human-pause realism that the phase's whole objective rests on [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/goal.md:36]. 002 has a fixed per-turn `delay_ms` [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/spec.md:168], no per-question pause, no randomization and no seed, and `actions.jsonl` has no required fields, so the sampled pause is not even recorded. As specified, 006 cannot be written in 002's format.

**Nudge lines per turn need a per-turn window the evidence contract does not provide.** 006 counts nudge lines in each turn's pane, S1 to S11, expecting `0,1,1,1,0,0,1,1,1,0,0` [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/spec.md:137]. 002 saves `turns/<id>/screen.txt` and one whole-run `raw-pane.log` [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/plan.md:83]. A `capture-pane` of the *settled* screen can miss a nudge line printed earlier in the same turn, and the raw log has no per-turn boundaries to cut. 002 needs a per-turn byte offset into `raw-pane.log` (or a capture taken before the check) for REQ-006 of 006 to be checkable; the fallback is for 006 to count from `$Q/*.nudge` and use the pane only as a presence sample — which is weaker, because it stops proving the line was *shown*.

**REQ-008 cannot detect an append, which is the failure it exists to catch.** 002 snapshots `git status --porcelain --ignored -- specs .skilled/skills/.state` before and after each runtime and fails on "any difference" [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/spec.md:173]. `git status` reports paths and their tracked/untracked/ignored state; it never reports file contents, so appending a line to an existing queue file, or bumping the count in an existing `<session>.nudge`, produces a byte-identical snapshot. Verified live against this repository's state tree: `git status --porcelain --ignored -- .skilled/skills/.state` prints one `!! <path>` line per ignored file, and `--ignored=matching` prints the same set here, so neither mode recurses into contents. The only detectable events are path creation and deletion. That is exactly backwards from the risk 006 names — "A run writes into the real repository's `specs/` or its real queue" [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/spec.md:175] — because a queue write *is* an append to an existing file. 006's own check has the same hole and one more: it uses `git status --short` with no `--ignored` [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/spec.md:133], so ignored state files never enter its snapshot at all, and its rescue clause ("the file list of the real `.skilled/skills/.state/decision-capture/`") catches a new file but not a new line in an old one. Fix direction for both: hash the state subtree (file list plus `shasum` plus `wc -l`), not `git status`.

**A smaller one, worth one line:** 006's checkpoints carry an "observed value" column [SOURCE: specs/system-speckit/043-decision-capture/006-live-conversation-test/plan.md:64], and 002's `check` contract is a bare exit code with `check.txt` kept [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/spec.md:171]. A bash script can assert everything, so the fit is fine — but the observed value has to be printed to reach `check.txt`, and nothing in 002 requires the check to print anything.

## Questions Remaining

None of the five key questions remain open. These are the decisions the review hands back, each with the probe or edit that would settle it. They are findings, not new research questions, and this run does not resolve them by design.

1. **Which doc owns S8, S9 and S12?** 006's stage content and 002's turn/scratch model disagree in three places. Either 002 gains a check-only stage, an action list per turn and a named second project, or 006 changes its stage count and its `env` mechanism. Decide before either is built, because every one of the three is a format change in 001's closed key set.
2. **Stage marks.** One of the two vocabularies has to yield. Adding DEVIATION and N/A to 002's verdict set is the smaller edit only if a stage status file is also added; otherwise 006 needs a documented derivation.
3. **Retry on DEVIATION.** 002's "first failed turn ends the run" [SOURCE: specs/sk-doc/065-conversation-playbook-scenarios/002-conversation-runner/spec.md:171] has to become attempt-aware, or 006's NFR-R02 becomes unimplementable.
4. **Snapshot mechanism.** Replace `git status` with a content hash over the state subtree in both packets, or the guard tests nothing.
5. **Probe additions for T001.** Verify `devin list`, what `devin --resume` with no id does, and whether Codex needs `--dangerously-bypass-hook-trust` for hooks to fire in a fresh project.

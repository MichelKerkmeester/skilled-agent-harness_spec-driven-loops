# Iteration 3: Styling and Theming — tokens, radius, typography, dark mode, colour

## Focus

Extract the concrete design-token values from evilcharts' Tailwind v4 theme layer, components.json and package.json, and map them onto the corpus's three colour systems, skeleton and templates, naming exact values on both sides.

## Findings

**F3-1. evilcharts' radius scale is a 4-step ladder around an 8.4px base; the corpus uses one 10px radius everywhere.** `--radius: 0.525rem` (=8.4px) with `sm = radius − 4px` (4.4px), `md = radius − 2px` (6.4px), `lg = radius` (8.4px), `xl = radius + 4px` (12.4px). Contextual use: tooltip `rounded-lg` (8.4px), legend swatches `rounded-[2px]`/`rounded-[3px]`, dot rings none. The corpus: all twenty templates and the skeleton declare `border-radius: 10px` for the card and nothing else. **F3-2. evilcharts is chromatic by default; the corpus is grey by default.** The shadcn default theme ships five chart hues per theme — light: orange 41°, teal 184°, blue 227°, yellow-green 84°, gold 70°; dark: blue 264°, teal 162°, gold 70°, purple 304°, red 16° — and the real examples go further: a two-series line chart uses emerald `#047857` and rose `#be123c` (light). The corpus catalog assigns 13 of 20 forms to `neutral` (lightness-ranked greys `#292825 → #8D8B89` with one terracotta emphasis `#B4471F`). The dominant delivered look is grey-on-warm-white with a single chromatic point. **F3-3. The corpus's own system-definition rule says several neutral rows should be categorical.** `color-system.md` defines `categorical` as "category membership" for "unordered categories" and `neutral` as the fallback "whenever hue would carry no stable meaning". A multi-series comparison chart's series identity *is* a category: `grouped-bars` (2 series) is assigned `neutral` while `stacked-bars` (segments) is assigned `categorical` — the same kind of series membership, two different systems. `stacked-area` (2-5 series) is `categorical`, `parallel-axes` is `categorical`, but `grouped-bars` is `neutral`. [SOURCE: ../../../../../../.opencode/skills/sk-doc/sk-create-chart/references/color-system.md:31-37] [SOURCE: ../../../../../../.opencode/skills/sk-doc/sk-create-chart/references/catalog.md:45-58]

**F3-4. Dark mode is a first-class, hue-shifted theme in evilcharts and absent in the corpus.** The `.dark` block re-derives every token: background `oklch(14% 0 270)` (near-black, blue-tinted), card `oklch(0.205 0 0)`, borders at 7.5% white, muted-foreground lifted to `oklch(0.708 0 0)` — and the chart palette is not lightened; it is *re-hued* for dark surfaces. The corpus palette file ships exactly one value set; `color-system.md` already defines the derivation rule ("a lighter value comes from mixing toward surface, a darker from mixing toward ink") but nothing consumes it in the dark direction. The spec's edge-case list explicitly names "a choice that only reads well in a dark theme" and asks whether the corpus should gain one. [SOURCE: context/evilcharts/src/app/globals.css:102-126] [SOURCE: ../../../../../../.opencode/skills/sk-doc/sk-create-chart/references/color-system.md:75] [SOURCE: ../../../../../../.opencode/skills/sk-doc/sk-create-chart/assets/color/palettes.json:1]

**F3-5. Numeric text is set in a mono face with tabular figures in evilcharts; the corpus uses the system face.** Tooltip values are `font-mono font-medium tabular-nums` (JetBrains Mono on the site, `font-mono` token). The corpus applies `font-variant-numeric: tabular-nums` to tick labels only (daily-line `.tick`); value labels inside the figure, notes and the source line do not. The exact fonts are not adoptable (the contract bans web fonts), but the *treatment* is: a system mono stack (`ui-monospace, SFMono-Regular, Menlo, monospace`) costs nothing and needs no network. [SOURCE: context/evilcharts/src/registry/ui/recharts-tooltip.tsx:154] [SOURCE: context/evilcharts/src/app/globals.css:16] [SOURCE: ../../../../../../.opencode/skills/sk-doc/sk-create-chart/assets/templates/daily-line.html:65] [SOURCE: ../../../../../../.opencode/skills/sk-doc/sk-create-chart/references/template-contract.md:128]

**F3-6. The corpus card is 10px radius, system-ui type, warm off-white surface; evilcharts cards are 8.4px-radius surfaces on pure white with Geist.** The corpus chrome (surface `#FAF8F5`, ink `#1A1917`, muted `#52504E`, rule `#E0DFDC`) is warmer and softer than evilcharts' `oklch(1 0 0)` white + `oklch(0.4 0 0)` muted. This is a deliberate product voice, not a deficiency; no adoption recommended on chrome itself. [SOURCE: ../../../../../../.opencode/skills/sk-doc/sk-create-chart/assets/color/palettes.json:1] [SOURCE: context/evilcharts/src/app/globals.css:56-67]

**F3-7. Motion is a dependency of the theme system in evilcharts (`motion` package, `tw-animate-css`), but the corpus contract already contains the hooks for animation.** The contract's rule 13 ("a file that animates carries a `prefers-reduced-motion` fallback") anticipates animation; rule 12 bans randomness and clocks, not animation. So the corpus's current zero-animation state is a choice of not exercising rule 13, not a ban. The specific motion values (1s intro reveal, ease `[0, 0.7, 0.5, 1]`, 200ms tooltip fade) are gathered in iteration 4. [SOURCE: ../../../../../../.opencode/skills/sk-doc/sk-create-chart/references/template-contract.md:166] [SOURCE: context/evilcharts/src/registry/charts/recharts-line-chart.tsx:59-60]

**F3-8. evilcharts strips SVG focus outlines and text selection; the corpus should not.** `svg:focus { outline: none }` and `text { user-select: none }` suit an interactive dashboard where the site owns focus management. A delivered chart is a document; keyboard users tabbing through its links need visible focus, and selectable text is a feature in an artifact people copy numbers from. ## Reflection

- **What worked**: Naming values on both sides (8.4px vs 10px; 5 hues vs 4 greys + terracotta; mono vs system) made every recommendation concrete. The palette file's own derivation rule made the dark-mode recommendation an extension of existing doctrine rather than a new invention.
- **What failed / ruled out**: Focus-outline stripping and chrome changes rejected; the mono font pair (Geist/JetBrains) ruled out by the no-web-font clause, treatment adopted instead.
- **Follow-up**: R3-3 and R3-4 are the two contract-level decisions most likely to change the operator's verdict on the output; they must lead the synthesis. Motion values, hover/focus states, empty state and first-paint animation are iteration 4.

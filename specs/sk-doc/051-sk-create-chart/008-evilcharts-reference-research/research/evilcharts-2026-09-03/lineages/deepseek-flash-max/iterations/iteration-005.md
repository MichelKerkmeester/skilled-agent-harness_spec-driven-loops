# Iteration 5: Registry and CLI Install — and the attribution gate the packet sets on itself

## Focus

How registry.json, the shadcn registry item shape and the CLI deliver evilcharts to a consumer; what the corpus's equivalent delivery surface is; and the one packet rule that re-verdicts every "adopt the code" recommendation made so far.

## Findings

**F5-1. A consumer installs one chart and receives the whole dependency graph.** `registry.json` carries 279 items of two types (`registry:component`, `registry:block`) under a `{name, homepage, items}` envelope. The install flow is: `shadcn add @evilcharts/recharts-line-chart` — the CLI resolves the `@evilcharts` scope through the `registries` entry in `components.json`, fetches the item JSON, copies `charts/recharts-line-chart.tsx` to `components/evilcharts/charts/`, recursively installs the six `registryDependencies` (chart, tooltip, legend, dot, brush, background) to `components/evilcharts/ui/`, and adds the npm dependencies (`recharts`, `motion`). The item JSON's `description` field is the only prose a consumer sees in the CLI. Everything is generated by `build-registry.mts` from the TS manifests; `registry.json` and `public/r/*.json` are never hand-edited. **F5-2. The packet's own NEVER clause blocks attribution-based adoption, whatever MIT says.** `SKILL.md` rule: "Never copy a template, a fragment or a snippet from an outside chart library into this packet. The corpus is authored here, and content under a license this repository cannot grant onward must not enter the tree." The evilcharts licence (MIT) *can* be granted onward, but the rule does not carve out MIT sources — it is a blanket ban on copying from outside chart libraries. This re-verdicts iteration 1's R1-4 (background patterns): the eleven pattern definitions cannot be copied in under this rule. The *idea* (re-authored patterns) survives; the *code* adoption is blocked until the operator amends the NEVER clause, which is a contract-level decision about the packet's provenance stance, not a licence question. [SOURCE: ../../../../../../.opencode/skills/sk-doc/sk-create-chart/SKILL.md:134] [SOURCE: context/evilcharts/LICENSE:1]

**F5-3. The install model is incommensurable by design, and that is the finding.** evilcharts' delivery is a dependency graph resolved by a package manager; the corpus's delivery is one file that is itself the whole install. Nothing in the evilcharts mechanics (registry envelope, item JSON, CLI resolution, target paths) maps onto the corpus, and nothing should: the corpus's equivalent "consumer contract" is the template contract's fourteen rules, and its equivalent "registry manifest" is `catalog.md`, which the corpus check reads in both directions exactly like the shadcn CLI reads registry items. The two systems already have the same shape: a manifest of named items, each with declared data requirements and a resolved file. [SOURCE: context/evilcharts/registry.json:1] [SOURCE: ../../../../../../.opencode/skills/sk-doc/sk-create-chart/references/catalog.md:36-38] [SOURCE: ../../../../../../.opencode/skills/sk-doc/sk-create-chart/references/template-contract.md:148-167]

**F5-4. The per-chart docs surface is the one thing evilcharts has that the corpus does not, and the corpus's catalog already covers its purpose.** evilcharts ships one docs page per chart type (installation steps, component preview, source tab, API reference, examples grid). The corpus's catalog row carries the data shape and ceiling per form, the contract carries the authoring rules, and `assets/examples/` carries one delivery per family. The purpose of evilcharts' docs pages — "what will I get and what do I need to know before I use it" — is served. A per-template API-reference page would duplicate the catalog row. [SOURCE: context/evilcharts/src/content/docs/recharts/installation.mdx:1-50] [SOURCE: ../../../../../../.opencode/skills/sk-doc/sk-create-chart/references/catalog.md:69-76] [SOURCE: ../../../../../../.opencode/skills/sk-doc/sk-create-chart/references/catalog.md:112]

**F5-5. The corpus validator is the corpus's "registry build", and it is already stricter than evilcharts' generation step.** `build-registry.mts` regenerates manifests and preview indexes; `check-corpus.cjs` validates every template against fourteen enforced rules *and* renders it headlessly, and prints the palette block to paste when a template drifts. evilcharts' pipeline checks that manifests resolve; the corpus's checks that the artifact is honest. No adoption needed. [SOURCE: context/evilcharts/src/scripts/build-registry.mts:1] [SOURCE: ../../../../../../.opencode/skills/sk-doc/sk-create-chart/references/template-contract.md:189-201]

**F5-6. Consolidated verdict audit.** Every "ADOPT WITH ATTRIBUTION" verdict from iterations 1-4 is re-checked against `SKILL.md:134`: none survives as code-copy; all survive as re-authored ideas. The full ranked list for the synthesis therefore carries exactly one attribution question (background patterns) and it is answered by the operator's stance on the NEVER clause, not by the licence.

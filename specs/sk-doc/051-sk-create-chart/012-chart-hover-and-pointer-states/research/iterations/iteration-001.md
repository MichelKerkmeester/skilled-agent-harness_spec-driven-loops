## Findings

**F1 — The corpus is 21 forms, and the predecessor's 7/7/7 tier table replicates exactly (measured).** Independent grep of the five pointer markers plus the wider signal set reproduces the spec's §2 table exactly: tier-1 (real hover, 5-6 markers) = `box-plot, calendar-grid, candlestick, distribution-strip, heat-matrix, scatter, treemap`; tier-2 (partial: 1-2 markers) = `parallel-axes, stacked-bars, stacked-area, grouped-bars, bar-line-composed, daily-line, waterfall`; tier-0 (zero markers) = `bar-columns, bar-rows, daily-range, independent-percentages, progress-single, unit-grid, unit-ring`. Evidence: `grep -c` across `.opencode/skills/sk-doc/sk-create-chart/assets/templates/*.html`, two independent signal sets, both runs landing 7/7/7. The prompt pack's "twenty forms" and "thirteen currently-inert" are both off: 21 forms; 14 lack a tooltip (7 partial + 7 zero-marker); 7 have nothing at all.

**F2 — Every template already ships a machine-readable pointer-contract surface, and the checker already reads it — the actual gap is the missing fourth register.** `check-corpus.cjs` line 1130: `INTERACTION_REGISTERS = ['data-chart-tooltip', 'data-chart-legend', 'data-chart-dim']` — "The three attributes a form declares when it answers a pointer" (comment, line 1127). The same section enforces the narrowed focus ring (`HYGIENE_RULE = /:focus\s*:not\(\s*:focus-visible\s*\)/`, line 1131: dropped for clicks, kept for tab) and errors when an `<svg>` lacks `aria-labelledby` or points it at nothing (lines 817-824). So REQ-004's "carried by a shared surface, not hand-applied" is already partly mechanised. What the vocabulary lacks: an **inert** register. REQ-001 requires "a contract of 'inert' names the reason the static figure already suffices" — but there is no fourth attribute for it, and the seven tier-0 forms carry zero interaction signals (measured), so the checker is silent on exactly the seven forms whose contracts the packet exists to record. That is the concrete checker work.

**F3 — The reference-implementation pointer mechanism, as read.** `box-plot.html` binds ONE delegated `pointermove` and ONE `pointerleave` on the whole `svg` (lines 390, 395) plus a document-level `click` for dismissal (lines 400, 410) — no per-mark listeners. The readout is one tooltip built once and refilled per hover ("built once and refilled on each hover so a pointer crossing the plot does" [not thrash], comment line 235), an SVG `<g data-chart-tooltip id="tip-box-plot">` (line 161) whose visibility is CSS: `opacity: 0 → 1` keyed on `[data-open]`, `transition: opacity 0.2s ease` (line 130-131), with `transition: none` inside what the surrounding reduced-motion media block carries (line 149). Decorative strokes — whiskers, median — are excluded from hit-testing by `pointer-events: none` (lines 138-140): overlap resolved by avoidance, not by nearest-mark resolution. Registration is opt-in per mark ("A mark answers a pointer only once it is registered here", line 273). No crosshair, no axis readout, no snapping, no focusable marks.

Firm: **progress-single is correctly-inert.** It is the spec's own edge case ("A single-datum chart, where a tooltip may duplicate a label already printed beside the mark"): the datum is printed at 56px beside the track, the goal, the share and the pace comparison are each printed in the figure, and the value + comparison are repeated in a `data-chart-table` whose caption the `desc` points at ("The table below the chart carries both figures as text"). A tooltip there would restate the largest element on the page. Waterfall, though tier-2, is read: it answers a pointer natively (a `<title>` on every mark — "A native SVG tooltip... the browser draws it and a screen reader reads it as the mark's name", `waterfall.html` tip() comment) AND prints every movement above its step; its unresolved question is only whether the card should add what the figure does not print (the running total, the share of swing) or whether printed-delta + table is its correct terminal state. The other five tier-0 forms — unit-ring, unit-grid, independent-percentages, bar-columns, bar-rows — are counted, not read: their values are not printed in the figure (zero pointer markers, and the corpus draws labels via `node('text', ...)` whose presence varies), so needs-pointer vs correctly-inert is UNRESOLVED for them. What would confirm: reading each.

**F5 — The a11y posture already answers the keyboard question in principle, and the corpus already states it.** Every template's `desc` ends by pointing at the data table ("The table below the chart carries every step as text" — waterfall; "carries both figures as text" — progress-single), and all 21 templates carry `data-chart-table` (measured: `grep -l "data-chart-table" | wc -l` = 21 of 21; zero files without). So the keyboard/screen-reader equivalent of anything a pointer reveals already exists as the table — the constraint any new hover must satisfy is: **nothing a pointer reveals may become the only way to get that value**, because the table is the non-pointer readout. The open question is not whether the a11y posture breaks (it does not, structurally) but whether marks should ALSO become focusable — note: no `tabindex` in tier-1 or tier-0 (measured), six tier-2 forms carry exactly one focusability signal each (bar-line-composed, daily-line, grouped-bars, parallel-axes, stacked-area, stacked-bars = 1 hit each in the tabindex/aria-valuenoy count) — and whether that is the "widget-isation" the spec's open question warns against.

## Questions Answered

- **"Which of the thirteen forms with no pointer response should gain one, and which are correctly inert?"** — Progressed, not closed. (a) The premise's count is wrong: 14 forms lack a tooltip (7 + 7), not 13; 7 have no pointer response at all. (b) Of the seven zero-marker forms, progress-single is correctly-inert (read, firm); unit-ring, unit-grid, independent-percentages, bar-columns, bar-rows, and — wait, that is six, because progress-single is one of the seven — the remaining six are UNRESOLVED, counted only. Next iteration reads them.
- **"What hover technique transfers to a single self-contained file?"** — Substantially answered at the mechanism level, from the corpus's own tier-1 reference (not recalled): delegated `pointermove`/`pointerleave` at the svg root + one persistent, refilled readout + `data-open`/opacity + `pointer-events: none` on decoration + opt-in registration + reduced-motion opt-out. All of it already survives the no-framework constraint, because it IS the corpus's own dependency-free code.
- **"Does a hover-only affordance break the corpus accessibility posture?"** — No, structurally: the `data-chart-table` (21 of 21) is the non-pointer readout, and the `desc` names it. The remaining question is whether marks gain focusability, which the checker's hygiene rule (`:focus:not(:focus-visible)`) already anticipates.

Search usage signals now capture how people use results. They also record what people search or do next. This builds a reliable dataset. It does not change what users see. That dataset is intended to improve ranking in a future release. That ranking improvement makes the workflow easier to follow and easier to trust.

> Spec folder: `.opencode/specs/system-spec-kit/023-hybrid-rag-fusion-refinement/014-feedback-signal-pipeline` (Level 2)

## Why This Release

The signals need enough volume and validation first. Then they can safely influence ranking without introducing bias.

## What's New at a Glance

- **Five usage signal types are recorded after every search, in the background.** They capture which results were shown. They capture which results arrive with full content as citations. They record whether the next search rephrases or repeats the question. They also record whether a non-search tool runs shortly after. The signals are stored for later analysis. They do not affect what users see. Search results are ranked exactly the same way as before.
- **Follow-up searches reveal rephrased queries and retries.** Someone searches again with slightly different wording. That is a rephrased query. Someone repeats nearly the same search. That is a retry. Telling the two apart compares word overlap between consecutive searches. The searches must be in the same session.
- **The system remembers the most recent session and uses it as a fallback.** Many tools do not carry a session identifier. So a non-search tool run shortly after a search links back to that search. That holds even when the tool knows nothing about sessions.
- **Signal collection adds 0.03ms per search on average.** This is well within the 5ms budget. So search speed is unaffected.

## Upgrade

No migration required. Signal collection activates automatically. No configuration changes are needed.

This release brings 28 fixes.

- They cover concurrency safety, search performance and database query optimization.
- They also cover error recovery and dead code removal.
- The goal is to make the workflow easier to follow and easier to trust.

Several fixes protect operations from unsafe data.

- It protects operations from restore-time changes, duplicate shared-space ownership and stale merge data.
- It closes recovery paths that could leave partial data behind.

It cuts repeated work.

- It reduces repeated work in search.
- It reduces repeated work in database lookups.

> [!IMPORTANT]
> 1 change can break an existing setup. Read it before you update.
>
> 1. In-memory BM25 no longer runs by default. [BM25 Becomes Opt-In](#c-bm25-becomes-opt-in)

&nbsp;

## Why This Release

The problems surfaced under concurrent load and after failures.

- Redundant database work also made saves and searches slower.

## Concurrency Safety

#### Mutations Get an Immediate Rejection <a id="c-mutations-get-an-immediate-rejection"></a>

- A checkpoint restore can take seconds.
- During that time search indexes, text indexes and graph caches rebuild.
- Nothing prevented saves, index scans or bulk deletes during that window.
- So a save that landed mid-rebuild could leave the database in an inconsistent state.
- The restore now sets a maintenance barrier before it begins.
- It clears the barrier only after all rebuilds complete.
- Saves, index scans and bulk deletes can arrive in between.
- Each gets an immediate `E_RESTORE_IN_PROGRESS` rejection.
- Cleanup releases the barrier if the restore fails or crashes.

#### Only the Creator Becomes Owner <a id="c-only-the-creator-becomes-owner"></a>

- Two requests to create the same shared space could both report `created: true`.
- Both could bootstrap themselves as owners.
- Ownership now goes only to the request that actually creates the row.
- A conflict is handled as an update.
- It does not promote its caller to owner.

#### Merges Reject Stale Predecessors <a id="c-merges-reject-stale-predecessors"></a>

- Memory merges can wait seconds for an AI service to generate an embedding.
- Previously, a change or deletion during that wait could be overwritten using stale data.
- It could also be archived despite no longer existing.
- Before committing, the merge reloads the original inside the transaction.
- It compares its content hash and last-modified timestamp.
- A changed original aborts as `predecessor_changed`.
- A deleted or archived one aborts as `predecessor_gone`.
- Either result uses the normal save path instead.

#### Index Scans Reserve a Lease <a id="c-index-scans-reserve-a-lease"></a>

- The cooldown check used to separate checking the last scan time from updating it.
- So simultaneous requests could both start scans.
- The check and reservation now happen atomically in one database transaction.
- A fresh lease rejects another request.
- A crash-expiry timer frees the slot after 2 minutes if a scan process dies mid-way.

## Search Performance

These changes reduce redundant computation in the search pipeline.

Search results do not change.

The same queries return the same answers, just faster.

#### Fallback Work Runs Once <a id="c-fallback-work-runs-once"></a>

- When a search finds too few results, the system tries progressively looser fallback tiers.
- Previously, each tier reran candidate collection, score fusion and the full post-processing pipeline.
- The pipeline is now split into two phases.
- Collecting and fusing candidates still runs for each fallback tier.
- That builds up the candidate pool.
- Reranking, co-activation boosts, folder relevance, confidence filtering, context headers and token trimming run once.
- They run on the final merged candidate set, after the last tier is chosen.

#### Each Result Is Sized Once <a id="c-each-result-is-sized-once"></a>

- Response sizing used to estimate each result twice.
- It also serialized complex nested metadata each time.
- A per-request cache keyed by result ID stores one estimate per result.
- The estimator now counts known fields directly.

#### BM25 Becomes Opt-In <a id="c-bm25-becomes-opt-in"></a>

> [!WARNING]
> If you relied on the in-memory BM25 engine in addition to FTS5, set `ENABLE_BM25=true` to keep it active.

- SQLite's built-in FTS5 and the in-memory BM25 engine used to run by default.
- BM25 performed a synchronous full-table scan at startup.
- That blocked the server from accepting requests.
- It could also drift out of sync.
- It is now opt-in behind `ENABLE_BM25`.
- `ENABLE_BM25=true` enables BM25.
- FTS5 is the only text-search engine by default.
- When enabled, BM25 syncs only changed rows.
- It rebuilds during background warmup instead of blocking startup.

#### Graph Search Avoids Repeat Work <a id="c-graph-search-avoids-repeat-work"></a>

- Graph degree scoring previously ran one database query per candidate.
- It ran another query for the global maximum used in normalization.
- It now scores all candidates in one query.
- It caches the global maximum with per-node results.
- Graph text search could return the same edge through both directions of an OR-based join.
- It then removed duplicates in JavaScript.
- The query now finds matching memory IDs once.
- It checks edges from both directions without overlap.
- FTS-table availability is also cached per database connection to skip repeated checks.

#### Adaptive Fusion Skips Unused Work <a id="c-adaptive-fusion-skips-unused-work"></a>

- Adaptive fusion used to run standard fusion, adaptive fusion and a comparison.
- That happened even though production only needs adaptive weights.
- A lightweight helper now returns the weights alone.
- The pipeline builds its fusion lists once.
- The fusion lists are built once using those weights.
- It no longer performs and discards a full standard fusion.

#### Reranking Reuses Vectors <a id="c-reranking-reuses-vectors"></a>

- Vector search had already fetched each result's vectors for similarity comparisons.
- The diversity reranker fetched them again one at a time.
- Vector search now passes its vectors in a request-scoped cache.
- The reranker checks that cache.
- It queries the database only for missing vectors.
- The linear `reranked.find()` lookup was replaced with a Map for O(1) access.

## SQLite Query Optimization

#### Save Lookups Use Exact Scopes <a id="c-save-lookups-use-exact-scopes"></a>

- Each memory save checked three times for an existing record.
- The checks were by path, content hash and main path.
- Nullable scope predicates for tenant, user, agent, session and shared space prevented SQLite from using indexes.
- So each check scanned the full table.
- Lookups now include only scope columns present in the request, as exact matches.
- The combined main-path and file-path check is split into separate probes.
- Two new partial indexes serve main-path lookups and content-hash lookups with scope columns.
- Both are filtered to non-chunk rows.
- Save, trigger-cache and working-memory operations avoid unnecessary scans or checks.

#### Trigger Refreshes Avoid Full Scans <a id="c-trigger-refreshes-avoid-full-scans"></a>

- Every mutation used to rebuild the trigger-phrase cache.
- It scanned all successfully embedded memories that had trigger phrases.
- A targeted index now covers that set.
- The prepared query is cached per database connection.

#### Related Memories Load in Batches <a id="c-related-memories-load-in-batches"></a>

- The co-activation boost raises results related to other high-scoring results.
- It used to fetch each related memory individually.
- Causal neighbors needed separate lookups in each direction.
- Related-memory details now load in one batch.
- Causal neighbors use one joined lookup.
- Neighbor counts are prepared before boosting.
- Related lookups avoid repeated full-table reads.
- They use batched lookups.

#### Time Searches Narrow the Range <a id="c-time-searches-narrow-the-range"></a>

- Temporal proximity searches used to apply date functions to `created_at`.
- That prevented SQLite from using the index and forced a full-table scan.
- They now narrow the search with a range on the raw `created_at` value.
- Then they calculate time differences only for the narrowed results.
- A new composite index on `(spec_folder, created_at DESC)` makes that range scan fast.

#### File References Resolve in Batches <a id="c-file-references-resolve-in-batches"></a>

- Causal link resolution used leading-wildcard searches.
- Those could not use an index and scanned the full table.
- It now tries exact matches on `main_file_path` and `file_path` first.
- It falls back to fuzzy matching only when exact matching fails.
- It resolves all references in a document in one batch.

#### Working Memory Avoids Extra Queries <a id="c-working-memory-avoids-extra-queries"></a>

- Working memory tracks recently active memories per session.
- Its last-focused and attention-score orderings previously required sorting without matching indexes.
- Two indexes now align with those query orders.
- Upserting an entry also no longer runs a separate existence count first.
- That is because the conflict handling already covers insert and update.

## Error Recovery

#### Chunk Saves Fail Cleanly <a id="c-chunk-saves-fail-cleanly"></a>

- When a large file was split and indexed in chunks, a failure could return an error.
- The failure was marking the old version as superseded.
- That error came after the new chunks were committed.
- A retry could then create duplicate chunks.
- The old version remained active.
- Superseding now shares the chunk commit's final transaction.
- If superseding fails, cleanup removes the newly created parent and child rows.
- That happens before the error returns.
- No orphaned data is left, and a clean retry is possible.

#### Safe Swaps Stay Transactional <a id="c-safe-swaps-stay-transactional"></a>

- During a safe swap, old chunk children used to be deleted after the transaction committed.
- If deletion failed, the old children could remain beside the new ones.
- They would be orphaned records.
- Deletion now happens in the finalization transaction.
- That transaction rolls back on failure and leaves the old version intact.

#### Search Updates Wait for Successful Chunks <a id="c-search-updates-wait-for-successful-chunks"></a>

- Chunking used to update BM25 with the new parent summary before indexing the chunks.
- If every chunk failed, the database restored the old parent.
- BM25 kept the new summary.
- That hid the old parent's content from word searches until a full rebuild.
- BM25 updates now wait until at least one chunk succeeds.
- So an all-failed fallback leaves its text index untouched.

#### Failed Search Repairs Can Be Retried <a id="c-failed-search-repairs-can-be-retried"></a>

- A merge could commit while updating the text-search index failed.
- The merged memory then stayed unavailable to word searches.
- The failure used to be logged but not recorded durably for later repair.
- A persisted `bm25_repair_needed` flag on the merged row now records the failed repair.
- A future reconciliation process or manual repair tool can use it.

## Dead Code Cleanup

These changes remove unused code.

That code increases maintenance burden and confuses code navigation.

#### Startup Warmup That Never Ran <a id="c-startup-warmup-that-never-ran"></a>

- Server startup held an eager warmup branch for embedding models.
- A helper fixed to return `false` guarded it.
- Nothing could ever reach that code.
- Both the dead code branch and the always-false helper were removed.

#### Unused Exports and Proxies Removed <a id="c-unused-exports-and-proxies-removed"></a>

- `tools/types.ts` exported `MCPResponseWithContext` and `parseValidatedArgs`.
- Nothing imported either one.
- The handler barrel `handlers/index.ts` exported 9 lazy module proxies.
- All actual handler usage goes through its named function exports.
- The two unused exports and all 9 proxies were removed.
- The named function exports that are actually used remain unchanged.

#### Debug and Type Exports Retired <a id="c-debug-and-type-exports-retired"></a>

- The trigger matcher and shadow scoring each carried a debug helper.
- Each was exported during development.
- No production or test code called either one.
- Three type exports also had zero imports across the codebase.
- They are `PipelineOrchestrator` from pipeline types, `InterferenceResult` from interference scoring and `SurrogateMatchResult` from query surrogates.
- Both debug helpers and all three type exports were removed.

#### Test Suite Drops Its Shim <a id="c-test-suite-drops-its-shim"></a>

- The shared memory handler tests sat in `shared-memory-handlers.test-suite.ts`.
- That is not the standard `.vitest.ts` extension.
- So a one-line shim (`shared-memory.vitest.ts`) existed.
- Its only job was to re-export the test suite so Vitest could find it.
- The test file was renamed `shared-memory-handlers.vitest.ts`.
- The shim file was deleted.

#### Score Resolution Lives in One Place <a id="c-score-resolution-lives-in-one-place"></a>

- One function decides which score field to use for a search result.
- It was defined in three places.
- `pipeline/types.ts` held the main version.
- `confidence-scoring.ts` and `profile-formatters.ts` each held a copy.
- Both copies now import the main version instead of defining their own.

## Upgrade Notes

The schema moves from version 21 to 24. It adds 6 new indexes and a new `bm25_repair_needed` column on `memory_index`. These changes are backward-compatible. They migrate automatically on startup, so no schema migration is required.

#### Before You Start <a id="c-before-you-start"></a>

- The schema migrates automatically on startup.
- No schema migration is required.

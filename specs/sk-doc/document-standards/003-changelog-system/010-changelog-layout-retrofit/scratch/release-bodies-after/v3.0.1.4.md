# v3.0.1.4, Changelog Publishing

The create:changelog command now publishes releases for you.

- Previously you made the changelog and the release as separate manual steps.
- Now the command handles the whole release flow.
- That flow is changelog creation, git tagging and GitHub release publishing.
- The --release flag does all of it.

Release note writing now has one standalone template.

- Previously the format lived in inline code inside workflow files.
- There was no single source of truth for that format.
- The template defines two formats based on how many changes a release contains.

The release workflows and guide share the same rules.

- Category headings use plain names instead of generic labels.
- The git-finish workflow points to the guided release command.

&nbsp;

## Why This Release

Publishing a release used to take several manual steps. The format for release notes was scattered across workflow files. There was no single place that defined it.

- You created a changelog, then a git tag, by hand.
- You pushed the tag and ran the GitHub CLI for the release page.
- No single file said how to write the release notes.

## Commands

The create:changelog command now covers the full release flow. It builds the release body from the changelog and handles release failures.

#### Release publishing no longer needs manual steps <a id="c-release-publishing-no-longer-needs-manual-steps"></a>

- Previously you created the changelog file first.
- Then, separately, you created a git tag.
- You pushed the tag and ran the GitHub CLI.
- That made a release page with properly formatted notes.
- Now the create:changelog command does all of this.
- Add the --release flag to turn it on.
- It creates the tag and strips local-only header lines from the changelog.
- It publishes the release with correctly formatted notes.

#### Release notes come from the changelog <a id="c-release-notes-come-from-the-changelog"></a>

- The command reads the changelog it just created.
- It removes lines that belong only in the local file.
- Those are the title line, the project link and the date header.
- The command composes the notes automatically.
- The remaining content becomes the GitHub release body.
- A link back to the full changelog file is appended at the end.

#### Release failures are handled gracefully <a id="c-release-failures-are-handled-gracefully"></a>

- If the tag already exists, the command asks whether to update it.
- It also offers to bump the version.
- If the GitHub CLI is not authenticated, it tells you which login command to run.
- If a release page already exists for that tag, it offers to update it.
- It also offers to skip.

## Documentation

The changelog format and writing rules now live in one template. The workflows, the command docs and the public guide all reference it.

#### Changelog format now has a standalone template <a id="c-changelog-format-now-has-a-standalone-template"></a>

- Previously the format was inline in the YAML workflow files.
- You could not read or reference it on its own.
- A new template file defines two formats.
- A compact format uses bullet points for releases with fewer than 10 changes.
- An expanded format uses numbered sections with "Problem" and "Fix" paragraphs.
- That format suits larger or more important releases.
- Both YAML workflows and the release documentation now reference this single template.

#### Writing style rules are consistent across surfaces <a id="c-writing-style-rules-are-consistent-across-surfaces"></a>

- The YAML workflows point to the same template and style rules.
- The command documentation points to them too.
- The public release guide points to them as well.
- Category headings now use plain names.
- Those are Search, Security, Commands and Documentation.
- They replace the generic labels New, Changed and Fixed.

#### git-finish now mentions the guided alternative <a id="c-gitfinish-now-mentions-the-guided-alternative"></a>

- When you use the git-finish workflow, this changes.
- If you choose to create a release, it now tells you more.
- It points to the create:changelog command.
- That command is a structured alternative to the manual release steps.

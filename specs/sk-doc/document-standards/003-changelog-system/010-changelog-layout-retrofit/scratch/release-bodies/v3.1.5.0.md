This release brings twenty-two fixes. They cover the memory indexing pipeline and frontmatter compliance system. They also cover spec templates and search retrieval quality.

The `contextType` field controls how memories are classified, decayed and retrieved. It had the wrong default value ("decision"). It was hardcoded in six separate locations. Those spanned two codebases plus 41 template files. Every time the backfill script ran, it re-introduced the wrong value. It did so across hundreds of spec documents.

The reindex pipeline also had three false-positive validation rules. They silently blocked legitimate files from being indexed. This left 36 memory files invisible to search. Additionally, the `memory_context` search pipeline had six quality issues. Caller intent was silently dropped during strategy dispatch. Folder discovery used a hard WHERE filter instead of a soft boost. The token budget enforcement dropped entire results instead of truncating content. And low-confidence intent auto-detection distorted result ranking.

This release fixes all root causes. It migrates all existing data. It updates all templates. It removes 13,000 duplicate database rows. It improves search retrieval precision.

## What's New at a Glance

- 1. The cross-spec contamination validator no longer blocks bulk reindex.
  - During bulk reindex, the rule checked a file's body text. It looked for references to other spec IDs.
  - It read the `spec_folder` from the file's YAML frontmatter. This told it which spec the file belonged to.
  - But older memory files and all spec documents don't have this field. That includes spec.md, plan.md and checklist.md.
  - Without it, the validator saw `current_spec: unknown`.
  - It treated every cross-reference as contamination.
  - This blocked 1,106 files per reindex run.
  - When the frontmatter `spec_folder` field is empty, the validator now extracts the spec folder. It reads it from the file's path.
  - For example, `.opencode/specs/02--system-spec-kit/024-compact-code-graph/memory/foo.md` resolves to `02--system-spec-kit/024-compact-code-graph`.
  - The `filePath` parameter is threaded through the v-rule bridge and memory-save handler. This makes it possible.
- 2. The topical coherence rule no longer blocks memory and spec doc files.
  - The rule blocked indexing when a file's content had zero keyword overlap. It compared against the parent spec's trigger phrases.
  - This was too strict for memory files. They use different terminology than the spec.
  - It was also too strict for spec documents. They define the triggers themselves.
  - Six memory files were silently excluded from the search index.
  - The rule now skips the check entirely for files in `*/memory/` directories.
  - It also skips known spec document filenames. These are spec.md, plan.md, checklist.md, tasks.md, decision-record.md, implementation-summary.md, research.md and handover.md.
- 3. The template contract no longer rejects older files during force reindex.
  - Force reindex (`memory_index_scan` with `force: true`) rejected 90 memory files. They didn't match the current template format.
  - These files were created before the v2.2 template standard. They lack newer frontmatter fields or blank-line formatting.
  - When `force=true`, the quality gate uses `warn-only` mode for all files. Spec documents already did the same.
  - Template issues are logged as warnings but don't block indexing.
  - Interactive `memory_save` still enforces the full template contract.
- 4. Frontmatter defaults now use the correct `contextType` value.
  - The `frontmatter-migration.ts` module is used by both `create.sh` and the backfill script. It had three bugs.
  - `VALID_CONTEXT_TYPES` didn't include "planning". Any file with that value got rejected.
  - `DOC_DEFAULT_CONTEXT` mapped spec and plan documents to "decision". Downstream consumers don't recognize that value.
  - `normalizeContextType()` aliased "planning" back to "decision". This actively reversed any manual fix.
  - Every backfill run re-introduced the wrong value across all spec documents.
  - "planning" was added to `VALID_CONTEXT_TYPES`.
  - Defaults changed: spec→implementation, plan→planning, decision_record→planning.
  - The alias was reversed so "decision"→"planning". This migrates legacy values.
  - `inferContextType()` now overrides existing "decision" values instead of preserving them.
- 5. The MCP parser no longer reverses corrected context types.
  - The MCP server's memory parser (`memory-parser.ts`) had an independent copy of the context type mapping. It also mapped "planning" to "decision".
  - When files were reindexed, the parser converted the corrected frontmatter value back to the wrong one.
  - It did this before storing the value in the database.
  - `CONTEXT_TYPE_MAP` was updated to map "decision"→"planning" and "discovery"→"general".
  - "planning" was added to the `ContextType` TypeScript union.
- 6. The session extractor now returns corrected context types.
  - `detectContextType()` in `session-extractor.ts` returned "decision" when decisions were recorded.
  - It returned "discovery" for web-heavy sessions.
  - These values propagated into saved memory files.
  - It now returns "planning" for decision-heavy sessions.
  - It returns "research" for web-heavy sessions.
- 7. Four runtime consumers now use "planning" as the primary context type.
  - Four runtime systems used "decision" as a contextType value.
  - `intent-classifier.ts` weighted `find_spec` and `find_decision` intents toward "decision".
  - `save-quality-gate.ts` had a special exception for `context_type === 'decision'`.
  - `fsrs-scheduler.ts` treated "decision" as no-decay. It did so in the stability multiplier and hybrid decay policy.
  - `memory-state-baseline.ts` validated against a set that excluded "planning".
  - All four were updated to use "planning" as the primary value.
  - They accept "decision" as a legacy alias for backward compatibility.
- 8. The database schema now accepts "planning" as a context type.
  - The `context_type` column in `memory_index` had a CHECK constraint.
  - It only allowed 'research', 'implementation', 'decision', 'discovery' and 'general'.
  - Any attempt to store "planning" failed with a constraint violation.
  - The CHECK constraint in `vector-index-schema.ts` and `schema-downgrade.ts` was updated to include "planning".
  - The same constraint change was applied to the live database.
- 9. 2,009 rows with legacy values were migrated.
  - The live database had 2,006 entries with `context_type = 'decision'`.
  - It had 3 entries with `context_type = 'discovery'`.
  - These came from before the migration.
  - A direct SQL UPDATE migrated all legacy values: decision→planning, discovery→general.
- 10. 13,211 duplicate database rows were removed.
  - Each force reindex created new rows instead of updating existing ones.
  - After multiple reindex runs, the database had 14,415 rows.
  - Only 1,204 of those were unique file paths.
  - That was 92% waste.
  - This inflated search result counts and slowed queries.
  - All duplicate rows were deleted, keeping only the latest entry per file path.
  - The database went from 14,415 to 1,200 unique entries.
- 11. A backfill fixed frontmatter in 828 spec documents.
  - After fixing the source defaults, old values still remained. They were in the frontmatter YAML of all existing spec documents.
  - `backfill-frontmatter.js --apply --include-archive --allow-malformed` was run across all 2,383 spec documents.
  - This included archived folders.
  - 828 files were updated.
  - Zero files with `contextType: "decision"` remain anywhere in the codebase.
- 12. The context template now uses corrected detection logic.
  - The `context_template.md` pseudo-code for contextType detection returned "decision" for decision-heavy sessions.
  - It returned "discovery" for web-heavy sessions.
  - The comment on the `context_type` field listed "decision|discovery" as valid values.
  - Detection logic now returns "planning" and "research" respectively.
  - The field comment now lists "implementation|planning|research|general".
- 13. All 41 template files now use doc-type-specific context types.
  - Every template file in `templates/` used `contextType: "general"` regardless of document type.
  - These spanned level_1, level_2, level_3, level_3+, core and addendum directories.
  - When a new spec folder was created from these templates, the resulting files started with the wrong contextType.
  - Those files required a backfill pass to correct.
  - All 41 template files were updated to the correct doc-type-specific default.
  - spec.md→"implementation", plan.md→"planning", decision-record.md→"planning", checklist.md→"implementation", tasks.md→"implementation", implementation-summary.md→"implementation", research.md→"research".
  - README.md, handover.md and debug-delegation.md remain "general".
  - New spec folders now start with the correct value without needing a backfill.
- 14. Parser test expectations were updated to the new contract (Review P1-1).
  - The `memory-parser-extended.vitest.ts` test suite still expected `planning` to alias to `decision`.
  - It also expected `bug` to alias to `discovery`.
  - Three test assertions failed after the CONTEXT_TYPE_MAP change.
  - T06 canonical types changed to `['implementation', 'research', 'planning', 'general']`.
  - T07 aliases changed to `{ decision: 'planning', bug: 'implementation' }`.
  - T08 was added for explicit legacy value assertions.
- 15. The spec folder regex now matches single-level paths (Review P1-2).
  - The spec folder extraction regex required two-level nesting (`specs/track/NNN-name/`).
  - Single-level paths like `specs/001-feature/memory/foo.md` didn't match.
  - This left `current_spec: unknown` for files in single-level spec folders.
  - The regex changed from `/[/\]specs[/\](.+?[/\](?:\d{3}-[^/\]+))/` to `/[/\]specs[/\]((?:[^/\]+[/\])*\d{3}-[^/\]+)/`.
  - It now captures everything from `specs/` up to the last `NNN-` prefixed segment.
  - It matches both nested and single-level paths.
- 16. Regression tests were added for the reindex and save path (Review P1-6).
  - The exact reindex/save path that motivated the V8 and V12 fixes had no regression tests.
  - All existing validator tests called `validateMemoryQualityContent(content)` without the new `{ filePath }` option.
  - 3 tests were added to `validate-memory-quality.vitest.ts`.
  - V8 filePath fallback extracts the spec folder from the path when frontmatter `spec_folder` is empty.
  - V12 skips topical coherence for files in `*/memory/` directories.
  - V12 skips topical coherence for spec doc files (spec.md).
- 17. Deep, resume and focused strategies now forward caller intent (RC3-A).
  - `executeDeepStrategy()` and `executeResumeStrategy()` did not accept or forward the `intent` parameter.
  - When `memory_context` was called with `intent: "understand"`, the intent was detected at the top level.
  - It was never passed to the underlying `handleMemorySearch()` call.
  - The search handler re-ran intent detection. It often produced a different result.
  - For example, `fix_bug` at 0.098 confidence for a general "semantic search" query.
  - An `intent: string | null` parameter was added to both strategy functions.
  - `executeStrategy()` was updated to forward `args.intent`.
  - When an explicit intent is provided, `autoDetectIntent` is set to `false`.
  - This prevents re-detection.
  - `executeFocusedStrategy()` was also updated for consistency.
- 18. Folder discovery now retries without the folder filter (RC1-A).
  - When `maybeDiscoverSpecFolder()` detected a spec folder from the query text, it set `options.specFolder`.
  - This hard-filtered results to that folder only.
  - If no memories existed in the discovered folder, the search returned 0 results silently.
  - This held even though relevant memories existed in other folders.
  - After strategy execution, the handler checks the result count.
  - If the count is 0 and a folder was discovered, it clears `options.specFolder`.
  - The handler retries the search without the folder filter.
  - An `extractResultCount()` helper parses result count from the MCPResponse JSON envelope.
  - Recovery is tracked in response metadata.
- 19. Token budget enforcement now trims content before dropping results (RC2-B).
  - `enforceTokenBudget()` went straight to dropping lowest-scored results when the response exceeded the token budget.
  - A single result with a long `content` field could consume the entire 3,500-token budget.
  - This caused all other results to be dropped.
  - 20 candidates were reduced to 1.
  - Phase 1 was added to the budget enforcement.
  - It truncates `content` fields to 500 characters before dropping any results.
  - It sets `contentTruncated: true` on affected results for caller transparency.
  - It re-estimates tokens after truncation.
  - It only proceeds to Phase 2 (dropping lowest-scored results) if still over budget.
- 20. Folder discovery now boosts matching results instead of filtering them (RC1-B).
  - `maybeDiscoverSpecFolder()` set `options.specFolder`, which acted as a hard WHERE clause.
  - It excluded all memories outside the discovered folder.
  - This was too aggressive for general queries that happened to mention a spec name or keyword.
  - `maybeDiscoverSpecFolder()` now sets `options.folderBoost = { folder, factor }` instead of `options.specFolder`.
  - `folderBoost` was added to `ContextOptions` and `SearchArgs` interfaces.
  - After pipeline execution in `handleMemorySearch()`, results matching the discovered folder get a boost.
  - Their similarity score is multiplied by the boost factor.
  - The boost factor defaults to 1.3x, configurable via `SPECKIT_FOLDER_BOOST_FACTOR` env var.
  - The boosted score is capped at 1.0.
  - Results are re-sorted by boosted similarity.
  - Folder boost metadata is surfaced in `appliedBoosts.folder` in the response.
- 21. Dropped results now appear as metadata in the response (RC2-A).
  - When `enforceTokenBudget()` dropped results to fit the token budget, they were invisible to the caller.
  - The caller had no way to know that additional relevant memories existed.
  - Those memories were beyond what was returned.
  - Nor could callers request specific results by ID.
  - After Phase 2 dropping, Phase 3 collects dropped results.
  - It appends metadata-only entries.
  - The entries are `id`, `title`, `similarity`, `specFolder`, `confidence`, `importanceTier`, `isConstitutional`, `metadataOnly: true`.
  - They are appended if they fit within the remaining token budget.
  - The caller can see what was dropped.
  - Callers can request full content via `memory_search` with specific IDs if needed.
- 22. Low-confidence intent detection no longer distorts ranking (RC3-B).
  - The intent classifier sometimes auto-detected low-confidence intents.
  - For example, `fix_bug` at 0.098 confidence for a general "semantic search" query.
  - These detections applied intent-specific weight adjustments that distorted ranking.
  - They pushed irrelevant results to the top.
  - They buried actually relevant ones.
  - After auto-detection, if confidence is below `INTENT_CONFIDENCE_FLOOR`, the detection is overridden to `understand`.
  - The floor is 0.25, configurable via `SPECKIT_INTENT_CONFIDENCE_FLOOR` env var.
  - The override also needs no explicit intent from the caller.
  - The override sets confidence to 1.0.
  - Explicit caller-provided intents bypass the floor entirely.

## Upgrade

Run the backfill to fix frontmatter in your spec documents:
```bash
node .opencode/skill/system-spec-kit/scripts/dist/memory/backfill-frontmatter.js --apply --include-archive
```

Then force reindex to update the database:
```bash
node .opencode/skill/system-spec-kit/scripts/dist/memory/reindex-embeddings.js
```

For items 17-22 (search retrieval quality fixes), restart the MCP server to pick up the updated handlers:
```bash
# The MCP server will auto-compile TypeScript on restart
# No database migration needed, these are runtime behavior changes only
```

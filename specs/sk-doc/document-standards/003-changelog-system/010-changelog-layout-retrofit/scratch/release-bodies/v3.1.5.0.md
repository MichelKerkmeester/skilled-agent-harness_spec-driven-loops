Twenty-two fixes for the memory indexing pipeline, frontmatter compliance system, spec templates, and search retrieval quality. The `contextType` field -- which controls how memories are classified, decayed, and retrieved -- had the wrong default value ("decision") hardcoded in six separate locations across two codebases plus 41 template files. Every time the backfill script ran, it re-introduced the wrong value across hundreds of spec documents. The reindex pipeline also had three false-positive validation rules that silently blocked legitimate files from being indexed, leaving 36 memory files invisible to search. Additionally, the `memory_context` search pipeline had six quality issues: caller intent was silently dropped during strategy dispatch, folder discovery used a hard WHERE filter instead of a soft boost, the token budget enforcement dropped entire results instead of truncating content, and low-confidence intent auto-detection distorted result ranking. This release fixes all root causes, migrates all existing data, updates all templates, removes 13,000 duplicate database rows, and improves search retrieval precision.

> Spec folders: `.opencode/specs/02--system-spec-kit/023-esm-module-compliance/008-spec-memory-compliance-audit/` + `009-reindex-validator-false-positives/` + `010-search-retrieval-quality-fixes/` (Level 2, Phases 8-10)

---

## 1. Cross-Spec Contamination Validator, False Positive on Bulk Reindex

During bulk reindex, the cross-spec contamination rule checked whether a file's body text referenced other spec IDs. It read the `spec_folder` from the file's YAML frontmatter to know which spec the file belonged to. But older memory files and all spec documents (spec.md, plan.md, checklist.md) don't have this field. Without it, the validator saw `current_spec: unknown` and treated every cross-reference as contamination -- blocking 1,106 files per reindex run. When the frontmatter `spec_folder` field is empty, the validator now extracts the spec folder from the file's path (e.g., `.opencode/specs/02--system-spec-kit/024-compact-code-graph/memory/foo.md` resolves to `02--system-spec-kit/024-compact-code-graph`). The `filePath` parameter is threaded through the v-rule bridge and memory-save handler to make this possible.

---

## 2. Topical Coherence Validator, Blocked Memory and Spec Doc Files

The topical coherence rule blocked indexing when a file's content had zero keyword overlap with the parent spec's trigger phrases. This is too strict for memory files (which use different terminology than the spec) and spec documents (which define the triggers themselves). Six memory files were silently excluded from the search index. The rule now skips the check entirely for files in `*/memory/` directories and for known spec document filenames (spec.md, plan.md, checklist.md, tasks.md, decision-record.md, implementation-summary.md, research.md, handover.md).

---

## 3. Template Contract Enforcement, Rejected Older Files During Force Reindex

Force reindex (`memory_index_scan` with `force: true`) rejected 90 memory files because they don't match the current template format. These files were created before the v2.2 template standard and are missing newer frontmatter fields or blank-line formatting. When `force=true`, the quality gate uses `warn-only` mode for all files -- same as spec documents already did. Template issues are logged as warnings but don't block indexing. Interactive `memory_save` still enforces the full template contract.

---

## 4. Frontmatter Defaults, Source of Truth Used Wrong contextType

The `frontmatter-migration.ts` module (used by both `create.sh` and the backfill script) had three bugs: (1) `VALID_CONTEXT_TYPES` didn't include "planning", so any file with that value got rejected. (2) `DOC_DEFAULT_CONTEXT` mapped spec and plan documents to "decision" -- a value that downstream consumers don't recognize. (3) `normalizeContextType()` aliased "planning" back to "decision", actively reversing any manual fix. Every backfill run re-introduced the wrong value across all spec documents. Added "planning" to `VALID_CONTEXT_TYPES`. Changed defaults: spec→implementation, plan→planning, decision_record→planning. Reversed the alias so "decision"→"planning" (migrating legacy values). `inferContextType()` now overrides existing "decision" values instead of preserving them.

---

## 5. MCP Parser, CONTEXT_TYPE_MAP Had Same Bug

The MCP server's memory parser (`memory-parser.ts`) had an independent copy of the context type mapping that also mapped "planning" to "decision". When files were reindexed, the parser converted the corrected frontmatter value back to the wrong one before storing it in the database. Updated `CONTEXT_TYPE_MAP` to map "decision"→"planning" and "discovery"→"general". Added "planning" to the `ContextType` TypeScript union.

---

## 6. Session Extractor, detectContextType Returned "decision"

`detectContextType()` in `session-extractor.ts` returned "decision" when decisions were recorded and "discovery" for web-heavy sessions. These values propagated into saved memory files. Returns "planning" for decision-heavy sessions and "research" for web-heavy sessions.

---

## 7. Runtime Consumers, Four More Locations Referenced "decision"

Four runtime systems used "decision" as a contextType value: (1) `intent-classifier.ts` weighted `find_spec` and `find_decision` intents toward "decision". (2) `save-quality-gate.ts` had a special exception for `context_type === 'decision'`. (3) `fsrs-scheduler.ts` treated "decision" as no-decay in both the stability multiplier and hybrid decay policy. (4) `memory-state-baseline.ts` validated against a set that excluded "planning". All four updated to use "planning" as the primary value, with "decision" accepted as a legacy alias for backward compatibility.

---

## 8. Database Schema, CHECK Constraint Missing "planning"

The `context_type` column in `memory_index` had a CHECK constraint that only allowed 'research', 'implementation', 'decision', 'discovery', 'general'. Any attempt to store "planning" failed with a constraint violation. Updated the CHECK constraint in `vector-index-schema.ts` and `schema-downgrade.ts` to include "planning". Applied the same constraint change to the live database.

---

## 9. Database Migration, 2,009 Rows With Legacy Values

The live database had 2,006 entries with `context_type = 'decision'` and 3 with `context_type = 'discovery'` from before the migration. Direct SQL UPDATE migrated all legacy values: decision→planning, discovery→general.

---

## 10. Database Deduplication, 13,211 Duplicate Rows

Each force reindex created new rows instead of updating existing ones. After multiple reindex runs, the database had 14,415 rows but only 1,204 unique file paths -- 92% waste. This inflated search result counts and slowed queries. Deleted all duplicate rows, keeping only the latest entry per file path. Database went from 14,415 to 1,200 unique entries.

---

## 11. Retroactive Backfill, 828 Spec Documents Fixed

After fixing the source defaults, all existing spec documents still had the old values in their frontmatter YAML. Ran `backfill-frontmatter.js --apply --include-archive --allow-malformed` across all 2,383 spec documents including archived folders. 828 files were updated. Zero files with `contextType: "decision"` remain anywhere in the codebase.

---

## 12. Context Template, Detection Logic Updated

The `context_template.md` pseudo-code for contextType detection returned "decision" for decision-heavy sessions and "discovery" for web-heavy sessions. The comment on the `context_type` field listed "decision|discovery" as valid values. Updated detection logic to return "planning" and "research" respectively. Updated the field comment to list "implementation|planning|research|general".

---

## 13. Templates, All 41 Template Files Had Wrong Default

Every template file in `templates/` (across level_1, level_2, level_3, level_3+, core, and addendum directories) used `contextType: "general"` regardless of document type. When a new spec folder was created from these templates, the resulting files started with the wrong contextType and required a backfill pass to correct. Updated all 41 template files to use the correct doc-type-specific default: spec.md→"implementation", plan.md→"planning", decision-record.md→"planning", checklist.md→"implementation", tasks.md→"implementation", implementation-summary.md→"implementation", research.md→"research". README.md, handover.md, and debug-delegation.md remain "general". New spec folders now start with the correct value without needing a backfill.

---

## 14. Parser Tests, Expectations Still Encoded Old Contract (Review P1-1)

The `memory-parser-extended.vitest.ts` test suite still expected `planning` to alias to `decision` and `bug` to alias to `discovery`. Three test assertions failed after the CONTEXT_TYPE_MAP change. Updated T06 canonical types to `['implementation', 'research', 'planning', 'general']`. Updated T07 aliases to `{ decision: 'planning', bug: 'implementation' }`. Added T08 for explicit legacy value assertions.

---

## 15. Regex Fallback, Single-Level Spec Paths Not Matched (Review P1-2)

The spec folder extraction regex required two-level nesting (`specs/track/NNN-name/`). Single-level paths like `specs/001-feature/memory/foo.md` didn't match, leaving `current_spec: unknown` for files in single-level spec folders. Changed regex from `/[/\]specs[/\](.+?[/\](?:\d{3}-[^/\]+))/` to `/[/\]specs[/\]((?:[^/\]+[/\])*\d{3}-[^/\]+)/`. Now captures everything from `specs/` up to the last `NNN-` prefixed segment, matching both nested and single-level paths.

---

## 16. Test Coverage, No Tests for filePath Fallback or V12 Skip (Review P1-6)

The exact reindex/save path that motivated the V8 and V12 fixes had no regression tests. All existing validator tests called `validateMemoryQualityContent(content)` without the new `{ filePath }` option. Added 3 tests to `validate-memory-quality.vitest.ts`: (1) V8 filePath fallback extracts spec folder from path when frontmatter `spec_folder` is empty. (2) V12 skips topical coherence for files in `*/memory/` directories. (3) V12 skips topical coherence for spec doc files (spec.md).

## 17. Intent Propagation -- Deep/Resume Strategies Ignored Caller Intent (RC3-A)

`executeDeepStrategy()` and `executeResumeStrategy()` did not accept or forward the `intent` parameter. When `memory_context` was called with `intent: "understand"`, the intent was detected at the top level but never passed to the underlying `handleMemorySearch()` call. The search handler re-ran intent detection, often producing a different result (e.g., `fix_bug` at 0.098 confidence for a general "semantic search" query). Added `intent: string | null` parameter to both strategy functions. Updated `executeStrategy()` to forward `args.intent`. When an explicit intent is provided, `autoDetectIntent` is set to `false`, preventing re-detection. The `executeFocusedStrategy()` was also updated for consistency.

---

## 18. Folder Discovery Recovery -- Zero Results When Folder Narrowing Fails (RC1-A)

When `maybeDiscoverSpecFolder()` detected a spec folder from the query text, it set `options.specFolder` which hard-filtered results to that folder only. If no memories existed in the discovered folder, the search returned 0 results silently -- even though relevant memories existed in other folders. After strategy execution, if the result count is 0 and a folder was discovered, the handler clears `options.specFolder` and retries the search without the folder filter. Added `extractResultCount()` helper to parse result count from the MCPResponse JSON envelope. Recovery is tracked in response metadata.

---

## 19. Adaptive Content Truncation -- Token Budget Dropped Results Too Aggressively (RC2-B)

`enforceTokenBudget()` went straight to dropping lowest-scored results when the response exceeded the token budget. A single result with a long `content` field could consume the entire 3,500-token budget, causing all other results to be dropped (20 candidates reduced to 1). Added Phase 1 to the budget enforcement: truncate `content` fields to 500 characters before dropping any results. Sets `contentTruncated: true` on affected results for caller transparency. Re-estimates tokens after truncation. Only proceeds to Phase 2 (dropping lowest-scored results) if still over budget.

---

## 20. Folder Discovery as Boost Signal -- Hard Filter Replaced with Soft Boost (RC1-B)

`maybeDiscoverSpecFolder()` set `options.specFolder` which acted as a hard WHERE clause in the search pipeline, excluding all memories outside the discovered folder. This was too aggressive for general queries that happened to mention a spec name or keyword. Changed `maybeDiscoverSpecFolder()` to set `options.folderBoost = { folder, factor }` instead of `options.specFolder`. Added `folderBoost` to `ContextOptions` and `SearchArgs` interfaces. After pipeline execution in `handleMemorySearch()`, results matching the discovered folder get their similarity score multiplied by the boost factor (default 1.3x, configurable via `SPECKIT_FOLDER_BOOST_FACTOR` env var), capped at 1.0. Results are re-sorted by boosted similarity. Folder boost metadata is surfaced in `appliedBoosts.folder` in the response.

---

## 21. Two-Tier Metadata+Content Response -- Dropped Results Invisible to Caller (RC2-A)

When `enforceTokenBudget()` dropped results to fit the token budget, those results were completely invisible to the caller. The caller had no way to know that additional relevant memories existed beyond what was returned, nor could they request specific results by ID. After Phase 2 dropping, Phase 3 collects dropped results and appends metadata-only entries (`id`, `title`, `similarity`, `specFolder`, `confidence`, `importanceTier`, `isConstitutional`, `metadataOnly: true`) if they fit within the remaining token budget. The caller can see what was dropped and request full content via `memory_search` with specific IDs if needed.

---

## 22. Intent Confidence Floor -- Low-Confidence Auto-Detection Distorted Ranking (RC3-B)

The intent classifier sometimes auto-detected low-confidence intents (e.g., `fix_bug` at 0.098 confidence for a general "semantic search" query). These low-confidence detections applied intent-specific weight adjustments that distorted ranking, pushing irrelevant results to the top while burying actually relevant ones. After auto-detection, if confidence is below `INTENT_CONFIDENCE_FLOOR` (0.25, configurable via `SPECKIT_INTENT_CONFIDENCE_FLOOR` env var) and no explicit intent was provided by the caller, the detection is overridden to `understand` with confidence 1.0. Explicit caller-provided intents bypass the floor entirely.

```bash
node .opencode/skill/system-spec-kit/scripts/dist/memory/backfill-frontmatter.js --apply --include-archive
```

Then force reindex to update the database:
```bash
node .opencode/skill/system-spec-kit/scripts/dist/memory/reindex-embeddings.js
```

For items 17-22 (search retrieval quality fixes), restart the MCP server to pick up the updated handlers:
```bash
# The MCP server will auto-compile TypeScript on restart
# No database migration needed, these are runtime behavior changes only
```

# Iteration 1: Command and bridge inventory

## Focus

Angle 1 (inventory): enumerate what the repository actually ships as commands, what the advisor's bridge inventory contains, and where the two disagree. Selected because every later angle (scoring, output contract, run-or-ask, invocation) depends on knowing which commands the advisor can even name. Deferred: the drift-proof inventory *design* (angle 1, second half) until the drift guards in `runtime/tests/command-bridges-drift-guard.vitest.ts` are read; the count comparison below is evidence for it, not the design itself.

## Actions Taken

1. Enumerated the command tree and counted command markdown files per group.
2. Read the bridge allow-list and the generated bridge inventory, then diffed bridge `command` values against the command tree in both directions.
3. Read the bridge generator's source-sum and per-runtime `enabled` handling.
4. Read `render.ts`'s recommendation labelling to see what a non-doctor bridge id renders as.

## Findings

1. `.skilled/commands` holds exactly 45 command markdown files, grouped as 13 `create/`, 3 `deep/`, 3 `design/`, 17 `doctor/`, 1 `local-skilled-alignment.md`, 1 `prompt/improve.md`, and 7 `speckit/` [SOURCE: .skilled/commands/speckit/plan.md:1]. A naive recursive walk over the tree reports 90 files because `doctor/scripts/tests/fixtures/**` contains fixture "commands" that are not commands; any inventory count must exclude fixture paths or it doubles the denominator [SOURCE: .skilled/commands/doctor/scripts/tests/fixtures/sk-skill-check/hubs/hub-gap/SKILL.md:1].

2. The bridge inventory is generated by summing three sources — 19 entries from the three hub `command-metadata.json` files, 8 from `allow-list.json`, and 35 from `doctor/_routes.yaml` — for 62 entries covering 43 distinct command strings [SOURCE: .skilled/skills/system-skill-advisor/runtime/scripts/command-bridges/command-bridges.generated.json:1]. The `counts` block states this explicitly: `commandMetadata: 19, allowList: 8, doctorRoutes: 35, generated: 62` [SOURCE: .skilled/skills/system-skill-advisor/runtime/scripts/command-bridges/command-bridges.generated.json:1].

3. Only three hubs declare `command-metadata.json` at all — `system-deep-loop`, `sk-design`, `sk-doc` — so nine of the command groups reach the inventory only through hand-maintained allow-list entries or doctor routes [SOURCE: .skilled/skills/sk-doc/command-metadata.json:1].

4. Five shipped commands have no bridge entry under their own command string: `/local-skilled-alignment`, `/prompt:improve`, `/speckit:handoff`, `/speckit:save`, `/speckit:search` [SOURCE: .skilled/commands/speckit/handoff.md:1]. `/prompt:improve` is reachable only through the legacy `/prompt` id in the allow-list, whose own `reason` field says the Python scorer "still recognizes legacy /prompt while JSON declares /prompt:improve" [SOURCE: .skilled/skills/system-skill-advisor/runtime/scripts/command-bridges/allow-list.json:51].

5. Three bridge commands have no command file at all: `/memory:save` (two ids: `command-memory-save` and `memory:save`), `/prompt`, and the deprecated `/spec_kit` [SOURCE: .skilled/skills/system-skill-advisor/runtime/scripts/command-bridges/allow-list.json:37]. The allow-list's `/spec_kit` reason says the deprecated generic bridge "remains live for one-release compatibility", and `command-memory-save` reasons that `system-spec-kit` "has no command-metadata.json yet" [SOURCE: .skilled/skills/system-skill-advisor/runtime/scripts/command-bridges/allow-list.json:41].

6. The TypeScript scorer enables only 40 of the 62 entries, and 22 distinct commands therefore have no TS-enabled bridge: all 11 `/create:*` commands except `agent` and `manual-testing-playbook`, `/deep:ai-council`, `/deep:research`, `/deep:review`, `/design:chart`, `/design:diagram`, `/design:extract`, `/prompt`, and `/speckit:complete|implement|plan|resume` [SOURCE: .skilled/skills/system-skill-advisor/runtime/scripts/command-bridges/command-bridges.generated.json:1]. The Python scorer enables 50. Overlap with the spec's measured behavior is exact: the two prompts that returned no recommendation in the spec (`plan a new feature…`, `research how our retrieval scoring works…`) belong to the two groups whose bridges are TS-disabled [SOURCE: specs/system-skill-advisor/routing-and-scoring/007-command-surfacing-and-workflow-enforcement/spec.md:43].

7. Ten command strings carry multiple bridge ids, all of them doctor routes, e.g. `/doctor:skill-advisor` → six ids (`…-tune`, `…-rebuild`, `…-skill-budget`, `…-skill-graph-freshness`, `…-router-reach`, `…-parent-skill`) [SOURCE: .skilled/commands/doctor/_routes.yaml:1]. So bridge ids are finer-grained than commands: one doctor command fronts 2-6 routable subcommands, while every other command is one id — a per-id recommendation surface cannot be turned into a per-command contract without a grouping key.

8. The brief has exactly one runnable-string path, and it is doctor-only: `recommendationLabel()` returns `doctorCommandString(skillId)` when the id starts with `command-doctor-`, else `sanitizeSkillLabel(skillId)` — the raw id — and the runnable strings come from a 35-entry hand-generated map `DOCTOR_COMMAND_STRINGS` [SOURCE: .skilled/skills/system-skill-advisor/runtime/lib/render.ts:228]. The map's own comment says it is "Generated by derive-command-bridges.cjs from the doctor route manifest" [SOURCE: .skilled/skills/system-skill-advisor/runtime/lib/render.ts:109].

9. The recommendation payload already carries a `kind` field with a `command` variant internally — `kind: recommendation.kind === 'command' ? 'command' : 'skill'` — but nothing in the inventory model marks a bridge as a command kind; the field is only a rendering-time widening of what callers passed in [SOURCE: .skilled/skills/system-skill-advisor/runtime/lib/render.ts:253].

## Ruled Out

- Counting commands by recursive `find`: reports 90 vs the real 45 because the doctor fixture tree contains SKILL/ROUTER markdown. Rejected as an inventory method; group-level enumeration is the reliable count.
- Treating the 62 bridge entries as "62 commands": entries over-count doctor subcommands and under-count five shipped commands. Rejected; command strings, not ids, are the unit that must be covered.

## Reflection

- What worked and why: diffing the generated inventory against the command tree in both directions surfaced both failure shapes at once — commands with no bridge (5) and bridges with no command (3). Counting per-runtime `enabled` rather than trusting `generated: 62` explained the spec's measured zero-recommendation result without running the CLI.
- What did not work and why: the first recursive file walk produced 90 "commands" because the doctor fixture tree is shaped like command folders. The count was wrong in a way that would have inflated every later coverage ratio; excluding fixture paths fixed it.
- What I would do differently: read `derive-command-bridges.cjs`'s `enabled` derivation *before* computing coverage, so the per-runtime table and the disabled-id list come from one read instead of two.

## 7. WHAT WORKED
- reading the run line for the exact row turned a dispatcher anecdote into a checkable fact (offer kind, policy, delivery) and exposed the gap between "offered" and "did". Reading the mention reader beside the depth vocabulary explained the refusal row without a model run. (iteration 1)
- counting the offers per row rather than reading the aggregate made the guard's blind spot measurable; the aggregate `startedOfOffered` would have hidden it because decline rows have no expected command to count against. (iteration 2)
- putting the byte split beside the per-policy start spread turned a wording question into a disconfirmation. If the brief were the binding constraint, the identical bytes would not produce 0 of 10 on Claude and 7 of 10 on dsh. (iteration 3)
- separating the recorded count (023) from the mechanism (typed-command-only guard) kept the lane from re-selling a known number as a discovery, and the row-by-row attribution made each recommendation measurable. (iteration 4)
- checking the root doc before the render falsified one of this lane's own findings, which is the cheapest kind of correction the lane can make; a recommendation built on it would have spent bytes for nothing. (iteration 5)
- counting per row instead of trusting the aggregate exposed the strongest number in this lane — 7 of 20 offers, identical everywhere — and the depth gate's inversion fell out of the same pass. (iteration 6)
- pairing a code or corpus source with a measured source per claim caught that the attention inference had only one class, which is why it is excluded rather than promoted. (iteration 7)

<!-- ANCHOR:what-failed -->
## 8. WHAT FAILED
- the summary JSON does not carry per-row model actions, so the started-command claim cannot be verified from the packet's own files; the run line's `offeredAs` is not a behaviour record. (iteration 1)
- the summary's `offered` field is scoped to rows with an expected command, so it reads 5 while the run lines carry far more offers; using it as an offer count would have been wrong. (iteration 2)
- the 015 live-head capture is pre-016 and cannot stand in for HEAD; it was used only for head shape, not for a current count. (iteration 3)
- the sealed fit sample cannot be joined to the fresh sample without printing sealed text, so the two decline rates cannot be pooled honestly. (iteration 4)
- iteration 2's paraphrase of the question text cost the registry a match and left a question open for three iterations. Exact text is not cosmetic in this machinery. (iteration 5)
- the first attempt to compute plain-row offers with a shell join returned zero and was wrong; the field is present on the raw line, so the join had failed, not the data. Re-reading one line before trusting the aggregate caught it. (iteration 6)
- the graph's claim signal treats a claim with no status as unverified, so an unregistered claim silently held convergence at zero; the fix is to register claims with their status, not to avoid claiming. (iteration 7)

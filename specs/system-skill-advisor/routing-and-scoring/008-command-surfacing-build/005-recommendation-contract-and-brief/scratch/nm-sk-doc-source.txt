## How a skill's token list is built

`scoreLexicalLane` builds each skill's candidate strings from `id`, `name`, `description`, `domains`, `intentSignals` and `keywords`. It scores them with `scoreTokenOverlap` and harvests `token:<x>` evidence with a plain `haystack.includes(token)` over the same joined candidates.
`projectionFromRow` fills `name`, `description` and `keywords` from the skill's `SKILL.md` through `parseSkillMarkdown`, and `domains` and `intentSignals` from the `skill_nodes` row. `indexSkillMetadata` reads that row from the skill's `graph-metadata.json` fields `domains` and `intent_signals`, so an edit to `graph-metadata.json` reaches the SQLite projection only after a re-index.

## Why sk-doc holds no documentation-edit token

`sk-doc` projects documentation artifacts and authoring actions (`documentation`, `markdown`, `authoring`, `readme`, `feature catalog`, `frontmatter`, `create`, `validate`, `review the docs`) but no term for editing existing prose, such as typo, heading, spelling, proofread or wording. The prompt's scorable tokens are `fix`, `typo`, `heading`, `setup` and `guide`, plus the synonyms `debug`, `correct` and `patch` that `fix` injects. None is a whole token in `sk-doc`'s candidate strings. The only literal "fix" sits inside "fixture" in `intent_signals` ("benchmark fixture" and "reviewer-prompt fixture"). Scoring is whole-token, so the 3-letter prompt token `fix` does not match `fixture`, `sk-doc` scores 0, and `scoreLexicalLane` drops a row at score <= 0.05 before it can harvest evidence. That is why `sk-doc` carries no token and never enters the recommendation list.

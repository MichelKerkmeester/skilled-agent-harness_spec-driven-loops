[P2] Phase 011 dropped phase 010's rule that a degraded turn writes no route receipt, and recorded no deviation. When the daemon is unreachable, a turn answered by the Python local scorer stores a receipt, and that receipt can later hold back a live turn.
Where: `.skilled/skills/system-skill-advisor/hooks/claude/user-prompt-submit.ts:380-390` (`recordRouteReceipt`). Second location: `.skilled/skills/system-skill-advisor/hooks/lib/skill-advisor-cli-fallback.ts:334-339` and `:400-402`.
Scenario: a confirmed session routes "Update the advisor README…" to `sk-doc`, and the receipt says `sk-doc`. The daemon then becomes unreachable. The user types "fix that too", and the CLI falls back to the Python scorer, which returns `sk-code` at 0.95 with no floor flag (the 011 summary records this output in its Local-scorer path row). The CLI payload is `degraded: true` with no `freshness`, so `freshnessFrom` returns `'stale'`, `resultStatus` returns `'ok'`, and `renderAdvisorBrief` renders a stale `ok` result. `recordRouteReceipt` then overwrites the receipt with `sk-code`, which was taken from a context-free follow-up on a different scorer. Once the daemon is back, the next floored weak follow-up whose native top is `sk-doc` is suppressed (`Advisor: prompt skipped.`) against that degraded receipt. This is the receipt drift the 010 design was written to prevent.
Evidence: `010-route-receipts-research/research/research.md:80` says: "Turns that write: only a turn with `status: 'ok'`, a non-null rendered brief and an unfloored top-1. Skipped, degraded, fail-open, no-match, crash and guarded turns write nothing, so a run of floored follow-ups cannot drift the receipt." The code checks only `if (!sessionId || !brief || !top || top.confidenceFloored === true) return;` and never reads `metrics.degraded` or the freshness. `freshnessFrom` reads `return degraded ? 'stale' : 'unavailable';`, and `resultStatus` reads `if ((freshness === 'live' || freshness === 'stale') && recommendations.length > 0) { return 'ok'; }`. Neither the six 011 Design Corrections nor the REQ table (REQ-001 to REQ-011) mention degraded writes. 011 Known Limitation 1 says "every turn delivers as it did before this phase". That holds for the degraded turn itself, but that turn now also writes a receipt that changes later live turns. No test covers a degraded write. Severity is P2 because the only effect is one floored, low-confidence route withheld, the cost class 011 already accepts in Limitation 5.
Confidence: confirmed (traced from the CLI degraded payload at `runtime/skill-advisor-cli.ts:1582-1590` through `resultFromCliData`, `renderAdvisorBrief` (`runtime/lib/render.ts:518-525`) and `recordRouteReceipt`).

[P2] Two docs say an invalid hook payload returns `{}`, and phase 009's recorded limitation names only the disabled path. When the working directory has been removed, an invalid payload returns the outage fallback instead, and the test named for this case cannot see it.
Where: `.skilled/skills/system-skill-advisor/hooks/claude/user-prompt-submit.ts:520-523` (with the catch at `:620-628`). Second location: `.skilled/skills/system-skill-advisor/hooks/skill-advisor-hook.md:57`.
Scenario: `handleClaudeUserPromptSubmit(null, deps)` runs in a process whose cwd was deleted. Inside the try, `process.cwd()` at `:523` throws `ENOENT`. The catch's guarded diagnostic swallows the second `process.cwd()` throw. `skippedResult` is null, so the catch renders `renderAdvisorTimeoutFallback(renderOptions)`, takes `{ effectiveEmitted: emitted }` because `input` is null, and returns `hookSpecificOutput.additionalContext` with the outage line, not `{}`.
Evidence: `skill-advisor-hook.md:57` says "It returns `{}` when its switch is off. It also returns `{}` when input is invalid." 009 Known Limitation 1 records only "A disabled hook in a removed working directory shows the outage fallback". 009 REQ-007 (`spec.md:158`) and its test "keeps a disabled hook and an invalid payload silent when the clock throws" throw only the clock, never `process.cwd()`, so the test stays green while this path behaves as described. Reaching it needs both an unparseable payload and a removed cwd. The missing-prompt branch is not affected: it reaches `process.cwd()` only through `workspaceRootFor` (`:206-210`), which sits on the earlier normal path, and its own diagnostic uses the already resolved root.
Confidence: confirmed (traced in code from the `!input` branch through the catch to `finishAdvisorDelivery`).

## What Was Built

A Claude sender whose hand-over is pending now gets a refusal when it tries to open a question dialog. The refusal tells it to end the turn and put the question in the handoff note, or to call the hand-over off first. The turn can then end, and the Stop hook can arm the hop.

### Phase 1: sender-dialog-after-prepare

On Claude Code only Stop arms a prepared record. A dialog keeps the turn open, so in four of the fourteen live attempts of packet 038's child 016 the record stayed pending and no hop followed. The PreToolUse guard that already turned away relaunch commands from a sub-agent now also checks each `AskUserQuestion` call. When `SKILLED_LOOP_ID` is set and the loop's record is pending for this session and the `claude` runtime, it denies the call. The reason names the handoff note path and `session-relaunch.cjs cancel --loop-id <id>`.

Every other case lets the dialog through: no record, another session's record, an armed record, no `SKILLED_LOOP_ID`, a disabled concern and a record that cannot be read.

<!-- ANCHOR:decisions -->
## Key Decisions

| Decision | Why |
|----------|-----|
| Refuse the dialog at PreToolUse | The turn has to end for Stop to arm the record. Refusing the one tool that holds it open keeps the hop and leaves every other tool alone |
| Hold only a pending record | Once Stop arms the record the killer ends the idle session, so a dialog after that cannot park the hop |
| Extend the existing guard | Parent decision D3 allows no new module, and the guard already runs at Claude's PreToolUse |
| Let a failed read through | A broken state directory must never block the operator's dialog |
| Not stronger wording only | `prepare` already prints "stop now and end this turn" |
| Not withdrawing the hand-over when a dialog opens | That loses the hop at the context limit, which is the case the hand-over exists for |
| Not recording and closing with no code | In all four saved runs a dialog after prepare cost the hop, so the gap is real even if its rate is unknown |

## Known Limitations

1. **The cause rests on runs where the harness ran `prepare`.** In the four failed runs the test harness ran `prepare`, not the sender, so the sender never saw prepare's "stop now and end this turn" line. A sender that runs `prepare` itself and then opens a dialog has not been observed live. No new live run was made for this child. A live run of such a sender would confirm the fix end to end.
2. **Claude Code only.** Pi, OpenCode and Codex arm on other events and were not examined.
3. **No test covers a throwing record read.** The fail-open path is confirmed by reading the code only. Note of 2026-11-14: phase 020 added the test `subagent-guard lets a question dialog through when the record read throws` in `.skilled/hooks/session-relaunch/tests/subagent-guard.test.cjs`, so this sentence no longer holds. The saved run is named in `acceptance-criteria.md` under AC-005.
4. **The saved pane captures do not show the dialog.** Each `pane-sender.txt` ends at a reply and a `Goal not yet met… continuing` line. The file carries no capture time, so it neither confirms nor refutes the dialog. The extracts are the evidence used.
5. **A pending record that Stop cannot arm keeps refusing questions.** The guard holds every question dialog while the record is pending. When the Stop hook does not arm it, for example because the Stop was deferred, the session gets the refusal on each later question until `session-relaunch.cjs cancel --loop-id <id>` clears the record. A read-only review on 2026-11-13 raised this and the guard's code confirms it. No test covers it. Note of 2026-11-14: phase 005 changed this. A Stop that cannot arm now stamps `deferredAt` on the pending record, and the next operator prompt withdraws it with reason `user-message`, so a refusal lasts until that prompt or `cancel` rather than until a later Stop.
6. **Other dialogs that hold the turn open are not covered.** The binding matches `AskUserQuestion` only. A plan approval or a permission prompt after `prepare` would hold the turn open the same way. This is inferred from the matcher and was not tried.

# Phase 040 context: hard rules out of SKILL.md frontmatter (session record, 2026-09-30)

## Operator messages and decision (verbatim)

- "you have hard rules in skill frontmatter? Thats not supported or something we should do"
- Asked to choose, the operator picked "Move rules out of frontmatter": "Put the rules in each SKILL.md body or a sidecar file and change the hook to read them there. This is larger and touches sk-git and 7 cli-* skills outside this packet."
- The session chose the sidecar: a `hard-rules.json` beside each SKILL.md. Reason: the rule engine is deliberately dependency-free and fail-open (`dispatch-rule-checks.mjs:1-7`), and JSON parses with `JSON.parse` without a YAML or markdown parser. The spec may name the file differently if the design finds a reason.

## Facts read in this session

- Claude Code ignores unknown SKILL.md frontmatter keys. The field works only because this repo's own hooks read it. sk-doc's frontmatter contract (`.skilled/skills/sk-doc/sk-create-frontmatter/`) never mentions `hard_rules` (a grep finds nothing).
- Nine SKILL.md files declare `hard_rules:` in frontmatter: `sk-git`, `cli-classifier/cli-usage` (renamed to `cli-classifier/cli-jev` by phase 039, which runs first), and `cli-external-orchestration/` `cli-opencode`, `cli-cursor`, `cli-codex`, `cli-hermes`, `cli-devin`, `cli-claude-code`, `cli-pi`. Each rule has `id`, `check`, `message` and `severity`.
- The engine: `.skilled/hooks/dispatch/lib/dispatch-rule-checks.mjs` (347 lines). `parseHardRules(text)` (line 23 on) finds `^hard_rules:` in the frontmatter and parses the flat list. `readHardRules(skillMdPath)` (line 61) reads a SKILL.md and returns `[]` on any read or parse error. Evaluation is at line 305 on. Every `check` id the nine skills use is implemented there (a count per id found each once for cli-usage and cli-pi).
- Readers that pass a SKILL.md path:
  - `.skilled/hooks/dispatch/claude/dispatch-preflight-lint.mjs:70`, `codex/dispatch-preflight-lint.mjs:63`, `devin/dispatch-preflight-lint.mjs:66` (`path.join(projectDir, '.skilled', 'skills', match.packetPath, 'SKILL.md')`) and `pi/dispatch-preflight-lint.ts:264`.
  - The command-shape registry with each `packetPath`: `.skilled/hooks/dispatch/lib/dispatch-audit.mjs:28-46`.
  - `.skilled/skills/sk-git/scripts/hooks/git-preflight-advisory.mjs:112` and `sk-git/scripts/lib/advisory-noise-audit.mjs:105`, both on `sk-git/SKILL.md`.
  - `.opencode/plugins/tests/source-root-consumers.test.cjs:29` and `:75` assert on `hard_rules:` text in `sk-git/SKILL.md`.
  - Tests: `.skilled/hooks/dispatch/lib/dispatch-rule-checks.test.mjs`, `dispatch-audit.test.mjs` and `sk-git/scripts/hooks/git-preflight-advisory.test.mjs`.
- Registered hooks: `.claude/settings.json:47` (PreToolUse), `.codex/hooks.json:69`, `.devin/hooks.v1.json:72`. So a regression here silently stops enforcement on three runtimes.
- `sk-design/sk-design-md-generator/backend/scripts/schema-v3.ts` has an unrelated `hardRules` field. Out of scope.
- Hermes copies of these skills are regenerated by `sync-skills-hermes.cjs`. Whether it copies sidecar files is UNKNOWN until the design reads it.

## Proposed frame (mark anything not above as proposed)

- Each of the nine skills gets `hard-rules.json` (proposed name) with the same rules, and its frontmatter loses `hard_rules:`. Content is copied exactly, rule for rule.
- `readHardRules` takes the skill folder (or keeps the SKILL.md path and reads the sibling file), parses JSON, and stays fail-open. Frontmatter parsing is removed once every skill is moved, with no dual read left behind unless the design shows a reader outside this repo needs it.
- Each reader and test above is repointed. The proof: every existing suite passes, and a before-and-after run of the preflight engine over a fixed set of commands per skill gives identical verdicts.
- sk-doc's frontmatter contract and the skill-creation templates say where hard rules live now, so new skills do not put them back in frontmatter.

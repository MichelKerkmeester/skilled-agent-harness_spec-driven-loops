# Orchestrator rulings on design.md section 6 (2026-09-29)

1. Every section 6 answer is accepted as proposed.
2. Phases 027, 028 and 030 share `runtime/changelog/`, the runtime catalog and the runtime playbook, and each proposes `v1.6.0.0`, `F056` and `DLR-056`. They build and commit one after another (027, 028, 029, 030), so each doc step re-reads the folder and index at doc time and takes the next version and the next IDs present then. The counts in the two indexes (`2 features`, `The 54 entries`, `54 deterministic scenarios`) are likewise read at doc time, never taken from this design.
3. Gate order (parent D1, "Jev first, else Deem"): with both switches, the Jev gate and arm run first, then the Deem gate and arm, each on its own gate and regardless of the other's outcome. A failed gate prints its skip line and never runs the other backend in its place.
4. Docs name only what the code prints. A `verdict` line is claimed nowhere unless a run printed it.
5. Tests run on a machine whose global git config sets `core.hooksPath`, and its commit-msg hook rejects a commit without a body. Every test that creates a git repository passes `-c core.hooksPath=/dev/null` (beside `-c commit.gpgsign=false`) to each `git commit` it runs, as `cli-classifier/benchmark/injection-screen/tests/score-injection-screen.test.mjs` line 48 does. Test code and the scripts never run the machine's hooks.
5. Design section 3's case "no headroom prints above 90 percent" (30 labeled rows, 28 real) cannot reach the headroom check, because the label gate runs first and 2 negatives are fewer than 20. Headroom needs `10*R > 9*K` with at least 20 negatives, so R > 180 and K >= 201. The test uses K 201, 20 negatives and 181 real (1810 > 1809). The code's gate order stays as section 2 gives it.

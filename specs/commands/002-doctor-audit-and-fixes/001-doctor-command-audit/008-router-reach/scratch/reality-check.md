## Presentation reachability discrepancy

The presentation accepts numeric answer `13` for `router-reach` at line 40 and lists the target at lines 77 and 103, but its startup menu ends at 11 (lines 9-24) and its help block says “Press 1-11, 0, or X” at line 70. Thus the explicit positional target route exists, but the shared numeric startup route does not advertise the target. This is a presentation defect, not a defect in the subsystem being inspected.

The shared route validator did not catch this presentation defect: it printed `PASS: J1` (`doctor-run.log:339`), but `route-validate.py:161-170` builds its “menu” target set from `target = ...` rows in the accepted-answers table instead of parsing the visible numbered startup menu. The validator therefore checks target-set parity while accepting an undisplayed numeric choice.

- The presentation's `bash .skilled/commands/doctor/scripts/route-validate.sh` troubleshooting command was also run in normal mode. It exited 0 and printed `OK: route-validate — 10 routes validated, 2 warnings` (`doctor-run.log:312-343`).
- A direct read-only `advisor_recommend` response-shape probe exited 0 but returned a degraded local-scorer envelope without recommendations or trust state (`doctor-run.log:11-35`). This proves that the current advisor CLI can answer without supplying the live trust metadata the workflow expects; the diagnostic does not classify that envelope as a probe error (`ci-router-vocabulary-reach.cjs:140-156`).

# Implementation Plan: Restrict which models may act as the prompt-improve agent

<!-- SPECKIT_LEVEL: 1 -->

## 1. SUMMARY

### Technical Context

| Aspect | Value |
|--------|-------|
| **Language/Stack** | Markdown agent definitions and skill contracts |
| **Framework** | Runtime agent discovery across opencode, claude, cursor, devin, pi, codex |
| **Storage** | None |
| **Testing** | Commit-gate scripts plus a live agent dispatch as the behavioral probe |

### Overview

The contract is authored once in `.opencode/agents/prompt-improver.md`, the file the
mirror gate treats as canonical. `.claude/agents/prompt-improver.md` carries the same
body because the gate compares their token sets; `.cursor` and `.devin` are symlinks into
`.claude` and need no edit; `.pi` is regenerated by its sync script. `sk-prompt/SKILL.md`
carries the operative rule a second time for the inline path, and names the agent
definition as the source of truth.

<!-- ANCHOR:architecture -->
## 3. ARCHITECTURE

### Pattern

One canonical document with generated and hand-kept mirrors, guarded at commit time.

### Key Components

- **`.opencode/agents/prompt-improver.md`**: canonical agent definition; the contract's home.
- **`.claude/agents/prompt-improver.md`**: hand-kept mirror in the Claude agent dialect (`tools:` instead of `permission:`); token-compared against the canonical by `check-agent-mirror-sync.cjs`.
- **`.cursor/agents/prompt-improver.md`, `.devin/agents/prompt-improver/AGENT.md`**: relative symlinks into the Claude mirror, maintained by `sync-runtime-mirrors.cjs`.
- **`.pi/agents/prompt-improver.md`**: generated from the canonical by `sync-agents-pi.cjs`, which rewrites the permission block into Pi's tool names.
- **`.opencode/skills/sk-prompt/SKILL.md`**: the other entry point; a caller can run the workflow inline and never load an agent definition.

### Data Flow

A dispatch resolves the agent file for the active runtime and injects its body as the
agent's instructions. An inline run loads `sk-prompt/SKILL.md` instead. The contract sits
on both paths, which is why it is written twice rather than once.

### Two readers, two placements

The rule has two distinct audiences and neither one can be served by the other's copy:

| Reader | Question it answers | Where it must appear |
|---|---|---|
| The model about to act as the agent | "May I run this?" | The agent body, inlined as the persona on every runtime including CLI children that resolve no file paths |
| The caller about to pick a model or route | "Whom may I dispatch?" | `sk-prompt`, which the caller loads before dispatching or running inline |

### Why no machine gate

The restriction keys on model identity. No runtime in this repository exposes the acting
model's identity to a script at dispatch time — the agent frontmatter carries no `model:`
field on any of the twelve agents, and neither `/prompt:improve` workflow YAML names a
model. A validator would therefore have nothing to read and would certify nothing. The
enforceable form of a model-identity rule is a rule the model reads, placed beside the
hard block the same file already enforces the same way.

<!-- ANCHOR:testing -->
## 5. TESTING STRATEGY

The behavioral probe is a live dispatch of the agent surface asking it to report its own
eligibility rule. It was run once before the change as a negative control and returned
"NO MODEL-ELIGIBILITY RULE PRESENT", so the same probe after the change proves the file
reaches the runtime rather than merely existing.

# Iteration 004 — Audit Workflow Fate and Consolidation Boundary

## Focus

Trace `design-audit` from its public command through executable checks, AI-fingerprint machinery, comparison-lane corpus, deterministic Python gates, and shared/private procedure cards. Decide which capabilities are independently invoked versus belonging to a sibling completion gate, and pick the consolidation topology that preserves audit's role after the hub contracts to four modes.

## Actions Taken

1. Read `design-audit/SKILL.md` plus the full reference, procedure, asset, script, and corpus tree to inventory every owned file.
2. Read `/interface:audit` router and the `interface-audit-auto.yaml` / `-confirm.yaml` / `-presentation.txt` execution contracts.
3. Read `mode-registry.json`, `hub-router.json`, and `command-metadata.json` to map the audit route and how siblings (foundations, design, motion, design-reference) treat audit in their discriminator fields.
4. Read `interface-command-contract.test.mjs` and `design-command-surface-check.test.mjs` to separate current-topology assertions from independently exercised audit behavior.
5. Cross-read `design-interface/SKILL.md`, `assets/interface-preflight-card.md`, the shared `polish-gate-orchestration.md`, and `design-motion/SKILL.md` to see whether interface or motion already owns an audit-equivalent gate.
6. Read the `accessibility-audit`, `ai-slop-check`, and `polish-gate-orchestration` procedure cards plus the `audit-report-template` and `audit-evidence-worksheet` assets to map the public command surface to private procedure selection.

## Findings

### 1. `/interface:audit` is a real, independently invokable user command — not an interface completion gate

The audit router exists at `.opencode/commands/interface/audit.md`, has its own auto and confirm workflows (`interface-audit-auto.yaml`, `interface-audit-confirm.yaml`), its own presentation asset, and its own argument grammar (`<target> [--scope] [--score] [--register brand|product] [:auto|:confirm]`). The auto workflow gates `STATUS=OK` on a real report and the status contract points the user back to `/interface:foundations`, `/interface:design`, `/interface:motion` — i.e. audit hands off upward, it does not run inside them. The pipeline section declares `stage: "review - validates design output before the build handoff"` and `recommend_only: true`. ## Ruled-Out Directions

- **Fold audit into `design-interface` as a polish/validation phase.** Rejected because interface already owns its own mechanical preflight (interface-preflight-card.md) and the five-dimension /20 scoring rubric, P0-P3 severity model, AI-fingerprint registry, and comparison-lane corpus are not interface obligations. Folding would either duplicate the preflight card or strip audit's scoring surface. - **Promote audit into a shared procedure callable from interface.** Rejected because audit carries its own corpus (comparison-lane.mjs), deterministic Python gates (perf_evidence_check.py, polish_readiness_check.py), AI-fingerprint registry, and a 70-file reference corpus. A procedure card cannot host a corpus, parity tests, and Bash-allowlist authority. Adding audit as an automatic completion gate would chain user requests without consent and would contradict the existing recommend-only posture. - **Reuse the audit severity rubric for interface's preflight card.** Rejected because interface's preflight card is intentionally binary (every box is pass/fail), while audit's severity model is intentionally graded (P0-P3) with a 0-4 dimension score. The two are different shapes for different decisions; collapsing them would either inflate the preflight into a scoring ritual or flatten the audit into a checklist. ## Questions Answered

- **Which `design-audit` capabilities are actually invoked, and should they become an interface gate or shared procedure?** Audit is independently invoked through `/interface:audit` with its own command contract, severity rubric, scoring rubric, AI-fingerprint registry, comparison-lane corpus, deterministic Python gates, and shared-procedure orchestration ownership. Audit is neither a completion gate (interface already owns the SHIP/FIX preflight) nor a procedure card (it carries a corpus and Bash authority). The correct topology is to extract audit to a standalone skill outside the four-survivor hub while keeping `/interface:audit` as a staged alias that the hub forwards to it, preserving the framing/application split, the cross-mode polish orchestration, and the sibling discriminator edges.

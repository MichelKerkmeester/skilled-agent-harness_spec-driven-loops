## Findings

- **The four YAMLs couple to the runner through exactly two channels, and both are relative-path, cwd-anchored.** The spawn lines invoke `node .opencode/skills/system-deep-loop/runtime/scripts/fanout-run.cjs \` (deep-research-confirm.yaml:234, deep-review-auto.yaml:236, deep-research-auto.yaml:220, deep-review-confirm.yaml:199); the single-executor `if_cli_*` heredocs import the guard relatively and pin the world to the template: `const repoRoot = '{repo_root}'`, `buildLineageCommand(lineage, promptBody, resolvedSandbox, resolvedPermission, { env: process.env, cwd: repoRoot })`, `runAuditedExecutorCommand({ ..., cwd: repoRoot, ... })`, `snapshotOutOfScopeDirtyPaths({ repoRoot, artifactDir })` (deep-review-auto.yaml:1568–1578, 1599–1616, 1621; the same heredoc shape repeats at 1557–1648, 1648–1741, 1739–1811, and in deep-review-confirm.yaml:1145–1191, deep-research-confirm.yaml:1073–1119, deep-research-auto.yaml:1185–1433).

- **The heredoc dispatches bypass the runner's containment-root precedence entirely.** `resolveContainmentRepoRoot` — the `DEEP_LOOP_REPO_ROOT` override plus the "artifact resolves outside cwd's worktree → redirect to the worktree physically holding the writes" rule — exists precisely for checkout-aliasing (runtime-bootstrap.cjs:43–74), and the runner honors it once per run (`fanout-run.cjs:2600–2607`: "resolved once for the whole run", `process.cwd()`-anchored). No heredoc calls it: the `{repo_root}` template variable is the single-executor branches' only root seam, so any worktree/pinning that flows through the bootstrap precedence is invisible to them.

- **The packet's own two affected-surface declarations disagree about which flag the YAMLs take.** spec.md:90–91 lists the YAMLs as Modify: "Runner flag and the inline containment calls" — singular "Runner flag", not saying whether that is the phase-1 preserve/restore mode flag or the phase-2 worktree toggle. The worktree ADR's "What changes" names only the runner and "the prompt-pack rendering … and the per-kind directory flags" (decision-record.md, ADR-003 Implementation). The plan's affected-surfaces row for the YAMLs is mode-only — "Update: pass the mode flag and align the inline calls", verified by "Grep for `enforceWriteContainment` across the four files; each call site carries a mode" (plan.md, FIX ADDENDUM) — so no verification anywhere asserts that the worktree toggle actually reaches the four spawn lines, which are the runner's only in-repo callers (the heredocs call `buildLineageCommand`, not the runner).

- **The heredoc import mechanism makes the guard portable but the caller immovable.** The heredocs are `node --experimental-strip-types --input-type=module <<'EOF'` with `working_directory: "{repo_root}"` (deep-review-auto.yaml:1550–1552, 1654–1656, 1745–1747) — a stdin/eval module, so the relative `'./.opencode/skills/...'` specifiers resolve against the dispatch cwd. That cwd must hold a tracked `.opencode/` — which the repo guarantees ("THIS repo is the SOURCE of .opencode/ content — it MUST be tracked", root .gitignore:6–11). Since the guard module itself imports only node builtins (write-containment.ts:14–16: `node:child_process`, `node:fs`, `node:path`), the single-executor containment would work unchanged from a fresh worktree; the zod/tsx burden sits one level up (executor-config.ts:2 imports `zod`; the runner re-execs under tsx per runtime-bootstrap.cjs:31–44) in the loop checkout, which already has `node_modules`.

- **The guard's contract was designed additively, so the scattered inline callers survive the migration untouched.** `EnforceInput.mode` defaults to `'preserve'` — "Omitted means 'preserve', so a caller that has not decided a HEAD restore is safe here cannot destroy uncommitted work by default" (write-containment.ts, EnforceInput) — and the planned baseline content capture is "an **optional** content capture" (plan.md, Key Components). Every existing caller (the runner at fanout-run.cjs:2567, 12+ heredoc copies, the council/benchmark importers, the scratch drivers importing by absolute path — specs/sk-design/018-.../012-.../scratch/dispatch-iter.mjs:5, specs/cli-external-orchestration/029-.../research-devin-hooks-portability/.iter-driver.mjs:41–43) therefore keeps working through the 045 signature additions with no edit. The breaking risk concentrates in the runner's internal call and the `{repo_root}` provenance, not the callers.

- **Isolation is fan-out-only by construction, and the signature clause freezes the other callers out.** REQ-005 speaks of "Each CLI lineage" (spec.md:115); the council orchestrator and model-benchmark dispatcher "import `buildLineageCommand` but never run the containment guard … named as blast radius, not changed" (spec.md:78), and "the two `buildLineageCommand` importers are the reason the worktree phase must keep that function's signature stable, or change all three call sites together" (spec.md:239; the plan confirms both "take the builder alone"). If worktree awareness arrives as a new builder option, callers that don't pass it silently keep the shared checkout — a partial migration by omission rather than by recorded decision.

- **The rollback clause institutionalizes a permanent duality.** "Turn the worktree option off for the run. The runner falls back to the main checkout under forced preserve mode, which is the Phase 1 behaviour" (decision-record.md, ADR-003 rollback) plus NFR-R02 — worktree create/remove failure "degrades to the current in-checkout behaviour under preserve mode, with a warning event" (spec.md:178). Both root-resolution semantics must stay correct forever, and the carve-outs the worktree makes unnecessary (sibling dirs, parent ledger files — write-containment.ts:23–27, 41–56) are frozen: "The `unattributableDirs` and `unattributablePaths` carve-outs … are correct and stay as they are" (spec.md:75). The heredocs permanently exercise the path the worktree never touches.

- **Copy-back geometry answers iteration-004's merge-vs-mirror question for exactly one collision.** The ordering is now pinned: "a copy-back step runs between the guard and the settle" (plan.md, Data Flow), and the guard's quarantine/patch land inside the lineage dir (plan.md: `containment/quarantine/`, `containment/baseline/` "under the lineage directory"), while the parent's ledgers "sit one level above every leaf's artifact dir" (write-containment.ts:23–27) — outside the copied subtree, so nothing the runner writes concurrently gets clobbered by the copy. What is not established: where `state_paths.state_log` physically resolves during a worktree lane — whether the seat's state records and the guard's `containment_violation` event land in the copied subtree or in the main checkout (UNKNOWN; the state-path construction was not read in this iteration).

- **The seeding design feeds the baseline budget, and the two bounds interact.** Each worktree is "seeded with the packet's uncommitted content" (plan.md, Lineage worktree), and the pre-dispatch baseline then captures *content* — not just hashes — into `containment/baseline/` inside the lineage dir, "bounded at 2 MiB per file and 64 MiB per lane", with over-bound paths "marked baseline-truncated, which forces preserve for that path regardless of mode" (plan.md). The seeded uncommitted packet therefore enters *every* lane's 64 MiB baseline, and incident-scale packets (the 1,858-path tree of spec.md:22) are precisely where the restore guarantee silently degrades to preserve, path by path.

- **Dead-runId prefixes have no reaper and no second chance.** The worktree name embeds the run: `git worktree add --detach <base>/<prefix>-<runId>-<label> HEAD` (plan.md). A re-run gets a new runId, so an interrupted run's worktrees fall outside the next run's "startup sweep of the runner's own prefix" (plan.md; decision-record.md risk table), while sk-git's reaper classifies 045 worktrees report-only (iteration-009). Teardown-on-settle is the only deletion incentive, and the spec's own failure paths waive it: "the worktree is retained rather than removed, and its path is named on the failure event" (spec.md:192).

- **Sequencing gives the migration its bisect point, deliberately.** "The worktree work ships second, on its own, because it changes where every lineage runs and wants a clean bisect point. Churn detection ships last … the detector then guards only the fallback path" (plan.md, §4 Sequencing rationale). So the YAMLs' mode-flag change and any worktree coupling are separate commits, and Definition of Done requires the four YAMLs (plus the two tracked compiled contracts, which must be "regenerated after the YAML change" — spec.md:231–232; only `compiled/manifest.jsonl` is ignored per root .gitignore) to "describe the shipped behaviour" (plan.md, Definition of Done).

## What this means for unlimited concurrency

- The binding ceiling today is the config schema, not the worktree layer: `concurrency: z.number().int().positive().max(8).default(2)` and `MAX_EXPANDED_LINEAGES = 256` (executor-config.ts, fanoutControlShape / lineages constant) — the recursion layer adds no breadth guard (iteration-006), so "effectively unlimited" currently means 256 expanded lineages, 8 at a time, until the schema is amended.

- Unlimited fan-out and the incident model *coexist by design*: the single-executor heredocs, the council and benchmark routes permanently keep the shared-checkout post-hoc diff (spec.md:78), so the failure surface that destroyed work twice today shrinks to the fallback path plus the non-fan-out routes — it stops being a fan-out concern, not a repository concern.

- The unreaped failure residue scales with successful runs: runId-scoped prefixes + teardown-only deletion + report-only reaper + retained worktrees on copy-back failure (spec.md:192) mean every interrupted run permanently deposits up to N worktrees, so iteration-005's disk/inode term compounds across dead runIds with no counterparty.

- The one non-kill switch becomes the load-bearing guarantee at scale: any worktree-creation failure anywhere degrades lane-by-lane to the shared checkout under forced preserve (spec.md:178) — at 200-wide fan-out, a transient git failure silently recreates the incident conditions, mitigated only by preserve's non-destructiveness.

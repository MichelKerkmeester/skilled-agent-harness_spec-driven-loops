# Open Question Iteration 004

**Model:** `swe-2-max` via cli-devin  
**Angle:** The verification gap: what a concurrent negative control must assert so a destructive sweep cannot pass, and which OTHER current acceptance criteria would wrongly certify a hazard as correct

---

Now let me read the acceptance criteria — the core document for this angle — plus the rest of spec.md and check the runner for any existing teardown/sweep logic.## Findings

- **The named gap is real and structural: every destructive actor in the worktree phase is invisible to every current criterion.** AC-009 (acceptance-criteria.md:71) asserts two absence/presence facts — "every lineage directory is present in the main checkout and no ephemeral worktree remains" — on a single, non-concurrent run. A startup sweep that `rm -rf`s the entire runner prefix satisfies "no ephemeral worktree remains" perfectly, and "lineage directory present" is satisfied by an empty or stale directory since nothing asserts its bytes match what the lane produced in the worktree. The criterion certifies the hazard it exists to exclude.
- **The sweep itself is specified with zero gating.** T021 (tasks.md:91) reads "Sweep the runner's own ephemeral worktree prefix at startup" — the prefix is shared across runs (ADR-003 names worktrees `<prefix>-<runId>-<label>`, decision-record.md:265), so run B's startup sweep targets run A's live worktrees by construction. R-004 (spec.md:217) supplies the mitigation "startup sweep of the runner's own ephemeral prefix" with no liveness requirement. There is no backstop: sk-git's reaper treats detached worktrees as report-only and never removes them (worktree-reaper.sh:191-194).
- **The repository already contains the correct sweep contract, one directory away.** worktree-reaper.sh reaps a wrapper worktree only when ALL of: tree clean, branch merged into live tip, session marker exists with a dead recorded PID, AND no live process holds a cwd inside it (worktree-reaper.sh:206-222), under the stated rule "absence of proof is never proof of absence" (worktree-reaper.sh:82-83). The runner's sweep spec requires none of these proofs. A negative control should assert this exact contract: removal requires positive proof of death.
- **What the concurrent negative control must assert — five conjuncts, all required:** (1) *Setup ordering*: run A's worktrees exist AND carry a live marker before run B's startup executes — otherwise the test is vacuous (B sweeps an empty prefix); (2) *Survival with usability*: after B's sweep and B's full run, every A worktree still exists on disk, still appears in `git worktree list --porcelain`, and `git -C <wt> status` still runs — a directory whose `.git` linkage or `node_modules` symlink was removed survives an `existsSync` check while being dead; (3) *Byte-level survival*: sentinel content (one untracked file + one modified-tracked file) inside each A worktree is hash-identical afterwards — untracked deletion leaves no HEAD copy, so `git status` cannot detect the loss (synthesis.md:32-33); (4) *A still completes*: A's lanes settle and copy back — presence of a husk is not survival; (5) *Positive discrimination control*: a planted stale entry under the same prefix (dead-PID marker or unmarked dir past a grace window) IS removed by B — without this, a sweep that deletes nothing passes the negative half, and the control cannot distinguish "safe sweep" from "no sweep".
- **AC-001 and AC-003 certify the wrong tree.** AC-001's evidence asserts an out-of-scope file "still holds the lane's bytes after enforcement" and AC-003 asserts a `containment_violation` event (acceptance-criteria.md:63,65). But `containmentRepoRoot` is resolved ONCE per run against the main checkout (fanout-run.cjs:2692-2696, via runtime-bootstrap.cjs:54-73 which falls through to `cwd`), then passed to every per-lineage guard call (fanout-run.cjs:3263-3265). Under per-lineage worktrees, the main checkout is a tree nobody writes to: "bytes unchanged" is vacuously true and "no violation event" is guaranteed, so both criteria go green precisely when the guard is watching nothing. The missing assertion is *which root was inspected* — no criterion requires the containment event to carry or match the lineage's worktree path.
- **AC-007/AC-008 certify broken attribution as success.** A lane with complete artifacts and zero findings settles `fulfilled`, not `completed_with_containment_advisory` (fanout-run.cjs:3313-3318 only assigns the advisory status when findings exist). With the guard aimed at the main tree there are never findings, so the outcome-separation criteria are met while attribution is entirely absent — they cannot distinguish "containment was exact and quiet" from "containment watched an empty tree."
- **AC-010 latches the wrong hazard.** The churn sampler counts churn in `containmentRepoRoot` — the main checkout — and its only consequence is forcing preserve *mode on the guard's remedy* (fanout-run.cjs:2700-2702; acceptance-criteria.md:72). Under worktrees the destructive actors are the startup sweep and teardown removal, which the containment mode does not govern at all. The criterion certifies a correct response to a hazard on a surface the lanes no longer touch.
- **The plan's own integration test exercises the old hazard model.** plan.md:121 specifies "a simulated concurrent editor dirtying tracked files mid-lane" in the tree the lane runs in; under the worktree phase the neighbour lives in the main checkout where it is neither detected nor harmed, so the test as written only covers the fallback path. SC-004 (spec.md:136) has the same defect — it is scoped to what "the guard" modifies, and the worktree-phase destroyer is not the guard.
- **CHK-124 and T028 are absence-polarity observations.** CHK-124 (tasks.md:271) requires only that an interrupted-run sweep "has been observed cleaning up" — a wholesale prefix deletion satisfies it. T028 (tasks.md:113) is the manual twin of AC-009 with the same presence/absence assertions and no concurrent run.
- **NFR-R02's fallback has no certified observability.** Degrading to the main checkout under forced preserve "rather than failing the run" (spec.md:178) is safe only if the operator can see it happened; no criterion requires the warning event to reach the run summary, so a silent per-lane fallback recreates the original shared-checkout hazard under a green gate.
- **A runner-side precedent for liveness-based exclusion already exists in the call site.** `discoverForeignLiveRunDirs` is already invoked per-lane to keep other runs' live directories out of attribution (fanout-run.cjs:3269) — the codebase already treats "foreign live run" as a detectable category; the sweep simply doesn't use it.

## Recommended design

- Gate the sweep on a per-worktree liveness marker written atomically at `git worktree add` time (PID + startedAt + heartbeat + runId/label — the `LoopLockData` shape), refreshed on the existing progress heartbeat; removal requires positive proof of death — heartbeat older than 2×TTL **and** `!kill(pid,0)` — with unmarked or unparseable entries kept past a creation-time grace window (absence of proof ≠ proof of absence, worktree-reaper.sh:83).
- Scope the sweep to prefix entries whose embedded runId differs from the current run's AND that fail the liveness proof; emit a per-entry keep/remove decision event with its reason to the run ledger so the control can assert discrimination happened, not just outcomes.
- Replace AC-009's "no ephemeral worktree remains" with a run-scoped teardown assertion ("no worktree of *this* run remains") plus a copy-back content assertion (each lineage dir in the main checkout hash-equals its worktree source), and add a new criterion carrying the five-conjunct concurrent negative control above.
- Add an inspected-root assertion: a lane that writes outside its lineageDir *inside its worktree* must produce a violation event naming the worktree root, and a neighbour's write in the main checkout mid-run must produce none and remain byte-untouched — this certifies the boundary moved rather than that the guard went quiet.
- Extend the negative control to the copy-back target: with A's published `lineages/<label>` present (label-keyed, fanout-run.cjs:2862), run B using the same label must not silently overwrite it — assert A's published bytes survive B's run.

## What would break it

- The single-heartbeat limit: the lock module heartbeats exactly one lock per process (loop-lock.ts per iteration-003), so N worktree markers either need the runner to refresh N marker mtimes itself or a per-lineage lease — a marker written once and never refreshed becomes false-positive dead after 2×TTL and licenses the sweep to kill a live peer.
- PID reuse without nonce/start-time corroboration: a dead run's PID recycled by an unrelated live process keeps a stale worktree "live" forever; the control must assert the marker's `acquireNonce`/`startedAtIso`, not liveness of the number alone.
- Test vacuity through ordering: if the harness cannot guarantee B's sweep executes strictly after A's worktrees are created and marked — or A's marker write races B's read — the control passes without ever exercising the gate; the test must assert the interleaving itself, and creation must write the complete marker atomically with the `worktree add`.

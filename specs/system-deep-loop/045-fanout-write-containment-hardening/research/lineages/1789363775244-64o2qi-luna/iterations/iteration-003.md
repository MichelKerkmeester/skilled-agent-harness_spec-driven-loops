## Findings

- Sparse checkout is the best direct Git-native lever on materialized tracked bytes. A sparse-plus-partial lane can reduce selected working-tree and object materialization while retaining exact attribution if it remains a registered linked worktree with worktree-specific sparse state. Setup time and byte reduction are UNKNOWN here. The sparse profile must include the runtime, command/configuration paths, packet seed, and all dynamic reads; the seven ignored dependency/build roots still need the current link/self-link handling [SOURCE: https://git-scm.com/docs/sparse-checkout; https://git-scm.com/docs/git-config; .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:138-158,560-751].
- Partial/blobless clone is complementary, not a substitute for sparse checkout. It reduces object transfer or lazy blob retention, while a dense checkout still materializes the snapshot. Shallow history similarly reduces history depth but not the dense working tree. Reference/shared clones reduce object duplication, but the packet already observes a shared object store for worktree lanes. These three mechanisms can preserve exact attribution only when wrapped in a private physical lane tree and Git metadata; none alone attacks the measured 1.6 GB checkout [SOURCE: https://git-scm.com/docs/git-clone; specs/system-deep-loop/045-fanout-write-containment-hardening/implementation-summary.md:105-106].
- A private-upper overlay or COW sandbox is the best theoretical absolute disk reducer, but it is not a drop-in change. Each lane needs a private mutable upper/work pair, private index and worktree administrative state, and a merged root used consistently by the executor, child cwd, `git -C`, containment, and churn detector. A shared lower and shared immutable object store are safe to share; a shared upper or index destroys exact ownership [SOURCE: https://docs.kernel.org/filesystems/overlayfs.html; .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:163-183,294-307; .opencode/skills/system-deep-loop/runtime/lib/deep-loop/write-containment.ts:282-336,740-773]. Setup, changed-block disk, and mount overhead are unmeasured.
- One physical worktree with per-lane environment write redirection is the cheapest theoretical setup and disk posture, but it is not exact under this runtime. Lifecycle Git calls remove redirector variables and use explicit `git -C`; some executor kinds retain the main checkout as cwd; the checkout watch is intentionally report-only. Complete interception of cwd-relative writes, child processes, symlink realpaths, Git status, and publish paths would be a new virtual-lane filesystem seam rather than a one-worktree configuration [SOURCE: .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:163-183,294-307; .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-paths.ts:109-126; .opencode/skills/system-deep-loop/runtime/scripts/fanout-run.cjs:3611-3651,3880-3905].
- Dependency roots and entry guards are independent of the storage mechanism. A wholesale link or lower-layer symlink that points into the main checkout remains pointed there in a COW view; it is not automatically reanchored. Workspace self-links require real ancestor directories and relative lane targets, while compiled entry guards require `argv[1]` and imported-module realpaths to agree. The packet’s reproduced exit-0/no-output behavior is therefore a negative control for every candidate, not merely for ordinary worktrees [SOURCE: .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:394-475; specs/system-deep-loop/045-fanout-write-containment-hardening/research/worktree-symlinks/synthesis.md:51-75].
- Git-managed relocation is the deciding differentiator. Sparse, partial, shallow, and reference variants can retain `git worktree move` and repair semantics when they remain registered worktrees; relative self-links are required, and reference alternates must remain reachable or be deliberately dissociated. An arbitrary COW mount or sandbox can be moved only by a separate mount/upper/work/index relocation protocol. A virtual view likewise needs its own relocation metadata. `git worktree move` alone does not move those external contracts [SOURCE: https://git-scm.com/docs/git-worktree; .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:466-475].
- Exact attribution means more than “the lane wrote different bytes.” It requires a distinct write root, a private status/index boundary, a path-consistent child process view, and a detector that can observe every candidate write. Shared immutable objects or lower layers do not violate that definition; a shared mutable checkout, status index, upper layer, or report-only warning does [SOURCE: .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-paths.ts:101-126; .opencode/skills/system-deep-loop/runtime/lib/deep-loop/write-containment.ts:740-773; .opencode/skills/system-deep-loop/runtime/scripts/fanout-run.cjs:3880-3905].

## Recommendation

Adopt sparse plus blobless partial materialization inside the existing registered per-lane worktree lifecycle as the lowest-risk optimization to measure first. Keep the physical worktree and private Git status/index boundary, derive a mandatory-path closure from the runtime and executor reads, retain the seven-root dependency handling, and run the packet’s self-link and compiled-guard negative controls. This preserves exact attribution and Git-managed relocation while targeting the measured checkout component. It does not meet a literal “one checkout” requirement, but no literal one-worktree design meets the current exactness contract.

If the dominant objective is the largest possible disk reduction, treat private-upper COW as a separate runtime feature, not a configuration toggle. It needs a new lane-view abstraction that owns Git admin/index, merged-root process routing, dependency reanchoring, containment, churn sampling, mount cleanup, and relocation. Its fraction-of-1.6-GB claim is a hypothesis until six-lane setup, apparent disk, changed-block disk, and failure-mode benchmarks pass.

## Questions Answered

- Sparse plus partial is the smallest credible exact optimization: it lowers materialization without surrendering registered worktree attribution, but its savings are unmeasured.
- Shallow history and reference/shared objects are useful secondary transfer/storage choices but do not independently lower the dense checkout cost already measured in the packet.
- COW and sandbox views can be exact only with private mutable Git and filesystem state; a single shared checkout with environment-only redirection cannot.
- The seven shared dependency roots, workspace self-links, compiled entry guards, and churn detector must be treated as acceptance surfaces for every candidate. COW does not repair them automatically.
- Git worktree move/repair survives for registered sparse/partial/shallow/reference lanes. COW, arbitrary sandboxes, and virtual views require a separate relocation protocol; relative self-links remain mandatory.

## Questions Remaining

- The recommendation still needs an implementation benchmark for mandatory-path sparse-plus-partial and, separately, private-upper COW; these are acceptance measurements, not unresolved mechanism conclusions.
- The dynamic read closure and Git version-specific worktree sparse behavior must be enumerated before enabling sparse mode by default.
- A relocation test must move a lane and re-run dependency links, compiled guards, containment, and status before any COW or sparse implementation is considered production-safe.

## Ruled-Out Directions

- Shallow or reference/shared modes as standalone answers to the 1.6 GB checkout cost: they change history/object storage, not a dense working tree [SOURCE: https://git-scm.com/docs/git-clone; specs/system-deep-loop/045-fanout-write-containment-hardening/implementation-summary.md:105-106].
- One physical checkout with environment-only write redirection: it cannot override the current explicit Git/path and report-only churn seams [SOURCE: .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:163-183,294-307; .opencode/skills/system-deep-loop/runtime/scripts/fanout-run.cjs:3611-3651,3880-3905].
- Unregistered COW or sandbox views where Git move semantics are required: they need a separate registration or relocation contract [SOURCE: https://git-scm.com/docs/git-worktree].
- Sparse profiles without the runtime/dependency closure: missing inputs can produce incomplete or silent execution [SOURCE: .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:138-158,693-751; specs/system-deep-loop/045-fanout-write-containment-hardening/research/worktree-symlinks/synthesis.md:61-75].

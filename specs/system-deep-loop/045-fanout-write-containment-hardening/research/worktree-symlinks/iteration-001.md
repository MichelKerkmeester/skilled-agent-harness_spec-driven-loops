**Angle:** Resolution mechanics: exactly how Node resolves an import through a symlinked node_modules directory, what --preserve-symlinks and --preserve-symlinks-main change, and which of those resolution paths the four workspace self-links actually break. ## Findings

- **Correction to the given link locations: all four self-links live one level deeper, under a scope dir `@spec-kit/` — the link targets are only consistent when anchored there.** `ls .opencode/skills/system-spec-kit/node_modules/@spec-kit` → `cli/ runtime/ shared/`; `ls .opencode/skills/system-deep-loop/runtime/node_modules/@spec-kit` → `shared/`. With dirname `…/node_modules/@spec-kit`, `runtime -> ../../runtime` = `…/system-spec-kit/runtime`, `cli -> ../../runtime/cli` = `…/system-spec-kit/runtime/cli`, `shared -> ../../shared`, and deep-loop's `../../../../system-spec-kit/shared` = `.opencode/skills/system-spec-kit/shared` — the exact npm workspace-link shape. The target strings in the brief are right; the shorthand path was not. Two top-level `ls` runs on those node_modules dirs show no `runtime`/`shared`/`cli` entries at top level, and repo code attests the link kind: `.opencode/bin/system-skill-advisor-launcher.cjs:303` ("resolves through the `@spec-kit/shared` symlink"). Direct `readlink` output is **UNKNOWN** — this dispatch's `ls` tool does not print link targets and I have no exec tool (see next bullet).

- **Execution constraint, stated up front: this dispatch has only read/grep/find/ls — no command execution. The required minimal reproduction was therefore specified but NOT run; everything below that depends on a Node process is documented-resolver reasoning, not observed output.** The decisive experiment to run (2 minutes, fixture only): (1) main checkout `M` with workspace pkg at `M/pkg` (`{name:"@scope/pkg"}`, `index.js` exporting `"MAIN"`), workspace root link `M/node_modules/@scope/pkg -> ../../pkg`; (2) `git worktree add W` with `W/pkg/index.js` exporting `"WORKTREE"`; (3) `ln -s M/node_modules W/node_modules` and `W/consumer.js` requiring `@scope/pkg`; (4) `node W/consumer.js` → predicted **`MAIN`** (silent cross-checkout); repeat with `--preserve-symlinks` → predicted **still `MAIN`**; (5) replace step 3 with a real `W/node_modules` whose `@scope/pkg -> ../../pkg` is created *in the worktree* → predicted **`WORKTREE`** with no flags. If step 5 prints `WORKTREE`, the hypothesis "symlinking is fine, wholesale carrying self-links is not" is proven mechanically; if not, the hypothesis is wrong. These predictions follow from OS link traversal (relative targets resolve against the link's real containing directory) plus Node's default realpath of resolved non-main modules; flag semantics are documented Node behavior, unverified here.

- **The runner symlinks the trees wholesale with absolute targets into main, which is exactly what lets the relative self-links re-anchor to main.** `.opencode/bin/worktree-session.sh` `default_shared_paths()` lists five paths and its link loop does `src="$MAIN_ROOT/$rel"; rm -rf -- "$dst"; ln -s -- "$src" "$dst"` (absolute source). `.opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:147-154` lists **six** paths (the wrapper's five plus `.opencode/skills/system-deep-loop/runtime/node_modules`) and `:415` does `symlinkSync(sourceAbs, destAbs, 'dir')`. The deep-loop variant has to carry the sixth path itself — the wrapper only ever launches a session against the spec-kit runtime, while a lane "resolves its own `tsx`, `zod` and `better-sqlite3` from that directory" (`worktree-lifecycle.ts:141-145`). So a worktree's `node_modules` is an absolute pointer to main's tree, and every relative link inside it resolves inside main's tree.

- **Which resolution paths break, per resolver family and per link.** Both CJS `require()` and ESM `import` walk `node_modules` directories upward from the *requesting module's* directory, find the worktree's `…/node_modules` (the absolute symlink), and then the OS follows the relative self-link into main's source; under default resolution Node then realpaths the result, so module identity, `__dirname`, and all further lookups run in main's tree. This is why the fix needs no flags: with the same relative target strings recreated *in the worktree*, the walk lands on the worktree's own `runtime`/`shared`/`cli`, realpath stays in the worktree, and dedupe/caching stays correct. `--preserve-symlinks` skips the realpath for non-main modules only: the *bytes* read are still whatever the OS opened through the links (main's files), so it cannot repair a cross-checkout self-link, and it splits module identity when the same file is also reachable by its real path (dual-instance hazard). `--preserve-symlinks-main` is scoped to the main entry module and touches none of these lookups. Live import traffic through the links, from grep across `.opencode`: `@spec-kit/shared` is imported by runtime TS (`runtime/lib/validation/orchestrator.ts:10`, `runtime/lib/parsing/content-normalizer.ts:11`, `runtime/hooks/claude/hook-state.ts:21`, …), sk-doc scripts (`sk-doc/sk-create-skill/scripts/lib/root-router-contract.cjs:62`), and the advisor launcher (`bin/system-skill-advisor-launcher.cjs:303`); `@spec-kit/runtime` is consumed via its `api/` surface (`runtime/api/README.md:50`, doctor build scripts `commands/doctor/scripts/doctor-runtime-bootstrap.sh:186`); the deep-loop tree's `shared` link serves anything loaded through `system-deep-loop/runtime/node_modules`. No import site for `@spec-kit/cli` was found in the grep — it appears only as an npm workspace name (`doctor-runtime-bootstrap.sh:187`), so of the four, it is the one that mostly exists for npm tooling. The other four of the six shared paths: `system-spec-kit/runtime/node_modules` contains only `.vite/` + `.vite-temp/` (ls), and the context's previously-verified no-self-link status for the two `dist` dirs and `cli/node_modules` was not re-derived here.

- **The git skill's prohibition is real and states this exact mechanism, so the hypothesis does not contradict it — it narrows it.** `.opencode/skills/sk-git/scripts/worktree-naming.sh:448-450`: "Provisioning INSTALLS rather than symlinking a tree from the source checkout. A package's node_modules carries its own workspace self-links, which are relative and resolve back to wherever they were created — symlink the tree and the worktree silently compiles against the other checkout's build output." `.opencode/skills/sk-git/feature-catalog/workflow-playbooks/large-reorg-playbook.md:28` carries the consumer-side symptom ("Node then resolves paths relative to the symlink target, so a generator can walk the wrong root and exit 0"). So the repo's rule is written against *tree-level* symlinking for this reason — consistent with the hypothesis that the mistake is carrying the self-links, not the technique.

- **Gap in the hypothesis as stated: recreating the four self-links against worktree source is necessary but not sufficient, because `@spec-kit/shared`'s exports map onto `dist/`, and `system-spec-kit/shared/dist` is not in the six provisioned paths.** `shared/README.md:59`: "the package maps every subpath onto `dist/`" (exceptions shipped as source: `workspace/repo-root.mjs`, `review-research-paths.cjs`), and `@spec-kit/shared` is native ESM per `system-spec-kit/changelog/v3.1.2.0.md:9`. Today that is masked: the whole-`node_modules` symlink plus `shared -> ../../shared` lands consumers in **main's** `shared/dist`, which exists. Relink `@spec-kit/shared` to the worktree's `shared` and the worktree has no `shared/dist` at all (gitignored, never provisioned) — imports fail hard with `ERR_MODULE_NOT_FOUND` instead of silently loading main. `runtime/dist` and `cli/dist` *are* provisioned (worktree-lifecycle.ts:150-151), so `@spec-kit/runtime` relinked to the worktree would at least resolve — but through main's compiled output. The fix therefore needs a decision on `shared/dist`, and `dist` staleness is a second, different defect from the self-links.

- **An existing automated check already encodes the intended invariant, and the current wholesale symlink should fail it.** `.opencode/skills/cli-external-orchestration/cli-opencode/manual-testing-playbook/stress/node-modules-integrity.md:51-56` runs vitest `-t "preserves independent worktree node_modules boundaries during cli-opencode dispatch"` in `system-deep-loop/runtime/tests/stress/cli-adapter/cli-opencode.vitest.ts`, ledger expectation: "their `node_modules` realpaths differ and each remains inside its owning worktree." Wholesale symlink makes every worktree's `node_modules` realpath equal main's — the invariant is unsatisfiable under the current mechanic and satisfiable under the proposed one. ## Recommended mechanism

- Replace "symlink the six trees" with a provisioner that creates a **real directory farm** in the worktree: `mkdir -p` each `node_modules` and its `@spec-kit/` scope dir, symlink every vendored top-level entry (including `@`-scopes other than `@spec-kit`) from main, then create the four workspace links **in the worktree** with the same relative strings (`runtime -> ../../runtime`, `shared -> ../../shared`, `cli -> ../../runtime/cli`; deep-loop's `shared -> ../../../../system-spec-kit/shared`). Relative-link error the first time is cheap and loud; silent cross-checkout loading disappears. No `--preserve-symlinks` or `--preserve-symlinks-main` anywhere — default realpath is what keeps the worktree's own files canonical and deduped.
- Provision `system-spec-kit/shared/dist` as part of the same step (symlink from main with the staleness accepted, or per-lane build). Without it the relink converts silent contamination into hard `ERR_MODULE_NOT_FOUND` for every `@spec-kit/shared/*` consumer.
- Give the wrapper and the deep-loop lane one shared provisioner (they duplicate the path list today — five vs six — and must stay in lockstep); have both derive the farm from main's `node_modules` inventory rather than a hand-maintained path list, so a new vendored top-level package or scope is picked up automatically.
- Treat `dist` reuse as an explicit, documented decision separate from the self-link fix: source edits under `runtime/`/`cli/` are still compiled-tested against main's `dist` unless a lane rebuilds (mirror-checkable via `plugins/tests/system-dist-freshness-guard.test.cjs`, which already exists).
- Enforce the invariant mechanically: assert every `@spec-kit/*` link's realpath is inside the worktree (the `node-modules-integrity` vitest cell above is the natural host), and make the provisioner fail loudly rather than skip when a self-link cannot be recreated.

## What would break it

- **The `shared/dist` gap in finding 6** — the mechanism as originally worded stops at "recreate the four links"; correct targets plus missing worktree-local `shared/dist` yields loud import failure. Fix the provision list first or the first lane run after relinking regresses.
- **Staleness through reused `dist`** — with `runtime/dist`/`cli/dist` (and a symlinked `shared/dist`) pointing into main, a worktree lane that edits source and runs a dist-loading path still executes main's build; source-vs-build skew looks like a flaky test, not a provisioning bug.
- **Cases reaching packages without passing through the farm** — anything resolving `@spec-kit/*` from a tree the provisioner forgot (a third `node_modules` added later), or any tool run with `preserveSymlinks` enabled through config rather than argv, re-opens either cross-checkout resolution or split module identity. The farm must cover every `node_modules` head that declares a workspace dependency, and the "no preserve-symlinks" rule must be checked, not assumed.

# Worktree Symlink Iteration 005

**Model:** `llmgateway/deepseek-v4.1-flash` at max thinking  
**Angle:** Proving isolation held: how a test can demonstrate that a lane resolved a workspace module from its own worktree rather than the main checkout, what the observable difference is, and whether the existing worktree test harness can carry that assertion

---

## Findings

- **The assertion technique already exists in-repo, already green, and is self-referential — which is exactly why it cannot see the leak.** `tests/unit/dependency-seams.vitest.ts:40-47` resolves bare specifiers from the runtime's vantage point and compares the realpath'd result against `realpathSync(resolve(runtimeRoot, 'node_modules')) + sep`, with the in-file comment (line 42): *"require.resolve() follows symlinks, so the comparison base must be realpath'd too — node_modules is a symlink when this tree is a git worktree"*. Run inside a worktree today, base and result both collapse through the wholesale link into the main checkout, so the guard passes vacuously: it proves the runtime uses *a* node_modules, never *its own*. An isolation assertion cannot borrow its expected root from the resolution system under test.
- **The observable difference, as a child process sees it:** `node -e "console.log(require.resolve('@spec-kit/shared/workspace/repo-root.mjs'))"` with cwd inside the lane prints the realpath of the file actually loaded — main-root prefix under a wholesale link, worktree-root prefix under a recreated self-link. Node canonicalizes module paths by default, and `runtime-bootstrap.cjs:26-36` deliberately strips `NODE_PRESERVE_SYMLINKS` ("the runtime never relies on preserved symlinks"). The entry point is stable whether or not `dist` is built because `shared/package.json` exports `"./workspace/repo-root.mjs"` by name. The only deep-loop importer exercising this today is `scripts/check-contract-drift.cjs:12` (`require('@spec-kit/shared/frontmatter/parse-frontmatter.js')`).
- **A value probe exists and is stronger than a path probe, and the module built for it is in-tree.** `shared/workspace/repo-root.mjs` walks up to `REPO_ROOT_SENTINEL = '.opencode/skills/system-spec-kit/SKILL.md'` (lines 1–45 of 71 read; the walk entry sits in the unread tail, so "starts from its own module location" is inferred — the test should pin it by construction). The pattern is confirmed live elsewhere: `system-skill-advisor-launcher.cjs:303` documents that `shared/embeddings/factory.ts`'s `resolveConfiguredDatabaseCandidates()` *"falls back to walking up from its own on-disk realpath, which resolves through the @spec-kit/shared symlink to that package's root — not this advisor's own database"* — the launcher pre-computes `MEMORY_DB_PATH` to dodge it. That is an in-production, user-visible instance of the leak, and it defines the assertion: a lane with a distinct marker beside its own copy must load its own bytes.
- **The harness that creates real worktrees can carry the assertion, but does not today — and its current expectation codifies the wholesale link as the desired shape.** `tests/unit/worktree-lifecycle.vitest.ts` builds a real temp git repo, plants an untracked dep root at `SHARED_DEPS_REL = '.opencode/skills/system-deep-loop/runtime/node_modules'`, then asserts `expect(realpathSync(linkPath)).toBe(realpathSync(join(fixture.repoRoot, SHARED_DEPS_REL)))` — passing *requires* the link to resolve into the fixture repo. The fixture has no `@spec-kit` self-link, no second physical copy of anything, and never spawns a node process, so nothing it does today can distinguish "resolved from the lane" from "resolved from main". It already has the rest: `vi.stubEnv('SPECKIT_WORKTREE_SHARED_PATHS', '')` in beforeEach (honoured by `resolveSharedPaths` in `worktree-lifecycle.ts`), real `createLineageWorktree`, `mkdtemp` roots. Carrying the assertion is a fixture extension, not a new harness.
- **The other harness is a worse fit.** `.opencode/bin/tests/worktree-session.test.sh` (whole file read) asserts only on stdout/stderr, exit codes, on-disk files and git config; it never executes a resolution in the allocated tree. `.opencode/skills/system-deep-loop/runtime/tests/stress/cli-adapter/fixtures/worktree-fixture.ts` exists (find listing) but was not read — UNKNOWN whether it creates real worktrees.
- **The runtime already has a second, git-anchored form of the same assertion.** `runtime-bootstrap.cjs:43-73` (`resolveContainmentRepoRoot`) compares `realpathSafe(artifactDir)` against `gitToplevel(cwd)` and redirects containment to *"the worktree that PHYSICALLY holds the writes"* only when they diverge. `git -C "$(dirname "$(node -p "require.resolve('@spec-kit/shared/workspace/repo-root.mjs')")")" rev-parse --show-toplevel` printing the lane toplevel states isolation in production's own terms and runs from bash or vitest.

## Recommended mechanism

- One new case in `worktree-lifecycle.vitest.ts`: fixture commits `shared/package.json` + `shared/workspace/repo-root.mjs` with a distinct lane-side marker/VERSION; fixture repo creates untracked `node_modules/@spec-kit/shared -> ../../shared`; set `SPECKIT_WORKTREE_SHARED_PATHS='node_modules'`; create; then spawn `process.execPath` with `-e` doing the `require.resolve` probe at `cwd: worktreeDir`.
- Anchor the assertion outside the system under test: realpath of the probe output equals `realpathSync(join(worktreeDir, 'shared', 'workspace', 'repo-root.mjs'))`, does NOT start with `realpathSync(fixture.repoRoot) + sep`, and the child reads the lane-side marker bytes. Add a negative control run at `cwd: fixture.repoRoot` asserting the main copy, so the probe is proven able to see both states.
- Update `dependency-seams.vitest.ts:40-47` in the same change: under split linking, vendored `zod/package.json` on a lane resolves to main's real path through its per-entry link, so the current `startsWith(own node_modules)` base fails. Replace it with vendored-resolves-from-the-tree-this-lane-uses, and add a NEW case: no `@spec-kit/*` self-link realpaths outside the lane root.
- Carry the probe on the lane path too, not only in fixtures — a resolution-origin check at lane bootstrap using the `resolveContainmentRepoRoot` comparison (`git rev-parse --show-toplevel` on the resolved module's directory) so a lane that silently degrades to the shared checkout is reported rather than passed.
- Keep the probe in a spawned `node` with a cleaned env (strip `NODE_PRESERVE_SYMLINKS`), never an in-process `import` from the vitest worker: the worker's cwd, module cache and env are not the lane's.

## What would break it

- Both existing guards encode the leak as the contract and will go red on the fix: `worktree-lifecycle.vitest.ts`'s `lstat(linkPath).isSymbolicLink() === true` plus realpath-into-fixture equality requires the wholesale shape (self-link-capable trees force `node_modules` to become a real directory with per-entry links, flipping that lstat), and `dependency-seams.vitest.ts:44-47` is only true while everything resolves through the single wholesale link. Relaxing either test until green deletes the only provenance guards in the repo.
- Two cheap false passes: if the lane fell back to the shared checkout (`createLineageWorktree` returns `{ok:false}` and callers degrade — stated in the module header), "resolved from its own tree" is trivially true; and if `NODE_PRESERVE_SYMLINKS` leaks into the probe process, the resolved string carries the worktree spelling while the bytes come from main. Assert lane-created-and-distinct first, strip the env, and prefer the value probe.
- A path probe alone is lexical and spellable — under preserved symlinks it reports the worktree spelling for a main-owned file. Distinct marker bytes at the two copies is the assertion that cannot pass unless the lane's own bytes were loaded.

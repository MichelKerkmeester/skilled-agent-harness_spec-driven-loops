# Worktree Symlink Iteration 003

**Model:** `llmgateway/deepseek-v4.1-flash` at max thinking  
**Angle:** Recreating the self-links inside a worktree: whether the recreated links should be relative or absolute, what each choice breaks (moving the worktree, nested worktrees, the containment path resolution that calls fs.realpath), and what happens when a linked tree is read-only or on a different filesystem

---

## Findings

- **Both link routines create only absolute, wholesale links today, so "recreate the self-links" first requires changing the creation shape, not just the link text.** `worktree-session.sh:325` is `ln -s -- "$src" "$dst"` with `src="$MAIN_ROOT/$rel"` (absolute); `worktree-lifecycle.ts:411-415` is `prepareDestinationParent(...)`, `rmSync(destAbs, {recursive:true, force:true})`, `symlinkSync(sourceAbs, destAbs, 'dir')` with `sourceAbs = join(repoRoot, ...segments)` (absolute). Neither creates per-entry links or a real worktree-local `node_modules`.
- **The six-path split means the four self-links live in two different trees. The deep-loop runner's list is six entries** (`worktree-lifecycle.ts:147-154`; the sixth is `.opencode/skills/system-deep-loop/runtime/node_modules`, which carries the `@spec-kit/shared` link), **while the launch wrapper's `default_shared_paths` in `worktree-session.sh` lists five** and omits it. A recreation pass must therefore be injected in both routines, not one.
- **Recreated self-links cannot live inside the currently-linked trees. Writing into a wholesale link writes into main, shared by every lane, and the codebase already declares that shape illegal for destinations.** `worktree-lifecycle.ts:332-335` resolves the destination parent through `canonicalTargetPath` → `realpathOrNull` (:257-271) and throws `destination escapes the worktree` unless the canonical parent is inside `worktreeRootReal` (:461). Relative-to-worktree self-links therefore presuppose a *real* `node_modules` and `@spec-kit` directory in the lane, with the vendored entries linked individually.
- **Relative link text is correct exactly when every directory from the link up to the lane root is a real directory; absolute text is the only form that tolerates a symlinked ancestor.** With the wholesale `node_modules` link, a recreated relative `@spec-kit/runtime -> ../../runtime` would re-anchor through the link's physical location and resolve into main — the original defect, unchanged. Placed under a real lane-local `node_modules/@spec-kit`, the same text resolves lane-locally under `git worktree add`, `git worktree move`, and any alias path (`/var` → `/private/var`, symlinked `SPECKIT_WORKTREE_BASE`), because both link and target share one physical tree.
- **Absolute text breaks under a relocation operation this repository actively uses.** `sk-git/scripts/migrate-legacy-branch-names.sh:121` runs `git worktree move "$dir" "$MAIN_TOPLEVEL/$new_dir"`, and `sk-git/changelog/v1.5.2.0.md:25` tells operators to "Relocate existing worktrees with `git worktree move <old> <new>` and run `git worktree repair` afterward." `git worktree move` rewrites git's registration, not symlink text; `repair` fixes git metadata only. An absolute self-link created at the old path then either dangles or, if a later lane occupies that path, silently reads another checkout.
- **The runtime's containment layer is realpath-based by explicit design, and it flips roots when things resolve outside the working tree — so link target choice decides which tree writes are attributed to.** `runtime-bootstrap.cjs:27-36`: `--preserve-symlinks` is deliberately unused because "write containment resolves every path through fs.realpath, and the repo root comes from the working directory"; `:44-69`: when "the artifact tree resolves (through symlinks) outside the working directory's git worktree … containment must run against the worktree that PHYSICALLY holds the writes." Same pattern at `hooks/goal/lib/goal-slice.cjs:248-255` (`realpathSync(root)` vs `realpathSync(absolute)`), and deep-loop artifacts reject state that "resolves outside the artifact directory" (`commands/deep/assets/deep-research-confirm.yaml:1470-1473`, with root from `realpathSync(artifactDir)` at `:1458`; `:1455-1456` even demands the lineages dir not be a symlink). Lane-local relative self-links realpath into the lane and keep containment on the lane; links into main move it to main.
- **There is already a production instance of a self-link's realpath escaping its own package, papered over with an explicit env var.** `bin/system-skill-advisor-launcher.cjs:301-305`: the DB-path candidate walk "resolves through the `@spec-kit/shared` symlink to that package's root — not this advisor's own database," so `MEMORY_DB_PATH` is computed explicitly. That is the exact class of failure recreating the link lane-locally removes (and why the recreation is semantic, not cosmetic).
- **Read-only vendored trees do not block the fix; they block the current shape.** Symlink creation needs write permission on the directory holding the link, never on the target, so links created *in the lane* pointing *into* a read-only store work. Patching `@spec-kit` inside a wholesale-linked read-only store fails (EROFS) and would be cross-lane unsafe anyway. Both current implementations pre-delete the destination first (`rm -rf -- "$dst"` adjacent to `worktree-session.sh:325`; `rmSync` at `worktree-lifecycle.ts:413`), so any store that must stay untouched has to be on the target side of the links, not the destination side.
- **Filesystem boundaries are not a tiebreaker between relative and absolute.** Symlinks carry a text target and cross mounts freely (unlike hard links, which nothing here uses); the difference is *what the text means later* — relative text is remap-safe under bind mounts/containers, absolute text is pinned to the mount path visible at creation.
- **A fresh worktree does contain the four link *targets*, but not their build output.** `.gitignore:43-51` ignores `node_modules/` and `dist/`; `.gitignore:75-86` ignores only compiled `.js`/`.d.ts` under `runtime/lib` and `shared`, so the `.ts` sources and `package.json` at `system-spec-kit/runtime`, `runtime/cli`, `shared`, and the deep-loop local `shared` are tracked and present. Relative lane-local links are non-dangling, but `runtime/dist` and `runtime/cli/dist` (the other two of the six linked paths) stay linked to main, so recreating self-links fixes resolution *identity* while the lane can still execute main's compiled output.
- **Nested worktrees are not a new nesting risk here, but "derive the text per lane" is still load-bearing.** `worktree-session.sh` refuses to nest (`AI_SESSION_CHILD=1` or already inside a linked worktree → exec in place), and `worktree-lifecycle.ts` builds each lineage tree from the `repoRoot` it is given, which may itself be a worktree. Linking per-entry from that `repoRoot` produces link→link→main chains (fine for reads; realpath lands in main, so vendored-dep paths must stay outside strict containment checks), but recreated self-links must always be computed against the lane being provisioned. Copying the outer lane's recreated links into an inner one reproduces the isolation bug one level down.

## Recommended mechanism

- Change both link routines (`worktree-session.sh` loop ending at :325; `worktree-lifecycle.ts:400-420` `linkSharedPath`) from "replace path P with one absolute symlink" to "make P a real directory; symlink each top-level entry of main's P into it; except for `@spec-kit`, create a real `P/@spec-kit` directory whose entries are recreated lane-locally." This satisfies the existing `prepareDestinationParent` guard instead of tripping it.
- Recreate the four self-links with **relative** text, computed from the link's directory to the lane's own source: `@spec-kit/runtime -> ../../runtime`, `@spec-kit/shared -> ../../shared`, `@spec-kit/cli -> ../../runtime/cli` under `<lane>/.opencode/skills/system-spec-kit/node_modules/`, and `@spec-kit/shared -> ../../../../system-spec-kit/shared` under `<lane>/.opencode/skills/system-deep-loop/runtime/node_modules/`. Relative is the only form that survives the repo's own `git worktree move` workflow (`migrate-legacy-branch-names.sh:121`) and it keeps `fs.realpath` inside the lane (`runtime-bootstrap.cjs:44-69`).
- Keep the vendored package entries as links into the main store (absolute or relative; either is fine because they are supposed to resolve to main). Do not attempt to recreate *those* lane-locally, and keep dependency roots excluded from strict "must realpath inside the worktree" checks, because they will legitimately resolve into main.
- Implement from one shared manifest of `(tree, linkPath, linkTarget)` rows used by both routines, including the sixth path that only `worktree-lifecycle.ts` links; do not derive it from npm workspace metadata alone, since the deep-loop `shared` link is not a workspace link (iteration-002).
- Treat `runtime/dist` and `runtime/cli/dist` as a separate decision: recreating self-links does not make them lane-fresh. Either keep them main-linked and state that lanes execute main's compiled output, or rebuild them in-lane when a lane's source changed.

## What would break it

- Any ancestor of a recreated link that is itself a symlink into main (today: `node_modules` itself). A relative self-link then re-anchors through the ancestor and reproduces the bug while looking fixed; the mechanism must assert the `node_modules`→`@spec-kit` chain is real directories before writing link text.
- Relocation via `git worktree move` (documented in `changelog/v1.5.2.0.md:25`): it rewrites git metadata, not link text. Relative self-links survive it; absolute ones dangle or silently point at whichever lane later takes the old path.
- A read-only or shared vendored store combined with any scheme that tries to write the recreated links inside the store rather than in the lane — `symlinkSync` fails, or succeeds and silently mutates a tree shared by every lane.

# Iteration 002

## Focus

Overlay or copy-on-write filesystem views, per-lane sandbox directories backed by a shared object store, and a single worktree with per-lane write redirection. The question is whether sharing immutable bytes can remove the 1.6 GB lane cost without sharing the Git status/index boundary or the runtime's physical path assumptions.

## Actions Taken

1. Re-read the packet measurements and the first iteration. The observed baseline remains 16.5 seconds without worktrees versus 149.7 seconds with worktrees for six lanes at concurrency 3, and 1.6 GB of checked-out files per tree; the packet says the Git object store is shared rather than copied [SOURCE: specs/system-deep-loop/045-fanout-write-containment-hardening/implementation-summary.md:98-110]. No new filesystem benchmark was run, so all alternative setup and byte deltas below are derived or inferred.
2. Traced the current Git and path seams. Worktree creation is a registered `git worktree add --detach ... HEAD`, followed by shared dependency linking and a lease [SOURCE: .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:560-628]. The lifecycle strips `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, object-directory, alternate-object, and config redirectors before invoking Git with an explicit `-C` repository root [SOURCE: .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:163-183,280-307]. Containment likewise invokes status with an explicit repository root and subtracts a pre-dispatch baseline from later status output [SOURCE: .opencode/skills/system-deep-loop/runtime/lib/deep-loop/write-containment.ts:282-336,689-773].
3. Traced the filesystem path seam. A worktree lane maps `writeSurface` and `containmentRoot` into its own tree, but some executor kinds retain the main checkout as `spawnCwd`; the publish target intentionally remains in the main checkout [SOURCE: .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-paths.ts:97-126]. The fan-out runner therefore samples the lane root and separately watches the main checkout when a lane can still start there. That checkout watch records a warning and leaves attribution open; it does not restore or assign the write to a lane [SOURCE: .opencode/skills/system-deep-loop/runtime/scripts/fanout-run.cjs:3591-3651,3880-3905].
4. Read the repository-specific link and compiled-entry behavior. Seven dependency/build roots are normally shared, and workspace-internal links are detected and rewritten to relative links into the lane; the packet reproduces a linked compiled `dist` entry guard that exits 0 while doing nothing when `argv[1]` and the imported module resolve through different physical paths [SOURCE: .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:138-158,384-507; specs/system-deep-loop/045-fanout-write-containment-hardening/research/worktree-symlinks/synthesis.md:45-75].
5. Consulted the authoritative OverlayFS and Git worktree/clone documentation for layer ownership, alternates, registration, move, and repair semantics [SOURCE: https://docs.kernel.org/filesystems/overlayfs.html; https://git-scm.com/docs/git-clone; https://git-scm.com/docs/git-worktree].

## Findings

- OverlayFS can share a read-only lower directory, but each mounted lane still needs its own upper and work directory; the kernel documentation explicitly treats the upper/work pair as per-mount state. That makes a shared lower plus per-lane upper/work a plausible low-copy implementation. Its setup time, initial apparent disk footprint, and changed-block amplification are UNKNOWN for this macOS-hosted repository because no benchmark was run. The 1.6 GB and 149.7-second packet measurements must not be projected onto or replaced by those unknowns [SOURCE: https://docs.kernel.org/filesystems/overlayfs.html; specs/system-deep-loop/045-fanout-write-containment-hardening/implementation-summary.md:105-106].
- An overlay view preserves exact attribution only when the process, every child process, the containment scanner, and the Git metadata all refer to that lane's merged view. A shared lower is compatible with attribution because it is read-only; a shared upper/work directory is not. More importantly, a lower `.git` plus a shared index gives lanes a common status/write owner even if their file bytes are copy-on-write. The current lifecycle cannot accept an environment-only fix for that: it strips the Git redirection variables and resolves lifecycle operations through `git -C` [SOURCE: .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:163-183,294-307]. A private per-lane Git admin directory and index are therefore required, either by a real linked worktree or by a new runtime seam.
- A per-lane sandbox directory with a shared object store has the same ownership rule. If each sandbox is a real linked worktree or an equivalent checkout with a private index, HEAD/worktree metadata, and status root, attribution stays exact while immutable objects may be shared. If it is only a directory that redirects writes back into one checkout, status remains combined and attribution is not exact. The packet already shares the object store for the measured worktree lanes, so object sharing alone cannot explain a checkout saving [SOURCE: https://git-scm.com/docs/git-clone; specs/system-deep-loop/045-fanout-write-containment-hardening/implementation-summary.md:105-106].
- A single worktree with `GIT_INDEX_FILE`, `GIT_WORK_TREE`, or related environment redirection has low theoretical setup and near-zero additional checkout bytes, but it is not exact in this runtime. The lifecycle deliberately deletes those redirectors, containment passes an explicit `repoRoot` to `git -C`, and the path resolver can leave `spawnCwd` at the main checkout for directory-argument executors [SOURCE: .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:163-183,294-307; .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-paths.ts:109-126]. Redirecting only known writes would miss ordinary cwd-relative writes, child processes, symlink resolution, and status scans. Redirecting every filesystem operation would be a new virtual-lane/filesystem-view implementation, not a transparent one-worktree optimization.
- The current churn detector does not turn shared writes into exact ownership. It samples out-of-scope dirty paths at the selected containment root and latches preserve mode after a burst; when a lane can start in the shared checkout, the separate checkout watch records `checkout_write_detected` as report-only because another writer may own the path [SOURCE: .opencode/skills/system-deep-loop/runtime/scripts/fanout-run.cjs:3611-3651,3880-3905]. An overlay upperdir hidden outside the merged root would be invisible if the detector continues scanning the main checkout. It works only when `containmentRoot`, `git -C`, and the write view all name the same merged lane root.
- Overlay or copy-on-write does not repair symlink topology. A wholesale link from a lane dependency root to the main checkout still resolves there; a relative workspace self-link under a symlinked ancestor can still re-anchor to the source checkout. The existing runtime detects those internal links and makes the containing scopes real before writing relative lane targets, which is a path-rewrite operation COW does not provide [SOURCE: .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:394-475; specs/system-deep-loop/045-fanout-write-containment-hardening/research/worktree-symlinks/synthesis.md:45-75]. The same physical-path mismatch can preserve the compiled entry-point guard's silent no-op. Copying or mounting the dependency/build roots into the lane can fix it, but consumes changed bytes and must preserve the seven-root closure [SOURCE: .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:138-158].
- A COW directory that is not registered with Git may be cheap to create and exact at the ordinary file layer if it has private Git metadata, but it is not a `git worktree`. Git's move/repair commands operate on registered linked worktrees and their administrative state; they do not discover or relocate an arbitrary overlay mount, sandbox, upperdir, or external mount table [SOURCE: https://git-scm.com/docs/git-worktree]. A registered worktree can retain Git-managed relocation semantics, while the COW view still needs its mount paths, upper/work paths, and any absolute dependency links to be re-established. Relative self-links remain a requirement for relocation [SOURCE: .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:466-475; https://git-scm.com/docs/git-worktree].
- Runtime bootstrap's realpath-based containment selection reinforces the physical-root requirement. It may redirect containment to the Git top-level that physically contains a symlinked artifact, but it does not virtualize arbitrary process filesystem calls or make a main-checkout path mean a lane path [SOURCE: .opencode/skills/system-deep-loop/runtime/scripts/runtime-bootstrap.cjs:23-73]. An overlay proposal therefore needs an explicit lane root handed through bootstrap, path resolution, child process cwd, Git status, and the checkout watch; otherwise it can report a clean lane while writes landed in the lower or shared checkout.

## Comparison by Mechanism

| Mechanism | Setup and disk posture | Exact attribution in this repository | Main breakage and relocation posture |
|---|---|---|---|
| Overlay lower + private upper/work + private Git admin | Potentially a fraction of a full copy; setup, changed blocks, and mount overhead unmeasured | Yes only when all process paths, status, index, and metadata are lane-private | Shared dependency symlinks and compiled guards still fail unless links/build roots are reanchored; Git `worktree move` does not move the mount contract |
| COW/sandbox directory + shared object store | Potentially low initial disk; actual copy-on-write behavior unmeasured; object savings are already present in baseline | Yes only with a private index/worktree metadata boundary; no with write-back into one checkout | Same dependency/self-link/churn risks; registered worktree can move, arbitrary COW directory requires external repair |
| One worktree + environment write redirection | Lowest theoretical setup and extra disk | No under current `git -C`, redirector stripping, explicit containment root, and shared cwd behavior | Combined status/churn and shared symlink/guard paths; no independent Git move target |
| Shared lower or shared object store without private upper/index | Low storage | No; immutable object sharing is not write attribution | Index, status, and upper writes race; relocation does not create lane ownership |

## Questions Answered

- Overlay and sandbox techniques can approach the desired cost only by adding a private per-lane view and private Git metadata. A shared lower or object store is safe to share; the upper/work directory, index, worktree admin state, and status root are not.
- A single physical worktree cannot provide exact attribution through environment-only write redirection in this runtime. Achieving it would require a new path-routing seam covering all filesystem and Git operations, which is logically a set of lane views.
- Filesystem COW does not repair the seven dependency roots, workspace self-links, or compiled entry-point guard. Those failures are caused by physical link targets and `argv[1]`/module realpath identity, so they require lane-local materialization or the existing self-link rewrite.
- The churn detector can validate a COW lane only if it scans the same merged root used by the lane and Git. The existing shared-checkout watch intentionally warns without assigning ownership, so it cannot supply exact attribution.

## Ruled-Out Directions

- One-worktree environment-only write redirection is ruled out as an exact solution: current lifecycle Git calls strip the redirectors, containment uses explicit roots, and the shared-checkout watch is report-only [SOURCE: .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:163-183,294-307; .opencode/skills/system-deep-loop/runtime/scripts/fanout-run.cjs:3611-3651,3880-3905].
- A shared overlay upper/work pair or shared Git index is ruled out: OverlayFS requires per-mount upper/work state, and a shared mutable Git boundary cannot attribute status or writes to one lane [SOURCE: https://docs.kernel.org/filesystems/overlayfs.html; .opencode/skills/system-deep-loop/runtime/lib/deep-loop/write-containment.ts:329-336,740-773].
- An unmanaged COW directory is ruled out as a drop-in replacement for registered worktrees when Git move/repair is required [SOURCE: https://git-scm.com/docs/git-worktree].
- A wholesale COW view of the seven shared dependency roots is ruled out until self-links and compiled guards are reanchored; the packet demonstrates the silent no-op failure that otherwise survives status checks [SOURCE: .opencode/skills/system-deep-loop/runtime/lib/deep-loop/worktree-lifecycle.ts:138-158,394-475; specs/system-deep-loop/045-fanout-write-containment-hardening/research/worktree-symlinks/synthesis.md:51-75].

- **Copy-back does not exist in code — only as a named step.** No `git worktree`, `copyBack`, or publish function exists anywhere under `runtime/`; the only matches are comments. The spec requires "copy-back of the lineage directory" (spec.md:70, REQ-005 at spec.md:115), the plan places it "between the guard and the settle" (plan.md:76), and the only failure contract is "the worktree is retained rather than removed, and its path is named on the failure event" (spec.md:192, decision-record.md:298). Ordering relative to the ledger settle, target claiming, and overwrite policy are all unspecified.

- **The publish target is label-keyed, not run-keyed — two runs collide on the same path.** `lineagesDir = path.join(baseArtifactDir, 'lineages')` (fanout-run.cjs:2674) and `lineageDir = path.join(lineagesDir, lineage.label)` (fanout-run.cjs:2862) mean `<specFolder>/<mode>/lineages/<label>` is identical for any two fan-out runs over the same packet using the same label — and for every retry attempt within one run (attempt at 2860, dir at 2862). `fs.mkdirSync(lineageDir, { recursive: true })` (fanout-run.cjs:2864) asserts no ownership; a pre-existing dir is silently reused.

- **The parent's own post-exit writes land inside the lineage dir and must precede copy-back or they race the published copy.** After the executor exits the runner writes `logs/fanout-lineage.out/.err` (fanout-run.cjs:3152–3157), then `runSalvageSweep` writes `iterations/iteration-NNN.md` unconditionally via `writeFileSync` (fanout-salvage.cjs:148, 160–164) and appends `salvaged_from_stdout` to the state log via `mergeJsonlUnderLock` (fanout-salvage.cjs:157). The quarantine writer also writes `containment/quarantine/` under `artifactDir: lineageDir` (write-containment.ts:985; call site fanout-run.cjs:3265–3273). Under the plan's ordering (guard → copy-back → settle) all of these are worktree-resident and get published — but any parent write that ever targets the main-checkout copy post-publish (a retry's salvage, a later attempt's logs) races a subsequent copy-back from that attempt's worktree.

- **Salvage's own merge semantics prove partial overwrite is the intended behavior — and copy-back can destroy it.** Salvage deliberately skips a non-empty iteration file (fanout-salvage.cjs:124–126), i.e. it merges into existing content rather than replacing the dir. A copy-back that overwrites per-file or wholesale would clobber exactly the content salvage was designed to preserve, while a copy-back that merges naively would intermix a stale previous copy's state log with the new run's — and `readLineageStateRecords`/`findMaxIterationsPolicyViolation` (fanout-run.cjs:3172–3179) consume that log, so a surviving stale `deep-research-state.jsonl` corrupts the *next* run's policy check.

- **The repository already bans the naive remedy.** The plan's execution rules state "No new code path may delete a file. Preserve, copy and restore are the only three outcomes" (plan.md:143). So copy-back may not `rm -rf` an existing `lineages/<label>`; a stale or foreign copy must be renamed aside, never deleted — which is also the only semantics consistent with the packet's preserve doctrine for the operator-as-writer case.

- **An ownership predicate for exactly this question already exists and is already wired in.** `discoverForeignLiveRunDirs` (fanout-run.cjs:584–587) answers "is this run dir owned by a live foreign run" using `isStaleLoopLock` (loop-lock.ts:549–554: TTL-expired OR dead `ownerPid`), and it is already called at the containment site (fanout-run.cjs:3269) — but only to *exempt* foreign dirs from attribution, never to gate a write. `acquireLoopLock(lockPath, data)` is path-agnostic (loop-lock.ts:565+), carries `ownerPid` + `acquireNonce` identity (loop-lock.ts:140–141, 495–504), fails when held (`LoopLockHeldError`, loop-lock.ts:66), and `releaseLoopLock` requires the nonce (loop-lock.ts:717). The machinery to govern copy-back exists; its scope just never covered `lineages/`.

- **Atomicity has a precedent but a hard constraint.** The runner already publishes JSON via tmp-write + `fs.renameSync` (fanout-run.cjs:1106–1109) — atomic on the same filesystem. But POSIX `rename` cannot replace a non-empty directory, so a directory-level atomic publish of `lineages/<label>` is impossible in one call; it requires staging-dir rename plus a rename-aside of any existing target, i.e. two renames with a window where the path is absent. There is also no completion marker separating a fully published lineage dir from a torn one — the state log's terminal record lives inside the dir being published.

- **Settle ordering is partially pinned but the failure channel is not.** Plan.md:76 puts copy-back before settle, and the worker must do it before returning `output` (fanout-run.cjs:3312–3349) since the pool settles on return. But the `output`/`failure` shapes have no field for "copy-back failed, worktree retained at X" — spec.md:192 requires the event to name the retained worktree path, which means either a new ledger event before settle or a failure subtype the pool can map; neither exists today.

- **`markOrphanedLineages` handles the ledger side of a stale previous run, not the directory side** (fanout-run.cjs:2799) — it marks prior incomplete lineages orphaned in `orchestration-status.log` but does nothing to `lineages/<label>` on disk. The "stale previous copy" writer is therefore currently unhandled at the filesystem level: a second run inherits whatever the first left.

## Recommended design

- **Publish by staged rename, never in-place write.** Copy-back builds `lineages/.<label>.incoming-<runId>-<attempt>` in the *main checkout* (same filesystem → `rename` atomic; avoid staging in the worktree, which may be on a different mount → EXDEV), fills it completely, writes a `PUBLISHED` manifest (file list + hashes + runId + attempt) last, then under the claim lock does the two-rename sequence: existing `lineages/<label>` → `lineages/.attic/<label>-<ts>` (preserve, never delete per plan.md:143), then `.incoming-*` → `<label>`.

- **Claim via the existing loop-lock on a sibling path.** `acquireLoopLock(lineages/<label>.copy-lock, { ownerPid, packetId: runId, acquireNonce })` held across the entire existence-check + rename transaction (closes check-then-act TOCTOU). A live foreign holder (different runId, `!isStaleLoopLock`) → copy-back refuses: retain worktree, emit failure event naming it (spec.md:192's existing contract). A stale holder → fenced reclaim via nonce-verified release, then proceed. Same-runId retries may republish — the claim record carries runId+attempt so attempt N+1 recognizes its own prior publish.

- **All parent writes stay inside the worktree lineage dir before copy-back.** Logs (3152–3157), salvage (3161), quarantine (3265–3273) all already write under `lineageDir`; keeping `lineageDir` worktree-resident until publish makes the worktree copy the single source and makes the parent's salvage pass a non-competitor — it is sequenced strictly before copy-back inside one process. Nothing in the worker may touch the main-checkout `lineages/<label>` except the publisher.

- **Overwrite policy per writer:** (a) parent's own salvage/logs — non-issue by ordering; (b) second fan-out, same label — refused by the live-lock check, its copy goes to a distinct claimed path or the run fails the lane with the worktree retained; (c) operator edits to a published dir — never overwritten in place; a republish moves the whole dir (operator edits included) to `.attic/`; (d) stale previous copy — same rename-aside path, gated on staleness proof (dead PID or expired heartbeat + nonce), never on age or arrival order.

- **Extend the startup sweep to staging residue.** The runner's own-prefix sweep (decision-record.md:265) must also remove `lineages/.<label>.incoming-*` and stale `.copy-lock` files, so a publisher that dies mid-transaction leaves reclaimable state rather than a permanent block.

## What would break it

- **Cross-mount worktrees.** If the worktree base resolves to a different filesystem than the main checkout (the runtime already tolerates symlinked artifact trees — fanout-run.cjs:2690, runtime-bootstrap.cjs:47), staging-inside-worktree + `rename` fails with EXDEV and the whole atomic design collapses into per-file `copyFileSync` — torn publishes return. Staging must be created in the main checkout, which reintroduces a visible partially-filled dir unless the `.incoming-` prefix is universally ignored by readers (`discoverForeignLiveRunDirs`, operator tooling).

- **The two-rename gap.** Between rename-aside and rename-in, `lineages/<label>` does not exist; a foreign run's `findMissingLineageArtifacts` or a human's `ls` sees ENOENT, and if the publisher dies in the gap the prior copy sits in `.attic/` with nothing pointing at it. Recoverable (attic sweep + ledger event) but must be specified, or "copy-back failed" becomes ambiguous between "not published" and "published but old copy displaced".

- **Lock-free readers can't see the claim.** `discoverForeignLiveRunDirs` and any future reader of `lineages/<label>` do not check `.copy-lock`; ownership is enforced only among writers that voluntarily acquire it. The operator and any runner code path that writes the target without acquiring the lock (the current `mkdirSync` at 2864 is exactly such a path) bypass the protocol entirely — so the claim must be enforced at the single copy-back call site and every other write to `lineages/` must be audited to go through it.

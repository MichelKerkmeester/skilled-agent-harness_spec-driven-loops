Now: the lock filenames constant, whether the runner itself holds a run-level lock, and how `lineageDir` labels are minted.## Findings

- **The lease machinery widens with zero schema change — but only as an ownership/liveness record.** `acquireLoopLock(lockPath, data)` takes an arbitrary path, and `LoopLockData` already carries `ownerPid/ttlMs/lastHeartbeatIso/packetId/acquireNonce/phase` (`.opencode/skills/system-deep-loop/runtime/lib/deep-loop/loop-lock.ts:14-24,565-590`); `runtimeKind: 'main'` already covers a runner-written lease (`loop-lock.ts:20`). Fenced single-winner reclaim (`tryReclaimStaleLoopLock`, `loop-lock.ts:286-303`) and nonce-checked refresh/release (`lockIdentityMatches`, `loop-lock.ts:495-509`) all transfer as-is.
- **Critical constraint: the module heartbeats exactly ONE lock per process.** `startHeartbeat` calls `stopHeartbeat()` first and stores a single module-global `heartbeatTimer` (`loop-lock.ts:57,681,699-706`). N lineage-worktree leases plus a copy-back lease cannot ride `startHeartbeat` — each acquire cancels the previous heartbeat. Widening therefore requires either a token registry in the module (a change to shared code) or the runner calling exported `refreshLoopLock` per lease inside its existing progress-heartbeat loop — the latter works today.
- **The codebase already uses the lease for exactly this job: directory-level ownership attribution.** `holdsLiveLoopLock` + `discoverForeignLiveRunDirs` scan packet dirs for `.deep-research.lock`/`.deep-review.lock` and treat a non-stale lock as proof a directory tree belongs to a live run (`fanout-run.cjs:490,549-622`). That is precisely the semantics a worktree sweeper needs — and the comment at `fanout-run.cjs:580-582` already encodes the right rule: a stale lock proves nothing.
- **The worktree *name* needs no lease at all.** Per-run label uniqueness is enforced at config validation (`executor-config.ts:905-911`), and the planned name already embeds runId (`plan.md:70`: `<prefix>-<runId>-<label>`); git serializes its own worktree registry under `$COMMON/worktrees/`. The shared surface on the prefix is *liveness attribution for sweeping leftovers*, not allocation.
- **The reaper will never clean the planned worktrees.** Detached worktrees are report-only (`worktree-reaper.sh:191-194`), so a dead runner orphans them forever unless a new sweep path exists — the lease is the missing liveness input for that sweep.
- **But a lease alone is weaker than the reaper's existing bar.** Staleness keys on `processAlive(ownerPid)` (`loop-lock.ts:549-555`); the owner would be the runner, while executor children can outlive it cwd'd inside the worktree. The reaper already closes this hole with `_busy_pid_in` (lsof `/proc` cwd check, `worktree-reaper.sh:142-167`) — worktree reclaim needs lease-stale AND no-cwd-holder, not lease-stale alone.
- **The copy-back target is the genuinely shared surface, and a lease only half-covers it.** `lineageDir = lineagesDir/<label>` is run-agnostic (`fanout-run.cjs:2674,2862`); `runId` exists but is not in the path (`fanout-run.cjs:2697`). A lease on the target serializes *cooperating* publishers but produces last-writer-wins overwrite — sequential data loss, not corruption — and cannot bind the non-cooperating writer (a human editing that path checks no lock).
- **Tree publish atomicity is a separate protocol the lease pattern does demonstrate.** `rename(2)` is atomic on directories, so the `tryReclaimStaleLoopLock` move-aside trick (`loop-lock.ts:286-303`) works on the lineage dir itself; but rename onto a non-empty target fails, so publish needs staging-dir + fenced swap, not just a lock.
- Lease files inside the worktree are self-cleaning but die with it; for postmortem ownership a mirror under the common git dir (like `worktree-number.lock`, `worktree-naming.sh:82`) is the established location. Lock names must differ from `DEEP_LOOP_LOCK_FILENAMES` or `discoverForeignLiveRunDirs` misreads them — no collision today since it only scans under `specs/` (`fanout-run.cjs:540-546`).

## Recommended design

- **Use the lease as evidence, not as a mutex.** The runner writes `.fanout-lineage.lock` into each worktree root at creation and refreshes every lease via `refreshLoopLock` on its existing heartbeat loop (never `startHeartbeat`). A sweeper removes a leftover worktree only when the lock is stale AND an lsof-cwd check (lift `_busy_pid_in` verbatim) finds no process inside.
- **Run-key the stage, lease-fence the final name.** Copy back into `lineages/.staging-<runId>-<label>`, then acquire `lineages/<label>.publish.lock`; if `<label>` is absent → rename staging in; if present and its publisher lock is stale → rename it aside (the existing fence) and rename in; if present and live → publish to `lineages/<label>.run-<runId>` and record an advisory. Silent overwrite becomes impossible.
- **Prefer eliminating the sharing over arbitrating it:** keying the copy-back target by runId removes the cross-run hazard outright; the lease then only answers "is this leftover owned by something live," which is what it is genuinely good at.
- Keep lock filenames distinct from `.deep-research.lock`/`.deep-review.lock` so `discoverForeignLiveRunDirs` semantics stay "foreign run dir" (`fanout-run.cjs:490`).

## What would break it

- The single-heartbeat module: naive per-lineage `startHeartbeat` calls silently cancel each other (`loop-lock.ts:681`), leaving the last lease's worktree looking dead mid-run and eligible for reclaim.
- Runner-death-with-live-executor: pid-keyed staleness fires while detached children still hold cwd inside the worktree — reclaim pulls the ground out unless the reaper's `_busy_pid_in` check is carried over (`worktree-reaper.sh:142-167`).
- The lease is advisory: `git worktree prune/remove`, human editors, and non-fanout tools never consult it; without the publish-lock on the final `<label>` name, two sequential runs still silently overwrite each other's results.

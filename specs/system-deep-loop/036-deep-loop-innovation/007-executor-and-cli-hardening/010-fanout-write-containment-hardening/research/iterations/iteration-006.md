## Findings
- **The enforced recursion guard is runner-level, centralized, and fail-closed**: it fires only when BOTH signals hold — the seat inherited `SPECKIT_FANOUT_LINEAGE_ID` non-empty (fanout-run.cjs:2888-2890) AND the seat's kind is already on `SPECKIT_CLI_DISPATCH_STACK` — then it throws `recursive <kind> dispatch blocked for lineage <label>: <kind> already on SPECKIT_CLI_DISPATCH_STACK` (fanout-run.cjs:2891-2897). Both signals are needed because `AI_SESSION_CHILD=1` alone is ambient — sk-git's launch wrapper also exports it for descendants (bin/worktree-session.sh:342; bin/README.md:189).
- **The guard is a same-kind membership check, not a cycle detector**: the error says the kind is "already on" the stack, and the comment says the stamp exists so "a seat that tries to recursively launch the same kind is detectable" (fanout-run.cjs:2900-2902). The membership reading implies at most ONE seat of each executor kind per ancestry chain — a depth ceiling equal to the kind roster (6) — but `detectSameKindFromStack`'s implementation was not read: the one-per-kind reading is INFERRED, its exact semantics UNKNOWN.
- **Breadth has no guard at all**: nothing in the recursion layer counts or caps concurrent lineages; the same-kind check (fanout-run.cjs:2893) constrains only kind ancestry, and sibling spawns are stamped and admitted (fanout-run.cjs:2900-2906).
- **The one documented binary-level nesting blocker is codex, and it fails silently**: "A codex process cannot spawn another codex from inside its own sandbox. The nested child dies at startup with `failed to initialize in-process app-server client: Operation not permitted` (observed 2026-09-02 on codex-cli 0.151.0 under `--sandbox workspace-write`), and the parent reads that as a failed iteration rather than a route violation. So when codex is itself the executor of a deep-loop fan-out lineage or any other orchestrating session, it must do each iteration's work in-process ... and never dispatch a second codex" (cli-codex/SKILL.md:286-292; remediation: "Grep that exact message"). No equivalent binary-level death is documented for the other five: UNKNOWN.
- **Model-side self-invocation guards are unevenly documented across the six**: cli-codex refuses to load on 3 signals — any `CODEX_*` env, `codex` in process ancestry, or `~/.codex/state/<id>/lock` — "Self-invocation creates a circular dispatch loop" (SKILL.md:46, 63, 89); cli-opencode's ADR-001 uses the same 3-layer shape (`OPENCODE_*` / `opencode` ancestry / `~/.opencode/state/<id>/lock`) and refuses on any positive UNLESS the prompt carries explicit parallel-session keywords, which permit a SEPARATE session id and state directory — the only documented breadth-1 escape hatch (SKILL.md:56, 77, 239); cli-cursor's layer 3 is "honestly weaker than the siblings' layer 3" — "No lock-file convention is documented for Cursor CLI (unlike Codex's ~/.codex/state/<id>/lock) ... Absence of a detected signal here is NOT proof no session is active" (SKILL.md:84-91, `CURSOR_INVOKED_AS` probe); cli-claude-code: "check `$CLAUDECODE` for nesting" (SKILL.md:266). For cli-pi and cli-devin no detection signal surfaced in my searches: their guard behavior is UNKNOWN.
- **cli-pi's documented recursion bound IS the shared runner, not a pi-side mechanism**: "Recursion bounds | A fan-out lineage and a repeated dispatch stack are still refused by the shared runtime" (cli-pi/README.md:163), consistent with delegation: execution of every kind "delegate[s] to the already-shipped deep-loop runtime at .../fanout-run.cjs" (cli-codex/SKILL.md:168; cli-codex/README.md:40) — one recursion surface, six routing skins.
- **Same-kind recursion is additionally machine-tested pre-spawn at the adapter layer**: hermetic stress scenario cli-codex:EC-014 "blocks same-kind recursion before spawning codex" (cli-codex/manual-testing-playbook/stress/self-invocation.md:3-6, 20).
- **The skill-layer default blocks breadth, not depth: one dispatch at a time, operator-gated**: "Default: launch ONE cli-* dispatch at a time across the cli-* family ... Only launch the next dispatch after the prior one is dead and RSS has dropped", with parallel-N only "when the operator explicitly authorizes N parallel dispatches", cleanup by captured PID because a blanket `pkill -9 -f "codex exec --model"` "kills EVERY running `codex exec` process on the machine, including the operator's unrelated codex sessions" (cli-codex/SKILL.md:281) — a real multi-lineage casualty mechanism. The fanout runner is the sanctioned bypass: "the deep-loop runtime is the execution authority" over "a packet-local Codex execution adapter" (cli-codex/SKILL.md:291-292; also README.md:40, SKILL.md:168).
- **The worktree-wrapper guard stack EXEMPTS children rather than isolating them, so it can never supply the per-lineage worktree**: `AI_SESSION_CHILD=1` → `exec_in_place` (bin/worktree-session.sh:159-160), plus the structural backstop "already inside a linked worktree (`git --git-dir` differs from `--git-common-dir`)" (bin/README.md:189; sk-git/feature-catalog/feature-catalog.md:65); the skills instruct the same: a dispatched seat "must SHARE the parent's worktree rather than allocate its own" (cli-codex/SKILL.md:282); the guard hook skips children — "they are expected to share the parent's tree, so they never warn" (hooks/git-worktree-guard/README.md:31, 91; bin/worktree-guard.sh:34) — and the session-cleanup plugin skips them too (system-spec-kit/manual-testing-playbook/plugins-and-hooks/session-cleanup-plugin.md:65). So per-lineage worktrees must be created by the runner itself, and if they were routed through any existing mechanism the failure would be exit-0 sharing, invisibly.
- **A guard that DID block legitimate dispatch work, now fixed in code**: the spec-gate classify step injected the Gate-3 question into children even with `ENFORCE=0` — "that only stops the deny, while the classify step still injects the Gate-3 question, which a cli-opencode child then answers instead of doing its work. DISABLED makes both classify and enforce no-ops" (fanout-run.cjs:2871-2876, keys `SYSTEM_SPEC_GATE_DISABLED: '1'` + `AI_SESSION_CHILD: '1'` at 2878-2879; `SYSTEM_SPEC_GATE_ENFORCE=0` also expected in the captured child env, cli-cursor/manual-testing-playbook/stress/child-spec-gate.md:68).
- **The prompt-side waiver that the hub skills mandate is NOT in the runner's prompt**: all six skills require "Set `AI_SESSION_CHILD=1` ... AND state the exemption in the prompt. ... the reader being waived is a model, and a model cannot see an environment variable" (cli-codex/SKILL.md:282; cli-opencode:256, cli-cursor:310, cli-devin:362, cli-pi:208, cli-claude-code:282 — all copying shared/references/child-dispatch-preamble.md). The waiver text exists for the deep-review path as a template ("## GATE 3 PRE-RESOLVED — AUTONOMOUS NON-INTERACTIVE DISPATCH (do not halt)", deep-review/assets/prompt-pack-iteration.md.tmpl:4), but fanout-run.cjs contains no "Gate 3"/"documentation-scope" waiver wording anywhere (grep over the file: only comment lines 2871-2876) — whether the workflow YAML a lineage orchestrates carries it: UNKNOWN.
- **An env-allowlist trap that 045's worktree work must clear**: `buildExecutorDispatchEnv` filters the parent env to a per-kind allowlist, so the guard keys are "re-injected here" (fanout-run.cjs:2877) and the SPECKIT_\* lineage/state-dir keys are applied AFTER the filter "to preserve the per-replica lockfile isolation they provide" (fanout-run.cjs:2903-2906). The only kind-conditional per-lineage state today is `CLAUDE_CONFIG_DIR` (fanout-run.cjs:2880-2881) plus `stateEnvKey → stateDir` (2879); no `OPENCODE_*`/`CODEX_*`/pi/cursor/devin equivalents — whether same-runtime concurrent lineages collide on the host's state dirs (the thing the Layer-3 locks of ADR-001 exist to detect) is UNKNOWN.

## What this means for unlimited concurrency
- Breadth is genuinely uncapped in the guard layer — no counter, no ceiling, only resource budgets (iteration-005) — while depth is implicitly capped by the one-kind-per-chain membership semantics of `SPECKIT_CLI_DISPATCH_STACK` (≈6 levels, INFERRED), so "effectively unlimited" holds for parallel lineages, not for lineage trees.
- Of the six runtimes, only cli-codex has a known hard nesting failure, and it is absorbed as an ordinary failed iteration (cli-codex/SKILL.md:286) — a tree in which a cli-codex seat orchestrates further fails systematically with no recursion signal, unless the runner learns to grep that exact message.
- The existing exemption architecture (`AI_SESSION_CHILD=1` → exec-in-place; structural `git --git-dir` backstop; guard-hook and cleanup-plugin skips) means the candidate structural answer — one worktree per lineage — must be entirely runner-owned; nothing today would warn if the runner relied on the wrapper, it would just silently share the orchestrator's checkout (bin/README.md:189; cli-codex/SKILL.md:282).
- Guard env plumbing is a silent-drop hazard: anything 045 adds (worktree path, lockfile dir, per-lineage state) must be applied after `buildExecutorDispatchEnv`'s per-kind allowlist, exactly as the guard keys and per-replica lockfile keys already are (fanout-run.cjs:2877, 2903-2906).

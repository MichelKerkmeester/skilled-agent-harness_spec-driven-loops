# Worktree Symlink Iteration 002

**Model:** `llmgateway/deepseek-v4.1-flash` at max thinking  
**Angle:** Deriving the self-link set instead of hardcoding four: how to detect reliably which entries in a dependency tree point back at repository source rather than at vendored packages, across the layouts npm, pnpm and yarn produce, and whether package.json workspace declarations are a sounder source than filesystem inspection

---

## Findings

- **The three system-spec-kit self-links are npm workspace links, and npm records them in the lockfile as machine-readable link entries — this is the soundest declarative source for the npm layout.** `.opencode/skills/system-spec-kit/package.json` declares `"workspaces": ["shared", "runtime", "runtime/cli"]` (private workspace root at the skill dir, not the repo root). `package-lock.json:1832–1843` carries exactly three entries — `node_modules/@spec-kit/cli` resolved `runtime/cli`, `node_modules/@spec-kit/runtime` resolved `runtime`, `node_modules/@spec-kit/shared` resolved `shared`, each `"link": true` — and the `packages` section (lines 5607–5650) records the inter-member `file:` specs (`@spec-kit/shared: file:../shared`, `file:..`, `file:../../shared`). The lockfile set matches the on-disk set 1:1. `resolved` is relative to the install root, so it doubles as the re-link target.
- **The fourth self-link is NOT a workspace link. `ls .opencode/skills/system-deep-loop/runtime/node_modules/@spec-kit` → `shared/`; `.opencode/skills/system-deep-loop/runtime/package.json` has no `workspaces` field at all** — the link comes from a cross-tree dependency, `"@spec-kit/shared": "file:../../system-spec-kit/shared"`. A workspace-declaration-only derivation returns 3 of 4 links and silently drops this one. **The given hypothesis that package.json workspace declarations are a sounder source is wrong: they are a proper subset.**
- **The observed link outcome is explained by config, and nothing here flips npm's link-vs-copy behavior.** `.opencode/skills/system-spec-kit/.npmrc` contains only `install-strategy=hoisted`; it does not set `install-links=true`, so npm's default for directory `file:` deps (symlink, not pack-and-copy) governs — consistent with the link that exists on disk. A flip of that setting would change outcomes without changing any declaration.
- **Layout reality in this repo: npm, per install root.** `.opencode/` holds `package-lock.json` plus `bun.lock`; `system-spec-kit/` and `system-deep-loop/runtime/` each hold their own `package-lock.json` and node_modules — three independent install roots. No `pnpm-lock.yaml`, `pnpm-workspace.yaml`, or `yarn.lock` seen in any of the three roots. (Caveat: the `find` tool skips the hidden `.opencode` tree entirely — a `find package.json` under it returned "No files found" while `ls` shows the files — so enumeration here was done by `ls` + explicit paths.) pnpm/yarn behavior below is stated from their documented layouts, not observed here.
- **Cross-layout derivation, per manager:**
  - **npm ≥7:** `packages["node_modules/<name>"].link === true` in the lockfile, `resolved` = target relative to install root. Covers workspaces *and* `file:` dir deps *and* transitive `file:` deps in one place. `node_modules/.package-lock.json` mirrors the actually-installed tree and catches drift from the committed lockfile.
  - **pnpm:** declarative source is `pnpm-workspace.yaml` `packages:` plus `workspace:`/`link:` dep specs; lockfile `importers:` records them. pnpm's own machinery (`.pnpm` store dirs, `node_modules/.pnpm/node_modules/*` hoisted links) resolves *inside* the node_modules root, so it is naturally excluded by an escape filter.
  - **yarn classic:** `workspaces` in package.json, symlinks in node_modules — same as npm. **yarn berry:** `workspace:`/`portal:`/`link:` protocols; with the PnP linker there is no node_modules at all, and a tree-symlink strategy does not apply.
  - **bun:** `workspaces` in package.json; whether bun symlinks or copies `file:` deps is UNKNOWN here (no exec available) — the outcome scan below covers it either way.
- **Naming: the `@spec-kit/` scope dir is derived from each member's package.json `name` field, not from its directory path** — lockfile `resolved` values are `shared`, `runtime`, `runtime/cli` (paths), while the installed locations are `node_modules/@spec-kit/{shared,runtime,cli}` (names). Any derivation must map path → `name` by reading the member's package.json; a member without `name` cannot be linked.
- **The layout-independent ground truth is an outcome scan, and it is cheap:** for every symlink under the tree, resolve `readlink` relative to the link's own directory, and flag exactly those whose resolution escapes the tree root. Vendored links (`.bin/*`, pnpm store links) resolve inside and are ignored; workspace and `file:` links escape by construction (`@spec-kit/cli -> ../../runtime/cli` from within `node_modules/`; `@spec-kit/shared -> ../../../../system-spec-kit/shared` from within `runtime/node_modules/`). This finds all four links on the current tree and would find them under npm/pnpm/yarn-classic alike because it inspects results, not declarations. No exec was available in this dispatch, so the scan itself is specified, not run.

## Recommended mechanism

- **Derive per install root (the dir holding `package.json` + the lockfile), never per repo** — here that is each skill dir separately. Run two derivations and union them: (1) `workspaces` members resolved to their package.json `name`s, plus every reachable `file:`-directory dep spec mapped to its dep name; (2) the lockfile link set — npm `link: true` entries with `resolved` targets, pnpm `importers:` link specs, yarn protocols. Prefer `node_modules/.package-lock.json` over the committed lockfile when present.
- **Adjudicate with the outcome scan, not the declarations alone:** escape-resolving symlinks are recreated against the worktree's own source; anything the declarations claim but the scan does not show (e.g. npm configured `install-links=true`, bun copying) is a mismatch to report, not to force into a symlink.
- **After the wholesale tree symlink is made, delete only the flagged entries and recreate each as a relative symlink into the worktree root**, using `worktree_root + (target path relative to main root)` — e.g. `ln -s ../../../../system-spec-kit/shared <worktree>/.../node_modules/@spec-kit/shared`. Everything else in the tree stays a symlink-to-main and is harmless because its links resolve inside the tree.
- **Gate on the escape set being non-empty before trusting a layout you have not seen:** if the scan finds zero escaping links in a tree the lockfile says should have N > 0, treat the derivation as failed (silent-miss guard) rather than concluding "no self-links".
- Reuse `.opencode/bin/worktree-session.sh`'s existing shared-path loop as the hook point: after the `ln -s -- "$src" "$dst"` line, run the scan + re-link against `"$dst"`, replacing iteration-001's hardcoded four with the derived set.

## What would break it

- **A config flip that changes outcomes without changing declarations** — `install-links=true` in `.npmrc`, bun switching `file:` deps to copies, or a pnpm `node-linker` change: the declaration-derived set would claim links that no longer exist. The scan-then-diff step is the mitigation; declaring the set without scanning reintroduces the silent-miss class.
- **Lockfile drift or absence** — a stale committed `package-lock.json` disagrees with the installed tree, or an install root installed without a lockfile (the hidden `.package-lock.json` is then the only npm record, and only if the install wrote it). Derive from the installed tree's own record, not the committed one.
- **Non-symlink link mechanics** — if any manager materializes a workspace/`file:` dep as a hardlink, junction, or copy, the escape scan sees a directory, not an escaping symlink, and the entry is treated as vendored. pnpm's hoisted node-linker and bun both need one observed install to confirm which form they take; UNKNOWN here.

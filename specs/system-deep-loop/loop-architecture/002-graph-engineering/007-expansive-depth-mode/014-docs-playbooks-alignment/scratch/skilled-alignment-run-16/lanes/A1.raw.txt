**Finding A1-1 (P1, needs a judgment call):** `frontier-admit.cjs` line 739. `closeNode` lets a node that was closed for being stuck come back to life.
- **The cause:** the only check is that a pruned node stays pruned. `active` is an allowed close status, so an exhausted, answered, blocked or abstained node can be moved back to `active`. That breaks the docstring's promise to "move a node to a later lifecycle status".
- **Why a real run hits it:** in `deep-review.yaml`, `active_frontier_node` is set once at line 1184. The stuck branch (lines 1599–1605) closes that node as `exhausted` and re-runs the reducer, then logs "moved to the next open node". But nothing resets the variable before `step_frontier_activate` (line 1699–1704) closes the same id as `active`.
- **The effect:** the stuck node is live again and counts toward `frontierOpen`, so the stop is blocked. It gets dispatched again and can loop through stuck → exhausted → active until the iteration cap.
- **Fix options:** make `closeNode` refuse to move a terminal status back to `active` (with a test for that case), or have the review workflow pick the active node again after the stuck close. The first is safer.

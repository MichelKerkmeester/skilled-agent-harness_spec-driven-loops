## Findings
- The prompt hands each leaf **one `lineageDir` string with two renderings, both anchored to the orchestrator**: the artifact-root override `config.fanout_lineage_artifact_dir: ${lineageDir}` (fanout-run.cjs:1309) and the write-surface instruction "Its absolute path is `${path.resolve(process.cwd(), lineageDir)}`; the relative form is resolved from the repository root" (fanout-run.cjs:1359), backed by a verbatim-copy order — "never retype it or rebuild it" (fanout-run.cjs:1360-1367). Under a worktree, that absolute string still names the main checkout unless the rewrite recomputes it from the worktree root; the leaf is told to use it, not to derive it.
- The native path repeats the same value in three more places: `--fanout-lineage-artifact-dir=${lineageDir}` (fanout-run.cjs:1393) plus `config.fanout_lineage_artifact_dir` (1414), and `spec_folder`/`review_target` are passed verbatim in both prompt and command input (fanout-run.cjs:1308, 1336, 1339, 1404, 1407). Every one of those is resolved leaf-side against the leaf's own cwd/worktree, not by the orchestrator.
- **Two kinds pin the workspace to the orchestrator cwd with an explicit flag**, so a worktree spawn-cwd alone would be overridden: native `opencode run … --dir process.cwd()` (fanout-run.cjs:1934-1935) and cli-opencode `opencode run … --dir process.cwd()` (fanout-run.cjs:2002-2003).
- **Five kinds emit no directory flag** and are steerable only through the spawn cwd: cli-codex (arg list ends `--sandbox <mode> -`, fanout-run.cjs:1836-1879), cli-claude-code (fanout-run.cjs:1887-1899), cli-devin (`['-p', prompt, '--model', model]`, `buildDevinLineageCommand`), cli-cursor in both write modes (`--force --sandbox enabled|disabled`, fanout-run.cjs:2144-2150), and cli-pi — explicitly "no `--dir` flag (it runs in the spawned working directory)" (fanout-run.cjs:2335). Spec 045 already scopes exactly this for pi: "its cwd must be the worktree" (spec.md:216).
- cli-cursor read-only is the one place a lineage is handed an **explicit main-checkout path as a read root**: `repoRoot = (options && options.cwd) || process.cwd(); … '--add-dir', repoRoot` (fanout-run.cjs:2166-2167) — and the fan-out caller never sets `options.cwd` (options bundle is loopType/specFolder/lineageDir/sessionId/convergenceThreshold/stopPolicy/researchTopic, fanout-run.cjs:2801-2820). Un-rewritten, a worktree-mode read-only cursor leaf reads the main checkout by construction.
- **The executor config cannot express a per-lineage directory at all**: `executorConfigSchema` carries kind/model/configDir/reasoningEffort/serviceTier/sandboxMode/timeoutSeconds/governor/liveTools and `EXECUTOR_KIND_FLAG_SUPPORT` has no directory/cwd row for any kind (executor-config.ts §1-2). Per-lineage placement must be a runner-level dispatch option.
- `buildLineageCommand` is imported by two other surfaces — deep-ai-council `orchestrate-session.cjs` and model-benchmark `dispatch-model.cjs` — and spec 045 says the signature must stay stable or all three call sites change together (spec.md:233-239). Threading a per-lineage cwd through its options is a three-surface change.
- **Containment resolves one repo root for the whole run with an explicit same-tree premise** — "Every lineage lives under the same tree, so this is the same for all of them" (fanout-run.cjs:2598-2606) — via `resolveContainmentRepoRoot` precedence DEEP_LOOP_REPO_ROOT → artifact-tree toplevel when the artifact tree lies outside cwd's worktree → cwd (runtime-bootstrap.cjs:43-73). The env pin is run-wide; per-lineage worktrees falsify the premise.
- Under worktrees the guard **fails silent, not loud**: `detectNewOutOfScopeViolations` throws only when repoRoot is not a worktree while artifactDir is outside it; when `lineageDir` stays main-tree-anchored and inside the main worktree, `resolveArtifactScope` resolves, the diff is clean because nobody wrote that tree, and containment returns `[]` — the documented fail-open posture (write-containment.ts module header; NFR-R01 spec.md:177) renders the guard vacuous.
- Sibling attribution exclusions are built from the one shared lineagesDir (`siblingLineageDirs = path.join(lineagesDir, other.label)`, fanout-run.cjs containment worker wiring): one-tree bookkeeping that N worktrees reduce to dead entries.
- If a worktree is created inside the main checkout's working tree, the main tree's containment diff sees it — `readStatusEntries` runs `git status --porcelain=v1 -z --no-renames --untracked-files=all` (write-containment.ts), which reports a nested linked-worktree directory as untracked, so the seeded worktree itself would be attributed to a running leaf. (Mechanism-level inference from the guard's git call; worktree location not verified here.)
- The packet already owns this contract but not its mechanics: spec.md:70 ("copy-back of the lineage directory and rewriting of every path the prompt hands the executor"), spec.md:85, REQ-005 (spec.md:115), decision-record.md:319-320 — and implementation-summary.md:109 concedes the residue: "anything an executor derives on its own is out of reach."
- No implementation of the rewrite exists in the dispatch path read: the worker builds the prompt from `path.resolve(process.cwd(), lineageDir)` and spawns every kind with a single `cwd: process.cwd()` (fanout-run.cjs:2992). Whether a worktree phase exists behind a flag elsewhere in the remaining ~1,200 lines of fanout-run.cjs: UNKNOWN.

## What this means for unlimited concurrency
- Worktree-per-lineage is a path-rewriting project, not a containment tweak: two kinds need their explicit `--dir` rewritten, five kinds need the spawn cwd changed (their only lever), one read-only kind needs its `--add-dir` read root rewritten, and the single prompt string must split into "write here now" (worktree) versus "artifacts land here" (copy-back/containment/polling, all main-tree keyed today).
- Containment cannot survive N trees as wired: one repo root per run + sibling dirs and ledgers from the main tree means the guard watches a tree nobody writes to and reports clean — the failure 045 exists to end, reintroduced by isolation itself.
- Blast radius is wider than one adapter: `buildLineageCommand` has two external importers, `ExecutorConfig` has no directory field, and `DEEP_LOOP_REPO_ROOT` is run-wide, so per-lineage cwd/repo-root is a new runner-level concept threaded through three call sites — not a flag bolted onto `buildPiLineageCommand`.
- Because the packet itself concedes that executor-derived paths (config discovery, `.cursor` loading, extension/skill loading, git toplevel) are out of rewrite reach, "unlimited" concurrency keeps a per-kind residue that only spawn-time OS isolation or per-kind env pinning can close.

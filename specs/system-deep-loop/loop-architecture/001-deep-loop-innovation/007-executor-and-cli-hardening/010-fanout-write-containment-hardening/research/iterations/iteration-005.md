# Iteration 005

**Model:** `llmgateway/deepseek-v4.1-flash` at max thinking  
**Angle:** resource ceilings that actually bound concurrency: disk, inodes, file handles, node_modules duplication, memory per CLI process

---

## Findings

- **The dependency-duplication cost is designed away, and the precedent is real code, not prose.** ADR-003 says "The shared `node_modules` and `dist` are symlinked in, mirroring the launch wrapper" (`specs/system-deep-loop/045-fanout-write-containment-hardening/decision-record.md:265`), and the launch wrapper it mirrors symlinks five paths — `.opencode/skills/system-spec-kit/{node_modules,runtime/node_modules,runtime/dist,runtime/cli/dist,runtime/cli/node_modules}` (`~/.opencode/bin` → `.opencode/bin/worktree-session.sh:80-87`), via `rm -rf -- "$dst"` + `ln -s -- "$src" "$dst"` (worktree-session.sh:324-325). So per-lineage disk excludes dependencies entirely; the flip side is that all N lineages and the main checkout share one mutable dependency/dist tree — a shared-state hazard, not a disk cost.
- **The in-tree executable model of a worktree contradicts the symlink design, and the contradiction flips the inode profile.** The stress fixture creates real, empty `node_modules` directories per worktree (`runtime/tests/stress/cli-adapter/fixtures/worktree-fixture.ts:57-58`) and asserts independent per-worktree realpaths (`worktree-fixture.ts:81-82`; `runtime/tests/stress/cli-adapter/fanout.vitest.ts:678-679`; requirement EC-013 "preserves independent worktree node_modules boundaries", `runtime/tests/stress/cli-adapter/matrix-manifest.ts:30,113`). If that model is the intent, N lineages each carry a full dependency tree (disk + inode explosion); if ADR-003's symlink is the intent, zero duplication but shared mutable state. Both artifacts live in-tree unreconciled; iteration-001 flagged the fixture half, but not that the tests *assert* isolation the ADR removes.
- **Per-lineage cost admitted by the packet: one checkout of tracked files + one fresh index, with the object store shared.** "One checkout per lineage of disk and inodes. Mitigation: worktrees share the object store, and teardown is part of lane settle" (`decision-record.md:289`). Detached-from-HEAD adds (prior iteration) mean no history duplication — but the tracked working tree is materialized N times, and the design puts the worktree base outside the primary checkout (`.worktree-session.sh:191-194`) so main-checkout watchers don't recurse into N trees.
- **Containment adds a per-lane disk budget on top of the checkout: 2 MiB per file, 64 MiB per lane for baseline content** (`goal.md:59` D3; `plan.md:67`), plus quarantine copies and the copy-back/artifact bytes. The bound bounds a *lane*, not a *run*: 200 concurrent lanes is a worst-case 12.8 GiB of baselines alone, before checkouts, seeds, artifacts, or quarantine. The packet knows the cost ("Storing content costs disk on a run with a large dirty tree", `decision-record.md:163,196`) but sets no run-total ceiling.
- **No measurement exists, and the packet's own perf task defers it.** CHK-112 (six-lineage worktree wall-clock setup vs. without) and CHK-113 (measured setup cost and **disk footprint per worktree recorded in `implementation-summary.md`**) are both unchecked (`tasks.md:236-237`), and the packet states "Nothing is built yet" (`acceptance-criteria.md:100`). Bytes/inodes/fd figures per checkout: UNKNOWN.
- **Per-lineage stdout is hard-capped at 20 MiB in the runner, and a breach kills the lineage.** `maxBuffer: 20 * 1024 * 1024` (`runtime/scripts/fanout-run.cjs:2995`), enforced as "stdoutBytes > maxBuffer → terminateLineageProcess(child, 'SIGTERM')" (`fanout-run.cjs:1713-1715`). That is a functional ceiling (a chatty CLI dies) before it is a memory ceiling, but it also bounds one in-flight lineage's retained buffer inside the *single* runner process. The batch `codex-dispatch.cjs` path uses a 32 MiB buffer with blocking `spawnSync` (`runtime/scripts/codex-dispatch.cjs:49,128`), so its cost is serialized, not multiplied.
- **All lineages spawn from one Node process and one event loop, with 2-3 pipe fds each and no resource guard.** `runCappedPool` runs the whole fan-out in-process (`fanout-run.cjs:2750-2752`; `runtime/scripts/fanout-pool.cjs:413-417` — "K-at-a-time"), workers spawn `detached: true` with `stdio: [pipe|ignore, 'pipe', 'pipe']` (`fanout-run.cjs:1664-1672`), and the pool's only clamp is a floor: `normalizeConcurrency` rejects <1 and imposes no upper bound (`fanout-pool.cjs:54-57`) — the `.max(8)` concurrency gate lives in the config schema, not the pool.
- **There is no resource-exhaustion handling anywhere in the runtime.** A grep of `.opencode/skills/system-deep-loop/runtime` for `EMFILE|ENOSPC|ENOMEM|EAGAIN|ulimit` returns no source hits (only `maxBuffer` and unrelated "memory"-word matches), and `NODE_OPTIONS`, `max-old-space-size` and any per-child memory/CPU flag are absent from `runtime/scripts` (grep for `NODE_OPTIONS|max-old-space` → no hits). Disk-full during worktree create, baseline capture, or copy-back is therefore not a classified failure; `preflightCodexLive` (`runtime/tests/stress/cli-adapter/fixtures/live-preflight.ts:34-41`) checks dependency *reachability* only, and is test-only.
- **Per-CLI-process memory is the largest unmeasured term.** Six agent runtimes (cli-codex, cli-opencode, cli-pi, cli-cursor, cli-devin, cli-claude-code) each run as their own process tree per lineage; nothing in the repo bounds, measures, or even names their RSS: UNKNOWN. The runner's own heap at K lineages is bounded only by a truncation/kill loop (K × up to 20 MiB stdout + baselines + scans), with V8's default heap as the unstated ceiling.
- **Per-worktree fsmonitor daemons (prior iteration) remain the one measured-ish process multiplier** — `core.fsmonitor=true`/`untrackedcache=true` means each live worktree can carry its own daemon (`iteration-001`, from repo config) — so process count per lineage is at minimum 2 (CLI tree + git daemon), plus each CLI's own watchers. Whether on this macOS host that exhausts FSEvents/kqueue or any fd limit: UNKNOWN.

## What this means for unlimited concurrency

- After the shared object store and the symlinked deps, the linear costs are: tracked-file checkouts (bytes + inodes) × N, one index × N, one fsmonitor daemon × N, plus a per-lane containment budget of 64 MiB × N and copy-back/quarantine bytes — with no run-total ceiling and no `ENOSPC` path, so the first disk failure is an unclassified crash inside worktree create / baseline / copy-back, the exact steps whose failure behavior (degrade vs. retain vs. abort) the packet otherwise specifies.
- The single runner process is a concurrency ceiling independent of disk: K lineages share one V8 heap, one event loop, and up to K × 20 MiB of stdout buffers plus baselines and scan state, with no `--max-old-space-size` tuning anywhere — long before N=200 the runner OOMs or stalls, and a stalled pool false-fires its lag-ceiling detector (`fanout-pool.cjs:471-479`).
- The dominant unknown is additive CLI RSS: N × (CLI process tree + watcher + git daemon) with no measurement, no limit, and the packet's disk/setup measurement explicitly deferred (CHK-112/113 unchecked; "Nothing is built yet"). "Effectively unlimited" is therefore bounded by host memory / swap pressure first, and no artifact in the repo records where that ceiling sits.
- File-handle exhaustion is plausible but unclassified: 2-3 pipe fds per in-flight lineage in the parent, plus each CLI's fd table and any git daemon sockets, with zero `EMFILE`/`EAGAIN` handling — the failure would present as a generic spawn error, and the pool would classify it as a retryable lineage failure, retrying into the same exhausted condition.

## Open question this raises

- With dependencies symlinked and the object store shared, what actually saturates first as K rises on this host — run-total disk from N checkouts + per-lane 64 MiB baselines + artifacts (against an untaxonomized `ENOSPC`), the single runner process's heap (K × buffered stdout + baseline/scan state), or the sum of six CLI runtimes' RSS — and at what N does each fail *visibly* (a classified lineage error) versus *silently* (stall, truncation, or SIGTERM-that-looks-like-a-slow-model)?

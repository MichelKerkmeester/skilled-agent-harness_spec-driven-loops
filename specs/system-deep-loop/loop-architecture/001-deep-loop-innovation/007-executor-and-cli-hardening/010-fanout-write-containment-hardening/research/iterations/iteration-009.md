# Iteration 009

**Model:** `llmgateway/deepseek-v4.1-flash` at max thinking  
**Angle:** failure and recovery: partial lane failure, orphaned worktrees after an interrupted run, and how a sweep avoids deleting a live one

---

## Findings

- **All of 045's failure/recovery design is two sentences, and neither specifies a liveness check.** R-004: "Teardown on lane settle plus a startup sweep of the runner's own ephemeral prefix; sk-git's reaper does not own this lane" (`specs/system-deep-loop/045-fanout-write-containment-hardening/spec.md:217`; ADR-003 risk row same wording, `decision-record.md:297`). Implementing tasks: T020 retain-on-copy-back-failure + remove (`tasks.md:74`), T021 "Sweep the runner's own ephemeral worktree prefix at startup" (`tasks.md:75`). No predicate for "is this worktree live" appears in any of them.
- **The evidence plan rewards deletion and never tests preservation.** The only worktree-lifecycle acceptance criterion asserts "no ephemeral worktree remains" (`acceptance-criteria.md:71`, AC-009), and CHK-124 wants an observed sweep after a killed driver (`tasks.md:249`, CHK-124). No acceptance criterion or checklist item asserts that a sweep *leaves a live foreign worktree alone*, so the gate can be fully green while the sweep is allowed to be maximally destructive.
- **The existing sk-git reaper is not merely un-owning this lane — its delete-safety predicates are structurally impossible for 045 worktrees, and it classifies them report-only.** The reaper auto-removes only when all of: machine-owned `work/<runtime>/<slug>` lane with branch↔directory cross-check, clean working tree, branch merged into the live tip, and a session marker whose recorded PID is dead; "absence of proof of inactivity is never treated as proof of inactivity" (`.opencode/skills/sk-git/feature-catalog/session-lifecycle/worktree-reaper.md:29`). It "never signals a process" and takes only `--dry-run` (`worktree-reaper.md:21`), and "Detached worktrees … are always report-only" (`worktree-reaper.md:33`). 045's worktrees are detached by decision (`decision-record.md:263`; `plan.md:70`), seeded with uncommitted packet content (intentionally dirty), and never committed or merged — so all four reaper gates fail or are inapplicable, and the detached class is explicitly out of its remit.
- **Consequence of the above: the one proven-safe deletion pattern in this repo (marker + dead-PID) has no counterpart in the design.** The reaper's liveness proof is a marker file recording a process id (`worktree-reaper.md:29`); 045 places no marker inside a worktree, so a prefix-scanning sweep has literally nothing to read that distinguishes a live worktree from an abandoned one.
- **A liveness oracle exists but is scoped to run dirs, not worktrees.** `holdsLiveLoopLock` (TTL + heartbeat + owner PID, `fanout-run.cjs:516-536`) drives `discoverForeignLiveRunDirs` (`fanout-run.cjs:551-575`), which the runner trusts everywhere else and re-polls mid-iteration precisely because "such a run can start mid-iteration" (`fanout-run.cjs:2967-2968`). But the lock lives at the run's artifact dir; a worktree directory contains no lock, and the sweep is specified to key on the prefix (`tasks.md:75`), not on the lock federation. The worktree base is shared by all runs and the directory name embeds `prefix-runId-label` (`decision-record.md:265`), so a foreign live run's worktrees sit inside the very namespace a new run's startup sweep intends to clean — and the run id in the name has no live/dead registry to consult.
- **The startup moment does two uncorrelated things to an interrupted run: it resurrects its lineages and it deletes their worktrees.** `markOrphanedLineages(ledgerPath)` runs unconditionally at startup (`fanout-run.cjs:2707`) and requeues every `started`-without-terminal lineage as a fresh attempt under the retry cap (`fanout-pool.cjs:286-326`; orphan consumes an attempt, `fanout-pool.cjs:273-283`; event mapping `fanout-run.cjs:256-257, 302`). Orphan detection is itself liveness-free — pure ledger-state inference, no PID check. So T021's sweep (a directory-prefix operation) and orphan requeue (a ledger operation) both fire against the same interrupted run, and nothing correlates them: the requeue does not name the worktree path, and the sweep does not consult the ledger. The interrupted attempt's unsalvaged output inside its worktree is deleted with no copy-back or quarantine step specified for that path.
- **Teardown-on-settle races post-exit writers, and the pool's own comment documents that such writers are real.** `fanout-pool.cjs:755-765`: "The tracked subprocess can exit while a child it spawned keeps writing the lineage's artifacts (a print-mode CLI that hands off to a worker process)" — the pool defeats false orphanhood by watching artifact progress within `postExitGraceMs`. Nothing in the lane-end pipeline gates worktree removal (or copy-back) on that same artifact-progress grace or on grandchild exit; the pipeline prose is verdict → copy-back → settle/removal (`plan.md:74-76`, per prior iterations), and T020 keys removal on the lane step, not on writer quiescence (`tasks.md:74`).
- **The abort-requeue path adds a second partial-failure shape with no worktree rule.** `LAG_CEILING_ACTION_ABORT_REQUEUE` exists (`fanout-pool.cjs:30`), the abort event is mapped to `failed` by the runner (`fanout-run.cjs:305`), and the pool settles the slot from the parent side via `buildSyntheticAbortResult` (`fanout-pool.cjs:573`). Whether that path kills the underlying process group I did not verify — UNKNOWN — but if "settle" can precede child death, a prefix sweep at another run's startup can delete the worktree out from under a still-running aborted writer. T020's only failure disposition is copy-back failure (`tasks.md:74`; `decision-record.md:298`).

## What this means for unlimited concurrency

- The isolation design's own safety property — "attribution is sound because each lineage has its own tree" — is only as good as the sweep that cleans those trees; with N concurrent lineages across overlapping runs sharing one worktree base and one prefix namespace, an unliveness-gated sweep converts every startup of a new run into a probabilistic deletion pass over live peers' working trees. The blast radius of a wrong delete is strictly worse than today's wrong `git checkout`: it destroys new untracked output with no HEAD copy to detect it by.
- The reaper precedent says the repository already knows the correct rule (absence of proof of inactivity is never proof of inactivity) and has a working implementation of it, but that implementation is structurally unusable for detached, dirty, unmerged lanes — so "sweep" must grow its own liveness marker (PID-stamped, heartbeat-refreshed, placed at worktree creation and deleted with the worktree) or the loop-lock lease must be projected into the worktree namespace. Anything short of that makes T021 safe only for exactly one run at a time, which is the opposite of "effectively unlimited".
- Orphan recovery and worktree reclamation are two mechanisms with opposite intents for the same artifact; at unlimited N with overlapping runs and day-scale lanes, interruption is not an edge case, so the two must be ordered and linked (sweep only what no live lock claims AND no ledger requeue is about to resume), or the resume path silently starts from a state the sweep already destroyed.
- The acceptance gate as written (AC-009 "no worktree remains", CHK-124 "observed cleaning up after a killed driver") will certify a destructive sweep as correct. Unlimited concurrency needs a negative-control criterion — "run B starts while run A is live; every A worktree survives" — or the verification plan cannot distinguish the fix from the hazard.

## Open question this raises

- Should the sweep's delete predicate be a positive liveness proof — a per-worktree marker whose recorded PID the sweep can test as dead, mirroring the sk-git reaper's "absence of proof of inactivity is never proof of inactivity" rule — and if so, who writes that marker (the runner at creation, a heartbeat refresh, or a projection of the existing loop-lock lease), given that until it exists no prefix sweep can distinguish a live peer's lane from an abandoned one?

## Findings

- **Copy-back does not exist yet — it is prose, not code.** The runner's only worktree mentions are comments (fanout-run.cjs:2601, 2875, 3129); the sole worktree-creation code in the skill is a stress-test fixture whose teardown is an unconditional `rmSync` of the whole temp root, no copy step (runtime/tests/stress/cli-adapter/fixtures/worktree-fixture.ts:52-53, 60). The implementing task is unchecked: "T020 Copy the lineage directory back into the main checkout after the lane, and remove the worktree; on a copy-back failure retain the worktree and name it on the failure event (`runtime/scripts/fanout-run.cjs`)" (specs/system-deep-loop/045-fanout-write-containment-hardening/tasks.md:74), its acceptance case is "Unmet" (acceptance-criteria.md:71), and implementation-summary.md:74 lists per-lineage worktrees as "Not delivered" (:99, manual worktree run "Not run"). Every copy-back property below is therefore design intent; implementation semantics = UNKNOWN.
- **The ordered pipeline places copy-back after the verdict is already computed, so failure can strand publication but never the verdict.** Sequence at lane end: "the runner reads the lane's artefacts and state log first, then runs the guard... combines the artefact verdict and the containment verdict into one settle call... a copy-back step runs between the guard and the settle" (plan.md:74-76), i.e. verdict computed inside the worktree → copy-back (worktree → main) → settle/removal. That is exactly why the failure remedy can be "retain the worktree, name its path on the failure event, recover by hand" (spec.md:192, decision-record.md:298, tasks.md:74): the lane's outcome survives inside the worktree, and the retained worktree is the only remaining copy of it.
- **No atomicity, no merge-vs-mirror, no fencing is specified anywhere I read.** All five copy-back operations (create, seed, copy-back, remove, startup sweep) are named in one decision line (decision-record.md:319: "`runtime/scripts/fanout-run.cjs`: worktree create, seed, path rewrite, copy-back, remove and startup sweep") and nowhere is the publication mechanism defined: whether the copy is staged-and-renamed or a racing recursive copy, whether a populated target is merged (leaving stale files the worktree had deleted) or mirrored, and who arbitrates — none appears in spec.md:70,150,188-192, plan.md:60-104, or decision-record.md:258-320. The runtime's existing publication discipline is per-FILE only — staging→fsync→atomic rename→read-back proof (lib/receipts-and-effect-recovery/effect-adapters.ts:249, 310-311), wx-lock + flock (lib/council/round-state-jsonl.cjs:200-222), salvage's lock-held dedupe-then-atomic-rewrite (manual-testing-playbook.md:338) — there is no directory-level staging+swap primitive in the runtime, and a POSIX rename cannot atomically replace a populated directory, so a single-PRIMITIVE-atomic copy-back is not reachable with the patterns that exist. Closest precedent for exclusion is the fixture's wx-claim (`openSync(claimPath, 'wx')`, worktree-fixture.ts:64-75); nothing connects it to copy-back.
- **The collision inventory at the copy-back target has four concurrent main-tree writers and no specified arbiter; last writer wins.** (1) the parent's own salvage writer, which writes missing-iteration .md files and placeholders INTO the lineage dir (scripts/fanout-salvage.cjs; behavior: "missing md + recoverable stdout → file written + `salvaged_from_stdout` event... `fanout_salvage_failed` placeholder", manual-testing-playbook/fanout/fanout-salvage-recovery.md:32) — and its ordering relative to copy-back is unstipulated, since plan.md:76 fixes only guard→copy-back→settle; if salvage's `statSync` existence checks run against the main-tree dir before copy-back lands, it invents placeholders that then collide with the arriving copies — UNKNOWN. (2) a second concurrent fan-out in the same packet (cross-run lineage-dir coexistence, fanout-run.cjs:2601). (3) the operator/another session — the very incident motivating the work (implementation-summary.md:58, 74: "keep working in it... a second session editing"). (4) the stale prior copy itself. The worktree side is safe by construction — inside it the lineage dir's only co-writers are the seeder and copy-back (already noted in research/iterations/iteration-002.md:22) — so the UNSYNCHRONIZED side is precisely the main-checkout target. Note also that copy scope is the whole lineage dir, which includes the runtime-internal `containment/quarantine/` + `containment/baseline/` trees (plan.md:~69-75) and `containment-reverted/` (written into the artifact dir, write-containment.ts:566) — copy-back publishes containment bookkeeping, not just research output.
- **The failure path is specified, but its recovery window is silently bounded by the next run.** Designated failure behavior: retain the worktree and name its path on the failure event (spec.md:192) — no automatic retry, no automatic salvage-into-main. But the runner also "sweeps its own prefix at startup so an interrupted run cleans up on the next one" (decision-record.md:265), and nothing I read exempts a deliberately-RETAINED failed-copy-back worktree from that next run's sweep — whether the sweep distinguishes retained-for-recovery from orphaned is UNKNOWN. Also unspecified: the failure event's shape (name, fields) and its effect on the lane's settle outcome — the outcome vocabulary has exactly three states (`fulfilled`/`rejected`/`completed_with_containment_advisory`, plan.md:~66-70) and none describes a completed-but-unpublished lane; conversely, worktree create/remove failure (not copy-back) degrades the lane to in-checkout forced-preserve + warning, not run failure (spec.md:178, 191). The copy-back failure event itself would be appended by the parent — single-writer, consistent with the logging-never-blocks rule (write-containment.ts, `appendContainmentEvent`, ~L573-580).

## What this means for unlimited concurrency

- Copy-back adds no new shared state: each lane publishes to its OWN lineageDir, and the worktree side of the copy is effectively single-writer, so N concurrent copy-backs are embarrassingly parallel — the contention surface shrinks to per-lineage target dirs vs. NON-run writers (operator, second fan-out), which is the same concurrent-editor class 045's preserve mode only detects (churn sampler, plan.md:~71-73) rather than fences.
- The verdict/publication split (plan.md:74-76) makes copy-back failure linearly containable: at most one retained worktree + one failure event per failed lane, never a run-level abort, and the retained worktree self-documents its recovery path (spec.md:192) — cost at high N is bounded, but the next run's startup prefix sweep (decision-record.md:265) bounds the hand-recovery window unless the sweep learns to skip retained worktrees (unspecified).
- The unresolved soundness risk moves, it does not vanish: today's post-hoc shared-tree diff is replaced by an UNSPECIFIED last-writer-wins publication into a dir that the parent itself also writes (salvage) and that other sessions/packets may hold stale copies of — at two lineages this is noise; at effectively-unlimited N with day-scale runs it is the same race 045 exists to kill, now at the publication step, and nothing read fences it.
- Everything above rests on docs, not code (tasks.md:74 T020 unchecked; the only compiled worktree teardown in the skill is a test-fixture rmSync, worktree-fixture.ts:60) — including whether teardown-under-concurrent-runs even coordinates removal through `git worktree` metadata in the shared main .git versus raw directory deletion (worktree-fixture.ts:60 precedent) — that stays UNKNOWN until T020's helpers exist.

## Open question this raises

When copy-back lands on a populated main-checkout lineage directory, what are its write semantics — staged-atomic publication or a racing copy-merge, mirror or overwrite-merge — and which of the four concurrent main-tree writers (the parent's salvage/placeholder pass, a second fan-out's same-labeled lineage, the operator, the stale previous copy) is it allowed to clobber, given nothing in spec.md, plan.md, or decision-record.md specifies a lock, ownership claim, or ordering?

## Findings

- **The candidate structural answer is already decided, and my angle is 045's own parked research.** The 045 packet's key decisions: each lineage gets an "ephemeral detached worktree outside the sk-git numbered namespace rather than an allocator-issued one" (specs/system-deep-loop/045-fanout-write-containment-hardening/spec.md:24); the workstream is "Per-lineage ephemeral git worktrees, with copy-back of the lineage directory and rewriting of every path the prompt hands the executor" (spec.md:70); REQ-005 requires the worktree be "created from HEAD", the lane never writing the main checkout, the lineage dir copied back (spec.md:115); purpose: "a lineage that runs in its own worktree makes the attribution question disappear rather than answering it more carefully" (spec.md:57). And the level-3 scoring row says exactly what this iteration investigates: "Worktree seeding for an uncommitted packet and prompt path rewriting both need investigation before implementation" (spec.md:203).

- **The spec's entire seeding answer is one mitigation line.** "An uncommitted packet is invisible inside a worktree created from HEAD | The lineage cannot read the spec it was pointed at | Seed each worktree with the packet's uncommitted working-tree content before dispatch, specified in the plan" (spec.md:151), with SC-003 checking only that "every lineage directory [is] present in the main checkout afterwards" (spec.md:135) — presence, not provenance. Whether 045's plan.md already details the mechanics: UNKNOWN (plan.md not read this iteration).

- **"Uncommitted" is three git states, and a working-tree copy is the only mechanism faithful to all of them.** Tracked-modified: a HEAD worktree silently serves the stale predecessor. Untracked: the whole packet is invisible — the normal state of a packet mid-iteration. Staged-but-uncommitted: `git worktree add` checks out the commit and never consults the main checkout's index. A fs copy of the working tree reproduces the bytes the lineage actually reads in all three cases; what it cannot reproduce is index state (worktree indexes are per-worktree), so any lane consulting `git diff --cached` diverges — UNKNOWN whether any lane does. In-repo precedent that a worktree here carries nothing but HEAD: `git worktree add --detach ... HEAD` (worktree-fixture.ts:55-56) followed by only EMPTY hand-made `node_modules` dirs (:57-58) — which also corrects iteration-001's citation: the adds are lines 55-56, not 52-53.

- **Seeding is two roots, not one, because the prompt addresses everything by relative path.** The lineage is handed `spec_folder: ${specFolder}` (fanout-run.cjs:1308; again at 1339 and 1407) and must load `.opencode/skills/system-deep-loop/deep-<review|research>/SKILL.md` (fanout-run.cjs:1264). Seeding only the packet means a lineage launched while 045 itself is mid-implementation reads the PRE-packet runtime from HEAD — 045's own worktree-phase tests would then exercise stale code while the working tree holds the fix.

- **Today nothing is worktree-resident; the dispatch anchors everything to the orchestrator's cwd.** Every lineage spawns with `cwd: process.cwd()` (fanout-run.cjs:2992, inherited by the codex adapter at codex-dispatch.cjs:123), the artifact↔spec pairing is validated against `process.cwd()` (validateBaseArtifactDir, fanout-run.cjs:590), and ONE containmentRepoRoot is resolved for the whole run under the stated invariant "Every lineage lives under the same tree, so this is the same for all of them" (fanout-run.cjs:2599-2602; 2601 grep-verified). The worktree-agnostic seam already exists: resolveContainmentRepoRoot honors `DEEP_LOOP_REPO_ROOT` or redirects containment to the worktree that physically holds the artifact when it resolves outside cwd's worktree (runtime-bootstrap.cjs:54-73, rationale :46-52), and 045 freezes detection, changing only the remedy (spec.md:75).

- **The unstated hard constraint: seeding must precede the worktree's pre-dispatch baseline.** In a fresh worktree that baseline is empty except for the seeder's writes; a seeded tracked-modified path detected after baseline is fatal under default preserve (`preserved_in_head` falls outside the `preserved_untracked` forgiveness set in enforceWriteContainment, write-containment.ts; exact line UNKNOWN — the caller's preserve/restore mode at the fan-out call site is likewise beyond this read, fanout-run.cjs:2900-3311 unexamined). Under 045's REQ-002 restore opt-in (spec.md:113), restore targets "pre-dispatch baseline bytes" — so a baseline taken pre-seeding restores the seeded file to HEAD and silently undoes the seed. Seeded-first, the baseline (snapshotOutOfScopeDirtyPaths, write-containment.ts; line UNKNOWN) becomes a free, mechanically-verified receipt of what was seeded, via the module's existing gitHashObject content-identity comparison.

- **The seeding enables the structural payoff 045 promises.** Inside its own worktree the lineage's only co-writers are the seeder and copy-back, so the `unattributableDirs`/`unattributablePaths` exemptions and the foreign-run discovery scan (write-containment.ts; FOREIGN_RUN_SCAN_* constants, fanout-run.cjs:~2579-2583, exact lines UNKNOWN) demote from correctness machinery to diagnostics, and the parent's in-HEAD ledger ambiguity ("once these files are committed the revert restores them from HEAD", fanout-run.cjs:2588-2598) disappears for lanes, since lanes stop writing the shared checkout at all (spec.md:115).

- **Feasibility guards 045 already pinned, which the seeding step must respect.** Shared `node_modules`/`dist` must be symlinked into each worktree at creation or the spec-kit/deep-loop generators "crash or silently no-op" (spec.md:147); worktree create/remove failure must degrade to in-checkout preserve mode with a warning, not fail the run (spec.md:178, 191); copy-back failure retains the worktree and names its path on the failure event (spec.md:192); interrupted-run accumulation is the runner's own ephemeral-prefix sweep, not sk-git's reaper (spec.md:146, 217); and the cross-runtime cwd constraint — "`cli-pi` has no directory flag and runs in the spawned working directory, so its cwd must be the worktree" (spec.md:216, rated High-impact) — lands directly on the fanout-run.cjs:2992 decision.

## What this means for unlimited concurrency

- Unlimited concurrent lineages are the decided substrate, not a proposal: the work is to implement 045's worktree phase (spec.md:24, 70, 115) rather than design a competing mechanism; the genuinely open work is exactly the two investigations 045 flags (spec.md:203), of which this iteration's seeding angle is one.
- The seeding mechanism should be a working-tree COPY of (a) the packet dir and (b) the uncommitted subset of the prompt-addressed roots (`.opencode/skills/...`, and the command assets the prompt pack references), because copy alone is faithful to all three uncommitted classes without desyncing the worktree from its detached HEAD via extra commits; the cost is packet-plus-skills scale, not history scale, consistent with iteration-001's per-lineage cost model.
- The invariant to build — and enforce, not assume — is the order: seed → baseline → dispatch, per lineage. Both failure modes of the wrong order are invisible: restore-to-HEAD (seed erased, worktree looks like bare HEAD) or a fatal preserve-mode violation, and nothing in the current code takes worktrees into account at all (UNKNOWN whether the harness-level "worktree wrapper" referenced at fanout-run.cjs:2875 would; that mechanism is outside this read).
- What 045 leaves unanswered and unlimited concurrency makes urgent: while the source packet keeps changing mid-run, N worktrees hold N silently diverging copies of the "same" spec, and no mechanism records which bytes each lane judged — SC-003 (spec.md:135) checks presence of lineage dirs, not provenance — which quietly reintroduces the post-hoc-inference unsoundness the worktree angle exists to kill, now at the read side.

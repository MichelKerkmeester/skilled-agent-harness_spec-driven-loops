# Iteration 007

**Model:** `llmgateway/deepseek-v4.1-flash` at max thinking  
**Angle:** provider quota and rate-limit behaviour under high concurrency, including how a 429 is distinguished from a broken model id

---

## Findings

- **The fan-out hot path has zero rate-limit vocabulary.** A grep of the 3000+-line `fanout-run.cjs` for `429|rate limit|quota|retry_scheduled` produced no matcher for 429/quota/rate at all; the only quota text in the file is a stale copied comment (`fanout-run.cjs:2198`). Failure classification in the lineage worker uses only process-level signals: `timedOut` (SIGTERM), `killedBySignal`, `exitCode !== 0`, then missing artifacts, then stop-policy (`fanout-run.cjs` failure block read at offset 3015, ended ~3092). The thrown reason is literally `exited with code ${exitCode}` — a 429 and a broken model id are therefore **identical to the runner**: same classification, same ledger shape, same terminal rejection.
- **`retry_scheduled` is vocabulary without a producer on this path.** In `fanout-run.cjs` it appears only at two reader sites that map it to a `'retrying'` status (`fanout-run.cjs:255`, `:301`); nothing in the file emits it. The behavior is locked in by tests: the rate-limit matrix entry is "rejects a rate-limited fan-out lineage without a retry spawn" (`tests/stress/cli-adapter/matrix-manifest.ts:103`), and the hermetic fixture asserts `retry_scheduled` events `toEqual([])` (`tests/stress/cli-adapter/fanout.vitest.ts:436-440`; same fixture at `fixtures/adapter-suite.ts:293-296`). Rate limit = terminal rejection, full stop.
- **cli-pi is the one kind where a 429 may *not* be terminal — it converts into a retry against the same exhausted quota.** The runner deliberately ignores cli-pi's exit code (`exitCodeIsFailure = exitCode !== 0 && lineage.kind !== 'cli-pi'`, same failure block) because "pi returns a non-zero exit code non-deterministically even on a successful dispatch." A pi 429 that exits fast therefore falls through to the missing-artifact branch, which is the salvage-miss path — and the salvage playbook documents "retries a salvage-miss lineage once" (`runtime/manual-testing-playbook/fanout/fanout-salvage-recovery.md:90`). INFERRED (did not read the retry emitter): a pi quota rejection can be retried immediately with no backoff, misclassified as salvage-miss, and the retry fires against the same exhausted account.
- **A mature 429 classifier exists — but only in the behavior-benchmark harness, not the fan-out.** `behavior-bench-run.cjs` checks provider rejection FIRST with `ENV_ERROR_RE` (`behavior-bench-run.cjs:39-48`: `"You've hit your session/usage limit"`, `rate_limit_exceeded`, `429 Too Many Requests`, `exceeded your current quota`), exits `EXIT_ENV=75` (retryable, `:21`), nulls dimensions so the cell is never scored, and requires the rejection to be *unescaped top-level stream text* to reject false positives from quoted text in tool output (`shared/behavior-benchmark/framework.md:201`). Note what it does **not** do: it has no positive classifier for a broken model id; anything not matching one of five quota strings is treated as real behavior.
- **The second 429 implementation is substring-based and off-path.** `deep-improvement/scripts/model-benchmark/dispatch-model.cjs:129-134` uses `RATE_LIMIT_PATTERNS = [/rate limit/i, /429/, /quota exceeded/i]` with backoff `[60000, 120000, 240000]` and, after 3 strikes, a pause sentinel `rate_limit_exhausted_3_strikes` (`:558-566`). It would false-positive on any output containing "429"; it uses the same per-invocation constant schedule with no jitter or shared state; and per the feature catalog it is "loaded only on the model-benchmark path" and its `KNOWN_EXECUTORS` excludes codex and native (`deep-improvement/feature-catalog/feature-catalog.md:308`). It does not protect the fan-out.
- **The typed quota-aware fallback router exists and has zero production callers.** `fallback-router.ts` implements exactly the required semantics — typed failure kinds, `unknown model` vs `pool exhausted` as distinct fail-fast reasons (`fallback-router.ts:369`, `:381`), hard refusal of same-pool fallback (`:404`) and an approval guard (`:415`) — exports `createFallbackRouter` (`:338`) and `resolveFallback`. A wiring grep (`fallback-router(\.js)?['"]|require\(.*fallback-router`) over the entire `runtime/` tree matches only two test files (`tests/unit/fallback-router.vitest.ts:8-12`, `tests/unit/executor-provenance-mismatch.vitest.ts:12`). When a quota pool exhausts at N-way concurrency, the only sanctioned reaction in shipped code is to fail the lineage.
- **cli-opencode's 429 is a hang, not an error — and it is documented to bite the deep loop specifically.** `cli-opencode/SKILL.md:13`: an out-of-quota default provider makes opencode "retry the 429 indefinitely and produce NO output — indistinguishable from a deadlock"; `:188` adds this is "the single most common cause of a 'hung' `opencode run` — including command-driven deep-loop runs, where the orchestrator inherits the default even though `--executor`/`--model` were passed for the leaf." Under the fan-out this manifests as stall-watchdog SIGTERM → classified `timed out`/`killed by signal` (failure block above). The runner's own taxonomy misattributes provider quota exhaustion to a timeout.
- **The only empirically documented quota-vs-broken-id discrimination method in this repo is a differential probe, not error parsing.** `cli-pi/changelog/v1.5.3.0.md`: on 2026-09-11, a brand-new id and the previously verified id both returned the same `429 "You have reached your monthly Clinepass limit"` — "That shared failure is how we know the block is the account's quota and not the id." The playbook skip list was then updated so a 429 "reads as 'route never exercised' rather than as a pass or as a model failure" (`:35`). The changelog also records a third, distinct id-failure mode: a stale local catalog that only `pi update --models` fixes.
- **Devin's precedent is the same probe pattern.** `cli-devin/SKILL.md:335`: a free-tier model still dispatches with the Pro quota at 0%, so "do not abandon a dispatch on the quota banner alone; probe with a trivial read-only call first"; persistent rate limits are an explicit stop-and-check-plan condition (`:377`). For auth errors, both cursor and devin require re-auth then retry, and explicitly forbid substituting an unapproved model (`cli-cursor/SKILL.md:204`, `cli-devin/SKILL.md:196`).
- **Quota is handled statically at model-curation time, not dynamically at dispatch time.** `executor-config.ts:356-360` records retiring Gemini 3.8 Flash High because "one research pass exhausted the daily quota. It stays reachable through the cursor route only" — the cross-pool escape is a hand-edited allowlist, not a runtime route.
- **UNKNOWN:** 429/quota semantics for cli-codex and cli-claude-code were not examined this iteration (iteration-006 covered only codex's sandboxed self-spawn failure, not quota), and I did not verify whether `fanout-run.cjs` consumes any durable-orchestrator library that emits `retry_scheduled` outside the file itself.

## What this means for unlimited concurrency

- **Worktree-per-lineage is orthogonal to this axis.** Isolation fixes whose files a lineage may write; it does nothing about N lineages sharing one provider account. The quota ceiling is per-account, so the constraint scales with fan-out width exactly when the git problem is solved — unlimited lineages will simply discover the provider's concurrency limit faster.
- **The architecture has no admission control at the quota layer.** There is no token bucket, no shared backoff state, no account-level concurrency cap, and no typed quota signal in the hot path — the only two backoff implementations are (a) per-process, jitter-free, 3-strike, benchmark-only and (b) nonexistent in the fan-out. N concurrent 429s will be N independent terminal rejections (or worse: an unbounded opencode retry storm, or a pi salvage double-fire).
- **The three providers collapse quota failure into three different, misclassified artifacts** — opencode: hang → "timed out"; pi: non-zero ignored → "salvage-miss" possibly retried; everything else: "exited with code N". Any operational dashboard built on the current ledger cannot tell "the account is out of quota" from "the model id is wrong" from "the CLI is broken", and at high concurrency that misdiagnosis is the default state.
- **The pieces for a correct fix largely exist and are unwired.** The `fallback-router` provides typed failure kinds and cross-pool routing; the behavior-benchmark regex provides the unescaped-stream discriminator for quota text. A quota-aware fan-out would classify provider rejections typed at the point of capture, defer or reschedule on quota (never count it as a lineage failure), and reserve retries for genuinely unknown failures — none of which is true today.

## Open question this raises

At what fan-out width does shared-account quota exhaustion become the dominant failure mode relative to per-CLI stalls, and is there a reliable *per-runtime* producer-side signal (opencode's `--print-logs` stream error, codex's stderr status line, pi's output text) that the runner could classify at capture time before the stall watchdog fires — or does every runtime require the cross-model differential probe to distinguish a 429 from a broken id?

# Worktree Symlink Iteration 004

**Model:** `llmgateway/deepseek-v4.1-flash` at max thinking  
**Angle:** The rule as written versus the invariant it protects: what sk-git's provisioning rule currently forbids that is actually safe, the narrowest correct wording, and every other place in this repository that depends on the current broad wording, including the launch wrapper which already symlinks and the large-reorg playbook

## Findings

- The rule exists in three different scopes, and they disagree with each other. Broadest (no mechanism qualification): `.opencode/skills/sk-git/references/worktree-workflows.md:533` — "**Do NOT symlink deps into the worktree.**" Middle: `.opencode/skills/sk-git/SKILL.md:363` (Rule 8, §4 ALWAYS) — "Provisioning **installs** rather than symlinking a tree from the main checkout, because a package's `node_modules` carries relative workspace self-links that resolve back to where they were created — symlink it and the worktree silently compiles against the other checkout's build output." Narrowest and closest to the truth: `.opencode/skills/sk-git/scripts/worktree-naming.sh:448-451` — "Provisioning INSTALLS rather than symlinking a tree from the source checkout. A package's node_modules carries its own workspace self-links, which are relative and resolve back to wherever they were created". Only the third names the invariant; the first bans the technique.

- The skill's own text already proves the technique is not the defect. `.opencode/skills/sk-git/SKILL.md:291`: "**Deliberate per-session deps override.** The wrapper **symlinks** the shared `node_modules`/`dist` into each worktree … an intentional exception to the §4 'bare worktree lacks gitignored deps' guidance." Same operation (`ln -s` of an absolute directory), legal or illegal depending on which caller runs it — that is a wording scoped to caller, not to defect.

- What the broad wording forbids that is safe: four of the six default shared paths contain no repo-internal links, so linking them wholesale cannot re-anchor anything. `worktree-session.sh:81-88` (`default_shared_paths`) lists `.opencode/skills/system-spec-kit/node_modules`, `runtime/node_modules`, `runtime/dist`, `runtime/cli/dist`, `runtime/cli/node_modules`; the deep-loop list adds `system-deep-loop/runtime/node_modules` (`worktree-lifecycle.ts:147-154`). Per the verified inventory, self-links exist only under `system-spec-kit/node_modules` (3) and `system-deep-loop/runtime/node_modules` (1). `system-spec-kit/runtime/node_modules` and `runtime/cli/node_modules` are vendored-only trees whose entries are third-party packages, and `worktree-workflows.md:533` still forbids linking them.

- Both privileged callers commit the exact defect the rule names, and neither recreates a self-link. Wrapper: `bin/worktree-session.sh:325` `ln -s -- "$src" "$dst"` over the whole tree, including `system-spec-kit/node_modules` (which carries 3 of the 4 self-links). Deep-loop: `worktree-lifecycle.ts:415` `symlinkSync(sourceAbs, destAbs, 'dir')` over its whole list, including `system-deep-loop/runtime/node_modules` (the 4th). So the exception at SKILL.md:291 is not a weaker rule, it is an unmitigated instance of the banned shape.

- Correction to the given hypothesis ("wholesale is the defect"): wholesale matters for two distinct reasons, and per-entry linking fixes only one. (a) Wholesale drags in the self-links — fixed by recreating them relative to the worktree. (b) Default Node resolution realpaths a loaded module regardless of how deeply the link sits, so first-party code in a linked `dist` still sees main's path as its own location even if every entry is linked individually. Compiled CLI entries do consult that value: `.opencode/skills/system-spec-kit/runtime/cli/dist/spec-folder/generate-description.js:135-136`, `observability/smart-router-analyze.js:11-12`, `observability/smart-router-measurement.js:18-19` all compute `IS_CLI_ENTRY = path.resolve(process.argv[1]) === fileURLToPath(import.meta.url)`. When invoked inside a lane through a wholesale-linked `dist`, `argv[1]` is the worktree spelling while `import.meta.url` realpaths to main, so the guard reads false. This is inferred from the code — no command execution is available in this dispatch; confirmation is to run one such entry from a wrapper lane and print the guard.

- `runtime-bootstrap.cjs` does **not** depend on the provisioning wording; it depends on resolution semantics, which constrains any fix. `.opencode/skills/system-deep-loop/runtime/scripts/runtime-bootstrap.cjs:26-36`: `NODE_PRESERVE_SYMLINKS` is stripped deliberately ("The runtime never relies on preserved symlinks — write containment resolves every path through `fs.realpath`"). So `--preserve-symlinks` is not an available mechanism for the narrowed rule.

- Full dependent inventory on the current broad wording (any wording change must touch these or the repo contradicts itself): `.opencode/skills/sk-git/SKILL.md:363` (Rule 8) and `:291` (wrapper exception); `scripts/worktree-naming.sh:448-451` (rationale comment), `:490-519` (`provision_worktree`, `npm ci|install` per path, documented idempotence keyed on the presence of `node_modules` at `:491` — so a path already linked reads as provisioned; that read is inferred from the comment, not observed), `:539-541` (usage), `:405-406` (create → provision); `references/worktree-workflows.md:533-536` (Caveat 1); `references/large-reorg-playbook.md:131` and `:167` ("Strict-validate 'passes' but touched 0 files | Ran in bare worktree (no deps) or via symlinked deps | Run toolchain on `main`" — a triage row that needs the disambiguation); `feature-catalog/workflow-playbooks/large-reorg-playbook.md:28`; `feature-catalog/session-lifecycle/launch-wrapper-session-isolation.md:37`; `feature-catalog/feature-catalog.md:65`; `bin/README.md:187`; `bin/worktree-session.sh:24, 78-88, 247, 325`; `worktree-lifecycle.ts:136-157, 415`. No automated check asserts the broad ban: `bin/tests/worktree-session.test.sh:83-85` and GIT-031 assert only that a traversal-shaped entry is skipped and the destination stays a non-symlink file; narrowing the rule breaks no test I read.

A full enumeration is required before classifying `dist` as safe-to-link.

## Recommended mechanism

- Replace the mechanism ban with a resolution-containment invariant in all four canonical spots (SKILL.md:363, worktree-naming.sh:448-451, worktree-workflows.md:533-536, large-reorg-playbook.md:28): *No path linked into a worktree may resolve any repository-internal reference back to the source checkout — neither a symlink inside the linked tree, nor the location a loaded module derives from its own file. A vendored dependency tree that does neither may be linked.*
- Make the per-path policy data, not prose: three classes — `link` (vendored-only `node_modules`), `link + recreate` (trees carrying repo-internal self-links: link vendored entries, then create each self-link relative to the worktree's own target, per iteration-003's constraint), `install` (first-party `dist` until its code locates the repo root from an explicit root/env instead of its own path). Compute the class at provision time from the lockfile link entries plus a scan for escaping symlinks, rather than hardcoding it in two duplicated lists (`worktree-session.sh:81-88`, `worktree-lifecycle.ts:147-154`).
- Scope the wording fix to the invariant; keep `provision_worktree`'s install path as the class-`install` implementation, and update its header comment (worktree-naming.sh:448-451) and the launch-wrapper exception note (SKILL.md:291) to say the wrapper satisfies the same rule, not that it is exempt from it.
- Reconcile the triage row at `large-reorg-playbook.md:167`: "via symlinked deps" → "via deps whose resolution re-anchors to the source checkout", so the failure mode is identified by symptom, not by technique.
- Ordering guard the current code lacks: `provision_worktree` must not treat an already-linked path as provisioned (present `node_modules` as a symlink passes a `[ -d ]` check); verify the class before skipping.

## What would break it

- Static classification drifts: add one workspace package with a self-link, or one `dist` entry that uses its own module URL, and a frozen whitelist silently misclassifies. The class must be recomputed per provision, and the two duplicated path lists must be unified.
- The `SPECKIT_WORKTREE_SHARED_PATHS` override (`worktree-session.sh:218-219`) lets an operator bypass classification entirely; the invariant has to be enforced at link time (refuse or recreate), not only in the default list.
- The `IS_CLI_ENTRY` reasoning is flag-dependent: under `--preserve-symlinks` `argv[1]` and `import.meta.url` agree and the guard fires, while `runtime-bootstrap.cjs:26-36` shows the repo strips that flag — any fix that relies on default realpath behavior without testing both modes can flip silently.

## 1. AGENT-SWARMS SUMMARY

For compact citations, `AS/` means `specs/system-deep-loop/037-graph-engineering/context/agent-swarms/`; `BLOG/` means `specs/system-deep-loop/037-graph-engineering/context/blog-posts/`.

AgentSwarms is a self-hosted, source-available agentic-AI and BI platform. Its main surfaces are agent chat, a visual multi-agent workflow canvas, RAG/knowledge bases, batch evaluations, traces and cost accounting, governed data access, notebooks, document generation, and warehouse-backed analytics (`AS/README.md:31-53,57-88,105-122`).

Its stack is TypeScript/React 19 on TanStack Start/Router, Supabase for Postgres/Auth/Storage/pgvector, XYFlow for the graph canvas, LangChain/LangGraph dependencies, DuckDB for local analytics, and Docker/Kubernetes services for notebooks and sandboxed execution (`AS/docs/ARCHITECTURE.md:9-34`; `AS/package.json:30-132`). User-authored JavaScript executes in a separate secretless, network-isolated worker container with time, memory, and concurrency caps (`AS/services/js-sandbox/server.mjs:1-30,48-63`).

The swarm subsystem has four principal layers:

- A visual editor and reusable templates under `AS/src/components/` and `AS/src/lib/swarmTemplates.ts`.
- Shared graph semantics in `AS/src/lib/swarmGraph.ts`, consumed by browser and server executors.
- Two execution paths: the interactive canvas runtime (`AS/src/lib/swarmRuntime.ts`) and the deployed/scheduled headless runtime (`AS/src/utils/swarmExecute.server.ts`).
- Supabase persistence for graph snapshots, runs, steps, approvals, checkpoints, evaluations, traces, and policies.

Although LangGraph is installed and swarms can be exported as LangGraph Python or TypeScript, the product runtime is a custom topological executor. The export generator even leaves loop bodies and full tool-loop wiring as TODOs (`AS/src/lib/swarmExportLangGraph.ts:149-166,295,339-349,526-539,677,720-730`). Thus AgentSwarms is most useful here as an implemented graph runtime and product architecture, not as a thin LangGraph wrapper.

## 2. HOW AGENT-SWARMS USES GRAPH ENGINEERING / LOOPS

- **OBSERVED-IN-CODE — executable DAG semantics.** Nodes are ordered into dependency levels; loop self-edges are exempted, while other cycles fail. Independent nodes in a level run through a bounded worker pool (`AS/src/lib/swarmGraph.ts:196-231`; `AS/src/utils/swarmExecute.server.ts:997-1025`). This implements the explicit node/edge contracts and fan-out/barrier model in `BLOG/Graph Engineering explained: what it is, when to use it and when not to.md:30-69,73-120`. It is a level-synchronous DAG, not a general cyclic or pipelined graph.

- **OBSERVED-IN-CODE — deterministic fan-in and branch pruning.** The headless executor stages writes, applies configurable `last|first|concat|sum` reducers in graph order rather than response order, and then applies branch decisions deterministically (`AS/src/lib/swarmGraph.ts:103-174`; `AS/src/utils/swarmExecute.server.ts:1023-1040`). `SkipTracker` kills untaken edges and cascades skips while allowing a diamond join to run if any incoming branch survives (`AS/src/lib/swarmGraph.ts:234-284`). These are direct implementations of deterministic reducers, diamonds, barriers, and typed handoffs from `BLOG/Graph Engineering Roadmap.md:22-95,96-153`.

- **OBSERVED-IN-CODE — routing fails closed.** Conditions must resolve unambiguously to YES or NO; routers must map to a declared route. Failed condition/router nodes cannot use `continueOnError`, because doing so would leave every branch live (`AS/src/lib/swarmGraph.ts:85-101`; `AS/src/lib/swarmRuntime.ts:472-485,1924-1967`). This matches the blog corpus's rule that routing decisions structurally control execution rather than merely annotate it (`BLOG/Harness, Loop, or Graph? Building Reliable Agent Systems at the Right Layer.md:52-90`).

- **OBSERVED-IN-CODE — loops inside graph nodes.** A loop node repeatedly passes the previous attempt back to the same model, with a hard cap of six. It stops when the output contains a line consisting of `DONE` (`AS/src/lib/swarmGraph.ts:34-59`; `AS/src/lib/swarmRuntime.ts:468-470,1348-1387`). The tool loop separately executes all tool calls in a model round concurrently, returns observations, and continues up to a fixed budget (`AS/src/utils/tools/loop.server.ts:257-478`). These instantiate the "graph contains loops" layering, but the refinement loop is weaker than the builder–independent-judge–manager pattern in `BLOG/How to Build a Self-Correcting AI Loop That Catches Its Own Mistakes Before You See Them.md:14-61`: completion is self-declared, not independently established.

- **OBSERVED-IN-CODE — evaluation can become an edge gate.** Evaluate nodes produce JSON metric scorecards; the Support Copilot template explicitly routes the scorecard through a condition, sending passing work to output and failing work to approval (`AS/src/lib/swarmRuntime.ts:1809-1893`; `AS/src/lib/swarmTemplates.ts:438-447,493-508`). Batch evaluation additionally supports deterministic `contains`, `exact`, and `regex` checks, recomputes weighted judge scores rather than trusting the model's claimed aggregate, and stores comparable per-case results (`AS/src/lib/evalScoring.ts:1-15,101-191,194-278`; `AS/supabase/migrations/20260809000000_batch_evals.sql:1-18,46-95`). NL-to-SQL is graded by execution result rather than generated SQL text (`AS/evals/nl2sql/grade.ts:1-49`). This approaches the "verdict changes the run" rule in `BLOG/Eval Engineering: build the gate that lets your agents merge without you (full 6-step course).md:14-62`; however, an evaluate node alone only emits data. The author must wire a downstream condition for it to govern flow.

- **OBSERVED-IN-CODE — durable state, graph pinning, and human interruption.** A checkpoint stores variables, completed/skipped nodes, dead edges, topological position, and a suspended approval node (`AS/src/lib/swarmCheckpoint.ts:11-80`). Headless runs checkpoint after each committed level and resume from the run's original graph snapshot; deployed runs normally use a pinned published graph (`AS/src/utils/swarmExecute.server.ts:1043-1056,1078-1125`; `AS/src/lib/swarmPublish.ts:1-42,44-121`). Approval routing supports users/groups and parks rather than completes a run (`AS/supabase/migrations/20260724100000_swarm_approvals_and_runs.sql:1-60`). These implement harness-level auditability, checkpoints, stable topology, and human gates.

- **OBSERVED-IN-CODE — nested subgraphs and bounded resources.** A swarm may execute another saved swarm as a node, capped at three nesting levels, while whole-run deadlines propagate into nested executions (`AS/src/lib/swarmRuntime.ts:1765-1806`; `AS/src/utils/swarmExecute.server.ts:286-319`). This realizes the "graph of loops/subgraphs" organization in `BLOG/Graph Engineering: After Loops, This Is How You Wire Multi-Agent Orgs.md:67-114`.

- **OBSERVED-IN-CODE — knowledge graphs, but as a separate retrieval path.** Graph construction extracts typed entities and free-form predicates, normalizes names, deduplicates triples, and records mentions; retrieval uses lexical seed entities plus one- and two-hop traversal (`AS/src/routes/api/kb/build-graph.ts:1-50,89-105,230-340`; `AS/src/utils/tools/kb-graph.server.ts:1-9,117-240`). Conventional RAG separately supports semantic/keyword hybrid fusion (`AS/src/lib/kbRag.ts:160-252`). **INFERRED:** a query router combining vector, keyword, and graph traversal would better implement the corpus's "route by question type" recommendation; today graph search is an explicitly selected tool, not an automatic hybrid strategy.

Two implementation cautions are research-worthy. First, checkpoint-save errors are logged and swallowed, making resumability best-effort (`AS/src/utils/swarmCheckpoint.server.ts:6-37`). Second, the server stages concurrent writes, while the browser executor's parallel path mutates shared state directly; its parity test primarily checks source-level node-kind/import presence rather than executing both runtimes against golden graphs (`AS/src/lib/swarmRuntime.ts:1970-2043`; `AS/tests/unit/swarmExecutorParity.test.ts:26-58,117-151`). **INFERRED:** this is a parity risk, not yet proof of divergent outputs. Headless runs also explicitly disable configured memory (`AS/src/utils/swarmExecute.server.ts:150-158`).

## 3. GRAPH-ENGINEERING CONCEPT MAP

The corpus's central hierarchy is:

**Harness → Graph → Loop.** The harness owns capabilities and operational boundaries: tools, sandboxes, permissions, memory, budgets, audit, checkpoints, and evaluators. The graph owns control flow: typed nodes, data-carrying edges, branches, joins, retries, and gates. A loop owns local iterative improvement based on evidence and bounded stopping conditions (`BLOG/Harness, Loop, or Graph? Building Reliable Agent Systems at the Right Layer.md:4-90`; `BLOG/LOOP ⭢ GRAPH ⭢ HARNESS: build the whole pipeline in one sitting.md:12-27,75-140`). A graph therefore does not replace loops; it composes multiple loops and deterministic operations within a governed harness.

A node should have a narrow contract—input shape, permitted context/tools, output type, failure semantics, and budget. An edge should be treated as a data/dependency contract, not merely a drawn arrow. The "fake-edge test" asks whether the target truly depends on the source; if not, they should probably execute independently (`BLOG/Graph Engineering explained: what it is, when to use it and when not to.md:30-69`). Typical topology is a diamond: parallel independent makers or researchers, deterministic reduction, fresh-context verification, then synthesis or escalation.

The corpus distinguishes a relatively stable **organizational/control graph**—roles, permissions, policies, and handoff rules—from a per-run **work graph** generated for the actual task (`BLOG/Graph Engineering: After Loops, This Is How You Wire Multi-Agent Orgs.md:124-170`). Knowledge graphs form a third complementary plane: typed entities and relationships support multi-hop retrieval, contradiction detection, temporal supersession, and evidence paths (`BLOG/What is Graph Engineering.md:82-158,184-235`).

Graphs are warranted when work has genuine independent branches, repeated multi-stage execution, complex conditional routing, multiple verification steps, expensive context isolation, or failure that should be localized. They are poor fits for small linear tasks, exploratory work whose topology is not yet known, tightly supervised one-offs, or intrinsically sequential dependencies. The corpus recommends tracing a simpler loop first and formalizing only stable patterns (`BLOG/Harness, Loop, or Graph? Building Reliable Agent Systems at the Right Layer.md:92-118`; `BLOG/Graph Engineering explained: what it is, when to use it and when not to.md:193-231`).

A robust self-correcting loop separates builder, judge, and manager; grounds the judge independently; uses structured handoffs; and stops on measurable quality, iteration, cost, or time limits (`BLOG/How to Build a Self-Correcting AI Loop That Catches Its Own Mistakes Before You See Them.md:14-99`). Robust eval gates run deterministic checks first, prefer independent or diverse judges, make verdicts structurally control the run, evaluate trajectories as well as final output, use negative controls, pin evaluator versions, and launch in shadow mode before granting authority (`BLOG/Eval Engineering: build the gate that lets your agents merge without you (full 6-step course).md:14-184`).

## 4. CURRENT system-deep-loop + 036 STATE

Today `system-deep-loop` exposes seven modes: research, review, AI council, agent improvement, model benchmark, skill benchmark, and alignment. Research/review/council share the graph-backed convergence runtime; improvement lanes use a separate improvement host, and alignment has its own convergence backend (`.opencode/skills/system-deep-loop/mode-registry.json:1-29,30-201`).

Deep research remains primarily a sequential outer loop: fresh LEAF context per iteration, externalized configuration/strategy/registry/dashboard, append-only JSONL state, per-iteration Markdown and delta files, then reduction and synthesis (`.opencode/commands/deep/assets/deep-research-auto.yaml:20-37,82-122`). Its inline three-signal stop vote combines rolling novelty average, MAD noise floor, and question coverage; a separate coverage graph may veto stopping using question/claim coverage, contradictions, source diversity, and evidence depth (`.opencode/commands/deep/assets/deep-research-auto.yaml:608-675`; `.opencode/skills/system-deep-loop/runtime/scripts/convergence.cjs:303-335,387-443`). Thus the existing graph is principally an evidence/convergence projection, not the orchestration topology.

Fan-out launches complete detached loop lineages into isolated artifact directories using a bounded flat pool. Wave/`depends_on` scheduling remains explicitly rejected until a conflict-safety substrate exists (`.opencode/skills/system-deep-loop/runtime/scripts/fanout-run.cjs:332-430,1081-1164,2171-2424`). The loop lock provides owner/nonce identity, heartbeat, stale detection and atomic reclaim (`.opencode/skills/system-deep-loop/runtime/lib/deep-loop/loop-lock.ts:542-717`).

036 supplies the stronger authority plane needed beneath any graph runtime: typed append-only events, fail-closed transition authorization, replay fingerprints, sealed artifacts, side-effect receipts, budgets, fencing, continuity identity, and blinded/counterfactual adjudication. Its migration is deliberately additive/dark: compatibility and shadow parity precede mode-by-mode authority cutover; legacy writers retire only after zero-use evidence (`specs/system-deep-loop/036-deep-loop-innovation/spec.md:45-103,123-169`).

## 5. RESEARCH ANGLES

1. **Typed executable graph IR over the 036 authority plane.** Determine the minimum node, edge, port, reducer, branch, retry, and subgraph schema needed to express existing modes without making checkpoints authoritative. Examine `AS/src/lib/swarmGraph.ts`, `AS/src/lib/swarmRuntime.ts`, `BLOG/Graph Engineering Roadmap.md`, `.opencode/skills/system-deep-loop/mode-registry.json`, and 036 phases 006–008/012. **Yield:** a versioned graph IR and an explicit rule that every graph transition must obtain 036 gateway authorization and emit ledger evidence.

2. **Scheduler semantics: barrier, pipeline, and conflict-safe waves.** Compare AgentSwarms' level barriers and deterministic reducers with deep-loop's detached flat pool and rejected wave metadata. Inspect `AS/src/lib/swarmGraph.ts:103-231`, `AS/src/utils/swarmExecute.server.ts:997-1056`, `BLOG/Graph Engineering with Claude: How to Stop Running a Line and Start Running a Fleet.md:195-211`, and `runtime/scripts/fanout-run.cjs:332-430`. **Yield:** a decision table for barrier versus pipelined execution, edge readiness, reducer algebra, write-set conflicts, and when 036 fencing authorizes a wave.

3. **Eval verdicts as first-class control edges.** AgentSwarms demonstrates deterministic evaluators and manually wired eval→condition→approval flow, while 036 provides blinded adjudication and sealed references. Examine `AS/src/lib/evalScoring.ts`, `AS/src/lib/swarmTemplates.ts:438-508`, `BLOG/Eval Engineering...md`, current convergence gates, and 036 phase 007/025. **Yield:** a typed `GateVerdict` edge contract with deterministic-first checks, blinded panels, mandatory structural routing, negative controls, and certificate binding.

4. **Durable graph replay, effects, and resumable human gates.** Contrast mutable, best-effort AgentSwarms checkpoints with the authoritative 036 ledger, receipts, fencing, and replay fingerprints. 5. **Loops as typed subgraphs with independent convergence.** Replace opaque self-editing nodes and `DONE` tokens with builder–judge–manager subgraphs whose exit edges carry measured evidence.

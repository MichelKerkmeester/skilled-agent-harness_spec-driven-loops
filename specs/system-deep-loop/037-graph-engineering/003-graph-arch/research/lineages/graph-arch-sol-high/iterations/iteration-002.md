# Iteration 2: GraphARC Governance Architecture and Trust Boundaries

## Focus

This iteration traced GraphARC's actual governance path from planner data through admission, materialization, kernel execution, tool/effect adapters, sessions, policy/audit, budgets, and observability. It distinguishes canonical objects within GraphARC's local boundary from convenience projections, identifies which facts are forgeable versus independently derived, and locates the enforcement chokepoints. It builds on iteration 1's decision ledger without reopening its blocked authority readings.

## Findings

1. **Proposal → admission → materialization → kernel is a four-boundary chain — CONFIRM Decision 1 and REFINE its sealed-compilation model.** `Subgraph` is untrusted planner data; `AdmissionChecker.check()` independently derives registry, policy, budget, depth, reachability, and acyclicity results without executing work; `Materializer.materialize()` checks admitted status plus exact proposal fingerprint and sources bodies only from the operator registry; the graph kernel then enforces declared writes, typed state, route confinement, isolation, budget, and trace wrappers. No one object is canonical for the whole chain. The actual pre-execution chokepoints are the checker and materializer; kernel controls remain necessary after both pass. [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/planner/admission.py:1-50] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/planner/admission.py:551-600] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/planner/materialize.py:1-43]

2. **Registry ownership is the executable trust root but not immutable by default — REFINE Decision 7 and EXTEND Decision 1's TOCTOU gap.** Node kinds, bodies, declared worst-case cost, and optional write declarations come from operator-owned registries rather than proposal fields. However, the governed loop explicitly reuses the same mutable `NodeRegistry` object across rounds and warns that a node body can widen it unless the operator calls `freeze()`. Proposal fingerprints do not bind registry contents. Planner `args` are also ungoverned: default materialization drops them, while `forward_args=True` passes raw unchecked JSON to factories. Therefore registry freeze/digest and typed per-kind argument validation are separate required proof facts. [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/planner/loop.py:12-24] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/planner/proposal.py:95-120] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/planner/materialize.py:11-27]

3. **The policy document is locally canonical, but compiled enforcement objects are lossy — EXTEND Decision 7's organization-policy compiler.** `PolicyDocument` is frozen, validates unique rule identities and approver roles, and hashes the parsed model; `PolicyDecision` records tenant, resource, rule, reason, role, version, digest, request, and context. The `permission_policy()`, `node_policy()`, and `edge_policy()` adapters deliberately lose rule identity, approver role, and audit recording because their target interfaces return bare decisions. The approval router re-asks the engine to recover role and audit. The chokepoint is therefore `PolicyEngine` only when callers route decisions back through it; a compiled policy alone is a convenience enforcement view, not the canonical decision record. [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/policy/document.py:89-110] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/policy/document.py:141-205] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/policy/engine.py:55-69] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/policy/engine.py:193-266] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/policy/engine.py:401-427]

4. **Approval is three independent enforcement surfaces, not one durable gate — REFINE Decisions 3 and 4 and EXTEND Graphene P7.** Policy ASK routing is synchronous, role-based, fail-closed, and policy-audited; planner-loop approval binds the proposal and admission result before execution; session approval holds tasks at a checkpointed node boundary. The session source and tests prove the same compiled graph can be invoked directly and run gated nodes while the session record still says approval is pending. Session holds also bind node/request IDs rather than the full live semantic dependency vector, and one session-runner claim is not a reclaimable lease. The actual chokepoint for a session approval is the session driver, not the compiled graph, so direct-call closure and atomic 036 revalidation remain unresolved. [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/policy/approvals.py:1-18] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/policy/approvals.py:88-140] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/session/runtime.py:16-34] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/session/runtime.py:36-65] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/tests/test_session.py:194-209]

5. **Graph governance ends at graph-local control; harness governance begins at capability execution — CONFIRM Decision 1's adapter boundary and Decision 7's non-authority rule.** Materialization confines declared topology and `Command(goto=...)`, but explicitly does not constrain what a registered body does internally. The harness is the code-level security chokepoint for tool execution: registry lookup → deny/ask/allow → approval → pre-hooks → sandboxed executor → post-hooks. The graph may decide what can happen next, while the harness decides which capabilities actually run and under what controls; neither substitutes for 036 transition/effect authority. [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/planner/materialize.py:29-43] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/planner/materialize.py:62-65] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/harness/core.py:1-8] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/harness/core.py:47-78] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/blog-posts/Harness, Loop, or Graph? Building Reliable Agent Systems at the Right Layer.md:72-90]

6. **Budget governance is partitioned across estimate, in-process meters, and provider spend — REFINE the cross-cutting budget decision.** Admission reads a registry-derived worst case and a remaining-budget snapshot but charges nothing. `GovernedLoop.run()` creates one `BudgetMeter` for its rounds and charges planning plus execution against it. Kernel invokes and gateway model objects have their own runtime meters; `SpendMeter` is mutable, unsynchronized, approximate under concurrent calls, and cannot enforce unreported provider costs. These objects are enforcement counters for their scopes, not durable allocation/reservation records. The missing chokepoint is a 036-owned reservation/debit/receipt lifecycle carried through resume, subgraph, node, attempt, and provider calls. [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/planner/admission.py:23-41] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/planner/loop.py:50-56] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/planner/loop.py:370-380] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/gateway/spend.py:1-19] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/gateway/spend.py:29-85]

7. **Session rows, policy audit, trace, replay, and OTel are different records with different authority — CONFIRM Decision 4 and Graphene P2/P3; REFINE the observability inventory.** Session status/queue/holds are durable coordinator state and graph state lives separately in the checkpointer. Policy audit is append-only only when given a path; an in-memory cap may discard records. `TraceRecorder` is an append-only JSONL operational record, but producers must be wired to the same recorder manually, long values are truncated, and it lacks reducer and parent identities. Replay reconstructs without re-executing and may require caller-supplied reducers; OTel is derived from that reconstruction. Thus the trace is canonical only for what its participating producers recorded, never for all governance facts, while replay/OTel are convenience projections. ## When Not to Use

- Do not introduce GraphARC graph governance for a single deterministic command or a small one-agent task without stable branching, coordination, approval, recovery, or resume needs; the blog explicitly warns that graphs add orchestration overhead when the work does not require explicit structure. [SOURCE: specs/system-deep-loop/037-graph-engineering/context/blog-posts/Harness, Loop, or Graph? Building Reliable Agent Systems at the Right Layer.md:92-108]
- Do not use admission to gate arbitrary tool arguments until per-kind argument schemas and policy checks exist; default materialization drops args, and opting into raw forwarding deliberately reopens the boundary. [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/planner/proposal.py:117-120] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/planner/materialize.py:21-27]
- Do not use session holds as the sole guard for irreversible effects while the compiled graph remains directly invokable; put effect authority at a non-bypassable gateway. [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/session/runtime.py:45-48]
- Do not treat a provider spend ceiling as complete enforcement when calls may be unpriced or concurrent; use it as bounded local protection and telemetry until durable accounting owns the full lifecycle. [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/gateway/spend.py:15-19] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/gateway/spend.py:29-36]
- Do not use topology to repair tool, permission, state, or sandbox defects; graph, loop, and harness own different failure classes. [SOURCE: specs/system-deep-loop/037-graph-engineering/context/blog-posts/Harness, Loop, or Graph? Building Reliable Agent Systems at the Right Layer.md:84-116]

- Treating direct compiled-graph invocation as session-gate compliant: the session runtime and regression test demonstrate the gated node executes while approval remains pending. [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/grapharc/session/runtime.py:45-48] [SOURCE: specs/system-deep-loop/037-graph-engineering/context/graph-arch/tests/test_session.py:194-209]

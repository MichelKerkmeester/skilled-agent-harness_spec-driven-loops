## 7. WHAT WORKED
- Decision-by-decision comparison exposed that GraphARC's new value clusters at governance seams rather than replacing the prior architecture, which prevents later iterations from restating broad graph benefits. (iteration 1)
- Tracing producers, stored objects, consumers, and bypass paths exposed where similarly named “policy,” “approval,” “budget,” and “audit” concepts have different enforcement scope. (iteration 2)
- Following the proof from checker output through materialization and into the existing gateway/append verifier separated precondition evidence from authorization and commit revalidation cleanly. (iteration 3)
- Following every producer consumed by `Materializer` exposed the gap between proposal identity and executable identity; mapping that to `withFence` then made the immutable-content/live-authority split precise. (iteration 4)
- Tracing each source rule through direct evaluation, lossy adapters, approval routing, and the 036 decision schema made provenance loss observable field by field. (iteration 5)
- Tracing the same approval through proposal, policy, session, authorization, fencing, and effect boundaries exposed exactly where each existing mechanism stopped carrying identity or freshness. (iteration 6)
- Following each diagnostic from deterministic check through planner feedback, audit evidence, new candidate, and 036 boundary separated useful actionability from executable authority. (iteration 7)
- Tracing every reader backward to its producer exposed duplication and inference directly; mapping each fact to one ledger owner then made replay and export failure semantics mechanical. (iteration 8)
- Following one unit of capacity from deterministic quote through ancestor reservation, attempt debit, provider observation, settlement, and recovery exposed exactly which layers own prediction, authority, enforcement, and accounting. (iteration 9)
- Treating each prior governance decision as a fault boundary, then assigning one injected defect to the earliest owner, converted a broad test inventory into a promotion-blocking oracle instead of a checklist of filenames. (iteration 10)
- Comparing the registry's documented routing-only alias contract with GraphARC's kind-based rename tests exposed the shared canonical-identity rule, while 036 captured-state hashing supplied a concrete integration point. (iteration 12)
- Tracing the generic harness's actual comparison order and certificate checks before reading GraphARC records separated reusable enforcement from graph-specific schema gaps. (iteration 13)
- Reading the closed budget scope types and fence commit contract before composing the graph lifecycle exposed where atomicity truly ends and forced explicit recovery receipts for every cross-service gap. (iteration 14)
- Reading the shipped gateway types and tests beside the normative spec exposed the difference between a field being present and being positively verified, which made the graph evidence resolver seam explicit. (iteration 15)
- Comparing claim families across duplicated posts exposed internal corrections and prevented repetition from counting as independent evidence. (iteration 16)
- Assigning each claim to harness, loop, work graph, supervision graph, knowledge graph, or 036 authority exposed category errors that a generic “graph” label hid. (iteration 17)
- Reading implementation docstrings beside executable regression tests separated candidly documented limitations from actual enforcement and revealed the task-identity/direct-invocation change. (iteration 18)
- bounded inventories and direct owner-source checks tested the synthesis claims without retrying exhausted broad scans; source-count and term matrices exposed the iteration-19 family-count and persistence/canonicalization overstatements. (iteration 20)

## 8. WHAT FAILED
- A heading-wide scan of the long Graphene synthesis was noisy and truncated because it mixed schemas with decision text; a narrower line-range reread recovered the authoritative P4-P7 and boundary anchors. (iteration 1)
- The initial repository-wide symbol scan and broad multi-file reads truncated because tests and extensive module docstrings dominated the output; narrow range reads recovered the policy/harness/spend seams. (iteration 2)
- Broad source reads again truncated around large modules; the final narrow read of gateway evaluation and append proof validation recovered the load-bearing order. (iteration 3)
- Initial broad symbol scans were noisy and truncated because tests and blogs contained many generic graph and policy references; narrow implementation and mutation-test ranges recovered the load-bearing evidence. (iteration 4)
- The reducer's generated next-focus text pointed to iteration 4's mutant finding rather than its explicit recommendation; the dispatch prompt and planned focus sequence were more specific and aligned with the prior narrative. (iteration 5)
- Treating the proposal fingerprint as the common key was insufficient because it omits current authority, budget, policy, role, and resource heads. (iteration 6)
- The prompt's convenience Graphene mirror path was absent; the canonical repo-study path recovered P6 without changing scope. (iteration 7)
- A broad blog scan was noisy because generic “audit” and “trace” language appeared in unrelated examples; the targeted observability passage plus P2/P3 supplied the load-bearing boundary. (iteration 8)
- Broad repository scans were noisy and truncated because generic budget language appears throughout blogs and runtime consumers; narrow authority, reducer, test, and alpha-blog ranges recovered the load-bearing contracts. (iteration 9)
- The prompt's example directory was stale, and broad governance-test scans truncated because the negative corpus is large. Repository discovery plus narrow stage, admission, parity, and certificate ranges recovered the authoritative paths and semantics. (iteration 10)
- The first source guess assumed one planner policy module; GraphARC splits policy document, compilation/evaluation, approval, and audit into separate modules. (iteration 12)
- The initial generic test name omitted the `-harness` suffix; exact file discovery exposed both the generic and mode-specific suites. (iteration 13)
- A broad 036 scan mixed many historical and downstream lock/budget mentions; narrowing to the owning phase-007 specs and runtime tests recovered the enforceable contracts. (iteration 14)
- Broad study and GraphARC scans were noisy because they mixed design conclusions with local implementation claims; targeted authority-boundary anchors recovered the useful contrast. (iteration 15)
- Named organizations and headline metrics lacked reproducible methods, so they could not support performance, cutover, or authority decisions. (iteration 16)
- Product/financial/benchmark claims were not reproducible from the corpus, and a guessed GraphARC knowledge-graph module was absent; neither can carry design authority. (iteration 17)
- Broad prior-iteration/blog scans truncated because the negative corpus is large; narrow load-bearing code and service contracts supplied the decisions, while truncated material was not used to close new questions. (iteration 18)
- the initial all-state display exceeded output limits because the registry and 19 records are large; bounded JSON extraction recovered iteration integrity and strategy constraints without loss of the required control facts. (iteration 20)

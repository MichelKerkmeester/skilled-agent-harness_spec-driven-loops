## Executive Decision

GraphARC confirms the central architecture from `study-1` and `study-2`: a graph runtime should be a compiled projection that proposes and schedules transitions over one external authority plane. GraphARC contributes a substantive governance layer—deterministic admission, operator-owned executable registries, organization-policy evaluation, approval transports, local budget enforcement, audit records, and replay/OTel projections—that should be adapted rather than discarded. [SOURCE: specs/system-deep-loop/037-graph-engineering/003-graph-arch/research/lineages/graph-arch-sol-high/iterations/iteration-002.md:7-21] [SOURCE: specs/system-deep-loop/037-graph-engineering/003-graph-arch/research/lineages/graph-arch-sol-high/iterations/iteration-020.md:7-17]

A key structural result: **admission is a precondition, not authorization**. GraphARC’s `AdmissionResult` is caller-constructible data that its materializer accepts within the Python process — an expected property of any unsigned in-process library, not a deep flaw unique to GraphARC. The consequence for us follows from an explicit threat model: an adversary able to run in-process (a compromised model, a malicious plugin, or supply-chain code) can fabricate a matching `AdmissionResult`. Under that model, admission establishes deterministic structural closure only when a **trust-separated issuer** (a signer in a different process / trust domain than the planner) authenticates the result, or when 036 reruns admission itself. Because the threat model makes the issuer — not the admission object — the root of trust, 036 must still independently revalidate current actor, capability, evidence, policy, authority epoch, ledger head, budget, gate, fence, and exact event identity before any domain append. This study assumes 036 exposes those revalidation primitives rather than auditing that it does (see Unexamined Assumptions). [SOURCE: specs/system-deep-loop/037-graph-engineering/003-graph-arch/research/lineages/graph-arch-sol-high/iterations/iteration-003.md:9-19] [SOURCE: specs/system-deep-loop/037-graph-engineering/003-graph-arch/research/lineages/graph-arch-sol-high/iterations/iteration-015.md:11-19]

The adoption decision is therefore: reuse GraphARC’s checks and governance concepts behind versioned, reference-closed contracts; do not treat any GraphARC object, callback, checkpoint, trace, or local meter as bearer authority. The contracts below remain proposals until a prototype proves their owner boundaries, crash behavior, negative mutants, measured overhead, and mode-scoped rollback. [SOURCE: specs/system-deep-loop/037-graph-engineering/003-graph-arch/research/lineages/graph-arch-sol-high/iterations/iteration-018.md:7-21] [SOURCE: specs/system-deep-loop/037-graph-engineering/003-graph-arch/research/lineages/graph-arch-sol-high/iterations/iteration-020.md:102-117]

`GraphTransitionEvidenceV1` is the integration object: a closed, canonical, resolver-produced bundle referencing the exact admission proof, sealed artifact, compiled policy, optional gate, live budget reservation, protected-resource claims/heads, actor, capability, prior domain state, and causality. The end-to-end owner order is:

1. Canonicalize one proposal and assign candidate identity.
2. Compile and admit statically, producing either complete authority-zero refusal or `GraphAdmissionProofV1`.
3. Compile and register organization policy with provenance.
4. Seal executable materialization.
5. Produce a non-authoritative budget quote.
6. If policy yields ASK, open a durable task-instance gate and wait without reservation, lease, or fence.
7. Revalidate the approved gate and every live dependency.
8. Reserve budget across all ancestors.
9. Acquire canonical protected-resource claims and fences.
10. Assemble and resolve `GraphTransitionEvidenceV1`.
11. Preflight the exact registered graph event.
12. Obtain a durable 036 allow or deny audit decision.
13. On allow, append through the current fence and expected head.
14. Debit the attempt before dispatch.
15. Execute computation, emitting only outputs and proposed effects/transitions.
16. Authorize each effect separately through intent and recovery.
17. Settle incurred usage and release only proven unused capacity.
18. Append terminal graph state through a new authorization/fence cycle.
19. Replay a reference-closed cut.
20. Update disposable status, checkpoint, parity, and OTel projections. [SOURCE: specs/system-deep-loop/037-graph-engineering/003-graph-arch/research/lineages/graph-arch-sol-high/iterations/iteration-015.md:23-45]

This is a receipt-linked saga, not a cross-ledger transaction. Each owner durably commits its own fact and exposes an immutable receipt to the next owner. An unapplied 036 allow remains visible audit evidence; a crash after external application but before confirmation becomes an effect-reconciliation problem; owner disagreement blocks forward action rather than being normalized by the graph. [SOURCE: specs/system-deep-loop/037-graph-engineering/003-graph-arch/research/lineages/graph-arch-sol-high/iterations/iteration-014.md:23-77] [SOURCE: specs/system-deep-loop/037-graph-engineering/003-graph-arch/research/lineages/graph-arch-sol-high/iterations/iteration-015.md:17-19]

## Unexamined Assumptions and Missing Coverage

Independent verification (DeepSeek V4 Pro) flagged several load-bearing assumptions that this study asserts rather than establishes. They are recorded here honestly, and every design decision above should be read as conditional on them:

- **The threat model is now explicit but narrow.** The "forgeable `AdmissionResult`" risk presupposes an in-process adversary (compromised model, malicious plugin, supply-chain code). The full adversary set and attack surface are not enumerated.
- **Issuer security is out of scope.** If the trust-separated issuer is compromised, every proof is worthless; key custody, rotation, revocation, and compromise response are not designed here.
- **036 capability is assumed, not audited.** The design offloads a ~10-item revalidation list to 036 without confirming 036 exposes each primitive. If it does not, the graph adapter must supply them — a materially larger build.
- **Owner-disagreement has no resolution mechanism.** "Owner disagreement blocks forward action" is a dead-stop; arbitration, escalation, and timeout are undefined.
- **No measurements.** Zero latency, memory, or admission/compile-cost numbers were produced; the proposed governance adds real, currently-unbounded per-transition overhead, all deferred to a prototype.
- **GraphARC's concurrency behavior is not analyzed** (GIL, async, threading, fan-out races) beyond noting local meters are "approximate under concurrency."
- **Citation granularity.** Several synthesis citations point to single-line iteration anchors that carry multi-claim bullets; the underlying evidence is real, but the per-claim line spans are approximate — treat the iteration narratives, not the exact line numbers, as the authoritative source.

# Graphene · 08 · The UI

## 1. Read-only. No exceptions.

**There is no write endpoint anywhere in the UI or its HTTP surface.**

This is architectural, not a policy that could be relaxed later:

| Because read-only | |
|---|---|
| No auth surface | nothing to protect — reading requires already having the store file |
| No CSRF, no accidental clicks | there is no state to change |
| `gr serve` is a static server plus an SSE stream | that is the whole thing |
| One writer | the agent, through the CLI, recorded in the log with an actor |

The last row is the substantive one. If a human could mutate the graph directly
you would have **two authors with different understandings of the constraints**,
and the audit answer to *"who made this edge, and did they know what it implied"*
becomes ambiguous.

There is also a semantic reason. Graph edits look atomic on screen and are not:
delete an edge and the target's binding still references the source, so the plan
now fails `gr check` and the user does not know why. Prompting *"drop the
dependency between fetch and score"* lets an agent fix the binding, the schemas,
and anything downstream that assumed them.

## 2. What it is for

**The human-node inbox**, first. A dashboard second.

That framing keeps it focused: the primary job is showing a person what needs
their input, with enough context to answer it cold. Everything else — watching a
run, debugging a failure, reviewing a plan — is secondary and falls out of the
same views.

## 3. Views

### 3.1 Graph

Layered DAG, left to right, ELK or dagre layout. Nodes coloured by state:

| State | Read as |
|---|---|
| `pending` / `blocked` | muted |
| `ready` | outlined, available |
| `claimed` / `running` | active, with the holding session's label |
| `awaiting` | **the loudest thing on screen** |
| `done` | settled |
| `failed` | error, with the skipped subtree visibly greyed |

Edges are distinguished by kind — a **model-decided** edge is visually distinct
from a deterministic one, because those are the branches a model chose and the
first place to look when a run went somewhere unexpected.

Live: edges activate as data flows, node states transition in place, session
labels move between nodes. The SSE stream carries `seq`, so the client can always
reconcile against `/api/graph/:id`.

### 3.2 Node detail

On click: kind, capability, spec, input bindings with their resolved values,
output, checkpoints, attempts, budget declared versus actual, the holding
session, and the beliefs it produced.

For a **failed** node: the reason, the retry policy, what was skipped.

### 3.3 Human nodes — the priority view

A dedicated list, prominent, sorted by age. Each entry shows exactly what
`gr node <id>` returns:

- the **ask**, and the options
- the **context beliefs**, each with its state and fidelity
- **contested or stale premises marked**, with what contradicted them
- the **consequence** of each answer — which nodes unblock
- age, and the timeout policy

> A draft whose premise went stale while waiting **says so before the approver
> reads it.** That single line is why beliefs and work share a graph.

### 3.4 Timeline

What actually ran when, per session. A Gantt of node execution makes real
parallelism visible — and makes a graph that *claimed* to fan out but ran serial
obvious at a glance.

### 3.5 Beliefs

Contested beliefs, stale beliefs, and a `why()` explorer — belief → support →
producing node → source. The audit trail, clickable.

### 3.6 Library

Graphs by state, with title, description, task, age, cost, and node counts.
Pending by default; completed on request. Clone from here.

## 4. The only path back to the agent: copy

The UI's write capability is **the clipboard**.

**Copy an ID.** Every node and belief has a copy button. The user pastes the bare
ID into a fresh agent session:

```
gn_7f3k2q9wx4m1v8p0rj6htzbn5c
```

The prefix makes it unmistakable, so the skill's trigger is reliable:
*"when the user provides a bare `gn_…`, run `gr node <id>` before anything
else."* The agent resolves it, understands the ask, takes the human's input in
conversation, and writes the resolution through the CLI.

Because IDs are opaque and self-identifying, no coupling exists between the UI's
copy text and what the skill expects — which is what lets both evolve
independently.

**Copy a selection.** Select several nodes or edges and copy. The UI becomes a
**precise pointing device** for prose: *"these three should be one node"* /
*"this edge isn't real."* Direct-manipulation ergonomics at zero architectural
cost, and the agent still makes every semantic fix.

## 5. Delivery

- **Embedded in the binary** via `rust-embed`. No npm install, no separate
  deploy, no version skew between binary and assets. One file is what makes
  "lightweight" true from the user's side.
- **`gr ui`** opens the browser at the already-running server; `gr attach`
  started it.
- **Loopback only** — never `0.0.0.0`, not behind a flag.
- **One UI per store.** It is a single graph library at the end of the day, and
  the view spans it.

## 6. Design rules

- **`awaiting` outranks everything visually.** If a human is blocking work, that
  is the most important fact on the screen.
- **Show provenance without a click** where it fits. A receipt one page away is
  not part of the answer.
- **Never render a stale-premise item as ready to approve.**
- **Distinguish the three belief axes visibly** — provenance, fidelity, and truth
  state are different questions and must not collapse into one badge.
- **Contested is a state, not a warning icon.** A `BOTH` belief should read as
  genuinely unresolved, because it is.
- **Degrade honestly.** If the SSE stream drops, say so — a stale view rendered
  as live is worse than a visible reconnect banner.

## 7. Performance

A 500-node graph must lay out and render without becoming spaghetti: layered
layout, subtree collapse, focus-and-context zoom, and a filter by state and
session.

Above the node limit the graph view degrades to the list and timeline views
rather than to an unreadable hairball.

## 8. Open questions

- **OPEN** — Frontend stack. Needs a good DAG layout (ELK is the strongest), a
  small runtime for embedding, and no build-time network access. Svelte or Solid
  plus `elkjs` is the current assumption; it is not decided.
- **OPEN** — Whether the belief layer gets its own view or is only reachable
  through nodes. A separate belief graph view is genuinely useful for audit and
  is a second layout problem.
- **OPEN** — Whether selection-copy emits IDs, a structured JSON fragment, or a
  human sentence. IDs are simplest and let the agent decide; a fragment is more
  precise. Leaning IDs.

2. **[P1] The repository defines graph engineering as two coupled but distinct graph problems.** Its knowledge-graph half models entities/facts, typed relationships, time, and provenance through an ontology → extraction → fusion → serving pipeline; its task-graph half models jobs and execution dependencies with parallel fan-out, separate verifiers, stop rules, and human gates. The explicit distinction from prompt and loop engineering is that graph engineering controls topology rather than only model wording or iteration behavior. 3. **[P1] `WORKFLOWS.md` turns that definition into a governed build/evaluation discipline, not a generic graph tutorial.** The tutor workflow requires domain, skill level, time budget, route approval, one module at a time, a build task, and evidence before progression. The single-purpose workflows require schema-before-code, typed outputs with evidence spans and provenance, separate event nodes, reversible merges, skeptical evaluation, and question-type routing. It explicitly rejects a graph when a question needs aggregation rather than traversal and requires a multi-hop evaluation to justify graph maintenance. 4. **[P1] The article corpus converges on an explicit-topology thesis, with a usable admission test for graphs.** A loop is presented as a sequential observe/decide/act/verify/retry cycle, or as the loop internal to one agent; a graph exposes nodes, real data-bearing edges, parallel branches, and conditional feedback between agents. The repeated “fake-edge” test is: remove an edge if the downstream job does not consume the upstream result. The supplied decision criteria favor graphs for complex work with independent verification, cross-domain coordination, or evolving task shape; they favor a loop for small, exploratory, approval-heavy, or genuinely sequential work. 5. **[P1] The corpus's practical task-graph pattern is a governed diamond, and its failure model is distributed-systems-like.** The recurring shape is fan-out → code reduction/deduplication → fresh-context verification → synthesis, with explicit input-count guards and human gates where errors are expensive to undo. The articles warn that context collapse, shared-resource collisions that create hidden edges, and silent worker failure can invalidate an apparently complete result. The multi-agent-org article adds a stable org graph for roles/ownership and a dynamic work graph for per-run tasks, while its harness must provide routing, failure isolation, state consistency, spawning, observability, and recovery.

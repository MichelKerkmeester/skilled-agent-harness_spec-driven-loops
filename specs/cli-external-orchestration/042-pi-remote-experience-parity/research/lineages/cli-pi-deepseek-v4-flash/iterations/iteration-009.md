# Iteration 9: Axis 7 — Onboarding/Pairing Simpler than Tailscale + Ticket

## Focus
Design a pairing flow that collapses install-Tailscale → tailnet-membership → app-auth-ticket into the smallest ceremony the posture allows. Prior art: Tailscale QR sign-in + auth keys, Signal/WhatsApp device-linking QR ceremony (and MITRE T1676 abuse model), Claude Code's account-bound QR pairing.

## Findings

### F1. Tailscale's own onboarding vocabulary
- Human devices: **QR-code sign-in** — scan from a trusted phone, complete IdP sign-in, device joins; with device approval enabled the device stays pending until an admin approves ([SOURCE: tailscale.com/docs/features/access-control/device-management/how-to/set-up-qr-code]).
- Unattended devices: **auth keys** — short-lived, single-use, tagged, optionally pre-approved; an auth key authenticates the new node as the user who generated it ([SOURCE: tailscale.com/docs/features/access-control/auth-keys]).
- Implication: Tailscale already has the two enrollment primitives (QR for humans, auth key for machines). The pain is that Pi's current flow needs **both plus a manual ticket**.

### F2. Signal/WhatsApp QR linking — the out-of-band ceremony, and its abuse model
- The QR encodes a temporary server address + a fresh device public key; the primary phone's scan is an **explicit authorization ceremony**; a one-time linking token provisions the device; each linked device holds distinct keys ([SOURCE: signal.org/blog/a-synchronized-start-for-linked-devices/]).
- MITRE T1676: QR linking transfers *authority*; social-engineering a victim into scanning a pairing QR links the attacker's device. Safeguards: intentional authenticated action before scanning; confirmation screen with device type/name and consequences; ephemeral QR + one-time tokens; linked-device inventory with one-tap revoke; never accept QRs from messages or "support" ([SOURCE: attack.mitre.org/techniques/T1676/], [SOURCE: support.signal.org]).

### F3. Claude Code pairing is account-cloud-bound
- QR/URL pairing requires a claude.ai subscription login with a full-scope token ([SOURCE: code.claude.com/docs/en/remote-control] — iteration 1). No cloud account exists in Pi's posture — an advantage to keep, not copy.

## Design: Axis 7 deliverables

### Target: one QR scan = tailnet join + device enrollment (ticket step eliminated)
1. **Host**: `pi remote pair` renders a QR and starts the relay bootstrap. QR payload (ephemeral, expires ~2 min): `{nonce, hostTailnetName (MagicDNS), hostPubkeyFingerprint, tailnetJoinURL}` — `tailnetJoinURL` is a **pre-approved, tagged, single-use, short-lived Tailscale auth key URL** generated by the host's admin (`tailscale` CLI or console) for exactly this enrollment; `nonce` is relay-side one-time.
2. **Phone (one-time Tailscale app install if missing)**: scan → the QR opens the Tailscale join (one tap joins the tailnet, no admin approval because the auth key is pre-approved) AND hands `nonce` to the PWA. The PWA then performs the enrollment exchange **over the tailnet WSS** (bootstrap endpoint reachable only from the tailnet — the loopback+Serve posture): it presents its device public key + nonce proof; the relay issues a long-lived **device credential** (per-device keypair, Signal-style).
3. **Ticket step eliminated**: the device credential replaces the manual one-use WS ticket bootstrap (004's per-*session* tickets remain — app sessions are still short-lived and ticket-bound; only the *bootstrap* is now device-credentialed). Every subsequent app open: device credential → fresh short-lived session ticket. Same auth strength, zero manual steps.
4. **Enrollment confirmation is bidirectional** (T1676 defenses): the phone shows host name + fingerprint + consequences before confirming (biometric); the host shows "Phone linked: <device model> ••12, fingerprint <abbrev>" and can revoke one-tap; linked-device inventory screen with one-tap revoke on both sides; nonces are single-use and time-boxed; the QR is rendered only on the host screen (never sent in messages).
5. **Workspace registration piggybacks**: the enrollment screen lists host-registered workspaces (axis 6) with labels; the user picks which are visible to the phone; no path typing, no server-side path storage.
6. **Failure modes**: QR expiry → re-run `pi remote pair`; tailnet auth key consumed/expired → host generates another; phone not yet on tailnet → Tailscale app join handles it; enrollment interrupted → nonce invalidated, clean retry.

### Prior-art comparison (the "simpler than" proof)
- **Current 041 flow**: install Tailscale → tailnet membership (admin approval or manual auth key) → app auth ticket. Three steps, admin dependency, manual ticket per bootstrap.
- **Claude Code**: install app → claude.ai account login (cloud account + full-scope token) → QR. Two steps but cloud-account-bound.
- **Pi target**: install Tailscale (once) → scan QR → confirm. Two steps, no admin, no cloud account, no ticket. The QR ceremony compresses tailnet join + device enrollment into one intentional act, with Signal-grade abuse defenses.

## Assessment
- newInfoRatio: 0.75
- Novelty justification: the single-QR compression (tailnet join URL + pairing nonce, device credential replacing bootstrap ticket) is new design; Tailscale/Signal prior art and T1676 defenses consolidated.
- Confidence: high on prior art; device-credential vs session-ticket split respects 004 contracts.

## Reflection
- What worked: asking "which step can the QR ceremony absorb?" — the answer was two (tailnet join + ticket bootstrap).
- What failed / ruled out: removing Tailscale entirely (the transport IS the trust boundary — not replaceable); account-based pairing (violates no-cloud posture); long-lived session tickets (violates 004 short-lived session rule).
- Ruled out: QR payloads carrying device credentials (ephemeral nonce + key exchange over WSS instead).

# Iteration 4: Safe security and network-exposure model

## Focus
This iteration defined the safe exposure boundary for a mobile client that can drive a coding agent with workspace tool authority. “Custom authenticated WSS bridge” is interpreted as an independently operated relay transport that may still be private; public reachability is an exceptional deployment mode, not the default. The baseline is a tailnet-only Tailscale Serve publication in front of a separately authenticated and authorized relay. Detailed PWA notification behavior remains deferred.

## Findings
1. **Critical — default to tailnet-only Serve, and treat public exposure as an explicit security exception.** Tailscale documents Serve as sharing a local service only within a tailnet, while Funnel is the separate command for public Internet exposure; Serve also applies tailnet access-control rules and requires tailnet HTTPS certificates. The safe default is therefore `PWA -> tailnet HTTPS/Serve -> loopback-bound relay -> Pi RPC`, with a narrow grant to the relay host/port and no Funnel configuration. A custom WSS listener should normally bind only to a tailnet/private interface or sit behind Serve; exposing it publicly requires a separate threat review, DDoS controls, and an operator-visible break-glass flag. [SOURCE: https://tailscale.com/kb/1242/tailscale-serve] [SOURCE: https://tailscale.com/kb/1312/serve] [SOURCE: https://tailscale.com/docs/features/access-control/grants] [INFERENCE: reducing network reachability is the strongest first boundary for a process that can execute workspace tools]
2. **Critical — separate network admission, user identity, device identity, and application authorization.** Tailscale grants are deny-by-default and can select users/devices and restrict destination protocols/ports, but their own documentation distinguishes network connectivity from application capabilities and makes the application responsible for interpreting application permissions. WebSocket itself prescribes no client-authentication mechanism. Use the tailnet grant and optional posture as network/device admission, then require a relay-issued, short-lived application session for a user principal; bind each socket to `(principalId, deviceId, authSessionId)`, periodically revalidate it, and revoke all sockets on logout/device loss. Do not infer workspace authority merely from tailnet reachability, and do not rely on unverified proxy identity headers; a production integration must either verify a Tailscale identity/capability API for the pinned version or use explicit relay login such as OIDC/passkey. [SOURCE: https://tailscale.com/docs/features/access-control/grants] [SOURCE: https://www.rfc-editor.org/rfc/rfc6455#section-10.5] [SOURCE: https://raw.githubusercontent.com/OWASP/CheatSheetSeries/master/cheatsheets/WebSocket_Security_Cheat_Sheet.md] [INFERENCE: network source admission and application principal authorization fail independently and must remain separate controls]
3. **Critical — a tailnet does not remove browser WebSocket CSRF/Origin obligations.** Browser handshakes carry `Origin` specifically to protect against unauthorized cross-origin use, and cookie-authenticated WebSockets are vulnerable to cross-site WebSocket hijacking. For the PWA route, require `wss://`, strong TLS, an exact allowlist of scheme/host/port, a `Secure; HttpOnly; SameSite=Lax` or `Strict` session cookie, and a single-use CSRF/connection ticket that must validate before subscriptions or mutations are accepted. Reject missing, `null`, suffix-matched, or unexpected origins with 403 on the browser endpoint; treat `Origin` only as a browser signal because non-browser clients can supply it and must authenticate independently. Close long-lived sockets on expiry/revocation and rotate credentials rather than letting connection age bypass session policy. [SOURCE: https://www.rfc-editor.org/rfc/rfc6455#section-4.1] [SOURCE: https://www.rfc-editor.org/rfc/rfc6455#section-10.2] [SOURCE: https://www.rfc-editor.org/rfc/rfc6455#section-10.6] [SOURCE: https://raw.githubusercontent.com/OWASP/CheatSheetSeries/master/cheatsheets/WebSocket_Security_Cheat_Sheet.md]
4. **Critical — authorize every message against a server-owned workspace/session/action tuple and enforce the same boundary at the OS layer.** Connection authentication is not blanket authority. Resolve opaque relay IDs server-side, then check `(principalId, deviceId, workspaceId, relaySessionId, action, currentEpoch)` for every list/read/prompt/abort/approval operation; reject browser-supplied filesystem paths and cross-workspace catalog queries. Run each workspace under a dedicated low-privilege OS identity or sandbox with an allowlisted root, minimal environment, and one binding per active session; network and relay checks cannot contain a compromised agent that already has host-wide credentials. Pi explicitly warns that project trust is only an input-loading guard and does not make untrusted prompts, code, or model output safe. 5. **High — prevent secret access first, then redact before every remote or retained representation.** Pi tool events expose tool arguments, accumulated partial results, and terminal results, so TLS protects transit but not relay replay storage, audit logs, push payloads, or a compromised mobile session. Deny credential paths and unnecessary environment variables at the tool/workspace policy; apply a Pi-side `tool_result` filter before RPC emission where feasible; independently redact the relay envelope before persistence/fan-out; and make push notifications metadata-only. Audit structured identity, workspace, action class, policy/approval decision, hashes, byte counts, and outcomes—not raw prompts, tool output, tokens, cookies, or filesystem paths. A concrete MVP retention ceiling is 7 days for diagnostic transport metadata, 30 days for security/authz events, and 90 days for approval/mutation decision metadata, with raw content retained for zero days and deletion jobs tested; organization/legal policy may shorten or override those ceilings. Redaction is defense in depth, not permission to read every secret. 6. **High — bound every queue and rate by principal as well as connection, and reserve capacity for safety controls.** Enforce handshake, concurrent-connection, frames/second, bytes/minute, message-size, mutation-rate, active-run, queued-prompt, replay-byte, and audit-buffer ceilings. OWASP recommends per-user limits, bounded message sizes (64 KiB or less as a starting point), rate limiting, idle/heartbeat cleanup, and explicit backpressure; the browser WebSocket API itself provides no backpressure. Serialize mutations per session, reject capacity before writing to Pi, record a terminal `rejected_capacity` ledger result, and never silently defer a prompt. Keep a small independent control lane for `abort`, approval denial, revocation, ping/pong, and settlement so output floods cannot prevent shutdown. Coalesce replaceable progress snapshots, but never drop terminal, authorization, mutation, or approval decisions. [SOURCE: https://raw.githubusercontent.com/OWASP/CheatSheetSeries/master/cheatsheets/WebSocket_Security_Cheat_Sheet.md] [SOURCE: https://developer.mozilla.org/en-US/docs/Web/API/WebSocket] [SOURCE: specs/cli-external-orchestration/041=pi-remote-mobile-agent-like-cc/research/lineages/cli-pi-gpt-56-sol/iterations/iteration-003.md] [INFERENCE: separate data and safety-control queues prevent overload from becoming an authority or liveness bypass]
7. **Critical — the approval extension is privileged policy code, not a trustworthy consequence of showing a mobile dialog.** Pi extensions run with full system permissions and arbitrary-code capability. The version-matched `tool_call` hook runs before tool execution and can block, but its input is mutable and is not revalidated after extension mutation; project trust is not a sandbox. Install the gate only from an admin-owned, read-only global/CLI location, pin and attest its source hash at child startup, prohibit project overrides, and fail closed for side-effecting tools if the extension, relay approval channel, or policy version is absent or mismatched. The extension must evaluate canonical tool name/arguments/workspace, request a negative-default dialog, and recheck the signed decision capability immediately before allowing execution; the relay must retain the epoch/payload-digest/first-decision invariant from iteration 3. An OS sandbox remains the final boundary because a malicious or compromised extension can bypass its own gate. 8. **High — failures must reduce authority, never silently widen reachability or continue stale capabilities.** Startup should attest private bind/Serve status, narrow grants, relay auth configuration, workspace root/UID, extension hash, queue ceilings, redactor version, and audit sink before enabling mutations. At runtime: bad Origin/TLS/auth gets no allocation; identity or authz-store loss closes or degrades sockets to no-mutation mode; device revocation closes all bound sockets; queue saturation rejects new work while preserving the control lane; redaction uncertainty withholds payload; extension mismatch disables side-effect tools; audit-buffer exhaustion denies destructive mutations; child/workspace/epoch mismatch quarantines events and reconciles; and recovered `dispatching` prompts remain explicitly `indeterminate` rather than being resent. ### Exposure decision matrix

| Dimension | Tailnet-only Tailscale Serve baseline | Custom authenticated WSS bridge |
|---|---|---|
| Reachability | Tailnet only; narrow source users/devices and destination port with grants; do not configure Funnel. | Bind to tailnet/private interface by default. Public bind is a separately approved exception with DDoS/WAF and emergency-disable controls. |
| TLS | Enable the tailnet HTTPS-certificate prerequisite and terminate at Serve; keep the relay backend loopback-only. | Own certificate issuance/renewal, strong TLS configuration, proxy upgrade behavior, and expiry monitoring. |
| Identity | Tailnet user/device selection is network admission; relay principal login and per-action authorization still apply. | Relay owns user login, device registration/revocation, token rotation, and abuse controls end to end. |
| Browser controls | Exact Origin allowlist, SameSite cookie, CSRF/connection ticket, expiry, and message authorization remain required. | The same controls are required; public reachability increases scanning, credential stuffing, and resource-exhaustion exposure. |
| Operational dependency | Tailscale policy, device enrollment, Serve configuration, and certificate availability. | Public DNS/proxy/TLS/IdP/rate-limit/audit stack plus incident response and continuous patching. |
| Decision | **Recommended default** for the coding-agent MVP. | Use privately when custom protocol control is needed; public use only when tailnet enrollment is impossible and the additional control plane is explicitly accepted. |

### Failure-mode contract

| Failure | Detection | Safe transition |
|---|---|---|
| Funnel/public listener or grant broader than policy | Startup/config attestation plus external canary | Refuse mutation service; require break-glass approval and audit event. |
| TLS, Origin, cookie, CSRF ticket, or relay login invalid | Handshake checks before allocating replay/session resources | HTTP 403/unauthorized; no socket subscription and no Pi command. |
| Principal/device revoked or session expires | Revocation subscription plus periodic session validation | Close every bound socket and invalidate outstanding approval leases. |
| Authorization store unavailable | Health check and per-message lookup failure | Deny mutations; optionally expose a redacted cached read-only view. |
| Queue/replay/audit buffer full | Per-principal and global watermarks | Reject new mutations, preserve abort/deny control lane, never unbounded-buffer. |
| Redactor errors or classification is uncertain | Versioned redactor result and fail-open detector | Withhold content; send metadata-only event. |
| Approval extension missing, changed, or unresponsive | Pinned hash/manifest and startup heartbeat | Disable side-effect tools; reject/expire pending approvals. |
| Relay crash after Pi stdin write | Recovered mutation state is `dispatching` | Mark `indeterminate`; never automatic resend. |
| Child binds wrong workspace/session/epoch | Catalog/path/UID/epoch attestation | Quarantine child output, kill binding, and reconcile before accepting work. |

[INFERENCE: each transition applies least authority while preserving the durable protocol limitations established in iteration 3]

## Ruled Out
- **Public Funnel or Internet-bound WSS as the default:** Serve is explicitly tailnet-oriented and Funnel is the separate public feature; coding-agent authority does not justify broader reachability for convenience. [SOURCE: https://tailscale.com/kb/1242/tailscale-serve] [SOURCE: https://tailscale.com/kb/1312/serve]
- **Tailnet membership as workspace/session authorization:** grants distinguish network and application permissions, and WebSockets still require per-message authorization. [SOURCE: https://tailscale.com/docs/features/access-control/grants] [SOURCE: https://raw.githubusercontent.com/OWASP/CheatSheetSeries/master/cheatsheets/WebSocket_Security_Cheat_Sheet.md]
- **Origin as authentication, or cookies without Origin/CSRF checks:** RFC 6455 permits non-browser clients to set Origin and OWASP documents cross-site WebSocket hijacking with automatically sent cookies. [SOURCE: https://www.rfc-editor.org/rfc/rfc6455#section-10.2] [SOURCE: https://raw.githubusercontent.com/OWASP/CheatSheetSeries/master/cheatsheets/WebSocket_Security_Cheat_Sheet.md]
- **A mobile confirmation card as the security gate:** only a pre-execution, fail-closed Pi policy hook can block the tool; extensions themselves are privileged code. [SOURCE: /Users/michelkerkmeester/.local/lib/node_modules/@earendil-works/pi-coding-agent/docs/extensions.md:111-113] [SOURCE: /Users/michelkerkmeester/.local/lib/node_modules/@earendil-works/pi-coding-agent/docs/extensions.md:753-765]
- **Raw transcript/tool-output audit logs or unbounded replay/queues:** they turn secrets and resource exhaustion into durable relay compromise paths. [SOURCE: https://raw.githubusercontent.com/OWASP/CheatSheetSeries/master/cheatsheets/WebSocket_Security_Cheat_Sheet.md] [SOURCE: https://developer.mozilla.org/en-US/docs/Web/API/WebSocket]

## Dead Ends
No productive category is exhausted. Inferring Tailscale user identity from undocumented proxy headers is eliminated for this design until a pinned-version official source or runtime test proves the propagation and anti-spoofing boundary. Public exposure as an MVP default is definitively eliminated; future work should not vary public-listener authentication schemes unless a concrete non-tailnet requirement is accepted.

## Edge Cases
- Ambiguous input: “custom authenticated WSS bridge” could mean either private custom transport or public Internet exposure. This iteration selected private-by-default and treated public exposure as an explicit exception.
- Contradictory evidence: remote convenience favors Internet reachability, while workspace tool authority demands minimum reachability. The conflict is resolved in favor of tailnet-only Serve; no public default is recommended.
- Missing dependencies: no official source proving Serve identity-header propagation was verified, and a stale device-posture documentation URL returned 404. The design therefore requires independent relay authentication and relies only on the grants page’s verified user/device selectors. A live WebSocket-upgrade test against the installed Tailscale version also remains outstanding.
- Partial success: official Serve, grants, RFC, OWASP, and version-matched Pi sources yielded sufficient evidence. Two broad extraction commands ended partially (one stale Tailscale URL and one `head`/pipe close), but their failed portions support no finding; status remains `complete`.

## Reflection
- What worked and why: Official Serve/grants material established the reachability boundary without inventing identity propagation, RFC/OWASP evidence supplied the browser handshake and resource controls, and version-matched Pi security/extension docs exposed the true approval-extension trust boundary.
- What did not work and why: A device-posture URL had moved, Tailscale identity-header behavior was not established from an official pinned-version source, and the broad local grep hit a pipe limit. Narrow primary-source anchors were sufficient, so unsupported claims were excluded rather than inferred.
- What I would do differently: In an isolated fixture, pin the Tailscale version and test WebSocket upgrades, Origin rejection, grant revocation, identity lookup/capability semantics, connection expiry, queue saturation, redactor failure, extension-hash mismatch, and audit-sink loss as executable fail-closed checks.

Define the PWA/mobile delivery phase: platform-specific push-notification and background constraints, generic/redacted notification payloads, service-worker reconnect behavior, install/auth onboarding for tailnet and relay identity, and a phased Claude-style UX that never places approval authority in a stale notification.

# Iteration 2: Pi RPC to Claude-style mobile UI state machine

## Focus
This iteration mapped Pi RPC commands and events to a behavioral Claude-style mobile UI. “Claude-style” is interpreted narrowly as session selection, prompt acknowledgement, streaming bubbles, tool cards, queued work, explicit approvals, and settled/idle presentation—not visual parity. The goal was to turn the high-level relay architecture from iteration 1 into ordering, idempotency, and reducer invariants.

## Findings
1. **High — model the UI as orthogonal state axes, not one linear request state.** A command response is correlated by request `id`, but most events are not; `prompt` success means accepted or queued rather than completed, and `agent_settled` is the only documented session-level terminal event. The mobile model therefore needs separate connection/reconciliation, mutation acknowledgement, run, message/tool, and approval substates. An event such as `agent_start` or `message_start` must be allowed to advance run/render state even if the correlated prompt acknowledgement has not yet reached the browser, and a later acknowledgement must not regress it. 2. **High — order live reductions by a relay stream epoch and sequence before interpreting Pi payloads.** Pi writes subscription events directly to RPC stdout, and RFC 6455 preserves fragment order on one WebSocket connection; neither supplies replay identity across socket replacement. Each relay envelope should therefore carry `(sessionId, streamEpoch, eventSeq)`: drop `eventSeq <= lastApplied`, pause and reconcile on a gap, and reset transient reducers only when the stream epoch changes. Sequence is for duplicate/gap detection, not for reordering a healthy connection. 3. **Critical — RPC request IDs correlate responses but do not make prompt mutations idempotent.** Persist a relay ledger keyed by `(principalId, sessionId, clientMutationId)` before writing to Pi. A retry with the same payload returns the stored acknowledgement/status without a second stdin write; reuse with a different payload is rejected. Serialize prompt/steer/follow-up mutations per session, keep acknowledgement state separate from eventual `agent_settled`, and retain the ledger across mobile reconnects and relay restarts. 4. **High — streamed assistant bubbles require append-then-authoritative-replace semantics.** On `message_start`, allocate a relay-scoped draft; route each `message_update.assistantMessageEvent` by `contentIndex`; append only `*_delta` content after envelope deduplication; accept the completed tool call from `toolcall_end`; then replace the entire draft with `message_end.message`. Never replay a delta into an already terminal message. If a sequence gap occurs, stop applying deltas rather than guessing and enter reconciliation. 5. **High — tool invocation content and tool execution cards are related but distinct reducers.** `toolcall_*` message updates describe the assistant constructing a call; `tool_execution_start` creates the activity card keyed by `(streamEpoch, toolCallId)`. Each `tool_execution_update.partialResult` is accumulated output and must replace, not append to, the card body. `tool_execution_end.result` and `isError` are authoritative terminal values; duplicate or post-terminal updates are ignored. Only link the assistant call block and execution card when their tool-call identifiers match. 6. **High — source the session list server-side from Pi’s version-matched SDK, and never expose switch paths as client authority.** RPC can open a known path with `switch_session` but documents no list command. The exported `SessionManager.list(cwd, sessionDir)` and `listAll(...)` APIs return `SessionInfo` with `id`, name, parent, timestamps, message count, and preview text. For a single-workspace mobile client, the relay should call allowlisted `list`, publish an opaque relay session ID plus redacted display metadata, retain the filesystem path server-side, and resolve `switch_session` only from that catalog. Unrestricted `listAll` or accepting a browser-supplied path expands data exposure across workspaces. 7. **Critical — approvals must be explicit dialog capabilities with a first-response-wins relay invariant, never inferred from tool activity.** Only dialog methods (`select`, `confirm`, `input`, `editor`) expect `extension_ui_response`; fire-and-forget methods use the same `extension_ui_request` event type but expect none. Pi creates a unique pending ID, deletes it on response, abort, or timeout, and silently ignores unknown/late duplicates. A purpose-built risk-policy extension must issue a negative-default `confirm` before invoking the protected tool. The relay must bind the request ID and request-payload digest to the authorized principal, session, and stream epoch; atomically accept one response; audit the decision; expire the mobile card; and reject stale or cross-session responses before forwarding. A `tool_execution_start` that precedes an approval is evidence that the tool was not gated by that approval. ## Reflection
- What worked and why: Combining the version-matched RPC contract with the actual pending-dialog and session-list declarations converted absence claims into implementable server and reducer invariants. Separating mutation acknowledgement from run state also removes dependence on an undocumented response/event arrival order.
- What did not work and why: The bounded RFC command’s second literal search did not match the document wording, although retrieval and the primary in-order clause succeeded. A live disconnect/duplicate/timeout transcript was not run in this documentation-focused pass.
- What I would do differently: Build a deterministic transcript harness that injects duplicate relay envelopes, sequence gaps, prompt retries, child restarts, simultaneous approval responders, timeout races, and `agent_end` followed by retry before accepting the state model as implementation-ready.

## Recommended Next Focus
Specify and fault-test the reconnection protocol and durable relay schema: stream-epoch creation, replay retention, `get_entries(since)` cursor mismatch handling, mutation-ledger lifecycle, session-switch reconciliation, and multi-client approval leases. Use a real Pi RPC transcript to verify every transition and explicitly record any event ordering that the written contract leaves unspecified.

# Iteration 4: Security and network exposure model

## Focus
Determine the safe exposure model for a coding agent with workspace tool authority: Tailscale Serve vs Funnel vs raw WebSocket bridge, relay authentication/authorization (identity, per-action authorization, origin/session controls), secrets handling, workspace containment, and audit. Ground in official Tailscale docs and OWASP WebSocket guidance.

## Findings
1. **High — Serve is the correct default exposure: tailnet-only, identity-aware, auto-TLS; Funnel is the public-internet escape hatch and should be avoided for an agent relay.** `tailscale serve` exposes a local HTTPS/HTTP service to the tailnet only, with an automatically provisioned TLS certificate terminated by the Tailscale daemon, MagicDNS hostnames (`https://my-node.example.ts.net/`), reverse-proxy targets restricted to `http://127.0.0.1` for plain HTTP, and PROXY protocol support for source-IP preservation. Access is governed by tailnet ACLs/grants — authenticated tailnet identities; deny-by-default once a policy exists. Funnel, by contrast, makes the listener reachable by anyone on the public internet with no per-visitor Tailscale identity, requires the `funnel` nodeAttr permission, and per Tailscale's own guidance must be treated as an internet-facing application with application-layer auth, rate limits, and no admin/debug exposure. For a coding agent relay, Serve keeps the attack surface to authenticated tailnet devices and lets tailnet policy (ACLs/grants) be the reachability boundary. [SOURCE: https://tailscale.com/kb/1242/tailscale-serve] [SOURCE: https://tailscale.com/kb/1223/funnel] [SOURCE: https://tailscale.com/docs/features/access-control/acls] [SOURCE: https://tailscale.com/blog/introducing-tailscale-funnel]
2. **High — Serve's identity layer is reachability, not authorization: the relay still needs its own authN/authZ.** Tailnet identity authenticates *who can reach* the served HTTPS endpoint; it does not authorize individual actions inside the app. Following OWASP: use `wss://` only; authenticate in/right after the opening handshake (WebSocket has no built-in auth); validate the `Origin` header on every browser handshake against an exact allowlist (primary CSWSH defense, never regex/substring/`*`); authorize every message and subscription server-side against the authenticated principal with default-deny (connection auth ≠ blanket permission); use short-lived scoped credentials, rotate/refresh for long-lived sockets, and redact tokens from logs; revalidate sessions and close sockets on expiry/revocation; treat every message as untrusted (schema validation, size limits); rate-limit and quota per user; log security events without tokens/payloads. [SOURCE: https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html] [SOURCE: https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/11-Client-side_Testing/10-Testing_WebSockets] [SOURCE: https://www.rfc-editor.org/info/rfc6455/]
3. **High — the relay needs a separate, minimal identity: per-action authorization mirrors Pi's own surfaces.** The coding agent's tools (bash, file edits) are higher-risk than a chat relay, so the relay should issue short-lived per-client credentials (e.g., OAuth/device-grant against the tailnet identity, or an API-token with rotation) and enforce a per-action authorization matrix: which actions may a principal send (prompt/steer/follow_up/abort), which sessions may it open, which privileged actions require re-approval (direct `bash`, `switch_session` to other projects, `fork`/`clone` across workspaces), and which are read-only (`get_*`). This mirrors the extension-UI approval channel from iterations 1-2: relay-level policy gates privileged RPC actions before they reach the Pi child, and every gated action is audited with principal, action, session, timestamp, outcome. Approval responses must be bound to the dialog's payload (digest) to prevent post-gate mutation — same rule as the mutation ledger (iteration 3). [INFERENCE: applies OWASP per-action authorization to the RPC surface mapped in iteration 2] [SOURCE: https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html] [SOURCE: rpc.md:1144-1335]
4. **High — workspace containment is a deployment decision: run the Pi child (and the relay) in an OS-level sandbox/container with least-privilege, and treat session files as sensitive.** Pi's `--session-dir` and `--no-session` control where session JSONL lands; the session files contain full conversation content (prompts, tool outputs, possibly secrets pasted by users). Containment: dedicated non-root user/container, no host home access, bounded disk, separate session-dir per principal or shared read-only templates, and `--no-session` for ephemeral one-off runs. Relay persistence (envelopes, mutations, approvals) must be restricted to the relay's own directory and encrypted at rest if it may contain payload echoes; metadata-only retention is the safer default (store digests, not full payloads, for dedup). [SOURCE: rpc.md:7-18] [SOURCE: rpc.md:1360-1471] [INFERENCE: session files contain conversation content; containment follows least-privilege practice]
5. **Medium — the WebSocket-bridge alternative (non-Tailscale) is viable only with the full OWASP layer: TLS termination, auth, origin checks, rate limits, and WAF-grade hardening.** For users without a tailnet, a WebSocket bridge on a VPS/cloud (e.g., wss://host/relay) can reach the Pi host over an outbound-only tunnel (SSH/Tailscale to the VPS), but then the public endpoint carries the whole burden: TLS at a real edge, exact-origin validation, short-lived session tokens, per-user quotas, payload limits, and DDoS/rate protection — plus the same relay-side authZ as finding 3. The recommendation stands: prefer Serve for the personal/team case; a public bridge is strictly more attack surface and must not expose admin/debug endpoints. [INFERENCE: applies OWASP checklist to the non-Tailscale transport] [SOURCE: https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html] [SOURCE: https://tailscale.com/blog/introducing-tailscale-funnel]
6. **Medium — audit and incident response are part of the design, not afterthoughts.** Log security-relevant socket events (open/close, identity, origin, auth/authz failures, rate-limit triggers) excluding tokens and full payloads; record per-action authorization decisions with outcomes; keep the mutation ledger append-only with digest verification; define rotation (credentials, Tailscale keys) and revocation (session invalidation, tailnet ACL changes) procedures; and test explicitly for unauthorized origins, expired/revoked credentials, cross-principal IDOR on sessions, replay, oversized messages, and flooding — the OWASP WebSocket test list maps 1:1 to this relay. [SOURCE: https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html] [SOURCE: https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/11-Client-side_Testing/10-Testing_WebSockets]
7. **High — the approval extension itself is a trust control: admin-owned, hash/version-pinned, and fail-closed for side-effect tools, because the extension bypasses its own UI.** Pi's own docs are explicit: "Extensions run with your full system permissions and can execute arbitrary code. Only install from sources you trust" — a compromised or malicious extension could approve or execute side-effect tools without any dialog. The approval extension must therefore be (a) owned by the relay operator (not user-editable), (b) pinned by content hash/version with signature or checksum verification at load, (c) fail-closed: any tool classed as side-effect (bash, file mutation, network) is blocked unless the relay's per-action authorization grants it, and (d) loadable per-workspace only from a controlled path. This closes the loop from finding 3: relay policy gates what the extension may even ask about, and the extension gates what Pi executes. ## Ruled Out
- **Tailscale Funnel as the exposure path:** public-internet listeners without per-visitor identity; needs funnel nodeAttr; violates least privilege for an agent relay. [SOURCE: https://tailscale.com/kb/1223/funnel] [SOURCE: https://tailscale.com/blog/introducing-tailscale-funnel]
- **Tailnet identity as sole authorization:** it authenticates reachability only; per-action authZ is still required (OWASP). [SOURCE: https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html]
- **Direct public WebSocket bridge as the default:** strictly more attack surface than Serve; acceptable only with the full OWASP layer for non-tailnet users. [INFERENCE: OWASP checklist applied to transport]
- **Storing full mutation payloads indefinitely:** metadata-only retention with digests for dedup is the safer default. [INFERENCE: least-privilege data handling]

## Dead Ends
- No live threat-model validation against a deployed Serve instance or a real attacker model; the analysis is source-grounded but not penetration-tested.
- Funnel docs confirm the default `autogroup:member` nodeAttr must be narrowed; no finding depends on Funnel being used.

## Edge Cases
- Contradictory evidence: none; Tailscale's own guidance (Funnel = public app) agrees with OWASP's application-layer requirements.
- Missing dependencies: no test of Serve's PROXY protocol against the relay's source-IP handling; flagged for the validation phase.
- Ambiguous input: "safe" interpreted as defense-in-depth: reachability (tailnet) + authentication + per-action authorization + containment + audit.

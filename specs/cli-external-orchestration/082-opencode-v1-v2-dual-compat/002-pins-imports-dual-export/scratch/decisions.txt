1. Import sites: all three `@opencode-ai/plugin/tool` imports are replaced in this phase, in system-speckit-completion.js, system-skill-advisor.js and opencode-goal.js, plus the test stub. Only the import line changes in the two files phase 3 ports.
2. "Guards" in the brief's scope-out means the dispatch rule code that phase 5 owns. The three -guard plugins stay in this phase.
3. Dev dependency placement: v1 1.19.3 installs devDependencies from .opencode/package.json at startup (scratch/devdep-probe.txt, scratch/devdep-config.out), so a v2 package listed there is downloaded on every v1 host. `@opencode/plugin` 2.0.32 goes in `.skilled/package.json` devDependencies only, where type checks and tests resolve it. `.opencode/package.json` lists only what v1 needs at runtime.
4. Phase 1 Q7 verdict: confirmed. A `z.toJSONSchema(z.object(shape), {io: 'input'})` output registers as a v2 tool input, so one zod shape serves both hosts (001-unknowns-and-baseline/findings.md Q7).
5. Phase 1 Q4 verdict: confirmed. v2 accepts extra default-export keys, so a `__test` seam is removed only where no test reads it.
6. Phase 1 v1 oracle: use 001-unknowns-and-baseline/scratch/v1-harness.mjs plus `opencode debug config` discovery for T025, because v1 1.19.3 logs no plugin lines.
7. v2 event legs use `for await` over `ctx.event.subscribe()`, which returns an async iterable (001 findings Q5).
8. Deviation from plan.md (per-plugin setup bodies): one shared bridge, `.opencode/plugins/lib/v2-bridge.js`, builds the v2 `setup` from the unchanged v1 `server` hooks. Why: the 11 plugins use the same five hook keys (event, tool.execute.before, tool.execute.after, experimental.chat.system.transform, tool), so 11 hand-written setup legs would repeat one mapping 11 times and drift. None of the 11 reads `client` or `$` (grep in this phase's scratch notes), so a v1 input built from `ctx.location` is enough. The default export stays the plain object `{ id, setup, server }` (decision D1).
9. Tool results on v2 (from the bridge review, P1): v1 `execute` returns a string or `{ title?, output, metadata? }`, while v2 `Info.execute` must resolve to a `Result` (`@opencode/schema/dist/tool.d.ts:66-70`). The bridge wraps execute and maps the result to `{ content, metadata }`, and builds a v1 ToolContext from the v2 one. `content` is chosen over `output` because `output` is typed by an output schema the bridged tools never declare, and research iteration-003.md:116 records `{ content }` as the v2 return. Not yet proven live: no capture runs a bridged tool's execute on v2. A live call is owed before phase 3 closes.
10. Scope addition: classifier-injection-screen failed on v2 before and after the port with "Plugin failed to load". The debug serve log (oracle.py with ORACLE_V2_SERVE_ARGS="--print-logs --log-level debug") gives the cause: `ENOENT: lstat '/$bunfs/root/opencode'`. OpenCode 2 is Bun-compiled, so `process.argv[1]` is a virtual path, and score-injection-screen.mjs:1769 realpaths it at import time inside the plugin's import chain. The fix is in that producer file, the one file this phase adds. Seven other files carry the same `realpathSync(process.argv[1])` check, but none is in a plugin import chain per the load log, so they stay out of scope. Phase 3 reruns the debug oracle on the hard plugins' chains.
11. The oracle lives at ../scratch/oracle.py (parent packet) for reuse by phases 3, 8 and 11. It filters v2 entries on the reported source path, not its realpath, because sk-vision.js is a symlink into .skilled.
12. Orchestrator error, corrected: the three port briefs told the implementer to keep each `__test` seam on the server function. That contradicted the frozen spec (spec.md lines 116 to 118, REQ-008, AC-008, tasks T010 to T013), which moves the classifier and post-edit-quality seams into two lib core modules and removes the two unread seams. The whole-phase review caught it (P1), and a follow-up dispatch implements the spec as written.
13. v2 session events (review P1): v1 plugins read the session id from `properties.info.id`, and v2 `session.*` data carries `sessionID` without `info`. The bridge adds `properties.info = { id: sessionID }` for `session.*` events only, because message events use `info` for the message. Live delivery of v2 session events is still unproven (001 findings), so the mapping is type-checked and unit-tested, not observed live.

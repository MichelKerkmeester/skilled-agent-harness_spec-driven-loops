## P1

**1. P1 — the v2 command cannot analyze an image attached to the `/vision` submission itself.**
- **File:line:** `.skilled/skills/sk-vision/vision-runtime/src/plugin.ts:190-206` (the shim feeds `handleVisionCommand` only from `ctx.session.context`); fix site `:218-224`.
- **Defect:** `createV2CommandInput` synthesizes the v1 message list exclusively from `ctx.session.context` (stored, already-sent messages). The invocation's own attachment lives in `CommandInvocation.prompt.files` and is re-sent to the model (`:235`) but never analyzed, so the v2 leg loses the exact flow v1 supports (in v1 the pasted draft part is already in `session.messages` — the plugin's own preload hook at `:159-173` exists because `message.part.updated` fires at paste time, before submission).
- **Failing input:** on v2, attach an image in the composer and submit `/vision what is this` in one message → `latestImage()` finds no image → the model receives `sk-vision: no recent image found. Attach an image, then run /vision <question>.` — the instruction the user just followed; for a text-only model the turn carries no evidence. Workaround: run `/vision` a second time (the first run's re-send stores the image).
- **Class:** instance-only (same site the earlier base64 fix touched).
- **Confidence note (INFERRED premise):** that the host does not admit the invocation prompt before `execute` — supported by `session.command`'s protocol contract ("Execute a slash command callback immediately", `SessionNotFound/CommandNotFound/CommandExecution` errors, `NoContent`) versus `session.prompt`'s ("Durably admit one session input…"), and by the project's own v2-types.txt §2.7 ("the command turn is sent" by the plugin). Confirmation: one live v2 run (attach + `/vision` in one submission), or the v2 command dispatch source.

**2. P1 — the plugin registers `vision` while the repo's own `.skilled/commands/vision.md` already registers `vision` in the same v2 location; the duplicate-name resolution is unverified and both branches diverge from v1.**
- **File:line:** `plugin.ts:215-217` (`name: 'vision'`).
- **Defect:** `.opencode/commands -> ../.skilled/commands` is exposed to both hosts (phase-004 evidence: the isolated v2 `GET /api/command` listing includes `vision`; the worktree v2 listing too), and `ctx.command.transform(editor.add)` adds a second definition with the same name. If the plugin wins, the model no longer receives the `vision.md` template that v1 delivers alongside the evidence (the template is load-bearing: "you must not claim to see anything the block does not contain"); if the markdown command wins, the plugin's `execute` never runs and no `<SK-VISION COMMAND>` block is injected while the template still asserts one was. The project's own research flagged exactly this ("a user-defined command of the same name would collide instead of being observed", `research/iterations/iteration-018.md:125-127`); no capture or decision resolves it.
- **Failing input:** on v2 in this worktree, run `/vision <q>` with both definitions registered (the phase-3 read shows the plugin `active` for the worktree root, where the markdown `vision` is listed).
- **Class:** cross-consumer (two registrations compete for one command name).
- **Confirmation:** `opencode2 api GET "/api/command?location[directory]=<worktree>"` after plugin load (one `vision` entry or two), or one live `/vision` run; both are model-free for the listing.

## P2

**3. P2 — `as Part` fabricates a v1 `FilePart` that is missing its required identity fields.**
- **File:line:** `plugin.ts:197-202`.
- **Defect:** the synthesized part is `{ type, mime, filename, url }` cast to `Part`; the real v1 `FilePart` (1.17.15 `types.gen.d.ts:201-210`) requires `id`, `sessionID`, `messageID`. Today's consumers (`isImagePart`, `materializeImagePart`, `latestImage`) read only `type`/`mime`/`url`, so it is inert — the cast hides that from the compiler.
- **Failing input:** any consumer that reads `part.id` / `part.sessionID` / `part.messageID` (e.g. a future change in `materializeImagePart`'s temp-file policy or the v1 message pipeline) receives `undefined`.
- **Class:** class-of-bug (unchecked structural cast of a shared type).

**4. P2 — the test pins the helper, not the mapping it protects.**
- **File:line:** `plugin.test.ts:8-19` (mapping at `plugin.ts:190-206`).
- **Defect:** the two cases cover `toV1FileUrl`'s wrap/passthrough branches only. Nothing asserts that the constructed part is recognized as an image (`mime` propagation into `isImagePart`) or that the produced `data:` URL reaches `materializeImagePart`'s decode branch — the integration the earlier fix was for.
- **Failing input:** a mapping regression that drops `mime` (or emits a URL without the `data:` prefix) keeps both tests green while `/vision` returns "no recent image found" or a decode error.
- **Class:** matrix/evidence.

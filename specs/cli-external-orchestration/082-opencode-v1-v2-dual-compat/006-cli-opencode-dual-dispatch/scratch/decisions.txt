2. Q3, working directory. v2 2.0.32 `run` takes no positional directory: every positional is message text (probes/v2-run-help.txt, "message... string"). A `run --standalone` started in a scratch project ran its plugin with process.cwd() and PWD equal to the spawn directory (probes/probe-log.jsonl line 1), and the model's shell tool printed the same directory from `pwd` (probes/run-slash.jsonl). 10. Binary order across PATH (amendment, found during T004). Existing deep-loop tests put stub executables named `opencode` at the front of PATH and keep the real PATH after them (tests/unit/fanout-run.vitest.ts, tests/unit/combo-matrix.vitest.ts, tests/unit/lineage-timestamp-window.vitest.ts, tests/stress/cli-adapter). This machine has a real `opencode2` in ~/.local/bin. Read literally, "the first binary in the order $OPENCODE_BIN, opencode2, opencode" searches all of PATH for opencode2 before any opencode, so those tests would bypass their stub and spawn the real v2 binary, with a real model call. Amended rule: `$OPENCODE_BIN` first; otherwise walk PATH in order and, inside each directory, take `opencode2` before `opencode`. Side-by-side installs in one directory (the documented ~/.local/bin layout) still resolve to opencode2, and PATH order keeps its usual meaning when the two sit in different directories. A missed stub now fails visibly at its own `--version` instead of reaching a real binary.

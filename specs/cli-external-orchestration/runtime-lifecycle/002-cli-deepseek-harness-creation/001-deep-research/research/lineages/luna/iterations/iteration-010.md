3. **Headless is suitable for a one-shot process, while telemetry and request cost require explicit policy.** The DSH headless process serves one task, opens no listening port, and exits when the run ends; no comparable startup-latency measurement against Pi or cost-per-run evidence exists. The shipped base enables OTLP telemetry in `FEEDBACK_ONLY` mode and documents `DSH_TELEMETRY_MODE=DISABLED`; the base also mounts DeepSeek session-log upload, which adds a session suffix to official DeepSeek API requests. For this third-party provider mode, make telemetry disabled by default and ensure the official-API session-log extension is not accidentally enabled; actual token price, cache behavior, and endpoint billing stay UNKNOWN until a provider-authorized probe. 4. **Put these rules in the future `cli-dsh` skill packet.** Use only the headless profile; send prompts over stdin with `-`, close the pipe after the task, and supervise with the shared timeout. Require JSON final status plus exit code 0. Use a lineage-owned cwd and DSH home, an explicit repo-local patch, `workspace-write` with `approval-policy never`, and the shared write-containment scan; do not add writable roots casually. Gate the mode on availability of any required subprocess/sandbox backend. Keep `DSH_TELEMETRY_MODE=DISABLED`, secrets out of prompts/logs, the two route/model entries allowlisted separately, MCP absent unless the explicit patch mounts it, and plugin-market Pi package claims unsupported. Avoid first-use help/dump-config/profile operations under the operator's normal home because profile bootstrap can create files.

# VIB-HK-025 procedure: run a mirrored prompt by name

Verdict: **OPERATOR-ONLY**. The runner cannot put a mirrored prompt into a new
session's system input: its first launch happens before any check can install
the prompt, and neither a restart nor `/new` creates a new Core, so the prompt
the session was created with is the one it keeps.

---

## 1. EXACT RUNNER LIMITATION

Three independent limits, all observed.

**First launch.** The runner's Vibe home is created inside the adapter's launch
callback, after all setup commands, and it copies only the repository config and
the rendered hooks (`run-conversation-scenario.cjs`, `prepareVibeHome()`, lines
1265-1279). No script action, setup command or turn check runs between that copy
and the `vibe` process starting, so `$VIBE_HOME/prompts/` cannot exist when the
config is validated. Vibe resolves a custom prompt id only through
`system_prompt_id`, `compaction_prompt_id` or `title_prompt_id`
(`vibe/core/config/vibe_schema.py` lines 1490-1510 and the prompt resolver in
`vibe/core/prompts/__init__.py` lines 76-103), and `_check_system_prompt()`
rejects an id with no matching file. Observed with a home that has no prompt
directory:

```text
INVALID: ValidationError Value error, Invalid system_prompt_id value:
'create-goal'. Must be one of the available prompts ("cli", "explore",
"tests", "lean", "minimal"), or correspond to a .md file in <no prompt dirs>
(available: <none>)
```

**Restart.** A turn check can install the prompt and prepend
`system_prompt_id = "create-goal"` to the home config after the first session
has started, and the runner's `restart` action relaunches with
`vibe --resume <session-id>`. The resumed Core keeps the prompt it was created
with; the new `system_prompt_id` is never applied. Observed in a live experiment (restart-run/matrix.md):
`run-prompt` reported `prompt-named`, `restart` reported
`restarted-with-named-prompt`, and the proving turn failed. The journal still
held `"core_system_instructions":"You are Mistral Vibe, a coding agent built by
Mistral AI..."` and the stub text appeared nowhere in the log tree.

**`/new`.** A second experiment (matrix.md and checkpoints.tsv beside this
file) sent the built-in `/new` command after the prompt and id were installed.
`run-prompt` and `new-conversation` passed, and the proving turn failed the
same way: the post-`/new` generation's
`core_system_instructions` was still the built-in CLI prompt, four times over,
and the stub text appeared nowhere. A new conversation does not create a new
Core in this build.

Vibe applies a new system prompt only to a new session process. The runner never
starts one after the home exists, so the row is operator-only. The restart
experiment is in restart-run/matrix.md and its checkpoints.tsv; the `/new`
experiment is in matrix.md and checkpoints.tsv beside this file.

## 2. MANUAL PROCEDURE

Run from the checkout root
`/Users/michelkerkmeester/worktrees/public/383-mistral-vibe-runtime`.

1. Create a disposable home outside the checkout, copy the repository config
   and the rendered hooks, and install the mirrored prompt:

   ```bash
   H=$(mktemp -d)
   mkdir -p "$H/prompts"
   cp .vibe/config.toml "$H/config.toml"
   cp .vibe/prompts/create-goal.md "$H/prompts/create-goal.md"
   node .vibe/plugins/repo-guards/render-home-hooks.cjs "$H"
   ```

2. Prove the id resolves to the mirror before starting Vibe. This is the text a
   new session's system message carries:

   ```bash
   VIBE_HOME="$H" "$(dirname "$(readlink -f "$(command -v vibe)")")/python" -c '
   from vibe.core.config.harness_files import init_harness_files_manager
   init_harness_files_manager("user")
   from vibe.core.config.vibe_schema import VibeConfigSchema
   print(VibeConfigSchema(system_prompt_id="create-goal").system_prompt)'
   ```

   Observed first two lines:

   ```text
   <!-- Generated by sync-prompts-vibe.cjs from .skilled/commands/create/goal.md. -->
   # Mistral Vibe prompt: /create-goal
   ```

3. Start a new interactive session with the mirrored prompt named by
   environment, so the home config stays untouched:

   ```bash
   VIBE_HOME="$H" VIBE_SYSTEM_PROMPT_ID=create-goal \
     vibe --output-dir "$H/output" --auto-approve
   ```

4. Type the scenario request:
   `In one sentence, tell me which instructions you are following right now.`

5. Confirm the first model input. The journal records the system instructions:

   ```bash
   grep -rls 'Mistral Vibe prompt: /create-goal' "$H/logs/session/unified"
   grep -rho '"core_system_instructions":"[^"]\{0,80\}' "$H/logs/session/unified" | head -1
   ```

   A match proves the mirrored prompt text is in the new session's first model
   input. The `/context` view names the same system-prompt category.

6. Exit the session and remove the disposable home:

   ```bash
   rm -rf "$H"
   ```

The same steps work for any other mirrored stub: copy
`.vibe/prompts/<name>.md` into `$H/prompts/` and set
`VIBE_SYSTEM_PROMPT_ID=<name>`. A dispatcher can also compose a stub into the
task text for a print-mode run; that path does not prove name resolution and is
not the scenario.

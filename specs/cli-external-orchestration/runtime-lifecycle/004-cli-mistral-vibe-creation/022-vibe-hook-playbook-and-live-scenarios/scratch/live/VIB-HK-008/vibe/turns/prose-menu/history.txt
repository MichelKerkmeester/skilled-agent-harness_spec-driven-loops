> I'm weighing two ways to cache the journal read: a small LRU inside the reader, or a memoized wrapper around it. Compare them as two labelled options, A) and B), with one trade-off each, reply in
  prose without opening the question box, and end by asking me which one I want.
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

⏵ Thought                                                                                                                     

  A) Small LRU inside the reader. The cache sits on the same object that owns the file handle and the parse state, so it can invalidate on the things that actually change — a reopen, a truncation, a
  seek past the cached window. The trade-off is coupling: eviction policy becomes the reader's problem, and each reader instance carries its own copy, so two readers over the same journal duplicate
  memory and never share a hit.

  B) Memoized wrapper around the reader. The reader stays a plain, testable read path, and you can enable, disable, or resize caching per call site without touching it. The trade-off is blindness:
  the wrapper only sees the public interface, so it can only key on arguments and has no way to notice that the underlying journal changed underneath it — you inherit a staleness bug the moment
  anything writes.

  Which one do you want?

⏵ Thought                           

  A) A small LRU inside the reader keeps the cache adjacent to the access pattern that benefits from it, so hit-rate tuning and invalidation live in one place. The trade-off is that the reader now
  owns state and lifetime, which makes it harder to test in isolation and easy to serve stale entries to callers who expect a fresh read.

  B) A memoized wrapper keeps the reader pure and moves caching policy to the call site, so you can swap it out or drop it per consumer. The trade-off is that every caller has to opt in and agree on
  the key, so invalidation becomes a coordination problem spread across call sites instead of a single place.

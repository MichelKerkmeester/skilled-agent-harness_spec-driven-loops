  moment. The trade-off is that the reader now owns two responsibilities, and every future read path has to remember the cache exists — you get correctness by discipline rather than by

  trade-off is that the wrapper can only see arguments, not file state, so it will happily serve a stale entry after an external append unless you thread a version or mtime through the key.

  Two options, one trade-off each.                                                                                                                                                                      
                                                                                                                                                                                                        
  A) Small LRU inside the reader. The cache sits next to the I/O, so it can key on the exact read shape and invalidate the moment the journal appends or rotates — the failure mode that actually       
  bites a journal. The cost is mutable state inside the reader: every instance carries its own cache, so parallel readers can't share it and tests can't easily bypass it.                              
                                                                                                                                                                                                        
  B) Memoized wrapper around the reader. The reader stays pure and the cache becomes composable — swap in a no-op for tests, share one cache across readers. The cost is that the wrapper only sees     
  the public call signature, so it can't tell when the journal changed underneath it and needs an explicit invalidation hook or TTL, which risks serving stale reads.

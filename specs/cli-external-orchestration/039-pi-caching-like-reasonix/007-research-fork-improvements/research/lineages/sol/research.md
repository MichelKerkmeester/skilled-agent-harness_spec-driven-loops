# Research Synthesis: Improving the Packet 039 Pi Forks

## 1. Executive Summary

The next improvement cycle should begin with executable evidence, then fix `pi-cache-optimizer` persistence correctness, then give DeepPi a versioned persistent report. Those three packages unlock reliable cold-start characterization, credential-independent routing checks, and honest cost comparisons without first expanding either fork's architecture.

The strongest demonstrated defect is `pi-cache-optimizer`'s shared statistics transaction. Its per-process serializer does not protect concurrent processes, and a malformed file is silently treated as empty before the next write. Atomic rename prevents a partial file but not lost updates or destruction of corrupt evidence. [SOURCE: .pi/extensions/pi-cache-optimizer/index.ts:4215] [SOURCE: .pi/extensions/pi-cache-optimizer/index.ts:4264] [SOURCE: .pi/extensions/pi-cache-optimizer/index.ts:4293]

DeepPi's largest operational gap is observability rather than its guarded routing. The full report is coupled to `ctx.ui.notify`, no cross-session stats file exists, and the documented live benchmark points to a missing script. A pure structured report feeding both TUI rendering and an atomic numeric snapshot closes all three evidence gaps cleanly. [SOURCE: .pi/extensions/deep-pi/extensions/deeppi.ts:64] [SOURCE: .pi/extensions/deep-pi/package.json:56]

## 2. Research Question and Scope

This lineage evaluated both packet 039 forks for concrete improvements in correctness, test coverage, telemetry, cost economics, and maintainability. It treated four known limitations as starting facts: incomplete non-interactive DeepPi reports, no persistent DeepPi statistics, an unresolved credential-blocked live check, and uncharacterized cache-optimizer cold starts.

The research inspected the two vendored packages, their tests and manifests, and the sibling packet evidence. It used official DeepSeek documentation for current cache semantics and mutable price data. It did not change either extension or run paid provider traffic.

## 3. Decision

Use this dependency order:

1. Restore and package the DeepPi live benchmark; add a fake-provider routing matrix, a shared ownership fixture, and first/second/restart cold-start fixtures.
2. Harden `pi-cache-optimizer` persistence with cross-process serialization, corruption quarantine, exclusive unique temp files, cleanup, and fault/race tests.
3. Add a versioned DeepPi numeric snapshot generated by a pure report builder and consumed by both TUI and automation.
4. Correct cost labels and cache-write accounting, then run a repeated enabled/disabled crossover benchmark with price provenance.
5. Add fork build identities, patch ledgers, package hygiene gates, then extract cache-optimizer modules one characterized seam at a time.

Defer a DeepPi cross-process edit lock until a concurrent-writer failure is reproducible. The TOCTOU window is real, but a stale-lock protocol adds complexity without current deployment evidence that it outranks the demonstrated stats-loss path. [SOURCE: .pi/extensions/deep-pi/extensions/deeppi/hashlines.ts:83]

## 4. Current Architecture and Ownership Boundary

DeepPi owns direct DeepSeek V4-style routes. `pi-cache-optimizer` contains a duplicate `isDeepPiOwned` predicate and skips all six relevant hooks for those routes. Prior live evidence already proved that guard, so further work should target contract drift rather than re-proving the broad behavior manually. [SOURCE: .pi/extensions/deep-pi/extensions/deeppi/eligibility.ts:1] [SOURCE: .pi/extensions/pi-cache-optimizer/index.ts:1279] [SOURCE: .pi/extensions/pi-cache-optimizer/index.ts:7280]

The predicate must remain narrow. A broad “DeepSeek-like” match would incorrectly exclude proxy and future model routes that DeepPi does not actually own. A shared fixture matrix should exercise both implementations across provider, API, base URL, known ids, aliases, and unknown future ids. This gives one executable contract without a shared runtime dependency.

## 5. Correctness Findings

### Cache-optimizer persistence

The stats path is an unlocked cross-process read/merge/write transaction. Two Pi processes can read the same baseline, merge different updates, and atomically rename different snapshots; the last rename wins. Use an advisory lock with bounded acquisition and stale-owner recovery, or another cross-process transaction primitive, around the complete read/merge/write sequence. [SOURCE: .pi/extensions/pi-cache-optimizer/index.ts:4264]

Malformed state is caught and treated as empty, then may be overwritten. Quarantine the original with a timestamped name, increment a parse-failure health counter, notify once, and only then initialize a new file. Temp files should use random unique names, exclusive creation, and `finally` cleanup. [SOURCE: .pi/extensions/pi-cache-optimizer/index.ts:4293] [SOURCE: .pi/extensions/deep-pi/extensions/deeppi/hashlines.ts:58]

### DeepPi edit safety

DeepPi verifies expected content before atomic replacement and detects some subsequent drift, but another process can modify the target between the expected-content read and rename. This is a real compare-and-swap gap, yet no recorded live clobber establishes urgency. First add a two-writer negative control; promote lock work only if the race reproduces or deployment actually permits concurrent writers. [SOURCE: .pi/extensions/deep-pi/extensions/deeppi/hashlines.ts:83] [SOURCE: .pi/extensions/deep-pi/extensions/deeppi/hashlines.ts:91]

The existing package test only asserts the script string, so it locks in a broken contract. The replacement test must prove the referenced file exists and appears in the dry-run package. ## 7. Telemetry and Observability Design

Create separate versioned files per extension. Never create one shared writable store.

For DeepPi, a pure report builder should produce a schema with `version`, local day, hashed session id, provider/model identity, response count, hit/miss/write tokens, actual cost, `estimatedSavingsVsNoCache`, retry/edit/error counts, health counters, price provenance, and `updatedAt`. Persist numeric and enum data only—no prompts, outputs, tool arguments, credentials, headers, raw errors, or raw session ids. The current-session view can reset independently; daily cumulative totals survive restarts. [SOURCE: .pi/extensions/deep-pi/extensions/deeppi/telemetry.ts:27] [SOURCE: .pi/extensions/pi-cache-optimizer/index.ts:330]

For `pi-cache-optimizer`, preserve aggregate economics and add bounded daily health totals: parse/write failures, missing usage, zero-read/nonzero-write observations, ownership skips, prompt-integrity fallbacks, and compatibility fallback activations. Its current last-50 request samples are memory-only; do not turn them into an unbounded durable event log. [SOURCE: .pi/extensions/pi-cache-optimizer/index.ts:370] [SOURCE: .pi/extensions/pi-cache-optimizer/index.ts:6818]

Separate structured data, text rendering, and transport. Render `/deeppi report` from the same object written to disk, and provide a tiny read-only JSON report command. This avoids relying on RPC/UI forwarding and makes report tests independent of terminal behavior. [SOURCE: .pi/extensions/deep-pi/extensions/deeppi.ts:64]

## 8. Cost Economics

DeepPi's savings arithmetic is valid as a fully uncached counterfactual when `usage.input` is the miss class and `usage.cacheRead` is the hit class. It is not a measured DeepPi treatment effect because DeepSeek caching is automatic. Rename the field to `estimatedSavingsVsNoCache`; causal language requires an extension enabled/disabled ablation. [SOURCE: .pi/extensions/deep-pi/extensions/deeppi/telemetry.ts:47] [SOURCE: https://api-docs.deepseek.com/guides/kv_cache]

The current calculation ignores nonzero `cacheWrite` in availability, totals, and cost. Direct DeepSeek documentation exposes hit/miss accounting and no separately billed write class, so the direct route likely reports zero. Keep the normalized field, include its model-provided cost when present, and record a health warning when the assumption changes. [SOURCE: https://api-docs.deepseek.com/api/create-completion]

Prices must be provenance, not constants asserted by behavior tests. Runtime computation already uses Pi model metadata; benchmark outputs should record provider/model, currency, price snapshot, and capture time. Synthetic prices remain the correct way to test arithmetic because DeepSeek's published table can change. [SOURCE: .pi/extensions/deep-pi/extensions/deeppi/telemetry.ts:61] [SOURCE: https://api-docs.deepseek.com/quick_start/pricing?push_animated=1&show_loading=0&theme=light&webview_progress_bar=1]

## 9. Benchmark Design

Use a paired randomized crossover with fixed prompt and tool fixtures. For each target model and round:

1. Randomize extension enabled/disabled order.
2. Record request 1 as cold, repeat the identical request twice as warm, and repeat after a fresh Pi process.
3. Capture normalized hit/miss/write tokens, input/output cost, provider latency, retries, request-prefix hash and byte length, model identity, price snapshot, and cache age.
4. Report distributions and paired deltas across multiple rounds; do not publish a single cold/warm percentage.

DeepSeek documents automatic best-effort caching and a construction delay, so repeats and process restarts are required. [SOURCE: https://api-docs.deepseek.com/guides/kv_cache]

Measure extension overhead separately with monotonic per-hook timing. DeepPi also needs temporary feature ablations for prompt shaping, tool-description shortening, and hashline editing; otherwise aggregate on/off results cannot identify which module caused a benefit or regression.

Add unique fork build versions, upstream base refs, local owner/contact metadata, and a machine-readable patch ledger containing patch ids, owned files, tests, last reconciliation date, and tree/patch checksum. ## Divergence Map

No divergent-mode pivots, Council artifacts, pivot failures, or audited overrides were recorded. Breadth came from seven scheduled focus tracks: architecture, correctness, testing, observability, cost economics, maintainability, and adversarial prioritization. ## 14. Testable Acceptance Conditions

- Two cache-optimizer processes updating the same baseline preserve both increments across repeated race runs.
- A malformed stats file is quarantined byte-for-byte and never silently overwritten.
- Injected write/rename failures leave no orphan temp files and preserve the last valid snapshot.
- Every ownership fixture returns the same result from both forks, and only one extension transforms each route.
- `npm pack --dry-run` includes every documented benchmark executable.
- DeepPi TUI text and JSON snapshot are generated from an identical structured report object.
- Restarted DeepPi sessions retain daily totals but reset session counters by documented semantics.
- Cold/warm/restart fixtures record normalized hit/miss/write classes for every newly added model.
- Benchmark output labels no-cache counterfactual savings separately from enabled/disabled treatment delta.
- Every benchmark result records price provenance and local hook duration separately from provider latency.

## 15. Implementation Boundaries

Keep the state files separate and versioned. Avoid prompt/output persistence. Do not widen DeepPi ownership while adding telemetry. Preserve the cache optimizer's default export and existing behavior during extraction. Add dependencies only if Node/Git primitives cannot provide bounded cross-process locking with stale recovery. Treat live provider calls as an explicit-cost optional suite.

## 16. Trade-offs, Risks, and Convergence Report

The evidence-first order delays the attractive monolith cleanup, but lowers the chance of moving defects across modules without noticing. File snapshots add disk I/O; batching and serialized writers should keep it bounded. Cross-process locks improve state correctness but need timeouts and stale-owner recovery. Feature ablations improve causal inference but should remain benchmark controls rather than permanent user complexity unless they prove operational value.

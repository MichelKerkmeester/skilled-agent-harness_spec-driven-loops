## Version-parser matrix (both parsers, run, not inferred)

`parseOpencodeVersion` is **byte-identical** in `opencode-version.mjs:104-130` and `opencode-version.cjs:142-168` (extracted and `diff`ed → identical), and both produced the same result on all 17 probed inputs.

| Input | Result | Disposition |
|---|---|---|
| `''` (empty) | `unknown` | refused (guard: unknown → version-specific rules warn; dispatcher: `E_OPENCODE_UNRESOLVED` → dispatch refused) |
| `'opencode'` / `'opencode2'` (binary name, no version) | `unknown` | refused — the name is never read as a version |
| `'2.0.32-rc.1'` | **`v2`** | parsed — `(?:[-+][\w.-]+)?` accepts the prerelease suffix by design; takes the v2 flag set (`run --standalone`) |
| path containing `1.`, e.g. `'/opt/tools/1.19.3/opencode'` | `unknown` | refused — the pattern is anchored and a path token cannot match; resolvers never feed a path to the parser (`.mjs` refuses path-qualified binaries without probing, `:143,146`; `.cjs` probes the file and parses only its output) |
| two version strings, e.g. `'opencode v2.0.32\n1.19.3'` | `v2` | parsed — first version token wins (line-major, then token-major); same for `'1.19.3 2.0.32'` → `v1` |

Also checked: `'opencode 3.0.0'` → `unknown` (unsupported major, fail-closed); `'opencode v1.19.3'` → `v1`; `'2.0.32+build.7'` → `v2`; `'opencode v2.0.32 (build 5)'` → `v2` (trailing text outside the matched token). **The two parsers agree on every case.** They diverge only in *failure policy*, deliberately: guard = `'unknown'` (fail-open, warn), dispatcher = throw (fail-closed, refuse).

Consequence worth naming: because a path-qualified invocation is never probed, version-specific *blocking* rules degrade to warnings there (`command-flag-for-slash-prompt`, `error` → `warn`, asserted at `dispatch-rule-checks.test.mjs:689-696`) — a tested, intended trade-off that lets a legitimate v2 path-qualified dispatch through, at the cost of an advisory-only verdict for a v1 one.

# Iteration 5: PWA/mobile behavior and product phasing

## Focus
This iteration defined the mobile delivery contract for a Claude-style Pi client: platform push/install constraints, event-triggered notifications, service-worker limits, safe approval revalidation, tailnet onboarding, offline behavior, core screens, accessibility, and phased scope. “Android support” is interpreted as a runtime-capability-gated browser target rather than an unsupported promise about every Android browser/version. Visual imitation and native-app background parity are deferred.

## Findings
1. **High — iOS/iPadOS push requires an installed Home Screen web app; Android must be capability-gated until a tested browser floor is pinned.** WebKit confirms that iOS/iPadOS 16.4 added Web Push for web apps added to the Home Screen, using the Push API, Notifications API, and service workers; those notifications participate in the Lock Screen, Notification Center, Apple Watch, and Focus. Apple documents the user-driven Add to Home Screen/Open as Web App flow. MDN confirms the standards path and says mobile notifications should use `ServiceWorkerRegistration.showNotification()` after permission requested from a user gesture. The client should expose a readiness check for secure context, service-worker registration, `PushManager`, notification permission, and successful subscription rather than infer support from user agent. Modern capable Android browsers are an expected target, but no Android-vendor version matrix was directly verified in this iteration; exact Android browser/version claims remain a release-gate test, not a confirmed fact. [SOURCE: https://webkit.org/blog/13966/webkit-features-in-safari-16-4/] [SOURCE: https://support.apple.com/guide/iphone/bookmark-a-website-iph42ab2f3a7/ios] [SOURCE: https://developer.mozilla.org/en-US/docs/Web/API/Push_API] [SOURCE: https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API/Using_the_Notifications_API] [INFERENCE: runtime capability and subscription checks are safer than an OS-name branch because the retrieved standards sources do not establish one Android-wide support floor]

2. **Critical — the relay, not the PWA or service worker, owns background execution and reconnection.** A push can start the registered service worker to handle a bounded event, but the Service Worker specification allows the user agent to terminate a worker whenever it has no event to handle; `waitUntil()` extends an event, not an indefinitely resident process. Background Sync is explicitly limited-availability. Therefore neither an open WebSocket, a Pi child, streaming state, an approval lease, nor prompt execution may depend on a background page/service worker. The relay continues the run. Foreground/open resumes WSS from the durable epoch/sequence/entry cursor; a push handler only displays a notification, while notification activation focuses/opens the app and lets the page authenticate and reconcile. [SOURCE: https://www.w3.org/TR/service-workers/#service-worker-lifetime] [SOURCE: https://developer.mozilla.org/en-US/docs/Web/API/Push_API] [SOURCE: https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API] [SOURCE: specs/cli-external-orchestration/041=pi-remote-mobile-agent-like-cc/research/lineages/cli-pi-gpt-56-sol/iterations/iteration-003.md] [INFERENCE: event-bounded execution cannot safely host the persistent RPC/WSS lifecycle]

3. **High — notifications are deduplicated hints for committed transitions, never a second event stream.** Emit push only when the target installation lacks a live visible attachment (or its user preference explicitly requests all alerts), and only after the relay commits one of: `agent_settled`, a newly pending policy approval, or a safety-relevant `indeterminate`/interrupted outcome. Do not notify on `agent_end`, token deltas, tool-progress updates, or replayed duplicates: Pi states that `agent_end` may be followed by retry/compaction/queued continuation, while `agent_settled` means no automatic continuation remains. Persist a notification key such as `(installationId, sessionId, streamEpoch, transitionSeq, kind)` before send, coalesce replacement states, and have app-open reconciliation remain authoritative if delivery is delayed, duplicated, suppressed by Focus, or never delivered. [SOURCE: /Users/michelkerkmeester/.local/lib/node_modules/@earendil-works/pi-coding-agent/docs/rpc.md:832-888] [SOURCE: https://webkit.org/blog/13966/webkit-features-in-safari-16-4/] [SOURCE: https://developer.mozilla.org/en-US/docs/Web/API/Push_API] [INFERENCE: committed transition identity plus foreground suppression prevents push delivery semantics from corrupting relay state]

4. **Critical — push payloads and lock-screen text are generic, and an approval notification carries zero approval authority.** Store push subscription endpoints as secrets because MDN describes each endpoint as a unique capability URL. Send only a random one-use notification lookup ID, coarse kind, and collapse/dedup key; do not send prompt text, assistant output, tool arguments/results, workspace/path, session title, model, approval choice, Pi request ID, payload digest, auth token, or filesystem identifier. Render generic text such as “Pi needs your attention” or “A run finished.” On activation, the foreground page reauthenticates, reconnects, and fetches current state. It shows an approval only if `(session, epoch, Pi request ID, payload digest, deadline, policy)` is still pending and the principal is still authorized; the relay’s atomic first-decision gate decides. Timeout, abort, prior response, revocation, or epoch replacement yields a disabled resolved/expired card, never a forwarded late response. 5. **High — onboarding is a staged reachability, relay-authentication, installation, then notification flow.** The operator first publishes the loopback relay with tailnet-only Serve and HTTPS; MagicDNS supplies a stable tailnet device name. On iOS the user installs Tailscale, accepts its VPN configuration, logs in, and verifies the Serve URL; the PWA then performs its own relay login/device registration, proves a read-only `/health`/session-catalog request, offers Add to Home Screen/Open as Web App, and only from an explicit in-app action asks for notification permission. A manifest should provide stable `id`, `start_url`, scope, standalone display, name, and icons, without credentials in URLs; WebKit specifically uses manifest `id` to distinguish multiple installations. Do not make a non-standard install prompt or successful tailnet reachability equivalent to relay authentication. The same conceptual sequence applies on Android, but its exact Tailscale/browser installation screens must be verified before release because the attempted legacy Android documentation URL redirected to an unrelated troubleshooting page. [SOURCE: https://tailscale.com/docs/install/ios] [SOURCE: https://tailscale.com/docs/features/magicdns] [SOURCE: https://tailscale.com/docs/features/tailscale-serve] [SOURCE: https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable] [SOURCE: https://webkit.org/blog/13966/webkit-features-in-safari-16-4/] [SOURCE: https://support.apple.com/guide/iphone/bookmark-a-website-iph42ab2f3a7/ios] [INFERENCE: ordering network admission before app authentication and notification consent makes each failure independently diagnosable without widening authority]

6. **High — offline mode is an explicitly stale, read-only snapshot, never an offline command queue.** Cache the versioned app shell and a bounded, redacted last-known view containing opaque session IDs, coarse run status, timestamps, and optionally user-enabled sanitized transcript excerpts. Mark the entire surface “Offline — last updated …”; disable prompt/steer/abort/approval/session-switch mutations and do not promise later send. Browser Cache lifetime is browser-dependent and entries do not update or expire automatically, so application metadata needs schema version, principal/device binding, snapshot revision, and a short expiry; logout or account change purges it, and reconnect transactionally replaces it after authorization. An offline approval card is display-only and visibly expired/unavailable. [SOURCE: https://developer.mozilla.org/en-US/docs/Web/API/Cache] [SOURCE: https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API] [SOURCE: specs/cli-external-orchestration/041=pi-remote-mobile-agent-like-cc/research/lineages/cli-pi-gpt-56-sol/iterations/iteration-004.md] [INFERENCE: a read-only stale snapshot avoids both duplicate mutation delivery and authorization decisions made without current relay state]

7. **High — the MVP information architecture needs four explicit state surfaces, with accessibility built into their reducers.** The session list shows redacted title/preview, last activity, and mutually clear `running`, `needs attention`, `settled`, `interrupted`, or `offline/stale` status. The thread renders user/assistant bubbles with one replaceable streaming draft; tool cards are collapsed by default and show name, running/succeeded/failed state, elapsed time, and sanitized summary; the composer distinguishes accepted, queued, running, and indeterminate submissions. Approval uses a modal/sheet with canonical risk/action/workspace summary, expiry, explicit “Deny” and “Allow once,” and a stale terminal state. Connection/reconciliation is a persistent banner rather than an ambiguous spinner. All functions remain keyboard operable, visible focus is preserved, names/roles/states are programmatic, targets meet at least WCAG’s 24-by-24 CSS-pixel minimum (44-by-44 product target), status changes use a concise live region, and token/tool deltas are coalesced rather than announced individually or stealing focus. [SOURCE: specs/cli-external-orchestration/041=pi-remote-mobile-agent-like-cc/research/lineages/cli-pi-gpt-56-sol/iterations/iteration-002.md] [SOURCE: specs/cli-external-orchestration/041=pi-remote-mobile-agent-like-cc/research/lineages/cli-pi-gpt-56-sol/iterations/iteration-003.md] [SOURCE: https://www.w3.org/TR/WCAG22/#keyboard] [SOURCE: https://www.w3.org/TR/WCAG22/#focus-visible] [SOURCE: https://www.w3.org/TR/WCAG22/#status-messages] [SOURCE: https://www.w3.org/TR/WCAG22/#target-size-minimum] [INFERENCE: coalesced announcements preserve the same authoritative-replace reducer without overwhelming assistive-technology users]

8. **High — phase by authority and platform certainty, not visual parity.** MVP is tailnet-only Serve plus independent relay auth; installable responsive PWA; session list/thread; streamed assistant and summarized tool cards; foreground prompt/abort; live revalidated approvals; generic settlement/approval push where capability checks pass; read-only offline shell/snapshot; and the accessibility requirements above. MVP explicitly excludes offline mutations, public exposure, raw-content push, background WSS, install-dependent auth, and a promise of universal Android push. Hardening next adds tested iOS/Android browser matrices, subscription-expiry/change handling, multi-device notification preferences/deduplication, badge counts derived from current relay state, cache remote-wipe/expiry tests, and device-level reconnect/approval race tests. Later phases may add richer redacted offline history, attachments/voice, native wrappers when business requirements truly need stronger OS integration, and multi-user administration; public Internet WSS remains a separate security exception rather than a maturity milestone. ### Platform and lifecycle decision matrix

| Condition | Confirmed behavior | Product behavior |
|---|---|---|
| iOS/iPadOS 16.4+ Home Screen web app | WebKit supports Web Push through Push/Notifications/Service Worker APIs. | Offer push only after installation and an explicit in-app gesture; still capability-test and show troubleshooting. |
| iOS/iPadOS ordinary browser tab | The retrieved WebKit source scopes support to Home Screen web apps. | Do not promise push; show “Install to enable notifications.” |
| Android browser | Standards APIs provide the implementation path; an exact vendor/version floor was not directly verified here. | Capability-test registration/subscription; publish a supported matrix only after device testing. |
| Foreground/live socket | Page can receive authoritative relay events. | Prefer in-app state; suppress duplicate push by installation preference/visibility lease. |
| Background/closed page | Push may start a bounded service-worker event; worker may later be terminated. | Show generic notification only; no background RPC/WSS ownership. |
| Offline | Cached data can persist but is browser-managed and stale. | Read-only, timestamped, redacted snapshot; all authority-changing controls disabled. |

### Notification transition contract

| Relay transition | Push? | Notification/action rule |
|---|---|---|
| `agent_end` / retry / compaction / token or tool update | No | Continue authoritative relay reduction; do not claim completion. |
| Committed `agent_settled` while no visible attachment | Yes, preference permitting | Generic “A run finished”; lookup ID only; opening reconciles current session. |
| Committed new pending approval while no visible attachment | Yes, preference permitting | Generic “Pi needs your attention”; opening fetches and revalidates; notification has no Allow/Deny action. |
| Approval timeout/abort/first response/epoch end | Cancel or collapse pending notice where supported | Current app state renders resolved/expired; any late click is harmless. |
| Recovered `dispatching` mutation becomes `indeterminate` | Yes, safety preference permitting | Generic “Check a submission”; never automatic resend. |

## Ruled Out
- **Keeping WSS/Pi work alive in a service worker:** the worker may be terminated whenever it has no event, and event lifetime extension is bounded to the event. [SOURCE: https://www.w3.org/TR/service-workers/#service-worker-lifetime]
- **Treating `agent_end` as the completion push trigger:** Pi explicitly permits subsequent retry, compaction, or queued continuation; `agent_settled` is the terminal trigger. [SOURCE: /Users/michelkerkmeester/.local/lib/node_modules/@earendil-works/pi-coding-agent/docs/rpc.md:832-888]
- **Putting transcript, tool, workspace, or approval data in push text/payload:** lock-screen presentation and endpoint-capability risk make notification transport the wrong content boundary. [SOURCE: https://developer.mozilla.org/en-US/docs/Web/API/Push_API] [SOURCE: specs/cli-external-orchestration/041=pi-remote-mobile-agent-like-cc/research/lineages/cli-pi-gpt-56-sol/iterations/iteration-004.md]
- **Approving from a notification or offline cache:** timeout, first response, revocation, or epoch replacement can make it stale; only current relay state can authorize a response. [SOURCE: /Users/michelkerkmeester/.local/lib/node_modules/@earendil-works/pi-coding-agent/docs/rpc.md:1144-1165] [SOURCE: specs/cli-external-orchestration/041=pi-remote-mobile-agent-like-cc/research/lineages/cli-pi-gpt-56-sol/iterations/iteration-003.md]
- **Queueing offline prompts through Background Sync:** availability is limited and the relay/Pi crash boundary already makes uncertain retries explicit. [SOURCE: https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API] [SOURCE: specs/cli-external-orchestration/041=pi-remote-mobile-agent-like-cc/research/lineages/cli-pi-gpt-56-sol/iterations/iteration-003.md]
- **Depending on a browser install prompt or OS-name check:** install promotion and platform API support vary; manual iOS installation and runtime capability proof are required. [SOURCE: https://support.apple.com/guide/iphone/bookmark-a-website-iph42ab2f3a7/ios] [SOURCE: https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable]

## Edge Cases
- Ambiguous input: “Android web push availability” spans multiple browser engines and versions. This iteration selected a capability-tested target and deferred a categorical support matrix.
- Contradictory evidence: native-style expectations suggest persistent background connectivity, while the Service Worker lifetime contract permits termination. The design resolves this by keeping execution in the relay and using push only to attract foreground attention.
- Missing dependencies: no live iOS/iPadOS or Android device test was available, and the attempted legacy Android Tailscale documentation URL did not resolve to Android installation guidance. Exact Android release support and tailnet-hosted Home Screen push remain release-gate verification items.
- Partial success: official WebKit/Apple, MDN/W3C, Tailscale Serve/MagicDNS/iOS, and installed Pi sources answered the safe product behavior and phasing question. Android-specific version coverage remains deliberately unclaimed; status is `complete` with that residual verification risk.

## Reflection
- What worked and why: WebKit/Apple established the iOS install boundary, W3C made service-worker lifetime non-negotiable, Pi’s settlement/dialog contracts identified safe triggers, and prior relay invariants turned stale notification behavior into a precise revalidation flow. A product phase table then separated verified MVP authority from platform validation work.
- What did not work and why: A legacy Android Tailscale URL redirected to generic troubleshooting, and no live mobile devices were available. Consequently, Android-specific browser/version and onboarding claims were not promoted from expectation to fact.
- What I would do differently: Use a real-device matrix to install from the private Serve URL, subscribe/unsubscribe/reinstall, background/kill the PWA, exercise Focus and denied permission, rotate tailnet/relay identity, and race approval timeout against notification activation while recording relay transition IDs.

# Iteration 3: Reconnect protocol and durable relay schema

## Focus
This iteration specified and fault-tested the relay contract for reconnect, bounded replay, durable Pi-entry reconciliation, idempotent mobile mutations, session switching, child restart, duplicate/gapped deltas, and multi-client approval leases. “Durable schema” is interpreted as a storage-neutral logical schema and transaction boundaries, not a database-vendor choice. Because a live Pi crash/switch harness would create session files outside the permitted lineage, the fault test was a deterministic, no-write state-machine model, as the iteration prompt permits.

## Findings
1. **High — a stream epoch is one immutable Pi-child/session binding, and bounded replay needs an explicit acceptance matrix.** Generate and durably store a fresh, never-reused `streamEpoch` before accepting events from every spawn, restart, or successful session rebind; start `eventSeq` at 1; commit each envelope before broadcasting it. Persist `floorSeq` and `highSeq` for the retained window. A reconnect cursor is replayable only when its session and epoch match and `floorSeq - 1 <= lastEventSeq <= highSeq`; an older, ahead-of-server, or cross-epoch cursor requires snapshot reconciliation. Within an epoch, clients ignore `seq <= lastApplied`, apply only `seq == lastApplied + 1`, and pause on a larger gap. Pi forwards asynchronous events but supplies no replay cursor, while the prior protocol pass established that WebSocket ordering does not survive connection replacement. 2. **High — resynchronization needs a committed barrier, not an unfenced mix of snapshot and live deltas.** On replay miss, freeze the client’s transient reducers; serialize reconciliation against session switching; issue `get_state` and `get_entries`; and, when their responses are read, append a synthetic `snapshot_barrier` at the next relay sequence before releasing later events. Send the snapshot with `throughSeq=barrierSeq`, then deliver only envelopes above that value. The client discards incomplete message/tool drafts through the barrier; if Pi is still streaming, later deltas may be incomplete, but the authoritative `message_end` replaces the draft. The RPC implementation handles `get_entries` synchronously and writes its correlated response on the same ordered stdout path as events, which gives the relay a usable observation fence. 3. **High — `get_entries(since)` failure is a cache-identity failure and must trigger transactional full replacement.** Pi returns `success:false` when `since` is absent from the active session; a successful call returns entries strictly after that append-order ID plus an independent current `leafId`. On failure, verify the `get_state.sessionId`, query `get_entries` without `since`, and atomically replace the cached entry set, cursor, and leaf. Do not continue from the foreign cursor and do not substitute only `get_messages`: entries include pre-compaction and abandoned branches, and the leaf can identify a branch position that is not equivalent to “last cached message.” A valid cursor permits append-by-entry-ID followed by a separate leaf update. 4. **Critical — the relay can deduplicate ordinary retries, but cannot honestly promise exactly-once prompt submission across its crash window without a Pi-side durable mutation key.** Use a unique key `(principalId, relaySessionId, clientMutationId)` and a canonical payload digest. Persist `prepared`, then `dispatching`, before the single Pi stdin write; the same key/digest returns the recorded status, while a different digest is a conflict. Persist `accepted` or `rejected` after the Pi response and keep a tombstone at least as long as the maximum accepted retry age. If the relay dies after the stdin write but before recording the response, recovered `dispatching` is `indeterminate`: blind resend can duplicate a prompt, while never resend can lose one written just before the crash. RPC request `id` is only response correlation, and prompt success is emitted after preflight with no durable client mutation field. The safe MVP is at-most-once recovery with an explicit “submission outcome unknown” UI; true exactly-once requires a Pi/extension change that atomically persists the mobile mutation ID with acceptance. 5. **Critical — `switch_session` is destructive to an active outgoing child and therefore cannot be a casual shared-client navigation operation.** Pi’s runtime calls `session.abort()`, emits shutdown, disposes the old session, opens the target, and rebinds before returning success; an extension may also cancel before replacement. A relay using one shared child must hold an exclusive binding lock, reject switching while another client owns or observes an active run (or require an explicit abort), quarantine transition output, and publish a new epoch only after `cancelled:false` plus a verifying `get_state`. On cancellation it retains the old epoch. Prefer one child per concurrently active session so selecting a conversation changes only a client attachment and cannot abort another client’s run. Never apply a late old-epoch delta or approval response to the new child. 7. **Critical — multi-client approval needs both a short interaction lease and an atomic first-decision gate; the lease is not authorization.** Scope each request by `(relaySessionId, streamEpoch, piRequestId, payloadDigest)`, persist it before fan-out, and separately verify the responding principal’s policy authority. ### Durable relay schema and invariants

| Relation | Required key/state | Transaction invariant |
|---|---|---|
| `session_catalog` | `relaySessionId` PK; private `piSessionId`, workspace, server-only path; current binding and `lastLeafId` | Mobile input never supplies a filesystem path; catalog change and binding ownership are serialized. |
| `child_binding` | `streamEpoch` PK; session, child start token, `starting/ready/draining/dead`, start/end reason | Epoch is persisted before event ingest and never reused; at most one writable binding per relay session. |
| `replay_meta` / `replay_event` | `(sessionId, epoch)` with `floorSeq/highSeq`; event PK `(sessionId, epoch, seq)` | Insert event and advance high watermark before broadcast; retention is bounded by server count/bytes/age, never pinned indefinitely by a client. |
| `session_entry_cache` | `(relaySessionId, piSessionId, entryId)`; append ordinal and payload; sync row with cursor/leaf/revision | Cursor mismatch replaces entries, cursor, and leaf in one transaction; valid suffixes are idempotent by entry ID. |
| `mutation_ledger` | unique `(principalId, sessionId, clientMutationId)`; payload digest, command, state, RPC ID, epoch, outcome | Same digest never causes a second write; different digest conflicts; recovered `dispatching` never auto-resends. |
| `approval_request` | `(sessionId, epoch, piRequestId, payloadDigest)`; state, authorized policy, lease owner/token/version/expiry, decision | Lease claim/renew and first decision are CAS operations; decision and Pi-write outbox are committed together. |

[INFERENCE: these relations are the minimum durable identities needed to make every reconnect decision depend on committed session, epoch, sequence, mutation, or approval state rather than socket memory]

### Deterministic fault-test matrix

| Injected fault | Expected result | Result |
|---|---|---|
| Duplicate non-cumulative delta | `seq <= lastApplied` ignored; naïve append demonstrably corrupts text | PASS |
| Gap within same epoch | reducer pauses; no speculative append | PASS |
| Cursor older than retained floor, ahead of high, or from old epoch | full resync, not partial replay | PASS |
| Valid vs foreign Pi entry cursor | valid suffix appends; foreign cursor full-replaces | PASS |
| Same mutation ID/same digest vs changed digest | recorded result vs conflict | PASS |
| Crash while mutation is `dispatching` | becomes `indeterminate`, never blind-resends | PASS |
| Two approval responders, duplicate response, or new child epoch | only current leased first response wins | PASS |

## Ruled Out
- **Blindly retransmitting `dispatching` mutations after restart:** it chooses at-least-once behavior and can duplicate an already accepted prompt. [INFERENCE: based on the uncoordinated relay/Pi commit boundary in Finding 4]
- **Continuing a transient reducer across an epoch change or sequence gap:** old and new children can reuse Pi-local identifiers, and missing non-cumulative deltas cannot be reconstructed. [SOURCE: specs/cli-external-orchestration/041=pi-remote-mobile-agent-like-cc/research/lineages/cli-pi-gpt-56-sol/iterations/iteration-002.md]
- **Using `get_messages` alone after a cursor mismatch:** it omits the append-tree identity needed for future durable cursors and abandoned/pre-compaction history. [SOURCE: /Users/michelkerkmeester/.local/lib/node_modules/@earendil-works/pi-coding-agent/docs/rpc.md:694-722]
- **Switching a globally shared child when another client has an active run:** Pi aborts and disposes the outgoing session as part of replacement. [SOURCE: /Users/michelkerkmeester/.local/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session-runtime.js:102-145]
- **Treating an approval lease as permission or carrying approval across epochs:** authority remains policy-bound, and Pi’s pending request exists only in the originating process. ## Dead Ends
No protocol category is exhausted. Relay-only exactly-once prompt delivery across process crashes is, however, an impossible guarantee with the current RPC contract; future work should either accept explicit `indeterminate` outcomes or add a Pi-side durable mutation primitive rather than varying relay retry logic.

## Edge Cases
- Ambiguous input: “durable schema” was narrowed to logical relations, keys, states, and transaction boundaries; SQL dialect, indexes, and retention numbers remain implementation decisions.
- Contradictory evidence: the desired mutation-idempotency behavior conflicts with RPC’s lack of a durable mutation token. The contradiction is resolved only for normal reconnect retries; crash-window delivery remains explicitly `indeterminate`, not exactly-once.
- Missing dependencies: no required dependency was missing. A live process-kill/switch transcript would write Pi session data outside the allowed packet, so the prompt-authorized deterministic no-write model was used instead.
- Partial success: none. All seven specified fault classes passed the deterministic model; OS-level partial-write timing and real Pi crash recovery remain residual verification work, not claimed empirical evidence.

## Reflection
- What worked and why: Reading the version-matched command handler, session replacement runtime, SessionManager persistence, and pending-dialog map exposed the exact process-memory/durable boundary. The deterministic model then forced every duplicate, gap, cursor, mutation, and lease decision into a pass/fail transition instead of relying on a happy-path narrative.
- What did not work and why: A live child-kill/interleaving transcript was not permissible because it would create or mutate Pi session artifacts outside this lineage. Consequently, OS/process timing is specified from code and fault modeling rather than empirically measured.
- What I would do differently: In an isolated, explicitly writable fixture, instrument stdout ordinals around `get_entries`, kill the relay immediately before/after its Pi stdin write, switch during a tool call, and race two approval clients to validate the same invariants against real scheduling.

## Recommended Next Focus
Investigate the safe security and network-exposure model: relay authentication and device identity, Tailscale Serve versus an authenticated WSS bridge, workspace/session authorization, CSRF/origin controls, secret redaction, rate and queue limits, audit retention, and the trust boundary for the Pi-side approval extension. Carry the mutation crash-window limitation forward as a protocol risk rather than reopening relay-only exactly-once retry variants.

## 2. PROBLEM & PURPOSE

### Problem Statement

The app documentation produced across phases 010-014 has no single quality measurement and no inventory that maps the app's live capabilities to their source and test anchors. Without a DQI gate, quality regressions in `docs/`, READMEs, and the converted references are invisible. Without a feature catalog, operators and agents cannot move from a capability name to the files that implement and test it. These are the two missing closing surfaces of the uplift.

### Purpose

Deliver a bounded workstream that measures documentation quality across the app with the `sk-doc` DQI tooling and produces a current-reality feature catalog in the `sk-create-feature-catalog` template.
<!-- /ANCHOR:problem -->

## 3. SCOPE

### In Scope
- A doc-quality gate procedure and baseline report using the `sk-doc` `extract_structure.py` DQI scoring across all app markdown under `Apps/Pi Mobile/`.
- A feature catalog root and per-feature files in the `sk-create-feature-catalog` template (`feature-catalog-template.md`), covering the app's live surfaces with source-file and test anchors.
- A documented quality bar and per-file score targets for the gate.

### Out of Scope
- Authoring new READMEs or runbooks (owned by phases 010-014).
- Any change to app source code, tests, or configuration.

## 4. REQUIREMENTS

### P0 - Blockers (MUST complete)

| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| REQ-001 | The DQI gate is runnable and recorded. | `dqi-gate.md` names the scoring command and bar, and `dqi-report.md` records per-file scores and bands from `extract_structure.py`. |
| REQ-002 | Every app doc is scored. | The gate covers `docs/*.md`, the realigned READMEs, `docs/code-standards.md`, and `docs/install-and-onboarding.md`. |
| REQ-003 | The catalog root is complete. | `feature-catalog.md` has the frontmatter, H1 intro, numbered ALL-CAPS H2 sections, and one link per per-feature file. |

### P1 - Required (complete OR user-approved deferral)

| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| REQ-004 | Per-feature files are anchored. | Each per-feature file has OVERVIEW, HOW IT WORKS, SOURCE FILES, and SOURCE METADATA sections with real file paths under `Apps/Pi Mobile/`. |
| REQ-005 | Quality regressions are visible. | The gate re-run after any doc change shows a delta, and files below the bar are listed as findings. |
| REQ-006 | The catalog is packet-history free. | Catalog entries cite current source files and tests, not spec or phase numbers. |

## L2: NON-FUNCTIONAL REQUIREMENTS

### Performance
- The gate scores all app markdown in one bounded run with recorded commands.

### Security
- No secret, enrollment payload, Serve anchor, or credential path enters the report or catalog.

### Reliability
- Files below the DQI bar are reported as findings, never silently dropped.

---

## L2: EDGE CASES

### Data Boundaries
- The catalog counts root entries against per-feature files; a mismatch is a blocking finding.

### Error Scenarios
- Missing source anchor: mark the feature file blocked and report it.
- Unscorable doc type: record the type and reason in the report.

### State Transitions
- The deliverables are Draft; implementation starts after this phase is approved.

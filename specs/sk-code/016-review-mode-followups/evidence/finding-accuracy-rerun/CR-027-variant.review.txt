1. [fixtures/clamp.js:5] Inverted bounds silently return `max` instead of failing or disclosing the precondition
   - Case: `clamp(5, 100, 0)` → `Math.max(5, 100)` is `100`, `Math.min(100, 0)` is `0`; the call returns `0`, the caller's `max`. Once `min > max`, `Math.max(value, min)` is always greater than `max`, so the result is `max` for *every* `value`, while the line-3 comment's "closed range [min, max]" is empty. Neither a guard, a thrown error nor a doc line claims to reject this input class, and no caller in scope sends it, so reach is unnamed and severity is capped at P2.
   - Risk: bounds derived from config, env parsing or upstream data can arrive reversed; the function answers with a plausible number instead of a signal that the range itself is broken.
   - User impact: if deferred, a reversed range becomes a silently clamped wrong value that surfaces far from its cause — a page size pinned to the wrong end, a limit persisted at the wrong number — with no error trace pointing at the bad bound.
   - Finding class: instance-only
   - Scope proof: `ls fa-variant` lists `fixtures/` alone and `ls fa-variant/fixtures` lists `clamp.js` alone, so the reviewed subtree is a single file with no second clamp implementation and no consumer to fix alongside it; a scratchpad-wide `grep -n "clamp"` returned only `clamp.js:4` (definition) and `clamp.js:8` (export) under `fa-variant/`, and that grep hit its 100-match cap, so the `ls` results are the dispositive evidence.
   - affectedSurfaceHints: ["clamp utility", "callers parsing numeric bounds"]
   - riskScore: 3 (advisory only)
   - Recommended fix: add the invariant above the return — `if (min > max) throw new RangeError('min must not exceed max');` — or, if silent clamping is deliberate, say so at line 3 so the comment states the real behavior.

2. [fixtures/clamp.js:5] Non-numeric and omitted operands propagate `NaN` out of the function instead of failing
   - Case: `clamp(5, Number.NaN, 100)` returns `NaN` — `Math.max` yields `NaN` for any `NaN` operand and `Math.min` then propagates it — and `clamp(5, 0)` with `max` omitted returns `NaN` by the same route (`Number(undefined)` is `NaN`). The doc comment says "a number", so both inputs sit outside the stated contract, and no line in the file claims to reject them.
   - Risk: `NaN` satisfies `typeof x === 'number'`, so it passes the type check a caller is most likely to write and then poisons every downstream arithmetic result.
   - User impact: if deferred, a `NaN` bound silently empties an array slice, blanks a rendered numeric value, or nulls a persisted limit after a JSON round-trip — with no error raised where the bad bound entered.
   - Finding class: instance-only
   - Scope proof: same single-file subtree as finding 1 (`ls fa-variant/fixtures` → `clamp.js` only), so there is no sibling validation site and no caller that already guards its own bounds.
   - affectedSurfaceHints: ["clamp utility", "bounds validation"]
   - riskScore: 2 (advisory only)
   - Recommended fix: reject non-numeric bounds in the same guard, e.g. `if (Number.isNaN(min) || Number.isNaN(max) || min > max) throw new RangeError(...)`. Do not widen to `Number.isFinite` — `±Infinity` is a legitimate clamp bound and `clamp(1e308, 0, Infinity)` must keep working.

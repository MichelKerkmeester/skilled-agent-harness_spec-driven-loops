## What Was Built

A reader could open the quality skill and see a header that looked fine, while every strict YAML reader refused it. That block parses now, and the validator says so when the next one does not: a frontmatter block that no strict parser will take is a blocking issue with the parser's line, not a silent pass.

### Phase 15: frontmatter-yaml-validity

The report started on one file. `sk-code-quality/SKILL.md` described the gate as running "after implementation, before verification" in an unquoted value, so a parser read the second colon as the start of a nested mapping. The description is quoted now and reads word for word as it did. The same report asked why nine `SKILL.md` files said `author: OpenCode`: nothing reads that field, it was not true, and the header is down to the fields a tool reads.

Scanning the rest of the tree is what made this a phase rather than a one-line fix. A strict parse of every tracked `.skilled` block rejected 29 files: 28 live blocks and the one deliberate fixture. Of the 28, 24 held an unquoted value with `: ` in it, three template assets carried a `{{...}}` placeholder a parser read as a flow mapping, and one playbook file kept its `version:` line inside a list. All 28 are repaired without rewording a value.

## How It Was Delivered

The scan and the validator were reproduced before anything was edited: 29 rejected blocks at `65bafca332`, and `"total_issues": 0` from the base validator on the file that started it. The repairs were made from the scan's own list, then every repaired block was compared key by key against its base version with the added quotes stripped, which printed no changed value and no moved body text. The check came next, run against the base version of the quality file to show one blocking issue and against the repaired file to show none. Both test files ran under both interpreters, then the whole sk-doc suite, the five hubs' parent-skill check, the compiled-route guard and sync, and this packet's own strict validation.

<!-- ANCHOR:decisions -->
## Key Decisions

| Decision | Why |
|----------|-----|
| Quote the value instead of rewording it | The description is the text the advisory router scores, and the block only needed the colon to stay inside a string |
| Put the parse in the validator rather than in a new script | Every document already passes through the validator, so one call covers each document type it knows |
| A line check where PyYAML is missing | The Homebrew interpreter has no PyYAML and the gate cannot depend on installing one; the fallback catches the one shape a strict parser rejects and a key reader misses |
| Exclude the fixture by name, and assert the exclusion still fails | A silent exclusion hides a real regression later; the second test makes the name expire by itself |
| Remove the author line rather than fill it in | Nothing reads it, and a true value would need keeping true; the header now states only what a tool reads |

<!-- ANCHOR:limitations -->
## Known Limitations

1. **`quick_validate.py` still reads frontmatter with regexes.** The strict parse lives in `validate_document.py`, and the fleet test is what covers every tracked `.skilled` file whichever checker runs. A document validated only with the regex reader elsewhere can still carry a block no parser takes.
2. **The setup battery's drift-guards leg fails on one path this branch does not touch.** `sk-code-review/scripts/README.md:43` points at `../shared/scripts/check-rule-overrides.cjs`, which does not resolve from that folder. The sibling docs-alignment child on `origin/main` rewrites it to `../../shared/...`, so the leg clears when this branch rebases; the other eight legs pass.
3. **The `author: OpenCode` text survives inside old changelog entries and archived logs.** Those record what was written at the time. No live header carries the field.

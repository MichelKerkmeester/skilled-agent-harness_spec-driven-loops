## What Was Built

A gate that dispatches the review agent no longer fails a change on a score below 70 when it has no blocking finding. The agent now applies the review mode's own rules and lets severity alone decide, every workflow that dispatches a review marks the prompt the way the mode promised, and the report checkers catch an agent report that contradicts itself.

### The Review Agent Follows the Mode

`@review` drops its own checklist and every house rule it carried: conventional commits, no merge commits, under 500 lines, cyclomatic below 10 and the browser-only checks. Its section 6 points at the mode's floor, default lens, checklists and `Rule sources:` line instead, and PR and commit rules come from what the reviewed repository declares, such as its sk-git rule files or its contributing guide. A verdict table derives `REQUESTED_CHANGES` and a failed gate from any P0 or open P1, and the 100-point score is advisory. Every report format uses the mode's three status values. The P0 hint follows the reach rule, the gate is the Review Gate Protocol, and skill files are named the way `@code` names them, by their place in the installed skill. `@deep-review` gets the same path pattern.

### Dispatchers, Checkers and Canary

`@orchestrate` adds the `CODE-REVIEW` marker to a code review dispatch, never to a deep-loop one, and reads `@code`'s `Quality Gate` field with one action per runner verdict. The `/speckit:implement` and `/speckit:complete` review entries carry a `dispatch_prompt` block that states the same marker for any step that dispatches `@review`, with a comment that the entry dispatches nothing, and a `verdict` line that says the gate follows severity. The mode's floor now says a dispatcher adds the marker.

`check-review-final-line.js` compares a `Recommendation:` line with the status line when its whole value is one status token or an older `APPROVE`, `REQUEST CHANGES` or `BLOCK` token, and validates a `Rule sources:` line when one is present, with the rule id grammar imported from the shared linter. `check-review-findings.js` fails a `Recommendation:` or a final status that approves or comments over a P0 or P1 finding, or requests changes with none. `check-rule-copies.js --mode-only` checks only the skill's own pins, names the skipped `AGENTS.md` checks on a `SKIPPED:` line and resolves the skill from the folder the script ships in.

## How It Was Delivered

The canary suite, the mirror gates and the speckit contract suites were baselined first, and the CI canary step was read so it stays on the full mode. The checkers and the canary changed first, with their cases. The agents, YAMLs and mode docs followed, then the mirrors were regenerated, the deep-review contract recompiled and Hermes resynced. Every new case was then run against `git archive HEAD` copies with only the new tests and fixtures copied in: the canary suite failed its 28 new failure cases and the dispatch contract test failed 5 of 5. A first review round asked for six fixes, all applied: the system-spec-kit version above origin/main, the shared id grammar, the stricter Recommendation reading, the status-line severity rule, the speckit wording and the P0 hint. Every suite that reads a touched file was rerun from the final state.

<!-- ANCHOR:decisions -->
## Key Decisions

| Decision | Why |
|----------|-----|
| `COMMENTED` passes the gate, and P2-only reviews may be `APPROVED` or `COMMENTED` | The mode treats `COMMENTED` as no new blocking findings, so only a P0 or an open P1 maps to `REQUESTED_CHANGES` and FAIL |
| The findings checker also fails `REQUESTED_CHANGES` over P2 findings alone | That is the score-only block the plan's verdict rule removes, and the mode says a P2 never blocks |
| The severity comparison runs only when the report has a `## Findings` section | A report in another shape has nothing to compare, and failing it would break reports the brief keeps passing |
| A `Recommendation:` is a verdict only when its whole value is a status token, or a legacy token followed by the end of the line or a comma, wherever it sits | A section skip let the Focused File Review shape's verdict through, and a loose prefix match read prose like "approve the migration after the fix" as approval |
| The findings checker skips the "requests changes with no P0 or P1" rule when a finding sits outside any severity group | That finding's severity is unknown and may be the blocker |
| Older `APPROVE`, `REQUEST CHANGES` and `BLOCK` tokens are mapped, not refused | Reports written before this change still get compared instead of slipping past |
| The `Rule sources:` check imports `RULE_ID` from the shared linter, which now exports it | One grammar for every reader. The hub gets its own changelog entry for the export |
| The PR rules cite sk-git's `.sk-git/` or `skgit.contractDir`, the contributing guide and the PR template, with the declared severity or P2 | sk-git's SKILL.md says each repository supplies its own rule copies there and an undeclared rule is not checked |
| `--mode-only` without `--root` reads the skill from the script's own folder | In another repository the skill is installed somewhere other than `.skilled/skills/sk-code`, so resolving against the working directory would find nothing |
| The marker and Quality Gate test lives in `.opencode/plugins/tests/` | CI runs that folder's `*.test.cjs`, and the speckit goal-offer contract test already pins speckit YAMLs from there |
| The speckit review entries state the marker but gain no dispatch | `agent_availability` says it is not instructions, and a dispatch would change workflow behavior beyond the approved plan |
| `@deep-review` changes logged in the deep-review mode, `@orchestrate` and the YAMLs in system-spec-kit | The last `@review` and `@deep-review` changes were logged in the owning mode's changelog, as the brief asked to follow |
| The deep-review compiled contract was recompiled | It records a digest of the agent and the mode's `SKILL.md`, so the deep-loop runtime job would refuse it as stale |
| Pre-existing em dashes left in lines this child did not write | Rewording 49 lines of `orchestrate.md` and the YAMLs falls outside the findings, and one quotes an AGENTS.md rule verbatim. No line this child wrote carries one |
| Brief item 4 done here although the plan lists it under child 009 | The brief assigns it to this child. Child 009 finds it done |

<!-- ANCHOR:limitations -->
## Known Limitations

1. **The checkers compare lines, not behavior.** A report can still state a verdict its evidence does not support, as long as its lines agree. Proving the agent's verdict against real code stays with the playbook scenarios.
2. **The review README and playbooks still describe the old agent in places.** Child 010 aligns them.
3. **The `/speckit:implement` dashboard still prints `pass`.** Child 009 owns that value.

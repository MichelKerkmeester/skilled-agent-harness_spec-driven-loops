RANK 11 — the compiled sk-code matcher and "x-y" vs "x y"
================================================================================
Investigator: @deep-research (LEAF, read-only). Run 2026-11-03T~12:33Z,
node v26.8.2, darwin. No repository file was edited: the probe compiles into
memory and writes only its own stdout.

SUSPICION UNDER TEST
  The sk-code hub picks a mode from hub-router.json aliases with a matcher that
  treats "x-y" and "x y" differently.

RESULT IN ONE LINE
  CONFIRMED. The matcher is a literal lowercased substring test
  (`canary-router.cjs` `containsSignal`), so "widget panel" matches
  "widget panel layout bug" and never "widget-panel layout bug", and the reverse
  for a hyphenated keyword. Compiling one extra alias into the registry alone
  changes nothing; the alias only reaches the router when it is mirrored into a
  hub-router vocabularyClasses keyword list, which is the list the matcher reads.

2. WHERE THE VOCABULARY COMES FROM
--------------------------------------------------------------------------------
  .skilled/bin/lib/compiled-routing/009-parent-hub-rollout/001-sk-code/lib/registry-compiler.cjs:228-236
    function modeVocabulary(hubRouter, workflowMode) {
      const signal = hubRouter.routerSignals[workflowMode];
      const words = new Set();
      for (const className of signal.classes || []) {
        const vocabulary = hubRouter.vocabularyClasses[className];
        for (const keyword of (vocabulary && vocabulary.keywords) || []) {
          words.add(String(keyword).toLowerCase());
        }
      }
      return [...words].sort(compareText);
    }

  So the live router scores only `hub-router.json`'s vocabularyClasses keywords
  for the mode's routerSignals classes. `mode-registry.json`'s `aliases` array
  feeds the generic detector projection (`registry-compiler.cjs:114` inside
  `vocabularyByMode`, and the alias detectors at :170) but not this
  `routingModel`. sk-code duplicates its aliases into the matching
  `*-aliases` vocabulary class, which is why the shipped router can route on
  them at all.

6. WHAT THE OUTPUT SHOWS, AND WHAT IT DOES NOT
--------------------------------------------------------------------------------
  Confirmed: the hyphen and the space are different signals to the shipped
  matcher, verified by C and D on the live scoring path, with the exact keyword
  lists printed before each route.
  Confirmed: adding the alias only to mode-registry.json (variant B) leaves the
  route identical to baseline — the alias never reaches this router's keyword
  list. So "the hub picks a mode from hub-router.json aliases" is only true when
  the alias is mirrored into a vocabularyClasses keyword list; the routing model
  reads keywords, not the registry's aliases array.
  Not tested here: whether some generator keeps those two lists in sync, and
  whether a hyphenating normaliser was intended. The runs say nothing about
  intent.

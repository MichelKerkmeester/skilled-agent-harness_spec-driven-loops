## 1. SUMMARY

### Technical Context

| Aspect | Value |
|--------|-------|
| **Language/Stack** | Markdown + JSON skill metadata; Node 20 `.cjs` gates; Python 3 generators |
| **Framework** | `sk-code` parent-hub routing: `mode-registry.json` + `hub-router.json` + `ROUTER.md` + `leaf-manifest.json` + a compiled policy |
| **Storage** | None |
| **Testing** | Repository gates: `parent-skill-check.cjs`, the `ci-*` freshness trio, `compiled-route-guard.cjs`, `validate.sh --strict`, link integrity, playbook validation, `sk-doc` pytest baselines |

### Overview

The hub drops one surface mode in reverse of the documented nested-packet order, so both
routing stages stay consistent: stage one (the advisor, reading the hub's `graph-metadata.json`)
loses the mode's vocabulary, and stage two (`hub-router.json` + `ROUTER.md`) loses its intent
key, resource entries and signals. Every derived artifact is then regenerated by the generator
that owns it rather than hand-edited, and the compiled-routing closure is re-minted and checked,
because only `SKILL.md`, `hub-router.json` and `mode-registry.json` change the compiled policy
hash while the manifest's authority, hash and generation must still match the live policy.

## 3. ARCHITECTURE

### Pattern

**De-registration in reverse of the documented registration order** (`parent-skills-nested-packets.md` §7).
The removed mode is `routingClass: "metadata"`: it has no advisor entry of its own, and its
vocabulary reached the advisor only through the hub's `graph-metadata.json` projection, which is
why stage one needs the derived block regenerated and stage two needs the intent key removed.

### Key Components
- **Authored routing inputs**: `SKILL.md`, `mode-registry.json`, `hub-router.json` — the only three files whose edit moves the compiled policy hash.
- **Authored documentation surface**: `ROUTER.md`, `graph-metadata.json`, `description.json`, `shared/references/stack-detection.md`, changelogs.
- **Derived artifacts and their generators**: `leaf-manifest.json`, the hub derived block, `skill-graph.json`, the trigger index and its fixtures, the `sk-doc` test baselines, the canary fixtures, the `compiled/` policy artifacts, the activation manifest.
- **Consumers**: the sibling `sk-code-obsidian` packet, `sk-doc` references and tests, the hub's own manual-testing-playbook, and the root `README.md`.

### Data Flow

A request reaches the hub in two stages: the advisor selects the hub from
`graph-metadata.json`, then `hub-router.json` and `ROUTER.md` pick the mode and its leaves. The
compiled resolver short-circuits stage two only while the activation manifest's serving
authority is `compiled` and its recorded hash and generation still match the live policy;
otherwise it silently falls back to the prose router. That fallback is why the re-mint is a
required step and not a nicety.

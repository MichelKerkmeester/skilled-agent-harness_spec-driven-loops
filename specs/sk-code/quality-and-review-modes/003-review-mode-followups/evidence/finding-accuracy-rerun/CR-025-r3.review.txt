## Findings

### P0 - Critical

1. [fixtures/users.js:5] SQL injection via string concatenation of an unescaped parameter
   - Case: a caller passes `findUserByEmail("x' OR '1'='1")` and the executed statement becomes `SELECT id, email, role FROM users WHERE email = 'x' OR '1'='1'`; the `WHERE` clause is always true, so the function returns the first row in `users` — typically the oldest account — instead of the row matching `x`. Passing `findUserByEmail("' OR role='admin' --")` selects an attacker-chosen row outright.
   - Risk: no workload assumption needed; the statement changes shape on the first crafted input, not after any scale threshold.
   - User impact: the exported lookup at `fixtures/users.js:10` is the identity path its name advertises, and its output is a `role` column. Any consumer that treats the returned row as "the account that owns this email" can be steered to a different account, which is an authentication/authorization bypass for the caller, not merely a data read. Deferring the fix also leaves the raw payload reachable if the query error text ever surfaces, because a syntax error from a crafted value echoes it to the caller.
   - Finding class: class-of-bug
   - Scope proof: `rg -n "SELECT|db\.query|\$\{|escaped|prepare"` over `fa-run/` returns only `fixtures/users.js:5` and `:6`, so this tree holds no second construction site; that inventory covers 3 scratchpad fixtures only and does not prove the wider codebase clean, so the class stays `class-of-bug` rather than `instance-only`. The finding survives any behavior of `./db`: once the payload is concatenated into the string, the value and the SQL are indistinguishable, so escaping at a lower layer cannot recover the boundary — the interpolation point is the only place it can be fixed.
   - affectedSurfaceHints: ["email lookup query", "db.query caller", "account identity resolution"]
   - riskScore: 9 (advisory only)
   - Recommended fix: build the statement with a bound parameter and pass `email` in the values array, in whatever form `db.query` supports (positional `?`/`$1` or a named-parameter object); confirm that capability against `./db` before writing the call, since its contract was outside this review. Keep the existing narrow projection (`id, email, role`) — it correctly avoids selecting credential material.

### P2 - Suggestion

2. [fixtures/users.js:5-7] Duplicate-email ambiguity is resolved silently and non-deterministically
   - Case: two rows in `users` carry the same `email`; the query has no `LIMIT` and no `ORDER BY`, so `return rows[0] || null` at `:7` hands the caller whichever row the storage engine happens to emit first, and the second account is unreachable through this function.
   - Risk: two-row case only; no performance dimension.
   - User impact: a caller that resolves identity through this function can act on one of two accounts with no signal that the ambiguity exists. The impact is real but the precondition is unproven — it depends on `users.email` lacking a unique index, and the schema lives in the out-of-scope `./db`, so this is hardening, not a demonstrated defect.
   - Finding class: instance-only
   - Scope proof: the single query at `:5` is the only row-selection site in this tree (`rg` above), and the fix is one statement plus one stated assumption.
   - Recommended fix: state the assumption the code already relies on — either reference the unique index on `users.email`, or add an explicit `ORDER BY id` with a comment recording that the first match is the intended semantic. Prefer documenting the constraint over adding a `LIMIT 1`, which hides the ambiguity instead of resolving it.

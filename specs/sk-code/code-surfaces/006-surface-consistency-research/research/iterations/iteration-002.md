### Scaffold ownership and shape

Put the surface scaffold under .skilled/skills/sk-code/shared/assets/surface-scaffold/. The sk-doc canon defines a surface as a read-only, advisor-invisible evidence packet and specifies its direct-child layout, but hub-skill-scaffold.md creates an entire routing hub and packet-skill-scaffold.md creates a primary workflow packet. Neither supplies the sk-code surface contract. Extending sk-create-skill would make sense only if a second hub needs the same specialized surface scaffold. [SOURCE: .skilled/skills/sk-doc/sk-create-skill/references/parent-skill/parent-skills-nested-packets.md:44-61] [SOURCE: .skilled/skills/sk-doc/sk-create-skill/assets/parent-skill/scaffold/hub-skill-scaffold.md:14-24] [SOURCE: .skilled/skills/sk-doc/sk-create-skill/assets/parent-skill/scaffold/packet-skill-scaffold.md:8-24]

Include a template SKILL.md with the surface frontmatter, WHEN THE HUB BUNDLES THIS, REFERENCE MAP, SMART ROUTING §2b, SURFACE STANDARDS, optional surface-specific sections and ASSETS last. Add a README template, a domain-first references tree example, a changelog/version pair, an assets/checklists/ home, and instructions to link the three shared workflow references. Keep shared/, scripts/ and benchmark/ optional. Include a registration checklist covering the registry, stage-one router, hub catalog, child and parent resource maps, generated leaf and compiled manifests, both detection references, the advisor hint, parent-check exception, router-sync inventories, playbooks and Hermes mirror. These fields cross Markdown and generated JSON, so a checklist is smaller and easier to review than a script that rewrites every surface.

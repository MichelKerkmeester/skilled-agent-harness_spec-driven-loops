## Findings

**f-iter004-001 — The three qualifiers are prose policy; no metadata field or validator records the artifact, so catch-all composition and artifact drift cannot be detected mechanically.** The rule requires same artifact, same track and a different change, and the parent `spec.md` must name the artifact and the closing condition. [SOURCE: .skilled/skills/system-spec-kit/references/structure/phase-definitions.md:70] [SOURCE: .skilled/skills/system-spec-kit/references/structure/phase-definitions.md:72] [SOURCE: .skilled/skills/system-spec-kit/references/structure/phase-definitions.md:76] The graph-metadata contract records lineage (`parent_id`, `children_ids`), typed manual relationships (`depends_on`, `supersedes`, `related_to`) and migration flags, but nothing names an artifact, series scope or closing condition. [SOURCE: .skilled/skills/system-spec-kit/runtime/lib/graph/graph-metadata-schema.ts:131] [SOURCE: .skilled/skills/system-spec-kit/runtime/lib/graph/graph-metadata-schema.ts:146] [SOURCE: .skilled/skills/system-spec-kit/runtime/lib/graph/graph-metadata-schema.ts:149] Parent content discipline is explicitly "a template convention, not a validated rule", and phase parents skip Level-N structural contracts entirely. [SOURCE: .skilled/skills/system-spec-kit/references/validation/template-compliance-contract.md:236] [SOURCE: .skilled/skills/system-spec-kit/references/validation/template-compliance-contract.md:238] The artifact slug in the parent folder name is the only artifact signal that exists, and it is not machine-compared against children.

**f-iter004-002 — The only anti-catch-all signal is a child-count advisory, and nothing consumes it.** `assessPhaseParentHealth()` returns `warning` at >=20 children and `error` at >=40, with the source comment stating buckets are advisory and "callers decide whether to fail validation or merely report"; the library README repeats that it flags sprawl "without failing validation by itself". [SOURCE: .skilled/skills/system-spec-kit/runtime/lib/spec/is-phase-parent.ts:60] [SOURCE: .skilled/skills/system-spec-kit/runtime/lib/spec/is-phase-parent.ts:69] [SOURCE: .skilled/skills/system-spec-kit/runtime/lib/spec/is-phase-parent.ts:145] [SOURCE: .skilled/skills/system-spec-kit/runtime/lib/spec/README.md:22] A non-test grep for `assessPhaseParentHealth` and its threshold constants found no production caller — only the README and a retrieval fixture. Consequence: a series parent holding up to 19 unrelated children is indistinguishable from a healthy one, and even the 40-child error changes nothing unless a caller is wired in. This is the concrete answer to "can it become a catch-all bucket": yes, silently, for the whole range below the first threshold, and unimpeded above it.

**f-iter004-003 — Cross-track grouping is structurally suppressed but the documented move-in path leaves no provenance trace.** Children are physically nested inside the parent folder, so same-track is enforced by construction when work is added as a new child. [SOURCE: .skilled/skills/system-spec-kit/references/structure/phase-definitions.md:73] The recipe for converting an existing packet, however, is `git mv` into the parent plus identity repointing (`specFolder`, `specId`, `parentChain`, `parent_id`, implementation-summary row) with no field recording which track the packet came from. [SOURCE: .skilled/skills/system-spec-kit/references/structure/phase-definitions.md:78] The schema's `migrated` / `migration_source: 'legacy'` exist for legacy imports, not for cross-track moves; nothing downstream can tell the difference between a same-track move and a cross-track capture. [SOURCE: .skilled/skills/system-spec-kit/runtime/lib/graph/graph-metadata-schema.ts:147] Guardrail need: record the pre-move track (or require the series-creation path to assert same-track) at the moment of the move.

**f-iter004-004 — Correction-vs-new-change has no mechanical anchor.** The rule is explicit that a correction continues the existing packet with Option A even when it is complete, and that a different change is what opens a series child. [SOURCE: .skilled/skills/system-spec-kit/references/structure/phase-definitions.md:74] In metadata, `manual.supersedes` and `manual.related_to` are shape-validated references (structured object with reason/source), but nothing requires a correction to be represented as a reopen or a supersedes link, so a correction filed as a new child is schema-legal and invisible. [SOURCE: .skilled/skills/system-spec-kit/runtime/lib/graph/graph-metadata-schema.ts:177] The only steering is behavioral and post-hoc: the create.sh lister nudges toward joining a matching packet after the folder decision, and Gate 3 presents C before B. [SOURCE: .skilled/skills/system-spec-kit/runtime/cli/spec/create.sh:1076] [SOURCE: .skilled/skills/system-spec-kit/runtime/cli/spec/create.sh:1115] Guardrail need: a create-time check that a same-artifact complete sibling recommends Option A, recorded as a relationship when a new child is still justified.

**f-iter004-005 — Existing parent-integrity flags guard linkage correctness, not grouping correctness.** `parent_id_review_required` fires only when a re-derive would have dropped a non-null parent — a re-parenting artifact, not a judgment that the parent is right. [SOURCE: .skilled/skills/system-spec-kit/runtime/lib/graph/graph-metadata-schema.ts:136] `children_ids` pruning detects only entries that no longer resolve to a folder on disk. [SOURCE: .skilled/skills/system-spec-kit/runtime/lib/graph/graph-metadata-parser.ts:1596] Neither checks whether a linked child shares the parent's artifact, whether a child drifted from the parent's documented scope, or whether a correction was misrouted as a new child. The validator's phase-parent mode is likewise structural: it recognizes the folder shape and skips Level-N expectations. [SOURCE: .skilled/skills/system-spec-kit/references/validation/validation-rules.md:189]

**f-iter004-006 — A minimal guardrail package can sit on surfaces that already exist, warn-only and operator-kept.** (1) Record the series artifact and closing condition at creation: series parents are created through `create.sh --phase` / `--parent`, and phase mode already has flag plumbing, so an artifact input can land in the parent's spec.md and an optional typed metadata field without new architecture. [SOURCE: .skilled/skills/system-spec-kit/runtime/cli/spec/create.sh:183] [SOURCE: .skilled/skills/system-spec-kit/runtime/cli/spec/create.sh:217] (2) Add a warn-only validator advisory comparing child trigger phrases / `description.json` topic text against the recorded artifact, registered like the existing advisory class rather than as a failing rule. [SOURCE: .skilled/skills/system-spec-kit/runtime/lib/spec/README.md:22] (3) Surface `assessPhaseParentHealth` in validate output — the function is ready and currently unconsumed. (4) At create time, when a complete same-artifact packet exists, recommend Option A for corrections and record `related_to`/`supersedes` when a new child is genuinely a different change. Every item recommends, none auto-selects, consistent with the existing "recommend, never decide" invariant [SOURCE: .skilled/skills/system-spec-kit/references/structure/phase-definitions.md:88].

## Questions Answered

- **Q4:** Can the series parent rule be gamed into a catch-all bucket or misapplied (a correction treated as a new change, cross-track grouping, artifact drift), and what guardrails in validators or metadata would prevent that? — Answered. Gameability verdict per vector: **catch-all bucket** — yes, silently; the only signal is a child-count advisory that no production code consumes, so up to 19 unrelated children pass with zero diagnostics (f-iter004-002); **artifact drift** — undetectable; no field or check records the artifact the series is for (f-iter004-001); **cross-track grouping** — suppressed for new children by nesting, but a moved-in packet leaves no provenance and the schema only tracks legacy migration (f-iter004-003); **correction-as-new-change** — schema-legal and invisible; no reopen/supersedes requirement ties a correction to its packet (f-iter004-004). Existing parent flags guard linkage, not grouping (f-iter004-005). The proposed guardrail package is warn-only and sits on existing surfaces: record the artifact at creation, advisory child-vs-artifact comparison, surface the health advisory, and a create-time correction check that recommends Option A (f-iter004-006).

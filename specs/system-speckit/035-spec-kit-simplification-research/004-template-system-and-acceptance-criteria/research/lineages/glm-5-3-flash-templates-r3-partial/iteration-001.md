## Findings (3: 1×P1, 2×P2)

### f-iter001-001 [P1] — The phase parent's rule-required description.json hangs on the untracked dist build
- CLAIM (`check-files.sh:41-48,55,57`): in the phase-parent branch, a missing `$folder/description.json` is unconditional *missing* — severity **error** ("Phase parent: missing N required file(s): description.json").
- ACTUAL (`create.sh:1426-1434`, children 1466-1475): the parent's description.json is written only when `APPEND_TO_EXISTING_PARENT != true` **and** `$SCRIPT_DIR/../dist/spec-folder/generate-description.js` exists; either miss → one stderr warning ("description.json generation skipped", 1432) and the scaffold still succeeds. The mirrored plain-path block (1690-1698) has the same dependency, but there the rule never demands the file (check-files.sh:82-86 numbered branch — no description.json) — requirement and guarantee diverge in exactly one place: the phase-parent branch.
- CONSEQUENCE: in this worktree the untouched `--phase` scaffold passes (the dist generator **exists here**: 6,743 B, Sep 7 09:09 — confirmed by read), but dist/ is untracked and charter-stale; in any checkout without that build, every fresh `--phase` parent silently skips the one file its own FILE_EXISTS rule calls an error, and the scaffolder's own comment rates failure "non-fatal" (1420-1421, in-code note "known gap (F10)" — a code note, not a census row).
- SEVERITY: P1 (wrong-or-unused: the scaffolder's only non-fatal failure mode is the exactly-one artifact the harshest presence rule demands; the failure surfaces later, as a validation error on an untouched scaffold).
- RECOMMENDATION: fix — write a bash-minimal description.json fallback (the pattern exists 30 lines away: `create_graph_metadata_file`, create.sh:513-588), or make the generator tracked/checked-in so `-f` cannot silentlymiss.

### f-iter001-002 [P2] — The phase-parent spec's provenance marker is indistinguishable from a plain spec.md's
- CLAIM (`check-template-source.sh:86-92`): the TEMPLATE_SOURCE marker "proves files were created from official templates" — the rule's own remediation example sells the slug as composition-specific ("spec-core + level2-verify + level3-arch + level3-plus-govern | v2.2", line 90).
- ACTUAL (`packet-types/phase-parent.spec.md.tmpl:28` vs `core/spec.md.tmpl:36`): both stamp literally `<!-- SPECKIT_TEMPLATE_SOURCE: spec-core | v2.2 -->` — the lean phase-parent spec self-identifies as a plain core spec; nothing downstream distinguishes them (the `[YOUR_VALUE_HERE: …]` substitution passes the marker line untouched, create.sh:1303-1304; `ensure_template_source_near_top` re-anchors but never rewrites the slug, 590-615; `finalize_scaffold_templates` never runs on the phase parent at all — its only call sites are 769/970/1480/1682).
- CONSEQUENCE: every other sampled template has a 1:1 slug (`acceptance-criteria | v2.2` at addons/acceptance-criteria.md.tmpl:31, `goal | v2.2` :31, `decision-record | v2.2` :31, `impl-summary-core` core/implementation-summary.md.tmpl:79, `plan-core` :42, `tasks-core` :38) — only the phase-parent variant shares its provenance identity with another template, so provenance-proving is weaker exactly where the template diverges most from its base.
- SEVERITY: P2 (cosmetic: the rule checks presence, not the slug; but the marker's stated purpose — proving *which* official template — is defeated for this packet type).
- RECOMMENDATION: fix (distinct slug, e.g. `phase-parent-spec`) or document that the slug names the family, not the file — after open question 4 settles what the parity test pins.

### f-iter001-003 [P2] — Phase children ship a graph-metadata stub the plain path's own comment says would "fail validation the moment it exists"
- CLAIM (`create.sh:1700-1703`): the plain path's in-code justification for its 1704-1708 backfill — "Derive the graph metadata from the documents that were just written, rather than leaving the stub the scaffolder guessed. A scaffold that disagrees with its own deriver fails validation the moment it exists, which teaches an author that the gate is broken before they have written a line."
- ACTUAL (`create.sh:1449` vs `1456-1463`, and `513-588`): the phase-children loop writes each child's graph-metadata.json **before** any child document exists (1449 precedes the 1452-1463 copies), so the stub's own elif chain (552-558: `-f spec.md && ! -f plan.md …`, `-f decision-record.md`) can never select anything but the 550-551 default `[spec.md, plan.md, tasks.md]` — at child levels 2/3 the just-scaffolded child then also holds implementation-summary.md (lifecycle, 451+428-442) and acceptance-criteria.md (optional-list, 455-457; L2 row 517-518) that the stub's `key_files`/`source_docs` never mention, and no backfill runs anywhere in 1436-1532 (1704-1708 belongs to the plain path; the phase flow exits at 1620). The same write-before-copies ordering exists on the `--subfolder` path (499 inside `create_versioned_subfolder`, copies at 962-969) — noted here because the defect's mechanism is the children's, which is in this angle's scope.
- CONSEQUENCE: for `--level 2|3 --phase` the scaffold's stub demonstrably disagrees with its own just-written documents — the exact condition the plain path's comment says it eliminates; whether any check enforces the disagreement is native-land (the two rules here only test existence: `check-files.sh:47-48`), so the finding is the inconsistency, not a proven validation failure.
- SEVERITY: P2 (cosmetic in impact today — the bash rules test presence only — wrong in principle under the file's own stated invariant).
- RECOMMENDATION: fix — run the 1704-1708-style backfill for phase children (or move the 1449 stub after the 1456-1463 copies); alternatively weaken the 1700-1703 comment to what actually holds.

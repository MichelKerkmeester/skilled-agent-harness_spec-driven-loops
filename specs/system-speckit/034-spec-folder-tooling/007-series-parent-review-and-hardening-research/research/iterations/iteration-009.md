## Findings

**f-iter009-001 (P2). The ~12 absent-carrier bound is refuted by the generator's own build: the template-phrase owner set is exactly in sync with the frozen index, and the drift is manifest-level, not phrase-level.** A live `buildIndex` over the current corpus (23,798 documents scanned, 13,465 indexed paths, 34,179 unique phrases, 0 malformed documents) yields exactly **199 owners for `feature specification`**; the committed artifact holds exactly **199** as well, and the set differences are empty in both directions. The iteration-8 estimate (207 spec.md carriers vs 199 postings [SOURCE: specs/system-speckit/034-spec-folder-tooling/007-series-parent-review-and-hardening-research/research/iterations/iteration-008.md:35]) compared an rg line-pattern count against an index owner set — two different measurement surfaces; the same rg count under a strict anchored pattern is 196, none of which changes the owner-set verdict. What is actually stale is the manifest: the live `manifestHash` differs from the committed `db7a86ec…`, indexed paths grew 13,460 → 13,465 and unique phrases 34,176 → 34,179 since the 2026-10-06 freeze, while every template-phrase owner still matches. The regeneration-cadence defect [SOURCE: specs/system-speckit/034-spec-folder-tooling/007-series-parent-review-and-hardening-research/research/iterations/iteration-008.md:35] is real, but its specific "absent carriers" symptom was a measurement artifact; the backfill recommendation is unaffected because it removes placeholder postings from personalized packets, a cause independent of staleness. Mechanism: a rebuild is all-or-nothing; `manifestIdentity` folds corpus hash, exclusions, ignored paths, included-path count, schema/parser versions and roots [SOURCE: .skilled/skills/system-spec-kit/runtime/cli/retrieval/generate-trigger-index.mjs:218], and postings are regenerated wholesale [SOURCE: .skilled/skills/system-spec-kit/runtime/cli/retrieval/generate-trigger-index.mjs:240]; the only in-tree freshness check is the builder's `--check` comparison [SOURCE: .skilled/changelog/skilled/v4.0.0.3.md:299].

**f-iter009-002 (P2). A Gate 1 scope is pin-safe but not "simply adopted": the byte pins are Gate 3 surfaces, yet 20+ invocation copies and the gate ordering make unconditional scoping both a multi-surface change and semantically wrong for the first-write decision.** The byte-length receipt and frozen delivery baseline [SOURCE: specs/system-speckit/034-spec-folder-tooling/007-series-parent-review-and-hardening-research/research/iterations/iteration-001.md:36] and the frozen `GATE_3_QUESTION` arrays [SOURCE: specs/system-speckit/034-spec-folder-tooling/007-series-parent-review-and-hardening-research/research/iterations/iteration-003.md:24] constrain the Gate 3 question, not the Gate 1 lookup; the repo-wide sweep found no test pinning the lookup invocation text, and only AGENTS.md's copy carries `--scoring-only`. Mechanically the `--spec-folder` flag exists and is exercised, so no pin is violated by adding it — but three blockers stand against treating adoption as cheap: (i) the invocation is duplicated across 20+ documented sites — AGENTS.md, both SKILL.md copies, CONTRIBUTING, speckit command YAMLs, doctor routes, five agent definitions, READMEs and playbooks — so changing the default is a coordinated doc sweep with the same drift class as f-iter003-001; (ii) Gate 1 runs before Gate 3 [SOURCE: AGENTS.md:51], so for new work there is no folder to scope to, and for a bound session scoping to the active packet suppresses the cross-packet sibling evidence the placement decision needs (iteration-8 numbers: unscoped 20 documents vs track-scoped 2 vs packet-scoped 0 [SOURCE: specs/system-speckit/034-spec-folder-tooling/007-series-parent-review-and-hardening-research/research/iterations/iteration-008.md:17]); (iii) scope is a folder-prefix exclusion, so it can never suppress an in-scope self-match (inv-iter008-001 [SOURCE: specs/system-speckit/034-spec-folder-tooling/007-series-parent-review-and-hardening-research/research/iterations/iteration-008.md:25]). Net: scope adoption is a resume/context-relevance device, not a first-write noise fix; f-iter008-001's mitigation survives with those two limits stated.

The fail-loud/advisory-only boundary is drawn in the wrong place by f-iter008-002: inv-iter002-001 governs the lister, and create.sh already fails the scaffold loudly on template-contract drift, so a seeder drift guard may follow that precedent.** inv-iter002-001 is explicitly scoped to `list_recent_track_packets` [SOURCE: specs/system-speckit/034-spec-folder-tooling/007-series-parent-review-and-hardening-research/research/deltas/iter-002.jsonl:9], not to the seeder.

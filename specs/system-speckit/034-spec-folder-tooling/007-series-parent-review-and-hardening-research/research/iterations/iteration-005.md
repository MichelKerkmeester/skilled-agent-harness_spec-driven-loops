## Questions Answered

- **Q5:** How should existing singleton clusters be detected and proposed for retroactive grouping (census tooling, a validator advisory, a proposal step in a speckit command) without noisy false positives or unsafe renumbering? — Answered. Verdict per sub-question: **detection** — there is no artifact key, so a census must rank stand-in signals (description synopsis, keywords, slug, seeded phrases) and can only be high-precision on post-006 packets (f-iter005-001); **proposal step** — a standalone read-only census following the dry-run repair-tool pattern, optionally surfaced from `/speckit:plan`, with the warn-only advisory class as precedent; SessionStart is constrained by its 5-second fail-open contract (f-iter005-004); **false positives** — the outcome-bucket precedent shows vocabulary-overlap proposals will include illegal groupings, so candidates ship with evidence and the operator makes the correction-vs-change call (f-iter005-003); **unsafe renumbering** — retro-grouping renumbers identities; the tools repair derived facts but not relationship lists or inbound references, so a move stays an explicit, operator-run recipe followed by a reference sweep (f-iter005-002).

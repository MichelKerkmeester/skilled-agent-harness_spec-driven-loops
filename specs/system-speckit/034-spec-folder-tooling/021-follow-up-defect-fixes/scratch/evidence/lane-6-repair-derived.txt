Round 2: re-derive child reads through planted links (measurement, then refusal)

Recorder
- The recorder is a CommonJS module loaded through NODE_OPTIONS, so the tool and every node process it starts load it, including the re-derive child.
- Each process writes its own record on exit: the path as given, the real path it resolves to, and the first call-stack frames.
- Only the tool process plants. The fixture is a packet with valid spec.md, plan.md and tasks.md, a stale implementation-summary.md, and description.json at level 1 while spec.md declares level 2.
- The plant fires after the third read of description.json, which is the apply read after both planning reads. At that point spec.md, plan.md and tasks.md become links to outside files.

Measurement (code before the guard, log S/L6/measure/run1.txt, summary S/L6/measure/run1-summary.json)
- The re-derive child (backfill-graph-metadata.ts) opened all three planted links, 12 reads in total.
- Each pass reads spec.md, plan.md and tasks.md through readDoc (graph-metadata-parser.ts line 507, from collectPacketDocs), then through computeSourceDocHashes (generated-metadata-drift.ts line 101, from deriveGraphMetadata). There are two passes.
- No other process opened an outside file. The tool process opened none after the plant, and the validator processes ran before the plant.
- Answer to the question: yes, the child reads through a planted link.

Writer check (read only, no change)
- All five writeAtomic call sites (description level, spec folder row, description specFolder, graph parent, packet pointer) sit in apply closures that call readForWrite earlier in the same closure. No other caller exists, so readForWrite runs before every writeAtomic.
- writeAtomic checks the target for a link first, then creates its random exclusive temp file, writes it, reads the target mode with statSync, and renames.
- The statSync therefore follows a link only when the target becomes a link between writeAtomic's own check and the stat call. That window is a race of microseconds, the call returns mode bits only, and the rename replaces the entry without following it.

Fix (repair-derived.cjs, the only source file changed in this round)
- New helper linkedRederiveInputs(folder): returns the top-level .md and .json names of the packet, plus research/research.md, that are links. The list is wider than REWRITE_TARGETS, because the child reads acceptance-criteria.md, goal.md, decision-record.md, research.md and resource-map.md as well. Those names come from the CANONICAL_PACKET_DOCS and SYNOPSIS_SOURCE_DOCS constants in the library, and the measurement covered spec.md, plan.md and tasks.md only.
- Apply: when the re-derive would start, a link among those names is refused. The child is not started, the failure reads "re-derive: <name>: symbolic link, not followed", and the exit is 2.
- The dry run is unchanged, so it still plans the step. That keeps the existing dry-run equality for a live plan.md link.
- Decision for the lead: this refuses rather than silently skipping. A linked graph-metadata.json is skipped silently in the existing code, but there the step is never planned. Here the step is planned and cannot land, which the header rule for exit 2 covers.

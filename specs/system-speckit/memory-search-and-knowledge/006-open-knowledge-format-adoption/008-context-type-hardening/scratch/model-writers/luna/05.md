# Plan a Database Migration

## Purpose

Create a reviewable plan for moving or changing a database while protecting data integrity and keeping service disruption within agreed limits.

## Goals

- Define the migration’s scope, constraints, and success criteria.
- Identify risks to data, availability, performance, and dependent systems.
- Specify preparation, execution, validation, and recovery steps.
- Assign owners and decision points for the migration.

## Non-goals

- Implementing migration scripts or infrastructure changes.
- Assuming a particular database engine, hosting platform, or migration method.
- Treating rollback as possible when the target changes make reversal unsafe or incomplete.

## Inputs

Gather or record:

- Source and target databases, versions, environments, and data volumes.
- Application services, jobs, integrations, and users that depend on the database.
- Availability requirements, acceptable downtime, and migration window.
- Security, privacy, retention, and compliance constraints.
- Existing backups, restore procedures, and operational owners.
- Known schema differences, data quality issues, and compatibility requirements.

Mark unknowns explicitly and identify who will resolve them.

## Planning requirements

1. **Define the migration approach.** Describe the proposed method, sequencing, expected downtime, and any period when both databases or schemas must be supported.
2. **Inventory dependencies.** Identify components that read or write the data, including scheduled jobs and external integrations. Document required changes and deployment order.
3. **Protect the data.** Specify backup or snapshot timing, retention, access controls, and how a restore will be verified. Include data transformation and reconciliation needs.
4. **Plan execution.** List ordered steps for preparation, migration, application cutover, and cleanup. Include estimated durations, owners, prerequisites, and go/no-go checks.
5. **Plan validation.** Define checks for record counts, critical fields, constraints, application behavior, performance, and dependent workflows. State acceptable tolerances.
6. **Plan recovery.** Document rollback or forward-recovery steps, decision thresholds, responsible decision-makers, and the latest safe point for each option. Explain when reversal is not feasible.
7. **Communicate and monitor.** Identify affected stakeholders, required notices, monitoring signals, alert owners, and the observation period after cutover.

## Deliverable

Produce a migration plan containing:

- Scope, assumptions, constraints, and success criteria.
- Chosen approach and alternatives considered.
- Risks, mitigations, dependencies, and unresolved questions.
- A sequenced runbook with owners, timing, and go/no-go checks.
- Backup, validation, recovery, monitoring, and communication plans.

## Acceptance criteria

The plan is ready for review when:

- The migration scope and success criteria are measurable.
- Every critical dependency and data safeguard has an owner.
- Execution steps have prerequisites and a clear order.
- Validation checks can detect incomplete or incorrect migration.
- Recovery actions and decision authority are documented.
- Downtime, risk, and unresolved issues are visible to approvers.

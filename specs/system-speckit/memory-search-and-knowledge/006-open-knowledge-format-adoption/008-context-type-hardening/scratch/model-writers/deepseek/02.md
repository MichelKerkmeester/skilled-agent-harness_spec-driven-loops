# Rename a Config Key

## Overview

A configuration key is misleadingly or inconsistently named. This packet covers renaming it to its intended name everywhere it is read, written, documented, or validated, while ensuring existing configuration files continue to load without error.

## Problem Statement

The current key name does not describe its behavior, which causes confusion and misconfiguration. A naive rename would silently break existing deployments whose config files still use the old key.

## Scope

In scope:
- Define the canonical new key name.
- Update every read/write site of the old key to the new key.
- Continue accepting the old key as a deprecated alias, emitting a warning when it is used.
- Update documentation, examples, and schema/validation definitions.

Out of scope:
- Renaming any other keys, even adjacent ones.
- Changing the key's value type, default, or semantics.
- Removing the deprecated alias (a follow-up packet).

## Requirements

1. The new key name is the single canonical name in code, docs, and examples.
2. Loading a config that uses the old key must succeed and behave identically to the new key.
3. If both keys are present, the new key wins, and a warning is emitted naming the conflict.
4. A deprecation warning is emitted once per process when the old key is used.
5. All schemas, validators, and generated documentation reflect the new key.

## Acceptance Criteria

- [ ] A config file using only the old key loads successfully with a deprecation warning.
- [ ] A config file using only the new key loads with no warning.
- [ ] A config file using both keys resolves to the new key's value and warns about the conflict.
- [ ] No occurrence of the old key remains as a primary reference in code or docs; remaining occurrences are confined to the alias and its tests.
- [ ] Existing test suite passes unchanged.

## Risks and Mitigations

- **Risk:** External tooling references the old key directly. **Mitigation:** keep the alias for at least one release cycle.
- **Risk:** Silent precedence bugs when both keys are present. **Mitigation:** explicit precedence rule plus a warning, covered by an acceptance test.

## Verification

- Run the stack's test suite and linter.
- Manually load representative old-style and new-style config files and confirm behavior and warnings.
- Grep the repository for the old key to confirm only alias, migration, and test references remain.

# Spec: Add Retry Support to Flaky HTTP Client

## 1. Overview

The HTTP client intermittently fails on transient network conditions (connection resets, timeouts, 5xx responses). This packet adds a bounded retry policy with exponential backoff and jitter so callers get consistent behavior without hand-rolling retry loops.

## 2. Problem Statement

Transient failures currently surface as hard errors, forcing each call site to retry ad hoc or fail user-visible operations. There is no shared policy covering which failures are retryable, how many attempts to make, or how long to wait between them.

## 3. Goals

- Retry transient failures automatically with bounded attempts and exponential backoff plus jitter.
- Retry only idempotent requests by default (GET, HEAD, PUT, DELETE, OPTIONS), with explicit opt-in otherwise.
- Honor server `Retry-After` when present, within a total time budget.
- Make the policy configurable per client instance with safe defaults.
- Keep observability: one log/metric per attempt.

## 4. Non-Goals

- Circuit breaking, bulkheads, or a full resilience framework.
- Retrying non-idempotent requests (POST/PATCH) by default.
- Changing timeouts, connection pooling, or the transport implementation.
- Request hedging or speculative duplication.

## 5. Requirements

### Functional

- FR-1: Retry on connection errors, timeouts, and 5xx responses.
- FR-2: Defaults: max 3 attempts, exponential backoff base 100 ms, cap 2 s, full jitter.
- FR-3: Never retry 4xx responses except 408 and 429.
- FR-4: Requests whose body cannot be replayed are not retried unless the body is explicitly rewindable.
- FR-5: Respect `Retry-After` for 429/503, clamped to the total deadline.
- FR-6: Allow per-client configuration of max attempts, backoff parameters, and retryable status codes.
- FR-7: Abort the retry loop when a retry would exceed the configured total deadline.

### Non-Functional

- NFR-1: No added latency or allocations on the first-attempt success path.
- NFR-2: Backoff is jittered to avoid synchronized retry storms.
- NFR-3: No shared mutable retry state between concurrent requests.

## 6. Acceptance Criteria

- AC-1: With default policy, a stubbed connection reset is retried and succeeds on the second attempt.
- AC-2: A 500 response is retried; a 400 response is returned immediately.
- AC-3: A POST without explicit opt-in is not retried.
- AC-4: `Retry-After: 1` on a 429 delays the next attempt by at least 1 s.
- AC-5: Attempts never exceed the configured maximum.
- AC-6: Existing tests pass unchanged.

## 7. Technical Notes

- The retry loop wraps the existing send/execute path; the transport layer is untouched.
- Backoff: `min(cap, base * 2^attempt)` multiplied by a random factor in [0, 1).
- Replayable bodies require buffering or a body-factory contract; document whichever is chosen.

## 8. Risks

- Retrying non-idempotent requests may duplicate side effects — mitigated by default-deny plus explicit opt-in.
- Retries add load to a struggling server — mitigated by jitter, attempt cap, and total deadline.
- Hidden latency in the failure path — mitigated by bounded attempts and the deadline check.

## 9. Open Questions

- Should 429 be retryable by default? (Proposed: yes, honoring `Retry-After`.)
- Is a per-client retry budget needed in v1, or are per-request attempt caps sufficient?

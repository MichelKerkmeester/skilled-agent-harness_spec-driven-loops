# Fix race condition in job queue

## Problem

The worker claim path is non-atomic: a worker reads the next pending job and marks it in-progress in two separate steps. In the window between read and update, a second worker can read the same job, producing duplicate execution — and in some interleavings a job can be left stuck in a half-claimed state.

## Goals

- Claiming a job is atomic: a pending job transitions to in-progress for exactly one worker.
- Concurrent claims on the same job produce exactly one winner; the loser cleanly moves on.
- A job whose worker dies mid-claim becomes claimable again (via the existing lease/timeout mechanism, or one is added — see Open Questions).

## Non-goals

- Redesigning the queue architecture or swapping the broker/store.
- End-to-end exactly-once delivery; downstream idempotency is out of scope.
- Throughput or latency tuning beyond what the fix requires.

## Scope — FROZEN

**In scope:**
- The dequeue/claim code path (worker poll → mark in-progress).
- New tests covering concurrent claims.

**Out of scope:**
- The enqueue/producer path, except where needed to set up tests.
- Job payload schema and public enqueue API.
- Dashboards, metrics, alerting.

## Requirements

- **R1.** Job claiming MUST be a single atomic operation — e.g., conditional `UPDATE ... WHERE state='pending'` with a claim token, `SELECT ... FOR UPDATE SKIP LOCKED`, a compare-and-swap, or a broker-native atomic ack — such that two concurrent claims on one job yield exactly one winner.
- **R2.** The losing worker MUST observe the job as already claimed and continue polling; no user-visible error and no crash.
- **R3.** A claimed-but-unfinished job MUST eventually return to claimable state via lease/visibility-timeout/heartbeat.
- **R4.** The fix MUST NOT change the enqueue API or the job payload schema.

## Acceptance criteria

- Regression test fails on the old code and passes on the fix: N workers racing on one pending job → exactly one executes it.
- Stress check: M jobs × N workers → every job executed exactly once, none stuck.
- Existing queue test suite passes with no regressions against the captured baseline.

## Verification plan

1. Write the failing concurrent-claim regression test first.
2. Apply the fix at the claim site (the producer of the race, not the symptom).
3. Run the regression test, the stress check, and the full queue test suite; report baseline vs. delta.

## Assumptions / open questions

- The queue backend supports an atomic conditional update; if not, the fix mechanism needs re-evaluation.
- Assumed a lease/visibility-timeout already exists for R3 — if none exists, flag before expanding scope.
- At-least-once semantics assumed acceptable; duplicates may still arise from legitimate retries.

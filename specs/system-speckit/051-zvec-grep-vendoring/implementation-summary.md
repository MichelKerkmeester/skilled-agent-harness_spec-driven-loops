## What Was Built

The fork the retrieval lane depends on is now part of the repository. Check the harness out anywhere, run the two build commands in the vendored directory, and the concept lane answers from the fork's own build instead of whichever `zg` happens to be on PATH.

### The vendored engine

`.opencode/skills/system-plugins/zvec-grep/` is a squashed git subtree of the fork's `harness` branch, which merges the Ollama backend, the daemon-free stdio MCP server and the scan-free direct query. It keeps its own manifest, dependencies and build; `node_modules/` and `dist/` stay ignored by the fork's own rules. `system-plugins` is a new home for engines the harness forks rather than authors, with a README that says what is vendored, why a subtree and not a registry pin, and how to build and pull updates.

### The resolution order

The lane resolves an entry point as override, vendored build, `zg` on PATH, then a fork checkout outside the harness. The vendored rung is anchored to the lane's own file, so it is found from any working directory, and it is injectable so the tests prove the order on a machine with or without the build. An unbuilt vendored copy falls through to the next rung and is a named doctor signal, never a silent swap to upstream.

## How It Was Delivered

The three fork branches were merged into `harness` in the outside clone and its unit suite run before the subtree add. The vendored copy was built against the clone's dependencies through a symlink for this session; a fresh checkout runs `npm ci` there instead. The lane change was tested with the vendored rung both present and absent, then confirmed live: status reports the vendored source, and the five baseline queries return the same top hits as the post-fix baseline.

<!-- ANCHOR:decisions -->
## Key Decisions

| Decision | Why |
|----------|-----|
| A squashed subtree, not a submodule or a registry pin | A submodule is invisible to a plain clone and a registry pin points at a package nobody publishes; a subtree puts the exact source in the tree and still pulls upstream with one command |
| Vendored outranks PATH, override outranks vendored | The global package is upstream and lacks the fork's behaviour, so PATH winning by default was the defect; an explicit override still has to win for testing another build |
| The vendored rung is anchored to the lane file and injectable | Anchoring finds the build from any cwd; injection lets the order be proven on a machine that has the build without the tests depending on it |
| Built output stays uncommitted | The fork's rules ignore it, and a committed `dist/` would drift from the source on every pull; the doctor route names the unbuilt state instead |
| Upstream's `.github` tree stays in the subtree | Pruning it complicates every later `subtree pull` for 15 MB that costs nothing at runtime |

## Known Limitations

1. **This session's build borrows the outside clone's dependencies.** The vendored directory's `node_modules` is a symlink for now; a fresh checkout must run `npm ci` there, roughly 620 MB.
2. **The outside clone still exists** and remains the place to edit the fork; the subtree is a consumer. Nothing in the harness references the clone path except the lane's last-resort rung.
3. **Upstream's `.github` adds 15 MB** to the tracked tree. Recorded as an open question rather than pruned.

# Audit Unused Dependencies

## Goal

Produce an accurate, evidence-backed list of dependencies declared in the project's manifest(s) (`package.json`, `requirements.txt`, `pyproject.toml`, `Cargo.toml`, `go.mod`, etc.) that are not actually used by the codebase, so they can be removed to shrink install size, reduce attack surface, and cut upgrade noise.

The default deliverable is a **report**, not a deletion. Removal is a separate, explicitly scoped step.

## Scope

### In scope
- All dependency manifest files at the repository root and workspace/package subdirectories that are part of the main project.
- `dependencies`, `devDependencies`, `optionalDependencies`, and equivalent sections in the project's language ecosystem.
- Cross-referencing each declared package against source imports, config files, scripts, and build/test entry points.
- A written report listing each candidate as `unused`, `likely-unused`, or `in-use`, with the evidence for each verdict.

### Out of scope
- Lockfile regeneration or version upgrades.
- Transitive (indirect) dependencies — they are owned by their parents.
- Removing or editing dependency entries without a separate approval step.
- Vulnerability auditing (that is a different audit; do not conflate).
- Refactoring imports or "cleaning up" adjacent code — scope is frozen to the audit.

## Requirements

1. Enumerate every declared dependency across all manifests in scope before judging any of them.
2. For each dependency, search for usage evidence across:
   - Static imports/requires in source files (including aliased, scoped, and subpath forms such as `lodash/debounce`, `@scope/pkg/sub`).
   - Config files (bundler, linter, formatter, test runner, CI), where packages are referenced by name rather than imported (e.g. Babel plugins, ESLint presets, Tailwind plugins, Jest transformers).
   - `scripts` blocks, `bin` entries, and CLI invocations in package scripts, CI pipelines, and Makefiles.
   - Peer/plugin relationships — packages consumed by another declared dependency's plugin mechanism.
   - Dynamic usage: `require(variable)`, `import()` with computed specifiers, code-generated imports, and framework auto-registration conventions.
   - Build-only and types-only usage (e.g. `@types/*`, typecheck-only imports).
3. Classify each package:
   - **in-use** — at least one confirmed usage channel; cite the file.
   - **likely-unused** — no usage found; list which channels were checked.
   - **ambiguous** — usage cannot be statically confirmed or denied; state why and what would resolve it. Never mark ambiguous packages as safe to remove.
4. Do not rely on a single automated tool's verdict. Tools (depcheck, deptry, cargo-udeps, etc.) may seed the candidate list, but every `unused` claim requires an independent manual check.
5. The report must name the manifest, the package, the version declared, the verdict, and the evidence for every dependency audited — not only the flagged ones.

## Acceptance criteria

- Every dependency declared in the in-scope manifests appears in the report with a verdict and evidence.
- No package is marked `unused` on the basis of absent import statements alone; config, script, plugin, peer, and dynamic channels were all checked and the check is recorded.
- No dependency entry, lockfile, or source file is modified during the audit.
- If a removal step is separately approved, it is verified by: clean install, build, lint, typecheck, and the full test suite all passing from a fresh dependency resolution — and the removal is trivially revertible (single manifest diff, restorable via lockfile).

## Risks and edge cases

- **False positives** are the primary failure mode: packages consumed by name (plugins, presets, CLI shims, peer requirements, postinstall consumers) look unused to import-scanning. These land in `ambiguous`, not `unused`.
- **Monorepos**: a package unused in one workspace may be a peer requirement of another; audit per-workspace and cross-check.
- **Platform/optional deps**: OS- or arch-gated packages may show zero local usage yet be required on other targets.
- Removal that "works locally" but breaks CI or a different platform is a known trap — the acceptance gate requires the full verification suite, not just a local smoke check.

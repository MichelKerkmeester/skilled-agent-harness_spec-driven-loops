# Research Two Caching Libraries

## Goal

Evaluate two candidate caching libraries and produce a written comparison with a
clear recommendation, so an implementation decision can be made without redoing
the research.

## Inputs

| Input | Value |
| ----- | ----- |
| Library A | `<name and ecosystem, e.g. node-cache (Node.js)>` |
| Library B | `<name and ecosystem, e.g. lru-cache (Node.js)>` |
| Use case | `<what is being cached, expected load, environment>` |

The two candidate libraries and the target use case MUST be filled in before
execution begins. If they are not provided, record them here from the dispatching
context or mark them `UNKNOWN` and halt.

## Scope

### In scope

- Document each library's feature set: TTL/expiry, eviction policies, size
  limits, persistence options, async support, and API shape.
- Record maintenance signals: latest release date, release cadence, open-issue
  health, license, and adoption.
- Compare both libraries against the stated use case in a side-by-side table.
- Close with a recommendation and the reasoning behind it, including the case
  where neither library is a good fit.

### Out of scope

- Writing or modifying production code.
- Benchmarking beyond citing published numbers; no custom load testing.
- Evaluating any library other than the two named candidates.
- Provisioning infrastructure or external cache services (e.g. hosted Redis).

## Requirements

- **R1** — Both libraries are evaluated against the same criteria list.
- **R2** — Every load-bearing claim cites its source (official docs, repository,
  release notes) with a link.
- **R3** — Versions researched are pinned in the output ("library X v1.2.3, as
  of <date>").
- **R4** — The recommendation states the deciding factor(s), not just the winner.

## Deliverables

- `research.md` in this packet: criteria list, side-by-side comparison table,
  per-library notes with citations, and the final recommendation.

## Acceptance Criteria

- [ ] Both libraries documented against every criterion in R1.
- [ ] All claims carry citations per R2; versions and dates recorded per R3.
- [ ] A single recommendation is made with its reasoning per R4.
- [ ] Packet validation passes (`validate.sh <spec-folder> --strict` → `RESULT: PASSED`).

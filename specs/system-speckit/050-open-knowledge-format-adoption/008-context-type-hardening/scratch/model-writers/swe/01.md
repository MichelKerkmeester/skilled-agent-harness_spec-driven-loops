# Add Retry Logic to Flaky HTTP Client

## Overview

The HTTP client intermittently fails on transient errors — connection resets, timeouts, DNS blips, and retryable 5xx responses — and surfaces these directly to callers, producing flaky behavior upstream. This packet adds a bounded retry mechanism with exponential backoff and jitter so transient failures self-recover without caller intervention.

## Problem Statement

- Requests fail on the first transient error; no recovery path exists.
- Callers currently compensate ad-hoc (or not at all), producing inconsistent behavior and intermittent failures in consumers that are hard to diagnose.
- Retrying blindly is unsafe: non-idempotent methods and permanent errors must not be retried.

## Scope (Frozen)

**In scope:**
- Retry loop inside the HTTP client's request path.
- Configurable policy: `max_attempts`, `base_delay`, `max_delay`, backoff multiplier.
- Exponential backoff with full jitter.
- Retry only on: connection errors, timeouts, and HTTP 408/429/500/502/503/504.
- Respect `Retry-After` header on 429/503 when present (capped at `max_delay`).
- Retry only idempotent methods by default (GET, HEAD, PUT, DELETE, OPTIONS); non-idempotent methods (POST, PATCH) opt-in via a per-request flag.
- Observability: log each retry attempt (attempt number, delay, error class) at debug/warn level.
- Default policy values chosen to be conservative (e.g., 3 attempts, 500ms base, 8s max).
- Tests covering the acceptance criteria.

**Out of scope:**
- Circuit breaker, bulkhead, or rate limiting.
- Retries for caller-initiated cancellation or deadline exceeded.
- Changes to request/response types or public API shape beyond adding the retry config/flag.
- Retrying 4xx responses not listed above.
- Migrating existing callers to opt in to POST retries.

## Requirements

- **REQ-001**: Given a request fails with a retryable condition, when attempts remain, then the client waits `min(base_delay * multiplier^(attempt-1) + jitter, max_delay)` and retries.
- **REQ-002**: Given `max_attempts` is exhausted, when the last attempt fails, then the client returns the final error to the caller unmodified.
- **REQ-003**: Given a response carries `Retry-After`, when it is a 429 or 503, then the delay uses that value capped at `max_delay`.
- **REQ-004**: Given the method is POST or PATCH, when no explicit opt-in flag is set, then no retry is performed regardless of error class.
- **REQ-005**: Given a 4xx response not in the retryable set (e.g., 400, 401, 404), then the client returns it immediately with zero retries.
- **REQ-006**: Given retry config is omitted, then the documented default policy applies.
- **REQ-007**: Given total elapsed time would exceed the caller's deadline/context timeout, then the client aborts remaining retries and returns promptly.

## Acceptance Criteria

1. Unit test: a client whose first two attempts fail with retryable errors succeeds on attempt 3 without caller involvement.
2. Unit test: a persistently failing endpoint returns the last error after exactly `max_attempts` calls — verified by a call counter, not just elapsed time.
3. Unit test: a 404 and a 401 response each result in exactly one underlying call.
4. Unit test: a POST without opt-in makes exactly one call on a 503; with opt-in it retries.
5. Unit test: `Retry-After: 2` on a 429 produces a delay of ~2s (asserted via injected clock/sleeper, not wall time).
6. Backoff delay is asserted through an injectable clock/jitter source so tests are deterministic and fast.
7. Existing client tests still pass; no public API breakage (config addition is additive only).

## Edge Cases

- `max_attempts` of 1 disables retry cleanly.
- Cancellation mid-backoff aborts the sleep and returns the context error.
- Response bodies of failed attempts are fully drained/closed before retry to avoid connection leaks.

## Assumptions

- The client already has (or can accept) an injectable clock/sleeper for testability; if not, adding one is in scope as an internal detail.
- Default retry config lives alongside existing client configuration.

## Open Questions

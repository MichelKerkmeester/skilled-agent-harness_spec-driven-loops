# Plan a Database Migration

## Overview

Create a migration plan that takes a database from its current source (engine,
version, or schema) to a defined target, with zero unplanned data loss and a
rehearsed rollback path. The output of this packet is the plan itself plus the
verification artifacts that prove the plan is executable — not the executed
migration.

## Problem Statement

Database migrations fail at the planning boundary: undocumented schema drift,
unmeasured data volumes, missing rollback paths, and cutover steps discovered
mid-flight. A written, validated plan forces these to the surface while they are
still cheap to fix.

## Goals

- Inventory the source: engine, version, schema objects, data volume, growth
  rate, dependencies (triggers, views, stored procedures, extensions), and
  every application that reads or writes it.
- Define the target: engine/version, topology, and any schema changes
  intentionally bundled with the move.
- Choose a migration strategy (dump/restore, logical replication, physical
  replication, dual-write, or shadow-copy) with the trade-off reasoning
  recorded.
- Produce a step-by-step runbook: pre-flight checks, migration execution,
  validation, cutover, and rollback, each with an owner and an observable
  success check.
- Quantify expected downtime and confirm it fits the agreed maintenance
  window.

## Non-Goals

- Executing the migration against production.
- Application-level refactors unrelated to the schema/data move.
- Performance tuning of the target beyond what the plan must document.
- Migrating more than one database or service boundary in this packet.

## Scope — FROZEN

**In scope:**

1. Source assessment document: schema inventory, data-volume baseline,
   dependency map (apps, jobs, reports, foreign keys across databases).
2. Target definition: engine/version, instance topology, storage/IOPS sizing.
3. Strategy selection record: candidate strategies, downtime/reversibility
   comparison, chosen approach and why.
4. Runbook: ordered steps with preconditions, verification checks, timing
   estimates, and rollback steps per phase.
5. Validation plan: row counts, checksums, constraint verification, and a
   sample-query diff between source and target.
6. Risk register: top risks, likelihood/impact, mitigation, and the trigger
   that sends execution to rollback.

**Out of scope:**

- Live execution of the migration.
- Schema redesign unrelated to the move.
- Data retention/archival policy changes.

## Requirements

- **R1.** Every source object appears in the inventory or is explicitly listed
  as intentionally excluded.
- **R2.** The plan states the exact point of no return and what rollback looks
  like before and after it.
- **R3.** Each runbook step names its preconditions and a pass/fail check a
  second engineer could execute.
- **R4.** Downtime estimate is derived from a measured rehearsal or a stated
  calculation, not a guess.
- **R5.** Application connection-string/config cutover steps are enumerated,
  including secrets/config locations.
- **R6.** The validation plan covers completeness (counts/checksums) and
  correctness (constraints, sample business queries).

## Approach

1. **Assess** — run inventory queries against the source; record engine,
   version, size, object counts, and dependencies.
2. **Decide** — compare strategies against measured volume and the downtime
   budget; document the decision.
3. **Rehearse** — dry-run on a copy or staging environment; capture timings
   and failure modes.
4. **Write the runbook** — fold rehearsal findings into concrete steps with
   rollback branches.
5. **Review** — plan is reviewed against R1–R6 before being marked complete.

## Risks

| Risk | Mitigation |
| ---- | ---------- |
| Undocumented writer keeps hitting the source | Dependency map + traffic audit during assessment |
| Data volume makes the window infeasible | Measure first; prefer replication-based strategy |
| Rollback fails after cutover | Define point of no return; rehearse rollback too |
| Schema drift between plan and execution | Freeze schema changes or re-baseline before run |

## Success Criteria

- Inventory, strategy record, runbook, validation plan, and risk register all
  exist at the packet paths.
- A reviewer can answer, from the documents alone: what moves, how, how long,
  how we verify, and how we go back.
- Rehearsal (or documented reason it was skipped) produced timing numbers the
  downtime estimate rests on.

## Verification

- `validate.sh <spec-folder> --strict` → `RESULT: PASSED`
- Requirements checklist: each of R1–R6 mapped to the artifact that satisfies
  it.
- Runbook step audit: every step has a precondition and a pass/fail check.

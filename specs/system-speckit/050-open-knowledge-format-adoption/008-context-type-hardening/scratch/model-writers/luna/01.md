# Retry Flaky HTTP Requests

## Goal

Improve reliability when an HTTP request fails due to a temporary network problem or server error, without creating unbounded delays or duplicating unsafe operations.

## Requirements

- Retry requests that fail because of transient connection errors, timeouts, or HTTP `429`, `502`, `503`, and `504` responses.
- Do not retry other HTTP responses by default.
- Retry only safe or explicitly retryable requests. Requests with side effects must require an idempotency key or explicit opt-in.
- Limit retries to a configurable maximum. Default to two retries after the initial attempt.
- Use exponential backoff with jitter between attempts.
- Respect a valid `Retry-After` header, subject to a configurable maximum delay.
- Apply an overall request deadline so retries cannot exceed the caller’s latency budget.
- Return the final response or error using the existing client interface. Preserve the last failure when retries are exhausted.
- Allow callers to disable retries per request.

## Acceptance Criteria

- A transient failure followed by a successful response returns the successful response.
- Non-retryable failures are returned without another attempt.
- Retry count and delays stay within configured limits.
- A request marked unsafe is not repeated unless explicitly made retryable.
- The overall deadline stops further attempts and returns the existing timeout error.
- Retries can be disabled for an individual request.

## Out of Scope

- Retrying requests in background queues.
- Circuit breakers, request hedging, or client-wide rate limiting.
- Changing HTTP response or error formats.

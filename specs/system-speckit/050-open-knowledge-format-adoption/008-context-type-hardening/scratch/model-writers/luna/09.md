# Feature Flag Service

## Purpose

Provide a central service for managing feature flags and evaluating them consistently across applications. Applications must continue using their last known flag configuration when the service is unavailable.

## Goals

- Create, update, enable, disable, and archive flags.
- Evaluate boolean flags for a user or other context.
- Support percentage rollouts and simple attribute-based targeting.
- Make flag changes auditable and safe to roll back.
- Keep evaluation fast and available to application SDKs.

## Out of scope

- Experiment analysis and analytics.
- Complex rule languages or arbitrary user-supplied code.
- Secrets management or authorization decisions.
- Automatic flag cleanup.

## Requirements

1. A flag has a stable key, description, enabled state, default value, and optional targeting rules.
2. Each environment has an independent flag configuration.
3. Evaluation returns a deterministic boolean for the same flag, environment, and context.
4. If no rule matches, evaluation returns the flag’s default value. If the flag or environment is unknown, the SDK returns the caller-provided fallback.
5. Percentage rollouts use a stable hash of the flag key and context identifier, so users do not shift between buckets during unrelated configuration changes.
6. Flag updates take effect without an application restart.
7. Every configuration change records the actor, timestamp, environment, and before-and-after values.
8. SDKs use cached configuration and refresh it periodically or when notified of a change. Service failures must not block application requests.
9. Admin access requires authentication and role-based authorization. Read-only SDK credentials cannot modify flags.

## Design

### Components

- **Admin API:** Authenticated interface for flag configuration and audit history.
- **Evaluation/configuration API:** Serves environment-specific flag snapshots to SDKs.
- **Storage:** Persists flags, environments, targeting rules, and audit events.
- **SDK:** Caches snapshots locally and evaluates rules in-process. It accepts a fallback value for every evaluation.

### Flag configuration

A flag consists of:

- `key`: unique, immutable identifier within the service.
- `description`: human-readable purpose.
- `enabled`: master switch.
- `default_value`: boolean used when no targeting rule matches.
- `rules`: ordered list of targeting rules.
- `updated_at` and `updated_by`: last-change metadata.

A rule may match context attributes using equality against a named attribute and return a boolean value. Rules are evaluated in order; the first match wins. Percentage rollout is a rule condition based on a configured percentage from 0 to 100.

The context includes a stable identifier, such as a user or account ID, and optional attributes. Missing attributes do not match rules that depend on them.

### API outline

- `POST /v1/flags` — create a flag.
- `GET /v1/flags?environment={env}` — list flags for an environment.
- `PUT /v1/flags/{key}?environment={env}` — replace a flag configuration.
- `POST /v1/flags/{key}/archive?environment={env}` — archive a flag.
- `GET /v1/config?environment={env}` — retrieve an SDK configuration snapshot.
- `GET /v1/audit?environment={env}&flag_key={key}` — retrieve change history.

Writes require an authenticated admin identity. SDK snapshot access requires a read-only environment credential. Responses include a configuration version and update timestamp.

## Operational expectations

- Evaluation occurs in the SDK from cached configuration; it does not require a network call per request.
- SDK refresh failures retain the last valid snapshot and emit a diagnostic signal.
- Invalid configuration updates are rejected atomically, leaving the prior configuration active.
- Configuration snapshots are versioned so SDKs can detect updates and recover from missed notifications.
- The service emits metrics for API errors, refresh failures, configuration propagation delay, and admin changes. It must not log raw context attributes by default.

## Acceptance criteria

- An admin can create a flag in one environment without changing another environment.
- A client can evaluate a flag with default, matching, and non-matching rules.
- Percentage rollout results are stable for a given flag and context identifier.
- A disabled flag returns its default value.
- An unknown flag returns the SDK-provided fallback.
- SDK evaluation continues with the last valid snapshot during service downtime.
- Invalid updates do not partially change active configuration.
- Each successful change appears in the audit history with actor, timestamp, and old and new values.

# Rename a Configuration Key

## Goal

Rename a configuration key from `<old_key>` to `<new_key>` without changing the setting’s meaning or its effect on the application.

## Scope

Update configuration parsing, defaults, validation, documentation, examples, and tests to use the new key. Preserve compatibility with existing configurations where required by the project’s migration policy.

## Requirements

- The application reads `<new_key>` and applies the same behavior as the former key.
- If backward compatibility is required, `<old_key>` remains supported for the documented migration period.
- When both keys are present, the precedence rule is explicit and consistent.
- Invalid values continue to produce clear validation errors.
- User-facing documentation and sample configuration use `<new_key>`.
- Unrelated configuration keys and behavior remain unchanged.

## Acceptance Criteria

- A configuration using `<new_key>` produces the expected behavior.
- Any supported legacy configuration using `<old_key>` follows the documented compatibility behavior.
- If both keys are provided, the documented precedence is applied.
- Tests cover the new key and any retained legacy behavior.
- No stale references to `<old_key>` remain outside intentional migration or compatibility code.

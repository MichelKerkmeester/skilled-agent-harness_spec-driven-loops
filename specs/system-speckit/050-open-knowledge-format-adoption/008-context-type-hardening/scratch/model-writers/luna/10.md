# Decision: Drop the Legacy API

## Status

Accepted

## Decision

The legacy API will be removed. New development should use its supported replacement.

## Context

The legacy API remains available but is no longer the preferred interface. Keeping it requires ongoing maintenance and can make compatibility and support expectations unclear.

## Rationale

- Reduce maintenance of obsolete interfaces.
- Direct users toward the supported replacement.
- Make the compatibility and support boundary explicit.

## Impact

Existing consumers may need to update their integrations. Before removal, document the affected versions and endpoints, the replacement path, and any behavior differences.

## Migration and removal

1. Identify consumers and affected API versions or endpoints.
2. Publish the deprecation notice and removal timeline.
3. Provide migration guidance and the replacement API.
4. Remove the legacy API at the announced date.
5. Update documentation, examples, and support guidance.

## Alternatives considered

- **Keep the API indefinitely:** rejected because it continues the maintenance burden.
- **Continue deprecating without a removal date:** rejected because consumers would lack a clear timeline.

## Consequences

The project must communicate the timeline and provide migration guidance. Consumers that do not migrate before removal may experience integration failures.

# Record Decision to Drop Legacy API

## Overview

Capture the decision to drop the legacy API as a durable, reviewable record. The deliverable is a decision document (ADR-style) that states what is being dropped, why, who is affected, and how consumers migrate before the sunset date. No code changes are made by this packet; it establishes the record and the migration commitments that later implementation packets will execute.

## Context

The legacy API remains in service but has been superseded. Operating it carries maintenance, security, and documentation cost, and its continued availability delays consumer migration. A decision to drop it has been made; without a written record, the rationale and commitments are lost to memory and re-litigated later.

## Decision Statement

Drop the legacy API. Existing consumers must migrate to the supported replacement API by the published sunset date. After sunset, the legacy endpoints are removed and return no service.

The record must state:

- The exact API surface being dropped (endpoints, versions, SDKs).
- The replacement surface and its migration mapping.
- The sunset date and the deprecation window.
- The owner accountable for execution and for consumer communication.

## Requirements

### Functional

1. A decision document exists at a stable path in the spec packet, containing status, date, owner, decision statement, rationale, alternatives considered, and consequences.
2. The document enumerates affected consumers and the migration path for each.
3. The document defines the sunset schedule: announcement, deprecation warnings, final removal.
4. The document names rollback or exception handling if a consumer cannot migrate in time.

### Non-Functional

1. The record is written so a reader unfamiliar with the API can act on it without additional context.
2. The rationale distinguishes confirmed reasons from assumptions.
3. Status is explicit (proposed, accepted, superseded) and dated.

## Acceptance Criteria

- [ ] Decision document present in the packet with all required sections.
- [ ] Drop list, replacement mapping, and sunset date are unambiguous and consistent throughout.
- [ ] Affected consumers and migration owners are named.
- [ ] Alternatives considered and rejected are recorded with the reason.
- [ ] Status and date set; the document is linked from the packet's spec.md.

## Out of Scope

- Implementing the shutdown (route removal, SDK retirement, infrastructure teardown).
- Negotiating individual consumer migration deadlines.
- Building new replacement API capability.

## Risks

- A consumer is missed in the impact list, causing an unplanned outage at sunset.
- Sunset date is announced before migration tooling is available.
- The record is treated as intent rather than commitment and drifts from the executed plan.

## Open Questions

- Is there a hard external or contractual deadline that fixes the sunset date?
- Who owns consumer communication, and through which channel?
- Are there consumers under a support contract requiring an exception process?

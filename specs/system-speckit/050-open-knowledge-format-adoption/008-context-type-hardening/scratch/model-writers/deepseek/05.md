# Plan a Database Migration

## Overview

Define the approach, sequence, and safeguards for migrating a database from its current schema and data state to the target state. The deliverable is a migration plan document plus a dry-run report — not the executed migration.

## Goals

1. A step-by-step migration sequence with explicit ordering and dependencies.
2. A tested rollback path for every irreversible step.
3. Downtime impact stated, measured, and acceptable to stakeholders.

## Non-Goals

- Choosing the database engine or hosting provider.
- Executing the migration in production (separate packet).
- Application code changes beyond what the migration itself requires.

## Requirements

### Functional

- FR-1: Inventory current schema, row counts, and dependent services.
- FR-2: Classify each change as additive, destructive, or type-changing.
- FR-3: Define expand/contract phases so old and new application versions can run concurrently.
- FR-4: Specify backfill strategy (batch size, throttle, idempotency) for any data movement.
- FR-5: Produce a dry run against a production-like copy and record duration, errors, and lock behavior.
- FR-6: Define verification queries that confirm success at each phase.

### Non-Functional

- NFR-1: Migration steps are idempotent and resumable after interruption.
- NFR-2: Rollback restores the prior state within the agreed maintenance window.
- NFR-3: No step holds a blocking lock longer than the agreed threshold.

## Acceptance Criteria

- [ ] Migration plan lists every step with its rollback counterpart.
- [ ] Dry run completed on a production-scale copy with results recorded.
- [ ] Downtime estimate and maintenance window approved.
- [ ] Verification queries defined and shown to pass on the dry-run target.
- [ ] Go/no-go checklist and stop conditions documented.

## Risks

| Risk | Mitigation |
| --- | --- |
| Long lock on a large table | Expand/contract; online DDL where supported |
| Backfill overloads primary | Batch with throttle; run off-peak |
| Rollback untested | Rehearse rollback in the dry run |
| Schema drift between environments | Snapshot and diff schema before planning |

## Open Questions

- Maintenance window available, and its maximum duration?
- Acceptable data-loss window (RPO) if rollback cannot fully restore?
- Who owns the go/no-go decision on migration day?

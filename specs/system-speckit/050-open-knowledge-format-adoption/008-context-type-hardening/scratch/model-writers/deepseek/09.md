# Feature Flag Service

## 1. Overview

Design a feature flag service that lets applications toggle features at runtime without redeploying. The service exposes an evaluation API for client applications and an admin API for managing flags, enabling progressive rollouts, kill switches, and per-user targeting.

## 2. Problem Statement

Deploying code to change behavior is slow and risky. Teams need a way to decouple release from deployment: enable a feature for a subset of users, roll it back instantly, and test variants without shipping new builds.

## 3. Goals

- Provide a single source of truth for flag definitions and their states.
- Evaluate flags quickly and deterministically for a given user/context.
- Support common targeting: on/off, percentage rollout, user/group allowlists, environment scoping.
- Expose a minimal admin surface for creating, updating, and disabling flags.
- Fail safely: a flag evaluation error must never break the calling application.

## 4. Non-Goals

- Full A/B experiment analytics or statistical significance testing.
- A polished end-user UI; a basic admin API is sufficient for this iteration.
- Multi-region replication or cross-datacenter consistency guarantees.

## 5. Functional Requirements

1. Flag model: key, name, description, enabled state, type (boolean, string, number), default value, and targeting rules.
2. Targeting rules: evaluated in order; first match wins. Rule types: user allowlist, group/segment match, percentage rollout (deterministic hash on flag key + user key), environment match.
3. Evaluation API: given a flag key and an evaluation context (user ID, attributes, environment), return the resolved value and a reason (rule matched or default).
4. Admin API: create, read, update, delete flags; enable/disable; audit who changed what and when.
5. Deterministic rollout: the same user must receive the same variant for the same flag across evaluations, using a stable hash (e.g., flag key + user key).

## 6. Non-Functional Requirements

- Evaluation latency: p99 under 10 ms in-process, under 50 ms over the network.
- Availability: evaluating a flag must not fail the caller; return the configured default on any error.
- Consistency: admin changes propagate to evaluation within 30 seconds.
- Security: admin API requires authentication; evaluation API is read-only and scoped by environment key.

## 7. Success Criteria

- A client can evaluate a flag and receive a deterministic result for a known user.
- A flag can be enabled for 10% of users and verified via evaluation context sampling.
- Disabling a flag takes effect for all clients within the propagation window.
- All evaluation errors degrade to the flag's default value with a logged reason.

## 8. Open Questions

- Storage choice: in-memory with persistence, or an external store (Redis/Postgres)?
- Client SDK caching strategy: polling, streaming, or both?
- Do we need flag versioning and scheduled changes in this iteration?

# Commit Message Style Guide

## Overview

Create a written style guide that defines how contributors to this repository should compose git commit messages. The guide standardizes format, tone, and content so history stays readable, searchable, and useful for reviews, changelogs, and debugging.

## Problem Statement

Commit messages across the repository vary in structure, length, and clarity. Some are terse ("fix stuff"), others mix multiple unrelated changes, and few follow a consistent format. This makes history hard to scan, complicates release notes, and slows down root-cause analysis during bisects.

## Goal

Produce a single authoritative `COMMIT_MESSAGES.md` (or equivalent section in existing contributing docs) that contributors can follow without prior context.

## Scope

**In scope:**
- Message structure: subject line, blank line, body, optional footer
- Subject line rules: imperative mood, max length, capitalization, no trailing period
- Body guidelines: what to explain (why over what), wrapping, bullet use
- Footer conventions: issue references, breaking changes, co-authors
- Examples of good and poor messages
- Relation to existing tooling (e.g., commit hooks, linters)

**Out of scope:**
- Changing or retroactively rewriting existing commit history
- Installing or configuring commit linting tooling
- Branching strategy or pull request conventions

## Requirements

- **REQ-1:** The guide must specify the subject line format (type/scope optional prefix, imperative mood, ≤72 characters).
- **REQ-2:** The guide must define when and how to use the message body, emphasizing rationale over restating the diff.
- **REQ-3:** The guide must describe footer conventions for issue links and breaking-change notes.
- **REQ-4:** The guide must include at least three before/after examples contrasting weak and strong messages.
- **REQ-5:** The guide must state how violations are handled (review feedback, not hard rejection), unless tooling enforcement exists.
- **REQ-6:** The guide must be linked from the repository's contributing documentation.

## Acceptance Criteria

- [ ] A style guide document exists at a discoverable path in the repository.
- [ ] Every requirement REQ-1 through REQ-6 is addressed in the document.
- [ ] Examples are accurate and consistent with the stated rules.
- [ ] The contributing docs reference the guide.
- [ ] A reviewer unfamiliar with the repository can compose a compliant message using only the guide.

## Dependencies

- Existing contributing documentation location and conventions.
- Any commit hooks or CI checks already present that the guide must not contradict.

## Risks

- **Adoption:** A guide nobody reads changes nothing; mitigate by linking from PR templates and contributing docs.
- **Over-prescription:** Excessively rigid rules can discourage contributions; keep mandatory rules minimal and justify each.

## Success Metrics

- Reviewers can cite a specific guide section when requesting message changes.
- New commit messages increasingly follow the subject-line and footer conventions.
- Release note generation, if applicable, requires less manual cleanup.

# Fix Race in Job Queue

## Problem

Under concurrent workers, the job queue can hand the same job to more than one worker. Symptoms reported:

- A job runs twice (side effects duplicated).
- A job is acknowledged by one worker while another still holds it.
- Failures are intermittent and scale with worker count.

## Goal

Guarantee that each job is claimed by exactly one worker for the duration of its lease, without changing job payloads or the public queue API.

## Root Cause (hypothesis — confirm before editing)

The claim path is not atomic: it reads a job's state, decides it is available, then writes the claim in a separate step. Two workers can interleave between read and write. Confirming evidence: reproduce with two workers against one job and inspect the claim sequence; UNKNOWN until reproduced locally.

## Scope

In scope:

- The claim/acknowledge code path in the job queue.
- Concurrency control needed to make claim atomic (e.g. conditional update / row lock / atomic compare-and-set — the mechanism follows from what the store supports).
- A regression test that fails on the current code and passes after the fix.

Out of scope:

- Queue throughput or batching changes.
- Retry/backoff policy changes.
- Schema changes beyond what the claim fix strictly requires.

## Requirements

1. Claiming a job is a single atomic operation relative to other workers.
2. A job in `running` state with a live lease cannot be claimed by a second worker.
3. An expired lease may be reclaimed, and reclamation must not race with the original worker's acknowledgement.
4. Acknowledge/fail transitions are scoped to the worker holding the lease (stale acknowledgements are rejected or ignored, not applied).
5. No change to the externally observable job lifecycle or existing API callers.

## Acceptance Criteria

- [ ] Concurrent claim test: N workers, 1 job, exactly 1 successful claim; the losers observe "not claimed", never run the job.
- [ ] Stale-ack test: an expired-lease worker's acknowledgement does not override the new claimant's state.
- [ ] Full queue test suite passes with no regressions (baseline captured before the change).
- [ ] Reproduction test fails on the pre-fix revision and passes on the fix (proof the test targets the race).

## Verification

- Capture baseline test results before editing.
- Run the concurrency test repeatedly (e.g. 100 iterations) to account for scheduling nondeterminism.
- Rerun the full queue test suite and report the delta against baseline.
- If the store cannot express the atomic claim, stop and report rather than widening scope to a storage redesign.

## Risks

- Mechanically serializing claims could reduce throughput; measure before claiming a performance regression.
- Lease-expiry timing changes can reintroduce the race in the reclaim path; the stale-ack test guards this.
- UNKNOWN: exact store/version in use; the atomic mechanism depends on it and must be chosen after reading the claim code.

## Open Questions

- What is the production worker count and observed duplicate rate? (Shapes reproduction scale.)
- Is the store transactional, lock-capable, or neither? Determines the fix mechanism.

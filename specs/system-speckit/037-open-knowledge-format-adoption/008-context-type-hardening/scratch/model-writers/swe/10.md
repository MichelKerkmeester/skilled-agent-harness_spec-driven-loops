# Record a decision to drop a legacy API

## Context

A legacy API is slated for removal. Before any deprecation or deletion work
begins, the decision itself must be recorded so that future maintainers can
understand what was decided, why, who approved it, and what consumers are
affected. This spec covers writing the decision record only — not executing
the removal.

## Goal

Produce a single, durable decision record (e.g., an ADR or equivalent doc in
the repo's decision-records location) that documents the dropping of the
legacy API.

## Requirements

The decision record MUST capture:

1. **Identity of the API** — name, version, base path/endpoints, and owning
   team or service.
2. **Decision** — a one-sentence statement that the API will be dropped, plus
   status (proposed / accepted / superseded) and the decision date.
3. **Rationale** — why the API is being retired (e.g., superseded by a newer
   API, no remaining consumers, maintenance cost, security exposure).
4. **Consumer impact** — known callers/integrations still using the API, or
   evidence that none remain (usage metrics, logs, dependency search).
5. **Migration path** — what replaces it, and what consumers must do
   (endpoint mapping, SDK version, cutoff date).
6. **Timeline** — deprecation announcement date, sunset/removal date, and
   any staged milestones.
7. **Approvers** — who signed off on the decision.
8. **Rollback / contingency** — what happens if a missed consumer surfaces
   after shutdown (e.g., temporary re-enable, redirect, grace period).

## Acceptance criteria

- [ ] Decision record file exists in the repo's designated location
      (e.g., `docs/adr/` or per project convention) and follows the naming
      convention used by existing records.
- [ ] All eight required elements above are present and specific (no
      placeholder dates or "TBD" owners).
- [ ] The record is linked from any index, changelog, or tracking issue the
      project uses for decisions.
- [ ] At least one approver other than the author is named.

## Out of scope

- Implementing the actual deprecation (warnings, headers, telemetry).
- Removing or altering the legacy API code.
- Migrating consumers.
- Announcing the decision to external users beyond linking the record.

# Commit Message Style Guide

## Goal

Produce a single authoritative document that defines how commit messages are
written for this project, so every contributor produces consistent, readable,
and mechanically verifiable history without guessing at conventions.

## In Scope

- One Markdown style guide file (e.g., `docs/COMMIT_MESSAGE_STYLE.md` or a
  dedicated section linked from `CONTRIBUTING.md`) covering:
  - Subject-line rules: imperative present tense, maximum length, no trailing
    period, capitalization convention
  - Header prefix format: whether Conventional Commits is adopted and the
    allowed `type` values (`feat`, `fix`, `docs`, `refactor`, `test`, `chore`,
    `perf`, `ci`, `build`) plus optional `scope`
  - Body rules: wrap at 72 characters, explain *why* not *what*, and when a
    body is required vs optional
  - Footer rules: `BREAKING CHANGE:` marker, issue references
    (`Closes #123`), co-author trailers
  - Conventions for revert, merge, and work-in-progress commits
  - At least three concrete examples, including at least one bad message
    rewritten correctly
  - A short enforcement note: how compliance is expected (code review today;
    linting tooling noted as a possible follow-up, not installed here)
- A link to the guide from `CONTRIBUTING.md` or the docs index

## Out of Scope

- Installing or configuring enforcement tooling (commitlint, husky hooks,
  CI checks)
- Rewriting, amending, or linting existing commit history
- PR title/description conventions beyond a brief cross-reference
- Git workflow policy (branching model, squash vs merge strategy) beyond
  what message format requires

## Requirements

1. The guide MUST define the subject-line format: maximum length, mood/tense,
   and punctuation rules.
2. The guide MUST state explicitly whether the project follows Conventional
   Commits and list every allowed `type` (and `scope` usage) if so.
3. The guide MUST clearly separate required elements from optional ones and
   state when a body or footer is required.
4. The guide MUST include at least three examples, all self-consistent with
   the stated rules; at least one MUST show a bad message and its corrected
   form.
5. A reader MUST be able to write a fully compliant commit message using only
   the guide — no external document required.
6. The guide MUST be discoverable via a link from `CONTRIBUTING.md` or the
   repository's documentation index.

## Acceptance Criteria

- [ ] The style guide file exists at its target path and renders cleanly.
- [ ] Every rule in the guide is demonstrated correctly by at least one
      example.
- [ ] `CONTRIBUTING.md` (or docs index) links to the guide.
- [ ] A commit message written from the guide alone passes every stated rule.

## Risks & Open Questions

- **Convention choice:** default to the standard Conventional Commits type
  set; document any deviation explicitly in the guide rather than silently
  narrowing it.
- **Future enforcement:** write the rules so they are mechanically checkable
  later (single header format, enumerable types), even though no linter is
  installed by this packet.

# Audit Unused Dependencies

## Purpose

Identify dependencies that the project does not use and document evidence before recommending their removal.

## Scope

Review direct dependencies in the project manifests. Check source code, tests, scripts, build configuration, generated code, and documented runtime entry points. Account for dependencies loaded dynamically or used through plugins, command-line tools, code generation, or package lifecycle scripts.

Do not treat a package as unused solely because a static import search finds no references. Do not remove transitive dependencies directly unless the project declares them as direct dependencies.

## Process

1. Identify the package manager, manifests, lockfiles, workspaces, and relevant project entry points.
2. Search for each direct dependency’s imports, dynamic loads, command-line calls, configuration references, and test or build usage.
3. Classify each dependency as **used**, **possibly used**, or **no usage found**. Record the evidence and any uncertainty.
4. Recommend removal only when no usage is found and relevant indirect or non-source usage has been considered.
5. For approved removals, update the manifest and lockfile together, then run the project’s relevant checks.

## Requirements

- Preserve dependencies required by consumers, plugins, peer dependency contracts, or published package metadata.
- Distinguish production, development, optional, and peer dependencies.
- Do not make removal recommendations based on package age, size, or lack of recent updates.
- Report unresolved cases as uncertain rather than asserting that a dependency is unused.
- Keep the audit report separate from changes unless the task explicitly includes dependency removal.

## Acceptance Criteria

- Every direct dependency in scope has a usage classification and supporting evidence.
- Possible dynamic, generated, configuration-based, and non-source usage is considered.
- Each removal recommendation names the affected package and explains the evidence.
- If dependencies are removed, the manifest and lockfile are consistent and relevant project checks pass.

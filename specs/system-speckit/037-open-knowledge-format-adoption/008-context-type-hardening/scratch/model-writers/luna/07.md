# Commit Message Style Guide

## Purpose

Define a consistent commit message format that makes changes easy to understand in code review and project history.

## Standard format

Use this structure:

```text
type(scope): summary

Optional explanation of why the change was made or relevant context.

Optional trailers
```

The scope is optional. Omit it when the change does not belong to one clear area.

## Rules

- Use a recognized type: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, or `chore`.
- Write the summary in the imperative mood, such as “add,” “fix,” or “remove.”
- Capitalize nothing after the colon unless required by a proper name.
- Do not end the summary with a period.
- Keep the summary focused on the change, ideally within 72 characters.
- Add a body when the reason or impact is not clear from the summary. Wrap body lines at about  body lines at about  72 characters.
- Use a blank line between the summary, body, and trailers.
- Use `!` after the type or scope to mark a breaking change, and explain it in the body or a `BREAKING CHANGE:` footer.
- Add issue references or metadata as trailers when useful, such as `Fixes #123` or `Reviewed-by: Name`.

## Type meanings

| Type | Use |
|---|---|
| `feat` | Add user-facing functionality |
| `fix` | Correct a defect |
| `docs` | Change documentation |
| `style` | Make formatting-only changes |
| `refactor` | Restructure code without changing behavior |
| `perf` | Improve performance |
| `test` | Add or update tests |
| `build` | Change build or dependency configuration |
| `ci` | Change continuous integration configuration |
| `chore` | Handle maintenance work that does not fit another type |

## Examples

```text
feat(auth): add password reset flow
```

```text
fix: preserve filters when returning to search

Restore the previous filter state so users can continue where
they left off.
```

```text
docs(api): clarify pagination defaults
```

```text
feat(api)!: require an explicit version header

BREAKING CHANGE: Requests without a version header now return 400.
```

## Before committing

Check that the summary identifies the change, the type fits its purpose, and the body explains any context a reviewer would otherwise need to infer.

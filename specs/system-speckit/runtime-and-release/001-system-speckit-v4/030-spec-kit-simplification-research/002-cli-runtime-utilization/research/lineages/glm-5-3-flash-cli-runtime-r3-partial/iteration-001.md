# Iteration 1: Command assets versus the argument parsers of the scripts they invoke

## Focus

The four speckit command assets (complete.md, validate.md, resume.md, save.md) against the argument parsers of every script they invoke — directly or through their owned workflow YAMLs. A flag the claim side names that the parser does not accept, an exit code the claim side describes that the script does not return, or an output the claim side promises that the script does not print, is a finding. Claim side: the .md assets and the hardcoded `command:`/`writer:` lines in their execution YAMLs. Actual side: the checked-in argument/exit/usage code of the invoked scripts (dist/ never cited; it is untracked and stale).

## Actions Taken

1. Read the census (research/confirmed-findings.md) once, in full — the dedup authority for rounds 1–2 rows.
2. Read complete.md, resume.md, save.md; validate.md → ENOENT (the read itself is the evidence; the directory holds complete, implement, plan, resume, save, search + README.txt + assets/).
3. Grepped the four execution YAMLs (complete-auto/confirm, resume-auto/confirm) for every hardcoded script invocation and flag they pass, with line numbers.
4. Read the argument/exit surfaces of the seven invoked scripts: validate.sh (usage + parse_args + RECURSIVE predicate), create.sh (flag arms), recommend-level.sh (usage — arms not reached), lookup-trigger-index.mjs (usage + parseArgs + return codes), generate-trigger-index.mjs (parseArgs), nested-changelog.ts (parseArgs), generate-context.ts (pre-filter + positional/structured branch).
5. Cross-checked each claim-side flag, exit code, and output promise against those parsers; located check-prerequisites.sh's sole copy with a repo-wide find.

## Findings (4)

1. **`complete.md:46`** (claim) vs **both execution YAMLs** (actual) — claimed: "`:with-context` | no value | Loads a context package before planning" (complete.md:46), routed as a workflow input alongside :with-research/:with-phases (complete.md:31-32). Actual: neither speckit-complete-auto.yaml nor speckit-complete-confirm.yaml contains any `with[-_]context` occurrence (grep, 0 hits in both), while its two siblings are consumed: `:with-research` binds at speckit-complete-auto.yaml:85 and speckit-complete-confirm.yaml:37 and gates dispatch steps (auto:372-373, 668; confirm:345-346, 636), and `:with-phases` binds at auto:104 / confirm:56. The documented context behavior never fires because nothing in the execution targets reads the flag. Severity P1 (wrong/unused — a documented invocation modifier silently absorbed). Recommendation: fix — either add the `flag: ":with-context"` binding plus a context-insertion step, or drop the modifier from complete.md's surface.

2. **`speckit-complete-auto.yaml:826`** (claim; also :890, :951, and confirm:805, :922) vs **`cli/setup/check-prerequisites.sh:1`** (actual) — claimed: five complete-workflow steps run `check-prerequisites.sh --json [--paths-only | --require-tasks]` by bare name with no path. Actual: no such file exists under `cli/spec/`, the directory the same YAMLs address by full path everywhere else (e.g. :110 recommend-level.sh, :118 create.sh, :129/:274/:724/... validate.sh); a repo-wide find (`find .opencode -name 'check-prerequisites*'`, node_modules excluded) locates exactly one copy, at `.opencode/skills/system-spec-kit/runtime/cli/setup/check-prerequisites.sh`. The step reference is resolvable only by search; every neighboring reference carries its directory. Severity P2 (reference-style drift; non-breaking). Recommendation: fix — give the five steps the full setup/ path, matching the YAMLs' dominant convention.

3. **`deep-research-config.json:3`** (claim — this lineage's frozen angle: "command assets ... (complete.md, validate.md, resume.md, save.md)") vs **`.opencode/commands/speckit/README.txt:3`** (actual) — claimed: a fourth command asset, validate.md. Actual: the file does not exist (read → ENOENT; the directory holds complete/implement/plan/resume/save/search); the command README's own description enumerates "planning, implementation, deep-research, resumption, continuity save and retrieval" — no validation command; and `grep -rn 'speckit:validate'` over .opencode/commands and CLAUDE.md returns 0 hits. The repository is internally consistent (validation is reached through the complete/plan YAMLs' eight+ hardcoded validate.sh invocations and the root document's direct validate.sh requirement); the stale reference is this instruction's premise. Severity P2 (cosmetic; premise-vs-tree drift, no broken behavior). Recommendation: document — record here that the speckit command surface is complete/implement/plan/resume/save/search and validation has no command asset.

4. **`validate.sh:74`** (claim) vs **`validate.sh:135`** (actual; also :222, :264) — claimed (usage, and the census's round-2 harmonization "every document, comment and code site now carries the enforced regex" — confirmed-findings.md §2 merge row 9 and §3 round-2 fix row 2): recursive mode validates "parent + all [0-9][0-9][0-9]-*/ child phase folders", i.e. the loose 3-digit-dash-anything glob. Actual: the three recursive loops sweep with exactly that loose glob (`for phase_dir in "$parent_folder"/[0-9][0-9][0-9]-*/`), while the census-fixed enforced regex is `^[0-9][0-9][0-9]-[a-z0-9][a-z0-9-]*$` (4th char constrained, then only [a-z0-9-]). Divergence materializes for children the glob admits and the enforced regex rejects — `001-Alpha` (capital) or `001-a_b` (underscore): the loops validate them as phase folders; whether the engine's phase-child detector then agrees depends on `has_phase_children` (validate.sh:357), not read this iteration. Severity P2 (documentation/predicate fidelity; latent behavioral edge, no demonstrated break). Recommendation: fix — swap the enforced char-class into the three globs and the usage line, or document the glob's intended looseness.

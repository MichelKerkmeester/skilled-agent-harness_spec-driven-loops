## 2. PROBLEM & PURPOSE

### Problem Statement
The spec-kit simplification program ran three research rounds over five lanes and remediated every confirmed finding in seventeen children, but it closed some rows as recorded decisions rather than fixes: duplicated hook adapter text, multiplexed rule scripts, playbook entries without provenance, 27 hand-written attestation stamps, 1,240 titles carrying template provenance, six lifecycle command assets that repeat each other, a links scan that is a tool rather than a rule, packet types the scaffolder cannot create, seventeen browse-only reference files, manifest fields nothing reads, the advisor's two Ollama implementations, eight root resolvers, one Gate 1 surface for five runtimes, five hook registration schemas, an unenforced criteria floor, and five operator items on other sessions' surfaces. Each was left with a reason, and each reason was a blast-radius or ownership judgement, not a finding that the work was wrong.

### Purpose
Every recorded row becomes a fix, one child per finding cluster, each child independently planned, implemented, tested and validated, so the program's last census reads fixed on every line.

> **Phase-parent note:** This spec.md is the ONLY authored document at the parent level. All detailed planning, task breakdowns, checklists, and decisions live in the child phase folders listed in the Phase Documentation Map below. This keeps the parent from drifting stale as phases execute and pivot.

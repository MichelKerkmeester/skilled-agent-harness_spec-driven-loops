### Overview
Each of the 17 files named by finding F3-14 gets its body read and a disposition recorded: route it by adding a `RESOURCE_MAP` intent entry or a `quick-reference.md` pointer, or delete it and its manifest rows because its content duplicates or is superseded by an already-routed file. The manifest is then regenerated and checked byte-stable, and the routing-registry-drift workflow's freshness gates confirm the change did not desynchronize the manifest from the corpus.

<!-- ANCHOR:architecture -->
## 3. ARCHITECTURE

### Pattern
Read-then-disposition sweep over a fixed 17-file list, followed by a generator-owned manifest regeneration.

### Key Components
- **Per-file disposition pass**: reads each browse-only file's body and classifies it route or remove, recorded in `goal.md`'s log.
- **Router surface edit**: adds a `RESOURCE_MAP` intent entry (`SKILL.md`) or a pointer (`quick-reference.md`) for each file kept routable.
- **Manifest regeneration**: `generate-leaf-manifest.cjs --write` then `--check` after every removal, so the manifest never drifts from the corpus by hand-editing.

### Data Flow
The 17-file list from F3-14 feeds the disposition pass. Route decisions write into `SKILL.md` or `quick-reference.md`, and remove decisions delete the file and trigger a manifest regeneration. The routing-registry-drift workflow's freshness gates then read the regenerated manifest and confirm it matches the corpus on disk.
<!-- /ANCHOR:architecture -->

## 7. ROLLBACK PLAN

- **Trigger**: `generate-leaf-manifest.cjs --check` fails after a removal, or a deleted file turns out to have a live external reference the pre-deletion grep missed.
- **Procedure**: `git revert` the commit that deleted the file or edited the router surface, then re-run `generate-leaf-manifest.cjs --write` to restore the manifest to match the restored corpus.

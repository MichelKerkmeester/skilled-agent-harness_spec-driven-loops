# Feature Specification: Feature Flag Service

**Status**: Draft
**Type**: System Design

## Overview

A centralized service that lets teams decouple deploys from releases: flags are
managed in one place, evaluated in near real time by server and client
applications, and can roll a feature out to a percentage or segment of users —
or kill it instantly — without a redeploy.

## Goals

- Flag lifecycle management: create, update, archive, per environment.
- Deterministic, low-latency evaluation via SDK and HTTP API.
- Targeting: on/off, percentage rollout, attribute-based rules, user segments.
- Safe defaults: evaluation never throws; SDK serves last-known-good on outage.
- Audit trail for every flag change.

## Non-Goals

- Billing, metering, or pricing of flag usage.
- Full A/B analytics platform (event exposure hooks only).
- Client-side UI rendering experiments beyond flag delivery.

## User Stories

- As an engineer, I toggle a feature on for 5% of users in prod and raise it to
  100% without redeploying.
- As an engineer, I target a flag to `plan=enterprise` users in `eu-west` so the
  same build behaves differently per segment.
- As an on-call engineer, I flip a kill switch that disables a broken feature
  globally within seconds.
- As an SDK consumer, evaluation completes in microseconds from a local cache
  and degrades to defaults when the service is unreachable.

## Functional Requirements

| ID | Requirement |
|----|-------------|
| FR-1 | CRUD API for flags: key, description, type (boolean / multivariate / migration), default variant, tags, owner. |
| FR-2 | Environment isolation: independent flag states per env (dev, staging, prod); promotion copies state, never shares it. |
| FR-3 | Targeting rules evaluated in priority order: individual targets → segment rules → attribute conditions → percentage rollout → default. |
| FR-4 | Percentage rollout uses deterministic bucketing (hash of flag key + user key) so a user gets a stable assignment across evaluations and SDKs. |
| FR-5 | Evaluation endpoints: `POST /evaluate` (single flag) and `POST /evaluate/all` (bulk) accepting a context object (user key + arbitrary attributes). |
| FR-6 | SDK delivers rules via streaming or polling; evaluates locally; falls back to cached ruleset, then to code-level defaults. |
| FR-7 | Flag state changes propagate to SDKs within 10 seconds (p95). |
| FR-8 | Every mutation writes an audit record: who, what, when, prior state; audit log is queryable per flag. |
| FR-9 | Mutating operations require authenticated role (writer/admin); read/evaluate requires only a scoped SDK key. |
| FR-10 | Flag keys are immutable once created; deletion = archive, preserving history. |

## Evaluation Semantics

- Context: `{ "key": "user-123", "kind": "user", "attrs": { "plan": "pro", "country": "NL" } }`
- Result: `{ "flagKey", "variant", "value", "reason" }` where `reason` ∈
  `TARGET_MATCH | RULE_MATCH | FALLTHROUGH | DEFAULT | FLAG_OFF | ERROR`.
- Rule match is first-match-wins. Errors always return the configured default.

## Non-Functional Requirements

| ID | Requirement |
|----|-------------|
| NFR-1 | Local SDK evaluation: < 1 ms p99. |
| NFR-2 | Remote `/evaluate`: < 50 ms p99. |
| NFR-3 | Service availability 99.95%; SDKs must function indefinitely on cached rules. |
| NFR-4 | Rulesets cached in a read-optimized store; evaluation path is read-only and horizontally scalable. |
| NFR-5 | No PII required in context beyond an opaque key; attribute values are not persisted by the eval path. |

## Data Model (sketch)

- `Flag`: key, type, variants, default, env-scoped state (on/off, rules, targets).
- `Segment`: key, conditions (attribute, operator, values).
- `Rule`: conditions + serve (variant or rollout split).
- `AuditEvent`: flag key, env, actor, action, diff, timestamp.

## API Surface (sketch)

- `GET/POST/PATCH/DELETE /flags`, `/flags/:key/rules`, `/segments`
- `POST /evaluate`, `POST /evaluate/all`
- `GET /stream` (SSE/streaming ruleset per env+SDK key)

## Edge Cases

- Flag missing or archived → return default with reason `FLAG_OFF`/`ERROR`.
- Rollout raised then lowered → users may fall out of the bucket; this is
  expected and must be documented.
- Cyclic segment references are rejected at write time.
- Clock-free consistency: ruleset versioned; SDK never evaluates a half-applied update.

## Success Criteria

- A flag change reaches all connected SDKs in ≤ 10 s (p95).
- SDKs continue evaluating correctly through a full control-plane outage.
- Every prod flag change is attributable to an authenticated actor.
- Bucketing produces identical assignments across Go/Java/JS SDK implementations
  for the same inputs (cross-SDK conformance test).

## Open Questions

- Streaming (SSE) vs polling-only for v1? (Streaming preferred; polling fallback required.)
- Multi-kind contexts (user + org + device) in v1, or single-kind only?
- In-scope or delegated auth (SSO/OIDC) for the admin API?

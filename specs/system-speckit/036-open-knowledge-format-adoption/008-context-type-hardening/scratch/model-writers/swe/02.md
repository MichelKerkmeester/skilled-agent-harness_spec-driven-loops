# Rename a Config Key

## Parameters

| Parameter | Value |
| --------- | ----- |
| Old key | `OLD_KEY` (fill in before planning) |
| New key | `NEW_KEY` (fill in before planning) |
| Compatibility | `OLD_KEY` accepted with a deprecation warning for one release, then removed |

## User Scenarios & Testing

### User Story 1 — Adopt the new name (P1)

As a user, I can set `NEW_KEY` in my configuration and get exactly the behavior `OLD_KEY` produced.

**Acceptance Scenarios:**

1. **Given** a config that sets `NEW_KEY`, **When** the application loads config, **Then** the value is applied with identical validation and semantics as `OLD_KEY`.
2. **Given** a config that sets neither key, **When** the application loads config, **Then** the previous default applies unchanged.

### User Story 2 — Backward compatibility (P2)

As a user with an existing config, my `OLD_KEY` setting keeps working during the deprecation window and I am told to migrate.

**Acceptance Scenarios:**

1. **Given** a config that sets only `OLD_KEY`, **When** the application loads config, **Then** the value is honored and a deprecation warning naming `NEW_KEY` is emitted.

### User Story 3 — Both keys set (P3)

As a user mid-migration, when both keys are set the new key wins and I am told about the conflict.

**Acceptance Scenarios:**

1. **Given** a config that sets both `OLD_KEY` and `NEW_KEY`, **When** the application loads config, **Then** `NEW_KEY` takes precedence and a warning is emitted.

### Edge Cases

- Environment-variable and CLI-flag spellings of the key are renamed consistently.
- If the key is nested (e.g., `section.old`), the rename covers the full path, not just the leaf.
- Serialized/exported config uses `NEW_KEY` only.

## Requirements

### Functional Requirements

- **FR-1:** `NEW_KEY` is accepted everywhere `OLD_KEY` was accepted, with identical type, validation and semantics.
- **FR-2:** Runtime behavior with `NEW_KEY` set is equivalent to the old behavior; the rename changes the name only.
- **FR-3:** `OLD_KEY` continues to work during the deprecation window and emits a deprecation warning naming `NEW_KEY`.
- **FR-4:** When both keys are set, `NEW_KEY` wins and a warning is emitted.
- **FR-5:** When neither key is set, the existing default is unchanged.
- **FR-6:** All internal references — parsing, defaults, validation, docs, examples, schemas — use `NEW_KEY`; `OLD_KEY` appears only in the compatibility shim, the deprecation notice and the changelog.

## Success Criteria

- **SC-1:** Automated tests cover all four input cases: new only, old only, both, neither.
- **SC-2:** A codebase search shows `OLD_KEY` referenced only in the compatibility path and deprecation messaging.
- **SC-3:** User-facing docs and examples show `NEW_KEY` exclusively.

## Assumptions

- This is a rename only: type, default, validation and semantics do not change.
- The deprecation window and the release in which `OLD_KEY` is removed are decided at plan time.

## Out of Scope

- Renaming any other config key.
- Changing the key's type, default or semantics.
- Automated rewriting of user config files.

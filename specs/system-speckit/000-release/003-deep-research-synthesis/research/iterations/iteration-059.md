#### Model-benchmark lane for deep-agent-improvement
The deep-agent-improvement skill grew a second, co-equal evaluation lane for benchmarking models and prompt frameworks. A new `mode` selector (`agent-improvement` | `model-benchmark`) with three pluggable seams — candidate source, dispatcher, scorer — reuses roughly 90% of the existing loop, state, convergence, and mutation plumbing, so no parallel machinery had to be built. At the command layer, `/deep:start-agent-improvement-loop` now resolves a use-case lane and a dedicated `/deep:start-model-benchmark-loop` command with its workflow YAMLs makes the lane first-class; a latent argument-forwarding defect in the loop host was fixed along the way. SKILL.md was restructured so the two lanes sit side by side with a `MODEL_BENCHMARK` smart-router intent, `references/` and `assets/` were physically reorganized into `agent-improvement/`, `model-benchmark/`, and `shared/` subdirectories with every path literal repointed, and the agent awareness note now reads as "lane awareness" byte-identical across all four runtime mirrors. An opt-in 5-dimension scorer was added for finer-grained variant grading, and a round of deep-review remediation fixed three P1 findings. Deep-loop commands also stopped leaving empty research/review archive folders behind: archive-root creation is now lazy and guarded, happening only immediately before a restart move.

#### Skill benchmarks: deep-improvement rename plus third lane
Deep-agent-improvement became deep-improvement and gained a third evaluation lane that benchmarks skills themselves. The skill package, agent id (`@deep-agent-improvement` → `@deep-improvement`), and advisor canonical references were renamed across all four runtime mirrors and roughly 180 files, while the command verbs `/deep:start-agent-improvement-loop` and `/deep:start-model-benchmark-loop` were intentionally kept. The new Lane C (skill-benchmark), launched via `/deep:start-skill-benchmark-loop`, measures whether a skill is discovered, routed to, and used effectively by an AI in situ, scoring five weighted dimensions — routing/activation accuracy (0.25), unprompted reference/asset discovery (0.25), efficiency (0.20), usefulness via ablation (0.20), structural connectivity (0.10). It runs a deterministic engine of router replay, contamination linting, a structural-connectivity gate, scorer, and report builder wired into the shared loop host, plus an opt-in deterministic advisor probe, and SKILL.md, README, and the feature catalog now present three co-equal lanes. The harness made sk-code benchmarkable end-to-end, and the resulting signal drove a surface-aware router change that lifted its benchmark score from 71 to 79 (D3 42 to 50) with no recall regression. A live task-outcome instrument measured D4 usefulness at 54/100 across five paid runs, confirming the skill helps most where the base model is weak and can add noise where it is already strong. **Breaking:** the skill package, agent id, and paths renamed from deep-agent-improvement to deep-improvement — update references accordingly; the advisor still resolves old prompts via retained legacy aliases.

#### Parallel multi-executor fan-out for deep loops
The deep research and review loops gained an opt-in parallel fan-out layer that runs several executor lineages concurrently — each in an isolated sub-packet using the existing loop verbatim — then merges the lineages into the canonical `research.md` or `review-report.md`. The default single-executor path is untouched and byte-identical; fan-out only activates when you pass `--executors`/`--concurrency`. This cycle shipped the plumbing: a validated fan-out config schema (per-lineage executor labels, replica counts, iteration overrides, and a concurrency cap) and a concurrency-capped worker pool with never-throws per-item settlement, ordered results, and a JSONL status ledger, both covered by a green unit suite (161 then 171 tests). Optional lineage attribution was added to executor audit records. The design for a per-iteration model schedule (ordered bands that desugar into the existing fan-out) is captured but not yet built, and a remediation phase is planned — not implemented — to fix 14 deep-review findings (2 P0) including making the review gate fail-closed and CLI fan-out genuinely concurrent. This is largely internal tooling; the user-visible effect is that long multi-model runs can now be parallelized on demand.

#### Manual-testing playbook validator enforces scenario coverage
The 11 hub playbook trees previously held two incompatible contracts under one directory name: coverage claims were hand-typed prose that drifted in every hub, several shipped scenarios even taught an operator to violate a hard repo rule, and the only existing gate checked the other contract and exited 0 on failure. This packet adds a node-only validator, `validate-playbook-package.cjs`, that walks package trees without mutating them, honors explicit whole-tree routing-gold overrides, and classifies every file by its expected workflow mode and leaf-resource signature. It derives census counts at runtime instead of trusting prose and ships strict-by-default exit codes with staged warning handling for the existing fleet, plus a fixture suite proving a clean package passes, seeded violations fail under strict mode, and `--no-strict` stays a local triage tool. Framework users now get a mechanical gate that fails closed on broken coverage instead of reporting success, so hazardous or unverified scenarios surface before they reach an operator. The packet SKILL and both templates document the two-contract boundary and the canonical PASS/FAIL/SKIP verdict set, while the manifest stays an additive override list so existing routing-gold and Lane-C consumers keep their paths.

#### Skill documentation aligned with real runtime contracts
Documentation across twelve skill roots described executors, canon, routing and hub surfaces that no longer matched the code, the registries or the installed CLI binaries. This packet corrected the drift and installed derivation mechanisms to keep it from re-rotting: executor and dispatch references were repaired against the live anchors, create-skill canon was made self-consistent (commandless hubs drop companion metadata, resource directories are conditional, naming guidance is lowercase kebab-case with disjoint valid/invalid examples), and the advisor gate, hook topology, prompt-model routing, stale-state and CLI-count claims now match reality. Two durable cli-pi contract notes were added: print mode exposes only the final assistant message, and captured stdout is hard-capped at 20 MB, so structured-output leaves must keep tool output bounded. Two suspected defects were closed without edits because the code was already correct, and a link-resolution and install-entry sweep ratified archive paths across the hub surface. This is internal tooling with no direct user-visible behavior change, but it removes misleading guidance and false smoke expectations, so future authors follow contracts that actually hold.

#### Skill READMEs rewritten purpose-first fleet-wide
The shared skill README template was refined from v1.8.0.6 to v1.9.0.0 to lead with outcome before tool names, add a capability-section pattern, an HVR enforcement block and versioning conventions, and a new parent-skill template (v1.0.0.0) now covers the six mandated hub surfaces for registry-routing parents. The create-skill workflow gained an explicit README authoring decision point and runs four checks (validator, HVR scan, link resolution, version field) before packaging. The whole fleet was then revisited on that standard: nine READMEs were rewritten purpose-first with a one-line pitch, problem-first overview, AT A GLANCE table and verification close — cli-external-orchestration, mcp-code-mode, mcp-tooling, sk-code, sk-design, sk-doc, sk-git, sk-prompt and system-deep-loop — each with a version bump and changelog entry. Stale claims were corrected along the way, including sk-prompt's real command `/prompt:improve`, sk-design's playbook count aligned to 35 scenarios across 9 categories, and version fields fixed to match release history (mcp-tooling 1.0.0.0 to 1.5.0.0). Prose was cleaned to the Human Voice Rules, and every durable fact was confirmed with fact batteries before each rewrite shipped. Framework users now land on a front door that states the delivered outcome within five seconds instead of a tabular reference card.

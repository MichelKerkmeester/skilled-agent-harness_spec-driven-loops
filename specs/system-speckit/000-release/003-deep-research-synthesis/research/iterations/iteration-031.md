#### Design motion mode gains tracked documentation
The shipped sk-design motion mode was running without any tracked specification, so a full reconstruction spec, plan, task list, and verification checklist were created from the intact source to close that gap. Before, the mode's contract lived only inside its skill files; after, its restraint gate, choreography workflow, and reduced-motion handoff are documented and inspectable. The entry preserves the named timing bands (100-150ms feedback, 200-300ms small state changes, 300-500ms modal or layout transitions, 500-800ms for earned entrances), ease-out entrances and ease-in exits, justified springs, and named duration/easing tokens. It also records the at-most-one procedure selection rule, the Read/Glob/Grep direct fallback, and the handoff of bounded mechanisms to the implementation workflow. This is internal documentation only, so no user-visible behavior changed.

#### Design audit mode gains tracked documentation
The shipped sk-design audit mode, the cross-cutting design QA and critique child, was missing from the tracked specification system, so a Level-2 reconstruction spec, plan, tasks, and checklist were authored from the intact source. Before, its evidence-backed review contract was undocumented in the spec system; after, its findings-first P0-P3 severity ordering, five-dimension `/20` scoring with rating bands, and the required report order are recorded. The entry captures the read-only boundary (Read/Glob/Grep only, no fixes applied, accepted findings handed to the implementation workflow), the accessibility seven-layer coverage matrix that gates any WCAG or release-ready claim, and the evidence labels that distinguish confirmed, inferred, and not-assessed findings. It also records that the two deterministic check scripts run only as downstream checks, never from the audit mode itself. This is internal documentation only, so no user-visible behavior changed.

#### Design token extraction mode gains tracked documentation
The shipped sk-design md-generator mode, which extracts measured design tokens from a live site and builds a v3 style reference, lacked a tracked specification and was reconstructed from its intact skill, references, procedures, and TypeScript backend. Before, the extraction boundary and write pipeline were only defined in source; after, the measured-only pipeline, five sampled viewports (1920, 1440, 768, 375, 320), and the deterministic `tokens.json`-to-document path are documented. The entry records that every value-bearing color, pixel, and spacing claim must trace verbatim to extracted tokens, that validation requires overall and claims scores of at least 80 with no critical failures, and that prose is kept separate from fenced, inert extracted values. It also captures the safety posture: approved output paths only, explicit overwrite handling, and no invented values when a source is unreachable. This is internal documentation only, so no user-visible behavior changed.

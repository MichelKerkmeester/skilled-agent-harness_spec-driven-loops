# Proposal: make /doctor:mcp Code-Mode-only

## Verdict: fix

Keep /doctor:mcp and its install/debug routes, but narrow both to Code Mode and its UTCP setup. The current install YAML defines Code Mode as its only registered server, then adds three unrelated CLI skill diagnostics; the router explicitly says those are included in install coverage (doctor-mcp-install.yaml:97-148; mcp.md:37, 73). The presentation also claims five servers, shows Skill Advisor and System Code Graph in install and debug reports, and gives a system_skill_advisor install example that is not a YAML server key (presentation.txt:9-14, 58-70, 138-184; doctor-mcp-debug.yaml:53-69, 239-247).

The single read-only health run returned unhealthy with exit code 2: it passed the launcher and UTCP JSON checks, but failed the manifest-derived Node engine check, missing dist/index.js, and missing node_modules (doctor-run.log:1-22). The checked-out Code Mode guide requires Node 24, and the lockfile declares >=24.0.0 <25.0.0, while the doctor only applies a generic >=20.11.0 prerequisite before it tries the missing manifest (INSTALL-GUIDE.md:144-163; package-lock.json:32-34; mcp-doctor.sh:100-110, 139-146). The current doctor scans only opencode.json, .claude/mcp.json, and .vscode/mcp.json; the repository has seven project registrations, and .vscode/mcp.json is absent (mcp-doctor.sh:259-280; opencode.json:10-20; .mcp.json:1-13; .claude/mcp.json:1-13; .codex/config.toml:11-16; .cursor/mcp.json:1-13; .pi/mcp.json:1-13; .devin/mcp_config.json:1-13; reality-check.md path table).

## Target behavior

/doctor:mcp install sets up the embedded Code Mode server, configures the selected existing runtime registrations, creates or preserves the root .utcp_config.json, adds one operator-selected UTCP manual, puts its credentials in the root .env, and ends with the read-only JSON health check. Code Mode exposes only manuals in .utcp_config.json; native MCP registrations are direct client tools and do not become UTCP manuals (SKILL.md:267-298, 321-354). Do not add separate MCP servers or CLI skill installers to this command.

## Exact install sequence

1. Preflight. Require Node 24 for this repository's embedded Code Mode build, plus npm and an MCP-compatible client; confirm the interpreter range through the server manifest and launcher because the launcher resolves from that manifest (INSTALL-GUIDE.md:144-167). The checked-out server manifest is currently missing even though package-lock.json declares the engine range; the workflow must stop before npm install/build when package.json is absent, report that the source manifest is missing, and leave the runtime configs untouched (package-lock.json:1-34; mcp-doctor.sh:139-146; doctor-run.log:13-17). Do not substitute host Node 26.8.2 for a passing engine check; that was the version reported by the generic preflight, while the manifest-based check returned an unknown range (doctor-run.log:9, 13).

2. Assess the embedded source. Check .skilled/skills/mcp-code-mode/mcp-server/package.json, package-lock.json, tsconfig.json, .skilled/bin/mcp-code-mode-launcher.cjs, and the existing dist/index.js and node_modules before changing anything; the workflow already identifies dist, node_modules, and the launcher as required installation checks (mcp-doctor.sh:139-146; doctor-mcp-install.yaml:97-110). If package.json is present and its engine range is satisfied, ask for approval before installing dependencies, then run: cd .skilled/skills/mcp-code-mode/mcp-server && npm install && npm run build. That is the existing YAML fallback command; after it succeeds, require both node_modules and dist/index.js to exist (doctor-mcp-install.yaml:108-113). The current checkout has no package.json, dist/index.js, or node_modules, so this command is a designed next step, not a command run during this audit (reality-check.md path table; doctor-run.log:13-17). Do not call scripts/install.sh as the sole build step: it installs dependencies and writes OpenCode wiring, but its verification checks for dist without invoking a build (install.sh:296-349, 351-400).

3. Create or preserve .utcp_config.json. If it is missing, create the guide's JSON skeleton with dotenv loading from .env, an in-memory tool repository, tag-and-description search, and an empty manual_call_templates array (INSTALL-GUIDE.md:223-245). If it already exists, preserve its current settings and append exactly one approved object to manual_call_templates, following the INSTALL-GUIDE example; the root file currently exists and already has that array (INSTALL-GUIDE.md:485-508; reality-check.md path table; .utcp_config.json:1-15). Prompt for a valid underscore-separated manual name, transport, server key, and connection details, then require approval before appending one object. Use call_template_type mcp and one mcpServers entry; for stdio, capture command, args, and env; for SSE, capture url and headers (configuration.md:162-185, 254-282). The manual name must be a valid JavaScript identifier (configuration.md:187-197). Use the operator's chosen local or package command, or URL; do not overwrite existing manuals (INSTALL-GUIDE.md:485-520).

4. Add the selected manual's credentials. Ask which environment variable names the manual needs, but do not echo their secret values. Keep secret values out of .utcp_config.json and runtime config files; place them in project-root .env and refer to them from the manual's env object or SSE headers using the Code Mode variable-substitution format (INSTALL-GUIDE.md:405-442; configuration.md:272-301). Prefix each .env key with the manual name plus underscore, such as example_service_API_TOKEN, because Code Mode applies the manual-name prefix when resolving variables (INSTALL-GUIDE.md:427-481; SKILL.md:331-348). The repository ignores .env and allows .env.example, so add only blank placeholders to .env.example and never put real credentials there (.gitignore:23-28). .env is absent now and is optional only when the selected manual needs external credentials (doctor-run.log:16; mcp-doctor.sh:216-224).

5. Register Code Mode in all seven existing project runtime configs by default; --runtime may narrow the operation to one supported target. Preserve each file's current format; leave matching entries unchanged and add the entry only when it is missing. Use runtime names opencode, claude, codex, cursor, pi, and devin; claude covers the existing .mcp.json and .claude/mcp.json entries (mcp.md:3, 51-54; reality-check.md path table). The repository values are:
   - opencode.json: mcp.code_mode with type local, command array node plus .skilled/bin/mcp-code-mode-launcher.cjs, and environment.UTCP_CONFIG_FILE set to .utcp_config.json (opencode.json:10-20).
   - .mcp.json: mcpServers.code_mode with command node, args containing the launcher, and env.UTCP_CONFIG_FILE set to .utcp_config.json (.mcp.json:1-13).
   - .claude/mcp.json: same mcpServers format and launcher target (.claude/mcp.json:1-13).
   - .codex/config.toml: [mcp_servers.code_mode], command node, launcher args, and UTCP_CONFIG_FILE = ".utcp_config.json" (.codex/config.toml:11-16).
   - .cursor/mcp.json: same mcpServers format and launcher target (.cursor/mcp.json:1-13).
   - .pi/mcp.json: same entry, preserving transport stdio and lifecycle lazy (.pi/mcp.json:1-13).
   - .devin/mcp_config.json: same mcpServers format and launcher target (.devin/mcp_config.json:1-13).
   - Hermes is user-level rather than repository-configured. Show the documented operator command, then the separate tool-enabling step; do not invent a project .hermes/config.yaml. The current manifest's command is printf 'Y\n' | hermes mcp add code_mode --command node --env UTCP_CONFIG_FILE=.utcp_config.json --args .skilled/bin/mcp-code-mode-launcher.cjs, followed by hermes tools enable code_mode:<tool>; the session must include code_mode (.hermes/SYNC.md:8-14, 37-44).
   - Do not offer .vscode/mcp.json as an existing repository runtime target: the file is absent (reality-check.md path table). Remove it from the doctor YAML's runtime map unless the operator later adds it.

6. Verify and summarize. Run python3 -m json.tool < .utcp_config.json and use Node JSON.parse for each edited JSON config. If .codex/config.toml is selected, validate it with Python 3.11 tomllib using python3 -c 'import pathlib, tomllib; tomllib.loads(pathlib.Path(".codex/config.toml").read_text())'; the current grep check only looks for a section header and does not validate TOML syntax (INSTALL-GUIDE.md:689-697; doctor-mcp-install.yaml:264-267; mcp-doctor-lib.sh:233-236). Check that chosen credential keys are present without printing values (INSTALL-GUIDE.md:689-697). Then run bash .skilled/commands/doctor/scripts/mcp-doctor.sh --json and summarize each Code Mode build, UTCP, and runtime-registration result; this is the install YAML's existing verification command (doctor-mcp-install.yaml:271-283). The current doctor only checks three project configs and has no Hermes project file to inspect, so its config checker must be expanded for the seven project files and must identify Hermes as user-level/operator-managed rather than pretend it is a project file (mcp-doctor.sh:259-280; .hermes/SYNC.md:8-14, 37-44). The health run in this audit is the baseline, not a post-install pass (doctor-run.log:1-22).

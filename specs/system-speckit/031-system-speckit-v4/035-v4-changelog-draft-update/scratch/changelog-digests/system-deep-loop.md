### v2.2.4.0 (`v2.2.4.0.md`)

Adds artifact-progress liveness to the fan-out runner so a non-streaming executor is judged live while it is genuinely working. A per-lineage poller in `runtime/scripts/fanout-run.cjs` watches the lineage artifact directory and resets the stall watchdog when on-disk output advances, and `runtime/scripts/fanout-pool.cjs` threads that callback into the worker context so the pool stall clock resets and the post-exit orphan watchdog treats fresh writes inside its grace window as still working. Four unit tests landed in `runtime/tests/unit/fanout-pool.vitest.ts`. The entry is unusually honest about its own premise: the reported cli-pi "requeues to death" symptom was disproved under controlled reproduction, the shipped runtime never arms the lag-ceiling abort, `stall_detected` is advisory only, and no ledger records a real `orphan_requeue`, so the release is bounded defense in depth rather than a fix for a live loop. Known caveat recorded: the tested pi config buffers all disk writes to the end of a run, so it still logs one advisory stall warning and completes anyway.

### v2.2.2.0 (`v2.2.2.0.md`)

Hardens the shared fan-out lineage prompt in `runtime/scripts/fanout-run.cjs` (`buildLoopPrompt`) that every mode's fan-out lineage renders. The old boundary said only that a lineage must not touch paths outside its lineage directory, and a cheaper model (DeepSeek Flash) read that as license to run the repo's own tooling during an observation pass, running `generate-context.js` and `validate.sh`, editing files across the tree and getting failed by write-containment for reverting eight out-of-scope tracked paths. The prompt now names the exact tooling to avoid, meaning `generate-context.js`, `validate.sh` (especially `--recursive`) and any `git` write, checkout or commit. Because the write boundary is loop-type agnostic and executor agnostic, the one change reaches every mode on cli-opencode and cli-pi alike. A regression test landed in `runtime/tests/stress/cli-adapter/fanout.vitest.ts`. Proven live: a two-executor fan-out review went from 1 succeeded and 1 failed to 2 succeeded and 0 failed, and the DeepSeek lineage's forbidden-tool invocations dropped from 26/24 to 0/0. The `write-containment.ts` enforcement layer was deliberately left untouched, since the hardening improves the odds rather than replacing the net.

## Facts the v4 draft gets wrong or misses

- The draft understates the alignment removal. Draft line 165 says only "An alignment mode was built during the cycle and removed before release", and draft line 445 lists "the `deep-alignment` mode" among removed surfaces. `v3.0.0.0.md` states the removal was a cascade that also retired the `/deep:command-benchmark` command and the `/create:benchmark` `conformance_benchmark` family branch, plus the `sk-create-benchmark` conformance authoring templates. A reader who used `/deep:command-benchmark` or authored a conformance benchmark package gets no warning anywhere in the draft.
- The draft never states that the `/deep:*` command count dropped from eight to six. Draft line 26 says the hub ships "six `/deep:*` commands" and draft line 456 says "The six modes behave as before", both correct as end states, but `v3.0.0.0.md` records the eight-to-six and seven-to-six transitions explicitly and calls them public surface, which is why it took a major version.
- Draft line 191 says "All seven ledger modes are now on the authoritative path". `v3.0.0.0.md` reduces the hub to six registered modes, and the live `mode-registry.json` lists exactly six `workflowMode` values (`research`, `review`, `ai-council`, `agent-improvement`, `model-benchmark`, `skill-benchmark`) with an empty `deprecatedModes` array. The seven-mode count reads as stale relative to the final release state. I did not find a ledger-specific mode list in these entries, so if "ledger modes" is a distinct axis the number may still be defensible, but as written it contradicts the six-mode framing on lines 26, 165 and 456.
- RENAME missed by the draft's "Repoint what moved" list at line 444: `v2.2.3.0.md` moved the hub's second-stage surface router from `shared/references/smart-routing.md` to root `ROUTER.md` and deleted the legacy file. Anything referencing the old `smart-routing.md` path breaks, and the draft's repointing list does not mention it.
- The draft is silent on Gemini remaining available through the executor rosters. Draft line 445 says "`cli-gemini` and `cli-copilot` are gone", which is about the orchestrator skills, but `v2.2.1.0.md` adds `gemini-3.7-flash-high` to the Cursor allowlist and `gemini-3-7-flash-high` to the Devin allowlist as dispatch-tested ids. A reader could reasonably conclude from line 445 that Gemini is unreachable from a deep loop, which these entries contradict.
- The draft's roster claim at line 218 credits DeepSeek V4 Flash to Pi only. `v2.2.0.0.md` records DeepSeek max tiers (`deepseek-v4-flash-max`, `deepseek-v4-pro-max`) on the Devin roster as well, and `v2.2.2.0.md` and `v2.2.4.0.md` both exercise DeepSeek through cli-opencode and cli-pi. The draft's "closed roster per executor" bullet at line 176 is correct in mechanism but does not convey that DeepSeek spans more than one executor.
- Draft line 175 compresses the fan-out hardening into "Each lineage's writes are contained". That is accurate as far as it goes and matches `v2.2.2.0.md`'s `write-containment.ts` net, but the draft omits the two named hardening releases: the weak-model prompt boundary in `v2.2.2.0.md` and the artifact-progress liveness in `v2.2.4.0.md`. Both are behavior a fan-out operator would notice, particularly the `v2.2.4.0.md` caveat that a fully buffering executor still logs an advisory `stall_detected` warning while completing normally.
- Verified as correct, not a defect: draft line 165's claim that the `deep-loop-workflows` and `deep-loop-runtime` identities no longer exist. `v2.0.0.0.md` left both as temporary compat symlinks, and `ls` under `.opencode/skills/` confirms neither path is present now.

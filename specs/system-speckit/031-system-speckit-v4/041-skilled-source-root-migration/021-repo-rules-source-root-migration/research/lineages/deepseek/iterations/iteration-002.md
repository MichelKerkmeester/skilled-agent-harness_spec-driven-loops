### C. `repo-rules-corpus.yml`

11. The workflow keys on four path filters in both the PR and push blocks: `REPO RULES.md`, `repo-rules/**`, and the checker under both roots (`.opencode/skills/sk-doc/sk-create-repo-rule/scripts/check-repo-rules.cjs` and `.skilled/...`), lines 5-9 and 12-16. The job runs `GUARD=".opencode/skills/.../check-repo-rules.cjs"`, fails closed when the guard is missing (lines 35-38), and runs the checker with node (line 39). [SOURCE: repo-rules-corpus.yml:5-16,29-44]

12. After the move, `repo-rules/**` alone no longer fires on canonical corpus edits (`.skilled/repo-rules/**`), so the filter must name the canonical path. But adding `.skilled/repo-rules/**` triggers the gate-inputs filter-twins rule: every workflow filter entry matching `^!?\.(opencode|skilled)/` must have its opposite-root twin **in the same `paths:` group**, and `twin()` only swaps `.opencode` ↔ `.skilled`. A lone `.skilled/repo-rules/**` entry therefore fails with `path filter .skilled/repo-rules/** has no twin .opencode/repo-rules/**` unless `.opencode/repo-rules/**` is added to the same group. Entries spelled `repo-rules/**` are not twin-checked because they do not match the root prefix. [SOURCE: check-gate-inputs.sh:113-116 (twin),356,369 (record),413 (verdict)] [SOURCE: repo-rules-corpus.yml:5-16]

### D. `.github/scripts/check-gate-inputs.sh`

### E. Trigger index, corpus-manifest, generation-diagnostics, phrase-variants

15. The generator walks exactly three roots: `CORPUS_ROOTS = ['specs', '.skilled/skills', '.skilled/hooks']` (re-spelled under whichever source root a checkout carries), and deliberately excludes the five runtime mirrors and the root `README.md`. `repo-rules/` is not a walked root, so moving the corpus changes no walked path. [SOURCE: lib/corpus.mjs:20-29,43-50] [SOURCE: README.md:20 (generates from specs/, .skilled/skills/, .skilled/hooks/)]

One corpus hash folds every walked file as `path + NUL + content + LF` (lines 141-145), one `manifestHash = sha256(stableStringify(manifestIdentity))` is computed at line 211 and embedded across the artifact set (sites at 217, 225, 276, 285); `publishJson` writes via a pid-suffixed temp file and `renameSync` (atomic publish, canonical text). [SOURCE: generate-trigger-index.mjs:64-67,141-145,211,217,225,276,285] [SOURCE: lib/artifact.mjs:108-128]

17. Byte-identical regeneration is a tested property: the suite asserts a byte-identical artifact on a second run over the same corpus (`trigger-index.vitest.ts:376`), that the published text equals the canonical `stableStringify` serialization (line 185), and that `manifest.manifestHash === report.manifestHash === index.manifestHash` with `variants.manifestHash === index.manifestHash` (lines 152, 169, 407-408). The documented determinism check runs the generator twice and diffs `indexSha256` (README §7). [SOURCE: trigger-index.vitest.ts:152,169,185,376,407-408] [SOURCE: README.md:136-145]

18. There is no `--check`/dry-run mode: the CLI flags are `--repo-root`, `--allow-malformed`, `--json`, `--quiet`, and the run publishes (exit 0) or refuses and publishes nothing (exit 1). Verifying "regenerated with no drift" for the migration therefore means running the generator (a write) and diffing the working tree — a step for the implementation, not a read-only check. [SOURCE: generate-trigger-index.mjs:27 (usage),31 (exit codes),369-405 (publish path),449-486 (flags)]

19. Migration consequence: because the migration edits walked documents (`.skilled/skills/sk-doc/sk-create-repo-rule/**`), the corpus hash and therefore `manifestHash` change, and all four artifacts are rewritten in the same change even though the phrase inventory is unaffected by moving `repo-rules/`. The frozen captured-once fixtures (latency-report, semantic-probes, prompt-set, recipe-execution, daemon-off-proof) pin their snapshot's `manifestHash` and are explicitly not refreshed; `corpus-manifest.json`, `generation-diagnostics.json` and `phrase-variants.json` are the opposite and every generator run rewrites them. A committed manifest whose hash differs from the committed index is what `/doctor speckit-retrieval` flags as a pair one run did not produce; no CI workflow invokes that doctor check (INFERRED from the absence of hits in `.github/`). [SOURCE: README.md:76-78] [SOURCE: rg over .github → no speckit-retrieval invocation]

## Questions Answered

- Which mirrors are generated from which authored source: `.skilled/agents/*.md` is the authoring source; `.claude` is the parity-enforced mirror and the cursor/devin dialect source; `.pi` and `.codex` are generated; `.hermes/skills` is generated from skill SKILL.md files plus agent personas.
- Which script checks each: `check-agent-mirror-sync.cjs` (claude/codex/opencode), `sync-agents.cjs --check` (codex), `agent-roster-mirror-check.cjs` (five-runtime roster), `sync-skills-hermes.cjs --check` (hermes), `sync-agents-pi.cjs --check` (pi, documented but not CI-wired).
- What the two gate surfaces key on: path filters + fail-closed guard for the corpus workflow; five text-parsing rules and strict `.opencode`/`.skilled` twin matching for gate inputs.
- Byte-identical regeneration: deterministic and tested for an unchanged corpus; the migration must regenerate all four artifacts because the embedded `manifestHash` covers every walked file's bytes.

## Ruled Out

- Treating `.claude/agents` as an unmanaged copy: parity is enforced by check-agent-mirror-sync with `.claude` as a required mirror, and roster coverage links cursor/devin to it.
- Treating `.hermes/skills` as covering all sk-doc docs: it mirrors one SKILL.md per skill, so references and the playbook do not ripple to Hermes.
- Assuming the trigger index walks `repo-rules/`: the walk roots are specs, .skilled/skills and .skilled/hooks only.
- Assuming a `--check` mode exists for the trigger index: it publishes or refuses; drift verification is regenerate-and-diff.

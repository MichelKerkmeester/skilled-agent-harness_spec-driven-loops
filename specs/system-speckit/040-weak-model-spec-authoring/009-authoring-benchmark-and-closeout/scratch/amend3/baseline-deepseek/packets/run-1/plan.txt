## 1. SUMMARY

### Technical Context

| Aspect | Value |
|--------|-------|
| **Language/Stack** | Bash (3.2+; the script must run on macOS system bash) |
| **Framework** | None; standalone CLI script under `runtime/cli/spec/` |
| **Storage** | None; the script reads no files and writes none |
| **Testing** | Shell regression harness plus `bash -n` syntax checks |

### Overview

The change is a single boolean and one branch. The argument parser learns
`--quiet` and `-q`, a `QUIET_OUTPUT` global joins `JSON_OUTPUT`, and
`output_text()` returns after printing the recommended-level line when quiet is
set. `output_json()` is not touched, so the JSON contract and the command assets
that consume it stay stable. The harness captures default output before the edit
and diffs it after, which is the proof that the flag is additive.

<!-- ANCHOR:architecture -->
## 3. ARCHITECTURE

### Pattern

Single-file CLI with a parse, score, render pipeline. The new flag is an output
modifier, not a scoring input, so it belongs to the render stage and must not
reach the scoring functions.

### Key Components

- **Argument parser** (`§5 MAIN SCRIPT`): the `while [[ $# -gt 0 ]]` loop that
  maps flags to globals. Gains `--quiet|-q`.
- **Scoring engine** (`calculate_*`, `determine_level`, `determine_phasing`):
  unchanged. It never reads the quiet flag.
- **Text renderer** (`output_text()`): owns the human-readable report. Gains the
  quiet early return.
- **JSON renderer** (`output_json()`): unchanged. Quiet is a documented no-op
  here.
- **Help surface** (file header OPTIONS block and `show_help()`): documents the
  new flag and the JSON composition rule.

### Data Flow

```
argv -> parser -> LOC / FILES / risk booleans / JSON_OUTPUT / QUIET_OUTPUT
                            |
                            v
              scoring engine (unchanged)
                            |
              +-------------+-------------+
              v                           v
     QUIET_OUTPUT = true          QUIET_OUTPUT = false
     one-line renderer            full text renderer
              |                           |
              +-------------+-------------+
                            v
                  JSON_OUTPUT = true
                  (quiet ignored, JSON rendered)
```

The quiet branch sits after scoring and before any report formatting, so it
cannot influence the level, the score or the confidence.

## L3: ARCHITECTURE DECISION RECORD

### ADR-001: Quiet applies to the text renderer only

**Status**: Accepted

**Context**: The script has two output contracts. `output_text()` serves humans
and shell callers; `output_json()` serves the `speckit-plan.yaml` and
`speckit-complete.yaml` command assets. A quiet flag could either filter both or
filter only the human report.

**Decision**: `--quiet` branches inside `output_text()` and is a documented no-op
with `--json`. The JSON schema stays single, and JSON callers keep the payload
they already parse.

**Consequences**:
- Positive: no JSON schema fork, no consumer changes, one obvious place to read
  the quiet behavior.
- Negative: a JSON caller cannot ask for a reduced payload. Mitigation: the
  payload already carries `recommended_level` as its first field, so a consumer
  that wants one value can select it.

**Alternatives Rejected**:
- Quiet filters both renderers: it would either change the JSON schema or emit a
  second, quiet-only JSON shape, both of which break the existing contract.
- Quiet plus JSON is a usage error: it turns a harmless combination into a
  failure and adds a validation branch for no benefit.

---

### ADR-002: Follow the sibling `--quiet, -q` convention

**Status**: Accepted

**Context**: `validate.sh`, `progressive-validate.sh` and `check-completion.sh`
already expose `--quiet` with the `-q` alias. The new flag could use a different
name, such as `--level-only`, or match the convention.

**Decision**: Use `--quiet` and `-q`, matching the sibling scripts.

**Consequences**:
- Positive: one vocabulary across the spec CLI; users transfer the flag without
  reading help.
- Negative: `--quiet` in the siblings means "minimal output", while here it means
  "one line". Mitigation: the help text states the exact line that is printed.

**Alternatives Rejected**:
- `--level-only`: more precise, but it adds a second quiet vocabulary to the same
  CLI family.
- `--porcelain`: conventional for stable machine output, but it implies a
  format guarantee this change does not need.

---

### ADR-003: Guard inside `output_text()` rather than at the dispatch site

**Status**: Accepted

**Context**: The quiet branch could live in the `§7 OUTPUT RESULTS` dispatch or
inside `output_text()`.

**Decision**: Put the early return at the top of `output_text()`. The dispatch
stays a two-way choice between the renderers, and the quiet behavior lives with
the report it suppresses.

**Consequences**:
- Positive: one function owns all text-output decisions; the dispatch remains
  unchanged.
- Negative: `output_text()` grows by one branch. Mitigation: the branch is three
  lines and returns immediately.

**Alternatives Rejected**:
- A third `output_quiet()` renderer: it duplicates the format string, which then
  has two homes and can drift from the report's first line.
- Dispatch-site guard: it splits knowledge of the report format across two
  functions.

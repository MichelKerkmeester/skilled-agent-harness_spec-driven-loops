## 1. SUMMARY

### Technical Context

| Aspect | Value |
|--------|-------|
| **Language/Stack** | Bash (3.2-compatible, `set -euo pipefail`) |
| **Framework** | None; a standalone CLI script under `runtime/cli/spec/` |
| **Storage** | None; the script reads arguments and writes stdout/stderr |
| **Testing** | Bash invocation checks plus the existing Node suites `tests/test-phase-system.js` and `tests/test-phase-validation.js` |

### Overview

The change lives entirely in `recommend-level.sh`: one `QUIET` global beside the other output flags, one `--quiet` case in the argument parser, one conflict check after parsing, and one output dispatch that prints the level line instead of calling `output_text()`. The technical approach is deliberately additive — no scoring function, no threshold constant, and no existing emitter changes, so the default output cannot drift by construction and the proof is a diff against a captured baseline.

## 3. ARCHITECTURE

### Pattern

Single script branch: one new output path beside the existing text and JSON paths.

### Key Components
- **`recommend-level.sh` argument parser**: reads `$@`, sets `LOC`, `FILES`, the risk flags, `RECOMMEND_PHASES`, `PHASE_THRESHOLD`, `JSON_OUTPUT`, and now `QUIET`.
- **`output_text()`**: the sixteen-line human report; unchanged, and not called when `QUIET` is true.
- **`output_json()`**: the JSON document; unchanged, and still reachable only when `JSON_OUTPUT` is true and `QUIET` is false.
- **Quiet emitter**: one `printf` of `Recommended Level: <N> (<Name>)` in the output dispatch block.

### Data Flow

`$@` → parser sets `QUIET` → numeric and required-input validation (unchanged, exits 1 on failure) → score calculation and `determine_level()` (unchanged) → output dispatch: `QUIET` prints the one line, else `JSON_OUTPUT` calls `output_json()`, else `output_text()`. The conflict check sits between parsing and validation so a contradictory invocation fails before any work runs.

## L3: ARCHITECTURE DECISION RECORD

### ADR-001: Print the existing label behind `--quiet`, and reject `--quiet` with `--json`

**Status**: Proposed

**Context**: The script already prints `Recommended Level: <N> (<Name>)` inside its human report, and it already has a machine format in `--json`. A quiet flag has to decide two things: what the one line looks like, and what happens when a caller asks for both machine formats at once.

**Decision**: `--quiet` prints the same label the report prints, on its own line, with no leading blank line. A `--quiet` and `--json` invocation is a usage error: the message goes to stderr, stdout stays empty, and the exit code is 1.

**Consequences**:
- A caller can move from `grep '^Recommended Level:'` on the report to `--quiet` without changing its pattern.
- The label becomes a public contract, so a future rename is a breaking change that needs its own packet.
- A contradictory invocation fails loudly instead of producing output the caller did not ask for, at the cost of one more error message to document.

**Alternatives Rejected**:
- Bare integer output (`0`): it is marginally easier to consume but drops the level name and gives a caller no stable prefix to anchor on.
- `--quiet` wins over `--json`: silent precedence produces a text line for a caller that asked for JSON, which is the failure mode hardest to notice.
- A new `--format level` option: a larger surface for the same one-line result, and it would invite a second format later.

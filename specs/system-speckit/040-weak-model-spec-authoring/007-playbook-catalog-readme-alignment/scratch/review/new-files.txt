     8	# 481 -- Authoring card loaded by four intents
     9	
    10	## 1. OVERVIEW
    11	
    12	This scenario validates the router change phase 5 makes. The `RESOURCE_MAP` in `SKILL.md` sends four authoring intents to a short card. The long template guide stays reachable from `ON_DEMAND` only. The scenario counts the card and guide lines inside the four intent blocks and inside the on demand list.
    13	
    14	### Why This Matters
    15	
    16	A weak model follows the first document it is given. If an authoring intent still loads the 1,200 line guide, the model spends its context on the long path and never sees the card. The counts prove the router points at the short path and keeps the long one for a deliberate lookup.
    17	
    18	---
    19	
    20	## 2. SCENARIO CONTRACT
    21	
    22	Operators count the card and guide lines in the router and read three numbers.
    23	
    24	- Objective: Prove that the four authoring intent blocks name the card four times and the guide zero times, and that the on demand list names the guide once.
    25	- Playbook ID: 481.
    26	- Real user request: `Show me which authoring document each writing intent loads, and confirm the long guide is only an on-demand lookup now.`
    27	- Prompt: `Show me which authoring document each writing intent loads, and confirm the long guide is only an on-demand lookup now.`
    28	- Preconditions: A checkout with `awk` on PATH and phase 5 closed so `SKILL.md` and the card exist. The scenario needs no network.
    29	- Expected execution process: Run one `awk` count over the four intent blocks for the card, one for the guide, and one over the on demand list for the guide.
    30	- Expected signals: The card count prints `4`. The intent guide count prints `0`. The on demand guide count prints `1`.
    31	- Desired user-visible outcome: The operator sees the four intents load the card and the guide held for an on demand read.
    32	- Pass/fail: PASS if the three counts are `4`, `0` and `1` in that order. FAIL if any count differs.

    12	# Versioned placeholder gate
    13	
    14	## 1. OVERVIEW
    15	
    16	The versioned placeholder gate decides the severity of an unfilled authoring token from the template stamp a document carries. A document stamped v2.3 or later warns while the packet status is Draft and fails at any other status. A document with an older stamp, or with no stamp, keeps the error it always had.
    17	
    18	The gate exists so a planning commit can land with tokens still in place, while a finished packet cannot. It also keeps every existing packet on its old verdict, because a new rule that failed them would break an external repository on update.
    19	
    20	---
    21	
    22	## 2. HOW IT WORKS
    23	
    24	### Stamp Detection
    25	
    26	The rule reads the first 70 lines of each document for a `SPECKIT_TEMPLATE_SOURCE` line. A version of v2.3 or later opens the gate. A version of v2.2 or earlier, or no line at all, leaves the document on the old rule.
    27	
    28	### Draft Lifecycle
    29	
    30	When the gate is open, the rule reads the first Status row of the packet's `spec.md`. The exact word Draft, ignoring case, bold marks, backticks, quotes and trailing punctuation, makes an unfilled token a warning. Every other value, and a missing Status row, makes it an error. An open question marker is an error in both cases.
    31	
    32	A warning does not fail `--strict`. The run passes when no other rule reports an error.
    33	
    34	### Scope
    35	
    36	The orchestrator reads every authored document that is present. The shell mirror reads `spec.md`, `plan.md`, `tasks.md` and `decision-record.md`, and it adds `acceptance-criteria.md`, `implementation-summary.md` and `goal.md` only when they carry the stamp. Both implementations answer with the same verdict, and one test file compares them.
    37	
    38	### Edge Cases
    39	
    40	A fenced code block is skipped, so a token shown in an example does not fail a document. A token inside an inline code span is skipped for the same reason. A status such as `Draft (phase 3)` is not the word Draft, so it counts as any other value.

    12	# Template section fill guidance
    13	
    14	## 1. OVERVIEW
    15	
    16	Template section fill guidance is the line below each content heading in the packet templates. It tells a writer the one action the section needs, then shows a good answer and a weak answer. A token alone says what to replace. The fill line says what a finished answer looks like.
    17	
    18	The guidance covers every content section of the four core templates and the ten addon templates. The `TEMPLATE INSTRUCTIONS` and `Author Instructions` headings hold fixed instructions and get no fill line.
    19	
    20	---
    21	
    22	## 2. HOW IT WORKS
    23	
    24	### The Fill Line
    25	
    26	Each line is one HTML comment that starts with `FILL:`. It sits directly below the section heading and stays on one physical line, so a renderer cannot break the section. The line names the action, then a good example, then a weak example where the section needs both.
    27	
    28	The text never holds an authoring token or an open question marker. A test renders the templates and fails when a section lacks its fill line, holds two of them, or carries a token inside one.
    29	
    30	### Render and Anchor Guards
    31	
    32	The fill guidance test renders all 16 level and document pairs. It compares the anchor count with a frozen table and checks one fill line per section. The golden snapshot test renders every level and compares the result with a stored file, so a change that moves a heading or prunes a gated block fails before it ships.
    33	
    34	### Example Alignment
    35	
    36	The hand-written examples a model copies carry the same anchors as their templates. The example drift guard compares each example with its template and reports a missing or extra anchor. The fill line and the anchor count are tested together, because a fill line inside a pruned block changes the rendered shape.

    15	
    16	The example drift guard is a read-only script that compares the hand-written example packets with the templates they came from. A model copies an example, so a drifted example teaches the model a structure the validator no longer expects.
    17	
    18	The guard reports one line per problem and exits 1 on any drift. It exits 0 and prints `EXAMPLE_DRIFT_OK` when every example agrees with its template.

    22	## 2. HOW IT WORKS
    23	
    24	### Anchor Comparison
    25	
    26	The guard calls `runtime/cli/utils/template-structure.js compare <level> <doc> <example> anchors`. It fails on every `missing_anchor` line and every `extra_anchor` line. The compare step reads the level contract, so the guard inherits the required and optional anchor lists instead of hard-coding a copy.
    27	
    28	### Description Check
    29	
    30	The guard reads the first `description:` line of each example. It fails when the line holds the end of an HTML comment, starts lowercase, or lacks a closing period. Those three defects were the leaked line phase 2 repaired, and the check keeps them from coming back.
    31	
    32	### Invocation
    33	
    34	The script takes one optional directory. With no argument it reads `templates/examples`. With an argument it reads that directory, which lets a test run it against a scratch copy. A vitest wrapper runs it in the suite.

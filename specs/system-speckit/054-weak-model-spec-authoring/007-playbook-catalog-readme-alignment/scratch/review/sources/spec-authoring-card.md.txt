    14	# Spec Authoring Card
    15	
    16	This card is the short path. Follow the steps in order. Each step has one action, one acceptance line and one command. When the command prints what the acceptance line says, go to the next step.
    17	
    18	`references/templates/template-guide.md` is the long guide. Read it only when this card sends you there.
    19	
    20	## 1. BOUNDS
    21	
    22	You write one packet, in one folder. The folder is the one `create.sh` prints.
    23	
    24	Allowed writes: the packet folder and its `scratch/` folder.
    25	Forbidden: `git commit`, `git push`, `git checkout`, `git switch`, `git branch`, `git reset`, `git stash`, `generate-context.js`, `/speckit:save`. Do not edit `.skilled/`, another packet or a source file. Do not run `create.sh` twice.
    26	
    27	Acceptance: you can name the packet folder and the one command you will run to check it.
    28	Verify: `pwd` prints the repository root, and `ls <packet folder>` lists `spec.md`.
    29	
    30	## 2. PICK THE LEVEL
    31	
    32	Run the level helper first.
    33	
    34	```bash
    35	bash .skilled/skills/system-spec-kit/runtime/cli/spec/recommend-level.sh --loc <lines> --files <count>
    36	```
    37	
    38	Use the level it prints. If it prints Level 0, use `--level 1`. Do not raise the level yourself. The level decides which files the packet needs.
    39	
    40	| Level | Files the packet needs |
    41	|-------|------------------------|
    42	| 1 | `spec.md`, `plan.md`, `tasks.md`, and `implementation-summary.md` once implementation starts |
    43	| 2 | the Level 1 files plus `acceptance-criteria.md` |
    44	| 3 | the Level 2 files plus the architecture sections and a decision record when one is written |
    45	
    46	Acceptance: the level in the scaffold header matches the level the helper printed.
    47	Verify: `rg -n 'SPECKIT_LEVEL' <packet folder>/spec.md` prints one line with that level.
    48	
    49	## 3. SCAFFOLD
    50	
    51	Create the packet with one command. Keep `--skip-branch` so no git state changes.
    52	
    53	```bash
    54	bash .skilled/skills/system-spec-kit/runtime/cli/spec/create.sh --skip-branch --with-goal --level <level> --track <track> --short-name <two-to-four-words> "<one sentence>"
    55	```
    56	
    57	The command prints the folder it made. Use that path for every later command.
    58	
    59	Acceptance: the folder holds `spec.md`, `plan.md`, `tasks.md` and `scratch/`.
    60	Verify: `ls <packet folder>` lists those names.
    61	
    62	## 4. READ BEFORE YOU WRITE
    63	
    64	Open one rendered example at the same level under `.skilled/skills/system-spec-kit/templates/examples/level-<level>/`. Read `spec.md` and `tasks.md`.
    65	
    66	Do not copy from a `.tmpl` file. A `.tmpl` file carries tokens and gate markers. The examples are filled and safe to imitate for shape.
    67	
    68	Each section of your scaffold carries a fill note. The note says what that section needs. Read the note before you write the section. The note is the contract for that section.
    69	
    70	Acceptance: you can say, in one sentence, what the first section of `spec.md` must contain.
    71	Verify: `sed -n '1,40p' <packet folder>/spec.md` shows the fill notes.
    72	
    73	## 5. ONE ACTION PER SECTION
    74	
    75	Each section does one job. Write one idea per paragraph. Do not repeat the same fact in two sections.
    76	
    77	- `spec.md` states the problem, the scope, the requirements and the success criteria.
    78	- `plan.md` states the approach, the files to change, the test plan and the dependencies.
    79	- `tasks.md` states the ordered actions.
    80	- `implementation-summary.md` states what changed and how it was checked. Write it last.
    81	
    82	Do not put a task list in `spec.md`. Do not put requirements in `plan.md`.
    83	
    84	Acceptance: every heading in the packet has content under it, and no heading holds content that belongs to another heading.
    85	Verify: `rg -n '^## ' <packet folder>/spec.md <packet folder>/plan.md` lists the headings you filled.
    86	
    87	## 6. THE PLAN SHAPE
    88	
    89	A plan has 3 or 4 steps. More than 4 steps means the feature is too large for one packet. Split it or raise the level.
    90	
    91	Each step carries three lines:
    92	1. What the step does.
    93	2. The acceptance line: what is true when the step is done.
    94	3. The verify command: the command a reader runs, and the text it prints.
    95	
    96	```markdown
    97	### Step 1: Add the flag parser
    98	
    99	Acceptance: `--quiet` is accepted and the default output is unchanged.
   100	Verify: `bash script.sh --quiet` prints one line.
   101	```
   102	
   103	Acceptance: `plan.md` holds 3 or 4 steps, and each step has an acceptance line and a verify command.
   104	Verify: `rg -c '^### Step ' <packet folder>/plan.md` prints 3 or 4.
   105	
   106	## 7. TASK LINES
   107	
   108	Every task line has one action, one file and one verify clause.
   109	
   110	```markdown
   111	- [ ] T001 Add the quiet flag to the option parser (`runtime/cli/spec/script.sh`). Verify: `bash runtime/cli/spec/script.sh --quiet` prints one line.
   112	```
   113	
   114	Rules:
   115	- One action per task.
   116	- Name the file in parentheses.
   117	- End with `Verify:` and the command plus its expected output.
   118	- Put the tasks in the order you will run them.
   119	- Mark a task `[x]` only after its verify command printed the expected output.
   120	
   121	Acceptance: every task line ends with a `Verify:` clause.
   122	Verify: `rg -c 'Verify: ' <packet folder>/tasks.md` and `rg -c '^- \[ \] T[0-9]' <packet folder>/tasks.md` print the same number.
   123	
   124	## 8. FILL EVERY TOKEN
   125	
   126	A scaffold stamped `v2.3` or later carries tokens. A token starts with `[YOUR_VALUE_HERE:` and ends at the next closing bracket. Replace the whole token, brackets included, with real content. Do not leave a token in a finished packet.
   127	
   128	If you cannot answer a question the token asks, write `UNKNOWN` in its place and write an open question in `goal.md` section 4.
   129	
   130	A token in a packet whose `spec.md` says `Status: Draft` is a warning, so strict validation can pass with tokens still in the file. A token in any other status is an error. Do not use the warning as permission. Count the tokens.
   131	
   132	Acceptance: the count is 0.
   133	Verify: `rg -o '\[YOUR_VALUE_HERE: ' <packet folder>/spec.md <packet folder>/plan.md <packet folder>/tasks.md | wc -l` prints 0.
   134	
   135	## 9. VALIDATE
   136	
   137	Run the validator before you claim the packet is done.
   138	
   139	```bash
   140	bash .skilled/skills/system-spec-kit/runtime/cli/spec/validate.sh <packet folder> --strict
   141	```
   142	
   143	The last line must be `RESULT: PASSED`. Read the summary line above it. `Errors: 0` is the pass condition. Warnings do not block the pass, but read them.
   144	
   145	When it fails, read the first failing rule. Fix that rule only. Run the command again. Stop after three fixes on the same rule and write the rule and the error in the packet's `goal.md`.
   146	
   147	Acceptance: the command prints `RESULT: PASSED` and `Errors: 0`.
   148	Verify: `bash .skilled/skills/system-spec-kit/runtime/cli/spec/validate.sh <packet folder> --strict | tail -1` prints `RESULT: PASSED`.
   149	
   150	## 10. CLOSE
   151	
   152	A packet is closeable when:
   153	- every required file exists for its level
   154	- every token is filled, or replaced with `UNKNOWN` and an open question in `goal.md`
   155	- `tasks.md` has no `[B]` line
   156	- `implementation-summary.md` names the files that changed
   157	- `validate.sh --strict` prints `RESULT: PASSED`
   158	
   159	Acceptance: all five are true.
   160	Verify: run the five commands in this card in order, then run the validator once more. The last line prints `RESULT: PASSED`.
   161	
   162	## 11. WHEN TO STOP AND ASK
   163	
   164	Stop and write the question in `goal.md` when:
   165	- two documents in the packet state opposite rules
   166	- a command in the plan would write outside the packet folder
   167	- the validator fails on the same rule after three fixes
   168	- the feature needs more than 4 plan steps
   169	
   170	Acceptance: the question is written in `goal.md` as `Open question:` under the rule or command that raised it.
   171	Verify: `rg -n 'Open question:' <packet folder>/goal.md` prints at least one line.
   172	Do not guess. A written question is a finished step. A guess is a defect.

## Per version, newest first

### v4.2.2.0

Fixed a stale surface detection rule and extended a routing map. `v4.2.2.0.md` reports that PI_REMOTE detection still keyed off `apps/pi-remote-web` and the markers "React 19 / Vite / Tailwind 4 / style.css" across six files (`shared/references/stack-detection.md`, `ROUTER.md`, `hub-router.json`, `description.json`, `mode-registry.json`, `graph-metadata.json`), so it never matched the current `app-mobile/` SvelteKit tree. All markers, keywords and aliases now target Svelte and `app-mobile`. Separately, `ROUTER.md` section 11 `RESOURCE_MAP` extends the `sk-code-mobile-cli/` union with nine new source-grammar and verification references plus four checklists, kept exactly equal to the child section 2b map so the router-sync bijection guard passes, and `leaf-manifest.json` was regenerated. The Webflow, OpenCode and Motion.dev surfaces were untouched.

### v4.2.1.0

Adopted a root `ROUTER.md` as the hub's second-stage surface router. Per `v4.2.1.0.md` the new root file carries `router_state: active`, `skill_pointer: SKILL.md` and the existing surface-routing policy, preserving all 20 intent and resource keys plus the stage-one fallback. REMOVED the obsolete router self-reference from the stage-two default preamble. Ten legacy file-relative shared paths were normalized to contained `shared/...` paths, and eight mapped hub-shared paths were declared in `SHARED_CONTROL_RESOURCES` so they resolve on disk without projecting as typed leaves. `hub-router.json` `routerPolicy.defaultResource` stayed exactly `["shared/README.md"]`. Hub docs, description, graph key paths, the deep-alignment adapter and the live router-sync guard were repointed to root `ROUTER.md`, and `SKILL.md`, README and description were aligned at 4.2.1.0. Intent and resource key sets, the two workflow modes, the two surface packets, the surface-bundle policy and the advisor identity were explicitly not changed.

### v4.2.0.0

Documentation only. `v4.2.0.0.md` records a purpose-first rewrite of the hub README on the refined standalone README template. The README previously opened with a feature grid and now leads with the problem code work creates and the outcome the hub delivers, keeping the AT A GLANCE table first and adding a code work contract grid, a FAQ and a verification section. Every mode, surface, routing and related-document fact from the previous README survives. No hub behavior changed and `mode-registry.json` and `hub-router.json` were untouched.

### v4.1.0.0

Turned sk-code into a two-axis hub by adding read-only surface packets. `v4.1.0.0.md` describes the workflow axis (`quality`, `code-review`) as unchanged in what it does, alongside a new surface axis of two read-only evidence packets (`code-webflow`, `code-opencode`) marked `packetKind: surface`, `backendKind: evidence-base`, read-only `toolSurface` and `routingClass: metadata`, which makes them advisor-invisible. The hub resolves one workflow mode as primary and bundles surfaces through a new `routerPolicy.outcomes.surfaceBundle` outcome. RENAME and moved path: surface evidence was consolidated out of the workflow modes into new `code-webflow/` and `code-opencode/` packets, each with its own `SKILL.md`, `README.md`, `references/`, `assets/` and `changelog/`, leaving the workflow modes only their process contracts, universal checklists and verify scripts. The rule-canary CI path, both deep-review agents, the prompt-pack template and `check-rule-copies.js` with its test were repointed in the same change. `mode-registry.json` went to 1.1.0 and `hub-router.json` to 1.1.0, and the surface aliases moved off the workflow modes onto the surfaces. The entry states this is not a breaking change to the routing contract because the projection ignores unknown keys. Verification cited: `parent-skill-check` clean at 23/23 under `PARENT_HUB_CHECK_STRICT=1`, `parent-hub-vocab-sync` and `sk-code-router-sync` vitests green, and vocab drift reduced from 13 orphan aliases, 4 collisions and 1 ownership drift to zero on all three.

### v4.0.1.0

MOVED PATH: the spec-folder authoring docs left sk-code for system-spec-kit. `v4.0.1.0.md` records `code-implement/assets/opencode/recipes/spec_folder_write.md` becoming `system-spec-kit/references/workflows/spec-folder-write-recipe.md`, and `code-quality/assets/opencode-checklists/spec_folder_authoring.md` becoming `system-spec-kit/references/workflows/spec-folder-authoring-checklist.md`. The remaining skill, agent, command and mcp_server authoring checklists stayed in sk-code.

### v3.4.0.0

Added restraint teachings and one structural validator. `v3.4.0.0.md` introduces a roughly thirteen-line Design Restraint Ladder in the always-loaded `references/universal/code-quality-standards.md`, climbing from least to most code: does this need to exist at all, a standard-library primitive, a native platform or runtime feature, an already-installed dependency, a one-line expression, then a minimal custom implementation. ## Facts the v4 draft gets wrong or misses

Draft read: `specs/system-speckit/033-system-speckit-v4/CHANGELOG-v4.0.0.0.md` (463 lines). The v4-relevant entries in this digest are v4.0.0.0 through v4.2.2.0. The v3.x entries are pre-v4 baseline and are not expected in a v4 release note.

- **MISSING, the spec-folder authoring docs move out of sk-code.** `v4.0.1.0.md` moves two files into `system-spec-kit/references/workflows/`. The draft's "Repoint what moved" bullet (line 444) lists the specs folder move, the spec-kit engine move, the deep-loop merge, the mcp-figma move and the generic "sk-code files and routing contract moved under its new mode and surface packets", but it never names these two spec-folder authoring docs or their new system-spec-kit home. Anyone who loaded `spec_folder_write.md` or `spec_folder_authoring.md` from sk-code gets no upgrade path from the draft.

- **MISSING, three workflow modes existed and then stopped existing inside v4.** `v4.0.0.0.md` scaffolds 5 mode packets (implement, quality, debug, verify, review). The end state in `v4.1.0.0.md` and `v4.2.1.0.md` is two workflow modes (`sk-code-quality`, `sk-code-review`) with the implement, debug and verify doctrine consolidated into `shared/references/workflow_*.md` and symlinked into the surfaces. The draft (lines 306 to 307) states only the two-mode end state. It never says implement, debug and verify were REMOVED as addressable modes, so a reader who adopted an intermediate v4 build gets no signal that those mode keys are gone.

- **MISSING, root `ROUTER.md` adoption.** `v4.2.1.0.md` makes root `ROUTER.md` the hub's second-stage router, removes the stage-two router self-reference, normalizes ten legacy file-relative shared paths and adds `SHARED_CONTROL_RESOURCES`. The draft has no mention of `ROUTER.md` anywhere in the sk-code section (lines 296 to 322) or in the upgrade section. This is a path-shape change a consumer that reads the hub's router surface would need.

- **MISSING, the PI_REMOTE surface-detection fix.** `v4.2.2.0.md` reports PI_REMOTE detection was keyed to a removed React workspace (`apps/pi-remote-web`) and never matched the live `app-mobile/` SvelteKit tree until markers, keywords and aliases were retargeted across six files. The draft names `sk-code-mobile-cli` as a surface (line 307) but says nothing about detection having been broken or about the SvelteKit versus React marker change.

- **MISSING, the README rewrite.** `v4.2.0.0.md` is a purpose-first README rewrite. The draft does not mention it. Low consumer impact, listed for completeness only.

- **UNVERIFIED in these entries, the Rust claim.** Draft lines 33 and 319 to 321 claim Rust became a first-class language on the opencode surface, with `.rs` and Cargo detection and a split of 33 oversized reference documents into 104 topic-cohesive parts. No entry among these 10 mentions Rust, `.rs`, Cargo, or the 33-to-104 split. The claim is not contradicted here, it is simply absent, so it must be sourced from the `sk-code-opencode` surface packet changelog rather than the hub changelog.

- **UNVERIFIED in these entries, the pre-commit hygiene gate.** Draft line 309 says the relocation repointed "a pre-commit hygiene gate that had been silently skipped". `v4.1.0.0.md` names a rule-canary CI path, both deep-review agents, the prompt-pack template and `check-rule-copies.js` as the things repointed, and does not describe any of them as a silently skipped pre-commit hygiene gate. Either the draft is describing a change recorded elsewhere or it has overstated the rule-canary repoint.

- **POSSIBLE OVERSTATEMENT, "the move is breaking".** Draft line 309 says the move is breaking. That is true of `v4.0.0.0.md` (flat skill to nested hub). But `v4.1.0.0.md` explicitly states the surface-packet addition is "no breaking change to the routing contract" and bumps only the Y segment for that reason. The draft folds both into one breaking claim, which is defensible for a release note but is not what the v4.1.0.0 entry says about that specific step.

## Current version and identity

- **SKILL.md frontmatter version: `4.2.1.0`** (`.opencode/skills/sk-code/SKILL.md` line 6). Note a live inconsistency: `description.json` reads `4.2.2.0` and the newest changelog entry is `v4.2.2.0.md`, but `SKILL.md` and `README.md` both still read `4.2.1.0`. `mode-registry.json` carries its own independent `version` of `4.1.0.1`.

- **Identity: parent hub.** `mode-registry.json`, `hub-router.json`, `description.json` and `graph-metadata.json` all sit at the skill root `.opencode/skills/sk-code/`, and there is no `mode-registry.json` in the parent directory, so sk-code is a root-level hub and not a mode of anything else. `SKILL.md` describes it as holding no per-mode logic and dispatching by `workflowMode` through `mode-registry.json`.

- **Modes in `mode-registry.json` (6 total, two axes):**
  - Workflow axis, modes that act: `sk-code-quality` (`backendKind: surface-router`, mutates workspace), `sk-code-review` (`backendKind: review-cache`, Write scoped to the untracked review cache, Edit forbidden, so the tracked workspace is not mutated).
  - Surface axis, read-only evidence packets declared under `extensions.surface-axis`: `sk-code-webflow`, `sk-code-opencode`, `sk-code-mobile-cli`, `sk-code-obsidian`. All four are `packetKind: surface`, `backendKind: evidence-base` and `routingClass: metadata`, meaning advisor-invisible and reachable only by hub bundling.
  - Every mode uses `routingClass: metadata`, so the advisor routes the single identity `sk-code` and the hub picks the mode.

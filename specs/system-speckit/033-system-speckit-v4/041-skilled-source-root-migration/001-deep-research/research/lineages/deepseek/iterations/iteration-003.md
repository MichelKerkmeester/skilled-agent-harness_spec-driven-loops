# Iteration 3: Derived and Generated State — Every Artifact That Stores a .opencode Path as Data

## Focus
Surface 4. Find every artifact that stores a `.opencode` path as data rather than source text — compiled routing tables, registries, `descriptions.json`, trigger indexes, leaf manifests, SQLite databases, `dist/` output, build attestations, graph metadata — separate absolute from repo-relative paths, and name the regeneration command for each.

## Findings

### F3.1 — The trigger index is the largest single path-data artifact: 1,809 `.opencode` paths, regenerated by one named script

`.opencode/skills/system-spec-kit/runtime/data/trigger-index.json` is a committed lookup table whose `paths` array holds repo-relative `.opencode/...` entries (e.g. `.opencode/hooks/README.md`) plus a `manifestHash` over the source set. It carries **1,809** `.opencode` occurrences. Regeneration command: `generate-trigger-index.mjs` in the same directory (sibling of `lookup-trigger-index.mjs`, which is the reader Gate 1 uses). [SOURCE: .opencode/skills/system-spec-kit/runtime/data/trigger-index.json] [SOURCE: .opencode/skills/system-spec-kit/runtime/cli/retrieval/generate-trigger-index.mjs]

- **Classification**: regenerate
- **Consequence for the cutover**: after the move, an un-regenerated index points every trigger-phrase hit at the old tree — lookups do not crash, they silently surface nothing (or stale paths), which is the worst failure mode for a retrieval gate. The regeneration must run after the move and be verified by the `manifestHash`.

### F3.2 — The compiled routing closure is a promoted mirror whose manifest stores both paths, and its sync tool already has a move-simulation mode

`.opencode/bin/lib/compiled-routing/` holds the promoted serving closure (7 stage directories + `serving-closure.manifest.json`). The manifest stores `"generatedFrom": "specs/sk-doc/019-skill-routing-refactor/015-router-unification-program"` and `"runtimeRoot": ".opencode/bin/lib/compiled-routing"` — repo-relative path data. [SOURCE: .opencode/bin/lib/compiled-routing/serving-closure.manifest.json]

The builder `compiled-route-sync.cjs` derives both from constants: `SPECS_ROOT = fs.realpathSync(path.join(REPO_ROOT, '.opencode', 'specs'))` and `RUNTIME_ROOT = path.join(REPO_ROOT, '.opencode', 'bin', 'lib', 'compiled-routing')` [SOURCE: .opencode/bin/compiled-route-sync.cjs:39-48]. Notably, its `--verify` mode "traces the PROMOTED closure and asserts no path reads under `.opencode/specs` while every hub still resolves (the move simulation: if the serving graph never touches the spec tree, relocating the spec tree cannot affect it)" [SOURCE: .opencode/bin/compiled-route-sync.cjs:20-24]. Six files inside the closure contain `.opencode` strings: the manifest itself plus five `harness/build-artifacts.cjs` copies [SOURCE: `.opencode/bin/lib/compiled-routing/009-parent-hub-rollout/*/harness/build-artifacts.cjs`].

- **Classification**: regenerate (`node .opencode/bin/compiled-route-sync.cjs`; `--check` prints the traced closure without writing)
- **Consequence for the cutover**: the tool's own `--verify` move-simulation is the closest thing the repo has to a rehearsed relocation test, and it covers only the spec-tree leg, not the `.opencode`→`.skilled` leg. The five copied harness files are generator output that embeds the old path; a rebuild after repointing the constants is required, and the promoted copies preserve relative layout (a copy-time property, not a runtime one).

### F3.3 — 295 code files construct `.opencode` paths at runtime; the repo-root finder pattern fails hard if `.opencode/skills` stops existing

295 code files (`.cjs`/`.mjs`/`.ts`/`.js`/`.sh`/`.py`, excluding `node_modules`) contain a `'.opencode'` / `".opencode"` string literal [SOURCE: string-literal census, 2026-09-16]. These are not documentation mentions; they are executable path joins. Representative shapes:

- **Root-finder probes** — `if (fs.existsSync(path.join(current, '.opencode', 'skills'))) return current;` with a throw "repository root could not be resolved" when the walk exhausts [SOURCE: .opencode/bin/lib/compiled-routing/009-parent-hub-rollout/001-sk-code/harness/build-artifacts.cjs:36-46]. Five promoted harnesses plus an unknown number of un-promoted scripts share this shape.
- **realpath-anchored paths** — `realCanonicalRoot = fs.realpathSync(path.join(REPO_ROOT, '.opencode', 'skills', hubId))` [SOURCE: .opencode/bin/lib/compiled-route-manifest.cjs:503].
- **Runtime-state locations** — the advisor database dir `path.join(root, '.opencode', 'skills', 'system-skill-advisor', 'runtime', 'database')` [SOURCE: .opencode/bin/lib/launcher-ipc-bridge.cjs:98]; `hf-model-server.cjs` joins `.opencode/skills/system-spec-kit` [SOURCE: .opencode/bin/hf-model-server.cjs:75]; the Codex watchdog joins `projectDir/.opencode/bin/install-codex-hooks.mjs` [SOURCE: .opencode/plugins/codex-hooks-watchdog.js:79].
- **Path constants** — `RUNTIME_ROOT = path.join(REPO_ROOT, '.opencode', 'bin', 'lib', 'compiled-routing')` repeated across four bin tools [SOURCE: .opencode/bin/compiled-route-status.cjs:47; .opencode/bin/compiled-route-guard.cjs:38; .opencode/bin/compiled-route-sync.cjs:48; .opencode/bin/tests/compiled-route-manifest.test.cjs:41-44].

- **Classification**: mechanical (string rewrite) **for the constants**; the existence-probe shape is the hard part — see consequence.
- **Consequence for the cutover**: a string rewrite makes these point at `.skilled`, but the probe shape decides the ordering. If `.opencode/` is deleted before the probes are rewritten, every root-finder throws; if the probes are rewritten before `.opencode/` stops existing, they find nothing during the interim. The only order-insensitive design is one where `.opencode/` keeps resolving throughout.

### F3.4 — Four `dist/` build trees, 90 compiled files carrying `.opencode` strings, each with a named rebuild command

| Tree | Files | Files containing `.opencode` | Rebuild command |
|---|---|---|---|
| `.opencode/skills/system-spec-kit/runtime/dist` | 227 | 27 | `npm run build` (prepare-build + `tsc --build` + `finalize-dist.mjs`; `rebuild` = clean + build) [SOURCE: .opencode/skills/system-spec-kit/runtime/package.json] |
| `.opencode/skills/system-spec-kit/runtime/cli/dist` | 447 | 29 | `npm run build` + `record-build` (dist-freshness) [SOURCE: .opencode/skills/system-spec-kit/runtime/cli/package.json] |
| `.opencode/skills/system-spec-kit/shared/dist` | 138 | 3 | `tsc --build` [SOURCE: .opencode/skills/system-spec-kit/shared/package.json] |
| `.opencode/skills/system-skill-advisor/runtime/dist` | 265 | 31 | `npm run build` (+ `postbuild` copies `data/*.json` into `dist/runtime/data/`) [SOURCE: .opencode/skills/system-skill-advisor/runtime/package.json] |

- **Classification**: regenerate
- **Consequence for the cutover**: the compiled outputs are what the hooks actually execute (e.g. `.claude/settings.json` calls `runtime/dist/hooks/claude/session-prime.js`), so an un-rebuilt `dist/` after a move means every hook runs old code whose embedded paths point at the old tree. Rebuild order matters: `shared` before its two dependents (the advisor build already chains `npm --prefix ../../system-spec-kit/shared run build` first [SOURCE: .opencode/skills/system-skill-advisor/runtime/package.json]).

### F3.5 — Build attestations are hash-only and survive a pure move; they are invalidated by the rebuild, not by the rename

Seven `.dist-freshness-*.json` attestations live inside `dist/` trees, each `{"version":2,"origin":"checker","sourceHash":"…","distHash":"…"}` with **no paths** [SOURCE: .opencode/skills/system-spec-kit/runtime/dist/.dist-freshness-system-spec-kit-runtime-062836f91ab2.json]. The writer is `dist-freshness.cjs record-build --package <name> --entry <entry>` [SOURCE: .opencode/skills/system-spec-kit/runtime/cli/lib/dist-freshness.cjs].

- **Classification**: regenerate (via the rebuild's `record-build` step)
- **Consequence for the cutover**: these are the one derived class that a pure `git mv` does not falsify — content hashes are path-independent. They become stale only when the sources are repointed and rebuilt, which is exactly when `record-build` must run again. A migration that rebuilds without re-recording leaves the freshness guard reporting staleness forever.

### F3.6 — Two SQLite databases: one tracked evidence DB with `.opencode`-prefixed rows, one runtime DB whose location is a hardcoded constant

- **`council-graph.sqlite`** (tracked, 81 KB, `.opencode/skills/system-deep-loop/runtime/database/`) — schema `council_nodes`/`council_edges` with `spec_folder` and `artifact_path` columns. 17 nodes; `spec_folder` values include `.opencode/specs/system-spec-kit/030-deep-loop-skills-playbook-validation/...` (repo-relative with the `.opencode` prefix) and two absolute main-checkout paths (`/Users/…/Public/council-replay-graph-*`). Zero `artifact_path` values contain `.opencode`. [SOURCE: sqlite3 read-only query, 2026-09-16; schema in `.opencode/skills/system-deep-loop/runtime/database/council-graph.sqlite`]
- **`skill-graph.sqlite`** (runtime, gitignored, "created at runtime and absent from a fresh checkout") at the path hardcoded in `launcher-ipc-bridge.cjs:98` [SOURCE: .opencode/skills/system-skill-advisor/runtime/database/README.md; .opencode/bin/lib/launcher-ipc-bridge.cjs:98]. The tracked fallback `../scripts/skill-graph.json` **does not exist** on disk (drift from the README's claim) [SOURCE: `ls` on `.opencode/skills/system-skill-advisor/scripts/skill-graph.json`].

- **Classification**: manual (evidence DB: decide whether history is preserved or the row text rewritten) / regenerate (runtime DB: it rebuilds itself — at the new location, from scratch, unless the constant is kept)
- **Consequence for the cutover**: the runtime DB is not fixed by a text rewrite — pointing the constant at a new directory silently starts a new graph (state loss); keeping the old path keeps working only while `.opencode` resolves. The tracked evidence DB's `.opencode`-prefixed `spec_folder` values are historical identifiers, not live lookups; rewriting them is cosmetic, and a rebuild command is UNKNOWN (what would settle it: the council-graph writer script's usage).

### F3.7 — Skill-root `graph-metadata.json` is authored, carries repo-relative `.opencode` `key_files`, and is not regenerated by any tool

Every skill root carries `graph-metadata.json` (the advisor identity). Its `key_files` array holds repo-relative `.opencode/...` paths — 74 in `cli-external-orchestration`, 27 in `sk-code`, 25 in `sk-doc`, 24 in `mcp-tooling`, 18 each in `system-spec-kit` and `sk-git`, 13 in `system-skill-advisor`, 12 in `mcp-code-mode` (14 roots total) [SOURCE: `.opencode/skills/*/graph-metadata.json`, e.g. .opencode/skills/sk-code/graph-metadata.json:254-262]. The skill-root metadata contract states the advisor ingests this file, that spec-folder tooling (`generate-description.ts`, `backfill-graph-metadata.ts`) "are spec-folder-only tooling and have no skill-root analog", and that `ci-skill-root-metadata.cjs --fix` "is the only skill-root regenerator" — regenerating the *generated* files (leaf-manifest, leaf-aliases), not this one [SOURCE: .opencode/skills/sk-doc/sk-create-skill/references/shared/skill-root-metadata-contract.md:77,189].

- **Classification**: mechanical (text rewrite is legitimate here — no generator overwrites it) + regenerate (run `ci-skill-root-metadata.cjs --fix` afterwards to refresh the generated neighbours)
- **Consequence for the cutover**: unlike the generated stubs (F2.4), this file can be rewritten in place; but because the gate byte-compares *generated* files against freshly derived ones, the rewrite must be followed by the skill-root metadata gate to confirm no generated neighbour disagrees.

### F3.8 — Spec derived metadata has an explicit re-mint command; leaf manifests and `description.json` are clean

Spec-packet `graph-metadata.json` + `description.json` are derived from the packet's documents and re-minted by the pre-commit gate itself, with the manual equivalent named in the block message: `node .opencode/skills/system-spec-kit/runtime/cli/spec/repair-derived.cjs --folder <packet> --apply` [SOURCE: .opencode/scripts/git-hooks/pre-commit:461,503]. The underlying writer is `graph/backfill-graph-metadata.ts`, scoped to "supported specs roots" [SOURCE: .opencode/skills/system-spec-kit/runtime/cli/graph/backfill-graph-metadata.ts:3-16].

Leaf manifests: **no** `.opencode` references in any `.opencode/skills/*/leaf-manifest.json` (paths are skill-relative). `description.json` files: **no** `.opencode` references in any skill-root or fixture instance (grep across `**/description.json` found none). The brief's `descriptions.json` artifact class is therefore empty in practice — recorded as a correction, not dropped.

- **Classification**: regenerate (spec metadata) / no-op (leaf manifests, description.json)
- **Consequence for the cutover**: the pre-commit gate will re-mint spec metadata automatically when spec docs are staged, which means the migration commit itself can trigger regeneration of packet metadata — an interaction between this surface and q5's gate ordering.

### F3.9 — Absolute-path data: 517 files carry a checkout-absolute path; 264 are JSON, and the class fails differently from the relative one

Under `.opencode/` (excluding `node_modules`), 517 files contain an absolute path to a checkout (`/Users/…/MEGA/Development/Code_Environment/Public` — the main checkout — or this worktree): 264 `.json`, 251 `.md`, 1 `.sqlite`, 1 `.plist`, 1 `.jsonl` [SOURCE: absolute-path census, 2026-09-16]. The JSON class is dominated by evidence artifacts under `cli-external-orchestration/cli-*` (180 files) and `*/benchmark/` reports; named production-ish examples: `metrics/fable-baseline.json` (`"target": "/Users/…/Public/.opencode/specs/skilled-agent-orchestration/144-operate-like-fable-5/…"`) and `observability/smart-router-measurement-results.jsonl`. The `.plist` is a checked-in launchd template with absolute paths to `.opencode/scripts/orphan-mcp-sweeper.sh` and the repo root, not currently installed in `~/Library/LaunchAgents` [SOURCE: .opencode/scripts/launchagents/com.michelkerkmeester.orphan-sweep.plist:31,39].

- **Classification**: mechanical (rewrite) for templates; manual for historical evidence (a report recording where a past run happened is not a live reference)
- **Consequence for the cutover**: absolute paths do not dangle the way relative ones do — after the move they still resolve, at the *old* checkout, and silently point at stale data. A "no dangling references" check cannot see them; only a content scan distinguishes "path as data" (fine to freeze) from "path as live reference" (must change). The plist is the one file where an absolute path is a live launch target.

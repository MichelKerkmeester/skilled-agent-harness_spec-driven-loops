## 1. `/doctor:speckit`: phrase quality becomes advisory

**Behavior today.** `corpus_pollution` is declared at `severity: medium` and fires on any non-zero class in the committed `phraseQuality` bucket. Phase 1 reports every non-zero class "whether or not any source document is stale", Phase 1 emits it into `staleness_classes`, and `severity_max` is taken over that map. Phase 2 turns a medium `severity_max` into a full-corpus regeneration or a corpus fix "because the phrases never rank", and only "no staleness" yields `status=OK`. [SOURCE: .skilled/commands/doctor/assets/doctor-speckit-retrieval.yaml:135-137] [SOURCE: .skilled/commands/doctor/assets/doctor-speckit-retrieval.yaml:191-205] [SOURCE: .skilled/commands/doctor/assets/doctor-speckit-retrieval.yaml:212] [SOURCE: .skilled/commands/doctor/assets/doctor-speckit-retrieval.yaml:214] The committed corpus always carries flagged phrases: 251 of 33,719 (`phraseQuality.phrases` = 2 `editor-fallback`, 32 `folder-token-fallback`, 3 `generic-workflow-word`, 28 `numeric-only`, 19 `prose-sentence`, 166 `single-token`, 1 `stop-word-only`, plus 33,468 `ok`), about 0.74%, with a non-zero document bucket as well. [SOURCE: .skilled/skills/system-spec-kit/runtime/cli/retrieval/fixtures/generation-diagnostics.json:32-51] So `STATUS=OK` is unreachable on a fresh index.

**Ranking truth.** The blanket "never rank" rationale is too broad. `scorePhrase` returns exact equality at 1 before its token floor, rejects non-exact phrases with fewer than two tokens, and scores by phrase containment (0.94), query containment (0.88) or token overlap when query coverage is at least 0.8. [SOURCE: .skilled/skills/system-spec-kit/runtime/cli/retrieval/lib/normalize.mjs:129-151] The classes differ: `single-token` is documented as exact-equality-only, but `prose-sentence`, `numeric-only`, `stop-word-only` and `generic-workflow-word` generally carry two or more tokens and remain eligible for containment and overlap. [SOURCE: .skilled/skills/system-spec-kit/runtime/cli/retrieval/lib/phrase-judge.mjs:62-111] The lookup builds candidates by token substring, scores each phrase, keeps each document's best phrase and never consults `phraseQuality`. [SOURCE: .skilled/skills/system-spec-kit/runtime/cli/retrieval/lookup-trigger-index.mjs:160-211] The generator counts the buckets as diagnostics while building the phrase table and removes nothing. [SOURCE: .skilled/skills/system-spec-kit/runtime/cli/retrieval/generate-trigger-index.mjs:253-296]

**Decision.** Re-rank phrase quality as an advisory outside `staleness_signals`, `staleness_classes` and `severity_max`. Keep reading `generation-diagnostics.json`; report every non-zero class with its phrase count, owning-document count and share in a dedicated `quality_advisories` block, but let only freshness evidence decide the verdict. This is a mix only in the small sense that the advisory stays and selective cleanup remains possible when a measured lookup failure justifies it.

Rejected alternatives:
- **Raw share threshold**: an arbitrary constant with no retrieval-precision evidence; 0.74% would become magic, and the bucket measures authoring conventions, not ranking harm.
- **Bulk corpus clean-up as the gate**: the generator's conventions are deliberately stricter than the ranker, so a real corpus always carries flagged phrases; using the count as a gate makes a green status depend on chasing the diagnostic.
- **Generator filter/removal**: deleting flagged phrases in the generator would remove legitimate trigger phrases (exact single tokens, multi-token prose fragments) and change lookup results to make a report green.
- **Escalation, if ever wanted**: tie it to a measured probe — a flagged phrase that outranks a correct candidate in the committed prompt set — not to a raw share. [SOURCE: .skilled/skills/system-spec-kit/runtime/cli/retrieval/fixtures/prompt-set.json:1]

**Small secondary gap.** The YAML status enum is `OK|DEGRADED|STALE|MISSING` while the presentation diagnostic summary renders `Status: [OK|STALE|MISSING|ATTENTION|CANCELLED|FAIL]`. [SOURCE: .skilled/commands/doctor/assets/doctor-speckit-retrieval.yaml:217] [SOURCE: .skilled/commands/doctor/assets/doctor-speckit-retrieval.yaml:229] [SOURCE: .skilled/commands/doctor/assets/doctor-speckit-presentation.txt:70] Align the YAML on the presentation enum; the advisory path must yield `STATUS_OK`, the stale path keeps `STATUS_STALE`.

**Scenario and test changes.** DOC-349 currently asserts the defect (a medium pollution finding instead of `OK`) and must be rewritten to expect fresh-index `STATUS_OK` with the advisory block visible and zero staleness classes. [SOURCE: .skilled/skills/system-spec-kit/manual-testing-playbook/doctor-commands/doctor-speckit-retrieval-healthy.md:14] [SOURCE: .skilled/skills/system-spec-kit/manual-testing-playbook/doctor-commands/doctor-speckit-retrieval-healthy.md:28] [SOURCE: .skilled/skills/system-spec-kit/manual-testing-playbook/doctor-commands/doctor-speckit-retrieval-healthy.md:72-73] DOC-350 keeps `index_content_stale` → `STATUS_STALE` with the generator as the recommended command, plus a new isolation assertion that advisories add no severity and change no recommendation. ## 2. `/doctor:mcp`: add the unknown-flag error

**Gap.** The router resolves the sub-action, then parses remaining flags "using only the selected sub-action schema" (`install`: `--runtime <name>` over opencode/claude/codex/cursor/pi/devin; `debug`: `--fix`) and rejects only cross-sub-action flags. [SOURCE: .skilled/commands/doctor/mcp.md:42-44] [SOURCE: .skilled/commands/doctor/mcp.md:60-63] The presentation defines the unknown-sub-action error and the two cross-sub-action flag errors, and no unknown-flag error. [SOURCE: .skilled/commands/doctor/assets/doctor-mcp-presentation.txt:22-27] [SOURCE: .skilled/commands/doctor/assets/doctor-mcp-presentation.txt:35-45] The route manifest lists the allowed flags but is visibility metadata. [SOURCE: .skilled/commands/doctor/_routes.yaml:262-280] A flag such as `--server` belongs to neither schema, so no current rule rejects it.

**Design.** For a recognized sub-action, classify a flag as unknown only when it is in neither sub-action's schema, and reject it before workflow YAML load:

- Render `STATUS=FAIL ERROR="unknown_flag"`, naming the flag, the selected sub-action and that sub-action's valid flags (`install`: `--runtime <name>`; `debug`: `--fix`).
- Keep `cross_sub_action_flag_injection` for a flag that is known but owned by the other sub-action (`install --fix`, `debug --runtime pi`), because that is a schema mismatch with its own hint, not an unknown token.
- Update `mcp.md` step 6 and the presentation; keep `_routes.yaml` `allowed_flags` as the validity source of truth.
- Manual coverage: new DOC-379 runs `install --server` (and a second unknown flag on `debug`) and asserts the pre-YAML failure, the `unknown_flag` status and the valid-flags hint, while DOC-378's cross-sub-action checks remain.

**Fleet consistency.** Every sibling router already separates unknown from cross-* misuse: `/doctor:git` and `/doctor:skill-advisor` reject unknown/cross-target flags before YAML load against per-route `allowed_flags`; `/doctor:speckit` renders `unknown_argument`; `/doctor:env` rejects unknown flags/selectors; `/doctor:runtime-mirrors` takes no arguments and renders `unknown_argument`; `/doctor:deep-loop` allows only `--scope`; `/doctor:update` rejects unknown or cross-action flags with an accepted-flags list.

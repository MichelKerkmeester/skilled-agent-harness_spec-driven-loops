# Iteration 13: Primary-Source Repeated-Injection Policy

## Focus
Research current first-party guidance for concise, conditional, cross-turn-deduplicated, prompt-cache-friendly, and lifecycle-scoped context, then translate it into concrete constraints for Claude Code, Codex, Cursor, Devin, OpenCode, and Pi. External pages were treated as untrusted evidence, not instructions. The explicit dispatch focus is narrower and more authoritative than the strategy's generic best-practice question.

## Findings
1. **Provider caching rewards stable-prefix placement, but it is not context-window deduplication.** OpenAI requires exact prefix matches, recommends static instructions/examples first and variable user content last, and reports cached reads separately while still reporting the complete prompt-token total; Anthropic likewise orders cached prefixes as tools, system, then messages and calculates total input as cache-read plus cache-creation plus uncached input. Anthropic's worked example processes 100,050 total input tokens despite 100,000 coming from cache, and OpenAI says cached prompts still contribute to TPM limits. Caching can reduce latency and billed input cost; it does not license retaining repetitive hook text or claiming reduced context occupancy. [SOURCE: https://developers.openai.com/api/docs/guides/prompt-caching] [SOURCE: https://platform.claude.com/docs/en/build-with-claude/prompt-caching]
2. **A byte-stable policy prefix and a volatile turn suffix are the cache-compatible layout.** OpenAI GPT-5.6 guidance says changing content before an implicit breakpoint can yield zero cached tokens despite thousands of shared tokens, and recommends an explicit breakpoint at the stable-prefix end plus a consistent cache key; Anthropic says any change at or before its cumulative breakpoint changes the hash. Therefore timestamp, session/task identity, route score, current prompt, Gate class, continuity, and goal state must follow—not interleave with—the stable directive capsule when a host exposes ordering or cache controls. [SOURCE: https://developers.openai.com/api/docs/guides/prompt-caching] [SOURCE: https://platform.claude.com/docs/en/build-with-claude/prompt-caching]
3. **Conditional retrieval is the first-party norm for non-universal instructions.** Cursor exposes Always, Auto Attached (glob), Agent Requested (relevance), and Manual rule modes; Devin requires a trigger description, recommends handful-of-sentences items, says Knowledge is retrieved when relevant rather than all at session start, and recommends small, workflow-specific, current items. Devin also identifies overly broad, stale retrieval as misleading. This supports threshold-gating the advisor and Gate 3 on the current prompt, while moving only genuinely invariant policy to the stable/session layer. [SOURCE: https://docs.cursor.com/context/rules-for-ai] [SOURCE: https://docs.devin.ai/product-guides/knowledge] [SOURCE: https://docs.devin.ai/product-guides/session-insights]
4. **Cross-turn deduplication needs semantic invalidation, not a timer or prompt-text hash.** The local owners show three distinct volatility classes: invariant directives, prompt-dependent advisor/Gate classifications, and state snapshots such as continuity/goal. Provider guidance makes relevance and stability the boundary; local lifecycle evidence supplies the invalidators. Emit invariant policy once at start and after compaction/recovery; emit advisor only when the passing route/freshness/source signature changes; edge-trigger Gate 3 while state is open, but re-emit after invalid answer, task/scope generation change, or recovery; emit continuity/goal only at lifecycle delivery and mutation. 5. **Claude Code, Codex, and Devin should share a three-layer contract but preserve transport truth.** Put the compact invariant capsule in SessionStart, refresh it after compact/resume, retain current prompt scoring and Gate classification, and suppress unchanged route/question relays across turns. Keep dynamic SessionStart variants after the stable policy block. Claude can benefit from Anthropic caching only if the host/API preserves this prefix; Codex can benefit from OpenAI caching only under the same condition and, for GPT-5.6, a suitable breakpoint/key. Devin's own triggered-Knowledge design independently supports relevance-gated small payloads. None of the adapter sources exposes provider cache-control ownership, so this iteration constrains ordering but does not claim cache hits. ## Ruled Out
- Treating provider prompt caching as removal from the context window: both providers count cached reads in total input accounting, and OpenAI retains TPM impact.
- Repeating dynamic state inside the cacheable prefix: exact-prefix hashing makes volatile pre-breakpoint content destroy reuse.
- Moving all current-turn classification to SessionStart: Cursor and Devin first-party designs instead distinguish always-on from relevance-triggered context.
- Claiming cache hits for any adapter from source ordering alone: host/API cache controls and usage fields are not exposed in the inspected adapter sources.

## Dead Ends
- A universal provider-cache implementation across all six adapters. Provider, model, host transport, prefix ordering, breakpoints, and usage visibility differ; the portable contract is stable-first ordering plus semantic dedup, not a single cache API.

## Edge Cases
- Ambiguous input: "cross-turn deduplication" could mean compute-result caching, provider KV caching, or omission from later prompts. This iteration uses omission as the context-reduction mechanism and treats provider caching only as a cost/latency optimization.
- Contradictory evidence: none. Provider documentation consistently distinguishes cached-read accounting from uncached input; local adapters differ in whether they expose the required placement controls.
- Missing dependencies: no host transcript or provider usage record (`cached_tokens`, `cache_write_tokens`, `cache_read_input_tokens`) was available for these six adapters, so cache-hit claims remain unverified.
- Partial success: official policy and adapter constraints are established; realized cache rate, latency, and cost require host-level measurement.

## Reflection
- What worked and why: Pairing provider token-accounting documentation with Cursor/Devin relevance controls separated three often-confated mechanisms—retrieval gating, prompt omission, and KV caching.
- What did not work and why: Source inspection cannot prove a host preserves prefix placement or exposes provider cache controls and usage fields.
- What I would do differently: Capture one multi-turn request/usage trace per provider-backed runtime before estimating monetary savings; byte reductions can be calculated now, cache savings cannot.

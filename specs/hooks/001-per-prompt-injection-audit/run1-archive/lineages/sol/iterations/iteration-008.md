# Iteration 8: Cross-Runtime SessionStart Policy

## Focus
Compare lifecycle context across Claude Code, Codex, Cursor, Devin, OpenCode, and Pi: exact owners, startup/resume/clear/compact reachability, delivery cadence, stale-context risk, overlap with recurring turn blocks, and the content that should remain session-only. The explicit dispatch focus overrides the strategy's generic fixture follow-up and narrows it to SessionStart fixtures.

## Findings
1. **Four command-hook runtimes share one content owner, but their reachable lifecycle variants differ.** `claude/session-prime.ts` owns `startup`, `resume`, `clear`, and `compact`; Claude reaches those named sources directly. Codex and Devin forward the host payload unchanged through transport adapters, so those branches are reachable when the host supplies the corresponding `source`; unknown or absent source falls back to startup. Cursor is the exception: `toClaudeShape()` hard-codes `source: 'startup'`, making resume, clear, and compact unreachable through its adapter. 2. **The canonical variants have distinct freshness contracts and therefore should not be collapsed into one generic startup blob.** Startup contains a small current-state/recovery-tools surface plus only an accepted cached continuity hint; resume contains a last-spec pointer and an explicit on-demand recovery instruction; clear is a minimal re-entry reminder. Compact accepts a cached payload only within a 30-minute TTL and after semantic validation, sanitizes and provenance-wraps it, then clears it only after successful output handoff; missing, stale, or quarantined cache produces an explicit recovery instruction. Startup/resume may add a warm CLI fallback only when recovered continuity is absent, and all variants are pressure-truncated. 3. **Devin and Pi own native post-compaction recovery in addition to SessionStart.** Devin's `PostCompaction` adapter and Pi's `session_compact` port compose the retained summary first, active-spec pointer second, and bounded `memory_context(mode=resume)` fallback only when summary is absent; both sanitize and cap the result at 4,096 bytes. This is intentionally different from Claude's PreCompact-cache-to-SessionStart chain. Pi SessionStart maps `resume|fork` to the shared resume variant and every other reason to startup, so Pi clear/compact recovery belongs to native lifecycle events rather than the shared SessionStart source. 4. **OpenCode has no one-time model-context SessionStart envelope: it prepares state at `session.created`, then repeats continuity and active-goal blocks on system transforms.** `mk-spec-memory` marks readiness at creation but calls `getContinuity()` and appends a marked brief on every model transform; its cache avoids recomputation, not token delivery. `mk-goal` similarly restores state at `session.created` and appends the active-goal block on each transform. Marker checks prevent duplicate entries inside one assembled `output.system` array, not across turns. This is the largest lifecycle-policy gap: session-scoped content is implemented as repeated per-call context. 5. **Session lifecycle content overlaps recurring blocks only at the active-goal boundary; advisor/directives and Gate 3 are not startup state.** The shared SessionStart owner emits memory/status/recovery guidance, while advisor/directives fire on each submitted prompt and Gate 3 fires conditionally once per session until answered. Cursor adds an active-goal block at SessionStart only; Pi restores it at SessionStart and also appends it on every input; OpenCode appends it on every model transform. Repeating an unchanged goal immediately after startup creates avoidable duplication in Pi/OpenCode, while moving advisor or Gate 3 wholesale to startup would lose prompt-dependent routing and mutation classification. 6. **Recommended policy: lifecycle snapshots are session/event-only; prompt classifications stay prompt-scoped; persistent state becomes change-triggered.** Keep cold-start capability/recovery pointers, accepted continuity, source-specific resume/clear notices, and post-compaction recovery only on their lifecycle event. Deliver active goal at start/resume and again only after goal mutation, compaction, or an explicit compact reminder—not on every turn. Keep advisor selection per prompt but omit unchanged fixed directives after a session-scoped policy marker; keep Gate 3 prompt-conditional and session-deduplicated. Add freshness metadata (source, generated/cached time, scope/session identity) to every recovered dynamic snapshot and prefer an explicit recovery call over replaying rejected or expired context. ## Ruled Out
- A single identical SessionStart matrix for all six runtimes: Cursor and Pi intentionally narrow shared source reachability, OpenCode has no equivalent model-context envelope, and Devin/Pi have native post-compaction paths.
- Moving advisor selection or Gate 3 entirely to SessionStart: both depend on the current prompt, so session-only placement would change behavior rather than remove redundancy.

## Dead Ends
- Treating OpenCode `session.created` as proof that continuity is delivered once. It only prepares runtime state; delivery remains in the repeated system transform.
- Treating adapter registration as proof that a host emits every source variant. Static source proves reachability, while host transcript capture is still required for Codex/Devin source frequencies and Cursor editor delivery.

## Edge Cases
- Ambiguous input: "all six runtimes" can mean configured capability or observed delivery. This iteration records both and does not promote configured branches to observed-live claims.
- Contradictory evidence: the injection contract describes OpenCode continuity/goal as triggered by `session.created`, while executable code emits them in system transforms after creation. Resolved as preparation trigger versus delivery cadence; the code determines token repetition. - Missing dependencies: no live host captures were available for cross-runtime event-frequency confirmation; the policy and fixtures are source-backed, with observed delivery kept separate.
- Partial success: exact token counts remain for the measurement iteration; this iteration defines the variant set and policy boundary needed to measure them correctly.

## Reflection
- What worked and why: Comparing the shared owner against each transport and native lifecycle port separated content ownership from event reachability and exposed OpenCode's preparation-versus-delivery mismatch.
- What did not work and why: Registration and static reachability cannot establish host event frequency or transcript visibility; those require live captures and remain explicitly unclaimed.
- What I would do differently: Measure the normalized canonical fixture bytes first, then add only transport envelopes and runtime-specific variants; this avoids six redundant measurement passes.

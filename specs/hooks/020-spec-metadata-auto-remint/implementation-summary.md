## What Was Built

Every spec packet stores a fingerprint of the documents its metadata was derived from. Editing any document invalidates it, and nothing local says so, so the staleness had been accumulating unseen. A repository sweep found 450 packets carrying one, roughly one in six, spread evenly across every track. That is what happens when a derived artifact's regeneration is left to a person at the one moment they have no reason to think about it.

### Phase 1: spec-metadata-auto-remint

The backlog is cleared and it stays cleared. A packet's metadata is now regenerated by the commit that invalidates it, in the same commit, so nobody has to remember. The gate refuses in the two cases where regenerating would describe content the commit does not carry, and stays silent on the common case where an edit leaves the derived fields identical.

Alongside that, two tooling fixes that the sweep forced into the open. The metadata writer had a check testing two conditions and reporting only one of them, which made eight correctly-excluded folders look like failures for a reason that was not true. And the script driving it used a different definition of "packet" than the writer, so it kept handing over targets the writer would refuse.

## How It Was Delivered

The sweep ran per track so a failure would localise rather than sink into one number, and the one subtree carrying another session's uncommitted work was excluded by name.

The gate is a near-copy of the compiled-routing re-mint gate added days earlier, because the two problems are identical: a derived artifact whose regeneration nothing enforced. Copying its shape also copied its refusals, which are the part that had already taken the measuring.

Then the eight failures, which are the story. The error read `target is not a spec folder (missing spec.md)` for eight folders that all had a `spec.md`. Three explanations were offered before any was tested. First that these were directories carrying metadata without being packets, which a search immediately contradicted. Then that the failures were transient write collisions, contradicted by a re-run producing the same eight. Then that they were folders missing metadata rather than carrying spurious metadata, contradicted by listing them.

Reading the check ended it in one look. It tested a numbered folder name AND a `spec.md`, and reported only the second. Every one of the eight failed on the name. Each wrong explanation had been reported before opening the four lines that decided the question.

Tracing it also exposed a live bug in the gate being added here. It resolved a document's packet by `graph-metadata.json` alone, so staging anything under one of those grouping directories would have called the repair tool, got a non-zero exit, and blocked the commit. The investigation was worth more than the fix it produced.

<!-- ANCHOR:decisions -->
## Key Decisions

| Decision | Why |
|----------|-----|
| The name rule was kept rather than relaxed | The operator explicitly allowed relaxing it. Measuring first showed the three-digit prefix is what keeps the discovery walk out of benchmark fixtures and backup directories that also carry a `spec.md`, so relaxing it would write generated metadata into test fixtures. |
| The error returns a reason rather than a boolean | A predicate with two conditions and one message sends every reader to the wrong place, which it did three times in one session. |
| The caller adopted the writer's rule | Two definitions of "packet" in one pipeline is what turned correctly-excluded folders into a failure count that meant nothing. |
| Auto-fix rather than block-and-instruct | Confined to derived artifacts whose content follows mechanically from the staged input, which is the same carve-out the routing gate documents. |
| `sk-design/019` excluded from the sweep | Another session was writing to it throughout. The exclusion is recorded rather than left implicit. |

## Follow-Up: The Sibling Route-Remint Gate Proved The Wrong Proposition

The route-remint gate sits directly above this one in the same `pre-commit` file and shares its shape: re-mint, copy the runtime manifest over its authored twin, `git add` both, then confirm the add landed. Its confirmation step was wrong, and it was wrong in both directions.

It counted paths whose **staged blob differs from HEAD**, while its own comment says the intent is to confirm both paths are **in the index**. Those are independent propositions.

- A mint that produced no change left both manifests equal to HEAD, so the count was zero and a correct commit was blocked. This fired twice in one session, on `sk-code` and on `cli-external-orchestration`, and both times the only way forward was the documented bypass.
- Worse in the other direction: a stale blob already staged from an earlier run still differs from HEAD, so the count reached two and a failed `git add` passed. That is precisely the failure the check exists to catch.

The confirmation now asks the intended question per path: the path is tracked, and there is no worktree-versus-index difference, so the index holds exactly what the mint just wrote. A no-op mint passes, and a failed add still blocks.

Reproduced both directions in an isolated repository with hooks disabled, and again against this repository's real `sk-code` manifests:

| Scenario | Old check | New check |
|---|---|---|
| Mint produced no change | 0, blocks a correct commit | 2, allows |
| Mint rewrote, add did not land | 2, passes a stale index | 1, blocks |

`bash -n` and `shellcheck -S error` both clean on the edited hook.

The diagnosis came from a DeepSeek dispatch through cli-opencode. It found the false-pass direction, which the original report of this defect had missed, and both directions were confirmed here before the change was written.

## Known Limitations

1. **Seven working directories inside two packets still get no derived metadata.** They are named `research`, `packet-docs`, `sandbox-test` and `scopes/A` through `C`, and they hold a `spec.md` without following the numbered-folder convention. That is now the correct outcome rather than a failure, and renaming them would change paths inside two completed packets. It is an operator decision, not a repair.

2. **`specs/sk-design/019-sk-design-diagram-upgrade` was not swept.** Another session held uncommitted work there for the whole of this one. It is a single command against a clean tree whenever that lands.

3. **The system-speckit track carries authored validation debt no tool clears**, led by 135 packets failing the grep convention and 78 missing a frontmatter memory block. It is hand-written content, it predates this work, and a future sweep that only runs the repair tool will not move those numbers. Whether any of it is mechanically fixable has not been measured.

4. **The effort pin between the two gates is duplicated, not shared.** The routing gate and this one each carry their own copy of the packet-name rule, and the metadata writer carries a third. Nothing forces the three to agree, which is the same class of problem this packet just fixed one instance of.

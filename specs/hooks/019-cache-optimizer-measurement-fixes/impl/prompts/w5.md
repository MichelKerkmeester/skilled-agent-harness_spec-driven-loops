## The defect

When a provider rejects `prompt_cache_key` with a 400, the extension learns it and stops sending
the key — but only into `promptCacheKeyUnsupportedModels`, an in-process `Set`
(`index.ts:8456`) with no persistence. Every new process re-learns the same fact by spending
another failed request.

## What to build

Persist the learned rejection so it survives a restart.

- Keep injection **default-on**. Do not flip the default to opt-in: an unconfigured proxy that does
  support the key should still get it. The fix is memory, not timidity.
- Persist alongside the existing extension state rather than inventing a second store.
- A persisted entry must be per model, not global.
- Loading a state file that predates this change must not crash and must behave as "nothing learned".

## Proof required

1. After a matching 400 for a model, a fresh load of the state omits the key for that model without
   a second 400.
2. Negative control: an unrelated 400 does not teach a rejection. The existing coverage at
   `tests/review-findings.test.ts:169-240` asserts this; it must still pass.
3. Negative control: a model that never 400'd still gets the key.
4. A pre-change state file loads cleanly.

Each new test must fail with your change reverted.

# The runtime answer seam

`answerItem` is assembled from six phases: 001 adds the actor and the scope, 002 the no-resume option, 005 the review seam, 006 the grant and the guarded write, 010 the conversation id and 011 the roster check and the channel surface. [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/001-activity-and-actor/spec.md, REQ-010] [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/002-routine-layer/plan.md, section "Key Components"] [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/005-memory/spec.md, REQ-013] [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/006-approval-grants/plan.md, section "Key Components"] [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/010-conversations/002-conversation-runtime-and-chat-verb/spec.md, REQ-012] [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/011-messaging-channels/003-link-roster-and-answer-gate/spec.md, REQ-021] This file is the one place the whole order is written.

The screen's side of an answer is drawn in [state-machines.md](../003-terminal-screen/005-answer-flow/design/state-machines.md): its section 3 is the sequence and its section 4 is the answer contract, the argv per answer kind in 4.1 and every return in 4.2. This file keeps those names: the worker's `Answer` effect, the `Answered` message and the three result classes `done`, `gone` and `refused`. It does not copy the screen's tables.

Field names of the item, the answer object and the grant object are owned by [records.md](records.md). Refusal rows are in [refusals.md](refusals.md).

## 1. THE SEQUENCE

Every step runs inside `answerItem` unless its owner column says `bots.cjs` or a transport. Steps 6 to 18 hold the item lock, and step 18 runs on every exit after step 6.

### 1.1 What the caller sees

| Path | `status` | stdout of `bots answer` | Exit | Screen class |
|------|----------|-------------------------|------|--------------|
| A resume was queued | `enqueued` | `bots: item <id> answered; resume request <rid> enqueued` [SOURCE: .skilled/bin/bots.cjs:298-300] | 0 | `done` |
| The same answer again | `duplicate` | `bots: item <id> answered; resume request <rid> duplicate: already queued` | 0 | `done` |
| A review kind settled it, or the no-resume option | `reviewed` | `bots: item <id> answered; <kind> review recorded` | 0 | `done` |
| Any refusal | none | `bots: <reason>` or `bots: <reason>: <detail>` on stderr | 4, or 2 for step 1 | `gone` for `item-unknown`, `item-expired` and `item-answered-differently`, `refused` for the rest, as section 4.2 of the screen contract rules |

`item-busy` reaches the screen as `refused`, and a retry with the same key is safe, because the answer is idempotent for one text and one scope.

The `reviewed` status carries the item's `kind`, and the answer verb prints the review line in place of the resume line, because no request is queued on that path. `AnswerResult` gains that status and the kind in `answer.ts`, and the verb reads them rather than assuming a resume.

## 2. ITEM STATE TRANSITIONS

`open`, `answered` and `expired` are derived on every read and never stored. [SOURCE: .skilled/skills/system-skilled-bots/runtime/lib/needs-you.ts:135-138] Whether an answered item still waits on its resume is derived too, by `itemAwaitingResume`. [SOURCE: .skilled/skills/system-skilled-bots/runtime/lib/needs-you.ts:320-333] Review kinds never hold a bot, because 005's kind filter skips every item whose `kind` is not `decision`. [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/005-memory/spec.md, REQ-009]

| From | Event | To | Writer | Holds the bot's unattended runs |
|------|-------|----|--------|---------------------------------|
| none | A run parks a `[NEEDS-DECISION]` question | `open`, kind `decision` | the runner's gate | Yes |
| none | A clean run prints `[REMEMBER] <type> <fact>` | `open`, kind `memory-proposal`, `botId` `memory-proposals` | the runner, 005 | No |
| none | `bots skill propose <run-id>` | `open`, kind `skill-proposal`, `botId` `skill-proposals` | `skill-proposal.ts`, 009 | No |
| none | The tenth consecutive failure | `open`, kind `decision`, `botId` the bot's own | `routine-state.ts`, 002 | Yes, and the `disabled` switch is set as well |
| `open` | Any refusal in steps 1 to 10 | `open` | none | unchanged |
| `answered`, awaiting resume | `bots enable` with the no-resume option on the fatigue item | `answered`, settled, the queued resume dropped | `answerItem` | No |
| `open` | Step 11 on a `decision` item | `answered`, awaiting resume | `answerItem` | Yes, until the resume leaves the queue |
| `answered`, awaiting resume | The resume request is claimed and finished | `answered`, settled | the drain | No |
| `open` | Steps 11 and 13 on a review kind, or the no-resume option | `answered`, settled | `answerItem` | No |
| `open` | `now` reaches `expiresAt` | `expired` | none, derived | No [SOURCE: .skilled/skills/system-skilled-bots/runtime/lib/needs-you.ts:243-246] |
| `answered` | The same text and scope again | `answered` | `answerItem`, duplicate path | unchanged |
| `answered` | Another text or scope | `answered` | none, refused `item-answered-differently` | unchanged |
| `expired` | Any answer | `expired` | none, refused `item-expired` | No |

## 3. GRANT LIFECYCLE

A grant is never a standing allow in this packet: its scope is `once` or `deny`, and an answer asking for more is refused `grant-scope-unsupported`. [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/006-approval-grants/spec.md, REQ-006] The `kind`, `action` and `rung` keys are set at birth and never change.

| State | `scope` | `grantedBy` | `grantedAt` | Entered when | Writer |
|-------|---------|-------------|-------------|--------------|--------|
| Born open | `null` | `null` | `null` | The item is written | Every item writer: the gate, the memory-proposal branch, `bots skill propose` and the fatigue item [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/006-approval-grants/spec.md, REQ-004] |
| Granted | `once` | the actor | the answer's `answeredAt` | Step 11 with the scope `once` | `answerItem` |
| Denied | `deny` | the actor | the answer's `answeredAt` | Step 11 with the scope `deny`, given or derived from a NO | `answerItem` [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/006-approval-grants/spec.md, REQ-005] |
| Expired with its item | `null` | `null` | `null` | The item passes `expiresAt` unanswered | none, the grant is never written again |

## 4. DECISIONS TAKEN

| Decision | Why |
|----------|-----|
| The review seam has two halves: a claim before the write and a settle after it | 009 requires a stale pin to leave the item open and write nothing [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/009-skills/spec.md, REQ-006] [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/009-skills/spec.md, SC-005], while 005 places the seam after the answer and the scope are written [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/005-memory/spec.md, REQ-013]. Only a split satisfies both, and the same split carries 005's refusal of an answer other than `confirm` or `reject` |
| The lock is taken before the read, not just before the write | Two answers that both read `open` before either locks would both write, which is the race 006 closes [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/006-approval-grants/spec.md, REQ-014] |
| A stale lock is reclaimed when its pid is gone or it is older than 60 s, waited on for 2,000 ms otherwise, then `item-busy` | 006 states no stale rule [SOURCE: specs/system-skilled-bots/002-openbot-parity-research/003-plan-depth-research/research/research.md:129]. The run lease already reclaims by owner pid and nonce, and this reuses that model [SOURCE: .skilled/skills/system-skilled-bots/runtime/lib/runner.ts:12-16]. An answer holds the lock for milliseconds, so 60 s is long |
| The repository identity (step 3) and the answer identity (step 8) are two steps | The plan-depth research lists one "identity check" [SOURCE: specs/system-skilled-bots/002-openbot-parity-research/003-plan-depth-research/research/research.md:255], and the runtime has both checks |
| The roster check runs before the lock | It reads no item and refuses most often, so it never makes a second answerer wait |
| Steps 14 and 15 are skipped when the item already names a `resumeRequestId` | The no-resume path sets that id with no request behind it. Re-sending the answer would otherwise enqueue a resume of the tenth failed run, because no seen marker exists for it |
| The no-resume path writes the id the resume would have had | `itemAwaitingResume` treats a null id as waiting [SOURCE: .skilled/skills/system-skilled-bots/runtime/lib/needs-you.ts:323-330], so an answered fatigue item with a null id would hold the bot's scheduled runs after `bots enable`. The derived id names no queued file, so nothing waits on it [SOURCE: .skilled/skills/system-skilled-bots/runtime/lib/request-record.ts:126] |
| `grantedAt` equals the answer's `answeredAt` | 006 writes the grant and the answer in one write so the two cannot disagree [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/006-approval-grants/spec.md, REQ-001] |
| A settle effect checks whether it already landed before it applies | A stop between steps 11 and 13 must not append the same fact twice when the answer is re-sent |
| Review items are born with `options: ["confirm", "reject"]`, `reject` derives the scope `deny`, and a NO records `deny` even when `--scope once` is given | The screen sends `approve`, `deny`, an option text or free text [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/003-terminal-screen/005-answer-flow/design/state-machines.md, section "4.1 The argv per answer kind"], and 011 sends a number or YES/NO [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/011-messaging-channels/004-approval-index-and-send-queue/spec.md, REQ-008]. With the two options set, the screen's digit key and 011's numbered reply and buttons send the literal. 005 accepts `confirm` and `reject` only [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/005-memory/spec.md, REQ-008] and 009 names no vocabulary, so a reject would otherwise record `once`, an approval, against 006 REQ-005 [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/006-approval-grants/spec.md, REQ-005]. The screen passes `--scope once` on every digit pick and every typed line, and an explicit scope always wins, so the rule has to sit in the runtime rather than in the screen, which ships before 005 and 006 |
| The no-resume option on an item already answered skips the answer-identity judgement, drops any queued resume and goes to step 16 | 006 lets `bots answer` or the screen answer the fatigue item first, which queues a resume [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/006-approval-grants/spec.md, REQ-004]. `bots enable` then answers with its own text [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/002-routine-layer/plan.md, section "Key Components"], and step 8 would refuse it `item-answered-differently`, so the resume would never be dropped. The text `enable` passes is still 002's to fix |
| A settled review prints `<kind> review recorded` with status `reviewed` | 009 says the verb reports a recorded review instead of a request and fixes no text [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/009-skills/spec.md, section "Files to Change"] |
| The terminal transport answers on the surface `channel` with the OS user as the actor | 011 chose it, because this sequence names every transport the `channel` surface [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/011-messaging-channels/005-polling-transports/spec.md, REQ-015]. The roster check in step 5 then applies, so on a state root with no roster `bots channel listen terminal` refuses an answer `channel-roster-missing` while `bots answer` from the same terminal refuses nothing. The operator adds a roster, or answers with `bots answer`. Giving the transport the `terminal` surface would be a change to this row and to 011 REQ-015 together |

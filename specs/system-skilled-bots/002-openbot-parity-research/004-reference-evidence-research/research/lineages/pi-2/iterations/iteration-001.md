## Findings

1. **The plan drops the reference's mid-poll webhook recovery, so a webhook set after start wedges the Telegram poller.** The reference clears a webhook twice: once before the first poll, and again *inside* the poll loop when `getUpdates` answers 409 whose description contains "webhook" — it calls `deleteWebhook` and `continue`s into a fresh poll with no backoff. [SOURCE: specs/system-skilled-bots/context/tinychannels-main/src/providers/telegram/channel_ops.rs:1936-1952] [SOURCE: specs/system-skilled-bots/context/tinychannels-main/src/providers/telegram/channel_core.rs:267-272] The plan clears the webhook only in the `listen` start sequence, then says "a `409` from Telegram waits 2 s and polls again". [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/011-messaging-channels/005-polling-transports/spec.md:212] [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/011-messaging-channels/005-polling-transports/spec.md:99] A 409 is not always "another poller": it is also "can't use getUpdates while webhook is active", a state anything that sets a webhook later can produce. Waiting 2 s against that condition never converges. **Observed** on both sides. The evidence supports the reference: the plan needs the in-loop branch, with the same discriminator (does the description name a webhook) so a genuine second-poller 409 still backs off rather than calling `deleteWebhook` in a loop.

2. **A deduplicated Telegram update must still advance the offset, and the reference has a test for exactly that; the plan's offset rule does not say it.** The reference advances `offset` on the seen path before `continue`ing. [SOURCE: specs/system-skilled-bots/context/tinychannels-main/src/providers/telegram/channel_ops.rs:1967-1971] The named test is `a_deduplicated_update_still_advances_the_offset`, asserting the second poll carries offset 21 after a duplicate of update 20. [SOURCE: specs/system-skilled-bots/context/tinychannels-main/src/providers/telegram/channel_ops_tests.rs:3736-3775] The plan states only "The offset moves past an update only after the seen record is written". [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/011-messaging-channels/005-polling-transports/spec.md:145] That phrasing is satisfied by "seen record already existed, so skip" — which leaves the offset pinned and re-fetches the same update forever. **Observed.** The evidence supports the reference; the plan's REQ-009 should gain the duplicate-path clause and its acceptance criteria should mirror this test.

3. **The reference commits the offset after the provider action succeeds, not after the seen record is written; the plan's wording admits a crash window that loses a message.** The reference marks the update acknowledged locally "only after its provider-owned action or typed ingress has succeeded", and both `track_update_id` and the offset bump happen inside that closure. [SOURCE: specs/system-skilled-bots/context/tinychannels-main/src/providers/telegram/channel_ops.rs:1973-1981] Under the plan's wording, a crash between writing the seen record and handing the message to the runtime counts as consumed: the offset has moved, the message is gone. [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/011-messaging-channels/005-polling-transports/spec.md:145] **Observed (reference) / inferred (plan's implementation risk).** The evidence supports the reference's ordering; the seen write should be the *last* step of ingest, or the offset should be derived from a record that is written after ingest commits.

4. **The plan collapses two distinct send-failure states into one `unknown` and therefore never retries a send that provably never started.** The reference carries three recovery states: `SendAttemptStarted` (marked before the platform I/O), `UnknownAfterSend` (an attempt reached the platform and the outcome is unknown), and nothing (a fresh entry). [SOURCE: specs/system-skilled-bots/context/tinychannels-main/src/delivery/queue.rs:79-90] Its drain routes both non-empty states into a reconciliation path that asks the handler for an `UnknownSendReconciliation` — `Sent` (ack), `NotSent` (retry), `Unresolved` (leave pending, log) — instead of resending blindly. [SOURCE: specs/system-skilled-bots/context/tinychannels-main/src/delivery/queue.rs:190-240] [SOURCE: specs/system-skilled-bots/context/tinychannels-main/src/delivery/types.rs:23-29] The plan's rule is one state: "a `sending` entry found at the start of a drain becomes `unknown`", and `unknown` is never retried. [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/011-messaging-channels/004-approval-index-and-send-queue/spec.md:130] That is correct at-most-once behaviour for `UnknownAfterSend`, and wrong for a process that died before issuing the HTTP request: the notice is never delivered and never retried, and the plan records it only as `unknown`. **Observed.** The evidence supports a two-state split with the reconciliation port: `send-attempt-started` is marked before the I/O, `unknown-after-send` is set when an attempt returned an ambiguous error, and only the second one is unretryable. The plan's handoff criteria ("an uncertain send is never retried") is satisfied by that split and by nothing less.

5. **The reference's approval surface is text-only and fail-closed, so the plan's button forms have no reference implementation to mirror.** The whole prompt vocabulary is `"Reply \`yes\` to approve or \`no\` to deny."`, and the surface is gated on the channel capability `chat_approvals`. [SOURCE: specs/system-skilled-bots/context/tinychannels-main/src/approvals/mod.rs:20-26] [SOURCE: specs/system-skilled-bots/context/tinychannels-main/src/approvals/mod.rs:44-52] When no reply context was recorded for a conversation, `surface()` returns `NoReplyContext` and the parked call "will time out denied". [SOURCE: specs/system-skilled-bots/context/tinychannels-main/src/approvals/mod.rs:54-60] [SOURCE: specs/system-skilled-bots/context/tinychannels-main/src/approvals/mod.rs:110-125] The plan's M02 and M04 rows design button forms for `telegram` and `slack` only, with the text forms M01 and M03 on the other three. [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/011-messaging-channels/001-channel-ux-and-message-map/design/message-catalog.md:44] [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/011-messaging-channels/001-channel-ux-and-message-map/design/message-catalog.md:46] **Observed.** Two consequences the plan does not record: (a) the only callback machinery to lift is the reference's `acknowledge_callback` plus `callback_is_allowed` pair, which acknowledges the callback query before the item is resolved [SOURCE: specs/system-skilled-bots/context/tinychannels-main/src/providers/telegram/channel_ops.rs:1978-1990]; acknowledging first means a crash after the ack loses the press, which is the opposite of the plan's index-first ordering and is worth a sentence in child 004's ordering decision. (b) The reference's fail-closed `NoReplyContext` is the failure the plan already answers better — its REQ-006 makes a press with no index entry fall through to `answerItem` rather than denying the parked call. [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/011-messaging-channels/004-approval-index-and-send-queue/spec.md:128]

6. **OpenMausBot has no liftable Slack or Telegram transport: its Slack surface is a hosted management URL on the enterprise tier.** `hostedSlackManagement` returns `{available:false}` unless hosted workspace configuration yields a portal membership, and when it does it returns only `https://<admin>/slack?...` — no message path, no socket, no webhook. [SOURCE: specs/system-skilled-bots/context/OpenMausBot-main/server/hosted-slack.ts:4-20] The prior synthesis already established that `enterprise/` is not Apache-2.0. [SOURCE: specs/system-skilled-bots/002-openbot-parity-research/001-openbot-parity-research/research/research.md:106] **Observed.** So for phase 011, OpenMausBot is a dead end and tinychannels is the only source; the node's OpenMausBot scope entry can be closed for transport evidence.

## Reflection
- What worked and why: reading the *test names* beside the code. `a_deduplicated_update_still_advances_the_offset` and `socket_mode_acks_envelopes_dispatches_events_and_reconnects_after_a_disconnect` each name the exact failure the repo was fixing, which is the cheapest reliable source of "what broke in production".

- What I would do differently: for every remaining phase, grep the reference test files for assertion names containing `reconnect`, `duplicate`, `restart`, `crash` before reading the implementation — the failure inventory is the part of this deliverable the plan cannot get anywhere else.

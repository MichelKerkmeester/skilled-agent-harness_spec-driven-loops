## Findings

1. **006-approval-grants (and 002-routine-layer's trigger seam).** The reference orders the approval decision by *who is asking* before it looks at the action, and one origin is refused outright: "a Cron external effect is refused outright", `durable_tool_trust` short-circuits on `request.caller.origin == Origin::Cron`, and a `Rule::Deny` from the origin evaluation returns `Error::Denied` before any prompt is created. The plan's ladder is kind-first: `classifyAction` reads the whole question and returns the strictest kind, then rung 1 asks or the `bot` fallback parks the question as a needs-you item (REQ-002, REQ-003). A scheduled routine that hits a `pay`, `send` or `credentials` kind therefore parks and holds the bot until a person answers, at whatever hour the cron fired, while the reference's own answer for that case is a refusal the operator can see in the run record rather than an indefinite wait. The evidence supports adding one origin rung *before* the kind rung: a run with a `cron` trigger whose kind is not `other` refuses by name instead of parking. 2. **006-approval-grants.** An answer in the reference is bound to the process that asked it, not only to the record: the review path refuses unless the answer carries a `decision_ticket_sha256` equal to the row's ticket, a non-empty `actor` of at most 1024 bytes, and a `host_instance` equal to the current instance unless the choice is `Deny`; a registration made against a scope whose `generation` is no longer current is refused with a doc comment that says exactly that ("Deny a registration made against a generation that is no longer current"). The plan's answer path keys on the item id — "the overlay captures the item id, never the row index, so a refresh that reorders rows cannot retarget the answer" — and REQ-005 records `grantedBy` and `grantedAt`, but nothing binds the answer to the process that wrote the question, so an item written by an earlier run of the same bot is answerable by a newer one with a different working state. The ticket-and-instance pair is the cheapest mitigation and needs one field on the item, not a store. 3. **008-vault.** The plan's leak matcher is value-based: the known-secret map plus each stored value's plain, standard-base64 and `encodeURIComponent` forms, and its own non-goal table names "a transformed value, such as reversed, split across lines or hex" as unmatched. The reference adds a second, value-free layer: a fixed pattern set with per-rule validators — `Always`, `Card`, `Iban`, `NationalId`, `Ip`, `Phone` — plus PEM private-key blocks, assignments, gated assignments, cookie headers, home paths and endpoint URLs, all compiled once and described as "fixed linear-time patterns". A customer's card number or IBAN that the vault never stored is caught by the validator layer and missed entirely by the plan's map. For a small team the card and IBAN validators are the two worth lifting as behaviour; the phone and IP validators cost false positives on ordinary logs, so the reference's own separation into named validators is what makes the choice possible. 4. **008-vault.** Redaction in the reference applies to a *parsed* value as well as to a string: the redactor returns `serde_json::Value::String(MARKER.into())` in place of a structured field, decodes and re-scans four base64 alphabets (`STANDARD`, `STANDARD_NO_PAD`, `URL_SAFE`, `URL_SAFE_NO_PAD`), and refuses an oversized input with `Error::InvalidArguments` rather than truncating it (`output_bounded` against `MAX_OUTPUT`). The plan's post-run scan reads raw stdout and files with the known-secret map, and its redaction token is `[redacted: <name>]`. Two consequences follow that the plan does not address: a value that appears only in a JSON-escaped form (`\u002f` for a slash, `\"` for a quote) is not matched by a raw byte scan, and a run that produces a gigabyte of stdout is scanned whole with no stated ceiling. Both are cheap to close — scan the parsed event payloads the runner already parses, and cap the scanned prefix the way the reference caps its input. 5. **Net-new candidate: an owner-shell command scanner for the run that has no app allowlist.** `tinysecurity-policy` states its own default as "Only concrete supported checks can authorize effects; unknown tools deny", and it carries a whole `command_shell` module for the owner's shell — `classify`, `env_guard`, `executor`, `scan`, with its own classify and scan test files. The 003 plan says in as many words that "`apps` is a filter, not a sandbox: it narrows the server list the run's config names, and it confines no child that reads a config from another path", so a bot declaring no apps still reaches a shell through its executor and nothing in the plan inspects the command. This is the one place where a reference repo has a guard with no plan counterpart at all, and it is not in the parity synthesis's skip list. Value to a small team: medium-high, because it is the difference between "the bot cannot reach that server" and "the bot cannot run that command"; size S for a deny-list classify-only pass over the command string with one refusal name, M for the env guard, and XL for doing it properly across executor kinds (which is why the reference's version is 288k lines). It belongs to no planned phase as written, so it is recorded here and recommended for a later packet rather than folded into 007. ## Reflection

- **What worked and why:** reading the plan's requirement tables before the reference. Every gap is stated as "REQ-nnn requires X and the reference does Y", which is checkable in both directions, and it prevented re-finding the two things the plan already does better than the reference (encoded-form matching, the `[redacted: <name>]` token with its withheld-delivery rule).
- **What did not work and why:** three greps for exported names in `tinysecurity-audit` produced nothing because the crate keeps its engine private and exports only a small bus contract; the crate-level doc comment was the only usable evidence, and it was too thin to carry a finding. The lesson repeats iteration 1's: in these workspaces, read the module doc first and treat an empty grep as "not established", never as "absent".
- **What I would do differently:** for a crate with a private engine, go straight to its `lib.rs` doc and its test file names — `command_shell_scan_tests.rs`, `engine_gaps_tests.rs`, `windows_acl_tests.rs` — because the test names announce the failure classes the authors guarded, which is exactly the "which failures does the plan not guard against" half of the topic.

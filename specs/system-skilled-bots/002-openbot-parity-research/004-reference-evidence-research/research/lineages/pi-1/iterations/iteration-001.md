# Iteration 1: openhuman-full, the five vendored crates and the terminal screen

## Focus

Frontier node F-1-003: what do openhuman-full's five vendored crates (tinyagents, tinyconnectors, tinymemory, tinyhumans-sdk, tinysecurity) and its openhuman-tui crate hold that openhuman-main lacks, and what does that change for 003-terminal-screen and its six children and for any other planned phase?

The first premise to test is the one the topic asserts: that openhuman-full carries "a built openhuman-tui crate that openhuman-main lacks". It does not, and section Findings item 1 states what it carries instead. The rest of the iteration reads the reference for what phase 003's six children must mirror, and for what the vendored crates change in the other phases.

## Findings

1. **003-terminal-screen, phase 003 child 006 (hardening).** openhuman-full does not carry a TUI crate that openhuman-main lacks: the two `crates/openhuman-tui` trees are the same 432K and their `src/` file lists are identical, and the single README the plan cites from `openhuman-main` is the same file. What openhuman-full adds is the *source* of the twenty-one vendored TinyHumans crates: every `vendor/<crate>` directory under `openhuman-main` is empty (0 bytes) while openhuman-full's `vendor/` is 417M, and openhuman-full's root manifest path-links them (`tinyagents-hooks = { path = "vendor/tinyagents/crates/tinyagents-hooks" }`). The reference evidence for phase 003 therefore comes from the same TUI source the plan already cites; the new material is the vendored crates. 2. **003-terminal-screen, child 006-hardening-and-proof.** The TUI treats terminal ownership as a panic-safe invariant, not as a normal-exit concern: its module doc says alternate screen and raw mode "**must** be undone on every exit path — normal return, `?` propagation, and panic — or the user's shell is left in a broken state (no echo, no line editing, stuck on the alternate screen)", a `TerminalGuard` restores on `Drop`, and `install_panic_hook` chains `restore` ahead of the previous hook so the backtrace prints to a sane terminal. `restore` itself is ordinary crossterm teardown (`LeaveAlternateScreen`, `disable_raw_mode`), and a failed restore is logged rather than propagated. The 003 plan's hardening child requires `cargo fmt`, `clippy --all-targets -D warnings`, `cargo test` and a release `pty_smoke` run; no line of it requires a panic hook or a restore-on-drop, so a panic in the render loop is a failure the plan does not guard against, and the pty smoke test would pass while a panicking frame still leaves the operator's terminal in raw mode. 3. **003-terminal-screen, child 004-panes.** openhuman-tui bounds every tool-output string in the reducer rather than at the draw call, and it marks the cut: `bounded(value, limit)` sanitizes, returns early when the length fits, walks back to a char boundary (`while !safe.is_char_boundary(end) { end -= 1 }`), and appends `\n[preview truncated]`. The plan clips by display width in `view/panes.rs` (REQ-021) and its mockups show a clipped too-small message, but no requirement in the phase names a marker for a clipped runtime string, so a clipped question reads as a complete one. The reference's char-boundary walk is the part to mirror: a byte-slice clip of a multi-byte question panics, and the plan's clip is display-width based only in `view/panes.rs`, which is a different code path from the answer overlay in child 005. 4. **003-terminal-screen, child 003-shell-and-navigation.** The reference's loop is fully parameterised and coalesced: `event::poll(Duration::from_millis(100))` for input, a `tokio::time::interval(Duration::from_millis(120))` spinner ticker, and a redraw gated on `dirty && last_draw.elapsed() >= Duration::from_millis(16)` so a burst of events draws once per frame. The 003 plan polls its verbs on a 5-second timer and redraws per event, and no child names a coalescing rule or an input poll timeout, so a key repeat storm redraws per key. The reference's 100 ms/16 ms pair is the cheap part to mirror; its 120 ms spinner belongs to a streaming transcript the plan's chat tab does not have yet. 5. **003-terminal-screen, child 004-panes.** The sanitizer the plan cites is a *filter*, and the plan's rule is a *replacement*, so the two differ in a way a test would catch: `safe_text` drops every control character except `\n` (`filter(|ch| !ch.is_control() || *ch == '\n')`), while the plan replaces each control character, line breaks included, with `?`. The plan's choice is the one the evidence supports for a one-line row — a kept `\n` inside a fixed-height row either corrupts the frame or is silently drawn as a space — and it is already recorded as the single sanitizer rule in `004-panes` REQ-021. What is new here is that the reference's behaviour is not copyable as written, because it keeps newlines by design: its rows are multi-line transcript blocks, and the plan's rows are single-line. [SOURCE: specs/system-skilled-bots/context/openhuman-full/crates/openhuman-tui/src/theme.rs:88-93] [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/003-terminal-screen/004-panes/spec.md:160] (observed; the plan-versus-reference reading is inferred)

6. **006-approval-grants, 007-per-bot-apps, 008-vault.** The vendored `tinysecurity` workspace (288,030 `.rs` lines, GPL-3.0-only) is the only reference in the corpus with an approval engine, and it answers the question the plan defers: it carries a four-way decision `ApprovalChoice2 { Once, Tool, Flow, Deny }` — `Tool` is "exactly this reviewed tool and content in the same bound context" and `Flow` is "exactly reviewed content in the same flow" — which is the shape behind OpenBot's "allow for this conversation" and "always allow here". The plan refuses both as `grant-scope-unsupported` and defers the rules store to a later packet, and its own risk row argues that refusal is the honest answer because a standing allow with no store is a lie. The reference supports the refusal on size, but it adds two guards the plan does not name: an approval request carries a TTL capped per origin at 180,000 ms for `Copilot`/`SubAgent` and 600,000 ms otherwise, and a *human-only* tool is barred from the automatic path however it is named (`judge_barred` returns true for `binding::is_native(tool)` or a `HUMAN_ONLY_TOOLS2` member). A plan with an unbounded "expired" item has no maximum age, and a later phase that adds any per-bot app grant inherits the need for both. Licence: GPL-3.0-only, so design reference only, no lifted code. 7. **011-messaging-channels, and 003 child 005-answer-flow.** The reference separates an approval *reply* from an approval *decision* by contract, not by convention: `reply.rs` opens with "Reply parsing produces intent only, never human or execution authority", rejects a reply longer than 4096 bytes as `Invalid`, maps a fixed vocabulary to `AllowOnce`, `Deny` or `Unrecognized`, and persists no text. The plan's terminal answer path is already stronger in one direction — the overlay captures the item id, never the row index, and deny is `n` alone (REQ-013), and a refusal naming `item-unknown`, `item-expired` or `item-answered-differently` moves the overlay to `gone` (REQ-016) — but it has no bound on the *size* of an answer text and no explicit statement that a parsed answer is intent rather than the write itself. The reference's 4096-byte bound and its intent-only sentence are the two parts a channels phase should mirror, because a channel reply is exactly the untrusted input this parser exists for. [SOURCE: specs/system-skilled-bots/context/openhuman-full/vendor/tinysecurity/crates/tinysecurity-approval/src/reply.rs:1-18] [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/003-terminal-screen/005-answer-flow/spec.md:145-158] (observed, plan gap inferred)

8. **005-memory.** `tinymemory` (99,763 `.rs` lines, GPL-3.0-only) models memory as a tree of namespaces, not as two files: the root holds what every agent shares, below it sit agents, teams, users, workspaces and projects nested arbitrarily (`team:acme/agent:writer`), every stored item lives at exactly one node, each `ItemKind` (learnings, documents, conversations) is kept apart so an engine can hold, recall and erase each on its own, and a reader names a `Reach` whose `inherit` defaults on so an agent sees its ancestors. The plan's two-file model (shared `memory/shared.md` plus per-bot `memory/<bot-id>.md`) is the same shape with one level of inheritance and no way to revoke or erase one kind without rewriting the file. Two further guards have no plan counterpart: provenance is a first-class policy where unknown namespaces are untrusted and a connector prefix overrides locally authored text, and the module says plainly that it "does not infer that a marker makes content safe". A bot-proposed fact recalled from a channel is exactly the text that needs that rule. ## Ruled Out

- **Treating openhuman-full as a new TUI design source.** Reading it as a second TUI would have been wasted work: `crates/openhuman-tui/src/` is byte-for-byte the same file list and the same size as `openhuman-main`'s, and the plan already cites that source. Read as a *vendored-crate* source instead, which is where the 658 MB of difference lives.
- **Lifting any vendored crate.** All five name GPL-3.0-only in their own `LICENSE` (and 25 of their crate manifests say `license = "GPL-3.0-only"`), the same licence as openhuman itself. They are design references only; no function is copyable into this MIT tree.
- **Adding `--demo` as a phase-003 requirement.** The reference's `--demo` offline preview is the closest thing to a deterministic renderer harness, but `006-hardening-and-proof` names it and rules it out ("a `--demo` binary, a bench flag, mouse support and a theme picker - the parent rules each out"), and REQ-022 already proves the answer path through a release `pty_smoke` run. Not a gap; not a finding.
- **Recording the sanitizer rule as a new gap in `004-panes`.** It is not a gap: REQ-021 lands exactly the rule the reference's filter is not, and the citation to `theme.rs` is already in the plan. Only the filter-versus-replace divergence is new, and it is finding 5.

- Reading `src/viewport.rs` for selection-anchor semantics (the plan's "a row selected by its index moves under the operator" defect) did not settle it: the cache anchors a *cached block* by index and offset (`anchor: Option<(usize, usize)>`), which is a scroll-position anchor for a transcript, not an identity anchor for a list. Not usable as evidence for the panes defect, so no claim is made.

## Reflection

- **What worked and why:** reading the two checkouts against each other before reading either one. A 757M-versus-99M gap with identical `src/` listings would have been missed by reading openhuman-full alone, and it is the whole answer to half the node's question. The second thing that worked was reading the plan's requirement tables *after* the reference file, because a requirement id makes a gap checkable: "006 has REQ-012 to REQ-022 and none of them names a panic hook" is a claim the citation resolves.
- **What did not work and why:** grepping the five vendored crates by contract name (`PermissionLevel`, `context.md`, `pub struct` in `tinyconnectors-bus`) returned nothing useful three times because these are large multi-crate workspaces whose module paths are nested two and three deep; the line was found only by listing crates first and then reading a named file. The `timememory` and `tinyconnectors-bus` `pub struct` greps failed for the same reason and produced no claim.
- **What I would do differently:** list a workspace's crate directories and read one file per crate before grepping for a contract, and cite directory-level facts by the manifest line that wires them (the `Cargo.toml:46-47` path dependencies) rather than by `du` output, which resolves no `path:line`.

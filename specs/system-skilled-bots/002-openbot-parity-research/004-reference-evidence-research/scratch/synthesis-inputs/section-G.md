## What openhuman-full adds over openhuman-main

`openhuman-full` is `openhuman-main` plus two things: the contents of the 21 vendored submodules under `vendor/`, and a `.git` folder. A `diff -rq -x vendor` of the two trees prints one line, `Only in openhuman-full: .git`. `openhuman-full` holds 29,050 files outside `.git` against 7,718 in `openhuman-main`, and 21,332 of them are under `vendor/`. In `openhuman-main` the same 21 folders exist and each holds 0 files, so a claim that `openhuman-main/vendor/` does not exist is wrong. The vendor tree is 417M on disk and the `.git` folder 241M. All 21 folders are the submodules `openhuman-main/.gitmodules` names [SOURCE: C/openhuman-main/.gitmodules:1-73]. The root manifest keeps `vendor` out of the workspace [SOURCE: C/openhuman-full/Cargo.toml:24-25] and path-links two `tinyagents` crates into it [SOURCE: C/openhuman-full/Cargo.toml:46-47]. That manifest is byte-identical in `openhuman-main` [SOURCE: C/openhuman-main/Cargo.toml:46-47], so the paths resolve only in the full checkout. There are 21 crates, not the five the run brief named. Every one is GPL-3.0, so every one is a design reference only: mirror the design, copy no code. Each crate is itself a Cargo workspace, and 16 of the 21 vendor a further copy of `tinybus` or other crates under their own `vendor/`. The lineage line counts add that nested copy (for example tinyeventqueues is 15,495 own lines plus 73,936 nested, which is the lineages' 89,431). Counting rule for the table: own files of every type and own `.rs` files and lines, with the crate's nested `vendor/` and `worktrees/` excluded, and the nested `vendor/` `.rs` lines in brackets. The whole tree is 15,057 `.rs` files and 4,379,258 `.rs` lines with nesting included. ## Proposed order

1. Per-bot hourly action cap: the smallest guard against the most likely cost surprise, and it applies to every trigger the plan already has.
2. Inbound coalescing and outcome per message: the first group chat after 011 meets it, and the dedupe half is already planned, so only the folding and the cap are new.
3. Stall watchdog: one timer and one cause, MIT, and it turns a silent 15-minute hold into a named row.
4. Silent health probe: MIT, small, and it reuses the routine layer, so an unattended host gets a signal it has none of today.
5. Pattern redaction on outgoing text: the leak class 008 does not catch, which becomes reachable once 011 sends text to chats.
6. Reader-set labels: the only guard against an audience leak, Apache-2.0, but it needs a label on memory and conversations, so it is larger.
7. Live skill-adherence check: cheap data, Apache-2.0, but it needs a tool-call trace the runtime does not record yet.
8. What-if read: MIT and read-only, and it pays off only once 006 to 008 have deciders to run.
9. Summary beyond the conversation window: felt in long chats only, and 010 already names compaction as a later packet.
10. Long-ask acknowledgement and routine-to-conversation link: weak, because the plan already returns a result at run end.
11. Next-step text on refusals: polish, a table of sentences.
12. Tool-name wording: polish, one pure function.
13. Document output: rarely asked for by a terminal-first team, and GPL design only.
14. Egress URL policy: the runtime's own outbound surface is small, and children's traffic is outside its reach.
15. Trace replay checker: built for a multi-tenant relay the skip list excludes.
16. Package manifest: needed only for cross-repository distribution, and half of it waits on deferred hooks.

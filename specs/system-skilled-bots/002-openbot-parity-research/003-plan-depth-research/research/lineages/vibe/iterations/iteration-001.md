Frontier node F-1-001 (depth 1, scope specs/system-skilled-bots/003-openbot-parity-build/001-activity-and-actor, specs/system-skilled-bots/003-openbot-parity-build/002-routine-layer, specs/system-skilled-bots/003-openbot-parity-build/005-memory, specs/system-skilled-bots/003-openbot-parity-build/006-approval-grants, specs/system-skilled-bots/003-openbot-parity-build/010-conversations, .skilled/skills/system-skilled-bots/runtime/lib): Data and contracts: for phases 001, 002, 005, 006 and 010, are every record schema, field, state machine and bots --json payload specified completely enough to build without a decision? ## Actions Taken

2. Searched the whole packet for schema artifacts: `find specs/system-skilled-bots/003-openbot-parity-build -name "*.schema.json" -o -name "*schema*"` returns no schema file; the only JSON files are research state and graph metadata.
3. Read the live record types the phases extend: `NeedsYouAnswer`/`NeedsYouItem`/`ITEM_KEYS` in `needs-you.ts`, `RunSummary`/`RunRow` in `status-index.ts`.
4. Read the parent phase map's dependency column and 003's child `006-hardening-and-proof` fixture paragraph, which is the only place the `--json` contract set is enumerated.
5. Grepped every phase spec for migration/backfill/rollback language to test whether a stored-shape change has a migration rule.

## Findings
1. **P0 — No schema file or contract document exists anywhere in the packet, so every record shape is prose in a REQ table and no builder can check a field name against a single source.** The packet holds fourteen phase folders and zero `*.schema.json` files; the only JSON under `specs/system-skilled-bots/003-openbot-parity-build/` is research state (`deep-research-config.json`, `findings-registry.json`, `frontier-nodes.jsonl`). The nearest thing to a contract is 003's fixture, described as "the copy of every `--json` contract the screen reads" [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/003-terminal-screen/006-hardening-and-proof/plan.md:122]. Closing artifact: a packet-level `contracts/` folder with one JSON Schema per record (needs-you item, answer, run record, run summary, activity payload, inbox payload, routines payload, conversation message, grant, memory entry, routine state) plus a `contracts/README.md` index naming the owning phase per file. Because 001, 002, 005, 006, 009 and 010 all add fields to the same three records, the folder belongs to a new cross-cutting phase (`015-contracts-and-schemas`) that lands before 001, not to any one child.
2. **P0 — 005's memory entry line format is unspecified: five fields are named, the serialization is not.** The plan says `memory.ts` "owns the entry line, its five fields, the four types, the three bounds, the parser, the renderer" [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/005-memory/plan.md:60], and REQ-001 names type, date, actor, source and text [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/005-memory/spec.md:157], but no literal example line, delimiter, escaping rule for a `|` or a newline, or `--forget` index rule appears in spec, plan or tasks. Two builders produce two incompatible files, and the acceptance criteria only test round-trip, so both pass. Closing artifact: `contracts/memory-entry.md` with one literal example line, the delimiter, the escaping rule, the index rule, and the 60-entry/3,600-byte/400-character bound restated as a table.
3. **P1 — 001 adds `by` and `scope` to the answer object but never states what an answer written before the phase reads as, while the run record's null rule is stated twice.** `NeedsYouAnswer` is `{text, answeredAt}` today [SOURCE: .skilled/skills/system-skilled-bots/runtime/lib/needs-you.ts:25-28] and `validateNeedsYouItem` requires `answer.text` and `answer.answeredAt` [SOURCE: .skilled/skills/system-skilled-bots/runtime/lib/needs-you.ts:117-120]. 001 states the null rule for `actor` and `answeredBy` on the run record [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/001-activity-and-actor/spec.md:193] and for the index summary [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/001-activity-and-actor/spec.md:192], but REQ-004 and REQ-010 say only that the answer "records" `by` and `scope` [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/001-activity-and-actor/spec.md:158] [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/001-activity-and-actor/spec.md:166]. A builder must decide whether a required `by` refuses every existing item file. Closing artifact: one nullability sentence in 001 REQ-004 plus a `needs-you.vitest.ts` row for a pre-phase answer, and the answer schema in `contracts/`.
4. **P1 — 002's routine state file has three named fields and no schema.** `recordUntilOutcome` writes `untilMetAt`, `evaluateFatigue` records `fatiguedAt` and the item id [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/002-routine-layer/plan.md:62], but the file's version key, its `botId`, the failure-streak field name, the absent-file default and the write atomicity are all unstated. `bots routines` reads "the identity's routine state files" [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/002-routine-layer/plan.md:73], so the reader and the writer must agree on a shape nobody wrote down. Closing artifact: `contracts/routine-state.schema.json` plus a `routine-state.vitest.ts` row for an absent file and a file written by an older shape.
5. **P1 — Three `--json` verbs use three envelope conventions and no rule picks one.** `bots activity --json` prints `{"groups":[]}` [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/001-activity-and-actor/spec.md:229], `bots chat --json` prints "the messages as a JSON array" [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/010-conversations/spec.md:158], and `bots routines --json` names its row fields but never says whether the payload is an array or an object [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/002-routine-layer/spec.md:178]. A builder of 002 must guess, and 003's fixture then encodes the guess. Closing artifact: `contracts/json-envelope.md` with one rule (object with a named collection key, or array) applied to every verb, and the three payload schemas beside it.
6. **P1 — 002's `until` observation on the run record is named but not shaped.** The Files to Change row says only "Carry the optional `until` observation on the record" [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/002-routine-layer/spec.md:135], while the same phase specifies the `until_check` exit semantics in REQ-004 [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/002-routine-layer/spec.md:161]. The record field list (`met`, `at`, `exitClass`, `command`?) is left to the builder, and `bots routines` reads `untilMetAt` from the state file rather than the record, so the record field has no reader and no shape. Closing artifact: the run-record schema in `contracts/` with the `until` object's fields, or a decision to drop the field because the state file already carries the outcome.
7. **P2 — The needs-you item lifecycle is a derived state with no transition table.** `NeedsYouState` is `open | answered | expired` and is never stored [SOURCE: .skilled/skills/system-skilled-bots/runtime/lib/needs-you.ts:47] [SOURCE: .skilled/skills/system-skilled-bots/runtime/lib/needs-you.ts:90-92]; 001 prints it [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/001-activity-and-actor/spec.md:153], 006 adds the second-answer refusal `item-answered-differently` and the guarded write [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/006-approval-grants/spec.md:170] [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/006-approval-grants/spec.md:171], and 005 adds a review seam that settles an item without a resume [SOURCE: specs/system-skilled-bots/003-openbot-parity-build/005-memory/spec.md:167]. The transition table is split across three phases and no doc states who writes `answeredAt`, when `expired` is computed, or what a second answer does on each kind. Closing artifact: `contracts/item-lifecycle.md` with the transition table and the writer per transition.

## Reflection
- What worked and why: reading the live TypeScript interfaces beside the REQ tables turned "is this specified?" into a diff between the current type and the phase's prose, which is what exposed the answer-nullability gap that a spec-only read would have missed.
- What did not work and why: grepping `tasks.md` for shapes wasted two calls; tasks carry verify commands, not field lists, so they can only confirm a symbol name.
- What I would do differently: read the plan's Architecture section before the spec's Requirements, because the plan names the module and the function while the spec names the field, and the gap usually sits between the two.

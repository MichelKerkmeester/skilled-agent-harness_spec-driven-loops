`parseDescription` (check-repo-rules.cjs:89-97) works correctly against the live corpus: I ran the checker and all 9/9 checks pass, including "index summaries," which is its only consumer. But it has a real edge-case gap in how it reports "missing" versus "empty."

The function returns `null` only when no line in the frontmatter range matches `^description\s*:`. If a maintainer writes a bare `description:` key with no value on that line, the regex still matches, `match[1]` is `""`, and the function returns an empty string, not `null`. I confirmed this directly: feeding it `description:` with nothing after the colon returns `""`.

The only caller, `checkIndexSummaries` (line 381), only special-cases the `null` case to report `"no description in frontmatter"`. An empty-string description skips that branch and falls into the generic mismatch check at line 385, producing the misleading message `"summary differs from its description"` instead of pointing at the actual problem, a missing value. `checkFrontmatterKeys` won't catch it either, since `parseTopLevelKeys` only checks that the `description:` key exists, not that it carries a value.

This doesn't fire today, every current `description:` line in `repo-rules/*.md` is a properly quoted single-line value. It's a latent diagnostic-quality gap: the fix would be treating an empty (post-strip) result the same as `null`, either in `parseDescription` or in the `checkIndexSummaries` guard at line 381.

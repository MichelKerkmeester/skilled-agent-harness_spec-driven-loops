## What Was Built

One registry entry, one bound route, a regenerated manifest, and the prose that lets a human find the member where they find the others.

The axis question the phase opened turned out to answer itself once the registration existed. The worry was that a CLI-backed bridge able to write `.tsx` files into the calling project could not honestly sit on an axis whose members all declare they write nothing. But the mutating family was never registered, so the concern applies to a surface that does not exist here: all fourteen registered tools are read-only, and `mutatesWorkspace:false` is a description of this mode rather than a stretched guarantee. The axis needed no widening and no clarifier.

The backend field did need a new value. The existing three cover a local desktop daemon and remote MCP servers reached through Code Mode; none describes a vendor CLI reached through Code Mode over a UTCP `cli` manual, which is what this is. `code-mode-cli` names it, and the axis description records why the provider forces it: MagicPath ships no MCP server.

## How It Was Delivered

The axis was settled before the entry was written, because writing the entry first and rationalising the axis afterwards is how a registry acquires a statement that is not true.

Routing was then proved by replaying the router's own signal and vocabulary tables over real phrasings rather than by reading the configuration and concluding it looked right. The same replay covered the neighbours, since the failure mode of a registry edit is a broken existing mode rather than a broken new one.
<!-- /ANCHOR:how-delivered -->

<!-- ANCHOR:decisions -->
## Key Decisions

- **Transport axis, no widening.** The registered surface writes nothing, so the axis guarantee holds as written. Had the mutating family been registered, this mode would not have belonged here, and the phase records that as the condition under which the question returns.
- **A new backend value rather than a near-fit.** Calling this `code-mode-remote-mcp` would have been false, since there is no remote MCP server anywhere in the path. `code-mode-cli` is one more value in a field that exists to distinguish exactly this.
- **Regenerate the manifest, never author it.** The manifest is derived from the tree, and the tool that audits it is the tool that writes it, so the two cannot disagree.
- **Update the advisor-facing metadata too.** The description and causal summary are what the advisor reads; leaving them saying "three design transports" would have left the hub describing a fleet it no longer has.

<!-- ANCHOR:limitations -->
## Known Limitations

- **Hub-level routing is proved; advisor-level routing is not, and one attempt to fix it failed.** Replaying the router's own signal and vocabulary tables resolves every MagicPath phrasing to this mode, and that is what the hub reads when it picks a mode. The advisor, which decides whether a request reaches this hub at all, behaves differently: a design-token-flavoured MagicPath request ranked `mcp-tooling` second at 0.22 behind `sk-design-md-generator` at 0.51 and was flagged ambiguous, and a plainer request - naming MagicPath, a component and its source - returned no recommendation at all, abstaining because nothing passed the confidence threshold.
- The obvious cause was ruled out rather than assumed. The index was rebuilt three seconds after the metadata edits and again after a second edit, so staleness is not it. The next hypothesis was that the hub's `derived.trigger_phrases` carried no MagicPath entry while all eight sibling providers had one; that gap was real and is now closed, and it did not change the abstain. Whatever governs the advisor's confidence for this hub is therefore not reachable from the hub metadata this phase owns, and diagnosing it further means opening the advisor's own scoring internals - a different subsystem, and out of this packet's scope.
- The practical consequence is narrow but worth stating: an operator who names the hub or the mode reaches it, and the hub then resolves MagicPath correctly. An operator who describes a MagicPath task cold may get no recommendation. That is a routing-precedence problem belonging to the advisor, not a defect in this mode's registration.
- The vocabulary class keys on the provider's name. A request that describes the need without naming MagicPath falls to the hub's defer path, which is the intended behaviour for a provider-specific transport but means discovery depends on the operator knowing the tool exists.
- The new backend value is declared and documented but has exactly one member, so nothing yet proves the distinction earns its place beyond this mode.
- The hub's catalog and playbook claimed seven modes while eight existed, because `mcp-notion` was added without updating them. Writing a sentence that correctly includes MagicPath forced that correction too, so this phase carries a fix it did not set out to make. Holdout coverage is now stated as 7 of 9 rather than 7 of 7: neither `mcp-notion` nor `mcp-magicpath` has a blind holdout scenario, and adding one for either is outside this packet.
<!-- /ANCHOR:limitations -->

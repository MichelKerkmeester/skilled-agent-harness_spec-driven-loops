## What Was Built

`mcp-notion` is now the 8th mode of the `mcp-tooling` hub (5 workflow modes + 3 transports) and is fully routable. A Notion prompt now reaches the mode through both awareness systems: the skill-advisor surfaces the `mcp-tooling` hub identity, and the in-hub router resolves `mcp-notion` from its `routingClass` metadata. Before this phase, the mode was invisible — the same strong prompt landed `mcp-tooling` in 3rd place at 0.133.

### Router registration (in-hub)

You can now route a Notion query to `mcp-notion` inside the hub. `mode-registry.json` gained the `mcp-notion` mode object (`packetKind: workflow`, `backendKind: code-mode-remote-mcp`, `mutatesWorkspace: true`, the MCP tool surface, 14 Notion aliases, and `routingClass: metadata`). `hub-router.json` gained the tie-break order, a `routerSignals` entry with the classes `notion-aliases` and `notion-data`, and the two matching `vocabularyClasses` keyword blocks. `ROUTER.md` gained the mode-list entry, an INTENT MODEL bullet, a NOTION INTENT_SIGNALS entry, and a NOTION RESOURCE_MAP pointing at `mcp-notion/references/mcp-tools.md` and `api-gap-tools.md`.

### Advisor registration (hub identity)

You can now discover the hub from Notion vocabulary. `description.json` gained the Notion description and 14 Notion keywords. `graph-metadata.json` gained the Notion domains, top-level and derived intent_signals, derived trigger_phrases and key_topics, an `mcp-notion` entity plus key_file and source_doc, and the edges and causal_summary bumped from seven to eight modes.

### Hub docs, manifest, and current-state packages

`SKILL.md` was updated across its description, keywords, §1 mode-table row, packetKind list, mode counts, directory tree, and workflow-packets list. `leaf-manifest.json` was regenerated by the canon checker `--fix` (never hand-edited). Two current-state packages were authored under the mode: `feature-catalog/FEATURE-CATALOG.md` (a 24-tool current-state capability inventory) and `examples/README.md` (Code Mode Notion workflow examples). Both pass `validate_document.py` with 0 issues.

## How It Was Delivered

Both awareness systems were edited from the `mcp-click-up` sibling as the template, then each was re-indexed by its own regenerator: `leaf-manifest.json` via the canon checker `--fix`, and the advisor via `skill_graph_scan` followed by `advisor_rebuild --force`. Verification confirmed the result: a strong Notion prompt ("query a notion database and update a notion page property via the notion mcp") now routes to `mcp-tooling` at score 0.792 / confidence 0.9458 as the unambiguous #1 (up from 0.133 / 3rd), and other phrasings score 0.95 confidence.
<!-- /ANCHOR:how-delivered -->

<!-- ANCHOR:decisions -->
## Key Decisions

| Decision | Why |
|----------|-----|
| Registered across two awareness systems, not one | The advisor (hub identity) and the in-hub router read disjoint files; editing only one leaves the mode either undiscoverable or unroutable |
| Advisor routes the hub, hub resolves the mode via routingClass metadata | Keeps the advisor surface at hub granularity while the mode object carries its own routing class — matches the `mcp-click-up` pattern |
| Regenerated the leaf-manifest with the canon checker `--fix` | Hand-editing the manifest diverges from the generator's contract and fails the byte-for-byte drift invariant |
| `backendKind: code-mode-remote-mcp` with `mutatesWorkspace: true` | Notion runs over the official `@notionhq/notion-mcp-server` through Code Mode and performs write operations on the workspace |

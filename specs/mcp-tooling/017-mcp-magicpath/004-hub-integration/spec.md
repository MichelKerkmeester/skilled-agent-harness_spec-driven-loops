## 2. PROBLEM & PURPOSE

### Problem Statement

A packet nothing routes to is a document, not a capability. The hub resolves a request to a mode by reading its registry, and MagicPath has no entry there.

Writing that entry surfaces a question the earlier phases could defer. The hub's registry declares a transport axis whose members all carry `mutatesWorkspace:false`, and the axis documents that posture explicitly: document mutation lands in the external tool, and no transport edits existing repository files. Two members are declared as performing no local writes at all; a third is export-only, writing to explicit output paths on request.

MagicPath does not fit that shape cleanly if its mutating family is exposed. Its `add` command writes `.tsx` files into the calling project and installs npm packages there. That is not export-on-request to a named path; it is a tool that modifies the working tree it is invoked in. Declaring such a mode as a transport with `mutatesWorkspace:false` would make the registry's own statement false, and the registry is the thing other tooling reads to decide what a mode may do.

The backend field has the same problem in smaller form. Its existing values cover a CLI with an MCP fallback, a desktop application driven over a local daemon, and remote MCP servers reached through Code Mode. A CLI reached through Code Mode is none of those.

### Purpose

Route the mode, and record honestly what kind of thing it is, rather than forcing it into a category whose stated guarantees it would break.

## 3. SCOPE

### In Scope

- The mode registry entry, including a backend value that describes a CLI reached through Code Mode
- The mutation posture, declared to match what the registration actually permits
- Router binding and the regenerated leaf manifest
- Hub readme and router prose

### Out of Scope

- Changing the other modes' declarations. If the axis needs widening, that is stated here and applied to this mode only.
- Editing the leaf manifest by hand. It is generated, and hand-editing it is what its generator exists to prevent.
- The packet's own documents, which phase 003 finished.

<!-- ANCHOR:questions -->
## 7. OPEN QUESTIONS

Both questions this phase opened are answered by the registration it had to describe.

- **Whether MagicPath belongs on the transport axis**: yes, and without stretching it. The concern assumed the mutating family would be exposed; it is not. Only read-only commands are registered, so `mutatesWorkspace:false` is literally true of this mode for the same reason it is true of the remote-MCP transports.
- **Whether the axis needs a clarifier for tools that write into the calling project**: not for this mode, because no such tool is reachable through it. The vendor's file-writing commands exist, but they are absent from the emitted manual, so the boundary is enforced by what was registered rather than by a caveat in prose. If that family is ever registered, the axis question becomes live again and this is where it returns.

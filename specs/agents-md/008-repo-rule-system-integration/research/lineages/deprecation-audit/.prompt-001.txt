1. Reachability. Can any command, router, registry, manifest, alias, symlink or generated artifact still resolve the lane? Search the bare name and every prefixed and suffixed variant, in every file type, not only markdown and json. A search for one spelling proving clean is not evidence the others are.
2. Dangling references. Does any surviving file point at a deleted path, script, fixture, test or document? Links in docs, requires in scripts, paths in config, test targets in shell runners, entries in indexes and catalogs.
3. Broken dependents. Did anything outside the lane consume it as a library? Run or load the suspects rather than reading them; some requires are lazy and a file that imports cleanly can still fail on the path that reaches the dead call.
4. Counts and indexes. Any catalog, index, README or metadata file claiming a count that the tree no longer matches.
5. Over-removal. Was anything deleted that did not belong to the lane? Historical benchmark reports under other skills are the specific risk, since they share a filename prefix with the lane and belong to other packets as run evidence.
6. Generated artifacts. Anything regenerated should be internally consistent and consistent with its source. A regenerated pair produced by two different runs reports as drift and the mismatch is invisible until something reads it.
7. Tests. Does any test still assert the lane exists, or assert a count that changed?

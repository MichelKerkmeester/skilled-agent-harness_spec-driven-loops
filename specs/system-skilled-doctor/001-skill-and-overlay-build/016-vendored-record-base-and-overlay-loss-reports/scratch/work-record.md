## Fix 1: `/doctor:update record-base` in a vendored layout

- Cause, confirmed in code: `scripts/release-update.cjs` `resolveRepo` always returned `git rev-parse --show-toplevel`. At the project root `.skilled` is a symlink, and `safeResolve` refuses a symlinked parent by design, so `record-base --repo . --dry-run --release v4.1.0.0` exited 1 with `path parent is not a real directory: <root>/.skilled`.
- Fix, root choice:
  - `--repo <dir>` whose `.skilled` is a real directory (lstat, not a symlink) is the root.
  - `--repo <dir>` whose `.skilled` is a symlink is followed only when its realpath is a directory named exactly `.skilled`, its parent sits inside the git top level, and `git rev-parse --show-toplevel` from that parent returns the same top level. The root is then that parent. Any other target (outside the work tree, not named `.skilled`, a file, a broken link) falls back to the top level and is refused by the unchanged `safeResolve` guard.
  - A normal checkout resolves exactly as before.
- Fix, git reads from a subfolder: a new `headFilesAt()` lists `<rev>:<show-prefix>` for the project's own HEAD (three call sites: `releaseContext`, `prepareWrites`, `recordBase`); framework release commits are still read at their top level. `releaseRenames` anchors its pathspec with `:(top)`.
- Fix, pin form: `record-base --pin <full-sha>` (40 or 64 lowercase hex; mutually exclusive with `--release`; either violation exits 2) records a unit as `{ commit, tree }` with no `release` key, because a SHA in `release` would break `isReleaseRecord` and `compareVersions`. The commit resolves locally first, otherwise `git fetch --no-tags <remote> <sha>`. `check` reads pinned units through `recordRevision()` (`baseSource: 'recorded'`, `baseRelease: null`). A downgrade guard reports `downgrade` when the target release commit is an ancestor of the pin. `--pin` skips the nearer-release check and returns `verified: false`. The flag is named `--pin`, not `--commit`, because the router contract test bans the word "commit" in `update.md` (it guards next-step wording).
- Docs: `update.md` record-base flag line and one sentence on pins (argument-hint left alone: it is 135 of 140 characters); `assets/doctor-update-record-base.yaml` gains a `pin` user input and passes `(--release <tag> | --pin <sha>)`; `assets/doctor-update-presentation.txt` lists `--pin=<full-sha>`.
- Tests, `scripts/tests/release-update.test.cjs`: 77/77 before, 81/81 after, exit 0. New: vendored record-base from the project root (failed before with the symlink error), the pin form (failed before with `unknown option`, its downgrade assertion failed before with `actual: 'update'`), an out-of-tree or wrongly named symlink is refused, a normal checkout is unchanged. Contract 12/12, compat 30/30, agents-md contract 39/39, before and after.
- Left open: a vendored copy kept as a git submodule has a different top level, so its symlink is refused. Relative `--remote` paths resolve against the git top level. Fetching a pin needs a remote that allows fetch by id (GitHub and local remotes do). A project's own `vN.N.N.N` tags would read as framework tags. align and rollback share the helpers but have no vendored-layout test.

## Fix 2: overlay engine content lost while status stays green

All five claims confirmed in `scripts/overlay-engine.cjs`.
- 2a. `set` on a json-entry replaced a whole array with no report once the hash named the new upstream copy. Fix: `jsonEntryLosses` and `upstreamLosses`, run in `repinUnderLock` before the copy, print `upstream-lost <id>: set at <path> drops <item>, which upstream added to <dest>` (or `overwrites the value upstream changed`). `setKeyOnItem` is covered too. Reported in `report.upstreamLost` and `--stage`; never blocks.
- 2b. A missing `before` anchor silently appended at the end (and `insertObjectKeys` `beforeKey` did the same; a `before` with no `identityKey` was ignored). Chosen: warn, not fail, because no strict flag covers anchors and failing would block an existing project's re-apply. `status` and `repin` print a `NOTE`; apply behavior is unchanged.
- 2c. The numeric-path warning covered `set` only. Fix: it covers every operation kind.
- 2d. A directory overlay deleted upstream-added files silently. Fix: `upstream-lost <id>: the directory overlay removes <path>, which upstream added|changed`. Extended to skill-root `replace` folders through a shared `removedUpstreamChanges`; `remove-root` and skill-root `remove` paths are removed by design and not listed.
- 2e. `setKeyOnItem` and `insertObjectKeys` kept no record (the NOTE said so). Fix: `insertObjectKeys` keys are recorded in `sets`; `setKeyOnItem` in a new `keys` map matched by item identity; `restoreDroppedKeys` takes a dropped key back (restores the pin's value, or deletes a key the overlay added) and refuses on a hand-edited value or no readable pin. The "keeps no record" NOTE is gone.
- Surfacing: `assets/doctor-overlay-repin.yaml` keep and plan lists carry `upstream-lost` and the anchor `NOTE` lines, and the report step tells the operator to carry each into the overlay; `assets/doctor-overlay-presentation.txt` gains `Upstream lost:` and `Notes:` slots and fixed NOTE rows; `assets/doctor-overlay-status.yaml` NOTE text; `.skilled/skills/system-skilled-doctor/references/overlays.md` records, notes table, re-pin section, and the upgrade notes below.
- Tests: overlay suite 195/195 before; 198 overlay-engine tests plus 8 contract tests after (206), exit 0. Fail-before proof: the final test files against a pristine engine copy fail 12 (sync 9, repin 3), plus the skill-root test failed before its fix. Existing tests changed on purpose: the index-note test, the cross-check test (deletes `keys` to simulate an older state file), the untracked-operation test (now "prints no note"), the dropped-set test (expects the `insertObjectKeys` record), and the no-set-records test (empty entry set).
- Visible changes: the first apply after upgrading rewrites `sync-state.json` even at `0 changed`; dropping a `setKeyOnItem` or `insertObjectKeys` now refuses when there is no readable pin or the value was hand-edited; an older engine drops the `keys` records. Any of the vendoring project's operations with a numeric path step now prints the array-index note instead of the record note.
- Left open: failing (not warning) on a missing anchor, for example behind an opt-in flag, is an operator call. The contract test does not check that the YAML keep lists name every line kind the engine prints.

The setting lives outside `.skilled` because a re-copy overwrites that folder, and outside the manifest because the manifest sits inside the folder the setting finds.

`sync-state.json` carries three optional records beside its hashes. `links` maps each layout link path to the target the engine confirmed there, so when the manifest moves a link target the engine retargets its own link instead of refusing a stranger at that path. `items` holds the array items each `json-entry` overlay added, so an item the overlay drops is removed from the live file while it still equals what the engine wrote. An item recorded there but edited since is refused rather than deleted, because the entry set no longer describes what it should be. `sets` holds each `set` a `json-entry` overlay applied: its path, the value written and whether the engine added the key. Two `set` operations on one path share one record, however the path spells an index. When the entry set stops naming that path, `apply` writes back the value the pin holds. A key the pin does not hold is deleted while it still carries the recorded value. A value edited since it was recorded is refused rather than overwritten. Two nested `set` operations dropped together both leave: the outer value returns first, and a value a later `set` wrote inside it counts as part of its record. A `set` the entry set still lists inside a dropped outer one is written again once the outer value returns. A dropped `set` that a kept `set` wrote over, or that another operation kind wrote inside, is refused, because the live value no longer equals the record. Put the `set` back or restore the value by hand. A path through an array is restored only while that array holds the same number of items in the live file and in the pin, the overlay adds no item to it, and the item at each index is the pin's item apart from the values this overlay's `set` operations wrote into it. A step into an array counts as an index however the entry set spells it. Otherwise `apply` refuses and names the outermost array on the path. That refusal clears once that array reads the same as the pin's. To clear it, put the whole array back to the pin's by hand and run `apply`. The operations the entry set still lists then write into it again. A key the pin does not hold is deleted even when a person added it by hand before a `set` named it, because the record cannot tell the two apart. The restore reads the pinned copy the run was given. For `apply` that is the checkout the manifest's pin names, and for a re-pin it is the new commit, whether or not the copy writes the file. Before its backup a re-pin plans each `json-entry` destination its copy leaves in place against the new commit, and when one cannot be applied it refuses with exit 2 and writes nothing. Without a pinned copy the overlay is refused, unless the live file holds exactly the bytes the entry's `pinnedSha256` names, because those bytes are the pinned copy. The refusal says to set `pin.checkout` or to put the file back to those bytes. Three cases stay silent. `setKeyOnItem` and `insertObjectKeys` keep no record, so a value either one wrote stays in the live file after the operation leaves the entry set. A `set` through an array index that stays listed while an `insertItems` on that array leaves moves to the next item, and the value it wrote on the item before stays behind with no record. A link the state has no record of is refused and reported, and an item or a value it has no record of is left in place. A state file from an older engine holds none of these keys, so nothing is retargeted, removed or restored until the first apply records them.

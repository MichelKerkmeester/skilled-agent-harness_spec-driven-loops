019 changed skill routing from loosely comparable prose routers into a measurable fleet surface: typed `(workflowMode, leafResourceId)` identities, per-hub registries and `defaultMode` policy, generated leaf manifests, a frozen scorer/benchmark contract, and a compiled serving engine for seven hubs. The angles below are conformance checks against those named authorities; observed discrepancies are evidence for running the loop, not assumed diagnoses.

Path convention: `019-*` and numbered phase paths are relative to `.opencode/specs/sk-doc/019-skill-routing-refactor/`; bare skill paths are relative to `.opencode/skills/`; `.opencode/bin` paths are repo-relative as written.

## 1. Compiled serving-state truthfulness

- **Angle and lanes:** Verify, for each of the seven compiled hubs, that live policy identity → activation manifest → `compiled-route-status.cjs` → `compiled-route.cjs`/resolver all report the same effective serving state. Lanes are `cli-external-orchestration`, `mcp-tooling`, `sk-code`, `sk-design`, `sk-doc`, `sk-prompt`, and `system-deep-loop`.
- **Authority:** 015/019 makes the status foundation a prerequisite (`015-router-unification-program/019-routing-coverage-activation-verification/spec.md:35`), requires an exact manifest minter/freshness predicate (`:45`), and makes compiled-serving status plus clean fallback a per-hub P4 gate (`:44,51`). The resolver’s identity binding is the serving canon: selected hash and generation must match or it returns legacy (`.opencode/bin/lib/compiled-routing/011-runtime-engine/lib/resolve.cjs:103-118`).
- **Suspected drift / observed smell:** **Confirmed current inconsistency.** `sk-design`’s activation manifest declares `servingAuthority:"compiled"` with selected hash `965e…` (`.opencode/bin/lib/compiled-routing/010-live-activation/activation/sk-design/manifest.json`, keys `selectedPolicy.effectivePolicyHash` and `servingAuthority`). A read-only status run reports `manifestFreshness.fresh:false`, `causeCode:"stale-manifest"`, and current policy hash `41ca…`, yet its top-level result still says `servingAuthority:"compiled"` / `causeCode:"compiled-serving"`. The code explains the split: freshness is computed at `compiled-route-status.cjs:178-180`, but the compiled-serving branch at `:191-210` never gates on it. The actual resolver correctly returns the legacy sentinel because its identity check fails (`resolve.cjs:109-117`).
- **Why it matters:** Operators and downstream health consumers can see a green compiled-serving state while the hot path silently runs legacy. That hides coverage loss and invalidates any assertion that all seven hubs are actually serving compiled decisions.
- **Scope/effort and payoff:** Seven short lanes, two to three iterations: compare identities, probe one canonical prompt, and exercise `=0` for each hub. **Expected payoff: highest**—one confirmed false-green state already exists, and the loop tests both safety and observability.
- **Coverage flag:** 015/019 phases 002 and 012 built this contract. This is a post-cutover recurrence/conformance check, not a proposal to redesign those phases.

## 2. Mandatory design-judgment + transport composition

- **Angle and lanes:** Check that design-bearing Figma, Open Design, Refero, and Mobbin requests resolve to the required design-judgment lane plus transport lane—not a bare transport—through both legacy and compiled entry points. Lanes: `sk-design:{interface|foundations|motion|audit, design-mcp-open-design}` and `mcp-tooling:{mcp-figma,mcp-refero,mcp-mobbin}`.
- **Authority:** The 019 sk-design research defines the conformance matrix: WIRE/inventory may be transport-only, while design-bearing READ and RUN require ordered judgment + transport (`001-research/003-sk-design-routing-research/research/research.md:82-84,144-147`). Current canon agrees: `mcp-tooling/SKILL.md:28-35,130-151` says the three transports are never taste authority, and `mcp-tooling/mode-registry.json:18-29` encodes `crossHubPairing` to `sk-design`.
- **Suspected drift / observed smell:** **Strong hypothesis with live evidence.** `sk-design/hub-router.json` key `routerPolicy.bundleRules` contains only `interface + foundations`; it has no judgment + `design-mcp-open-design` rule, exactly the machine-contract gap already observed by the research (`research.md:84`). `sk-design/mode-registry.json:22-24` describes mandatory pairing but carries no per-transport pairing map. In live read-only probes, compiled `mcp-tooling` routed “Create a polished landing page in Figma,” “Research mobile onboarding patterns in Mobbin and recommend a visual direction,” and a Refero checkout-redesign prompt to a **single transport target**. Whether a higher caller reliably adds `sk-design` is the bounded conformance question; the compiled result itself does not prove the required pair.
- **Why it matters:** A transport-only route can perform mechanics while silently dropping design taste, accessibility, responsiveness, or acceptance authority. That is precisely the boundary both hubs say must never disappear.
- **Scope/effort and payoff:** Four transport lanes plus representative judgment modes; three to five iterations across WIRE, inventory, design-bearing READ, RUN, and explicit bundle cases. **Expected payoff: very high** because the risk spans two hubs and produces plausible-looking but ungoverned design work.
- **Coverage flag:** Already identified in `001-research/003` as the one concrete sk-design machine-contract gap. Run this as the implementation/conformance loop for that finding; do not reopen design exploration.

## 4. Default-on documentation parity

- **Angle and lanes:** Align the seven hubs’ root feature catalogs, compiled-routing feature pages, SKILL directives, activation manifests, and kill-switch wording to the default-on authority.
- **Authority:** The parent states that all seven manifests are compiled and the only fleet-wide fallback is `SPECKIT_COMPILED_ROUTING=0` (`019-skill-routing-refactor/spec.md:71-75`; `timeline.md:253-261`). 015/019 requires catalog wording to change atomically only after per-hub serving/parity/kill-switch gates (`019-routing-coverage-activation-verification/spec.md:39,44,51`).
- **Suspected drift / observed smell:** **Confirmed fleet-wide documentation drift.** Every current hub-root `feature-catalog/feature-catalog.md` still says “The directive is off by default” and “unset in normal operation”: `cli-external-orchestration:55`, `mcp-tooling:53`, `sk-code:53`, `sk-design:83`, `sk-doc:53`, `sk-prompt:53`, and `system-deep-loop:53`. Their feature-specific `compiled-routing-and-legacy-fallback.md` pages say the reverse—for example `sk-prompt/.../compiled-routing-and-legacy-fallback.md:18-32` and `system-deep-loop/...:18-32` correctly state default-on and `=0` kill-switch behavior.
- **Why it matters:** Operators following the root catalog may assume they are testing legacy or that unset disables compiled routing. That can produce wrong rollback, audit, and incident conclusions without any runtime error.
- **Scope/effort and payoff:** Seven documentation lanes, one to two iterations with exact phrase and flag-matrix checks. **Expected payoff: high for very low effort.**
- **Coverage flag:** 015/019 phase 006 and P4 already owned this wording and were treated as complete. This is a regression against that completed authority.

## 7. Typed-gold completeness and comparability

- **Suspected drift / observed smell:** **Confirmed coverage gaps, not yet proof of wrong routes.** A current frontmatter scan found only 1 known workflow-mode file among 33 `sk-code` playbook Markdown files, 0 among 42 `sk-git` files, and 19 among 425 `system-spec-kit` files. ## 8. Advisor confidence/threshold consumer semantics

- **Angle and lanes:** Conform every consumer of advisor `confidence`, `uncertainty`, and `passes_threshold` to the scorer’s named semantics across MCP dispatch, shared brief, Claude hook, CLI fallback, prompt-policy eligibility, and Gate 2 documentation.
- **Authority:** 019 phase 012 states that public confidence is a quantized policy function—not a probability—and freezes the public thresholds while measurement freshness is repaired (`012-skill-advisor-routing-fixes/spec.md:37-53,79-109`). Its named P1-6 authority is a threshold-surface-parity suite across four environment surfaces and two call-override surfaces (`:102,133,158`).
- **Suspected drift / observed smell:** **Known, still-open conformance risk.** Current `AGENTS.md:120-122,448` treats `confidence >= 0.8` as a mandatory-invocation gate. The 019 research found that exact `0.82` is a policy floor, not 82% correctness; its plateau accuracy was roughly 58–65%, and both calibration baselines were stale (`001-research/002-skill-advisor-routing-research/research/research.md:34,49-52,62-71,87`). Current phase tasks T004 and T006 remain unchecked (`012-skill-advisor-routing-fixes/tasks.md:70-72`).
- **Why it matters:** One surface can over-read a categorical floor as probability, another can resolve thresholds differently, and a fallback can silently change whether a skill is mandatory. Every one of the 12 skills depends on this upstream routing decision.
- **Scope/effort and payoff:** Six consumer surfaces, four to six iterations including environment-reset cases and ambiguous prompts. **Expected payoff: high, but the result is already predictable until phase 012 lands.**
- **Coverage flag:** Fully covered by open 019 phase 012 (P0-4/P1-6/P2-8). Best scheduled as its acceptance alignment run, not as a competing remediation.

## 11. Standalone typed-projection shape

- **Angle and lanes:** Determine whether all five standalone skills expose the same canonical typed projection shape to replay, or whether path-plus-alias projection is an authorized equivalent; then conformance-test that decision. Lanes: `mcp-code-mode`, `sk-git`, `system-code-graph`, `system-skill-advisor`, and `system-spec-kit`.
- **Authority:** 015/001 defines the normal-standalone tier as canonical inline router + registry-less manifest config and names all missing surfaces in REQ-003 (`001-3-tier-consistency-standard/spec.md:89-100,122-133`).
- **Suspected drift / observed smell:** **Shape divergence is confirmed; whether it is non-conformant remains a hypothesis.** `system-code-graph/SKILL.md:265-319` and `system-skill-advisor/SKILL.md:232-285` return explicit `workflowMode` and `leafResources`. `mcp-code-mode/SKILL.md:71` and `system-spec-kit/SKILL.md:95` claim fleet-standard typed projection, but their router returns remain flat `resources` objects (`mcp-code-mode/SKILL.md:163-207`; `system-spec-kit/SKILL.md:348-400`) and rely on aliases/replay to recover pairs. `sk-git/SKILL.md:160-201` is flat and has no committed leaf manifest. The alignment loop should first resolve whether alias projection satisfies the canonical shape, then test exactly that—not assume the stricter return schema.
- **Why it matters:** Two legal-looking shapes can make the shared harness treat equivalent standalone routes differently, reproducing the non-comparability 015/001 was created to remove.
- **Scope/effort and payoff:** Five lanes, three to five iterations including replay and mutation. **Expected payoff: medium.**
- **Coverage flag:** This is directly covered by in-progress 015/001 REQ-003/004. Use it as the normal-tier acceptance loop rather than a standalone redesign.

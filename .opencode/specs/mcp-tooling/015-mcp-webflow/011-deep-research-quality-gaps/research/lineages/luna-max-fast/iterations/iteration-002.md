# Iteration 2: CMS draft semantics, page/site publishing, and page branch lifecycle

## Findings
1. **P0 — Missing/unsafe CMS draft encoding.** The local payload example labels a request “CREATE A DRAFT COLLECTION ITEM” but sends only `fieldData`; the CMS pairing scenario likewise calls `create_collection_items` “(draft)” without an explicit draft field. Official Data API schemas expose `isDraft`, `isArchived`, `lastPublished`, and `cmsLocaleId`, while the official MCP guidance says items may be created directly in the live site or as queued/drafted items. The official OSS adapter accepts `isDraft` and defaults an omitted value to `false`, so the packet's example is not a reliable draft contract on the local surface. Add an explicit `isDraft: true` example, state remote/local differences beside the payload, and require a read-back assertion of `isDraft`, `lastPublished`, and locale before treating the write as draft-safe. 2. **P0 — Contradictory CMS publish-target semantics.** The remote action inventory and Data API publish endpoint define `publish_collection_items` with a collection and item IDs, not a domain or staging flag; the local baseline describes it as deploying drafts to live, and the CMS card explicitly says CMS item publish has no staging-domain target. However, the publish/deploy card labels the same action “staging-first” and its prompt says to publish collection drafts to the staging subdomain. That contradiction can make an operator believe an item publish is isolated to `*.webflow.io` when the item endpoint itself has no domain selector. Reconcile the card and prompts: describe item publish as a separate live CMS publish, reserve staging-subdomain language for `publish_site`, and add a confirmation/refusal scenario that prevents domain assumptions. 3. **P1 — Too concise CMS read verification.** The read-only example and READ-001 scenario stop after “collection items returned,” and the draft pairing scenario stops after the create call. They do not require recording whether the returned item is draft or live, whether it is archived, which locale was addressed, or whether `lastPublished` changed. Those fields are part of the official item model, and the publish API also supports locale-specific item publication. Add before/after assertions and a locale-aware readback step to the CMS read and draft scenarios; otherwise a successful read cannot prove which content state the workflow inspected. 4. **P1 — Missing publish completion and staged-blast-radius checks.** The official site-publish contract returns `202 Accepted`, requires either `customDomains` or `publishToWebflowSubdomain`, accepts an optional `pageId`, limits successful publish queues to one per minute, and warns that promoting staging to production publishes all staged changes after multiple page-to-staging publishes. The local feature card records the queue and broad staging rule, but the staging example and SAFE-001 scenario only capture a receipt and staged URL; they do not distinguish accepted from completed, assert `publishScope`, or test the “all staged changes” promotion case. Add a staging single-page scenario plus a separately gated production-promotion scenario with explicit domain choice, page/site scope, receipt fields, and post-publish verification. 5. **P1 — Too concise page-settings publish boundary.** The official repository's pages tool describes page metadata reads as returning draft/published status and page-settings updates as including publishing status. The local packet acknowledges that `update_page_settings` can flip status, but the draft payload/example and DRAFT-001 scenario show no concrete body, status omission rule, or postcondition that the status stayed unchanged. The official changelog also records that slug updates can be silently ignored for home, collection-template, utility, and some secondary-locale pages. Add a status-safe DW payload, a separate explicit PB payload, and read-back checks for status and returned fields; document the slug/page-type/locale caveat so a `200` is not treated as proof that every requested setting applied. 6. **P1 — Missing remote/local page-branch lifecycle contract.** Official MCP documentation describes creating, inspecting, and deleting page branches. The remote action reference exposes `create_branch`, `list_branches`, `get_branch_details`, and `delete_branch`, but the local site-pages card says “page branches (create/update)” even though no `update_branch` action is listed, and the Designer reference says isolation lasts “until the branch merges” without identifying a merge action. The official OSS `dePages.ts` source exposes page creation/folders/current-page/switch-page but no branch lifecycle, so this is also a surface-boundary gap. Add a remote-only branch matrix with parent-page/current-branch readbacks, create/list/details/delete coverage, an explicit “merge is not exposed here” statement, and a deletion confirmation scenario; do not imply an automatic merge. This refines the prior merge concern with new surface-split and manual-coverage evidence. 7. **P2 — Missing item-publish/unpublish payload and manual coverage.** The remote action inventory includes both `publish_collection_items` and `unpublish_collection_items`, and the official publish schema supports bulk primary-locale IDs and locale-specific `cmsLocaleIds` with a response containing published IDs and errors. The packet has a CMS card row for publish/unpublish but its payload asset contains only draft creation and site publishing, while the manual playbook covers CMS reads and site publishing rather than item publish/unpublish. Add primary- and secondary-locale payload shapes, confirmation expectations, partial-error handling, and a deterministic publish-then-unpublish scenario.

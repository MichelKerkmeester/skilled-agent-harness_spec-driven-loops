## Findings
1. **P1 — Webhook lifecycle is reduced to CRUD and omits delivery, authentication, and versioned trigger semantics.** The local remote action table exposes only `create_webhook`, `list_webhooks`, `get_webhook`, and `delete_webhook`, with `create_webhook` reduced to `site_id`, `trigger_type`, and `url`; the feature card calls this “integration config” but no payload asset or manual scenario covers delivery. The available worked examples cover discovery, CMS/page reads, generic destructive refusal, staging publish, and draft page settings, not webhook delivery. Official Data API guidance adds the optional form filter, the current trigger set, signed delivery headers (`x-webflow-timestamp` and `x-webflow-signature`), HMAC-key provenance, a required HTTP 200 response, up to three retries at ten-minute intervals, deactivation after repeated failures, and a limit of 75 registrations per trigger type. The current OSS source additionally accepts `filter` and enumerates `user_account_*` triggers that are absent from the current Data API create/get enum, so the packet needs an explicit remote/local/version qualification rather than an unconstrained string. Add a webhook payload, create→get/list→delivery-verification→delete scenario, signature/replay and retry/deactivation notes, the endpoint-specific Data Client App/`sites:write` requirement, and a discovery-time trigger matrix. 2. **P0 — Enterprise robots replacement/deletion lacks a high-impact safety boundary.** The local action table classifies `replace_robots_txt` as an ungated DW action and `delete_robots_txt` as DS, but gives both only `site_id`; the generic DW matrix therefore does not require confirmation before a whole robots policy can be replaced. 3. **P1 — Redirect and activity-log workflows are too concise for audit-safe use and omit partial-result behavior.** The local action reference lists redirects and `list_site_activity_logs` with only site-level required parameters, while the feature card supplies no redirect pagination, activity `limit`/`offset`, event/source/actor fields, or scenario. Official Data API responses return redirect IDs and pagination; activity logs accept `limit`/`offset` (maximum 100) and expose event, resource operation, source (`WEBFLOW_MCP`, `WEBFLOW_AI`, `DESIGNER`, or `SYSTEM`), actor type, and attribution fields. Add redirect list/create/update/delete payloads, paginated activity-log readback, attribution assertions, Enterprise scope/plan failures, and a mixed-site partial-result scenario to `content/site-pages-scripts.md`, `assets/payload-examples.md`, and the playbook. 4. **P1 — Agent Instructions omit provenance and read-resolution semantics despite being governance inputs.** The local card covers the six action names, path grammar, cascade-on-delete, and same-parent move rule, but its payload only demonstrates creating a rule and `DRAFT-002` only exercises create plus a hypothetical delete. Official MCP documentation says site instructions are automatically supplied to connected agents, references resolve server-side against current site primitives, Shared Libraries can distribute them across a workspace, `search_instructions` returns metadata/resource URIs, and `read_instruction` inlines references by default. Without those semantics, an operator cannot tell whether an instruction is merely stored, which referenced version an agent received, or what a cascading skill move/delete affects. Expand `intelligence/agent-instructions.md`, `assets/payload-examples.md`, and `manual-testing-playbook/draft-write/instructions.md` with rule/skill path examples, search/read resolution and provenance checks, partial update behavior, same-parent move checks, and a gated cascade readback. 5. **P1 — Utility and AI tools have no complete operating contract or guide-first scenario.** The remote action reference lists `ask_webflow_ai`, `get_guidelines`, and `get_more_tools`, but the site/pages card only mentions `ask_webflow_ai` and `webflow_guide_tool`; the local OSS baseline has `aiChat` and `rules` but no `get_more_tools` or `get_asset_preview`, and the 17-scenario index has no utility/AI scenario. 6. **P1 — WHTML is a one-row remote action with no syntax, batching, payload, or verification contract.** The local action reference records only `build_label`, `parent_element_id`, `creation_position`, and `html`; the feature card says merely “builds page structure,” contains the `WHMTL` typo in its metadata/description, and provides only a prompt. There is no WHTML payload in `payload-examples.md`, no WHTML manual scenario, and the five worked examples contain no WHTML build/readback flow. The local baseline correctly identifies WHTML as remote-only without explaining what that means for an authenticated stdio session. 7. **P1 — The error contract stops at auth and 429 and does not describe structured errors or preserved partial results.** Local troubleshooting documents 401/403 causes and 429 backoff, while `mcp-wiring.md` documents rate headers but not the common 400/404/409/500 response contract; the combined-action pattern also has no packet-level rule for retaining successful results when a later action fails. Official Data API error handling defines `code`, `message`, `externalReference`, and `details`, and distinguishes `bad_request`, `not_authorized`, `forbidden`, `resource_not_found`, `conflict`, `too_many_requests`, and `internal_error`. The official Enterprise implementation demonstrates per-action catches and an `isError` result while preserving other action results. Add a cross-cutting error matrix and evidence format to `mcp-wiring.md`/`troubleshooting.md`, including no-retry rules for ambiguous non-idempotent writes, and add a manual scenario for one successful action followed by a plan/validation/404 failure. 8. **P2 — Rate-limit guidance is generic and SAFE-003 is not a reproducible endpoint-aware test.** The local wiring/troubleshooting contract covers plan rates, `X-RateLimit-*`, `Retry-After`, and the one-publish-per-minute queue, but it does not state that quotas are per API key or enumerate endpoint-specific limits. The manual scenario asks operators to hammer a real read until a 429 and then “retry once,” while the read example only says to honor `Retry-After`; neither distinguishes SDK exponential backoff from agent policy or records endpoint-specific limits. Add a general-versus-endpoint rate matrix, quota-key and header capture, explicit idempotency/retry rules, and a controlled/fixture-backed alternative to an unbounded real-server exhaustion test.

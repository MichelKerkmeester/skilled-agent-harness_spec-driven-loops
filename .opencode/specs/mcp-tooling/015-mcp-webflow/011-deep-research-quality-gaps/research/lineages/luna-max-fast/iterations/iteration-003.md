## Findings
1. **P0 — Custom-code release and gate semantics conflict across the packet’s remote/local documentation.** The remote action reference classifies registration, application, freeform-code, and script-set actions as draft writes, while `mcp-wiring.md` groups “script registration” with deploy actions that require confirmation; the operations card also says scripts “ship with publish.” The local OSS baseline exposes only a smaller seven-action scripts module. Official OSS code shows that inline-site-script handling registers a script and then applies it, that inline scripts are limited to 2,000 characters, and that page upsert replaces all existing page scripts. The packet therefore lacks one surface-specific contract for whether registration/application is draft-write, publish-adjacent, or deploy-gated. This is a P0 boundary gap because an agent could select a weaker gate or report custom code as live without a clear release rule. Reconcile `references/mcp-wiring.md`, `references/tool-surface.md`, `feature-catalog/operations/sitemap-scripts-assets-whtml.md`, and `feature-catalog/content/site-pages-scripts.md`; add a remote-vs-OSS matrix, replacement/length semantics, and a confirmation plus read-back scenario for custom-code changes. 2. **P1 — Forms and submissions are listed without a schema, scope, mutation, or evidence contract.** The remote action table has seven distinct form actions, including form-schema reads, per-form and site-wide submission reads, submission update, and destructive deletion; the local feature card only summarizes “related reads” and deletion. None of the 17 manual scenarios is a form scenario, and the payload asset contains no form or submission shape. Official Data API evidence shows that form reads include field definitions, response settings, page/form identifiers, and pagination; submission reads require both `site_id` and `form_id` and return submission date, arbitrary `formResponse`, `localeId`, and pagination. Add an exact action table and payload example to `feature-catalog/content/localization-fonts-forms.md` and `assets/payload-examples.md`, plus a manual scenario covering per-form versus site scope, pagination, locale, update read-back, redacted response evidence, and confirmation before deletion. 3. **P1 — The localization card advertises locale management and deletion that the exposed action surface does not provide.** The card calls the capability “localization (locales + secondary-locale content),” lists generic localization deletes as destructive, and gives “list the locales” and “add a Spanish locale” examples. The remote action reference instead exposes only content/component reads and updates plus static-content updates, all with an explicit `localeId`; it has no locale-create, locale-list, or localization-delete action. Official MCP limitations also state that new localized CMS items cannot be created and that existing CMS/static content is read or updated in secondary locales. The official repository’s tool directory and local OSS baseline do not expose a localization module. Rewrite the card as secondary-locale content support, remove unsupported locale-management/delete examples, label remote-only actions, and add a locale-aware read/update/read-back scenario. 4. **P1 — Broader page/site metadata coverage omits the schema-markup and structured-data action family.** Official MCP documentation says page management includes schema markup and structured data in addition to SEO metadata and Open Graph tags. The remote action reference exposes `bulk_update_pages_schema_markup` and `query_pages_schema_markup`, but the local site/pages card only names page listing, metadata reads, and SEO/OG/slug/title settings. Add the missing schema/query actions, request fields, site/page/locale applicability, bulk-selection gate, and read-back assertions to `feature-catalog/content/site-pages-scripts.md`, the shared references, and a dedicated manual scenario. This finding is limited to schema/structured-data and metadata coverage; it does not repeat iteration 2’s page status/slug boundary. The official repository page tool exposes a distinct metadata read with optional `localeId`, and the remote action reference names `get_page_metadata` separately from content reads. 6. **P1 — Asset and image-compression coverage lacks the task lifecycle, payload, read-back, and remote/local boundary.** Official MCP documentation promises asset/folder list, organization, update, deletion, and compression jobs. The remote action reference provides `compress_assets(site_id, asset_ids[], format)`, task list/get actions, upload-by-URL, preview, folder operations, and asset metadata operations; the local operations card reduces this to “upload/update assets” and “compression requests.” The payload asset has no asset example and the 17-scenario playbook has no asset/compression scenario. Official Data API asset responses include `localeId` and `folderId` filtering plus size, alt text, responsive variants, quality, and variant errors. The official OSS `deAsset.ts` source only covers Designer folders/assets/update and image preview, while the local baseline has no data-assets/compression module. Add a remote-vs-OSS matrix, asset/compression payloads, task polling and variant read-back, and an isolated deletion/compression scenario that distinguishes `data_assets_tool` from Designer `asset_tool`.

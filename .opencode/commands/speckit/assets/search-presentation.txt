# SpecKit Search Presentation Contract

Single source of truth for `/speckit:search` startup questions and result displays.

Register (COSTAR): these contracts are written objective-first for an automated-pipeline audience — fixed response shapes, no preamble, no conversational framing inside the rendered block. This is the wording style of the contract itself, not a prompt framework imposed on callers.

## Template Index

Start with the matching render contract before drafting any response:

- Trigger-index results: Section 2, `SPECKIT:SEARCH TRIGGERS "<query>" ... STATUS=OK CANDIDATES=<count>`.
- Free-text evidence results: Section 3, `SPECKIT:SEARCH "<query>" ... STATUS=OK RESULTS=<count>`.
- No-hit results: Section 4, the clean empty result.
- Unsupported requests: Section 6.
- Errors: Section 7.

## 1. Startup Question Policy

This section applies ONLY when the command's `ARGUMENT RESOLUTION` header reported `ARGS_PRESENT=false`. If `ARGS_PRESENT=true`, skip this section entirely and render the result for the resolved `QUERY` — never ask the startup question over a populated query.

When `ARGS_PRESENT=false` (bare invocation), ask one open-ended question:

```text
What phrase should I look for?
```

Accept any natural-language answer as the query. Do not dump a menu at startup.

Ask a targeted follow-up only when genuinely ambiguous:

| Ambiguity | Targeted question |
| --- | --- |
| The query is a single generic workflow word (`session`, `context`, `memory`, `summary`) | `That phrase is too generic to be distinctive. What specific term, decision, symbol or failure symptom should I look for?` |
| The user names a packet but no phrase | `Which phrase should I look for inside that packet?` |
| The user asks for lineage, drift, ablations or dashboards | Render the unsupported notice in Section 6. |

## 2. Trigger-Index Result Display

The keyed lane. Renders the output of `lookup-trigger-index.mjs` — a match against author-declared `trigger_phrases`, not a scan of prose.

```text
SPECKIT:SEARCH TRIGGERS "<query>"
--------------------------------------------------
index     <indexHash short>   manifest <manifestHash short>
scope     <specFolder or (unscoped)>
<score>  <matchClass>  <path>
<score>  <matchClass>  <path>

STATUS=OK CANDIDATES=<count> LANE=trigger-index
```

Field mapping:

| Source field | Template slot |
| --- | --- |
| The resolved `QUERY` | `"<query>"` |
| `indexHash`, `manifestHash` | `index` / `manifest`, first 12 characters each |
| `specFolder` | `scope`, or `(unscoped)` |
| `result.score` | `<score>` — the lookup's own score, three decimals, exactly as the tool emits it |
| `result.matchClass` | `<matchClass>` — `exact`, `query-containment`, `partial`, verbatim from the tool |
| `result.path` | `<path>` — the repo-relative document path |
| `results.length` | `CANDIDATES=<count>` |

Rules:
- Render candidates in the order the tool returned them. The lookup is deterministic; do not re-sort.
- Never rename `score` to `confidence`, `similarity` or `relevance`, and never render it as a percentage. It is the tool's own score, not a probability.
- `matchClass` is a label, not a rank. Do not translate it into a quality adjective.

## 3. Free-Text Evidence Display

The scan lane. Renders parsed ripgrep output, addressed by path and one-based line.

```text
SPECKIT:SEARCH "<query>"
--------------------------------------------------
recipe    <section id from retrieval-conventions.md>
roots     <positional search roots>
<path>:<line>  <field>  <matchClass>
<path>:<line>  <field>  <matchClass>

STATUS=OK RESULTS=<count> LANE=ripgrep
```

Filled example:

```text
SPECKIT:SEARCH "trigger index generator"
--------------------------------------------------
recipe    2.2 path-only
roots     specs/system-speckit/049-memory-decommission
specs/system-speckit/049-memory-decommission/001-trigger-index-replacement/spec.md:14  trigger_phrases  exact
specs/system-speckit/049-memory-decommission/001-trigger-index-replacement/tasks.md:34  body  containment

STATUS=OK RESULTS=2 LANE=ripgrep
```

Field mapping:

| Source | Template slot |
| --- | --- |
| The resolved `QUERY` | `"<query>"` |
| The recipe actually run | `recipe` — its section number and name from `retrieval-conventions.md` Section 2 |
| The positional search roots | `roots` |
| Parsed match path and one-based line | `<path>:<line>` |
| Evidence field per the ranking tuple | `<field>` — `trigger_phrases`, `title`, `description`, `anchor`, or `body` |
| Normalized match class per the ranking tuple | `<matchClass>` — `exact`, `containment`, or `token-coverage` |

Rules:
- Ripgrep produces matches, never a relevance ranking. Order rows with the Section 5 ranking tuple from `retrieval-conventions.md`: evidence field, then match class, then path and line. Never imply the tool ranked anything.
- Do not invent a numeric score for this lane. There is none. A row carries a field, a class, a path and a line, and that is the whole record.
- Label a line inside an `<!-- ANCHOR:id -->` block as `anchor`, established by searching for the marker itself.
- Report an unmatched or orphan anchor marker as a diagnostic line, never by silently dropping it.
- One output mode per invocation. Never combine `--json` with the path-only or count modes; the last flag wins silently and a JSONL parser reads count output as empty.

## 4. No-Hit Display

Ripgrep exit `1` and a lookup with zero candidates are the same thing: a correct empty answer. Render it plainly and stop.

```text
SPECKIT:SEARCH "<query>"
--------------------------------------------------
No match. The phrase does not appear in the searched roots.

roots     <positional search roots>
recipe    <section id>

STATUS=OK RESULTS=0 LANE=<trigger-index|ripgrep>
```

Rules:
- A no-hit is `STATUS=OK`, never `STATUS=FAIL`. Exit `1` means the command worked and found nothing.
- Never soften a no-hit into a paraphrase, a nearest neighbour or a guess. Retrieval here is lexical: if the phrase is not present, the honest answer is that it is not present.
- Offer at most one narrower or broader phrase as a follow-up, and only when the query was plainly too generic.

## 5. Forbidden Vocabulary

Never emit legacy labels that combine trigger wording with the generic noun `memory` or `memories`.

Required labels:
- Trigger-lane rows: `Trigger-matched spec-doc records` or `Trigger-matched spec-doc record`.
- Generic result-class label: `Spec-doc record`.

Also banned, because the mechanism no longer exists: `semantic match`, `similarity`, `confidence`, `relevance score`, `fused`, `reranked`, `recalled`, `decayed`, and any phrasing that implies the result set was ranked by meaning rather than matched by text.

Pre-render gate: scan the candidate output case-insensitively for these labels, then rewrite them before emitting.

## 6. Unsupported Capability Display

These capabilities lived in the retired continuity database. None has a replacement, and no recipe approximates one. Say so and stop.

```text
SPECKIT:SEARCH
--------------------------------------------------
UNSUPPORTED  <capability>
Why          <one line: what the retired mechanism did that text matching cannot>
Instead      <the nearest honest alternative, or "none">

STATUS=OK ACTION=unsupported
```

| Requested capability | What to say |
| --- | --- |
| Semantic or paraphrase search | Retrieval is lexical. A phrase that is not written in the corpus is not found. Rephrase with the exact wording. |
| Vector and BM25 fusion, reranking, decay, access tracking, session dedup | Removed with the database. There is no ranking channel to blend, no usage history and no dedup state. |
| Causal graph, lineage, drift analysis (`causal`, `link`, `unlink`, `causal-stats`) | Grep cannot traverse or statefully update graph edges. Read the packet's `decision-record.md` and its explicit Markdown cross-links instead. |
| Epistemic baselines (`preflight`, `postflight`, `history`) | Removed with the database. The packet's own `tasks.md` and `implementation-summary.md` are the record. |
| Channel ablations and eval dashboards (`ablation`, `dashboard`) | Removed with the database. There are no stored eval snapshots and no channels to ablate. |

## 7. Error Display

Reserved for a genuine execution failure: ripgrep exit `2` or higher, or a lookup exit `2`. Never used for a no-hit.

```text
SPECKIT:SEARCH
--------------------------------------------------
FAIL        <short reason>
stderr      <the tool's stderr, verbatim>
Recovery    <next safe action>

STATUS=FAIL ERROR="<message>"
```

Rules:
- Always attach stderr. Exit `1` and exit `2` both produce empty stdout, so stdout alone cannot tell a clean miss from a broken invocation — the exit status is the only discriminator, and hiding stderr destroys the evidence.
- A missing or unreadable trigger index is an error, not a no-hit. Say the index is absent and name `/doctor speckit-retrieval` as the diagnostic.

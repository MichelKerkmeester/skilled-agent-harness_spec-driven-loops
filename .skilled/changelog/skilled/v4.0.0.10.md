# v4.0.0.10, Adapt sk-code to Your Stack, Keep Untrusted Clones Out

The git hooks are safer. Every commit carries a Commit-Id.

- The hooks do not trust some cloned repositories. Those clones can no longer run their own code through the hooks.
- Untrusted helpers now resolve under `/dev/null`. No repository can fill that path.
- A repository that uses ids refuses a commit. It also refuses a push without one.
- Every commit in such a repository now carries a Commit-Id.

The code skill adapts to your own stack. OpenCode stays native.

- Webflow and Obsidian are examples you can remove.
- A surface you add can land ahead of OpenCode.
- A new guide starts at a fresh clone. It ends at a working setup.
- One command checks the setup. It prints the fix for each failure.

Pi now starts its GPT targets in Fast Mode.

- The Fast Mode extension is on by default. It is on in new worktrees too.
- It still changes only the provider and model pairs. They are in its configuration.

&nbsp;

## Why This Release

The git hooks are installed once. They cover every repository on a machine. In a repository they did not trust, they still read their helpers. The helpers came from that repository's own tree.

- Commit-Id stamping also stopped quietly in those repositories.
- Adapting the code skill was not a supported path either.
- The README told you to replace all three code surfaces. That included the native one.
- Removing an example broke the checks.
- A surface you added lost every keyword tie to OpenCode.

## Hook Safety and Commit-Id

The git hooks changed how they treat an untrusted repository. Commit stamping gained a safe fallback and a refusal rule.

#### Untrusted Clones Cannot Run Code Through the Hooks <a id="c-untrusted-clones-cannot-run-code-through-the-hooks"></a>

- The git hooks are installed once. They cover every repository on a machine.
- For a repository they do not trust, they used to read their helpers from a `.skilled-untrusted` folder. It sat inside that same repository.
- So a clone could plant a guard library or a Commit-Id allocator there.
- That code would run on your next commit, pull or push.
- An untrusted repository's helpers now resolve under `/dev/null`, which no repository can fill.
- So the hooks read nothing from its tree.
- The hooks still trust their own checkout and its worktrees.
- They also trust any repository whose local config sets `skilled.trustRepoHooks=true`.
- Trust covers the repository, not a branch.
- So review an untrusted branch in a separate clone.

#### Every Commit Carries a Commit-Id <a id="c-every-commit-carries-a-commit-id"></a>

- The commit hooks used to mint a Commit-Id only through the repository's own allocator.
- The hook trust gate hides that allocator in an untrusted clone.
- So commits there went out with no id. Nothing said so.
- `prepare-commit-msg` now falls back to the allocator shipped beside the hooks.
- It does that without running code from the repository.
- It stamps a continued revert and a squash commit too.
- In a repository that uses ids, `commit-msg` refuses a message without one.
- `pre-push` refuses any added non-merge commit without one.
- A repository uses ids when it ships the sk-git allocator. It also uses ids when it ships spec-kit.
- It also uses ids when its last 50 commits carry one.
- `git config --local skilled.commitId true` or `false` decides before either test.
- Both checks refuse `0000000`, an id the allocator never mints.

## Adapting the Code Skill

The code skill now works with your own stack. OpenCode stays as the native surface, and the shipped examples are yours to remove.

#### OpenCode Is Native and the Examples Are Optional <a id="c-opencode-is-native-and-the-examples-are-optional"></a>

- OpenCode (`sk-code-skilled`) is the native code surface and stays.
- Webflow (`sk-code-webflow`) and Obsidian (`sk-code-obsidian`) are optional examples you can remove.
- The README, the hub `SKILL.md` and the hub README now say so.
- None of them tells you to replace OpenCode.
- The README block "What Adapting `sk-code` Looks Like" covers the hooks to install and the folders to keep.
- It covers removing an example and adding a surface.
- It also covers the checks that prove each step.

#### The Guide Starts From a Fresh Clone <a id="c-the-guide-starts-from-a-fresh-clone"></a>

- The block's "Before you start" step opens with `bash .skilled/skills/sk-git/scripts/worktree-naming.sh provision .` for a fresh clone.
- It opens with `git config --local skilled.trustRepoHooks true` for a clone that should run the hooks.
- The removal steps name the two feature-catalog files.
- They regenerate `graph-metadata.json` with `regenerate-skill-derived.cjs`.
- The add steps name `leaf-scopes.json` and the surface-count lines the documentation claim checker reads.

#### A New Surface Lands Ahead of OpenCode <a id="c-a-new-surface-lands-ahead-of-opencode"></a>

- `/create:skill-parent update --surfaces` writes a new surface into `routerPolicy.tieBreak`.
- It goes after the workflow modes. It goes ahead of the existing surfaces.
- Several go in the order you give them.
- So it wins a keyword tie against OpenCode.
- Its report names the two steps it cannot run for you.
- They are a canary case with its fixture copy. The other is a commit with the hooks installed.
- If you edit `hub-router.json` by hand and list your own surface after `sk-code-skilled`, the parent-skill doctor fails.
- It says to move it ahead.

#### Removing an Example Keeps the Checks Working <a id="c-removing-an-example-keeps-the-checks-working"></a>

- The sk-code drift guards read only the surface packets on disk.
- They skip archived route gold for a mode. The hub no longer declares that mode.
- The documentation claim checker takes the surface count from `mode-registry.json`.
- So "two surfaces" passes on a hub with two.
- Removing an example no longer makes a guard throw.

#### Failures Name Their Fix <a id="c-failures-name-their-fix"></a>

- When a surface folder is missing, the doctor names a README block. That block finishes the removal.
- When a hub's routing inputs change without a re-mint, the compiled-route guard used to print only `Re-mint: <hub>`.
- It now names the `compiled-route-manifest.cjs` refresh command. It also names both manifest paths and the copy that clears it.
- A missing authored compiled-routing folder under `specs/` stops sync. It stops the guard too.
- Both name the folder to restore.
- Before, they passed or printed a stack trace.
- None of them gives a bare message or a stack trace.

<details>
<summary><b>Smaller fixes</b></summary>

- In a fresh clone `ci-skill-root-metadata.cjs` printed a raw Node stack.
- It now prints one line naming the provision command.

</details>

#### One Command Checks the Setup <a id="c-one-command-checks-the-setup"></a>

- `/doctor:sk-code setup` runs eight read-only checks from the repository root.
- They are provisioning, the parent-skill doctor and root metadata. They also cover the compiled-route guard, sync, the drift guards, derived freshness and a route probe.
- Each prints PASS, SKIP or FAIL. Each gives a `repair:` line naming the command that clears it.
- The run ends `STATUS=OK legs=8` or `STATUS=FAIL failed=<n> skipped=<n>`.
- The probe passes only on a real compiled route.
- It names `SPECKIT_COMPILED_ROUTING` when that variable has switched compiled routing off.
- On a checkout older than v4, the run reports the missing layout. It reports it once.
- It skips the other seven checks.
- The run writes nothing.
- `--prompt=<text>` sets the probe's prompt.
- The probe line it prints quotes the prompt.
- So pasting the line reruns the same prompt.

## Pi

Pi now starts its GPT targets in Fast Mode.

#### Pi Starts GPT Targets in Fast Mode <a id="c-pi-starts-gpt-targets-in-fast-mode"></a>

- The Pi Fast Mode extension is now on by default. It is on in new worktrees too.
- It still changes only the provider and model pairs in its configuration.
- A saved state and the `--fast` flag still decide over the default. So does the value a parent hands to its subagents.
- So `/fast off` stays off after a restart.

&nbsp;

## Upgrade Notes

These steps cover the hooks and Commit-Id checks. They also cover the setup command and Pi.

#### Before You Start <a id="c-before-you-start"></a>

1. Update every machine that has the hooks installed.
2. A machine on an older copy still lets a cloned repository run its own code. It runs that code through the hooks.
3. Pull this release in the checkout the hooks link to.
4. Some repositories of your own should run the full checks. For those, run `git config --local skilled.trustRepoHooks true`.

<details>
<summary><b>Hook Safety and Commit-Id</b></summary>

- Expect a Commit-Id check at commit and push.
- A repository that uses ids refuses a commit without a `Commit-Id` trailer.
- Install the hooks so `prepare-commit-msg` stamps one.
- Or run `git config --local skilled.commitId false` in a repository that should not use them.

</details>

<details>
<summary><b>Adapting the Code Skill</b></summary>

- Run `/doctor:sk-code setup` after you adapt sk-code.
- It names the command that clears each failing check.

</details>

<details>
<summary><b>Pi</b></summary>

- Turn off Pi Fast Mode with `/fast off`.
- Run it once.
- The saved state outlasts a restart.

</details>

# v4.0.0.5, Spec Repairs Write Only What Evidence Proves

v4.0.0.5 makes each spec-folder repair show its work.

- A repair the packet's own evidence cannot support is refused.
- The refusal is recorded.
- The upgrade no longer writes a trigger phrase the checker later rejects.
- An upgrade you regret can be undone.

The update path is safer to start.

- The doctor shows what an upgrade would find before anything moves.
- An upgrade stops while a release apply holds its lock.

Validation and the commit checks catch more problems inside a packet.

- A pull request no longer fails on problems it inherited from its base.
- Nested anchors now fail validation.

&nbsp;

## Why This Release

Spec-folder repairs used to guess. The update path had gaps of its own. The checks around the packet lifecycle missed cases too.

- A template header could be stamped on a document. The document did not match its level.
- A fill could take a description from a frontmatter line instead of the body.
- An upgrade could write a trigger phrase the checker later rejected.
- An apply on uncommitted files could not be undone.
- The doctor did not show a v3 layout before a compat run moved it.
- A resumed run could treat an owed step as a planned move.
- An upgrade could start while a release apply was still running.
- Nested anchors passed validation.
- A new phase packet failed its own checks the moment it was created.
- The pull request gate could not tell a new failure from one the branch inherited.

## Spec Upgrades

v4.0.0.5 makes each spec-folder repair show its work.

#### Upgrades Change Only What Evidence Proves <a id="c-upgrades-change-only-what-evidence-proves"></a>

- `heal-spec-docs --lane-modes` runs five repairs.
- They are anchor wrapping, link repointing, continuity placeholders, filling the level from `spec.md` and header stamping.
- Each repair reads the text the one before it left.
- Each one refuses when the packet cannot prove the fix.
- The command is a dry run by default.
- `--apply` writes.
- `upgrade-legacy --apply` runs the same repairs after its healer.
- It records every refusal in the packet's `upgrade-baseline.json` under `refusals`.
- A template header is stamped only when a document's anchors match its level's template exactly.
- Nothing may be extra or missing.

#### Fills Come From Each Document's Template <a id="c-fills-come-from-each-documents-template"></a>

- A fill may need a missing `importance_tier` or `contextType`.
- It takes the value from the template for that document's class.
- A value the document already carries is never rewritten.
- The runtime tables are reached only when no template can be read.

#### Frontmatter Fill Ignores the Frontmatter Block <a id="c-frontmatter-fill-ignores-the-frontmatter-block"></a>

- A document may have frontmatter but no `description`.
- The fill now takes the description from the body.
- It reads after every leading frontmatter block.
- It used to take the block's first line.
- So a document could end up with `description: 'title: "..."'`.

#### Upgrades Write Only Admitted Phrases <a id="c-upgrades-write-only-admitted-phrases"></a>

- The upgrade no longer writes a trigger phrase.
- The phrase checker grades such a phrase as a negative class.
- `trigger_phrases` may be present but empty in `plan.md`, `tasks.md` or `implementation-summary.md`.
- The upgrade then refills it.
- The phrases are derived from the packet folder name.
- An inferred phrase is kept only when the checker admits it.

#### Phrase Cleanup Trims Only Generated Phrases <a id="c-phrase-cleanup-trims-only-generated-phrases"></a>

- The phrase cleanup trims a trigger phrase only when it is a verbatim eight-word cut.
- The cut must match one of the packet's own recorded descriptions.
- An authored phrase with the same shape keeps all its words.

#### Failures Print Grouped by Rule <a id="c-failures-print-grouped-by-rule"></a>

- `upgrade-legacy` prints each packet's failures under one heading per rule.
- The number of details sits under it.
- This happens on every dry run and every apply.
- A packet whose report cannot be read gets its own heading.

## Undoing and Previewing Upgrades

An upgrade you regret can be undone.

#### Upgrades Can Be Undone <a id="c-upgrades-can-be-undone"></a>

- `upgrade-legacy --apply` refuses to run in a repository without git.
- On a tree with uncommitted changes, it first writes a manifest of before-images.
- The manifest covers the dirty files inside the failing packets.
- It goes into the git directory before it changes anything.
- A manifest from an earlier run is trusted only while the commit still matches it.
- The packet contents must match too.
- So a stale manifest stops the apply instead of being overwritten.
- The dry run lists each finding a baseline will downgrade.
- An apply may pass every packet.
- A second apply on the same tree then prints `plan changes=0`.
- It exits 0 and leaves the tree as it was.
- The `spec/` README explains how to restore from the manifest.
- Each before-image now goes to its own file under `upgrade-legacy.before-images/` in the git directory.
- The file is named by the sha256 digest of the saved bytes.
- So the manifest holds only paths and digests.
- The inline form it replaced could grow into one string.
- That string was too long for the engine to write (`Invalid string length`).
- That refused the apply on a large tree.
- A later apply removes sidecar files the new manifest does not reference.
- A manifest written by an older run still restores from its inline content.
- The README's restore script reads and checks every sidecar before it writes anything.
- So one unreadable or altered sidecar leaves the tree untouched.
- It also refuses a sidecar name that leaves the manifest directory.
- It refuses a sidecar directory that is a symbolic link.

#### Upgrades Survive a Real Repository <a id="c-upgrades-survive-a-real-repository"></a>

- `upgrade-legacy` keeps each symbolic link as written.
- It does this when it copies a packet.
- That copy may be for a preview or an apply.
- Before, a link that pointed at its own folder made the copy recurse.
- The path then passed the filesystem limit.
- The preview failed with `ENAMETOOLONG`.
- The healer still reports a link that leaves the packet as not followed.
- The README's restore script brings a packet back byte for byte.
- A packet left failing only `METADATA_DISK_PATH_CONSISTENCY` is named for manual review.

#### Layout Is Checked Before Anything Moves <a id="c-layout-is-checked-before-anything-moves"></a>

- `/doctor:update check` reads the spec layout.
- It counts the pre-v4 signals in a read-only phase.
- The compat action is separate.
- It runs a preflight, previews the layout move and waits for your approval.
- After the move it previews the upgrade.
- It asks a second time before it applies anything.
- Nothing is written before the first approval.
- Nothing under `.skilled/` is written.
- `upgrade-legacy --layout-map` prints the planned moves as JSON.
- It names each collision with its reason.

#### A Dry Run Reports Legacy Signals <a id="c-a-dry-run-reports-legacy-signals"></a>

- After the per-packet results, the dry run prints a repository era report.
- It names the layout as v3, v4, both or unknown.
- It says where that answer came from.
- It also counts documents with and without frontmatter.
- The underlying classifier also counts template markers, generated metadata and level documents.
- It does this for each packet.
- The report only reads.

#### A Resumed Compat Run Finishes Its Owed Step <a id="c-a-resumed-compat-run-finishes-its-owed-step"></a>

- A step the run still owes is not counted as a planned move.
- So a resume runs it without the dirty-roots refusal.
- The move log closes on every terminal status reached after a run starts.
- A layout map that prints no JSON now fails the run.
- A failed step keeps its run open.
- So the next resume still lists it as owed.

#### Release Locks Block Legacy Upgrades <a id="c-release-locks-block-legacy-upgrades"></a>

- `upgrade-legacy` now exits 2 while `.skilled/release/.apply.lock` exists.
- Its message names the lock file.
- The refused run writes no packet or manifest data.

## Spec Validation

Validation and the commit checks catch more problems inside a packet.

#### Nested Anchors Are Errors Now <a id="c-nested-anchors-are-errors-now"></a>

- `ANCHORS_VALID` now checks three things it did not check before.
- It reports an anchor opened inside another anchor.
- It also reports a closer that arrives before its opener.
- It reports a closer that arrives while another anchor is still open.
- A name closed more times than it is opened is reported too.
- These findings are errors.
- So a packet that has one fails validation.
- The one nesting that stays allowed is a decision record's child anchor inside its parent.
- The nesting check skips inline code.
- The other anchor checks still count markers in it.
- A phase parent stays exempt.
- Its lean document set passes `ANCHORS_VALID` without these checks.
- It did so before.

#### Anchor Repair Previews Before It Writes <a id="c-anchor-repair-previews-before-it-writes"></a>

- `heal-spec-docs --anchor-repair` fixes three kinds of defect.
- It removes a duplicate anchor pair.
- That pair sits on a line next to another anchor marker.
- That pair also overlaps another pair.
- It renames each other isolated duplicate.
- The new name is its name plus its position.
- That position counts the pairs that share the name.
- So a second `problem` pair becomes `problem-2`.
- It also moves a questions anchor so it sits directly above its heading.
- The run is a dry run by default.
- `--apply` writes.
- A document is refused when its heading sits inside another wrapper.
- It is also refused when its questions anchor does not hold exactly one heading.
- A rename is refused when the new name already exists.
- Each write goes through a temporary file.
- So a failed write leaves the original in place.

#### New Packets Pass Their Own Checks <a id="c-new-packets-pass-their-own-checks"></a>

- `create.sh --phase` writes graph metadata for the parent and every child before it exits.
- So a fresh phase passes strict validation.
- Before this change, the metadata failed the integrity and drift checks.
- It failed the moment it existed.
- New `spec.md` files also place the questions anchor directly above the questions.
- This happens in each level.
- So anchor-based retrieval and merges see the sections below it.

#### Lean Parents Check Every Child <a id="c-lean-parents-check-every-child"></a>

- A phase parent now derives `complete` only when every child's `graph-metadata.json` loads.
- Every child must also be complete.
- Otherwise a parent that would read `complete` reads `in_progress`.
- If no child metadata loads, the parent keeps its stored status.
- Existing metadata changes only when a later re-derive runs.

#### A Text Null Parent Counts as None <a id="c-a-text-null-parent-counts-as-none"></a>

- A packet stored `parent_id` as the text `"null"` in `graph-metadata.json`.
- It failed the metadata path check.
- It needed a hand fix.
- A re-derive now treats that text as no parent.
- It writes JSON null.

## Spec Checks at Commit and Pull Request

A pull request no longer fails on problems it inherited from its base.

#### Trigger Phrases Are Checked Before Commit <a id="c-trigger-phrases-are-checked-before-commit"></a>

- The pre-commit check compares the trigger phrases of each staged Markdown file.
- It compares them with the committed version.
- It grades only the phrases you added.
- A template-default or editor-fallback phrase blocks the commit.
- The block message names the bypass.
- Other negative classes only print a warning.
- The linter, its YAML library, `node` or git may be unavailable.
- Then the check warns and lets the commit through.
- The phrase cleanup now covers all 18 template kinds.
- It writes each file atomically.
- It routes a file without frontmatter to the fixer.
- It no longer counts that file as skipped.

#### Pull Requests Fail Only on New Problems <a id="c-pull-requests-fail-only-on-new-problems"></a>

- The changed-packet gate validates each packet that fails at the head.
- Then it validates the same packet at the merge base.
- It uses the same validator.
- It blocks only on rules the head fails.
- The base must not fail them.
- A report it cannot read counts as a failure.
- So the gate fails closed.
- The weekly sweep now downloads the previous successful run's report as its baseline.
- A folder may pass in that baseline and fail now.
- It is then marked as a regression.
- With no previous report, the run records a baseline and reports no error.

## Upgrade Notes

These steps cover upgrades, restores and the checks around them.

#### Before You Start <a id="c-before-you-start"></a>

1. Apply upgrades from a git checkout. `upgrade-legacy --apply` exits 2 when the repository has no git. An apply may be interrupted. The saved before-images in the git directory then let you restore the files. The README in `spec/` explains how.
2. Wait for a release apply to finish before running `upgrade-legacy`. It exits 2 while `.skilled/release/.apply.lock` exists.
3. Read the refusals before you rerun an upgrade. Each packet's `upgrade-baseline.json` lists the repairs the upgrade refused under `refusals`. A refused repair stays as it was. So you need to fix it yourself.
4. Expect a pre-commit phrase check. The hook blocks added template-default and editor-fallback trigger phrases. Set `SPECKIT_SKIP_PHRASE_LINT=1` to skip the check. The hook prints that bypass when it blocks a commit.

- So run it as `UPGRADE_LEGACY_REPO_ROOT="$repo_root" node --input-type=module --eval "$(cat restore.mjs)" "$manifest"`.
- It checks every sidecar before its first write.
- So one bad sidecar leaves the tree untouched.
- To restore one packet, write a packet-scoped copy of the manifest.
- Put it beside the real one.
- Reduce `beforeImages` and `scopeHashes` to that packet.
- Keep the `baselineMap` as it is.
- Then pass the copy as the manifest argument.

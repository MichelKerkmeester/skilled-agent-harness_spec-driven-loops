# v3.5.0.0, Memory That Maintains Itself

Memory now keeps embeddings on your machine.

- Embeddings run locally first.
- They run on your own machine through Ollama or a Python-free local server.
- They reach the cloud only when you ask.

The runtime gets out of its own way.

- Memory still gets smarter on its own after every save.
- The index keeps itself reconciled.
- The MCP servers are now three separate processes.
- The memory one runs as a single shared daemon.

Restarts stay quiet and deep work fans out.

- A front-proxy sits in front of the memory daemon.
- A restart stops surfacing as an error.
- deep-research and deep-review learned to fan out across several executors.
- The prompt toolkit became forkable, with a small-model hub for open models.

The 026 program made its history canonical.

- It documented every phase into one canonical changelog tree.
- It did that before closing itself out.
- A cleanup pass removed the vendored research repos.
- That code was never ours to ship.

&nbsp;

## Why This Release

A large part of this release went into the launcher and daemon lifecycle.

- That surface was behind most of the prior release's friction.
- It was also behind a hard-to-pin disconnect.
- The 026 program's changelogs had also scattered and drifted.
- So this release made that history canonical.

## Memory and Embeddings

Embeddings now follow a strict local-first order. Memory also enriches itself in the background after each save.

#### Embeddings Stay on Your Machine <a id="c-embeddings-stay-on-your-machine"></a>

- Resolution follows your explicit `EMBEDDINGS_PROVIDER` when set.
- Then it follows a persisted Ollama embedder.
- Then it uses a Python-free local fallback server.
- The common case runs on a single small nomic model on your own machine.
- So it never leaves the box.
- Cloud embeddings are opt-in only.
- Providers like OpenAI or Voyage are never auto-selected.
- This release closed the last place where the local-first rule was not honored.
- The primary resolver used to pick a cloud provider.
- It did that when Ollama was down and an API key happened to be set.
- That was the exact opposite of the intended priority.
- It now follows the local-first order everywhere.
- The Python-free local server matured in the prior release.
- So did the consolidation onto a single nomic model.
- This release made the resolver match the design.

#### Enrichment Moves to the Background <a id="c-enrichment-moves-to-the-background"></a>

- Saves return immediately.
- Post-insert enrichment, reconsolidation and quality auto-fix are now on by default.
- Enrichment and causal relation inference run in the background.
- Enrichment runs async.
- A save comes back with `enrichmentStatus: deferred`.
- A bounded background scheduler then enriches graph and entity data after the commit.
- Reconsolidation stays opt-in behind `SPECKIT_RECONSOLIDATION_ENABLED`.

#### Lineage Becomes Causal Edges <a id="c-lineage-becomes-causal-edges"></a>

- Spec-document chains and lineage links are now promoted into typed `created_by='auto'` causal edges.
- The backfill is bounded, dry-run by default and reversible.
- Two opt-in collectors add a similarity `supports` signal and a structural `contradicts` signal.
- A conflict guard refuses to invalidate an existing valid edge.
- That closes one case.
- A committed `contradicts` run over a reciprocal lineage pair could silently undo the valid `caused` edge it had just created.

#### An Index That Reconciles Itself <a id="c-an-index-that-reconciles-itself"></a>

- Redundant concurrent scans collapse into one.
- Orphans get swept.
- A relocated spec folder is re-pointed instead of orphaned.
- The index reports its state through `memory_health`.
- An active-row uniqueness guard and multi-tenant scope isolation close the door on duplicate rows and cross-scope bleed.

#### Checkpoints Survive a Crash <a id="c-checkpoints-survive-a-crash"></a>

- Checkpoints are real database files.
- Restores are crash-safe.
- Checkpoints used to be in-process snapshots.
- Create now writes a complete file with `VACUUM INTO`.
- Restore swaps a finished file in behind a crash-safe journal.
- If a restore cannot finish, for example after a crash, a `.needs-rebuild` sentinel forces a clean rebuild on the next boot.
- The downgrade guard was updated for schema v30.

## MCP Servers and Sessions

Sessions now share one memory daemon through a front-proxy. A lease holder owns the daemon child, and other launchers bridge to it.

#### Many Sessions, One Daemon <a id="c-many-sessions-one-daemon"></a>

- Memory, code-graph and skill-advisor are separate MCP servers.
- Each has its own launcher.
- Sessions share one `system-spec-memory` daemon.
- Each session no longer spawns its own.
- Sessions no longer contend on the database.
- A lease-holder launcher owns the daemon child.
- Other launchers bridge their own client to it through a session proxy.
- The owner stores its real IPC socket path in the lease.
- A secondary launcher pointed at a different socket directory still finds the live daemon.
- It does not fail with no bridge socket.

#### Clients Stay Connected Through a Recycle <a id="c-clients-stay-connected-through-a-recycle"></a>

- The front-proxy sits in front of the memory daemon.
- It hides a recycle.
- The front-proxy sits between clients and the daemon.
- When the daemon recycles, a connected client no longer sees a hard error.
- The launcher reconnects.
- It re-handshakes on a protocol-version drift.
- It keeps each connected client independently transparent.
- It is also hardened against an externally killed or slow-booting daemon.
- A boot-time full-text-search auto-heal fixed the daemon-lifecycle root cause behind the recurring corruption-looking failures.
- So did a launcher clean-close barrier.

#### Worktree-Per-Session Isolation <a id="c-worktree-per-session-isolation"></a>

- Sessions can each run in their own worktree.
- The worktree is reaped when the session closes.
- Per-session worktrees prevent the multi-session contention behind much of the prior release's daemon friction.
- The guard is wired into the Claude session-start chain.
- Child sessions launched through the CLI dispatchers share the parent's worktree.

## Deep Loops

Deep loops can now fan out across several executor lineages. The single-executor path stays the default.

#### Fan-Out Across Executor Lineages <a id="c-fan-out-across-executor-lineages"></a>

- The fan-out layer is opt-in.
- Each lineage is an isolated sub-packet with its own state directory.
- The lineages run behind a concurrency-capped pool with a status ledger.
- A salvage path recovers a lineage's work from captured output if its write fails.
- One loop drives several executor lineages.
- It recovers from a flaky one, instead of grinding through a single lineage at a time.
- A consumer-specific merge folds the lineages back together.
- Research dedups and attributes findings.
- Review rolls up severity.
- It fails closed if any lineage reports a P0.
- The single-executor sequential path stays the default.
- It is byte-identical to before.

#### Lineages Still Run Serially <a id="c-lineages-still-run-serially"></a>

- In this release the fan-out runs under the cap.
- It still issues its lineages serially.
- The genuine-concurrency remediation was specced here.
- It lands in the next release.

#### Two Parser Fixes Behind the Loops <a id="c-two-parser-fixes-behind-the-loops"></a>

- The review transcript parser no longer concatenates a model's prompt-echo into invalid JSON.
- It no longer zeroes out findings.
- The convergence snapshot writer refuses to coalesce every snapshot to one id.
- It refuses to silently overwrite history.

#### A Skill-Benchmark Lane <a id="c-a-skill-benchmark-lane"></a>

- deep-agent-improvement was renamed deep-improvement this cycle.
- The skill gained a skill-benchmark lane and a model-benchmark framework.
- The skill-benchmark lane measures how a real agent discovers, routes to and uses a skill in situ.
- It scores routing accuracy, unprompted discovery, efficiency and usefulness into a ranked, remediable report.

#### One Framework for Model Benchmarks <a id="c-one-framework-for-model-benchmarks"></a>

- A reusable, config-driven model-benchmark framework replaced the one-off rigs.
- A single profile runs a framework bake-off or a model-versus-model comparison with no mode branches.
- Correctness is a gate.
- So a saturated score cannot crown a winner.
- The verdict is WINNER, TIE or INCONCLUSIVE against a noise floor.

## Prompt Toolkit and Skills

The prompt toolkit now has three layers and a forkable core. A small-model hub holds the per-model craft.

#### Three Layers and a Forkable Core <a id="c-three-layers-and-a-forkable-core"></a>

- The prompt toolkit was re-architected into three layers.
- Framework craft lives in `sk-prompt`.
- Per-model craft lives in `sk-prompt-models`.
- Executor mechanics live in the `cli-*` skills.
- The model registry and benchmarks moved into `sk-prompt-models`.
- `sk-prompt` lifts out cleanly.
- `sk-prompt-models` drives open models through cli-opencode.
- So the generic `sk-prompt` skill can be lifted out of this repo without dragging the small-model registry with it.

#### Open Models That Pay Off <a id="c-open-models-that-pay-off"></a>

- The small-model hub holds the per-model prompt-craft profiles, the model registry and the benchmark run-data.
- Open models like DeepSeek, MiniMax and Xiaomi MiMo can be driven effectively through cli-opencode rather than prompted blind.
- MiniMax now defaults to its Token Plan provider.
- Xiaomi MiMo-V2.5-Pro was added as a selectable executor.

#### Supporting Skill Work <a id="c-supporting-skill-work"></a>

- A new `mcp-click-up` skill handles task work.
- `sk-code` gained surface-aware routing and mined animation principles.
- `sk-git` gained a numbered `wt/{NNNN}-{name}` worktree convention.
- Feature-catalog standards were applied retroactively across roughly 370 catalog files.

## Upgrade Notes

This release has no breaking API changes. New capability is additive. The MCP server reports `1.8.0`.

#### Before You Start <a id="c-before-you-start"></a>

1. Verify and repair with `/doctor` after upgrading.
2. The doctor command is the fastest way to confirm each subsystem is healthy.
3. `/doctor <target>` runs a focused diagnostic.
4. Targets are `memory`, `embeddings`, `causal-graph`, `code-graph`, `deep-loop`, `skill-advisor` or `skill-budget`.
5. Most targets are read-only.
6. They report drift with a recommended action rather than mutating anything.
7. For a quick read-only install check, run `bash .opencode/skills/system-spec-kit/scripts/doctor.sh --strict`.
8. That confirms the memory server's dist and native modules are present.

# v3.5.0.2, Sessions Keep Their Hands to Themselves

This patch stops one session's cleanup from killing the MCP launchers of other open sessions. It refuses to serve a memory index that a dirty shutdown has corrupted. It salvages the live index that was already damaged.

It closes a long-open case. The case was why MCP transports kept dying mid-session. That was true even after the front-proxy work. The answer was not in the daemon at all.

The session-cleanup hook took its identity from `CLAUDE_SESSION_PID`. When that was missing, it guessed with the hook's parent pid. Under a shared terminal, that guess hit an ancestor of every open session. So "walk my descendants" quietly became "walk everyone's descendants". One session ending would sweep away its siblings' MCP launchers by name.

The result was the whole familiar failure. There was a dead launcher, a dirty daemon exit, a stale socket and a refused connection. All of it came from one bad fallback. The probe work that followed found the damage was not hypothetical. The live memory index was already structurally corrupted. The cleanup bug's dirty shutdowns did it.

&nbsp;

## What's New at a Glance

- Session cleanup now needs explicit session identity.
  - The Stop-hook cleanup in `session-cleanup.sh` is supposed to reap only the MCP helpers of the session that just ended.
  - With no identity it now does nothing at all.
- Each kill re-proves ancestry first.
  - Ancestry is no longer trusted from a snapshot.
  - Immediately before each kill, the script walks the candidate's live parent chain.
  - The script proceeds only if it reaches this session's pid.
  - A sibling session's process can never satisfy that.
  - The session's own helpers still die on schedule.
- Every kill and skip is logged.
  - Each entry carries `matched_by=` and `ancestor_ok=` fields.
  - So if a transport ever vanishes again, the log answers who and why.
- A boot after a dirty shutdown checks the whole database.
  - The daemon already marked dirty shutdowns with an `.unclean-shutdown` marker.
  - But it only ran a detect-only check of the FTS shadow index.
  - A marker present at open now also triggers a whole-database `PRAGMA quick_check`.
  - Clean shutdowns skip the probe entirely, so the common case pays nothing.
- A corrupted database is refused, never served.
  - On a failed check the store writes the checkpoint `.needs-rebuild` sentinel.
  - That is the same crash-safe machinery checkpoints already use.
  - The store refuses to start rather than serve a silently malformed index.
  - The store fails loudly because that beats serving corrupted rows to every connected session.
- The live index was salvaged the same evening.
  - The gate was pointed at the live `context-index.sqlite`.
  - The gate reported real b-tree damage, with invalid page numbers and doubly-referenced pages.
  - There was no checkpoint to restore.
  - `sqlite3 .recover` rebuilt a clean candidate that passed `quick_check`.
  - The clean candidate kept 9,888 of 9,890 memory rows.
  - The recovery parked 368 orphaned rows in `lost_and_found` for triage.
- The swap is reversible by design.
  - The corrupted original remains on disk beside the recovered file.
- Two flagged hardening items had already shipped.
  - Recording the daemon child pid in the launcher lease came in earlier daemon-reliability phases.
  - So did reclaiming a stale bootstrap lockdir.
  - Both were verified in source and recorded as no-ops.
- The remaining root causes keep their existing owners.
  - The bridge liveness probe, the provider dispose and the exit watchdog are planned phases.
  - This release deliberately did not touch them.
- A suite rerun and an index reconcile are owed.
  - The vitest runner would not start in this sandbox.
  - That is an environmental problem.
  - The suite rerun is owed to the next dev session.
  - An embedding-reconcile pass over the recovered index is the recorded follow-up.

&nbsp;

## Upgrade

- No API changes.
- The cleanup fix is active on the next session stop.
- The integrity gate activates on the next daemon start.
- Dist is rebuilt.
- So if a daemon is already running, recycle it.
- A refused boot is the gate working.
- If a future start stops with a needs-rebuild sentinel, the checkpoint rebuild path takes it from there.
- `/doctor memory` remains the fastest health read after any daemon lifecycle event.

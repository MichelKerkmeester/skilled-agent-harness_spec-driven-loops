Spec documents now enter indexing without being rejected for lacking memory-file metadata. This makes spec content searchable. The goal is to make the workflow easier to follow and easier to trust.

&nbsp;

## What's New at a Glance

- Indexing warns instead of rejecting spec documents.
  - About 97% of spec documents had been silently rejected.
  - That is because the quality gate required memory metadata such as trigger phrases and importance tiers.
  - Spec documents such as `spec.md`, `plan.md` and `tasks.md` follow their own templates.
  - Spec documents intentionally lack that metadata.
  - Spec documents now pass indexing with warnings.
  - The normal save path for memory files continues to enforce all checks.
- Re-indexing can build spec-document causal chains.
  - Only about 7 links existed while spec documents were rejected.
  - After re-indexing, hundreds of chains can form.
  - The chains run across spec documents, plans, tasks, checklists and implementation summaries.
  - The chains use `caused` and `supports` relationships.
- Save orchestration handles a TypeScript build error.
  - The code assumed a value was always a list.
  - The value could sometimes be an empty object.
  - The added check handles both cases.
- A one-time cleanup removed stale memories and repaired orphaned records.
  - The cleanup purged 128 stale memories.
  - 112 were marked as deprecated.
  - 14 were leftover test entries.
  - 2 were test stubs.
  - The cleanup also repaired 3,035 orphaned causal edges and 2 orphaned chunks.
  - These orphaned records were pointing to deleted parents.
- The full re-index recovered previously missed files.
  - The memory count rose from 358 to 407.

&nbsp;

## Upgrade

- Rebuild. Run `npm run build` in `mcp-server/`.
- Restart the MCP server.
- Re-index. Run `memory_index_scan({ force: true })` to re-index all spec documents and rebuild causal chains.
- No database migration is required.

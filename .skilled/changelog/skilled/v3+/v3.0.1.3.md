This release brings 28 fixes across concurrency safety, search performance, database query optimization, error recovery and dead code removal. It protects operations from restore-time changes, duplicate shared-space ownership and stale merge data, reduces repeated work across search and database lookups and closes recovery paths that could leave partial data behind. The goal is to make the workflow easier to follow and easier to trust.

> Spec folder: `.opencode/specs/system-spec-kit/022-hybrid-rag-fusion/026-memory-database-refinement/` (Level 2)

## Why This Release

The problems surfaced under concurrent load and after failures, while redundant database work made saves and searches slower.

---

## What's New at a Glance

- **Restore-time mutations are guarded.** `E_RESTORE_IN_PROGRESS` tells callers when restore work prevents a change.
- **Only the request that creates a shared space gets ownership.** Simultaneous requests no longer both claim `created: true`.
- **Memory merges reject changed predecessors.** Changed or missing records fall back to the regular save path.
- **Index scans reserve an atomic lease.** Concurrent scans cannot claim the same cooldown slot.
- **Fallback search and response sizing avoid repeated work.** Post-processing runs once and each result's size is calculated once.
- **FTS5 is the default text search and BM25 is opt-in.** `ENABLE_BM25=true` enables BM25.
- **Graph search batches scoring and avoids duplicate matches.** Candidate degree scoring and graph text search need less repeated work.
- **Adaptive fusion skips standard fusion when production needs only adaptive weights.** The fusion lists are built once using those weights.
- **Diversity reranking reuses vectors already fetched by vector search.** It queries the database only for missing vectors.
- **Memory and working-memory lookups use targeted queries.** Save, trigger-cache and working-memory operations avoid unnecessary scans or checks.
- **Related, temporal and file-reference lookups avoid repeated full-table reads.** They use batched lookups or a narrowed time range.
- **Chunked saves and search repairs recover without leaving inconsistent state.** Failed operations no longer leave duplicate chunks or an unrecorded search-index repair.

## Concurrency Safety

#### Mutations Get an Immediate Rejection

A checkpoint restore can take seconds while search indexes, text indexes and graph caches rebuild. Nothing prevented saves, index scans or bulk deletes during that window, so a save that landed mid-rebuild could leave the database in an inconsistent state. The restore now sets a maintenance barrier before it begins and clears it only after all rebuilds complete, and saves, index scans and bulk deletes that arrive in between receive an immediate `E_RESTORE_IN_PROGRESS` rejection. Cleanup releases the barrier if the restore fails or crashes.

&nbsp;

#### Only the Creator Becomes Owner

Two requests to create the same shared space could both report `created: true` and bootstrap themselves as owners. Ownership now goes only to the request that actually creates the row. A conflict is handled as an update and does not promote its caller to owner.

&nbsp;

#### Merges Reject Stale Predecessors

Memory merges can wait seconds for an AI service to generate an embedding. Previously, a change or deletion during that wait could be overwritten using stale data or archived despite no longer existing. Before committing, the merge reloads the original inside the transaction and compares its content hash and last-modified timestamp. A changed original aborts as `predecessor_changed`, while a deleted or archived one aborts as `predecessor_gone`. Either result uses the normal save path instead.

&nbsp;

#### Index Scans Reserve a Lease

The cooldown check used to separate checking the last scan time from updating it, so simultaneous requests could both start scans. The check and reservation now happen atomically in one database transaction, and a fresh lease rejects another request. A crash-expiry timer frees the slot after 2 minutes if a scan process dies mid-way.

## Search Performance

These changes reduce redundant computation in the search pipeline. Search results do not change: the same queries return the same answers, just faster.

#### Fallback Work Runs Once

When a search finds too few results, the system tries progressively looser fallback tiers. Previously, each tier reran candidate collection, score fusion and the full post-processing pipeline. The pipeline is now split into two phases: collecting and fusing candidates still runs for each fallback tier to build up the candidate pool, while reranking, co-activation boosts, folder relevance, confidence filtering, context headers and token trimming run once on the final merged candidate set after the last tier is chosen.

&nbsp;

#### Each Result Is Sized Once

Response sizing used to estimate each result twice. It also serialized complex nested metadata each time. A per-request cache keyed by result ID stores one estimate per result, and the estimator now counts known fields directly.

&nbsp;

#### BM25 Becomes Opt-In

SQLite's built-in FTS5 and the in-memory BM25 engine used to run by default. BM25 performed a synchronous full-table scan at startup, blocking the server from accepting requests, and could drift out of sync. It is now opt-in behind `ENABLE_BM25`, with FTS5 as the only text-search engine by default. When enabled, BM25 syncs only changed rows and rebuilds during background warmup instead of blocking startup.

&nbsp;

#### Graph Search Avoids Repeat Work

Graph degree scoring previously ran one database query per candidate, with another query for the global maximum used in normalization. It now scores all candidates in one query and caches the global maximum with per-node results. Graph text search could return the same edge through both directions of an OR-based join, then remove duplicates in JavaScript. The query now finds matching memory IDs once and checks edges from both directions without overlap. FTS-table availability is also cached per database connection to skip repeated checks.

&nbsp;

#### Adaptive Fusion Skips Unused Work

Adaptive fusion used to run standard fusion, adaptive fusion and a comparison even though production only needs adaptive weights. A lightweight helper now returns the weights alone, and the pipeline builds its fusion lists once instead of performing and discarding a full standard fusion.

&nbsp;

#### Reranking Reuses Vectors

Vector search had already fetched each result's vectors for similarity comparisons, but the diversity reranker fetched them again one at a time. Vector search now passes its vectors in a request-scoped cache. The reranker checks that cache and queries the database only for missing vectors. The linear `reranked.find()` lookup was replaced with a Map for O(1) access.

## SQLite Query Optimization

#### Save Lookups Use Exact Scopes

Each memory save checked three times for an existing record by path, content hash and main path. Nullable scope predicates for tenant, user, agent, session and shared space prevented SQLite from using indexes, so each check scanned the full table. Lookups now include only scope columns present in the request as exact matches, and the combined main-path and file-path check is split into separate probes. Two new partial indexes, both filtered to non-chunk rows, serve main-path lookups and content-hash lookups with scope columns.

&nbsp;

#### Trigger Refreshes Avoid Full Scans

Every mutation used to rebuild the trigger-phrase cache by scanning all successfully embedded memories that had trigger phrases. A targeted index now covers that set, and the prepared query is cached per database connection.

&nbsp;

#### Related Memories Load in Batches

The co-activation boost raises results related to other high-scoring results. It used to fetch each related memory individually, while causal neighbors needed separate lookups in each direction. Related-memory details now load in one batch, causal neighbors use one joined lookup and neighbor counts are prepared before boosting.

&nbsp;

#### Time Searches Narrow the Range

Temporal proximity searches used to apply date functions to `created_at`, preventing SQLite from using the index and forcing a full-table scan. They now narrow the search with a range on the raw `created_at` value, then calculate time differences only for the narrowed results. A new composite index on `(spec_folder, created_at DESC)` makes that range scan fast.

&nbsp;

#### File References Resolve in Batches

Causal link resolution used leading-wildcard searches that could not use an index and scanned the full table. It now tries exact matches on `main_file_path` and `file_path` first, falls back to fuzzy matching only when exact matching fails and resolves all references in a document in one batch.

&nbsp;

#### Working Memory Avoids Extra Queries

Working memory tracks recently active memories per session, and its last-focused and attention-score orderings previously required sorting without matching indexes. Two indexes now align with those query orders. Upserting an entry also no longer runs a separate existence count first because the conflict handling already covers insert and update.

## Error Recovery

#### Chunk Saves Fail Cleanly

When a large file was split and indexed in chunks, failure to mark the old version as superseded could return an error after the new chunks were committed. A retry could then create duplicate chunks while the old version remained active. Superseding now shares the chunk commit's final transaction. If superseding fails, cleanup removes the newly created parent and child rows before returning the error, leaving no orphaned data and allowing a clean retry.

&nbsp;

#### Safe Swaps Stay Transactional

During a safe swap, old chunk children used to be deleted after the transaction committed. If deletion failed, the old children could remain beside the new ones as orphaned records. Deletion now happens in the finalization transaction, which rolls back on failure and leaves the old version intact.

&nbsp;

#### Search Updates Wait for Successful Chunks

Chunking used to update BM25 with the new parent summary before indexing the chunks. If every chunk failed, the database restored the old parent but BM25 kept the new summary, hiding the old parent's content from word searches until a full rebuild. BM25 updates now wait until at least one chunk succeeds, so an all-failed fallback leaves its text index untouched.

&nbsp;

#### Failed Search Repairs Can Be Retried

A merge could commit while updating the text-search index failed, leaving the merged memory unavailable to word searches. The failure used to be logged but not recorded durably for later repair. A persisted `bm25_repair_needed` flag on the merged row now records the failed repair for a future reconciliation process or manual repair tool.

## Dead Code Cleanup

These changes remove unused code that increases maintenance burden and confuses code navigation.

#### Startup Warmup That Never Ran

Server startup held an eager warmup branch for embedding models, guarded by a helper fixed to return `false`. Nothing could ever reach that code. Both the dead code branch and the always-false helper were removed.

&nbsp;

#### Unused Exports and Proxies Removed

`tools/types.ts` exported `MCPResponseWithContext` and `parseValidatedArgs`, and nothing imported either one. The handler barrel `handlers/index.ts` exported 9 lazy module proxies, while all actual handler usage goes through its named function exports. The two unused exports and all 9 proxies were removed, and the named function exports that are actually used remain unchanged.

&nbsp;

#### Debug and Type Exports Retired

The trigger matcher and shadow scoring each carried a debug helper exported during development, and no production or test code called either one. Three type exports also had zero imports across the codebase: `PipelineOrchestrator` from pipeline types, `InterferenceResult` from interference scoring and `SurrogateMatchResult` from query surrogates. Both debug helpers and all three type exports were removed.

&nbsp;

#### Test Suite Drops Its Shim

The shared memory handler tests sat in `shared-memory-handlers.test-suite.ts` instead of the standard `.vitest.ts` extension, so a one-line shim (`shared-memory.vitest.ts`) existed solely to re-export the test suite so Vitest could find it. The test file was renamed `shared-memory-handlers.vitest.ts` and the shim file was deleted.

&nbsp;

#### Score Resolution Lives in One Place

The function that decides which score field to use for a search result was defined in three places. `pipeline/types.ts` held the main version while `confidence-scoring.ts` and `profile-formatters.ts` each held a copy. Both copies now import the main version instead of defining their own.

## Upgrade Notes

- The schema moves from version 21 to 24, with 6 new indexes and a new `bm25_repair_needed` column on `memory_index`. These changes are backward-compatible and migrate automatically on startup, so no schema migration is required.
- **BM25 users.** **Breaking:** If you relied on the in-memory BM25 engine in addition to FTS5, set `ENABLE_BM25=true` to keep it active. Most users will not notice because FTS5 handles the same queries. BM25 is only needed for specific benchmarking or experimental scenarios.

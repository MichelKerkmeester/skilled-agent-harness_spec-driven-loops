# v4.0.2.1, Search Says How Much It Found

Gate 1 and `/speckit:search` used to hide what they left out. A short answer looked complete. A new spec document could not be found until the next index build. One common phrase could fill the whole result with two files. All three now say what they found and what they held back.

The work began as research into sweet-search, an outside code-search tool. Skilled kept its own search. It took three lessons from the research and built them. This release also fixes the routing and the checks that the build turned up.

> Spec folder: `specs/hooks-plugins-extensions/retrieval-integrations/001-sweet-search-integration`

&nbsp;

## Why This Release

An agent trusts a Gate 1 answer. It reads the answer as the full picture.

That was not always true. With `--limit 2` the agent saw two results. Nothing said that nine more matched. A packet written an hour ago returned nothing, because CI rebuilds the index only after a push. In free-text search, one long file could fill every row. The other files dropped out of view.

A missing result and a hidden result looked the same. So the agent either stopped too early or searched again for something that was not there.

&nbsp;

## Trigger Lookup

#### A Limited Answer Says What It Cut

The lookup now returns `totalCandidates`. That is the number of documents that matched before `--limit` cut the list.

The human view reads `candidates : 2 of 11 (truncated) from 1090 phrase(s)`. The word `truncated` shows only when the limit hid something. A full answer reads as it did before.

#### A Lookup With No Hits Reads What the Index Missed

Sometimes the index returns nothing. The lookup then compares the `specs/` tree with the paths in the index. Any spec document the index does not list is new.

The lookup reads the trigger phrases of those new documents, up to 500 of them. It scores them like any other match.

The answer says when this happened. JSON carries `staleFallback`. The human view adds `fallback   : <files> unindexed doc(s) read, <matches> match(es)`.

The first design asked `git status` for new documents. That took 0.8 to 1.1 seconds per lookup. The budget is 200 ms. The path comparison replaced it. It is faster. It also finds documents committed since the last build.

One gap remains. A phrase edited inside a document the index already lists still needs a rebuild.

To keep an answer to the index alone, pass `--no-stale-fallback` or an explicit `--index`.

#### A Linked Project Scans the Right Tree

A project linked to a Skilled checkout reads its host's index. The extra scan now walks the host repository. That is where the index's paths live.

A linked install with a packaged index is different. Its index names other documents, so the scan is skipped there. Before this fix it reported every host packet as a match.

#### An Error Is Not a Clean Miss

A crash inside the lookup used to exit 1. That is the code for "nothing matched". It now prints the error and exits 2.

`staleFallback.files` also counted a document it failed to open. It now counts only what it read.

## Free-Text Search

#### Each File Appears Once

`rg-wrapper.mjs structured` ranks every match first. Then it keeps the best row per file. A file with more matches ends its row with `(+N more in this file)`.

`--limit` now counts files. The default is 20. `--limit 0` shows them all. When the limit drops files, the answer ends with `+N more files with M matches`.

The cut happens after ranking on purpose. Stopping ripgrep at the first match per file would keep each file's first line. That is often not its best line.

#### The Search Command Runs the Wrapper

`/speckit:search` used to run raw ripgrep. It never got the one-row-per-file result. Its default search now runs `rg-wrapper.mjs structured '<QUERY>' --json`.

A phrase that starts with `--` still runs raw ripgrep. The wrapper would read it as a flag.

#### Path and Count Lists Respect the Limit

The wrapper's `path` and `count` recipes took `--limit` and ignored it. A broad pattern still printed every file.

Both lists are now sorted and cut at the limit. The count list puts the busiest file first. Each answer says how many files it hid. The totals still cover every file.

#### The Record Carries the Totals

Wrapper JSON is now `schemaVersion: 3`. It reports `matchCount`, `fileCount`, `limit`, `truncated` and `hidden: { files, matches }`. Each row carries `moreInFile`.

An unused recipe builder was removed. It capped each file at its first line.

## Routing

#### Index Questions Reach the Skill That Owns the Lookup

The skill advisor keeps every skill at a low score on a read-only prompt. With no skill passing, the doctor helper claimed any prompt that named the index.

A read-only prompt that names the trigger index now lifts `system-spec-kit`. A prompt about index drift is not lifted. It still reaches the doctor, which owns the repair.

`system-spec-kit` also gained new intent signals. They cover spec-document search, the ripgrep wrapper, trigger phrases and unindexed spec documents.

## Fixes Along the Way

- **The command reference check passes.** It tripped on the gitignored deep-loop graph databases. It now skips them.
- **Both READMEs name the host-only index paths.** The reference check reported them as missing.
- **The speckit command README has its purpose and instructions sections.** The document validator requires both.
- **`SPECKIT_RG_BIN` is in the environment reference.** The code read the variable. No document listed it.

#### Found in Review

- **The human view no longer cuts twice.** It printed 20 rows even when `--limit` asked for more. The hidden count did not cover the gap.
- **The retrofit baseline counts every match.** It used to count rows after the cut.
- **The fallback has less code.** A review looked for overengineering. It found nothing blocking and ten small points. The valid ones were applied. A sort of an already sorted list went. So did three exports nothing imported and four tests that repeated another test.

## How It Was Checked

#### Before and After

|---|---|---|
| Lookup with `--limit 2`, 11 documents match | 2 candidates, no total | `2 of 11 (truncated)` |
| Lookup for a packet written after the last index build | no result | found, with `fallback : N unindexed doc(s) read` |

| `path` recipe with `--limit 2`, 4 files match | 4 paths | 2 paths and `+2 more files` |

#### What It Costs

The lookup budget is 200 ms at p95. It did not move.

A lookup with no hits takes 89 to 102 ms against the index alone. It takes 155 to 176 ms when the fallback reads 156 documents. A lookup that finds something skips the fallback. Its median stayed at 72 ms. The wrapper's median query time stayed at 38 ms.

## Upgrade Notes

- **No migration required.** The new output fields are additions.
- **If you parse wrapper JSON:** `results` holds one row per file. `paths` and `counts` hold only the files inside the limit. Read `schemaVersion`. Use `matchCount` and `fileCount` for the totals.
- **If you run the skill advisor from a built copy:** run `npm run build` in `.skilled/skills/system-skill-advisor/runtime` once.
- **To keep a lookup to the index:** pass `--no-stale-fallback`.

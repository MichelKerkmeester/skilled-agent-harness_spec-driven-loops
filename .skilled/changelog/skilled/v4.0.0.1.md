# v4.0.0.1, The Foundation Hardened: Old Specs Forward and Quieter Sessions

v4.0.0.1 makes the v4 rebuild usable on the work you already have and quieter to work in.

- It is a hardening release.
- It was proven on this repository's own years of spec history rather than on a demo.
- The rest of the release closes the seams the first weeks of real use found.

The headline is the migration path.

- Spec folders written under v3.x fail the strict validator almost without exception.
- Until now every workflow stopped at that failure.
- A new command repairs them in one pass with no language model involved.
- It fills in what a document lacks without rewriting a word you wrote.

The command records what it cannot clear.

- So old findings stop looking like new mistakes.
- The question that binds a session to a spec folder now arrives once at your first save.
- It no longer arrives on every turn.
- It reaches every runtime.

The tools that create, move and archive spec folders keep them consistent.

- Saves stop touching files they do not own.
- The model rosters moved up a generation across every dispatch surface.
- Documentation changed with them.
- The always-loaded rules no longer contradict the prompting guides a model reads first.

> [!IMPORTANT]
> 1 change can break an existing setup. Read these before you update.
>
> 1. Pi and OpenCode reach MiMo through LLM Gateway alone now. [MiMo Runs Through the Gateway](#c-mimo-runs-through-the-gateway)

&nbsp;

## Why This Release

A rebuild as large as v4.0.0.0 moves so much. So its own history becomes the fastest way to find the seams. Everything here was measured against real packets, real sessions and real dispatches. It also carries the one thing a person upgrading from v3.x needs most.

- Old spec folders should cost one command to adopt.
- They should not cost a repair project paid for in AI time.
- This release ships that command.
- It also ships the validator change that keeps legacy findings from blocking new work.

## Spec Folders and Their Tools

Spec folders now behave like one system. They are created in the right place and numbered once. They are archived with their family and saved without collateral damage.

#### Old Specs Upgrade Without a Model <a id="c-old-specs-upgrade-without-a-model"></a>

- A person coming from v3.x holds spec folders that fail strict validation almost without exception.
- Every workflow stops at that failure.
- `node .skilled/skills/system-spec-kit/runtime/cli/spec/upgrade-legacy.mjs` fixes this in one pass.
- It needs no language model.
- It works on packets in a top-level `specs/` folder, where v4 reads them.
- If yours still live in `.opencode/specs`, it stops.
- It prints the one move that fixes that.
- It is a dry run until you pass `--apply`.
- `--roots <dir>` narrows it to the folders you name.
- `--include-archive` brings archived packets in too.
- It works on each active packet that fails.
- It fills in the frontmatter keys a document lacks.
- Those keys are the metadata block at the top of each document.
- It rewrites no value already there.
- A document whose metadata block it cannot read is left as it is.
- The run names it.
- It then runs the existing repair tools on the packet.
- It writes every finding they cannot clear into the packet's `upgrade-baseline.json`.
- The validator now reads that file.
- A finding listed there is a warning.
- So old findings stop blocking new work.
- A finding the file does not list is still an error.
- So a new mistake in an upgraded packet still fails.
- Findings about generated metadata are never listed for an active packet.
- That is because re-deriving the metadata clears them.

<details>
<summary><b>Smaller fixes</b></summary>

- The same work tightens the backfill that regenerates a packet's derived metadata.
- It now exits with a failure when a folder cannot be re-derived.
- So the repair tool reports the failure instead of calling the packet repaired.
- The pre-commit hook therefore blocks a commit whose metadata cannot be re-derived.
- Set `SPECKIT_SKIP_SPEC_REMINT=1` when you mean to bypass that check.

</details>

#### Track Roots List What They Hold <a id="c-track-roots-list-what-they-hold"></a>

- Fifteen of the eighteen track roots listed packets they did not hold.
- They also missed packets they did hold.
- Nothing wrote these lists.
- The one check compared counts and ran nowhere.
- A writer now sets each track root's list from disk.
- Scaffolding adds a new packet to its track's list as it creates it.
- A push whose lists disagree with the folders beside them stops at the hook.

#### Archives Keep Packets at Home <a id="c-archives-keep-packets-at-home"></a>

- Archiving used to send everything to one pile at the specs root.
- A track packet left its track.
- A restore dropped it at the root.
- Same-numbered phases from different packets collided there.
- A packet now archives into the `z_archive/` beside its own track.
- A phase archives into its parent's.
- A restore returns each one where it came from.
- The track list refreshes after every move.
- So the push gate has nothing to block.

#### New Packets Land in the Right Place <a id="c-new-packets-land-in-the-right-place"></a>

- New packets were briefly written to a tree nothing reads.
- Each new name started its numbering at 001.
- Scaffolding now writes to the canonical `specs/` root.
- A packet made at the root takes the highest number already there.
- Making one no longer fetches or prunes remotes.
- So it never touches your network or your refs.
- It also works in a fresh checkout with no install.
- It writes the same documents the full toolchain would.
- It names the missing build when a generated file cannot be written.

#### Saves Write What They Carry <a id="c-saves-write-what-they-carry"></a>

- A save used to ignore the continuity fields it was given.
- Those fields are the session bookkeeping a packet records.
- It also rewrote one file that every packet in the track shares.
- So concurrent sessions kept colliding and resume state went stale.
- The save now writes those fields into the packet that holds the work.
- The track's pointer lives in the store that resume reads first.
- The reader also accepts hand-written continuity blocks as people actually write them.
- So a block you wrote by hand is read rather than rejected.

#### Level Upgrades Add Whole Sections <a id="c-level-upgrades-add-whole-sections"></a>

- Upgrading a packet's level injected changed template lines along with the new sections.
- It left a second title and broken tables behind.
- A level upgrade now adds whole sections only.
- The upgraded packet passes strict validation straight away.
- The phase-map tool beside it now changes only the rows that disagree with their child.
- It reports a completion mismatch instead of writing over it.

## The Gate That Asks Once

The spec gate decides which folder a session's work belongs in. It grew quieter and more complete at once.

#### One Question at the First Save <a id="c-one-question-at-the-first-save"></a>

- The gate used to append its option menu to every turn that looked like a write.
- One recent session carried 52 injections with most gate states still open.
- The question now arrives once per session at your first real file change.
- It comes through whatever channel the runtime has.
- On Pi that is an interactive dialog.
- Elsewhere it is a tool-call notice.
- Where nothing better exists it is a one-shot deferral.
- The answer is remembered on disk.
- So a later write stays quiet.
- Answering also works for a folder you just named that does not exist yet.

#### Every Runtime Hears the Question <a id="c-every-runtime-hears-the-question"></a>

- Moving the question left one runtime holding a gate that opened and never spoke.
- That is because the shared adapter had gone silent.
- The plugin's own mocks hid it.
- Hermes gets the same delivery the other runtimes have now.
- The pages that still described the old turn-time behavior were corrected against the code.
- Two claims were wrong about when the question appears.

#### The Gate Covers Every Repository <a id="c-the-gate-covers-every-repository"></a>

- The gate used to exempt anything under `/tmp`.
- That switched it off for a repository that itself lives there.
- A repository is now gated wherever it lives.
- Scratch space outside it stays exempt.
- The CI workarounds that the old rule forced are gone.
- The recorded probe scripts run under the shell standard the drift check expects.

#### Advisories Stop Crying Wolf <a id="c-advisories-stop-crying-wolf"></a>

- Two advisers warned about problems that were not there.
- The staging advice now stays quiet when a path is about to be expanded by the shell.
- The completion sentinel no longer reads a cited document as a missing packet.
- The destructive checks still fire.

## Models and Dispatch

Two model generations moved at once. The dispatch rules that name them were brought in line with what their runners actually accept.

#### MiMo Steps to v2.6 <a id="c-mimo-steps-to-v26"></a>

- The Xiaomi MiMo ids moved to the v2.6 generation.
- Every surface that names one moved with them.
- That covers the skill pages and the settings.
- It also covers the allowlists that decide whether a dispatch resolves at all.
- Those allowlists are the fixed rosters a runtime will accept.

#### MiMo Runs Through the Gateway <a id="c-mimo-runs-through-the-gateway"></a>

> [!WARNING]
> Pi and OpenCode reach MiMo through LLM Gateway alone now.
>
> The direct Xiaomi routes are gone from both.
>
> `mimo-v2.6-pro-ultraspeed` is off the rosters.
>
> Point anything that names a Xiaomi route at `llmgateway/mimo-v2.6-pro` instead.

- That is because the gateway serves no ultra-speed tier.
- So a dispatch naming it fails before it launches.

#### Luna and Sol Step Up <a id="c-luna-and-sol-step-up"></a>

- OpenAI's GPT-6 Luna and Sol replace the 5.6 pair everywhere a dispatch can name them.
- Their `-fast` and `-pro` forms come with them.
- So do provider prefixes wherever a runtime serves them.
- Claude Code names one Opus id, Opus 5.5.
- Terra keeps its `gpt-5.6-terra` id.

#### Dispatch Rules Say What They Cover <a id="c-dispatch-rules-say-what-they-cover"></a>

- Five CLI packets told an orchestrator to send every dispatch through the shared fan-out runner.
- That runner is the tool that spreads a research or review pass across several models.
- It accepts nothing else.
- So every build dispatch had to break the rule to get done.
- The rules now send research and review lineages to the runner.
- They name the exact command shape a single build or doc dispatch takes instead.
- One sandbox limit is recorded as a gotcha with its workaround.

## Routing and the Skill Advisor

The advisor brief returned to Pi. Skill keywords were corrected and the design hub got a compiled routing table.

#### Pi's Skill Brief Is Back <a id="c-pis-skill-brief-is-back"></a>

- Since the source root moved, every Pi prompt lost its skill suggestion.
- It failed open in about two milliseconds.
- The warm path probed the old root name and found nothing.
- It now checks both names.
- It takes every part from the same found root.
- So a half-migrated checkout cannot mix old and new paths.
- A recommendation that rotates mid-session reaches you again.
- That is because the dedup receipt now keys on the whole delivery instead of half of it.

#### Prompts Reach the Right Skill <a id="c-prompts-reach-the-right-skill"></a>

- A skill that answers judgment questions carried the bare word "run" among its keywords.
- A resume prompt about an overnight run reached it instead of the deep-loop skill.
- The keyword is gone.
- The derived topics were regenerated.
- The routing baselines were re-captured against the corrected scoring.

#### Design Requests Route From a Compiled Table <a id="c-design-requests-route-from-a-compiled-table"></a>

- The design hub became the seventh hub whose routing runs from a compiled decision table.
- That table is a build-time artifact derived from the registry of its four modes.
- It is verified before it ships.
- The compiled front door keeps an off switch and a legacy fallback.
- So a bad build cannot strand a design request.

## Documentation as a System

Documentation changed with them. Release notes, playbook prompts and the always-loaded rules all changed.

#### Release Notes Read Like a Story <a id="c-release-notes-read-like-a-story"></a>

- The changelog workflow now writes the narrative format this file follows.
- A small release reads as a summary, a glance list and an upgrade note.
- A large one opens with why it matters.
- It names its sections for the domain they change.
- It closes with what you must do.
- The voice rules are enforced while it writes.
- File inventories and test metrics stay out by default.

#### Playbook Prompts Cannot Drift <a id="c-playbook-prompts-cannot-drift"></a>

- A playbook scenario could say one prompt in its contract and another in its table.
- It could pass the validator clean.
- The validator now compares the copies.
- It warns at the line where they disagree.
- Formatting differences are ignored.
- That is because an operator types the words and not the styling.

#### Rules Stop Contradicting Each Other <a id="c-rules-stop-contradicting-each-other"></a>

- The always-loaded guidance and the prompt skill were written before the current vendor prompting guides.
- A literal model meets a contradiction in them as a reason to stop early.
- That is gone.
- Questions are asked once.
- They are asked before the work the answer would change.
- A model that a rule stops names the file and quotes the line that stopped it.
- The pause before a yes now covers irreversible work and installs instead of everything.
- The prompt skill picked up the techniques both vendors document.

#### Old Notes Grouped by Generation <a id="c-old-notes-grouped-by-generation"></a>

- The v1 release notes moved into `.skilled/changelog/system-spec-kit/v1+/`, byte-identical.
- So the changelog folder shows its generations instead of one mixed pile.
- The README link follows the move.

## Upgrade Notes

Upgrading from v3.x? A v3 checkout tracks `specs` as a link to `.opencode/specs`. So the link goes first. `rm -f` never removes a real folder.

#### Before You Start <a id="c-before-you-start"></a>

1. If your packets still live in `.opencode/specs`, move them first with `rm -f specs && git mv .opencode/specs specs && ln -s ../specs .opencode/specs`.
2. Then run `node .skilled/skills/system-spec-kit/runtime/cli/spec/upgrade-legacy.mjs`. It shows what it would change. It writes nothing until you pass `--apply`.
3. The first section above explains every part of it.

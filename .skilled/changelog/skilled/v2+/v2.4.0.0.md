This release removes a large chunk of old, unused search code. It also fixes 35 bugs found during a thorough code review. The most important fixes address data integrity issues. These include leftover database records after deletions, scores going out of range and search filters that silently did nothing. The release also adds several new capabilities to the memory system.

## Why This Release

The goal is to make the workflow easier to follow and easier to trust.

## What's New at a Glance

- **The unused V1 search pipeline is deleted.** V2 is now the only path a search takes.
- **Stemming and spec-folder filtering are fixed.** Words match on their true roots. A folder filter now narrows the results.
- **Ranking math is repaired.** Errors in result merging, intent-based ranking and weight overrides are fixed.
- **Scores stay in bounds.** Working memory scores are clamped to the 0-1 range. Very large lists no longer crash the scoring math.
- **The search API exposes three more options.** Access history tracking, archived items and search mode selection are now available.
- **Updated memories are findable by their content.** Their search embedding now comes from the full title and content.
- **Deleting a memory cleans up its related records.** Six types of record no longer stay behind.
- **Orphaned chunks and self-loops are caught.** The integrity checker detects leftover chunks. The causal graph rejects an edge from a memory to itself.
- **Evaluation run IDs persist.** A server restart no longer resets them.

## Search and Scoring

#### Dead Search Code Removed

The memory system had two search pipelines. One was the original (V1). The other was a newer replacement (V2). V1 was no longer used. It was still sitting in the codebase as dead code. That included 8 functions that were never called.

&nbsp;

#### Stemming and Folder Filtering Fixed

Stemming reduces a word to its root form for matching. For example, "running" should become "run". The stemmer was producing "runn" and "stopp" instead. It now handles double consonants.

The exact-word search filter was a no-op. A filter by spec folder compared the wrong kind of identifier. So it never actually filtered anything. It now does a proper database lookup.

&nbsp;

#### Fusion and Ranking Math Repaired

When search combined results from multiple query variations, a bonus was applied twice. That technique is called "fusion". Each result now gets the bonus once.

The system adjusts search results based on what it thinks you are trying to do. Examples are "find recent work" versus "find a definition". The time-based component of that adjustment was missing. It is now added.

You can override some scoring weights. The rest should then adjust proportionally, so they still sum to 1.0. They were not adjusting. Now they auto-normalize. Core weights are also normalized after document-type adjustments. The search pipeline stages share one function for resolving scores.

&nbsp;

#### Attention Scores and Large Lists

Working memory scores track what the system is currently "paying attention to". An unchecked boost could push them above 1.0. A decay factor reduces old scores over time. That factor was also applied twice to attention scores. It made them drop too fast. The duplicate is removed.

A function finds the highest score in a list. It used a technique that fails when the list has more than 100,000 items. That is a JavaScript engine limit. A simple loop replaces it.

&nbsp;

#### Search Options and a Tunable Threshold

All three search parameters existed internally before this release. They were hidden from the tool interface. A function detects "interfering" memories, ones too similar to each other. It now accepts a custom similarity threshold instead of a fixed value.

&nbsp;

#### Smarter Embeddings on Update and Search

Updating a memory used to generate its search embedding from the title alone.

The embedding is also cached during search. The system computes a mathematical representation of your query for similarity search. It now reuses that computation instead of doing it twice. That applies when constitutional memories are involved. These are always-present rules.

## Data Integrity

#### Deletion Leaves Nothing Behind

Before this release, deleting a memory left records behind. These were graph snapshots, community assignments, summaries, linked entities, causal edges and search index entries. Bulk deletions now also clear the cache.

&nbsp;

#### Orphaned Chunks and Self-Loops Caught

When a parent memory was deleted, its chunks remained in the database. Chunks are smaller pieces stored for search. There was no way to find or clean them. The integrity checker can now optionally remove them too.

The causal graph tracks how memories relate to each other. It could create an edge from a memory to itself. That edge is meaningless. Orphaned causal edges are now cleaned up as well.

&nbsp;

#### A Stronger Deduplication Hash

Session deduplication used a 64-bit hash. That hash has a small but real chance of collisions. A collision is two different items producing the same hash. The hash is now 128-bit.

---

## Evaluation and Server Upkeep

#### Evaluation Runs Keep Their IDs

A counter assigns IDs to evaluation runs. It now reads the last-used ID from the database on startup. Evaluation reporting also takes a configurable search limit. Completed evaluation records can now be updated.

&nbsp;

#### Smaller Repairs Across the Server

- **Input checks.** Graph traversal depth and argument parsing both get input validation.
- **Save errors.** Save validation returns better error codes.
- **Exit handlers.** Access tracking cleans up its exit handlers properly.
- **Graph communities.** Change detection for graph communities is better.
- **Pipeline metadata.** The search pipeline passes metadata between its stages. The constitutional count passes through to the filter stage.

---

## Upgrade Notes

No upgrade needed. The `SPECKIT_PIPELINE_V2` environment variable is still accepted. It is now ignored. That variable was the feature flag that toggled between the two pipelines.

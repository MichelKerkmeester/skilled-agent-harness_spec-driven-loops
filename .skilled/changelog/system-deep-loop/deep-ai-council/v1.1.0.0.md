This is the first major iteration of `deep-ai-council` after its initial v1.0.0.0 release. It adds a dedicated graph projection and the operator coverage around it. It also adds fixture-driven value comparisons. It adds a runnable local test gate. It adds skill-surface links for the catalog and replay helper.

> Spec folder: `.opencode/specs/skilled-agent-orchestration/101-deep-multi-ai-council-skill`

Child folders: `.opencode/specs/skilled-agent-orchestration/101-deep-multi-ai-council-skill/{003-deep-ai-council-graph-support, 004-deep-ai-council-playbook-graph-coverage, 005-deep-ai-council-fixups-and-graph-value-scenarios, 006-council-graph-value-scenario-automation, 007-council-infrastructure-hardening, 008-council-surface-polish}` (Level 1-3 across the six phases).

## Why This Release

The work is additive. Seven phases land in `101` as child packets. Runtime code and authoritative artifact contracts stay unchanged.

## What's New at a Glance

- **Council deliberation has its own graph tool family.** Four MCP tools expose upsert, query, status and convergence. They sit apart from the research and review graph family.
- **The operator playbook adds graph coverage and comparisons.** Its scenarios cover graph behavior. They also cover the value of working with graph support.
- **Value comparisons measure read savings and correctness.** Speed-focused scenarios show one kind of value. Safety- or structure-focused scenarios show another.
- **Council testing has a shared matrix and a local wrapper.** One entry point runs vitest. The other adds sk-doc and strict parent-spec validation.
- **The skill entry point links the catalog and replay helper.** The catalog mirrors the playbook. The helper emits a graph payload from council state artifacts.

## Council Graph

#### Council Deliberation as a Graph

Phase 003 adds a derived SQLite projection. It indexes council deliberation as graph rows. Four MCP tools expose the projection: `council_graph_upsert`, `council_graph_query`, `council_graph_status` and `council_graph_convergence`. They form a separate family from the research and review `deep_loop_graph_*` tools.

The handlers expose these entrypoints with input validation. They also shape responses to be prompt-safe. The decision record for the dedicated derived council graph documents the choice. The choice was a dedicated projection over reuse of the deep-loop graph.

Eight node kinds cover `SESSION`, `ROUND`, `SEAT`, `CLAIM`, `EVIDENCE`, `DISAGREEMENT`, `DECISION` and `RECOMMENDATION`. Ten relation kinds are `PARTICIPATES_IN`, `PROPOSES`, `SUPPORTS`, `CONTRADICTS`, `DERIVES_FROM`, `AGREES_WITH`, `RESOLVES`, `ESCALATES`, `EVIDENCE_FOR` and `RECOMMENDS`. Together they cover the full council deliberation lifecycle.

&nbsp;

#### Bounded Queries and Convergence

The query surface has five modes: `unresolved_disagreements`, `evidence_chain`, `decision_support`, `convergence_blockers` and `hot_nodes`. Convergence returns one of `STOP_ALLOWED`, `CONTINUE` or `STOP_BLOCKED`. Query results have bounded outputs and prompt-safe metadata.

&nbsp;

#### Safe Updates and Replay

Graph upserts use strict-schema validation. They are idempotent and reject self-loop edges. Empty input counts as explicit no-op success. Before serialization, arbitrary metadata is reduced to an allowlist of scalar fields.

Graph rows can be deleted within `(specFolder, sessionId)`. They can be rebuilt from `ai-council/**` artifacts without changing those artifacts. The artifacts remain authoritative.

## Operator Playbook

#### Scenarios Cover Graph Behavior

The manual testing playbook grows from 18 to 32 scenarios across 9 categories. Phase 004 adds eight functional integration scenarios. They match the shipped MCP surface one-to-one. They cover idempotent upsert with self-loop rejection, empty-input no-op and hostile-metadata redaction. They also cover the five query modes, the three convergence buckets and recovery payload. The remaining two are derived-projection replay and tool-family separation.

&nbsp;

#### Compare Graph and No Graph

Phase 005 adds six value-comparison scenarios. They contrast the no-graph operator baseline with the graph workflow. The six are unresolved-disagreement triage, decision provenance audit and convergence safety under critical disagreement. They also cover stalled-council blocker ranking, hot-topic discovery and mid-run interruption recovery. Under critical disagreement, the graph blocks a stop. The naive two-of-three baseline would allow that stop.

Phase 005 also includes six fix-ups. It repairs two pre-existing vitest failures: the Claude translated-frontmatter parity assertion and the stale `persist-artifacts` `HELPER_PATH`.

&nbsp;

#### Measured Value Comparisons

Phase 006 turns the value-comparison scenarios into a fixture-driven vitest. Before, they were contract-only documents. Speed-driven scenarios show 7×-13× fewer file reads. Safety-driven `DAC-029` and structure-driven `DAC-032` scenarios show their value through correctness rather than read count.

Each test opens a fresh in-memory SQLite DB. It seeds the graph through the same upsert handler the runtime uses. Then it runs the no-graph baseline (`fs.readdirSync` + grep predicates). It runs the with-graph workflow through MCP handler calls. It then asserts answer equivalence. Each test also seeds a synthetic artifact tree. Temp directories clean up between tests for isolation.

Each run writes measured baseline-versus-graph ratios to `council-graph-value-report.json`. Shared seed-data JSON feeds both vitest and the operator seeder, `scripts/seed-council-value-fixture.cjs`.

Inline normalization comments in `tests/fixtures/council-value/seed-helpers.ts` explain why the `DAC-030` and `DAC-032` fixture-side answers come from grouped runtime responses.

## Test and Skill Surface

#### One Matrix, Two Entry Points

With Phase 007, the council vitest matrix is now one command. `npm run --prefix .opencode/skills/system-spec-kit/mcp-server test:council` runs it with vitest only. The standalone bash runner at `.opencode/skills/system-spec-kit/scripts/test-council-matrix.sh` wraps that matrix. It adds sk-doc validation and strict parent spec validation.

The test gate is local-only. It does not use GitHub Actions. No new top-level commands ship in this release.

&nbsp;

#### Catalog and Replay Helper

The 32-entry feature catalog at `.opencode/skills/deep-loop-workflows/deep-ai-council/feature-catalog/` mirrors the playbook one-to-one. It replaces the previous `No feature catalog exists yet` placeholder. A reverse-anchor meta-test checks that every playbook vitest file and test-name reference resolves to a real test. So renaming a test name surfaces the need to update the playbook.

The replay helper reads `ai-council-state.jsonl` and emits a `council_graph_upsert` payload. Run it with `node .opencode/skills/deep-loop-workflows/deep-ai-council/scripts/replay-graph-from-artifacts.cjs --spec-folder <path> --session-id <id> [--dry-run]` for operator-piped MCP replay.

&nbsp;

#### Skill Resources and Parity

Phase 008 surfaces the new artifacts through the skill entry point. It also includes this changelog. `SKILL.md` now references `feature-catalog/` and `scripts/replay-graph-from-artifacts.cjs` in its Resource Domains section. Smoke coverage exercises the replay helper end-to-end on a synthetic JSONL fixture. It also checks the bash runner's shape.

The Codex TOML runtime mirror's name and description prose now have parity assertions. These sit alongside the existing sandbox and permissions checks. The `test:council` npm script grew to ten vitest files.

## Upgrade Notes

No migration is required. The council graph is a derived projection. So existing `ai-council/` artifacts remain authoritative and replayable. Callers already using `@deep-ai-council` need no changes. The agent body and runtime mirrors are stable.

External tooling that counts playbook entries should update its counters. If a downstream consumer depends on the literal `No feature catalog exists yet` placeholder in playbook §17, switch to the real `feature-catalog/NN--<category>/NN-<slug>.md` paths indexed there.

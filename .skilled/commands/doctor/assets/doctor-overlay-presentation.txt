# /doctor:overlay Presentation Contract

This file is the single source of truth for user-facing presentation in `/doctor:overlay <target>`. It owns every line the operator reads, from the argument failure to the next-step text. The command router owns target resolution and asset loading. The workflow YAML owns execution behavior.

## 1. Argument Failure

Every argument failure happens before any workflow YAML loads. It prints the wording below with the bracketed parts filled in, then ends with the status line. Nothing is read and nothing is changed.

| Situation | Wording |
|-----------|---------|
| The first token is not a target | `Unknown target: [target]` then `/doctor:overlay runs status. Try: /doctor:overlay menu` then `STATUS=FAIL ERROR="unknown_target"` |
| A flag no target accepts | `Unknown argument: [argument]` then one line per target naming the flags it accepts, in the order of the route manifest display below, then `STATUS=FAIL ERROR="unknown_argument"` |
| A flag another target owns | `Argument '[argument]' is not valid for target '[target]'. Did you mean /doctor:overlay [suggested-target] [argument]?` then `STATUS=FAIL ERROR="cross_target_flag"` |
| A value flag given without its value, such as `--root` or `--capture` at the end of the line | `Missing value: [argument] needs [a directory for --root, the destination path a status line named for --capture, the vendored file or folder to bring under an overlay for --adopt, the upstream checkout for --upstream, a commit for --to, a run id for --rollback]` then `Try: [the accepted invocation for the bound target]` then `STATUS=FAIL ERROR="missing_argument"` |
| `repin` without `--rollback`, and without `--upstream` or `--to` | `A re-pin needs both --upstream <dir> and --to <commit>.` then `Try: /doctor:overlay repin --upstream <dir> --to <commit> [--root <dir>]` then `STATUS=FAIL ERROR="missing_argument"` |
| `--rollback` given with `--upstream` or `--to` | `--rollback restores one earlier run and takes no --upstream or --to.` then `Try: /doctor:overlay repin --rollback <run-id> [--root <dir>]` then `STATUS=FAIL ERROR="conflicting_arguments"` |
| `--capture` given with `--adopt` or `--relayout`, or `--adopt` given with `--relayout` | `--capture saves a live edit, --adopt adds a new entry and --relayout moves overlay sources. Give one of them.` then `Try: /doctor:overlay apply [--root <dir>] [--capture <path> | --adopt <path> | --relayout]` then `STATUS=FAIL ERROR="conflicting_arguments"` |
| A target bound with a second positional, such as `status foo` | `Only one target may be bound.` then `Try: [the accepted invocation for the bound target]` then `STATUS=FAIL ERROR="too_many_arguments"` |
| The engine prints its usage block and exits 2 | `USAGE: [the engine's first usage line]` then the rest of the block. The workflow only ever runs the documented calls, so this is the engine's own contract rather than a route the operator reaches |

The flags each target accepts, for the unknown-argument wording:

| Target | Accepts |
|--------|---------|
| `status` | `--json`, `--audit` and `--root <dir>` |
| `apply` | `--root <dir>`, `--capture <path>`, `--adopt <path>` and `--relayout` |
| `repin` | `--root <dir>`, `--upstream <dir>`, `--to <commit>` and `--rollback <run-id>` |

The accepted invocation for each target, for the `Try:` lines:

| Target | Invocation |
|--------|------------|
| `status` | `/doctor:overlay status [--json] [--audit] [--root <dir>]` |
| `apply` | `/doctor:overlay apply [--root <dir>] [--capture <path> | --adopt <path> | --relayout]` |
| `repin` | `/doctor:overlay repin --upstream <dir> --to <commit> [--root <dir>]`, or `/doctor:overlay repin --rollback <run-id> [--root <dir>]` |

## 2. Startup Presentation

This command is always interactive and has no `:auto` mode. With no target, `status` runs because it only reads, so a bare invocation needs no answer. The menu below appears for any menu word in the router's argument table. Ask it once, then wait.

```text
What do you want to do?

1) status
2) apply
3) repin
X) Cancel
```

Accepted answers:

| Answer | Result | Meaning |
|--------|--------|---------|
| `1` | target = `status` | Report every overlay destination that is not in sync, and change nothing |
| `2` | target = `apply` | Show the status report as the plan, then apply the overlays only on yes |
| `3` | target = `repin` | Ask once for the upstream checkout and the commit, stage the re-pin as the plan, then re-pin only on yes |
| `X`, empty, `cancel` | `STATUS=CANCELLED ACTION=cancelled` | Stop. Nothing changes |

On any other response, re-emit the menu once. On a second invalid response, return `STATUS=FAIL ERROR="unknown_selection"`.

Answer `3` asks one question before the workflow loads: `Upstream checkout and commit? [<dir> <commit>]`. The two values are the ones `--upstream` and `--to` carry. An empty answer or `cancel` ends with `STATUS=CANCELLED ACTION=cancelled`, and an answer without both values gets the missing-argument wording above.

Valid targets: status, apply, repin

### Route Manifest Display

Render this table for any menu word. Values mirror `_routes.yaml`.

| Target | Workflow | Mutation Class | One-Line Purpose |
|--------|----------|----------------|------------------|
| `status` | `doctor-overlay-status.yaml` | read-only | Name each overlay destination that is not in sync, with the engine's fix for it |
| `apply` | `doctor-overlay-apply.yaml` | mutates | Put the overlays back into the vendored tree, capture one live edit, adopt one unowned path, or move overlay sources onto their layout paths, after one yes |
| `repin` | `doctor-overlay-repin.yaml` | mutates | Move the vendored tree to a newer upstream commit over a staged plan after one yes, or roll one re-pin back |

## 3. Status Report

The engine prints one line per destination that is not in sync. Each line names the state and the destination. It then names the overlay source and the fix the engine suggests. Quote the lines rather than paraphrasing them.

```text
Overlay status: [the root the engine read]

[state] [destination]  ([overlay: <folder>/<source> | layout link | remove-root row: <id>])  fix: [the engine's fix]
...
in-sync=[n] overlay-edited=[n] live-edited=[n] both-changed=[n] upstream-moved=[n]
MISS     [one line per check that failed, when any did]
STALE    root-file [path]: [the engine's line about the pin, one per stale root file]
LAYOUT   [overlay]: [field] [from] belongs at [to]; run [the engine command] apply --relayout
AUDIT    [kind] [path], with --audit only
audit=[n], with --audit only
checked=[n] ok=[n] miss=[n]
RESULT: [PASSED|FAILED]
```

What each state means, and who acts on it:

| State | Meaning | Fix |
|-------|---------|-----|
| `in-sync` | The destination holds what its overlay would write | None, and the engine prints no line for it |
| `overlay-edited` | The overlay source changed, or a layout link is missing, so the destination is behind | `/doctor:overlay apply` |
| `live-edited` | Someone edited the destination itself, and the overlay source does not have that edit yet. A path under a skill-root entry's `remove` list is never `live-edited`: it is `overlay-edited` and `apply` deletes it | `/doctor:overlay apply --capture <path>` |
| `both-changed` | The overlay source and the destination both changed since the last apply | A person resolves the two, then reruns `/doctor:overlay status` |
| `upstream-moved` | A re-pin brought in an upstream change to a file an overlay owns | A person resolves the overlay against the new upstream, then reruns `/doctor:overlay status` |

The `fix:` text the engine prints names the engine command itself. Show it as printed, and name the matching `/doctor:overlay` form from the table beside it.

### Status Lines Beyond The Destinations

The engine prints three more kinds of line after the counts, and the report tells them apart:

| Line | When it prints | What it means | Status |
|------|----------------|---------------|--------|
| `STALE` | An upstream file named in a `repin.rootFiles` overlay changed since that overlay was pinned | A re-pin never copies a root file, so between re-pins this comparison is the only place the drift shows. Rebase the overlay onto the new upstream bytes, then set its `pinnedSha256` to theirs | fails the status |
| `LAYOUT` | An overlay source sits off the layout path its destination maps to, such as a copy kept under `<overlay folder>/.skilled/skills/...` | The copy still applies, so the tree is not broken and nothing is lost. `/doctor:overlay apply --relayout` moves it to the same path with the leading dot dropped and points the manifest there | does not fail the status |
| `AUDIT` | Only with `--audit`. A vendored path that no overlay owns and no `generated` glob matches is `differs` from upstream at the pin, `missing` from the tree while upstream has it, or `extra` in the tree while upstream never had it | Nothing else reports a path like this, so the drift would otherwise go unseen until a re-pin or a strict write refused it | fails the status |

`AUDIT    skipped: no upstream checkout at the pin` means the comparison could not run on this machine, because the manifest names no checkout that holds the pinned commit. Show it as printed and treat the audit as not run rather than as clean.

With `--json`, print the engine's JSON and nothing around it. The JSON carries the state counts and one entry per destination not in sync, beside the full check, the stale root files, the off-layout sources, and, with `--audit`, the audit findings.

### Status Summary

```text
DOCTOR DIAGNOSTIC RESULT
Target: status
Status: [OK|FINDINGS|ERROR]
Mutation class: read-only
Scope: [the root the engine read]
Evidence: [the engine's state counts line] / [the engine's checked line] / [the engine's audit count, with --audit only]
Recommendation: [the fix for each line not in sync, or none]
STATUS=[status]
```

Statuses this route prints, each on its own line so a workflow never has to compose one:

```text
STATUS=OK
STATUS=FINDINGS
STATUS=ERROR ERROR="[message]"
```

## 4. Apply Plan and Approval

### Setup

Render this compact panel after target resolution and before the plan, when the target or flags were non-trivial.

```text
DOCTOR ROUTE SETUP
Target: apply
Workflow: .skilled/commands/doctor/assets/doctor-overlay-apply.yaml
Mutation class: mutates
Execution mode: INTERACTIVE
Root: [the vendored tree the run reads and writes]
Capture: [the --capture path, or none]
Adopt: [the --adopt path, or none]
Presentation: .skilled/commands/doctor/assets/doctor-overlay-presentation.txt
Next: run the status report, which writes nothing
```

### The Plan The Operator Approves

The engine has no plan mode, so the plan is the status report the same run just printed. Every `overlay-edited` line is a destination the apply rewrites or a layout link it restores. After those writes, the manifest's regenerate steps rebuild what they own and its verify steps check the result.

```text
OVERLAY APPLY PLAN
Root: [the vendored tree]
Overlay folder: [the folder the engine reads, from .skilled-overlays.json or the default skilled-overlays/]
Will apply: [one line per overlay-edited line the report printed, in its order]
Checks that failed: [one line per MISS line, or none]
Then: the manifest's regenerate steps run, then its verify steps
Lock: the engine holds [overlay folder]/.build-lock for the whole run

Apply these overlays now? [yes/no]
```

The report on screen is the report the question covers. The engine classifies every destination again under its own lock before the first write. A destination that became a conflict since the report makes the engine refuse, and in that case it writes nothing.

### When The Run Asks Nothing

| Report | What the run shows | Status |
|--------|--------------------|--------|
| `RESULT: PASSED` | The unchanged result. Nothing is out of sync, so there is nothing to apply | `STATUS=OK` |
| Any `live-edited` line | Each such line with its capture command. A plain apply refuses while one is there, so capture each one first | `STATUS=FAIL ERROR="live_edit_first"` |
| Any `both-changed` or `upstream-moved` line | Each such line with the engine's fix. A person resolves it, and the engine writes nothing until then | `STATUS=FAIL ERROR="needs_resolution"` |
| No line at all, but `RESULT: FAILED` | Each `MISS` line. No destination is behind, so an apply has nothing to write | `STATUS=FAIL ERROR="check_failed"` |

### The Apply Question

`Apply these overlays now? [yes/no]` covers the whole write: every line under `Will apply:` plus the regenerate and verify steps. Any answer other than yes counts as no. Print the cancelled result and write nothing.

## 5. Capture Plan and Approval

With `--capture <path>`, the plan is the one report line whose destination is that path.

```text
OVERLAY CAPTURE PLAN
Root: [the vendored tree]
Destination: [the path]
Report line: [the live-edited line the status report printed for it]
Will write: the overlay source that line names, and the engine's record of what it last applied

Capture this live edit now? [yes/no]
```

| Report line for the path | What the run shows | Status |
|--------------------------|--------------------|--------|
| `live-edited` | The capture plan and the capture question | asks |
| No line names the path | `Nothing to capture: [path] has no line in the status report.` The path is either in sync or not an overlay destination, and nothing is written | `STATUS=OK` |
| Any other state | The line with the engine's fix. Capture moves only a live edit | `STATUS=FAIL ERROR="not_live_edited"` |

`Capture this live edit now? [yes/no]` covers the one overlay source and the engine's record. Any answer other than yes counts as no. Print the cancelled result and write nothing.

## 6. Adopt Plan and Approval

With `--adopt <path>`, the run brings one vendored file or folder that no overlay owns under a new manifest entry, then applies. The path sits under `.skilled`, under a runtime folder the manifest's `repin` block names, or is a root file named in `repin.rootFiles`. The plan is the status report plus that path.

```text
OVERLAY ADOPT PLAN
Root: [the vendored tree]
Path: [the --adopt path, relative to the tree]
Will copy: the path into [overlay folder]/[the same path without its leading dot], unless that copy is what already exists
Will append: one entry to [overlay folder]/overlay-manifest.json, a file entry for a file and a directory entry for a folder
Pinned: an upstream file is pinned to upstream's bytes at the manifest's pin, read from the checkout pin.checkout names
Will also apply: [one line per overlay-edited line the report printed, or none]
Lock: the engine holds [overlay folder]/.build-lock for the whole run

Adopt this path now? [yes/no]
```

| Report | What the run shows | Status |
|--------|--------------------|--------|
| In sync, or only `overlay-edited` lines | The adopt plan and the adopt question | asks |
| Any `live-edited`, `both-changed` or `upstream-moved` line | Each such line with its fix. The engine appends the entry first and applies after, and that apply would be refused | `STATUS=FAIL ERROR="needs_resolution"` |

`Adopt this path now? [yes/no]` covers the copy into the overlay folder, the new manifest entry and the apply that follows. Any answer other than yes counts as no. Print the cancelled result and write nothing.

### Refusals Before Any Write

The engine prints one `refuse:` line and exits 2. Nothing was written.

| The engine refuses because | Fix |
|----------------------------|-----|
| The path is not under a vendored root and is not named in `repin.rootFiles` | The file is the project's own and needs no overlay. For an upstream root file, add its name to `repin.rootFiles` in the manifest first |
| The path is on the manifest's `generated` list | Change what the file is generated from, then rerun its generator |
| The path overlaps an existing overlay | That entry already owns it. Edit the entry's source, or its `replace` list for a skill-root entry |
| Both the path and its overlay copy exist | Keep one of the two, then rerun |
| Nothing exists at the path or at its overlay copy | Create the overlay copy the message names, then rerun |
| A file is a protected name | A `.env` file is never read. A token-named file is adopted only when it is source or prose: `.md`, `.css`, `.ts`, `.js`, `.cjs`, `.mjs` or `.svelte` |
| The upstream checkout cannot be read | Run the adopt on a machine that has the checkout `pin.checkout` names, with the pinned commit fetched |
| Upstream ships files under the folder | Adopt each upstream file on its own. A directory entry would replace the whole upstream folder |

### Strict Writes

Three keys in `overlay-manifest.json` belong to the vendoring project. All three are optional, and a tree without them behaves as it did before they existed.

| Key | Value | What it does |
|-----|-------|--------------|
| `strictWrites` | `true` or `false`, off when absent | When on, the engine's `--guard` also refuses a write under a vendored root that no overlay owns, so the `overlay-guard` hook stops it before it is written. A new file is refused with the overlay path to create, and an edit to an upstream file with its `--adopt` command. `overlay-engine.cjs pre-commit` then refuses a staged change of the same kind, for a project to call from its own commit hook |
| `generated` | A list of globs, where `*` stays inside one path segment and `**` crosses segments | Paths a project's generators write, such as runtime mirrors and hook settings. The guard, `--adopt` and `pre-commit` leave them alone |
| `repin.rootFiles` | A list of root files the project carries from upstream, such as `REPO RULES.md` | A re-pin never copies a root file. Each listed file that upstream changed gets its own `root-file` line in the re-pin report, and `--adopt` and the strict guard treat it as a vendored path |

`pre-commit` skips its check while the staged manifest moves the pin, because that commit is a re-pin and the re-pin ran its own drift scan. A staged file that equals upstream's bytes at the pin passes. Skilled's own repository vendors nothing and has no manifest, so none of this runs there.

## 7. Relayout Plan and Approval

The engine has no plan mode for `apply --relayout`, so the plan is the `LAYOUT` lines the same run's status report printed. Each one names the overlay, the manifest field, the path the copy sits at now and the path it belongs at. Every move stays inside the overlay folder: the copy keeps the same path with the leading dot dropped, and the destination the overlay writes is untouched.

```text
OVERLAY RELAYOUT PLAN
Root: [the vendored tree]
Overlay folder: [the folder the engine reads, from .skilled-overlays.json or the default skilled-overlays/]
Will move: [one LAYOUT line per source off its layout, restated as from -> to]
Backup: [overlay folder]/relayout-runs/[stamp]/, holding every copy the run moves and the manifest, written before the first move
Will rewrite: the manifest's source, fragment and base fields that name a moved copy, and the layout-link targets that reach one
Then: /doctor:overlay apply, run in this same run, so the destinations catch up with the moved sources

Move these sources now? [yes/no]
```

| Report | What the run shows | Status |
|--------|--------------------|--------|
| No `LAYOUT` line | The nothing-to-move result. Every source already sits on its layout path | `STATUS=OK` |
| At least one `LAYOUT` line, and nothing else outstanding | The relayout plan and the relayout question | asks |
| Any `live-edited`, `both-changed` or `upstream-moved` line | Each such line with its fix, beside the `LAYOUT` lines. The apply that follows the move would be refused until it is settled | `STATUS=FAIL ERROR="needs_resolution"` |
| A `MISS` line or a `STALE` line, and no line above | The relayout plan and the relayout question, with each such line shown beside the `LAYOUT` lines. The engine moves the sources and still exits 0, so the run goes on and ends on that line | asks |

`Move these sources now? [yes/no]` covers every move, the backup, the manifest rewrite and the layout-link retargeting. Any answer other than yes counts as no. Print the cancelled result and write nothing.

The run prints one `skipped` line per file the backup did not copy, because the read rule protects it, and one `relinked <path> -> <target>` line per layout link it rewrote. A `skipped` line for a file inside a moved folder comes before the `backup` line, and that file still moves with its folder. A `relinked` line comes after the last `moved` line, and the manifest records the same target.

### Refusals Before Any Write

The engine prints one `refuse:` line and exits 2. Nothing was written.

| The engine refuses because | Fix |
|----------------------------|-----|
| The target path already exists in the overlay folder | Keep one of the two copies, put the bytes you want in it, then rerun |
| A copy the manifest names is missing | Point that field at the copy that exists, or create the copy the manifest names, then rerun |
| Two copies belong at one path, or one copy is claimed by two fields | Settle the manifest so one copy owns one path, then rerun |
| A field or a link no longer holds the path the run planned against | Nothing moved. The manifest changed under the run, or two entries claim one copy. Fix the field or the link the `refuse:` line names, then rerun |
| Two copies sit one inside the other | Move the outer copy in its own run, then the inner one |
| The overlay lock is held | Wait for the other run to end, then remove the lock file the message names by hand. A lock whose owner has ended is taken over by the next run with a `note:` line instead of refused |

## 8. Repin Plan and Approval

### Setup

Render this compact panel after target resolution and before the plan.

```text
DOCTOR ROUTE SETUP
Target: repin
Workflow: .skilled/commands/doctor/assets/doctor-overlay-repin.yaml
Mutation class: mutates
Execution mode: INTERACTIVE
Root: [the vendored tree the run reads and writes]
Upstream: [the --upstream checkout, or none for a rollback]
To: [the --to commit, or none for a rollback]
Rollback: [the --rollback run id, or none]
Presentation: .skilled/commands/doctor/assets/doctor-overlay-presentation.txt
Next: [stage the re-pin in a temporary folder, which leaves the live tree untouched | read the run folder, which writes nothing]
```

### The Plan The Operator Approves

The plan is the stage report. The engine runs the re-pin on a copy in a fresh temporary folder, and the live tree is not touched. The copy has no project install, so the manifest's regenerate and verify steps run only in the live run, and the stage says how many it skipped. Quote the engine's lines rather than paraphrasing them.

```text
OVERLAY REPIN PLAN
Root: [the vendored tree]
Upstream: [the --upstream checkout]
To: [the --to commit]
Stage: [the temporary folder the plan ran in]
Copy: [the engine's copy <n> paths, delete <n> paths line]
Now equal to upstream: [one equals-upstream <overlay-id> line per overlay, or none]
Not copied: [the engine's not-copied lines, upstream changes the re-pin leaves for the operator, or none]
Root files: [the engine's root-file lines, one per file in repin.rootFiles that upstream changed, or none]
Skipped on the copy: [the engine's stage skipped line, or none]
Stage result: RESULT: STAGED
Then: the live run backs up every path it touches into [overlay folder]/repin-runs/<run-id>/, copies, sets the pin, applies the overlays and runs the full check
Lock: the engine holds [overlay folder]/.build-lock for the whole run

Re-pin this tree to [commit] now? [yes/no]
```

A `root-file` line names a root file upstream changed, which no re-pin copies. One that says no overlay owns it is carried over by hand or adopted. One that says to rebase the overlay that owns it is settled in that overlay's source.

An overlay that now equals upstream needs no change to re-pin. Its entry can be dropped from the overlay manifest after the run, and the plan names it so the operator knows.

### When The Run Asks Nothing

| Stage report | What the run shows | Status |
|--------------|--------------------|--------|
| Exit 1 with any `blocked <overlay-id>: <state> <path>` line | Each blocked line. Rebase each blocked overlay onto the new upstream file, then rerun `/doctor:overlay repin --upstream <dir> --to <commit>` | `STATUS=FAIL ERROR="blocked_overlays"` |
| Exit 1 with no `blocked` line, and `RESULT: FAILED` | Each `MISS` line. The full check fails on the staged copy, so the live run would end the same way | `STATUS=FAIL ERROR="stage_check_failed"` |
| Exit 2 | The engine's refusal, with its fix from the refusal table below. Nothing was written | `STATUS=FAIL ERROR="refused"` |

### Refusals Before Any Write

| The engine refuses because | Fix |
|----------------------------|-----|
| The overlay lock is held | Wait for the other run to end, then remove the lock file the message names by hand. A lock whose owner has ended on this host is taken over by the next run, which prints a `note:` line, so this row covers a live owner, another host or a line with no pid |
| A destination is `live-edited`, `both-changed` or `upstream-moved` | Settle it first: `/doctor:overlay apply --capture <path>` for a live edit, or resolve the overlay by hand for the other two, then rerun `/doctor:overlay status` |
| An overlay is refused, shown as `blocked <overlay-id>: refused ...` | Follow the fix the line names, usually adding a token-named file to that entry's `protectedPaths`, then rerun `/doctor:overlay status` |
| An unowned file in the copied roots differs from the old pin, at the path the engine names | That file holds an edit made in place, which the copy would revert. Move the edit into an overlay or upstream, then rerun |
| A commit is missing from `--upstream` | Fetch both the pinned commit and the `--to` commit into that checkout, then rerun |

### The Repin Question

`Re-pin this tree to [commit] now? [yes/no]` covers the whole live run: the backup, the copy and delete counts, the new pin, the apply and the full check. Any answer other than yes counts as no. Print the cancelled result and write nothing.

### The Rollback Question

After a live run fails behind its backup, the engine prints `rollback: node .skilled/commands/doctor/scripts/overlay-engine.cjs repin --rollback <run-id>`. Show that line, then ask a separate question. Nothing is rolled back without its own yes.

```text
REPIN FAILED AFTER ITS BACKUP
Root: [the vendored tree]
Engine: [each line the live run printed, as printed]
Run folder: [overlay folder]/repin-runs/[run-id]/
Rollback: [the rollback line the engine printed]

Roll this re-pin back now? [yes/no]
```

With `--rollback <run-id>` given directly, the plan is what that run folder holds.

```text
OVERLAY REPIN ROLLBACK PLAN
Root: [the vendored tree]
Run folder: [overlay folder]/repin-runs/[run-id]/
Holds: [one line per file the run folder holds]
Will restore: every path that run backed up, byte for byte, and remove the files that run created

Roll this re-pin back now? [yes/no]
```

| Run folder | What the run shows | Status |
|------------|--------------------|--------|
| Present | The rollback plan and the rollback question | asks |
| Missing | `No re-pin run: [overlay folder]/repin-runs/[run-id]/ does not exist.` Nothing is written | `STATUS=FAIL ERROR="unknown_run"` |

`Roll this re-pin back now? [yes/no]` covers only the paths that one run backed up and the files it created. Any answer other than yes counts as no. After a failed re-pin, print the left-in-place result. On the direct path, print the cancelled result. Neither writes anything.

```text
Run folder: [overlay folder]/repin-runs/[run-id]/, kept for a later rollback
Now equal to upstream: [one equals-upstream line per overlay, or none]
Re-read: [the status report's RESULT line and its state counts]
STATUS=OK
```

### Rolled Back

```text
REPIN ROLLED BACK
Root: [the vendored tree]
Run: [run-id]
Engine: [each line the rollback printed]
Re-read: [the status report's RESULT line and its state counts]
STATUS=[OK on the direct path | FAIL ERROR="repin_rolled_back" after a failed re-pin]
```

### Left In Place

```text
REPIN FAILED, NOT ROLLED BACK
Root: [the vendored tree]
Engine: [each line the live run printed]
Changed: the tree is partly moved to [commit], and the run folder keeps its backup
Next: [the rollback line the engine printed]
STATUS=FAIL ERROR="repin_failed"
```

### Cancelled

```text
OVERLAY RUN CANCELLED
Declined: [the apply | the capture of the path | the adoption of the path | the relayout of the overlay folder | the re-pin to the commit | the rollback of the run]
Changed: none
STATUS=CANCELLED ACTION=cancelled
```

### Failure Summary

```text
DOCTOR TARGET FAILED
Target: [status|apply|repin]
Step: [the phase that stopped the run]
Error: [the engine's exit code and its message lines]
Changed: [what the engine reported writing before it stopped, or none]
Next: [the repair, or the accepted invocation]
STATUS=FAIL ERROR="[code]"
```

What each engine exit means for `Changed:`:

| Engine result | Changed |
|---------------|---------|
| Exit 2: a refusal or a failed precondition, such as a held lock | none |
| A relayout, exit 0 with `skipped` lines | The copies the run reported moved. A skipped file was never copied into the backup: one that is a source on its own stayed where it was, and one inside a moved folder went with that folder |
| Exit 1 with `BLOCKED` lines or `changed=0` | none |
| An adopt, exit 1 after its `adopted` line | The overlay copy and the manifest entry were written, and the apply after them was blocked. Name the entry |
| Exit 1 after `regeneration failed` | The overlays were written and the tree is only partly rebuilt. Name each failed step |
| Exit 1 with `MISS     generated:` lines after the changed count | The overlays were written and recorded, and a generator check still fails. Name each check |
| A re-pin stage, any exit | none. The stage writes only its temporary folder |
| A live re-pin, exit 2 with no `rollback:` line | none |
| A live re-pin, exit 1, or exit 2 with a `rollback:` line | The tree is partly moved and the run folder keeps the backup. Name the rollback line |

## 10. Troubleshooting Display

| Situation | Suggested Action |
|-----------|------------------|
| `no overlay manifest at ...` | The tree has no overlay folder yet, or `.skilled-overlays.json` names another one. When the message says no setting file was found, add `.skilled-overlays.json` at the tree root naming the folder that holds `overlay-manifest.json`. Then rerun `/doctor:overlay status` |
| `refusing to inspect a protected path: ...` | That one entry is blocked and every other overlay is still reported. Follow the fix the line names: add the file to that entry's `protectedPaths`, or move a `.env` file out of the overlay. Then rerun `/doctor:overlay status` |
| `not-copied` lines in a re-pin report | Upstream changed these paths, and a re-pin never copies them: they sit under `repin.exclude` or in a top-level file or folder outside the copied roots, such as `AGENTS.md`. Carry over what applies by hand. For the shipped `AGENTS.md` sections, run `/doctor:agents-md` |
| `stage skipped ... regenerate and ... verify step(s)` | Expected. The stage has no project install, so the generators run only in the live re-pin |
| `.skilled-overlays.json` is refused | The setting must name a relative folder inside the tree with forward slashes. Fix the file, then rerun `/doctor:overlay status` |
| `refuse: the overlay lock is held` | Another run holds the lock. Wait for that run to end, then remove the lock file the message names by hand. A lock whose owner has ended on this host is taken over by the next run, which prints a `note:` line, so this row covers a live owner, another host or a line with no pid |
| A `live-edited` line | Run `/doctor:overlay apply --capture <path>` for that path, then `/doctor:overlay apply` |
| A `LAYOUT` line in a status report | Run `/doctor:overlay apply --relayout`, which moves each off-layout source and then applies. The copy still applies while it sits off its layout path |
| A `STALE` line in a status report | Upstream changed a root file a `repin.rootFiles` overlay owns. Rebase the overlay onto the new bytes, then set its `pinnedSha256` to theirs and rerun `/doctor:overlay status` |
| A relayout printed `skipped` for a path | The backup did not copy that file because the read rule protects it. A source on its own stayed where it was, so move it by hand to the path the `LAYOUT` line named. One inside a moved folder already sits on that path, and only the backup lacks it |
| A relayout refused because the target exists | The overlay folder holds both the old copy and the path it belongs at. Keep one of them, then rerun |
| `note: took over the overlay lock of a run that has ended: ...` | The earlier run ended without removing its lock, so this run took it over and carried on. Nothing to do, unless that run is still working under another host |
| `AUDIT    differs <path>` | No overlay owns the path and it no longer matches upstream at the pin. Adopt it with `/doctor:overlay apply --adopt <path>`, or add an overlay that owns it |
| `AUDIT    missing <path>` | Upstream has the file at the pin and the tree lacks it. Restore it from the checkout the manifest names, or take it through a re-pin |
| `AUDIT    extra <path>` | The tree tracks a file upstream never had at the pin. Move it into an overlay, adopt it, or remove it |
| `AUDIT    skipped: no upstream checkout at the pin` | The comparison needs the checkout `pin.checkout` names with the pinned commit fetched. The audit did not run here, so read nothing into its silence |
| The guard refuses a write with `is a vendored file no overlay owns` | The manifest has `strictWrites` on. Run `/doctor:overlay apply --adopt <path>` for that file, then edit its copy in the overlay folder and run `/doctor:overlay apply` |
| The guard refuses a write with `is a new file in the vendored tree` or `is a new file inside overlay` | Create the file at the overlay path the line names. Then run `/doctor:overlay apply --adopt <path>` with the path it names, or `/doctor:overlay apply` when the line says an overlay already holds the folder |
| The guard refuses a file a generator writes | Add a glob for it to the manifest's `generated` list |
| `pre-commit` prints `refuse: staged ...` | Each named path changed under a vendored root outside an overlay. Adopt it, add a generator's output to `generated`, or unstage it |
| `root-file` lines in a re-pin report | Upstream changed a root file named in `repin.rootFiles`, and a re-pin never copies one. Carry the change over by hand or adopt the file, and rebase the overlay when the line says one owns it |
| A `both-changed` line | Compare the overlay source with the destination and settle the content in the overlay source. Then rerun `/doctor:overlay status` |
| An `upstream-moved` line | A re-pin changed a file an overlay owns. Rebase the overlay source onto the new upstream bytes, then rerun `/doctor:overlay status` |
| `regeneration failed` after an apply | The overlays landed but a generator failed. Read the failed step's output, fix it, then rerun `/doctor:overlay apply` |
| The apply question was answered no | Nothing was written. Rerun `/doctor:overlay apply` when the report is acceptable |
| A re-pin stage lists `blocked` overlays | Rebase each one onto the new upstream file, then rerun `/doctor:overlay repin --upstream <dir> --to <commit>` |
| A re-pin refuses on an unowned file | The named file holds an edit made in place. Move it into an overlay or upstream, then rerun |
| A re-pin refuses on a missing commit | Fetch both commits into the `--upstream` checkout, then rerun |
| A live re-pin failed after its backup | Run `/doctor:overlay repin --rollback <run-id>` with the run id the rollback line names, then `/doctor:overlay status` |
| Route manifest parse error | Run `bash .skilled/commands/doctor/scripts/route-validate.sh` |

# /doctor:overlay Presentation Contract

This file is the single source of truth for user-facing presentation in `/doctor:overlay <target>`. It owns every line the operator reads, from the argument failure to the next-step text. The command router owns target resolution and asset loading. The workflow YAML owns execution behavior.

## 1. Argument Failure

Every argument failure happens before any workflow YAML loads. It prints the wording below with the bracketed parts filled in, then ends with the status line. Nothing is read and nothing is changed.

| Situation | Wording |
|-----------|---------|
| The first token is not a target | `Unknown target: [target]` then `/doctor:overlay runs status. Try: /doctor:overlay menu` then `STATUS=FAIL ERROR="unknown_target"` |
| A flag no target accepts | `Unknown argument: [argument]` then one line per target naming the flags it accepts, in the order of the route manifest display below, then `STATUS=FAIL ERROR="unknown_argument"` |
| A flag another target owns | `Argument '[argument]' is not valid for target '[target]'. Did you mean /doctor:overlay [suggested-target] [argument]?` then `STATUS=FAIL ERROR="cross_target_flag"` |
| A value flag given without its value, such as `--root` or `--capture` at the end of the line | `Missing value: [argument] needs [a directory for --root, the destination path a status line named for --capture, the vendored file or folder to bring under an overlay for --adopt, the upstream checkout for --upstream, a commit for --to, a run id for --rollback]` then `Try: [the accepted invocation for the bound target]` then `STATUS=FAIL ERROR="missing_argument"` |
| `repin` without `--rollback`, and without `--upstream` or `--to` | `A re-pin needs both --upstream <dir> and --to <commit>.` then `Try: /doctor:overlay repin --upstream <dir> --to <commit> [--root <dir>]` then `STATUS=FAIL ERROR="missing_argument"` |
| `--rollback` given with `--upstream` or `--to` | `--rollback restores one earlier run and takes no --upstream or --to.` then `Try: /doctor:overlay repin --rollback <run-id> [--root <dir>]` then `STATUS=FAIL ERROR="conflicting_arguments"` |
| `--capture` given with `--adopt` or `--relayout`, or `--adopt` given with `--relayout` | `--capture saves a live edit, --adopt adds a new entry and --relayout moves overlay sources. Give one of them.` then `Try: /doctor:overlay apply [--root <dir>] [--capture <path> | --adopt <path> | --relayout]` then `STATUS=FAIL ERROR="conflicting_arguments"` |
| A target bound with a second positional, such as `status foo` | `Only one target may be bound.` then `Try: [the accepted invocation for the bound target]` then `STATUS=FAIL ERROR="too_many_arguments"` |
| The engine prints its usage block and exits 2 | `USAGE: [the engine's first usage line]` then the rest of the block. The workflow only ever runs the documented calls, so this is the engine's own contract rather than a route the operator reaches |

The flags each target accepts, for the unknown-argument wording:

| Target | Accepts |
|--------|---------|
| `status` | `--json`, `--audit` and `--root <dir>` |
| `apply` | `--root <dir>`, `--capture <path>`, `--adopt <path>` and `--relayout` |
| `repin` | `--root <dir>`, `--upstream <dir>`, `--to <commit>` and `--rollback <run-id>` |

The accepted invocation for each target, for the `Try:` lines:

| Target | Invocation |
|--------|------------|
| `status` | `/doctor:overlay status [--json] [--audit] [--root <dir>]` |
| `apply` | `/doctor:overlay apply [--root <dir>] [--capture <path> | --adopt <path> | --relayout]` |
| `repin` | `/doctor:overlay repin --upstream <dir> --to <commit> [--root <dir>]`, or `/doctor:overlay repin --rollback <run-id> [--root <dir>]` |

## 2. Startup Presentation

This command is always interactive and has no `:auto` mode. With no target, `status` runs because it only reads, so a bare invocation needs no answer. The menu below appears for any menu word in the router's argument table. Ask it once, then wait.

```text
What do you want to do?

1) status
2) apply
3) repin
X) Cancel
```

Accepted answers:

| Answer | Result | Meaning |
|--------|--------|---------|
| `1` | target = `status` | Report every overlay destination that is not in sync, and change nothing |
| `2` | target = `apply` | Show the status report as the plan, then apply the overlays only on yes |
| `3` | target = `repin` | Ask once for the upstream checkout and the commit, stage the re-pin as the plan, then re-pin only on yes |
| `X`, empty, `cancel` | `STATUS=CANCELLED ACTION=cancelled` | Stop. Nothing changes |

On any other response, re-emit the menu once. On a second invalid response, return `STATUS=FAIL ERROR="unknown_selection"`.

Answer `3` asks one question before the workflow loads: `Upstream checkout and commit? [<dir> <commit>]`. The two values are the ones `--upstream` and `--to` carry. An empty answer or `cancel` ends with `STATUS=CANCELLED ACTION=cancelled`, and an answer without both values gets the missing-argument wording above.

Valid targets: status, apply, repin

### Route Manifest Display

Render this table for any menu word. Values mirror `_routes.yaml`.

| Target | Workflow | Mutation Class | One-Line Purpose |
|--------|----------|----------------|------------------|
| `status` | `doctor-overlay-status.yaml` | read-only | Name each overlay destination that is not in sync, with the engine's fix for it |
| `apply` | `doctor-overlay-apply.yaml` | mutates | Put the overlays back into the vendored tree, capture one live edit, adopt one unowned path, or move overlay sources onto their layout paths, after one yes |
| `repin` | `doctor-overlay-repin.yaml` | mutates | Move the vendored tree to a newer upstream commit over a staged plan after one yes, or roll one re-pin back |

## 3. Status Report

The engine prints one line per destination that is not in sync. Each line names the state and the destination. It then names the overlay source and the fix the engine suggests. Quote the lines rather than paraphrasing them.

```text
Overlay status: [the root the engine read]

[state] [destination]  ([overlay: <folder>/<source> | layout link | remove-root row: <id>])  fix: [the engine's fix]
...
in-sync=[n] overlay-edited=[n] live-edited=[n] both-changed=[n] upstream-moved=[n] cannot-apply=[n]
MISS     [one line per check that failed, when any did]
STALE    root-file [path]: [the engine's line about the pin, one per stale root file]
REGEN    pending: [every regenerate step id in the manifest, comma-separated, when an earlier apply did not finish its regeneration]
  an earlier apply did not finish its regeneration, so the next apply reruns these steps
  Next: from [root]: node .skilled/commands/doctor/scripts/overlay-engine.cjs apply
LAYOUT   [overlay]: [field] [from] belongs at [to]; run [the engine command] apply --relayout
LAYOUT   [overlay]: [field] [from] belongs at [to]; change the destination or remove the entry
NOTE     [one line per note: a check the run skipped, a value no record covers, an operation path through an array index, an insert anchor that matched nothing, or unowned upstream paths missing from the tree]
AUDIT    [kind] [path], with --audit only
audit=[n], with --audit only
DOCS     missing-readme [overlay label]/[folder], with --audit only
DOCS     invalid-readme [overlay label]/[folder]/[README.md or README.markdown]: [first blocking error][ (+N more)], with --audit only
DOCS     skipped: [reason], with --audit only
docs=[n], with --audit only
checked=[n] ok=[n] miss=[n]
RESULT: [PASSED|FAILED]
```

The second remedy, `change the destination or remove the entry`, is printed when [to] sits under root/skilled, which relayout refuses because that folder holds no copy.

What each state means, and who acts on it:

| State | Meaning | Fix |
|-------|---------|-----|
| `in-sync` | The destination holds what its overlay would write | None, and the engine prints no line for it |
| `overlay-edited` | The overlay source changed, or a layout link is missing, so the destination is behind | `/doctor:overlay apply` |
| `live-edited` | Someone edited the destination itself, and the overlay source does not have that edit yet. A path under a skill-root entry's `remove` list is never `live-edited`: it is `overlay-edited` and `apply` deletes it | `/doctor:overlay apply --capture <path>` |
| `both-changed` | The overlay source and the destination both changed since the last apply | A person resolves the two, then reruns `/doctor:overlay status` |
| `upstream-moved` | A re-pin brought in an upstream change to a file an overlay owns | A person resolves the overlay against the new upstream, then reruns `/doctor:overlay status` |
| `cannot-apply` | A json-entry overlay's entry set cannot be applied to a destination nobody edited, and the `fix:` text names why | A person changes the entry set or the destination as the fix says, then reruns `/doctor:overlay status` |

The `fix:` text the engine prints names the engine command itself. Show it as printed, and name the matching `/doctor:overlay` form from the table beside it.

### Status Lines Beyond The Destinations

The engine prints six more kinds of line after the counts, and the report tells them apart:

| Line | When it prints | What it means | Status |
|------|----------------|---------------|--------|
| `STALE` | An upstream file named in a `repin.rootFiles` overlay changed since that overlay was pinned | A re-pin never copies a root file, so between re-pins this comparison is the only place the drift shows. It needs the checkout `pin.checkout` names with the pinned commit fetched. Without one the check does not run, and a `NOTE` line says it was skipped. Rebase the overlay onto the new upstream bytes, then set its `pinnedSha256` to theirs | fails the status |
| `REGEN` | An earlier apply wrote and recorded the overlays, then a regenerate step failed, so the state file still marks the regeneration as pending. The line reads `REGEN    pending: <ids>`, naming every `regenerate` step id in the manifest, comma-separated, because the next apply reruns them all. Under it come `an earlier apply did not finish its regeneration, so the next apply reruns these steps` and `Next: from <root>: node .skilled/commands/doctor/scripts/overlay-engine.cjs apply`. A manifest with no `regenerate` steps prints no line | Every destination can be in sync while the rebuild is still owed, so this line is the only sign of it. Fix the step that failed, then run `/doctor:overlay apply`. `status --json` names the same ids in `regeneratePending`, after `staleRootFiles`. The field is always present and holds `[]` when nothing is pending | fails the status |
| `LAYOUT` | An overlay source sits off the layout path its destination maps to, such as a copy kept under `<overlay folder>/skilled/skills/...` that belongs under `<overlay folder>/framework/skills/...` | The copy still applies, so the tree is not broken and nothing is lost. `/doctor:overlay apply --relayout` moves it to its layout path and points the manifest there: a `.skilled/X` destination maps to `framework/X`, and any other destination `X` maps to `root/` plus `X` with its leading dots dropped. Status prints at most 20 of these lines, then one overflow line, in one of three forms, where N is the hidden lines, M the ones relayout can move and B the ones under root/skilled: `LAYOUT   … N more; run node .skilled/commands/doctor/scripts/overlay-engine.cjs apply --relayout` when none is under root/skilled, `LAYOUT   … N more under root/skilled; change the destination or remove the entry` when all are, and `LAYOUT   … N more; run node .skilled/commands/doctor/scripts/overlay-engine.cjs apply --relayout for M, and change the destination or remove the entry for the B under root/skilled` when they mix. Under the overflow line the engine prints an indented `Next:` line in one of three forms. It reads `Next: from <root>: node .skilled/commands/doctor/scripts/overlay-engine.cjs apply --relayout` when a hidden line can move and no move, shown or hidden, sits under root/skilled. It reads `Next: change the destination of each entry under root/skilled in <manifest path>, or remove the entry, then from <root>: node .skilled/commands/doctor/scripts/overlay-engine.cjs apply --relayout` when a hidden line can move and any move, shown or hidden, sits under root/skilled, so it can follow an overflow line that names relayout. It reads `Next: change the destination of each entry under root/skilled, or remove the entry` when no hidden line can move. A LAYOUT line whose [to] sits under root/skilled names `change the destination or remove the entry` instead of the relayout. Relayout refuses every move while any `offLayout` item sits under root/skilled, so fix those entries first and relayout after, even where a line or the overflow names relayout for the rest. `status --json` keeps every move in its `offLayout` array | does not fail the status |
| `NOTE` | The state file is schema version 1, a check was skipped because no checkout at the pin could be read, an operation's path goes through an array index, an insert's `before` or `beforeKey` anchor matches nothing so its items or keys go at the end, an in-sync json-entry destination differs from its entry set applied to the pinned copy (`cross-check`), or unowned upstream paths at the pin are missing from the tree | Each line names its own fix. A `cross-check` line on a file a `regenerate` step writes means the step does not list that file in its `outputs` | does not fail the status |
| `AUDIT` | Only with `--audit`. A vendored path that no overlay owns and no `generated` glob matches is `differs` from upstream at the pin, `missing` from the tree while upstream has it, or `extra` in the tree while upstream never had it | Nothing else reports a path like this, so the drift would otherwise go unseen until a re-pin or a strict write refused it | fails the status |
| `DOCS` | Only with `--audit`. A folder in the overlay folder has neither a `README.md` nor a `README.markdown` (`missing-readme`), or a README there fails sk-doc's validator with a blocking error (`invalid-readme`), and the line names the file it read. Only a regular file counts, so a README that is a link counts as missing, and a folder the walk cannot read is skipped and not counted. The walk skips `repin-runs/` and `relayout-runs/` directly under the overlay folder, any folder whose name starts with a dot, any `node_modules` or `__pycache__` folder and any folder reached through a link | The overlay folder's own documentation is incomplete. Shipping and documentation-only READMEs are both checked, under either name. The line is advisory: show it as a finding to fix, never as a failure, and never let it change the Status line. `docs=[n]` counts the findings | does not fail the status |

`AUDIT    skipped: no upstream checkout at the pin` means the comparison could not run on this machine, because the manifest names no checkout that holds the pinned commit. Show it as printed and treat the audit as not run rather than as clean.

`DOCS     skipped: [reason]` means python3 or sk-doc's validator is missing, so no README was validated. The `missing-readme` lines still print. The skipped line is not a finding and `docs=` does not count it. Show it as printed and treat README validation as not run rather than as clean. The `DOCS` leg reads only the overlay folder, so it still runs when `AUDIT    skipped` printed.

With `--audit` the `DOCS` lines and `docs=` never change `RESULT:` or the exit. A report can end `RESULT: PASSED` with exit 0 and still carry `DOCS` lines, so show them under an OK status too.

With `--json`, print the engine's JSON and nothing around it. The JSON carries the state counts and one entry per destination not in sync, beside the full check, the stale root files, the off-layout sources, the notes under `notes`, and, with `--audit`, the audit findings and a `docs` key with the README counts and the `DOCS` findings, sorted by path.

### Status Summary

```text
DOCTOR DIAGNOSTIC RESULT
Target: status
Status: [OK|FINDINGS|ERROR]
Mutation class: read-only
Scope: [the root the engine read]
Evidence: [the engine's state counts line] / [the engine's checked line] / [the engine's audit count and docs count, with --audit only]
Recommendation: [the fix for each line not in sync, or none]
STATUS=[status]
```

Statuses this route prints, each on its own line so a workflow never has to compose one:

```text
STATUS=OK
STATUS=FINDINGS
STATUS=ERROR ERROR="[message]"
```

## 4. Apply Plan and Approval

### Setup

Render this compact panel after target resolution and before the plan, when the target or flags were non-trivial.

```text
DOCTOR ROUTE SETUP
Target: apply
Workflow: .skilled/commands/doctor/assets/doctor-overlay-apply.yaml
Mutation class: mutates
Execution mode: INTERACTIVE
Root: [the vendored tree the run reads and writes]
Capture: [the --capture path, or none]
Adopt: [the --adopt path, or none]
Presentation: .skilled/commands/doctor/assets/doctor-overlay-presentation.txt
Next: run the status report, which writes nothing
```

### The Plan The Operator Approves

The engine has no plan mode, so the plan is the status report the same run just printed. Every `overlay-edited` line is a destination the apply rewrites or a layout link it restores. After those writes, the manifest's regenerate steps rebuild what they own and its verify steps check the result.

```text
OVERLAY APPLY PLAN
Root: [the vendored tree]
Overlay folder: [the folder the engine reads, from .skilled-overlays.json or the default skilled-overlays/]
Will apply: [one line per overlay-edited line the report printed, in its order, or none when only a REGEN line is outstanding]
Checks that failed: [one line per MISS line, or none]
Stale root files: [one line per STALE line with its fix, or none. An apply does not clear these]
Pending regeneration: [the step ids the REGEN line names, which this apply reruns, or none]
Notes: [the engine's NOTE lines, such as an insert whose anchor the file no longer holds, or none. They do not stop the apply]
Then: the manifest's regenerate steps run, then its verify steps
Lock: the engine holds [overlay folder]/.build-lock for the whole run

Apply these overlays now? [yes/no]
```

The report on screen is the report the question covers. The engine classifies every destination again under its own lock before the first write. A destination that became a conflict since the report makes the engine refuse, and in that case it writes nothing.

A `STALE` line does not stop the apply, and no apply clears it. The plan carries the line, says it stays after the write, and names the fix: rebase that overlay onto the new upstream bytes, then set its `pinnedSha256` to theirs. The status re-read after the write still fails on it.

A `REGEN` line makes the apply worth running even when no destination line printed. The plan names its steps under `Pending regeneration:`, `Will apply:` reads none when nothing else is behind, and the engine reruns every regenerate step, then its verify steps. The status re-read after the write shows whether they finished.

### When The Run Asks Nothing

| Report | What the run shows | Status |
|--------|--------------------|--------|
| `RESULT: PASSED` | The unchanged result. Nothing is out of sync, so there is nothing to apply | `STATUS=OK` |
| Any `live-edited` line | Each such line with its capture command. A plain apply refuses while one is there, so capture each one first | `STATUS=FAIL ERROR="live_edit_first"` |
| Any `both-changed`, `upstream-moved` or `cannot-apply` line | Each such line with the engine's fix. A person resolves it, and the engine writes nothing until then | `STATUS=FAIL ERROR="needs_resolution"` |
| No destination line and no `REGEN` line, but `RESULT: FAILED` | Each `MISS` line. No destination is behind, so an apply has nothing to write | `STATUS=FAIL ERROR="check_failed"` |

### The Apply Question

`Apply these overlays now? [yes/no]` covers the whole write: every line under `Will apply:` plus the regenerate and verify steps. Any answer other than yes counts as no. Print the cancelled result and write nothing.

## 5. Capture Plan and Approval

With `--capture <path>`, the plan is the one report line whose destination is that path.

```text
OVERLAY CAPTURE PLAN
Root: [the vendored tree]
Destination: [the path]
Report line: [the live-edited line the status report printed for it]
Will write: the overlay source that line names, and the engine's record of what it last applied

Capture this live edit now? [yes/no]
```

| Report line for the path | What the run shows | Status |
|--------------------------|--------------------|--------|
| `live-edited` | The capture plan and the capture question | asks |
| No line names the path | `Nothing to capture: [path] has no line in the status report.` The path is either in sync or not an overlay destination, and nothing is written | `STATUS=OK` |
| Any other state | The line with the engine's fix. Capture moves only a live edit | `STATUS=FAIL ERROR="not_live_edited"` |

`Capture this live edit now? [yes/no]` covers the one overlay source and the engine's record. Any answer other than yes counts as no. Print the cancelled result and write nothing.

## 6. Adopt Plan and Approval

With `--adopt <path>`, the run brings one vendored file or folder that no overlay owns under a new manifest entry, then applies. The path sits under `.skilled` or under a runtime folder, or is a root file named in `repin.rootFiles`. The runtime folders are the ones `repin.runtimeFolders` lists, or `.claude`, `.codex`, `.cursor`, `.devin`, `.dsh`, `.opencode`, `.pi` and `.vibe` when the manifest lists none. A path under `repin.exclude` is adopted only from an overlay copy that already exists. The plan is the status report plus that path.

```text
OVERLAY ADOPT PLAN
Root: [the vendored tree]
Path: [the --adopt path, relative to the tree]
Will copy: the path into [overlay folder]/framework/[the path under .skilled] for a .skilled/ path, or [overlay folder]/root/[the path with its leading dots dropped] for any other path, unless that copy is what already exists
Will append: one entry to [overlay folder]/overlay-manifest.json, a file entry for a file and a directory entry for a folder
Pinned: an upstream file is pinned to upstream's bytes at the manifest's pin, read from the checkout pin.checkout names
Will also apply: [one line per overlay-edited line the report printed, or none]
Lock: the engine holds [overlay folder]/.build-lock for the whole run

Adopt this path now? [yes/no]
```

| Report | What the run shows | Status |
|--------|--------------------|--------|
| In sync, or only `overlay-edited` lines | The adopt plan and the adopt question | asks |
| Any `live-edited`, `both-changed`, `upstream-moved` or `cannot-apply` line | Each such line with its fix. The engine appends the entry first and applies after, and that apply would be refused | `STATUS=FAIL ERROR="needs_resolution"` |

`Adopt this path now? [yes/no]` covers the copy into the overlay folder, the new manifest entry and the apply that follows. Any answer other than yes counts as no. Print the cancelled result and write nothing.

### Refusals Before Any Write

The engine prints one `refuse:` line, for the one path an adopt takes, and exits 2. Nothing was written. Most lines name their own fix after the semicolon, so show the line as printed and the fix from this table beside it. A refusal this table does not list is still a refusal before any write: quote it, follow the fix it names and rerun the adopt.

| The engine refuses because | Fix |
|----------------------------|-----|
| The path is not under a vendored root and is not named in `repin.rootFiles` | The file is the project's own and needs no overlay. For an upstream root file, add its name to `repin.rootFiles` in the manifest first |
| The path is on the manifest's `generated` list | Change what the file is generated from, then rerun its generator |
| The path overlaps an existing overlay | That entry already owns it. Edit the entry's source, or its `replace` list for a skill-root entry |
| Both the path and its overlay copy exist | Keep one of the two, then rerun |
| Nothing exists at the path or at its overlay copy | Create the overlay copy the message names, then rerun |
| The copy would land under `root/skilled` | `root/skilled` holds no copy. Adopt the framework's own file through its `.skilled/` path, which maps to `framework/` |
| The path is under `repin.exclude` and its overlay copy does not exist | Move or create the file at the overlay copy the line names, then adopt again |
| The overlay copy resolves outside the overlay folder through a link | Adopt writes only inside the overlay folder. Replace the link with a real folder, then adopt again |
| Adopting would ship a documentation-only README | Move that README out of the way and adopt again, then put it back if it should ship. To ship it, name it as a source in the manifest by hand |
| A file in the path is not a regular file | Adopt takes files and folders only. Remove or replace the link or special file the line names, then adopt again |
| A manifest layout link escapes the tree root or is listed twice | The same refusal `status` prints. Fix the `layoutLinks` entry the line names, then rerun `/doctor:overlay status` |
| A file is a protected name | A `.env` file is never read, except `.env.example`, `.env.sample` and `.env.template`, which are adopted like any vendored file. A token-named file is adopted only when it is source or prose: `.md`, `.css`, `.ts`, `.js`, `.cjs`, `.mjs` or `.svelte` |
| The upstream checkout cannot be read | Run the adopt on a machine that has the checkout `pin.checkout` names, with the pinned commit fetched |
| Upstream ships files under the folder | Adopt each upstream file on its own. A directory entry would replace the whole upstream folder |

### Strict Writes

Three keys in `overlay-manifest.json` belong to the vendoring project. All three are optional, and a tree without them behaves as it did before they existed.

| Key | Value | What it does |
|-----|-------|--------------|
| `strictWrites` | `true` or `false`, off when absent | When on, the engine's `--guard` also refuses a write under a vendored root that no overlay owns, so the `overlay-guard` hook stops it before it is written. A new file is refused with the overlay path to create, and an edit to an upstream file with its `--adopt` command. `overlay-engine.cjs pre-commit` then refuses a staged change of the same kind, for a project to call from its own commit hook |
| `generated` | A list of globs, where `*` stays inside one path segment and `**` crosses segments | Paths a project's generators write, such as runtime mirrors and hook settings. The guard, `--adopt` and `pre-commit` leave them alone |
| `repin.rootFiles` | A list of root files the project carries from upstream, such as `REPO RULES.md` | A re-pin never copies a root file. Each listed file that upstream changed gets its own `root-file` line in the re-pin report, and `--adopt` and the strict guard treat it as a vendored path |

`pre-commit` skips its check while the staged manifest moves the pin, because that commit is a re-pin and the re-pin ran its own drift scan. A staged file that equals upstream's bytes at the pin passes. Skilled's own repository vendors nothing and has no manifest, so none of this runs there.

## 7. Relayout Plan and Approval

The engine has no plan mode for `apply --relayout`, so the plan is the `offLayout` list that `status --json` prints for the same run, one row per move, because the text report stops after 20 `LAYOUT` lines. Each item names the overlay, the manifest field, the path the copy sits at now and the path it belongs at. Every move stays inside the overlay folder: a copy for a `.skilled/` destination lands at its `framework/` path, a copy for any other destination lands at its `root/` path, and the destination the overlay writes is untouched.

```text
OVERLAY RELAYOUT PLAN
Root: [the vendored tree]
Overlay folder: [the folder the engine reads, from .skilled-overlays.json or the default skilled-overlays/]
Will move: [one row per offLayout item in status --json, restated as overlay: field from -> to]
Backup: [overlay folder]/relayout-runs/[stamp]/, holding every copy the run moves and the manifest, written before the first move
Will rewrite: the manifest's source, fragment and base fields that name a moved copy, and the layout-link targets that reach one
Then: /doctor:overlay apply, run in this same run, so the destinations catch up with the moved sources

Move these sources now? [yes/no]
```

| Report | What the run shows | Status |
|--------|--------------------|--------|
| An empty `offLayout` list, so no `LAYOUT` line | The nothing-to-move result. Every source already sits on its layout path | `STATUS=OK` |
| Any `offLayout` item whose [to] sits under `root/skilled` | Each such `LAYOUT` line with its remedy. The engine refuses every move while one is there, so the run asks nothing. Change that destination or remove the entry, then rerun `/doctor:overlay apply --relayout` | `STATUS=FAIL ERROR="needs_resolution"` |
| At least one `offLayout` item, none under `root/skilled`, and nothing else outstanding | The relayout plan and the relayout question | asks |
| Any `live-edited`, `both-changed`, `upstream-moved` or `cannot-apply` line | Each such line with its fix, beside the `LAYOUT` lines. The apply that follows the move would be refused until it is settled | `STATUS=FAIL ERROR="needs_resolution"` |
| A `MISS` line or a `STALE` line, and no line above | The relayout plan and the relayout question, with each such line shown beside the `LAYOUT` lines. The engine moves the sources and still exits 0, so the run goes on and ends on that line | asks |

`Move these sources now? [yes/no]` covers every move, the backup, the manifest rewrite and the layout-link retargeting. Any answer other than yes counts as no. Print the cancelled result and write nothing.

The run prints one `skipped` line per file the backup did not copy, because the read rule protects it, and one `relinked <path> -> <target>` line per layout link it rewrote. A `skipped` line for a file inside a moved folder comes before the `backup` line, and that file still moves with its folder. A `relinked` line comes after the last `moved` line, and the manifest records the same target.

### Refusals Before Any Write

The engine prints one `refuse:` line per refusal and exits 2. Nothing was written. Any one refusal stops every move, so settle each line before the rerun. A refusal this table does not list is still a refusal before any write: quote it, follow the fix it names and rerun `/doctor:overlay apply --relayout`.

| The engine refuses because | Fix |
|----------------------------|-----|
| A move would land under `root/skilled` | `root/skilled` holds no copy. Change that entry's destination or remove the entry, then rerun |
| A documentation-only README sits at the target | Merge that README's text into the overlay copy and delete it, or move it, then rerun |
| A path the manifest names leaves the overlay folder | Point that field at a copy inside the overlay folder, then rerun |
| A manifest layout link escapes the tree root or is listed twice | Fix the `layoutLinks` entry the line names, then rerun `/doctor:overlay status` |
| The target path already exists in the overlay folder | Keep one of the two copies, put the bytes you want in it, then rerun |
| A copy the manifest names is missing | Point that field at the copy that exists, or create the copy the manifest names, then rerun |
| Two copies belong at one path, or one copy is claimed by two fields | Settle the manifest so one copy owns one path, then rerun |
| A field or a link no longer holds the path the run planned against | Nothing moved. The manifest changed under the run, or two entries claim one copy. Fix the field or the link the `refuse:` line names, then rerun |
| Two copies sit one inside the other | Move the outer copy in its own run, then the inner one |
| The overlay lock is held | Another run holds the lock. The `Next:` line under the refusal names the check and the lock file: `ps -p <pid>` for an owner on this host, then `rm` of that file once the run has ended. A lock whose owner has ended on this host is taken over by the next run, which prints a `note:` line, so this row covers a live owner, another host or a line with no pid. A refusal that names a takeover marker says to run it again in a minute: do that and leave the lock. |

## 10. Troubleshooting Display

| Situation | Suggested Action |
|-----------|------------------|
| `no overlay manifest at ...` | The tree has no overlay folder yet, or `.skilled-overlays.json` names another one. When the message says no setting file was found, add `.skilled-overlays.json` at the tree root naming the folder that holds `overlay-manifest.json`, such as `{"overlayDir": "../overlays"}` for a folder beside the tree. Then rerun `/doctor:overlay status` |
| `refusing to inspect a protected path: ...` | That one entry is blocked and every other overlay is still reported. Follow the fix the line names: add the file to that entry's `protectedPaths`, or move a `.env` file out of the overlay. `.env.example`, `.env.sample` and `.env.template` are never refused, because they are read like any vendored file. Then rerun `/doctor:overlay status` |
| `not-copied` lines in a re-pin report | Upstream changed these paths, and a re-pin never copies them: they sit under `repin.exclude` or in a top-level file or folder outside the copied roots, such as `AGENTS.md`. Carry over what applies by hand. For the shipped `AGENTS.md` sections, run `/doctor:agents-md` |
| `upstream-lost` lines in a re-pin report | The copy brings in an upstream change that an overlay then writes over or removes: an item a json-entry `set` drops from an array, a value a `set` or `setKeyOnItem` overwrites, or a file a directory overlay or a folder a skill-root overlay replaces does not carry. The re-pin does not stop for it. Carry the change into the overlay source by hand when it applies, then run `/doctor:overlay apply` |
| `stage skipped ... regenerate and ... verify step(s)` | Expected. The stage has no project install, so the generators run only in the live re-pin |
| `.skilled-overlays.json` is refused | The setting must name a relative folder with forward slashes, inside the tree or a direct sibling `../<name>`. A backslash or an absolute path prints `.skilled-overlays.json must name a relative folder with forward slashes: <value>`. A deeper path such as `../../x` or `../a/b`, the tree's own name as `../<tree>`, a dangling sibling link and a looping link print `.skilled-overlays.json names a folder outside the tree root: <value>`. A sibling link that leads back to the tree, and a sibling name that is a case variant of the tree's own, print `.skilled-overlays.json names a sibling that resolves into the tree root: <value>`. A sibling that resolves to a folder holding the tree root prints `.skilled-overlays.json names a sibling that resolves to a folder holding the tree root: <value>`. A folder named inside the tree that resolves outside it, for example through a link, prints `.skilled-overlays.json names a folder inside the tree that resolves outside it: <value>`, and one that resolves to the tree root itself prints `.skilled-overlays.json names a folder inside the tree that resolves to the tree root: <value>`. A sibling that resolves outside the tree's git repository, or into its `.git`, is refused by every command, `status`, `apply`, `guard` and `pre-commit`, with exit 2: `.skilled-overlays.json names a folder outside the git repository at <top>: <value>`. Fix the file, then rerun `/doctor:overlay status` |
| `refuse: the overlay lock is held` | Another run holds the lock. The `Next:` line under it names the check and the lock file: `ps -p <pid>` for an owner on this host, then `rm` of that file once the run has ended. A lock whose owner has ended on this host is taken over by the next run, which prints a `note:` line, so this row covers a live owner, another host or a line with no pid. A refusal that names a takeover marker says to run it again in a minute: do that and leave the lock. |
| A `live-edited` line | Run `/doctor:overlay apply --capture <path>` for that path, then `/doctor:overlay apply` |
| A `LAYOUT` line in a status report | Run `/doctor:overlay apply --relayout`, which moves each off-layout source and then applies. The copy still applies while it sits off its layout path. A line whose path sits under `root/skilled` ends `change the destination or remove the entry` instead. Change that entry's destination or remove it, because relayout refuses that move |
| A `STALE` line in a status report | Upstream changed a root file a `repin.rootFiles` overlay owns. Rebase the overlay onto the new bytes, then set its `pinnedSha256` to theirs and rerun `/doctor:overlay status` |
| A relayout printed `skipped` for a path | The backup did not copy that file because the read rule protects it. A source on its own stayed where it was, so move it by hand to the path its `offLayout` item named. One inside a moved folder already sits on that path, and only the backup lacks it |
| `layout link path is listed twice: <path>` | The manifest's `layoutLinks` lists one `path` twice, compared as normalized paths, so `ext/`, `./ext`, `ext/.` and `x/../ext` are one path, and on a filesystem that ignores letter case so are `ext` and `EXT`. It is refused where the escape below is: `status` and `apply` exit 2 with that message, and `apply --relayout` and `apply --adopt` print it after `refuse:` and exit 2. Nothing was written. List each link once, then rerun `/doctor:overlay status` |
| `refuse: a documentation-only README sits at <path>: merge it into the overlay copy or move it, then relayout` | A relayout move would land on a README that no manifest entry ships. Nothing was moved. Merge that README's text into the overlay copy and delete it, or move it, then rerun `/doctor:overlay apply --relayout` |
| `layout link path escapes the tree root: <path>` | A manifest `layoutLinks` entry names a `path` or `replaces.path` that leaves the tree, as text or through a linked folder on its way. `status` and `apply` exit 2 with that message, and `apply --relayout` and `apply --adopt` print it after `refuse:` and exit 2. Nothing was written. Point the link at a path inside the tree, then rerun `/doctor:overlay status` |
| A relayout refused because the target exists | The overlay folder holds both the old copy and the path it belongs at. Keep one of them, then rerun |
| `error: relayout failed while writing the backup` | The run stopped before it moved anything. Read the rest of the line: `nothing was moved and the partial backup was removed` means the run removed its own partial backup, while `nothing was moved, but the partial backup at <backup> could not be removed: <message>` names a backup to delete by hand. Fix the cause the message names, then rerun `/doctor:overlay apply --relayout` |
| `note: relayout left an emptied folder in place after moving` | Nothing failed. The copy moved to its layout path and the run could not remove the folder it emptied. The moved count and the apply line are still printed, and the run exits 0. Remove the empty folder by hand if you want it gone |
| `note: took over the overlay lock of a run that has ended: ...` | The earlier run ended without removing its lock, so this run took it over and carried on. Nothing to do, unless that run is still working under another host |
| `AUDIT    differs <path>` | No overlay owns the path and it no longer matches upstream at the pin. Adopt it with `/doctor:overlay apply --adopt <path>`, or add an overlay that owns it |
| `AUDIT    missing <path>` | Upstream has the file at the pin and the tree lacks it. Restore it from the checkout the manifest names, or take it through a re-pin |
| `AUDIT    extra <path>` | The tree tracks a file upstream never had at the pin. Move it into an overlay, adopt it, or remove it |
| `AUDIT    skipped: no upstream checkout at the pin` | The comparison needs the checkout `pin.checkout` names with the pinned commit fetched. The audit did not run here, so read nothing into its silence |
| `DOCS     missing-readme <path>` | That folder in the overlay folder has neither a `README.md` nor a `README.markdown` as a regular file. Add one, named `README.markdown` in a folder under a `commands/` path, because sk-doc reads a `README.md` there as a command document. A README in a folder a `directory` entry covers, or inside a skill-root entry's `replace` folder, ships into the tree on the next `/doctor:overlay apply`. Any other README is documentation only and the engine never applies it. The status result does not change |
| `DOCS     invalid-readme <path>: <message>` | sk-doc's validator found a blocking error in that README, and `(+N more)` counts the rest. Run `JEV_FEATURE_CITE_DRIFT=0 python3 .skilled/skills/sk-doc/scripts/validate_document.py <README> --json` for the full list, the same way the engine runs it, fix the README, then rerun `/doctor:overlay status --audit`. The status result does not change |
| `DOCS     skipped: <reason>` | python3 or sk-doc's validator is missing on this machine, so no README was validated. The `missing-readme` lines still count. Install what the reason names, then rerun `/doctor:overlay status --audit` |
| The guard refuses a write with `is a vendored file no overlay owns` | The manifest has `strictWrites` on. Run `/doctor:overlay apply --adopt <path>` for that file, then edit its copy in the overlay folder and run `/doctor:overlay apply` |
| The guard refuses a write with `is a new file in the vendored tree` or `is a new file inside overlay` | Create the file at the overlay path the line names. Then run `/doctor:overlay apply --adopt <path>` with the path it names, or `/doctor:overlay apply` when the line says an overlay already holds the folder |
| The guard refuses a file a generator writes | Add a glob for it to the manifest's `generated` list |
| `pre-commit` prints `refuse: staged ...` | Each named path changed under a vendored root outside an overlay, and the commit is refused with exit 1. For a staged change, the engine prints one pair per path: `Next: from <root>: node .skilled/commands/doctor/scripts/overlay-engine.cjs apply --adopt <path>` to give it an overlay, then `or drop it: git -C <root> restore --staged -- <path>` to unstage it. For a staged deletion, the `Next:` line is `git -C <root> restore --staged --worktree -- <path>`, which puts the file back, because the next re-pin would copy it back anyway. A path a generator writes goes on the manifest's `generated` list instead |
| `root-file` lines in a re-pin report | Upstream changed a root file named in `repin.rootFiles`, and a re-pin never copies one. Carry the change over by hand or adopt the file, and rebase the overlay when the line says one owns it |
| A `both-changed` line | Compare the overlay source with the destination and settle the content in the overlay source. Then rerun `/doctor:overlay status` |
| A `cannot-apply` line | The engine cannot apply a json-entry overlay's entry set to a file nobody edited. Do what the line's `fix:` text says to the entry set or the destination, then rerun `/doctor:overlay status` |
| An `upstream-moved` line | A re-pin changed a file an overlay owns. Rebase the overlay source onto the new upstream bytes, then rerun `/doctor:overlay status` |
| `regeneration failed` after an apply | The overlays landed and were recorded, but a generator failed. Read the failed step's output and fix it. The engine records the pending regeneration, and until an apply finishes it, `status` prints a `REGEN    pending:` line and fails. Run `/doctor:overlay apply`, which reruns every regenerate step even when every destination is in sync. Then run `/doctor:overlay status` |
| A `REGEN    pending: <ids>` line in a status report | An earlier apply wrote the overlays and did not finish its regeneration. Fix the step that failed, then run `/doctor:overlay apply`, which reruns the steps the line names |
| `<manifest path> is not valid JSON: <parser message>` | The overlay manifest does not parse, and every command reads its overlays from it first, so the engine exits 2 with that message, its why line and `Next: fix the JSON in <manifest>, then from <root>: node .skilled/commands/doctor/scripts/overlay-engine.cjs status`. Nothing was written. Fix the JSON where the parser message points, then rerun `/doctor:overlay status` |
| `NOTE     could not remove the Python cache folder <folder>` after an apply | Nothing failed. The apply was only clearing Python caches from a folder its overlay no longer ships, and the folder stays. Run the `Next:` line under it, `chmod -R u+w <folder> && rm -r <folder>`, to remove it by hand |
| A `BLOCKED` or `MISS` line with `does not match what apply last wrote there` or `exists but is not the link to` | A file, folder or link stands where an overlay writes a different shape, and apply did not write it, so it stays. Apply changes a destination between file, folder and layout link only when the thing there is its own earlier output. Keep the unowned one aside with the `Next:` line, `mv <path> <path>.keep`, then rerun `/doctor:overlay apply` |
| `multiple overlays own the same destination: <path>` | Two entries write one destination, and the second would overwrite the first. Keep that destination in one entry, as the `Next:` line says, then rerun `/doctor:overlay status` |
| A `NOTE` line in a status report | Nothing failed. Do what the line says: run `apply` once for a version 1 state file, name or fetch the checkout for a skipped check, point an insert anchor at an item or key the file holds, prefer an identity match over an array index, remove a value by hand that no record covers, add a file a `regenerate` step writes to that step's `outputs`, or restore missing upstream paths from the pinned commit |
| The apply question was answered no | Nothing was written. Rerun `/doctor:overlay apply` when the report is acceptable |
| A re-pin stage lists `blocked` overlays | Rebase each one onto the new upstream file, then rerun `/doctor:overlay repin --upstream <dir> --to <commit>` |
| A re-pin refuses on an unowned file | The named file holds an edit made in place. Move it into an overlay or upstream, then rerun |
| A re-pin refuses on a missing commit | Fetch both commits into the `--upstream` checkout, then rerun |
| A live re-pin failed after its backup | Run `/doctor:overlay repin --rollback <run-id>` with the run id the rollback line names, then `/doctor:overlay status` |
| Route manifest parse error | Run `bash .skilled/commands/doctor/scripts/route-validate.sh` |

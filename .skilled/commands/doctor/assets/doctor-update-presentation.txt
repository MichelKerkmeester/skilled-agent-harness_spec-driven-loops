# /doctor:update Presentation Contract

This file is the single source of truth for user-facing wording and layout in `/doctor:update check`, `align`, `apply`, `rollback` and `record-base`. The router owns argument parsing and action routing. Each workflow YAML owns execution behavior.

## 1. Action and Flag Errors

### Unknown action

```text
ERROR: /doctor:update does not recognize action "[action]".
Choose check, align, apply, rollback or record-base.
No workflow was started.
```

### Cross-action or unknown flag

```text
ERROR: [flag] is not valid for /doctor:update [action].
Accepted flags: [flags for this action]
No workflow was loaded and no engine command was run.
```

Accepted flags by action:

| Action | Flags |
|--------|-------|
| check | `--json`, `--release=<tag>`, `--scope=all|<unit-key,...>`, `--offline`, `--include-prerelease`, `--remote=<name-or-url>` |
| align | `--release=<tag>`, `--scope=all|<unit-key,...>`, `--offline`, `--dry-run`, `--include-prerelease`, `--remote=<name-or-url>` |
| apply | `--decisions=<path>`, `--dry-run`, `--release=<tag>`, `--scope=all|<unit-key,...>`, `--include-prerelease`, `--offline`, `--remote=<name-or-url>` |
| rollback | `--run=<runDir>`, `--dry-run` |
| record-base | `--release=<tag>`, `--remote=<name-or-url>`, `--scope=all|<unit-key,...>`, `--offline`, `--include-prerelease`, `--trust-release`, `--dry-run` |

Latest-upstream resolution takes stable `vN.N.N.N` tags only. `--include-prerelease` also admits `vN.N.N.N-<pre>` tags. Both compare version segments as numbers. A tag named with `--release` is used as given.

A check may fetch release commits it lacks into the git object store. That changes no checkout file or ref. Pass --offline to prevent every fetch.

Bare `/doctor:update` runs `check`. There are no `:auto` or `:confirm` suffixes.

## 2. Check Dashboard

Render the engine report using this layout. Use `UNKNOWN` when upstream latest or the overall report status is unknown. Never treat unavailable upstream data as proof that the checkout is current.

When the operator passes `--json`, return the engine report as one JSON document and omit the prose dashboard and next steps.

```text
Spec-kit Release Check

Release position: [ahead|behind|at-release|unknown] [release tag or UNKNOWN]
Upstream latest: [tag or UNKNOWN]
Checkout: [head]  Ahead: [count]  Behind: [count]  Dirty: [yes|no]
Report status: [status]

Quiet units: [current count] current, [local count] local (no action)

| Status | Unit | Kind | File changes | Changelog highlights |
|--------|------|------|--------------|----------------------|
| [update|new|customized|conflict|removed|blocked|downgrade|unknown] | [unit] | [kind] | [class counts] | [highlights or none found] |

Next steps
[action-specific next step]
```

Files the engine classes `generated` (a leaf manifest, the trigger index and its sidecars, a compiled-route activation manifest, or a graph-metadata change inside its `derived` block) were rewritten by a generator. They never count as customizations. Include them in class counts and offer no decision.

Show a row for each unit that is not `current` or `local`, grouped by status. Combine `current` and `local` into the quiet line and include both counts. Include counts for statuses with no matching unit as zero in the summary when the engine report provides status counts. Preserve an unexpected unit status visibly as `unknown`. Show available changelog highlights from the selected release and unit. If upstream latest is unavailable, display `UNKNOWN` and its engine error when present.

### Check next steps

Use the applicable line or lines:

```text
Customized or conflict units need decisions: /doctor:update align [same release and scope flags]
Removed units need a decision review: /doctor:update align [same release and scope flags]
Only update or new units need writes: /doctor:update apply [same release and scope flags]
Removed, blocked or unknown units need review before applying: inspect the status details, then choose align or apply as appropriate.
Downgrade units are older in the selected release than in this checkout. Apply never writes them. Roll back the apply that took the newer release, or use git, to return to an older release.
Database regeneration after an update: /doctor:rebuild
No selected units need an update.
```

When offering apply without a decisions file, add this note if no earlier alignment run is known:

```text
No alignment run is needed for update and new units. /doctor:update apply plans from the current check, writes only those units, and re-checks each file against its base before writing. Customized or conflicting units are skipped until /doctor:update align records decisions for them.
```

When the report's `baseRecording.needed` is true, add:

```text
[count] unit(s) have no verified recorded base, so their status rests on an inferred or unverified base. This is normal right after copying or installing .skilled/.
Record-base refuses a release that is farther from this tree than another release, and names the nearest one. Record the release this tree was installed from, with your approval, by running:
/doctor:update record-base --release=<installed-release> [--remote=<framework-remote>]
It writes .skilled/release/base.json. Commit that file, then run /doctor:update again.
```

```text
This checkout's remote lists no framework release tags. If .skilled/ was copied from the framework, name the framework repository with --remote=<name-or-url>. When the base is recorded with --remote, .skilled/release/base.json keeps that remote, and later commands use it without the flag.
```

If the report is unknown, end with:

```text
Upstream status is UNKNOWN. The report cannot confirm that this checkout is current.
```

## 3. Align Evidence Cards and Decision Batches

### Run-root ignore error

When `git check-ignore` does not match the run root, show:

```text
The release run root is not ignored by git in this checkout.
Add these two lines to .skilled/release/.gitignore:
  runs/
  .apply.lock
Or add these two lines to the repository .gitignore:
  .skilled/release/runs/
  .skilled/release/.apply.lock
Commit the ignore file, then run /doctor:update again.
```

Present one consolidated batch per `customized`, `conflict` or `removed` unit. Show each non-same file's complete evidence card before asking for the batch response.

````text
ALIGNMENT REVIEW
Release: [release]
Run directory: [runDir]

Unit: [unit]  Status: [customized|conflict|removed]
Files needing review: [count]

Evidence card [number] of [count]
Path: [file path]
Class: [class]  Conflict type: [kind or none]
Base blob / mode: [blob or absent] / [mode or absent]
Local blob / mode: [blob or absent] / [mode or absent]
Release blob / mode: [blob or absent] / [mode or absent]
Rename: [from path -> to path, or none]
Merge summary: [summary]
Changelog rationale: [rationale]
Recommended decision: [decision or review]
Accepted for this file: [engine-eligible answers for this file]

Base-to-release diff
```diff
[complete evidence diff]
```

Base-to-local diff
```diff
[complete evidence diff]
```
```

For `merge` or `use-proposal`, show the entire proposal before asking for that answer:

````text
Proposed text for [file path]
```text
[complete proposal text]
```
````

If the proposal contains conflict markers, ask:

```text
The proposal still has conflict markers. Reply with the complete resolved file text.
It will replace only [runDir]/proposals/[relative path] inside this run directory. The decision is recorded after the resolved proposal passes marker validation.
```

Write the supplied resolved content to exactly that proposal path with a quoted Bash heredoc using a delimiter absent from the supplied content. Do not show or run `Edit`. Re-read the full proposal and confirm all markers are gone before offering `merge` or `use-proposal`.

After all evidence cards for one unit, ask:

```text
Decision batch for [unit]
For each file, reply with one accepted decision:
  adopt-release  take the release version when the engine allows it
  keep-local     preserve the checkout version
  merge          accept the resolved proposal for a mergeable conflict
  use-proposal   accept the resolved proposal after conflict markers are removed
Or reply defer to defer this entire unit.

Answers: [file path] = [decision]; [file path] = [decision]; ...
```

Accept only `adopt-release`, `keep-local`, `merge`, `use-proposal` for eligible files, or `defer` for the whole unit. The engine may reject a decision that does not match the file class. Do not infer an answer from silence or from the recommendation. Record every file answer through the engine `decide` command, including an answer matching a prefilled suggestion. Record `defer` through `decide --unit <unit-key> --defer`, using the unit's `key` from the report (`kind:name`, for example `skill:sk-git`). A plain name works only when no other unit shares it.

### Align summary

```text
Alignment decisions recorded
Release: [release]
Run directory: [runDir]
Decisions: [count]
Deferred units: [list or none]
Unresolved files: [list or none]
State log: [runDir]/.doctor-update.last-run.json, or none for dry-run or preflight failure
Commit the applied files and the changed release records under .skilled/release/ before applying this decision set.

Apply a completed decision set:
  /doctor:update apply --decisions=[runDir]/decisions.json
```

When a dry-run plan was requested, use:

```text
STATUS=DRY_RUN
No run directory or decisions file was written. No apply handoff is available yet.
```

## 4. Apply Plan and Startup Approval

### Run-root ignore error

When `git check-ignore` does not match the run root, show:

```text
The release run root is not ignored by git in this checkout.
Add these two lines to .skilled/release/.gitignore:
  runs/
  .apply.lock
Or add these two lines to the repository .gitignore:
  .skilled/release/runs/
  .skilled/release/.apply.lock
Commit the ignore file, then run /doctor:update again.
```

Show the engine dry-run plan before asking for approval:

```text
Release Apply Plan
Release: [release]
Run directory: [runDir, or a new run under .skilled/release/runs when apply plans without a run]

| Operation | Path | Unit |
|-----------|------|------|
| [add|replace|delete] | [path] | [unit or release metadata] |

Applied units: [list or none]
Skipped units: [unit and reason, with the paths for undecided files, or none]
Follow-up checks: [regenerate hubs, generated files and their generators, hooks, runtime mirrors, databases]
Targets modified since alignment: [none or engine refusal]
```

If the dry-run plan is valid, ask once:

```text
Apply exactly this release plan to the checkout?
Reply yes to approve the planned writes, or no to leave release-managed files unchanged.
```

Only an unambiguous `yes` approves. On an explicit `no` or an ambiguous answer, do not run engine apply without `--dry-run`. Write the terminal state log and report `STATUS=DECLINED`. On cancellation or interruption, do not run engine apply without `--dry-run`. Write the terminal state log and report `STATUS=CANCELLED ACTION=cancelled`. If the operator supplied `--dry-run`, do not ask this prompt; stop after the plan with `STATUS=DRY_RUN`.

## 5. Post-Apply Battery and Recovery

Show every applicable check and its observed result:

```text
Post-apply checks

| Check | Result | Detail |
|-------|--------|--------|
| Leaf manifests | [PASS|FAIL|not applicable] | [output tail] |
| Trigger index | [PASS|FAIL|not applicable] | [output tail] |
| Compiled routes | [PASS|FAIL|not applicable] | [output tail] |
| Skill-derived metadata | [PASS|FAIL] | [changed count, error count, exit code] |
| Route validation | [PASS|FAIL] | [output tail] |
| Command catalog mirror | [PASS|FAIL] | [output tail] |
| Runtime mirrors | [PASS|FAIL] | [output tail] |
| Codex prompts | [PASS|FAIL] | [output tail] |
| Pi prompts | [PASS|FAIL] | [output tail] |
| Hermes prompts | [PASS|FAIL] | [output tail] |
| Hook installers | [PASS|FAIL|not applicable] | [output tail] |
```

For a failing check with a documented write counterpart, ask:

```text
[check] failed: [short evidence]
1) Run the documented repair command, then rerun this check
2) Roll back the release update
X) Stop and leave the applied release in place
Reply 1, 2 or X:
```

Run the write counterpart only after an unambiguous `1`. Route validation and the command catalog checker have no write mode; for those failures, explain the mismatch and offer rollback or stop. Do not invent a checker write flag.

Rollback uses the engine first:

```text
Rollback release update from [runDir] using the engine rollback record?
Reply yes to restore paths that still match the applied release, or no to leave the checkout as-is.
```

If engine rollback reports skipped paths, show each exact path and ask before running `git restore`:

```text
The engine skipped these paths because their contents changed after apply:
[exact skipped paths]

git restore will discard their current contents and restore the index version.
Reply yes to restore only these paths, or no to leave them unchanged:
```

Run `git restore -- [exact engine-reported skipped paths]` only after an unambiguous yes. Report each restored and skipped path. Never call a partial rollback complete.

## 6. Rollback

When a stale lock is present, show its owner and state before asking to clear it. Clearing the lock and restoring a run need separate approvals. A live or unreadable lock stops the workflow.

```text
The release apply lock is held.
Owner: process [pid] ([command]), started [startedAt]
State: [running, stale or unreadable]
Running: another /doctor:update apply, rollback or record-base is still working. Wait for it to finish, then try again.
Stale: that process is no longer running. Run /doctor:update rollback to clear the lock with your approval and, when the interrupted run recorded a rollback, to restore its partial changes.
Unreadable: the lock names no owner. Confirm that no /doctor:update apply, rollback or record-base is running, then remove .skilled/release/.apply.lock by hand.
```

If the supplied run differs from the run named by a stale lock, show both paths and ask which one to restore. When no run is supplied and the stale lock names none, list runs with `rollback.json` under `.skilled/release/runs`, newest first, and ask the operator to choose. If a stale lock was cleared but its run has no rollback record, report that the interrupted run wrote nothing and stop with `STATUS=UNLOCKED`.

Show the preview before asking for rollback approval:

```text
Release Rollback Preview
Run directory: [runDir]
Paths to restore: [every path in restored, or none]
Paths to skip: [every path in skipped, or none]
```

```text
Restore the displayed paths from this release update?
Reply yes to approve the rollback, or no to leave the checkout unchanged.
```

If the engine skips a path, list it and say it changed after apply and was left unchanged. Never run `git restore` from this workflow.

### Rollback result

```text
Doctor Update Rollback
Run directory: [runDir]
Lock: [absent|cleared|refused]
Restored: [paths or none]
Skipped: [paths or none]
State log: [runDir]/.doctor-update-rollback.last-run.json
STATUS=[ROLLED_BACK|PARTIAL|UNLOCKED|DRY_RUN|DECLINED|CANCELLED|FAILED]
```

## 7. Record Base

When no release is supplied, ask which release this tree was installed from. Show every unit the engine would record and whether the nearest-release check ran:

```text
Release Base Preview
Release: [release]
Remote: [remote or none]
Nearest-release check: [verified|not verified]
| Unit | Status | Base source |
|------|--------|-------------|
| [unit key] | [status] | [source] |
```

If another release is nearer, show the unit keys and nearest release reported by the engine. Offer to retry with that release when every listed unit names the same nearest release. Otherwise, offer to keep the selected tag only after explicit approval with this risk statement:

```text
The selected release may not match the files in this tree. Approve recording [release] anyway with --trust-release?
Reply yes to retry with --trust-release, or no to stop.
```

After the nearest-release check passes or an approved trust retry succeeds, ask before writing:

```text
Record release [release] as the base for these units?
Reply yes to write .skilled/release/base.json, or no to leave it unchanged.
```

When .skilled/release/base.json has uncommitted changes, show:

```text
Commit the existing .skilled/release/base.json changes, then run /doctor:update record-base again.
```

When the engine reports a lock, use the release apply lock template above and stop. A dry run stops after the preview without writing a state log.

### Record-base result

```text
Doctor Update Record Base
Release: [release]
Remote: [remote or none]
Units recorded: [unit keys or none]
Nearest-release check: [verified|not verified]
State log: .skilled/release/runs/.doctor-update-record-base.last-run.json, or not persisted
STATUS=[RECORDED|DRY_RUN|DECLINED|CANCELLED|FAILED]
After STATUS=RECORDED: Commit .skilled/release/base.json, then run /doctor:update again.
```

## 8. Database Rebuild Prompt

After the battery, ask:

```text
The release update completed its post-apply checks.
Run /doctor:rebuild now to refresh spec-kit databases?
Reply yes to run it, or no to skip.
```

Record `reindex=rebuilt` only after successful completion is observed. If skipped, show:

```text
Database rebuild skipped. The spec-kit database index may be stale.
Run /doctor:rebuild when you are ready.
```

If rebuild fails, record `reindex=failed`, show the observed error and the same stale-index warning. Never present skipped or failed reindexing as full success.

```

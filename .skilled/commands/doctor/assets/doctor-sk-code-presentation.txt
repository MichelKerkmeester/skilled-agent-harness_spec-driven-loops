# /doctor:sk-code Presentation Contract

This file is the single source of truth for user-facing presentation in `/doctor:sk-code <target>`: the argument failure, the startup menu, the setup per-leg result table, the quality status table and plan, result templates and next-step text. The command router owns target resolution and asset loading. The workflow YAML owns execution behavior.

## 1. Argument Failure

Every argument failure happens before any workflow YAML loads and prints the wording below with the bracketed parts filled in, then ends with the status line. Nothing is read or changed.

| Situation | Wording |
|-----------|---------|
| The first token is not a target | `Unknown target: [target]` then `/doctor:sk-code runs setup or quality. Try: /doctor:sk-code menu` then `STATUS=FAIL ERROR="unknown_target"` |
| A flag no target accepts | `Unknown argument: [argument]` then `setup accepts --prompt=<text>, and quality accepts --dry-run.` then `STATUS=FAIL ERROR="unknown_argument"` |
| A flag that belongs to the other target | `Flag '[flag]' is not valid for target '[target]'. Did you mean /doctor:sk-code [suggested-target] [flag]?` then `STATUS=FAIL ERROR="cross_target_flag_injection"` |

## 2. Startup Presentation

This command is always interactive and has no `:auto` mode. With no target, `setup` runs because it only reads. The menu below appears for `menu`, `list` and `?`. Ask it once, then wait.

```text
What do you want to check?

1) setup
2) quality
X) Cancel
```

Accepted answers:

| Answer | Result | Meaning |
|--------|--------|---------|
| `1` | target = `setup` | Run the read-only setup battery and name the repair for each failing leg |
| `2` | target = `quality` | Show the quality config the gate reads and check it, then create `.sk-code/quality.json` once after you approve |
| `X`, empty, `cancel` | `STATUS=CANCELLED ACTION=cancelled` | Stop. Nothing changes |

On any other response, re-emit the menu once. On a second invalid response, return `STATUS=FAIL ERROR="unknown_selection"`.

Valid targets: setup, quality

### Route Manifest Display

Render this table for `menu`, `list` or `?`. Values should mirror `_routes.yaml`.

| Target | Workflow | Mutation Class | One-Line Purpose |
|--------|----------|----------------|------------------|
| `setup` | `doctor-sk-code-setup.yaml` | read-only | Run the sk-code setup battery in its check-only form and name the repair for each failing leg |
| `quality` | `doctor-sk-code-quality.yaml` | mutates | Report and check the repository quality config, and create `.sk-code/quality.json` once after an explicit approve |

## 4. Quality Results

### Quality Status Table

Render the config source first, then one row per tool the status names, then what the gate would apply.

```text
Config: [path and source, or none, the gate runs its built-in checks alone]
Errors: [each config error, or none]
Trust: [trusted or untrusted with the rule that decided it, the repair line when untrusted, or none]
Layers: pre-commit [state], ci [state], post-edit [state]
Hygiene: [disabled and the rules, or every core rule applies]
```

| Tool | Named by | State | Repair |
|------|----------|-------|--------|
| [tool] | [check ids, or the suggestion that names it] | [PASS|SKIP|DEGRADED] | [the repair line, or none] |

`PASS` means the tool is on PATH. `DEGRADED` means a configured check names it and it is absent. `SKIP` means only a suggestion names it, so no check would look for it.

### Applied Rules

Render the status's `applies` block: one row per checklist the gate would load, then the hygiene rules. The runner resolves it through `quality-gate.cjs --explain` over the sample the status names, one file per first three folders and extension, and runs no check. A paths selector deeper than three folders, a contentMarkers selector, or a surface file or content marker can miss every sampled file, so each checklist the repository config declares is listed and checked even when the sample did not reach it, marked `declared, not reached by the sample`.

```text
Checklists: [N], resolved over [N] of [N] listed files, or not resolved and why
Hygiene rules: [N] apply ([rule ids]), disabled [rule ids, or none]
```

| Checklist | Seat | Overrides |
|-----------|------|-----------|
| [checklist file] | [default|repo-config|hub-surface|outside-skill, each seat that lists it] | [each row as `<rule id> none` or `<rule id> replace: <text>`, REFUSED with each reason, or none] |

A seat is where the checklist was declared: `default` is the shipped base layer, `repo-config` is `checklists[]` in `.sk-code/quality.json`, `hub-surface` is a hub surface's `quality` block and `outside-skill` is a skill outside the hub that declares one. A refused section applies none of its rows, so print every reason the shared linter gave, such as a floor rule that cannot be overridden. A refused section, or one with a row whose id no rule carries, fails the status with `CONFIG_INVALID`, and a checklist error such as `CHECKLIST_MISSING` fails it with that code, because every gate run that loads the file stops on it with exit 3. A row the sample did not reach is checked the same way. Two checklists at one level that disagree on a rule for a sampled file print `override-conflict <rule id> <checklist> <checklist>` with the sampled files it covers: neither row applies there and the gate reads `UNVERIFIED`, exit 4, so the status lists it and does not fail on it. A resolution that broke reads `DEGRADED` with its reason.

## 6. Troubleshooting Display

| Situation | Suggested Action |
|-----------|------------------|
| A setup leg reports FAIL | Run the `repair:` command printed under that leg, then rerun `/doctor:sk-code setup` |
| The provisioning leg fails | Run `bash .skilled/skills/sk-git/scripts/worktree-naming.sh provision .` |
| The provisioning leg says the checkout predates the v4 layout | Install the `.skilled/` tree from a v4 release, run `/doctor:update compat`, then rerun `/doctor:sk-code setup` |
| The guard leg fails after a routing edit | Run the refresh and copy commands the guard leg's `repair:` line names, or commit with the hooks installed so the pre-commit gate does both |
| The probe leg fails on the legacy stub | The hub serves no compiled route; run the `repair:` command printed under the probe leg |
| The quality leg fails | Each detail names one check, tools, executables, tables, tests or route, and the `repair:` line under it fixes that check |
| A setup leg reports SKIP | The skipped legs wait on the provision step or the v4 layout, so run the provisioning leg's `repair:` command and rerun |
| The quality status reports a DEGRADED tool | Install the tool, or remove the checks that name it from the config, then rerun `/doctor:sk-code quality` |
| The quality check reports CONFIG_INVALID | Fix each field the errors name, as `.skilled/skills/sk-code/sk-code-quality/references/quality-config.md` describes, then rerun |
| The quality status reports CHECKLIST_MISSING | A declaration names a checklist file that is not there. Restore the file, or fix the `checklists[]` row or the surface's `quality` block that names it, then rerun |
| The applied rules show a refused override section | Fix or remove each row the reason names: a floor rule cannot be overridden, and a machine-checked id takes `none` only. Run `node .skilled/skills/sk-code/shared/scripts/check-rule-overrides.cjs <checklist.md>` to check it, then rerun |
| The quality status reports CONFIG_PATH_MISSING | Create the named file, or fix the `--config` value or the `skcode.qualityConfig` git config value that names it |
| Quality init reports CONFIG_EXISTS | The file is kept and never overwritten. Edit it by hand, or delete it and rerun `/doctor:sk-code quality` |
| Quality init reports OUTSIDE_REPOSITORY | `.sk-code` is a link that leads out of the repository. Replace it with a real folder, then rerun |
| Route manifest parse error | Run `bash .skilled/commands/doctor/scripts/route-validate.sh` |

End interactive presentations with: `What would you like to do next?`

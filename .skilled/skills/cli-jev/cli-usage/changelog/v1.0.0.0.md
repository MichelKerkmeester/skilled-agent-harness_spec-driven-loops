## What's New at a Glance

- **The hub gains its first `packetKind: "transport"` mode, `cli-jev`.** Through the hub's `transport-axis` extension, it dispatches the TypeSafe Jev CLI (`jev`), pinned at 0.6.2, for `noul` probabilities, `choice` selections, `score` positions and batched `run` requests. It declares `mutatesWorkspace: false` and forbids `Write`, `Edit` and `Task`.
- **Eight hard rules have implemented checks.** They cover availability, stdin bounding, `choice` and `score` cardinality, `--value` against `run`, the `custom` endpoint requirement, inline credentials and host-only `jev-mcp`.
- **Dispatch identifies Jev by command.** `jev` and `jev-mcp` resolve to `cli-jev` from the command, not from text that merely contains the word.
- **Four references and one asset document Jev.** The references include the CLI contract with its exit-code taxonomy, the provider and model table with per-provider translation, four integration patterns and the `jev-mcp` server contract with its operator step. The question-shaping card is the asset.
- **`jev-mcp` remains unwired in repository MCP config.** It ships in the same installation and is documented, while the operator chooses the host and config file.
- **Live provider responses remain unconfirmed.** With no Jev provider key in the workspace, `references/providers-and-models.md` marks every statement about live provider responses as unconfirmed. It records, with receipts, the conclusion derived from the vendored source that an OpenAI-compatible LLM Gateway key cannot front Jev without a translating proxy because the request and response use the native System One contract.
- **Jev cannot be pinned as a `/deep:research` executor.** It has no file tools, loop or lineage, so `EXECUTOR_KINDS` gains no entry.

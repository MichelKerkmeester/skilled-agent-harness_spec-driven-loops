The hub now routes typed Jev judgments through `cli-jev`. Jev reads state. It prints a value. It does not edit or run anything.

## What's New at a Glance

- **The hub gains its first `packetKind: "transport"` mode, `cli-jev`.** Through the hub's `transport-axis` extension, it dispatches the TypeSafe Jev CLI (`jev`). It is pinned at 0.6.2. It handles `noul` probabilities, `choice` selections, `score` positions and batched `run` requests. It declares `mutatesWorkspace: false`. It forbids `Write`, `Edit` and `Task`.
- **Eight hard rules have implemented checks.** They cover availability and stdin bounding. They cover `choice` and `score` cardinality. They cover `--value` against `run` and the `custom` endpoint requirement. They cover inline credentials and host-only `jev-mcp`.
- **Dispatch identifies Jev by command.** `jev` and `jev-mcp` resolve to `cli-jev` from the command. They do not resolve from text that merely contains the word.
- **Four references and one asset document Jev.** The references include the CLI contract and its exit-code taxonomy. They include the provider and model table with per-provider translation. They include four integration patterns. They include the `jev-mcp` server contract with its operator step. The question-shaping card is the asset.
- **`jev-mcp` remains unwired in repository MCP config.** It ships in the same installation and is documented. The operator chooses the host and config file.
- **Live provider responses remain unconfirmed.** The workspace has no Jev provider key. So `references/providers-and-models.md` marks every statement about live provider responses as unconfirmed. It records a conclusion with receipts. The conclusion comes from the vendored source. An OpenAI-compatible LLM Gateway key cannot front Jev without a translating proxy. That is because the request and response use the native System One contract.
- **Jev cannot be pinned as a `/deep:research` executor.** It has no file tools, loop or lineage. So `EXECUTOR_KINDS` gains no entry.

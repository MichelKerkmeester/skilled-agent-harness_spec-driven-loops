# v0.1.0.0, cli-orca: Orca CLI as a Standalone Skill

The first `cli-orca` release moves Orca CLI work out of the `mcp-tooling` parent hub.

- It ran there as the `mcp-orca-cli` mode.
- The standalone class-S skill brings its own routing contract and safety envelope.
- It has authored references and verbatim snapshots for all eight official Orca skills.

The standalone skill ships references and snapshots for the official Orca skills.

- Authored references cover all eight official Orca skills.
- The set includes an overview.
- Each official skill has a verbatim snapshot.
- The release records snapshot provenance for each skill.

Routing and safety rules carry forward into the standalone skill.

- The routing contract follows the running Orca CLI version.
- A bare `orca` token does not route.
- The safety envelope is carried forward.
- The predecessor mode versions are superseded.

&nbsp;

## Why This Release

The `mcp-tooling` hub could not hold one authored reference for each official Orca skill.

- Nor could it hold one verbatim snapshot for each.

## Orca CLI Skill

Orca CLI work now lives in a standalone class-S skill.

#### A Root Without Hub Files <a id="c-a-root-without-hub-files"></a>

- The class-S root is `.skilled/skills/cli-orca/`.
- `SKILL.md` is its only discovery surface.
- The class-S contract forbids `mode-registry.json`, `hub-router.json` and `description.json` there.

#### The Hub Returns to Nine Modes <a id="c-the-hub-returns-to-nine-modes"></a>

- The hub returns to nine modes.
- `mcp-tooling` sheds one non-MCP member.
- It keeps its single responsibility of MCP tool bridging.
- The `mcp-orca-cli` mode leaves the `mcp-tooling` parent hub.
- The predecessor packet moved to `specs/cli-orca/001-mcp-orca-cli`.
- It is a live packet with an addendum recording its supersession.

&nbsp;

## Official Orca Skills

The skill carries references and snapshots for the eight official Orca skills.

#### References Cover Each Skill <a id="c-references-cover-each-skill"></a>

- `references/orca-skills/` contains an authored reference for `computer-use`, `linear-tickets`, `orca-cli`, `orca-emulator`, `orca-emulator-android`, `orca-linear`, `orca-per-workspace-env` and `orchestration`.
- The set includes an overview.
- Its overview includes the boundary matrix and install commands.

#### Snapshots Preserve Upstream Files <a id="c-snapshots-preserve-upstream-files"></a>

- `assets/<name>.txt` contains each official `SKILL.md`.
- Each official skill has a verbatim snapshot.
- Each is an unmodified copy from the vendored `orca-main` tree at declared app version `1.4.197`.
- The `.txt` extension keeps upstream bytes outside the repository's frontmatter contracts for Markdown leaves.

## Routing Boundaries

Routing follows the running CLI and qualified Orca terms.

#### Flags Follow the Running CLI <a id="c-flags-follow-the-running-cli"></a>

- The routing contract follows the running Orca CLI version.
- The contract resolves exactly one executable: `ORCA_CLI_COMMAND`, `orca-dev`, `orca-ide` or `orca`.
- It loads the version-matched `orca-cli` guide from that binary before trusting any flag.
- It records a capability the guide does not establish as unknown.

#### Qualified Terms Set the Route <a id="c-qualified-terms-set-the-route"></a>

- A bare `orca` token never routes.
- That is because it also matches the `OpenOrca` model label.
- It also matches the GNOME Orca screen reader on Linux.
- Orca-qualified multi-word phrases and named Orca surfaces define routing.
- Generic worktree, terminal, browser and orchestration vocabulary stays with the sibling owners.

&nbsp;

## Safety Boundaries

The safety envelope and receipt rules carry forward.

#### The Safety Envelope Carries Forward <a id="c-the-safety-envelope-carries-forward"></a>

- State-changing work requires explicit authorization.
- Read-only discovery stays free.
- The archive-hook gate survives on worktree deletion.
- That is because a force flag does not bypass a failed hook.

#### Receipts Keep Actions Unconfirmed <a id="c-receipts-keep-actions-unconfirmed"></a>

- Receipt rules cover terminal inputs, bulk closes and denied share or publish outcomes.
- An accepted terminal input is not a started turn.
- A bulk close stays unverified until the host confirms every process stopped.
- A denied share or publish is a final permission result rather than a retry cue.

#### Untrusted Inputs Stay Untrusted <a id="c-untrusted-inputs-stay-untrusted"></a>

- Repositories, terminals, artifacts, skill files and fetched pages are treated as untrusted.
- Page-provided text never becomes shell, `eval` or `exec` input without explicit authorization.

## Snapshot Provenance

The release records provenance for each snapshot.

#### Provenance Records Each Snapshot <a id="c-provenance-records-each-snapshot"></a>

- `assets/PROVENANCE.md` records each skill's `releaseRevision`, `packageDigest`, `gitTreeSha` and `SKILL.md` sha256 from the snapshot's `current-manifest.json`.
- It also records the snapshot source tree, declared app version, snapshot date and unknown source commit status.
- It includes the source, declared app version and manifest data.
- The provenance record includes the refresh procedure for a newer snapshot.

## Supersession

Earlier mode versions are superseded.

#### Earlier Mode Versions Are Superseded <a id="c-earlier-mode-versions-are-superseded"></a>

- The superseded `mcp-orca-cli` versions are `v0.1.0.0` and `v0.1.1.0`.
- Both were released under the `mcp-tooling` hub on `2026-09-19`.
- The first introduced the CLI-first Orca workflow packet for the hub.
- The second closed its documentation gaps.
- Its routing, mutation gates and safety semantics were unchanged.
- The hub no longer carries the retired packet.

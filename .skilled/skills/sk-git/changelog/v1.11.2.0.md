# v1.11.2.0, The Numbered Sweep Keeps a Worktree Whenever It Cannot Be Sure

Four places in the worktree reaper could read a failure as good news. A failed worktree list looked like a list with no worktrees in it, a half-finished process listing looked like an idle worktree, and a database inside a build folder looked rebuildable. The squash-merge check also wrote objects into the repository during a dry run. Each of the four now ends in keep.

> Spec folder: `specs/sk-git/035-fsmonitor-daemon-and-worktree-relocation-regression/006-numbered-worktree-cleanup` (Level 2)

&nbsp;

## What's New at a Glance

- **An unreadable worktree registry no longer looks empty.** When `git worktree list` fails or times out, the reaper judges no worktree and deletes no session marker or socket directory that run.
- **A partial process listing counts as busy.** A listing that printed rows and then exited non-zero is no longer trusted as a complete answer.
- **SQLite files and `.state` folders stay protected in any folder.** An ignored `dist/session.sqlite` now keeps its worktree, as the catalog always said it would.
- **A dry run writes nothing to the repository.** The squash-merge check merges inside a throwaway object directory that is deleted afterwards.

&nbsp;

## Upgrade

No migration required. A worktree that held a SQLite file or a `.state` folder inside a build or cache folder was removable before and is now kept, so remove it by hand once you are sure nothing in it matters. `GIT_BOUND_SECONDS` is an internal per-call override, so set `SPECKIT_GIT_TIMEOUT` to change the git bound.

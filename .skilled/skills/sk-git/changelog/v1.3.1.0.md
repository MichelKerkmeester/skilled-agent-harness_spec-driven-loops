Safety hardening protects owner-first worktree operations after an adversarial review reproduced correctness and safety defects the original harnesses missed because they had never exercised adversarial inputs. The release changes no public or tooling interface, branch grammar or command surface. Its fixes are internal, with permanent regression coverage backing the safety guarantees in code rather than assertion.

## What's New at a Glance

- **`worktree-naming.sh` now reserves distinct numbers during stale-lock recovery.** The previous dead-lock reclaim could let two contenders proceed as owner and mint the same number. Only one contender can win the atomic rename-steal: it renames the lock directory aside, discards the stale lock and races a fresh `mkdir` rather than re-inserting it. N concurrent allocations always yield N distinct, monotonically increasing numbers. A high-water persistence failure now aborts allocation without emitting a number, and the validators enforce the documented `0001..9999` bound and exact `.worktrees/<pair>` path.
- **`worktree-reaper.sh` requires proof that a worktree is safe to remove.** The complete session-marker file must match a PID grammar, and malformed markers keep the worktree because ambiguity is not proof of inactivity. A `work/*` branch is reaped only when it is an exact `work/<runtime>/<slug>` triple whose runtime and slug match the directory basename. `--reap-daemons` signals a daemon only when its referenced worktree or database path is gone and the PID identity still matches.
- **`worktree-session.sh` rejects unsafe inputs before they act.** A runtime identity that cannot form a legal Git ref is refused before `worktree add`, and child execution no longer passes the diagnostic reason in the runtime arguments. Entries in `SPECKIT_WORKTREE_SHARED_PATHS` containing `..` or absolute components are rejected. Source and destination paths are canonicalized and containment-checked so a shared-path copy cannot delete or symlink outside the worktree.
- **`pre-push` separates invalid names from validator failures.** A genuine invalid name still blocks, while internal validator errors such as a failed owner-discovery scan fail open so tooling faults do not block legal pushes. Only version-controlled `SKILL.md` files can authorize remote owners, so an untracked skill can no longer authorize one.
- **Sourced allocator behavior and closeout wording are corrected.** The sourceable allocator uses a guarded strict-mode pattern without imposing `set -e` on callers that source it. The related closeout docs for the first ship were reconciled to describe the hardened behavior and to replace blanket "0-ahead" cleanup wording with reachability-based losslessness.

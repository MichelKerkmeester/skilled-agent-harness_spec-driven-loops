# v1.11.13.0, A Nested Lockfile Package Installs in a New Worktree

`worktree-naming.sh create` skipped the install for `.skilled/skills/system-spec-kit`. Provisioning decides a package is installed when it finds the package's first dependency in a `node_modules` folder above it. `.skilled` had already installed `@types/node`, system-spec-kit's first dependency, so system-spec-kit looked installed. Its own `npm ci` never ran, and four builds failed in every new worktree.

&nbsp;

## What's New at a Glance

- The npm walk stops where npm installs.
  - It ends at the nearest folder holding a `package-lock.json`.
  - A workspace member has no lockfile, so it still counts its workspace root's install.
  - With no lockfile on the way, the worktree root bounds the walk, as before.
- A new worktree provisions with no failed build.
  - Before: `10 installed, 1 built, 4 already present, 4 failed`.
  - After, on the same tree: `0 failed`.
- A regression case covers a nested lockfile package and a workspace member.

&nbsp;

## Upgrade

A worktree created before this release still lacks system-spec-kit's dev dependencies. Run `worktree-naming.sh provision <path>` once on it.

&nbsp;

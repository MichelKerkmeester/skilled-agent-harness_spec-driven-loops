# v0.17.17.0, Launchers That Start Together Settle on One Owner

When two advisor launchers started at the same moment, the race for the owner lease could go wrong three ways. The loser could stop itself, a reclaim could delete the lease the winner had just written or a second client could kill a daemon that was still starting. Each of these is fixed, and two sessions that open together now share one daemon.

> Spec folder: `specs/system-speckit/053-ci-workflow-efficiency/015-advisor-lease-reclaim-flake` (Level 2)

&nbsp;

## What's New at a Glance

- **A losing launcher defers to the winner.** The owner lease is now written in one step, so the loser reads the winner's complete lease and steps aside. Before, it could read the lease while it was still empty, take itself for the owner and stop itself.
- **A reclaim removes only the stale lease it read.** If another launcher has written a fresh lease in the meantime, the reclaim puts it back and defers to it, so two launchers never both believe they own the advisor.
- **A second client waits for a daemon that is still starting.** The daemon opens its connection only after its startup work. A client that arrives first now waits up to seven seconds for it and joins it, where it used to kill the starting daemon and launch a new one. `SPECKIT_LEASE_STARTUP_GRACE_MS` sets a longer wait, up to 30 seconds. With `SPECKIT_LAUNCHER_BRIDGE_DISABLED=1` the client only reports the owner, so it reports at once without waiting.
- **A damaged owner lease no longer blocks startup.** A lease file that holds no readable owner, such as the empty one a launcher killed mid-write used to leave, is reclaimed. Before, every later launcher stopped against it, so no daemon could start.
- **The two-launcher test waits for the daemon.** The CI test that starts two launchers against a stale lease now waits until the surviving daemon has started, so a slow runner no longer fails it.

&nbsp;

## Upgrade

No action is needed. Each launcher picks up the new behavior the next time it starts.

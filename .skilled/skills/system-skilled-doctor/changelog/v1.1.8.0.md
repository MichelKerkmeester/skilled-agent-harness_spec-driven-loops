# v1.1.8.0, The Hub Check Reads the Hub's Own Repository

The parent hub check used to read every hub's data from its own checkout. Run from Skilled on a vendored project's hub, it checked that hub against Skilled's canary cases. Every mode Skilled does not ship then failed. The check now reads a hub's data from the repository that holds the hub.

&nbsp;

## What's New at a Glance

- The check now uses two roots.
  - Its own code comes from its own checkout.
  - So do the shared contract libraries and the routing-shape debt ledger.
  - The hub's canary cases, bound commands, drift guard and advisor come from the hub's repository.
- A vendored project's `sk-code` hub now passes from the Skilled checkout.
  - Before, it printed 13 `5k-canary` failures and exited 1.
  - Now it prints `PASS: 5k-canary` and exits 0.
- A hub repository with no canary fixture reads as not applicable.
  - The line names that repository: `no compiled-routing canary fixture for hub "sk-code" in <repo>, leg not applicable`.
  - The check never falls back to its own checkout's fixture.
- A hub outside any repository still reads the checker's own checkout.
  - Temp test hubs keep their old results.
- `PARENT_HUB_CHECK_COMMANDS_DIR` still overrides the commands tree.

&nbsp;

## Upgrade

No migration required. Every Skilled hub gives the same verdicts as before. A project that vendors Skilled keeps its own canary cases. Never add its modes to Skilled's fixture.

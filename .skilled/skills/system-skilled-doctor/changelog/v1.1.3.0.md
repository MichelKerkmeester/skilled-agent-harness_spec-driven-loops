# v1.1.3.0, Re-pins Stop Blocking Replaced Folders

A skill-root overlay can replace a whole folder. Upstream may change a file in that folder that your copy lacks. The re-pin copy then wrote upstream's file there. `repin --stage` called it a live edit and blocked. It also told you to capture it, which would pull upstream's file into your overlay. The stage now knows the copy wrote it.

> Spec folder: `specs/system-speckit/runtime-and-release/006-test-cycle-speed/006-overlay-replaced-subtree-repin`

&nbsp;

## What's New at a Glance

- **The copy's own file no longer blocks.** A file inside a replaced folder that holds upstream's bytes shows as `overlay-edited`. `apply` deletes it, and the stage goes on.
- **Your own files still count as yours.** A file you add inside a replaced folder keeps showing as `live-edited`. Its bytes differ from upstream's, so it stays yours to capture.
- **The check reads the right commit.** During a re-pin it compares with the new commit. Before the copy it compares with the old one. Outside a re-pin it uses the manifest's pin, when the pin names a `checkout`.

&nbsp;

## Upgrade

Nothing to run. A `repin.exclude` line you added only to get past this block can go on your next re-pin.

# v1.0.0.0, Hub Wiring

The bots runtime already ran from its CLI. This release gives it a hub. A request to author, run, schedule or check a bot now has a route.

&nbsp;

## What's New at a Glance

- Four `metadata` modes: author, run, schedule and status.
- Each mode is its own packet, with a router and one reference leaf.
- `bots inbox` routes to status. `bots answer` routes to run.
- `/bots:author`, `/bots:run`, `/bots:schedule` and `/bots:status` ship with grants cut to each mode.
- `/doctor:bots` runs the definition checker read-only over a `bots/` folder.
- Every routing signal names a bot or the bot-only term needs-you. Bare run, schedule or status phrasing does not reach the hub.

&nbsp;

## Upgrade

A new install needs no migration. The hub ships a compiled activation manifest and is on by default. The compiled front door serves its routes. `SPECKIT_COMPILED_ROUTING=0` sends every hub back to `hub-router.json` and the root `ROUTER.md`.

A job installed before this release lacks the pinned state root and identity. Run `bots schedule install <id>` once per installed bot. Run `bots schedule install drain` for an installed drain job. A reinstall keeps a first-install or definition hold. A bot disabled with `bots disable` refuses the reinstall with `label-kill-switch`. Run `bots enable <id>` first, reinstall, then run `bots disable <id>` again to restore the kill switch.

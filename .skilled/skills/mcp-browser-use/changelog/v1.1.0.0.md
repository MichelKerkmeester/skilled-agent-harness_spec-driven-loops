# v1.1.0.0, Browser Requests Reach the Hub and the Right Mode

The three modes were registered, but nothing reached them. The advisor still sent Chrome DevTools requests to `mcp-tooling`. The root router loaded no leaves. A mode counts as integrated only when both routing stages reach it. This release wires both.

&nbsp;

## What's New at a Glance

- The advisor picks this hub for browser requests.
  - `graph-metadata.json` carries the vocabulary of all three modes.
  - `agentic browser` and `ai browser automation` now land here, not in `mcp-tooling`.
  - Aside is named by phrases such as `use aside` and `run aside`.
  - Lighthouse is named by `run lighthouse` or `lighthouse audit`.
  - Bare `aside`, `lighthouse` and `click through` stay out of stage one. Otherwise "as an aside" or "click-through rate" would land here.
  - The Chrome, DevTools, HAR, staging and browser-console boosts now name this hub.
- The hub picks the mode.
  - Bare `aside` is back in the Aside aliases. Without it, "run aside on the pricing page" deferred.
  - "replay this signed-in" goes to Aside.
  - "browser I already have open" goes to Bladebro.
  - "export a HAR" goes to Chrome DevTools.
  - Generic phrasing such as "browser automation" still defers.
- A compiled route serves the hub.
  - It is the eighth hub with its own compiled routing engine.
  - The route returns the mode, not the legacy sentinel.
- The root router loads leaves.
  - `ROUTER.md` is `active` with matching intent and resource maps.
  - The maps cover Chrome DevTools, Lighthouse and trace, Aside and Bladebro.
  - `leaf-scopes.json` makes the new Lighthouse leaf routable.
- `SKILL.md` has a capability matrix.
  - Lighthouse and performance trace are separate rows.
  - Both run on the MCP lane only.

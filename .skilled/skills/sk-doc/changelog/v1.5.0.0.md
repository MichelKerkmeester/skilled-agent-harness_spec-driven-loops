# v1.5.0.0, A Reshaped sk-doc Surface

Version 1.5.0.0 is the first major `sk-doc` iteration after the v1.3.0.0 series. Packet 102 ships five sequential phases that reshape the skill surface through reference relocation, a dedicated skill-package README asset, the rename from `@create` to `@markdown`, manual coverage for the renamed agent and remediation of phase-parent deep-review findings. All five phases land as additive child packets under the Level 2 phase parent: `001-sk-doc-reference-relocation`, `002-sk-doc-skill-readme-asset`, `003-markdown-agent-rename`, `004-sk-doc-playbook-markdown-agent-coverage` and `005-deep-review-p1-p2-remediation`.

> Spec folder: `.opencode/specs/skilled-agent-orchestration/102-sk-doc-skill-readme-and-structure/{001-sk-doc-reference-relocation, 002-sk-doc-skill-readme-asset, 003-markdown-agent-rename, 004-sk-doc-playbook-markdown-agent-coverage, 005-deep-review-p1-p2-remediation}` (Level 2)

## Why This Release

The rename separates the documentation executor from the `/create:*` command family, whose identities had been conflated and could put command callers at risk.

---

## What's New at a Glance

- **Creation guides leave `references/specific/`.** The guides now sit at the references root alongside global standards.
- **Skill packages gain a dedicated README scaffold.** `/create:sk-skill` uses a scaffold separate from folder README authoring.
- **The documentation executor changes from `@create` to `@markdown`.** No new top-level commands ship, and the `/create:*` command family stays surface-stable.
- **The manual playbook adds `@markdown` coverage across three CLI runtimes.** Its preamble, Categories row and Scenario Index now align on the runtimes covered.
- **SD-019 changes to `dispatch_inline_contract`.** Its Codex run follows the agent instructions without dispatching a sub-agent.
- **A transactional pass closes the phase-parent deep-review findings.** The parent spec gains a Known Issues register.

## Documentation Resources

#### Creation Guides at the Root

The six sk-doc creation guides moved from `.opencode/skills/sk-doc/references/specific/` to the references root. `specific/` was the only directory under `references/` that grouped creation guides separately from global standards, and `global/` remains for the global-standards subset.

Smart routing, README related-document links, asset-template links and manual-playbook expected resources now point to the root-level locations. `/create:*` command documents, YAML assets and `graph-metadata.json` source-doc paths were updated as well. The empty `specific/` directory is gone. YAML key names such as `specific_creation` remain unchanged, avoiding behavior changes beyond the path relocation.

**Breaking:** The former `references/specific/` location no longer contains the creation guides.

&nbsp;

#### A README Scaffold for Skill Packages

The skill-creation flow adds `.opencode/skills/sk-doc/assets/skill/skill-readme-template.md` for skill-package README scaffolding inside `/create:sk-skill`. The template sits alongside the SKILL.md and reference templates and follows `skill_asset_template.md`. It starts with a short H1 introduction, then `## 1. OVERVIEW`, `Purpose`, `Usage` and `Location & Naming` before the content model.

The `SKILL_CREATION` intent now loads four resources instead of three, and `references/skill-creation.md` adds README guidance. Folder README authoring continues to use `assets/readme/readme-template.md`, while skill-package README authoring uses the dedicated asset. The `assets/skill/` category joins the four existing asset categories and separates these scaffolds because they target different content models. This is the only new asset path in the skill-creation flow.

## Agent Identity

#### Documentation Work Uses `@markdown`

The documentation executor changes from `@create` to `@markdown` across `.opencode/agents/markdown.md`, `.claude/agents/markdown.md` and `.codex/agents/markdown.toml`. Codex's prior `.codex/agents/create.toml` was wired through `[agents.create]` in `.codex/config.toml`. The registry entry changes to `[agents.markdown]` with `config_file = "agents/markdown.toml"`. Orchestrator and code-agent references route documentation and component authoring through `@markdown`.

The `/create:agent`, `/create:sk-skill`, `/create:feature-catalog`, `/create:testing-playbook`, `/create:folder_readme` and `/create:changelog` commands keep every invocation unchanged. Internally these commands now route their component-authoring work through `@markdown` instead of `@create`.

**Breaking:** `@create` no longer identifies the documentation executor.

## Manual Testing and Dispatch

#### Coverage Spans Three CLI Runtimes

The new `06--agent-dispatch/` section first adds three `dispatch_real` scenarios invoking `@markdown`. The playbook preamble, Categories row and Scenario Index now agree on three runtimes, correcting the prior gap where the preamble admitted three CLI runtimes while listing only two.

SD-018 uses cli-claude-code with Claude Opus 4.7. SD-019 uses cli-codex with `gpt-5.5 / fast` and sandbox network access. SD-020 uses cli-opencode with the DeepSeek v4 Pro direct API, `deepseek/deepseek-v4-pro`, `--pure` and `--variant high`.

&nbsp;

#### Codex Uses an Inline Contract

In Codex v0.130.0, there are two registries. `.codex/config.toml` user-defined agents are read for CLI context, but the separate baked-in `SpawnAgent` runtime allowlist does not include them. Real typed-agent dispatch through Codex `SpawnAgent` remains upstream-blocked in that version.

SD-019 changes to `execution_mode: dispatch_inline_contract`, explicitly forbids `SpawnAgent`, pre-answers Gate 3 with `D) Skip` and requires a BINDING trace plus contract-acknowledgment fields in its success criteria. It also sets `expected_skip_in_non_interactive: true` with a documented rationale. During the cli-codex run, `gpt-5.5` reads `developer_instructions` from `.codex/agents/markdown.toml` and follows them itself without dispatching a sub-agent.

SD-018 and SD-020 still verify real typed-agent dispatch, so the three CLIs test the same agent identity through three different mechanisms. A future Codex release that maps `.codex/config.toml` user-defined agents into the `SpawnAgent` runtime list would let SD-019 return to `dispatch_real` and exercise typed-agent dispatch under `codex exec`.

## Review Remediation

#### Findings Close in One Pass

A single transactional pass using the `cli-codex gpt-5.5 / high / fast` dispatch closed all 16 findings from the 102 phase-parent deep-review in 129 seconds. Seven P1 status-sync and handoff issues plus nine P2 hygiene items were resolved across nine files, with 26 checklist items marked.

The parent `102/spec.md` adds a Known Issues register that cross-references F-001, F-002 and F-003 plus every new finding ID. The structural P1, the cli-codex `@markdown` dispatch gap, was resolved later in the same session through the inline-contract workaround.

## Upgrade Notes

- **Adopt.** Downstream agents and orchestrators that used `@create` as the documentation executor must switch to `@markdown`.
- **Repoint.** Consumers of `[agents.create]` must read `[agents.markdown]`. Saved prompts and templates that name `agents/create.md` or `agents/create.toml` must point to `agents/markdown.md` or `agents/markdown.toml`.
- **Drop.** Consumers that depended on the `references/specific/` prefix must use `references/skill-creation.md`, `references/agent_creation.md`, `references/readme_creation.md`, `references/install_guide_creation.md`, `references/feature_catalog_creation.md` or `references/manual_testing_playbook_creation.md`.

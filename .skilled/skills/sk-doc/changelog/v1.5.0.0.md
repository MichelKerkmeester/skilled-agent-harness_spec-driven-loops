# v1.5.0.0, A Reshaped sk-doc Surface

Version 1.5.0.0 is the first major `sk-doc` iteration after the v1.3.0.0 series.

- Packet 102 ships five sequential phases.
- They reshape the skill surface through reference relocation.
- They add a dedicated skill-package README asset.

The phases rename `@create` to `@markdown` and add manual coverage.

- Manual coverage targets the renamed agent.
- One phase remediates phase-parent deep-review findings.

All five phases land under one phase parent.

- The parent is Level 2.
- Child packets are additive.
- The packets are `001-sk-doc-reference-relocation`, `002-sk-doc-skill-readme-asset`, `003-markdown-agent-rename`, `004-sk-doc-playbook-markdown-agent-coverage` and `005-deep-review-p1-p2-remediation`.

> [!IMPORTANT]
> 2 changes can break an existing setup.
>
> 1. The old references path no longer holds the guides. [Creation Guides at the Root](#c-creation-guides-at-the-root)
> 2. `@create` no longer names the documentation executor. [Documentation Work Uses @markdown](#c-documentation-work-uses-markdown)

&nbsp;

## Why This Release

The rename separates the documentation executor from the `/create:*` command family.

- Their identities had been conflated.
- That could put command callers at risk.

## Documentation Resources

#### Creation Guides at the Root <a id="c-creation-guides-at-the-root"></a>

- The six sk-doc creation guides moved to the references root.
- They moved from `.opencode/skills/sk-doc/references/specific/`.
- `specific/` was the only directory under `references/` grouping guides apart from global standards.
- `global/` remains for the global-standards subset.
- Smart routing now points to the root-level locations.
- README related-document links now point to the root-level locations.
- Asset-template links now point to the root-level locations.
- Manual-playbook expected resources now point to the root-level locations.
- `/create:*` command documents were updated as well.
- YAML assets were updated as well.
- `graph-metadata.json` source-doc paths were updated as well.
- The empty `specific/` directory is gone.
- YAML key names such as `specific_creation` remain unchanged.
- That avoids behavior changes beyond the path relocation.

> [!WARNING]
> The former `references/specific/` location no longer contains the creation guides. Use the root-level reference paths.

#### A README Scaffold for Skill Packages <a id="c-a-readme-scaffold-for-skill-packages"></a>

- The flow adds `.opencode/skills/sk-doc/assets/skill/skill-readme-template.md`.
- It scaffolds skill-package READMEs inside `/create:sk-skill`.
- The template sits alongside the SKILL.md and reference templates.
- It follows `skill_asset_template.md`.
- It starts with a short H1 introduction.
- Then come `## 1. OVERVIEW`, `Purpose`, `Usage` and `Location & Naming`.
- These sections come before the content model.
- The `SKILL_CREATION` intent now loads four resources instead of three.
- `references/skill-creation.md` adds README guidance.
- Folder README authoring continues to use `assets/readme/readme-template.md`.
- Skill-package README authoring uses the dedicated asset.
- The `assets/skill/` category joins the four existing asset categories.
- It separates these scaffolds because they target different content models.
- This is the only new asset path in the skill-creation flow.

## Agent Identity

#### Documentation Work Uses `@markdown` <a id="c-documentation-work-uses-markdown"></a>

- The documentation executor changes from `@create` to `@markdown`.
- The change spans `.opencode/agents/markdown.md`, `.claude/agents/markdown.md` and `.codex/agents/markdown.toml`.
- Codex's prior `.codex/agents/create.toml` was wired through `[agents.create]` in `.codex/config.toml`.
- The registry entry changes to `[agents.markdown]`.
- It uses `config_file = "agents/markdown.toml"`.
- Orchestrator and code-agent references route documentation through `@markdown`.
- They route component authoring through `@markdown`.
- `/create:agent`, `/create:sk-skill`, `/create:feature-catalog`, `/create:testing-playbook`, `/create:folder_readme` and `/create:changelog` keep every invocation unchanged.
- No new top-level commands ship.
- The `/create:*` command family stays surface-stable.
- Internally these commands now route component-authoring work through `@markdown`.
- They route it instead of `@create`.

> [!WARNING]
> `@create` no longer identifies the documentation executor. Switch consumers to `@markdown`.

## Manual Testing and Dispatch

#### Coverage Spans Three CLI Runtimes <a id="c-coverage-spans-three-cli-runtimes"></a>

- The new `06--agent-dispatch/` section first adds three `dispatch_real` scenarios.
- The scenarios invoke `@markdown`.
- The preamble, Categories row and Scenario Index now agree on three runtimes.
- That corrects the prior gap.
- The preamble admitted three CLI runtimes while listing only two.
- The cli-claude-code scenario uses Claude Opus 4.7.
- The cli-codex scenario uses `gpt-5.5 / fast` and sandbox network access.
- The cli-opencode scenario uses the DeepSeek v4 Pro direct API.
- It uses `deepseek/deepseek-v4-pro`, `--pure` and `--variant high`.

#### Codex Uses an Inline Contract <a id="c-codex-uses-an-inline-contract"></a>

- In Codex v0.130.0, there are two registries.
- `.codex/config.toml` user-defined agents are read for CLI context.
- The baked-in `SpawnAgent` runtime allowlist does not include them.
- Real typed-agent dispatch through Codex `SpawnAgent` remains upstream-blocked in that version.
- The cli-codex scenario changes to `dispatch_inline_contract`.
- It sets `execution_mode: dispatch_inline_contract`.
- It explicitly forbids `SpawnAgent`.
- It pre-answers Gate 3 with `D) Skip`.
- Its success criteria require a BINDING trace plus contract-acknowledgment fields.
- It sets `expected_skip_in_non_interactive: true` with a documented rationale.
- During the cli-codex run, `gpt-5.5` reads `developer_instructions`.
- It reads them from `.codex/agents/markdown.toml`.
- It follows them itself without dispatching a sub-agent.
- The cli-claude-code and cli-opencode scenarios still verify real typed-agent dispatch.
- So the three CLIs test the same agent identity through three different mechanisms.
- A future Codex release could map `.codex/config.toml` user-defined agents into the `SpawnAgent` runtime list.
- That would let the cli-codex scenario return to `dispatch_real`.
- It would then exercise typed-agent dispatch under `codex exec`.

## Review Remediation

#### Findings Close in One Pass <a id="c-findings-close-in-one-pass"></a>

- A single transactional pass closed all 16 findings.
- The findings came from the 102 phase-parent deep-review.
- It used the `cli-codex gpt-5.5 / high / fast` dispatch.
- The pass took 129 seconds.
- Seven P1 status-sync and handoff issues were resolved.
- Nine P2 hygiene items were resolved.
- The work spanned nine files.
- 26 checklist items were marked.
- The parent `102/spec.md` adds a Known Issues register.
- It cross-references F-001, F-002 and F-003.
- It also references every new finding ID.
- The structural P1 was the cli-codex `@markdown` dispatch gap.
- It was resolved later in the same session through the inline-contract workaround.

## Upgrade Notes

Three actions apply, depending on which part of the old surface you used.

<details>
<summary><b>Agent Identity</b></summary>

- Downstream agents and orchestrators that used `@create` as the documentation executor must switch to `@markdown`.

</details>

<details>
<summary><b>Codex registry</b></summary>

- Consumers of `[agents.create]` must read `[agents.markdown]`.
- Saved prompts and templates that name `agents/create.md` or `agents/create.toml` must point to `agents/markdown.md` or `agents/markdown.toml`.

</details>

<details>
<summary><b>Reference paths</b></summary>

- Consumers that depended on the `references/specific/` prefix must use root-level paths.
- Those paths are `references/skill-creation.md`, `references/agent_creation.md`, `references/readme_creation.md`, `references/install_guide_creation.md`, `references/feature_catalog_creation.md` and `references/manual_testing_playbook_creation.md`.

</details>

# v2.3.7.0, A Version on Every Skill Doc

The 4-part `version` field had been limited to `SKILL.md`, so a reference, asset, catalog or playbook doc could change without any record that it had. Each skill doc now carries its own edition. `SKILL.md` keeps the skill edition, and every other doc tracks its own changes.

> Spec folder: `specs/sk-code/011-sk-code-poinytail-based-refinement/022-doc-version-and-playbook-paths/001-per-doc-versions` (Level 2)

&nbsp;

## What's New at a Glance

- **Every skill doc is versioned.** `frontmatter-version.mjs verify` requires a valid 4-part `version` on every hand-authored doc with frontmatter. Changelogs, tests, fixtures, runtime and benchmark output, and the spec-doc examples stay out of scope.
- **A body change raises the version at commit.** The new `bump` mode compares each staged doc's body, frontmatter excluded, with the base and raises the third segment, so `1.2.3.4` becomes `1.2.4.0`. A frontmatter-only change raises nothing, and a hand raise is kept.
- **The pre-commit hook runs it.** The `doc-version-bump` gate raises and re-stages each changed doc. `SPECKIT_SKIP_DOC_VERSION_BUMP=1` skips it, and a pull request runs `bump --check` against its base.
- **The packager and the post-edit check agree.** `package_skill.py --check --strict` and the post-edit quality router apply the same scope rule as the engine.
- **The removed version lines are back.** Every child doc that lost its `version` line has it again, and the docs that never had one start at `1.0.0.0`.
- **Templates seed `version: 1.0.0.0`.** The README, code README and architecture templates and the playbook index generator write the field, and `frontmatter-versioning.md` states the contract and the bump rule.

&nbsp;

## Upgrade

Add `version: 1.0.0.0` to a new skill doc, or let `frontmatter-version.mjs apply` add it. Commit as usual and the hook raises the version of any doc whose body changed.

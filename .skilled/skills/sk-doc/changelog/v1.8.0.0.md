sk-doc now defines a four-part frontmatter `version` standard for skill docs. A deterministic engine stamps that version into every in-scope skill doc.

> Spec folder: `.opencode/specs/skilled-agent-orchestration/154-frontmatter-versioning`

## Why This Release

The release gives generated docs and the existing skill corpus the same enforced version rule.

## What's New at a Glance

- **The four-part frontmatter standard is now explicit.** `references/frontmatter-versioning.md` defines how skill versions are derived and inserted.
- **The version engine has four modes.** Its named operations preview changes, apply versions and check them.
- **Newly generated docs now include `version`.** The templates include the field in `create:*` output.
- **Skill validation now enforces four-part versions.** Commands remain outside that requirement.
- **The existing skill corpus now follows the standard.** Docs without frontmatter are skipped rather than synthesized.
- **Version writes are confined to the skills root.** `apply` cannot write outside that boundary.

---

## Versioning Standard

#### One Four-Part Rule

The new `references/frontmatter-versioning.md` is the single source of truth for the 4-part `X.Y.Z.W` format, the changelog-anchored derivation, the numstat-gated build segment, the line-wise insertion rule and the enforcement rollout. The version anchor is the higher of the frontmatter and changelog versions. The build segment is gated by real file edits.

The guide also records one exception: `SKILL.md` is brought to its anchor without `--update`, because the `SKILL.md` version is the anchor of record.

&nbsp;

#### Generated Docs Start Versioned

`assets/frontmatter-templates.md` and the nine doc templates now require a `version` field. Every document generated by `create:*` is born with that field.

---

## Version Tools

#### Compute and Apply Versions

The new `scripts/frontmatter-version.mjs` exposes four modes. `compute` returns a preview manifest. `apply` inserts the version line and avoids duplicates on repeat runs. `verify` checks for a value match. `gate` checks presence and format.

The engine resolves each skill's anchor and normalizes three-part versions to four-part form. It counts real edits from each file's Git history.

&nbsp;

#### Skill Checks Enforce Versions

`quick_validate.py` and `package_skill.py` now require a four-part `version` for skills. Commands keep `version` optional. The new `scripts/check-frontmatter-versions.sh` is the corpus-wide CI and pre-commit gate. It rejects in-scope docs with missing or malformed versions.

&nbsp;

#### Existing Docs Receive Versions

The standard was applied across the whole skill corpus. A total of 2,210 in-scope docs now carry four-part versions, while the 12 docs without frontmatter were skipped rather than synthesized.

---

## Safer Version Updates

#### Version Updates Fail Safely

`scripts/frontmatter-version.mjs` removed a dead variable and raised the git-history `maxBuffer` from 64 to 256 MB so a pathological history cannot silently yield a zero edit count. Its `apply` mode fails closed and writes only inside the skills root, even if `--paths` includes a stray path. `scripts/check-frontmatter-versions.sh` now fails fast with a clear message when `node` is missing from `PATH`.

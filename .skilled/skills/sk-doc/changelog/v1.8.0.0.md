# v1.8.0.0, Four-Part Frontmatter Versions

sk-doc now defines a four-part frontmatter `version` standard for skill docs.

- The four-part frontmatter standard is now explicit.
- `references/frontmatter-versioning.md` defines how skill versions are derived and inserted.
- Newly generated docs now include `version`.

A deterministic engine stamps that version into every in-scope skill doc.

- The version engine has four modes.
- Its named operations preview changes, apply versions and check them.
- Skill validation now enforces four-part versions.
- Commands remain outside that requirement.

The existing skill corpus now follows the standard.

- A total of 2,210 in-scope docs now carry four-part versions.
- The 12 docs without frontmatter were skipped rather than synthesized.
- Version writes are confined to the skills root.
- `apply` cannot write outside that boundary.

&nbsp;

## Why This Release

The release gives generated docs and the existing skill corpus the same enforced version rule.

- Generated docs get an enforced version rule.
- The existing skill corpus gets the same enforced version rule.

## Versioning Standard

The new `references/frontmatter-versioning.md` is the single source of truth. It defines how skill versions are derived and inserted.

#### One Four-Part Rule <a id="c-one-four-part-rule"></a>

- It covers the 4-part `X.Y.Z.W` format and the changelog-anchored derivation.
- It also covers the numstat-gated build segment and the line-wise insertion rule.
- The enforcement rollout is covered there too.
- The version anchor is the higher of the frontmatter and changelog versions.
- The build segment is gated by real file edits.
- The guide also records one exception.
- `SKILL.md` is brought to its anchor without `--update`.
- That is because the `SKILL.md` version is the anchor of record.

#### Generated Docs Start Versioned <a id="c-generated-docs-start-versioned"></a>

- `assets/frontmatter-templates.md` and the nine doc templates now require a `version` field.
- Every document generated by `create:*` is born with that field.

&nbsp;

## Version Tools

The new `scripts/frontmatter-version.mjs` exposes four modes. They preview changes, apply versions and check them.

#### Compute and Apply Versions <a id="c-compute-and-apply-versions"></a>

- `compute` returns a preview manifest.
- `apply` inserts the version line and avoids duplicates on repeat runs.
- `verify` checks for a value match.
- `gate` checks presence and format.
- The engine resolves each skill's anchor and normalizes three-part versions to four-part form.
- It counts real edits from each file's Git history.

#### Skill Checks Enforce Versions <a id="c-skill-checks-enforce-versions"></a>

- `quick_validate.py` and `package_skill.py` now require a four-part `version` for skills.
- Commands keep `version` optional.
- The new `scripts/check-frontmatter-versions.sh` is the corpus-wide CI and pre-commit gate.
- It rejects in-scope docs with missing or malformed versions.

#### Existing Docs Receive Versions <a id="c-existing-docs-receive-versions"></a>

- The standard was applied across the whole skill corpus.
- A total of 2,210 in-scope docs now carry four-part versions.
- The 12 docs without frontmatter were skipped rather than synthesized.

## Safer Version Updates

Version updates fail safely.

#### Version Updates Fail Safely <a id="c-version-updates-fail-safely"></a>

- `scripts/frontmatter-version.mjs` removed a dead variable.
- It also raised the git-history `maxBuffer` from 64 to 256 MB.
- So a pathological history cannot silently yield a zero edit count.
- Its `apply` mode fails closed.
- It writes only inside the skills root, even if `--paths` includes a stray path.

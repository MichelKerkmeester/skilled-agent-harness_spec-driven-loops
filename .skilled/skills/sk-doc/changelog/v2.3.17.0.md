# v2.3.17.0, The README Audit and Changelog Check Stop Flagging What Is Not Broken

The README audit reported a link to a log file as broken. It did the same for a state file or a build output. Such a path is absent from a clean checkout by design. The audit now asks git, in one call, about each unresolved path. It asks whether each path inside the repository is ignored. It reports an ignored path as resolved, with the evidence `gitignored_runtime_path`. The folder holding the path must exist or be ignored as well. So a broad rule cannot hide a mistyped link. A bare path in a package's docs now also resolves from the nearest package root. That is the nearest folder above the README that holds a `package.json`. The path is written the way the package's own tooling sees it.

Discovery now matches `README.md` and `README.markdown` exactly. The `/create:readme` command file is named `readme.md`. It was audited as a README. It drew a template failure and a coverage finding. It is no longer read. A folder whose name ends in `-fixture` is now test input. It is treated like a folder named `fixture` or `fixtures`. A numbered spec folder with that ending stays in scope.

The changelog omission check read the hash name SHA-256 as an internal id. Algorithm names such as SHA-256 and AES-256 no longer warn. Decision, requirement and task ids still warn. A task id written as a letter T and three digits now warns too.

&nbsp;

## What's New at a Glance

- **Runtime paths stop counting as broken.** A link to a git-ignored path inside the repository is reported as resolved, with its evidence.
- **Package docs resolve the way the package reads.** A bare path also resolves from the nearest package root.
- **Only real READMEs are audited.** The lowercase command file and folders named as fixtures are left out. The durable-directory manifest follows the same rule.
- **Algorithm names are not ids.** SHA-256 and AES-256 no longer draw the internal-id warning.

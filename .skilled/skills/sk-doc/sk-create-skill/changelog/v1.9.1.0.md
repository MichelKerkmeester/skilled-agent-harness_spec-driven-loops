# v1.9.1.0, The Skill Format Command Joins the Packet's Own Docs

A scaffold that points at a file the reader then deletes is a trap. The leaf manifest config template now names the router in the sibling `ROUTER.md` rather than in `SKILL.md`, the router reach check can score one skill, and the packet documents the command that brings an existing skill onto this format.

> Spec folder: `specs/sk-doc/075-doctor-sk-skill-command/007-docs-and-changelogs` (Level 2)

&nbsp;

## What's New at a Glance

- **The leaf manifest template says where the router lives.** Its note now reads that only the docs the router in the sibling `ROUTER.md` actually routes into belong in `leafRoots`, so a scaffolded leaf entry follows a file that exists.
- **The router reach check takes one skill.** `ci-router-vocabulary-reach.cjs --skill <name>` scores that root instead of walking every hub, and it refuses `--hub` beside `--skill` because the two probe different sets.
- **The packet says how a skill already in the world gets here.** Section 6 and the adopter guide name `/doctor:sk-skill`, with the read-only check, the in-place conversion of an older Skilled skill and the staged conversion of a plain one.
- **The gaps a conversion closes are listed where an adopter reads them.** The guide no longer claims a single skill has no way off the old shape, and it keeps the hub path at `/create:skill-parent` for a skill that really holds two jobs.
- **The playbook follows the command end to end.** Four scenarios cover the read-only check with its hub report, the conversion of an existing skill, the plain-skill conversion and the hub refusal, so an operator can run each path instead of inferring it.

&nbsp;

## Upgrade

No migration required. A skill scaffolded before this release keeps its leaf manifest config, and the router it names still resolves.

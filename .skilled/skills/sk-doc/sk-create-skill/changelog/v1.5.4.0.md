# v1.5.4.0, A new surface leads its tie

The parent-skill scaffold now places a new surface mode ahead of the existing surfaces in tieBreak, and its completion report names the two follow-ups it cannot run.

> Spec folder: `specs/sk-code/011-sk-code-poinytail-based-refinement/026-external-surface-priority-build/001-scaffold-surface-placement` (Level 2)

&nbsp;

## What's New at a Glance

- **A new surface leads its tie.** `/create:skill-parent update --surfaces` writes each new surface mode into `routerPolicy.tieBreak` between the workflow modes and the surfaces the hub already had, and leaves every mode already listed where it is. Before this, a new surface was appended last and lost every keyword tie to the surfaces already there.
- **The contract says it once.** `parent-hub-router-schema.md` and the integration checklist in `parent-skills-nested-packets.md` state the same rule in the same phrase as both workflow twins.
- **The report names what is left.** The completion report of a `--surfaces` run now tells you to author a canary case for each new surface and copy the fixture to its authored twin, and to commit with the hooks from `install-git-hooks.sh` installed, or refresh and copy the activation manifest by hand. The command runs neither.

&nbsp;

## Upgrade

No migration required. Existing hubs keep their `tieBreak` order.

# v1.1.0.0, Changelogs That Read Like Release Notes

Changelogs from `/create:changelog` now read like the v4 release notes instead of a machine report. Each entry opens with why the release matters, names its sections for the part of the system it changes and leaves file lists and test counts in the spec packet. The template, the workflow and the command files now teach the same shape, so what the skill describes is what the command writes.

> Spec folder: `specs/sk-doc/057-sk-create-changelog-v4-style` (Level 1)

## What's New at a Glance

- **The template teaches the v4 exemplar's shape.** Compact entries carry a summary, bold-sentence bullets and an upgrade note. Expanded entries add Why This Release, topical sections and story items.
- **A decision aid says what to leave out.** File inventories, test metrics and schema churn stay out by default, and work that was tried and reverted shrinks to one sentence.
- **Voice is checked before anything is written.** A draft with an em dash, a semicolon, an Oxford comma or a banned word is fixed first.
- **The length limits fit the exemplar.** Most headings run 2-7 words and most story items one to three paragraphs, with ceilings set so the reference release passes every check it teaches.
- **The GitHub release step is documented.** `--release` tags the version, pushes the tag and publishes the release with the changelog as its body.
- **The command files and the skill agree.** Both command workflows use the tiers, limits and format checks the template teaches.

## Upgrade

No migration required. Existing changelog files stay as written, and new changelogs follow the narrative format.

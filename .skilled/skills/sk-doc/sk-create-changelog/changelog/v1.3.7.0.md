# v1.3.7.0, An Untagged Release Takes New Work Into Its Own Entry

Release notes are often written before the release is tagged. Work keeps landing in the meantime. `/create:changelog` could only number a new entry. So adding that work opened a second untagged release. Or it meant editing the open one by hand.

&nbsp;

## What's New at a Glance

- **An open release is detected.** For the `skilled` release line, the workflow checks origin for a tag. It looks for a tag on the latest entry's version. With no tag, the release is still open. The run keeps its version.
- **New work is folded into the open entry.** The run adds sections or items. It adds a glance bullet and the spec folder. It widens the opening only enough to name the new theme. It corrects only the sentences the new work makes untrue.
- **Nothing is dropped silently.** A bump chosen for the run is not applied while the release is open. The report says so. When the tag check fails, the run numbers a new entry. It says so rather than risk editing a release that already shipped.
- **Every other component works as before.** Skill entries and a tagged release still get a new, higher version. An existing skill entry is never overwritten.

&nbsp;

## Upgrade

No migration required. To start a new release while the last one is untagged, tag and publish the open release first. A run whose open entry exists only upstream stops. It asks for a merge or rebase.

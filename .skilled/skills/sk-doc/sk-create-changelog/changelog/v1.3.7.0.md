# v1.3.7.0, An Untagged Release Takes New Work Into Its Own Entry

Release notes are often written before the release is tagged, and work keeps landing in the meantime. `/create:changelog` could only number a new entry, so adding that work either opened a second untagged release or meant editing the open one by hand.

> Spec folder: `specs/system-speckit/054-weak-model-spec-authoring/028-changelog-release-extension` (Level 2)

&nbsp;

## What's New at a Glance

- **An open release is detected.** For the `skilled` release line, the workflow checks origin for a tag on the latest entry's version. With no tag, the release is still open and the run keeps its version.
- **New work is folded into the open entry.** The run adds sections or items, a glance bullet and the spec folder, widens the opening only enough to name the new theme and corrects only the sentences the new work makes untrue.
- **Nothing is dropped silently.** A bump chosen for the run is not applied while the release is open, and the report says so. When the tag check fails, the run numbers a new entry and says so rather than risk editing a release that already shipped.
- **Every other component works as before.** Skill entries and a tagged release still get a new, higher version, and an existing skill entry is never overwritten.

&nbsp;

## Upgrade

No migration required. To start a new release while the last one is untagged, tag and publish the open release first. A run whose open entry exists only upstream stops and asks for a merge or rebase.

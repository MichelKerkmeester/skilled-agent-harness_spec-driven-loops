# v1.3.1.0, Hubs Resolve to Their Own Changelogs

`/create:changelog` now writes a hub's changelog where the hub keeps it. A hub such as `sk-doc` holds one link per mode plus `parent` in its changelog folder. It holds no entry of its own. So the workflow found no version there. It would have written beside the links. It now resolves the hub to `parent` or to the one mode a change belongs to.

## What's New at a Glance

- **A hub resolves to one of its links.** A change under `.skilled/skills/sk-doc/sk-create-changelog/` resolves to `sk-doc/create-changelog`. That is the link whose target is that packet's changelog. The hub's own files resolve to `sk-doc/parent`. So does a hint that names the hub.
- **The version reader finds the hub's versions.** It reads the resolved link. So a run for `sk-doc` now reads its newest `parent` entry. It used to find none there.
- **Identity phrases keep the skill's name.** An entry written to `sk-doc/create-changelog` still declares `sk-create-changelog v<version>`. That is because the phrase takes the `name:` in the packet's `SKILL.md`. Both workflows now say so.
- **Routing a global component changelog checks the hub.** The scenario expects the `sk-doc` hint to land in `sk-doc/parent`. It expects a mode's change to land in that mode's link.
- **Preparing release notes without publishing matches the release step.** It checks that a run without `--release` tags and publishes nothing. It used to call the release mechanics undefined.
- **The README and the command docs caught up.** They describe the search metadata, the release gate for `skilled` and the real bump rules. A troubleshooting row named a `--component` flag. It now points to the first argument. That is because no such flag exists.

## Upgrade

No migration required. A run that names a hub now lands in the hub's `parent` link.

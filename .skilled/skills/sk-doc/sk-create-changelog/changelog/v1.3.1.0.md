# v1.3.1.0, Hubs Resolve to Their Own Changelogs

`/create:changelog` now writes a hub's changelog where the hub keeps it. A hub such as `sk-doc` holds one link per mode plus `parent` in its changelog folder and no entry of its own, so the workflow found no version there and would have written beside the links. It now resolves the hub to `parent` or to the one mode a change belongs to.

> Spec folder: `specs/sk-doc/061-skilled-release-changelog/003-adjacent-alignment` (Level 2)

## What's New at a Glance

- **A hub resolves to one of its links.** A change under `.skilled/skills/sk-doc/sk-create-changelog/` resolves to `sk-doc/create-changelog`, the link whose target is that packet's changelog. The hub's own files and a hint that names the hub resolve to `sk-doc/parent`.
- **The version reader finds the hub's versions.** It reads the resolved link, so a run for `sk-doc` now reads its newest `parent` entry, where it used to find none.
- **Identity phrases keep the skill's name.** An entry written to `sk-doc/create-changelog` still declares `sk-create-changelog v<version>`, because the phrase takes the `name:` in the packet's `SKILL.md`. Both workflows now say so.
- **CHG-001 checks the hub.** The scenario expects the `sk-doc` hint to land in `sk-doc/parent` and a mode's change in that mode's link.
- **CHG-006 matches the release step.** It checks that a run without `--release` tags and publishes nothing, where it used to call the release mechanics undefined.
- **The README and the command docs caught up.** They describe the search metadata, the release gate for `skilled` and the real bump rules. A troubleshooting row that named a `--component` flag now points to the first argument, since no such flag exists.

## Upgrade

No migration required. A run that names a hub now lands in the hub's `parent` link.

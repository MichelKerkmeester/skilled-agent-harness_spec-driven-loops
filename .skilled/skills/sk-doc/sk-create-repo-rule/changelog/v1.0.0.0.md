The first release adds `create-repo-rule`, a workflow packet in the `sk-doc` parent hub, giving requested behavior and recurring failures a route into repository guidance. The spec folder has seven phases.

> Spec folder: `specs/sk-doc/040-create-repo-rules` (Level 2)

## What's New at a Glance

- **Rules live in `repo-rules/` and connect to `REPO RULES.md`.** `create-repo-rule` also revises and retires them. A repo rule supplements the `harness` rather than binding it. A live operator instruction can override a rule, which can change when it stops matching the work or be removed when it stops earning its load.
- **Four decision tests refuse most requests.** They cover Always-loaded, scope boundary, a four-part refusal test and restraint. Each refusal names the test it failed and where the content belongs instead.
- **The rule template derives from the corpus instead of copying it.** Ten elements are fixed because all eight shipped rules carry them. The numbered body is open because section count follows the subject.
- **A router template is emitted as a prerequisite when a repository has no trigger table.** The router shares almost no structure with the rules it routes to, so it is a separate template rather than a variant.
- **Creation standards add five reader tests.** They decide whether a structurally correct rule is worth loading.
- **The integration and lifecycle contract protects interrupted changes.** It defines three wiring points and create, revise and retire orderings chosen so that stopping halfway always leaves an unreferenced file rather than a router row pointing at nothing.
- **`/create:repo-rule` supports auto and confirm workflows.** It includes a presentation contract. `retire` defaults to confirm even with an auto suffix because it deletes a file and removes two router rows.
- **Rule length bands are operator-set.** The maximum is 250, 200 is good and 160 or lower is preferred, including frontmatter.
- **Generated rules default to zero sideways cross-references.** The reference corpus carries four across eight files, so the rules are nearly independent.
- **The common refusal path works, but the accept path has not run end to end.** The refusal path names destinations and the accept path is built and structurally proven in parts. The reference set was saturated by a five-iteration review that returned zero warranted new rules, so no genuine accept case exists in this repository yet.

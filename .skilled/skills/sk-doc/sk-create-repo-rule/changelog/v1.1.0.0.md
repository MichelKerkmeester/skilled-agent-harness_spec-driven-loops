`create-repo-rule` gains the two things it shipped without: a manual testing playbook recording how an operator confirms the mode behaves, and a README that explains what a repo rule is to someone who has never seen one. A conformance audit against the skill-authoring contract found and fixed one violation.

> Spec folder: `specs/sk-doc/040-create-repo-rules/008-conformance-playbook-and-readme` (Level 2, phase 8 of 8)

---

## What Changed

#### New Features

- **A ten-scenario manual testing playbook**, across `rule-decision`, `rule-authoring` and `lifecycle-and-wiring`. Four scenarios cover the refusal paths, three cover authoring, and three cover wiring and retirement. The weighting is deliberate: the mode refuses most of what it is asked for, so a package weighted toward authoring would test the rare case and miss the common one.
- **An inverted grading rule, stated twice.** A run producing no file is usually a pass, graded on whether the refusal named its test and its destination. A run producing a well-written rule is a failure when the scenario expected a refusal. A reviewer's instinct runs the other way, so the root document says it in the overview and again in the acceptance rules.
- **A README on the nine-section skeleton** the sibling create modes share. It answers what a rule is, how the trigger table loads one, where a rule sits in the precedence ladder and why the create and retire orderings run in opposite directions. Written to the Human Voice Rules standard.

#### Bug Fixes

- **`WHEN TO USE` no longer names files.** The section carried three file references where the sibling contract requires none, so the routing advice now describes destinations rather than paths.

#### Notes

- The playbook is registered in `playbook-failclosed-allowlist.txt`, so its clean state is enforced rather than incidental. A warn-listed package reports violations and ships anyway.
- Commands in the package are run against the live corpus, not composed. The first pass caught three defects (an invalid comma-separated grep alternation, a phrase search matching body prose, a step disagreeing with its own table cell) and then overclaimed that all commands had been run. An independent review found three more: a divider count that graded every conforming rule as FAIL, an unbounded `git log` returning 30,773 lines newest-first where the scenario needed a bounded chronological one, and a second table-versus-commands disagreement returning opposite results. All six are fixed and re-run.
- The authoring scenario's subject changed during writing. Dependency intake looked unowned and turned out to belong to `overengineering.md`, which would have failed the duplication test the scenario exists to pass. It now uses concurrent-session work, which no shipped rule covers.
- `validate_document.py --type reference` calls all eight shipped rules invalid, because a repo rule has no Overview section by design. The README documents this rather than recommending a command that fails.
- No scenario has been executed yet. The package defines how the mode is validated and records no run.

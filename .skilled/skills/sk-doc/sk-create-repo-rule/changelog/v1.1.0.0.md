The release gives `create-repo-rule` a manual testing playbook for confirming how the mode behaves and a README that explains repo rules to newcomers. It also corrects a skill-authoring contract violation in `WHEN TO USE`.

> Spec folder: `specs/sk-doc/040-create-repo-rules/008-conformance-playbook-and-readme` (Level 2)
> phase 8 of 8

## What's New at a Glance

- **The playbook covers ten manual scenarios.** The scenarios cover `rule-decision`, `rule-authoring` and `lifecycle-and-wiring`: four cover refusal paths, three authoring and three wiring and retirement. More scenarios cover refusals because the mode refuses most requests, so an authoring-heavy package would focus on the rarer case.
- **Refusal outcomes use an inverted grading rule.** A run that produces no file usually passes if its refusal names the test and destination, while a well-written rule fails when the scenario expected a refusal. The overview and acceptance rules both state the inversion because reviewers instinctively expect the opposite.
- **The authoring scenario avoids duplicating an existing rule.** Its subject changed during writing. Dependency intake looked unowned but belongs to `overengineering.md`, which would fail the duplication test. The scenario now uses concurrent-session work, which no shipped rule covers.
- **The playbook commands are run against the live corpus rather than being composed.** The first pass caught an invalid comma-separated grep alternation, a phrase search matching body prose and a step disagreeing with its own table cell, then overclaimed that all commands had been run, while an independent review found a divider count that graded every conforming rule as FAIL, an unbounded `git log` returning 30,773 lines newest-first where the scenario needed a bounded chronological result and another table-versus-commands disagreement returning opposite results. All six are fixed and re-run.
- **The playbook is registered in `playbook-failclosed-allowlist.txt`.** Its clean state is enforced rather than incidental. A warn-listed package reports violations and ships anyway.
- **The README explains repo rules and their lifecycle.** It follows the nine-section skeleton the sibling create modes share and is written to the Human Voice Rules standard. It explains what a rule is, how the trigger table loads one, where it sits in the precedence ladder and why create and retire orderings run in opposite directions. It also documents that `validate_document.py --type reference` calls all eight shipped rules invalid because a repo rule has no Overview section by design, rather than recommending a command that fails.
- **`WHEN TO USE` describes destinations rather than files.** It removes three file references because the sibling contract requires none.
- **No scenario has been executed yet.** The package defines how the mode is validated and records no run.

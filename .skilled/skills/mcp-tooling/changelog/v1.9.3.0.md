# v1.9.3.0, Routing Rules Move to ROUTER.md

The routing rules for mcp-tooling moved out of SKILL.md and into a final MACHINE ROUTER section of ROUTER.md. That section holds the two-axis model, the routing rule, the outcomes and the surface router. SKILL.md stays short, and the move leaves the hub's routes as they were.

> Spec folder: `specs/sk-doc/072-skill-routing-and-clarity/014-skill-router-files/004-hub-router-merge` (Level 1); `specs/sk-doc/072-skill-routing-and-clarity/015-routing-data-alignment` (Level 2)

&nbsp;

## What's New at a Glance

- **SKILL.md keeps a single pointer.** SKILL.md no longer carries a MACHINE ROUTER section. Its SMART ROUTING section ends with one line that points to ROUTER.md.
- **The move changed no route.** The map from intent to files is byte for byte the same, and every route the hub selects matches the run before the move. The compiled admission check gives the same result.
- **The compiled activation manifest was regenerated.** Its sources changed, so the manifest was rebuilt from the new files.
- **The hub meets the routing-shape canon.** Its known-debt entry is removed, so the hub no longer needs an exception in that check.
- **Hub router pointers name `ROUTER.md`.** The README, the defer checklist and two feature-catalog role tables now describe where the machine router actually lives.
- **Two aliases stop steering requests to the wrong mode.** "screen examples" no longer scores `mcp-mobbin`, so a request that names neither Refero nor Mobbin defers between the two research transports, as the hub contract says. "extract design.md" no longer scores `mcp-figma`, so a DESIGN.md request that names no Figma file reaches `sk-design`. A new primary scenario gives `mcp-notion` the routing gold it lacked, and the bare tool-bridge scenario now says it tests the hub's own routing.

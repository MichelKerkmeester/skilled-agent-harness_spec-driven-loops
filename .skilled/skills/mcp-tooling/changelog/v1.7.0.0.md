# v1.7.0.0 - Orca CLI workflow bridge

Orca owns state that ordinary Git, shell and browser tools cannot observe. This release adds a dedicated Orca CLI workflow to the MCP tooling hub.

## Why This Release

The public Orca skill is a discovery stub whose flags are supplied by the installed Orca version. The packet resolves one executable and loads the matching `orca-cli` guide before relying on command details. The inspected 1.4.205 command registry exposed no native Orca MCP command, so the new member remains CLI-only rather than inventing a Code Mode manual.

## What's New at a Glance

- **The hub adds a nested `mcp-orca-cli` workflow packet.** It covers Orca-managed worktrees, repositories, terminals, handoffs, automations, artifacts, skill sharing, comments and embedded browser state.
- **The hub adds a registry entry for `mcp-orca-cli`.** It records `packetKind: workflow` and `backendKind: cli-only`.
- **Stage two adds packet-qualified resources for Orca.** The router additions also include an Orca stage-one router signal, vocabulary classes and a tie-break entry.
- **Six hub items were updated for six workflow modes and four transports.** They were the single hub advisor identity, hub README, root router, description, feature catalog and hub manual-testing inventory.
- **The canonical metadata command regenerated the hub leaf manifest.** All Orca reference leaves are reachable through it.
- **The hub graph was corrected.** The corrections covered vocabulary, causal context, key files, source documents and packet entities, without creating a second advisor identity.
- **The packet treats listed Orca operations as state-changing.** These include worktree, terminal, agent, browser, automation, publishing, authentication and skill-sharing operations.
- **Generic work stays with its designated packets.** `mcp-chrome-devtools` remains with generic Chrome/CDP work, `mcp-aside-devtools` remains with generic agentic browser work and supervised orchestration remains outside this packet.
- **Orca command flags remain version-sensitive.** The installed guide and command help outrank this packet's representative examples.
- **Unperformed checks have a required status.** They must be recorded as `SKIP` with their blocker.
- **Ordinary packet creation does not promote the compiled-routing activation manifest.** The registry and legacy router remain the source of truth.

## Safety and Boundaries

#### Deletion and Browser Boundaries

The packet preserves archive-hook deletion gates, terminal receipt distinctions and tab-scoped browser refs. It also preserves untrusted page content, publishing permission denials and explicit authorization requirements.

&nbsp;

#### Sensitive Scenarios Have Clear Requirements

Mutating, authenticated, publishing, terminal and browser scenarios require:

- Operator authorization.
- Disposable targets.

&nbsp;

#### Promotion Controls Routing Status

The compiled-routing activation manifest is not promoted by ordinary packet creation. Until a separately authorized promotion refreshes it, the hub status may report legacy authority with a stale-manifest cause.

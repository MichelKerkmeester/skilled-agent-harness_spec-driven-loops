# v1.6.1.0, CLI Transport Design Pairing

The CLI design transport now declares an unconditional pairing with `sk-design`.

- It does so under the design agent persona.
- The hub gained the machine-readable field to hold it.

The prose also changed with this release.

- It assumed one pairing for all four design transports.
- That prose was corrected.

&nbsp;

## Why This Release

The CLI transport already had its own themes.

- `get_theme` already returns named CSS variables and fonts for the CLI transport's themes.
- The other three transports hand off to `sk-design-md-generator`.

## Design Pairings

Design pairings tell each transport which skill decides design.

#### The Pairing Field Has a Narrow Role <a id="c-the-pairing-field-has-a-narrow-role"></a>

- The `transport-axis` extension carries `"crossHubPairing": {}`.
- The axis description names the pairings in prose.
- That reads as an unfinished field.
- This change populated it before discovering otherwise.
- `sk-design` is a flat standalone skill with no `mode-registry.json`.
- So it can never be a member.
- The field is therefore deliberately inert, not unfinished.
- It returns to `{}`.
- The reason is now recorded so the next reader does not repeat this.

<details>
<summary><b>Why the field stays inert</b></summary>

- At `registry-compiler.cjs:249-255`, the compiler reads the object's values as skill ids.
- It resolves each against `judgmentRegistries`.
- It fails with `JUDGMENT_REGISTRY_MISSING` on one it cannot find.
- The comment above `registry-compiler.cjs:249-255` records the rest.
- That comment sits on the code that resolves those values.
- The pairing is kept "purely for provenance hashing and input-integrity checking".
- It no longer contributes a live rule.
- That is because a bundle built from it "could add a target legacy never routes".
- That is exactly how the design-reference search over-routed `sk-design`'s md-generator alongside `mcp-refero`.

</details>

#### Each Transport Has Its Own Handoff <a id="c-each-transport-has-its-own-handoff"></a>

- The `transport-axis` description read: transports "never produce a measured design reference themselves and hand off to `sk-design-md-generator`."
- That was true of three transports, not of four.
- It was wrong for the CLI transport.
- `get_theme` already returns named CSS variables and fonts.
- So there is nothing to re-measure.
- The revised description states that a transport never decides design.
- It always hands off to a standalone skill.
- It then names which skill and why.
- `mcp-figma`, `mcp-refero` and `mcp-mobbin` retrieve visual material with no token vocabulary of its own.
- So they hand off to `sk-design-md-generator`.
- The CLI transport pairs with `sk-design`, the decide skill.
- `sk-design-md-generator` still applies to it when the reference is an external live site.
- That is not one of its own themes.

#### Registry Pairing Has Limits <a id="c-registry-pairing-has-limits"></a>

- `crossHubPairing` remains empty and cannot be populated for any transport.
- So a transport's design partner is still not resolvable from the registry.
- Making it resolvable requires a routing-compiler change.
- That change reopens the design-reference over-routing path.
- It belongs in its own packet.
- Nothing enforces any pairing mechanically.
- The declarations are prompt-time discipline.
- No gate or validator observes whether the paired skill was actually loaded during a request.

## Hub Documentation

The hub docs and skill file named design partners.

#### Hub Guidance Names Each Owner <a id="c-hub-guidance-names-each-owner"></a>

- The README said "Every design-affecting operation pairs in `sk-design-md-generator`".
- It also said "Design work always pairs a transport with `sk-design-md-generator`."
- Both now name the judgment owner per transport.
- They no longer assume one for all four.
- The related-skills table listed `sk-design-md-generator` as the partner for all four design transports.
- It now scopes that partner to `mcp-figma`, `mcp-refero` and `mcp-mobbin`.
- It adds an `sk-design` row for the CLI transport.

<details>
<summary><b>Smaller fixes</b></summary>

- `SKILL.md`'s `packetKind: "transport"` line enumerated only three transports.
- It omitted the CLI transport.
- The omission had been stale since the mode was added in v1.6.0.0.
- It was unrelated to this change.
- It was corrected because the same sentence had to be rewritten.

</details>

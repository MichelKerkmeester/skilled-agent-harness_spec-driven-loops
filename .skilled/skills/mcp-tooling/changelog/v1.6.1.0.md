# v1.6.1.0 - MagicPath Design Pairing

**Released:** 2026-08-29

`mcp-magicpath` now declares an unconditional pairing with `sk-design` under the design agent persona. The hub gained the machine-readable field to hold it, and the prose that assumed one pairing for all four design transports was corrected.

---

## What Changed

### crossHubPairing Stays Empty, And Now Says Why

- The `transport-axis` extension carries `"crossHubPairing": {}` while the axis description names the pairings in prose. That reads as an unfinished field, and this change populated it before discovering otherwise.
- The compiled-routing pre-push gate refused the push. A bisect against the pre-change registry isolated the field: the version bump and the axis rewrite both compiled, an unrelated added extension key compiled, and any `crossHubPairing` value produced `compile-error` with a null policy hash - including a bare `{"mcp-magicpath": "sk-design"}`.
- `registry-compiler.cjs:249-255` reads the object's values as skill ids, resolves each against `judgmentRegistries`, and fails `JUDGMENT_REGISTRY_MISSING` on one it cannot find. `sk-design` is a flat standalone skill with no `mode-registry.json`, so it can never be a member.
- The comment above that code records the rest: the pairing is kept "purely for provenance hashing and input-integrity checking" and no longer contributes a live rule, because a bundle built from it "could add a target legacy never routes - exactly how MT-008 over-routed sk-design's md-generator alongside mcp-refero".
- The field is therefore deliberately inert, not unfinished. It returns to `{}`, and the reason is now recorded so the next reader does not repeat this.

### The Axis Description Was Wrong After The Addition

- It read: transports "never produce a measured design reference themselves and hand off to `sk-design-md-generator`". True of three transports, not of four.
- It now states the general rule — a transport never decides design and always hands the judgment to a standalone skill — and then names which skill and why. `mcp-figma`, `mcp-refero` and `mcp-mobbin` retrieve visual material with no token vocabulary of its own, so they hand off to `sk-design-md-generator`. `mcp-magicpath`'s `get_theme` already returns named CSS variables and fonts, so there is nothing to re-measure and it pairs with `sk-design`, the decide skill.
- `sk-design-md-generator` still applies to `mcp-magicpath` when the reference is an external live site rather than a MagicPath theme.

### Hub Prose Corrections

- `README.md` claimed "Every design-affecting operation pairs in `sk-design-md-generator`" and "Design work always pairs a transport with `sk-design-md-generator`". Both now name the judgment owner per transport rather than assuming one.
- The related-skills table listed `sk-design-md-generator` as the partner "for the four design transports". It now scopes that to three and adds an `sk-design` row for `mcp-magicpath`.
- `SKILL.md`'s `packetKind: "transport"` line enumerated only three transports and omitted `mcp-magicpath` entirely — stale since the mode was added in v1.6.0.0 and unrelated to this change, but corrected here because the same sentence had to be rewritten anyway.

### Aggregation Directory Completed

- `.opencode/changelog/mcp-tooling/mcp-magicpath` was created, pointing at the packet's own `changelog/` directory. It was the only design transport missing.
- `mcp-notion` and `mcp-obsidian` were also missing and are now linked too, on an explicit operator request. All ten entries resolve; the directory is complete for the first time.
- The changelog files stay real files inside their packets. Only the aggregation directory entries are symlinks.

### Generated

- `leaf-manifest.json` regenerated by `ci-skill-root-metadata.cjs --fix` to pick up the packet's new `references/design-authority.md`. Fleet audit: `checked=14 passed=14 failed=0`.

## Known Limitations

- `crossHubPairing` remains empty and cannot be populated for any transport, so a transport's design partner is still not resolvable from the registry. Making it resolvable requires a routing-compiler change that reopens the MT-008 path, and belongs in its own packet.
- Nothing enforces any pairing mechanically. The declarations are prompt-time discipline; no gate or validator observes whether the paired skill was actually loaded during a request.
- The hub's advisor-level routing for MagicPath phrasings remains unresolved from v1.6.0.0: hub-level routing resolves correctly, but a cold MagicPath description may still return no advisor recommendation. This change does not touch that, and the diagnosis still lives in the advisor's scoring internals.

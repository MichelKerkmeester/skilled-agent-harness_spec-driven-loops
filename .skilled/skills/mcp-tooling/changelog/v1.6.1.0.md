# v1.6.1.0, MagicPath Design Pairing

`mcp-magicpath` now declares an unconditional pairing with `sk-design` under the design agent persona.
The hub gained the machine-readable field to hold it, and the prose that assumed one pairing for all four design transports was corrected.

## Why This Release

`get_theme` already returns named CSS variables and fonts for MagicPath themes, while the other three transports hand off to `sk-design-md-generator`.

## What's New at a Glance

- **`"crossHubPairing": {}` does not carry the `mcp-magicpath` pairing.** The pairing is described in the transport prose.
- **`transport-axis` now describes transport-specific design handoffs.** It replaces wording that was true of three transports, not four.
- **`README.md` now names the judgment owner per transport.** Its claims and related-skills table no longer assume a single partner for all four.
- **The transport line was corrected.** `SKILL.md`'s `packetKind: "transport"` line now includes `mcp-magicpath`.
- **All ten changelog aggregation entries now resolve.** This completes the directory for the first time.
- **The packet's new reference is included in the manifest.** It is `references/design-authority.md` in `leaf-manifest.json`.

## Design Pairings

#### The Pairing Field Has a Narrow Role

The `transport-axis` extension carries `"crossHubPairing": {}` while the axis description names the pairings in prose.
That reads as an unfinished field, and this change populated it before discovering otherwise.
At `registry-compiler.cjs:249-255`, the compiler reads the object's values as skill ids, resolves each against `judgmentRegistries` and fails with `JUDGMENT_REGISTRY_MISSING` on one it cannot find.
`sk-design` is a flat standalone skill with no `mode-registry.json`, so it can never be a member.
The field is therefore deliberately inert, not unfinished. It returns to `{}`, and the reason is now recorded so the next reader does not repeat this.
The comment above `registry-compiler.cjs:249-255`, the code that resolves those values, records the rest: the pairing is kept "purely for provenance hashing and input-integrity checking" and no longer contributes a live rule, because a bundle built from it "could add a target legacy never routes", which is exactly how MT-008 over-routed `sk-design`'s md-generator alongside `mcp-refero`.

&nbsp;

#### Each Transport Has Its Own Handoff

The `transport-axis` description read: transports "never produce a measured design reference themselves and hand off to `sk-design-md-generator`." That was true of three transports, not of four. It was wrong for `mcp-magicpath`: `get_theme` already returns named CSS variables and fonts, so there is nothing to re-measure. The revised description states that a transport never decides design and always hands off to a standalone skill, then names which skill and why. `mcp-figma`, `mcp-refero` and `mcp-mobbin` retrieve visual material with no token vocabulary of its own, so they hand off to `sk-design-md-generator`. `mcp-magicpath` pairs with `sk-design`, the decide skill. `sk-design-md-generator` still applies to `mcp-magicpath` when the reference is an external live site rather than a MagicPath theme.

&nbsp;

#### Registry Pairing Has Limits

`crossHubPairing` remains empty and cannot be populated for any transport, so a transport's design partner is still not resolvable from the registry. Making it resolvable requires a routing-compiler change that reopens the MT-008 path, and belongs in its own packet. Nothing enforces any pairing mechanically. The declarations are prompt-time discipline, and no gate or validator observes whether the paired skill was actually loaded during a request.

## Hub Documentation

#### Hub Guidance Names Each Owner

The README said "Every design-affecting operation pairs in `sk-design-md-generator`" and "Design work always pairs a transport with `sk-design-md-generator`." Both now name the judgment owner per transport rather than assuming one for all four. The related-skills table listed `sk-design-md-generator` as the partner for all four design transports. It now scopes that partner to `mcp-figma`, `mcp-refero` and `mcp-mobbin` and adds an `sk-design` row for `mcp-magicpath`. `SKILL.md`'s `packetKind: "transport"` line enumerated only three transports and omitted `mcp-magicpath`. The omission had been stale since the mode was added in v1.6.0.0. It was unrelated to this change, but it was corrected because the same sentence had to be rewritten.

## Changelog Aggregation

#### All Entries Resolve

`.opencode/changelog/mcp-tooling/mcp-magicpath` was created to point to the packet's own `changelog/`. It was the only design transport missing. `mcp-notion` and `mcp-obsidian` were also missing and were linked on an explicit operator request. The changelog files stay real files inside their packets. ## Advisor Routing

#### Cold MagicPath Phrasings Can Miss

The hub's advisor-level routing for MagicPath phrasings remains unresolved from v1.6.0.0. Hub-level routing resolves correctly, but a cold MagicPath description may still return no advisor recommendation. This change does not touch the issue. Its diagnosis still lives in the advisor's scoring internals.

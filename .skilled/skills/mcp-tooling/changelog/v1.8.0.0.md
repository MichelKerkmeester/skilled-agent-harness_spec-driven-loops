# v1.8.0.0, Orca CLI Moves to a Standalone Skill

v1.8.0.0 moves the Orca CLI subject out of the MCP tooling hub and into the standalone class-S skill `cli-orca`. The hub returns to a single responsibility: nine MCP tool bridges, five workflow modes and four read-only design transports.

## Why This Release

Orca-managed worktrees, terminals, the embedded browser, automations, artifacts, handoffs and skill sharing are CLI surfaces, not MCP transports. Keeping that subject inside a hub whose identity is MCP tool bridging forced a permanent exception into the hub identity, mode table, description, router vocabulary and manifest. The subject also gained a knowledge layer the hub could not carry: one authored reference and one verbatim snapshot for each of the eight official Orca skills.

## What's New at a Glance

- **`mcp-orca-cli` was removed from the hub.** An Orca request now defers here instead of being captured.
- **Hub guidance and graph metadata changed.** The hub's identity and routing descriptions were updated.
- **The retired nested packet was deleted from the hub tree.** Its routing contract, references and safety envelope were superseded by `cli-orca`.
- **Orca benchmark records moved to separate destinations.** The move split integration evidence from two hub-routing scenarios.
- **The hub's coverage records were updated.** The retired coverage gap was recorded rather than inferred.
- **The hub leaf manifest was regenerated.** Every remaining manifest leaf resolves. All nine modes reach back to a registered mode.
- **Compiled routing was not promoted or re-authorized.** The hub continues to report its serving authority and cause code honestly.
- **Generic work keeps its named owners.** Git, terminal, browser and supervised orchestration work stay with their named surfaces.

## MCP Tooling Hub

#### Orca Routing Leaves the Hub

`mode-registry.json` lost the `mcp-orca-cli` entry, including its tool surface, aliases and advisor routing metadata. The registry now declares nine modes. In `hub-router.json`, the stage-one router signal, the `orca-cli-aliases` and `orca-worktree-terminal` vocabulary classes and the tie-break entry were removed. The `ROUTER.md` changes removed the `ORCA_CLI` intent signal and its two stage-two packet-qualified resources. The retired mode was dropped from the router's mode lists.

&nbsp;

#### Hub Guidance Follows the Move

The hub `SKILL.md` mode table and identity text changed, along with the README mode lists and quick-start prompts and `description.json`. Graph metadata changed in its vocabulary, domains, key files, source documents and entities. No Orca signal remains. The release updated the hub feature catalog and manual testing inventory for nine modes and recorded the retired coverage gap rather than inferring it.

&nbsp;

#### Routing Scope and History

For compiled routing, this change only removes a source mode. The retired mode's historical changelog entry remains in this directory as the record of that release.

## Orca CLI

#### Safety After the Extraction

The extraction removes vocabulary, not caution. Orca CLI work keeps its own safety envelope in the standalone skill `cli-orca`, covering:

- Mutation classification
- Archive-hook deletion gates
- Terminal receipt distinctions
- Tab-scoped browser refs
- Untrusted page content
- Publishing permission denials
- Explicit authorization requirements

&nbsp;

#### Benchmark Records Move

The mode's benchmark evidence moved to `specs/cli-orca/001-mcp-orca-cli/benchmark/reports/orca-integration/`. Its two hub-routing scenarios moved to `benchmark/reports/hub-routing-archived/` in the same packet.

## Work Boundaries

#### Generic Work Keeps Its Owners

Generic Git worktrees stay with `sk-git`. Generic terminal work stays with the normal coding workflow. Chrome/CDP work stays with `mcp-chrome-devtools`. Generic agentic browser work stays with `mcp-aside-devtools`. Supervised orchestration stays with the official `orchestration` skill.

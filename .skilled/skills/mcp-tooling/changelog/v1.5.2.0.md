# mcp-tooling completes the root ROUTER.md two-state contract (golden alignment)

The hub's root `ROUTER.md` gains the two frontmatter fields the two-state root-router contract requires of every class-H parent hub: `router_state: active` (this hub owns second-stage leaf selection) and `skill_pointer: SKILL.md` (the hub's own root SKILL.md is the resolvable entry point). The machine-readable `INTENT_SIGNALS` / `RESOURCE_MAP` block is untouched and remains byte-identical to the frozen baseline (sha256 `8477b664…`), so replay and benchmark behavior is unchanged.

---

## Why

The two-state contract (root-router-contract.cjs) requires `router_state`, a four-part `version`, and `skill_pointer` in the ROUTER.md frontmatter in both states. The pilot ROUTER.md shipped the machine block and prose correctly but predated the final frontmatter schema, so the golden checkpoint's only delta is completing the declaration — no routing policy bytes move.

- `ROUTER.md` (v1.1.0.0 → v1.1.1.0): frontmatter gains `router_state: active` and `skill_pointer: SKILL.md`. No prose or machine-block bytes changed; the Python fence sha256 stays `8477b664…`.
- `SKILL.md` (v1.5.1.0 → v1.5.2.0): version alignment only.
- `README.md` (v1.5.1.0 → v1.5.2.0): version alignment only.
- `description.json` (v1.5.1.0 → v1.5.2.0): version alignment only.

## Upgrade

None. The root router now validates clean against the two-state contract; stage-one and stage-two routing semantics are unchanged.

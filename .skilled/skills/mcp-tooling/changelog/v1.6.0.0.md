# mcp-tooling gains a transport whose provider ships no MCP server

mcp-tooling now routes a provider's component and design-system surface through the hub.

- The release adds the hub's ninth mode.
- A UTCP `cli` manual reaches it.
- The new provider publishes no MCP server.

The registry and router record the new mode.

- `mode-registry.json` adds `backendKind: "code-mode-cli"`.
- The registry moves from v1.0.2.0 to v1.1.0.0.
- `hub-router.json` moves from v1.1.4.0 to v1.2.0.0.

The docs and safety notes reflect the read-only transport.

- The new transport is read-only by design.
- The hub descriptions now name the new transport.
- The transport axis reads four rather than three.

&nbsp;

## Why This Release

Every other bridge in the hub binds to an MCP server. The new provider publishes no MCP server.

- All thirteen manuals registered in `.utcp_config.json` used `call_template_type: "mcp"`.
- Its published integration is a Node CLI plus vendor-authored instruction files.
- Those files are dropped into three runtime directories.
- That integration bypasses the hub, registry and advisor.
- Every other tool bridge routes through them.
- The `@utcp/cli` transport was already installed beside `@utcp/mcp`.
- It was unused.
- Registering the provider through it avoids standing up a protocol surface.
- It also avoids owning one.
- The vendor does not ship that surface.

## The CLI Transport

The new mode is the first reached through a UTCP `cli` manual.

#### The First CLI Manual <a id="c-the-first-cli-manual"></a>

- The new mode is the hub's first member reached through a UTCP `cli` manual rather than an MCP server.
- The manual is called through Code Mode.
- A mode packet describes it.

#### A Backend for Vendor CLIs <a id="c-a-backend-for-vendor-clis"></a>

- The existing `backendKind` values cover a local desktop daemon and remote MCP servers.
- Neither describes a vendor CLI reached through Code Mode.
- So the `transport-axis` extension records why `code-mode-cli` is needed.
- `mode-registry.json` adds `backendKind: "code-mode-cli"`.
- The registry moves from v1.0.2.0 to v1.1.0.0.

&nbsp;

## Routing and Discovery

The router and metadata record the new mode's phrasings and signals.

#### Routing Signals for the New Mode <a id="c-routing-signals-for-the-new-mode"></a>

- `hub-router.json` moves from v1.1.4.0 to v1.2.0.0.
- It adds a vocabulary class for the provider's aliases.
- It adds a `routerSignals` entry at weight 4.
- A `routerPolicy.tieBreak` entry also joins the update.
- At the hub level, the provider's phrasings resolve to the new mode.
- Sibling routing is unchanged after the registry change.

#### Trigger Phrase Coverage <a id="c-trigger-phrase-coverage"></a>

- Every other provider had trigger phrases.
- The new provider had none.
- `graph-metadata.json` adds six trigger phrases for the new mode.
- Its causal summary also changes.

#### Advisor Scoring Gap <a id="c-advisor-scoring-gap"></a>

- A cold request names neither the hub nor the mode.
- Such a request for the new provider has been observed returning no recommendation at all.
- That behavior belongs to advisor scoring, not the registration.
- Advisor-level precedence is not established.
- Adding trigger phrases did not alter the advisor-level outcome.

## Hub Documentation

The docs now report nine modes and name the new transport.

#### Corrected Mode Counts <a id="c-corrected-mode-counts"></a>

- The `feature-catalog/` and `manual-testing-playbook/` had claimed seven modes.
- Eight existed after `mcp-notion` was added without updating them.
- Both now enumerate the axes correctly.
- Holdout coverage is stated as 7/9.
- That is because neither `mcp-notion` nor the new transport has a blind holdout scenario.
- `feature-catalog/` and `manual-testing-playbook/` now report nine modes.
- The playbook adds scenario `MT-011` for component lookup through the new transport.

#### Member Descriptions and Leaf Resources <a id="c-member-descriptions-and-leaf-resources"></a>

- `SKILL.md`, `README.md` and `description.json` move from v1.5.2.0 to v1.6.0.0.
- `leaf-manifest.json` was regenerated.
- It has four leaf resources.
- The hub descriptions now name the new transport.
- The transport axis reads four rather than three.

&nbsp;

## Workspace Safety

None of the provider's write commands is registered.

#### Write Commands Stay Unregistered <a id="c-write-commands-stay-unregistered"></a>

- The new transport is read-only by design.
- The `.tsx`-writing, package-installing, remote-project and component-revision commands listed below are unregistered.
- The provider's CLI can write `.tsx` files into the calling project.
- It can install npm packages.
- It can create remote projects and component revisions.
- None of those commands is registered.
- So `mutatesWorkspace: false` holds for the same reason it holds for the remote-MCP transports.
- The destructive half is unreachable from a tool call.
- It is not merely discouraged.

&nbsp;

# mcp-tooling gains mcp-magicpath, a transport whose provider ships no MCP server

The hub adds a ninth mode. `mcp-magicpath` bridges to MagicPath's component and design-system surface, and it is the first member reached over a UTCP `cli` manual rather than an MCP server, because MagicPath publishes no MCP server to reach.

---

## Why

Every other bridge in this hub binds to an MCP server, and all thirteen manuals registered in `.utcp_config.json` were `call_template_type: "mcp"`. MagicPath has none: its published integration is a Node CLI plus vendor-authored instruction files dropped into three runtime directories, which bypasses the hub, the registry and the advisor that every other tool bridge routes through.

The `@utcp/cli` transport was already installed beside `@utcp/mcp` and unused. Registering MagicPath through it keeps the provider reachable the way every other provider is reachable — one registered manual, called through Code Mode, described by a mode packet — without standing up and owning a protocol surface the vendor does not ship.

## What Changed

- `mode-registry.json` (v1.0.2.0 → v1.1.0.0): one mode added. New `backendKind: "code-mode-cli"`, since the existing values cover a local desktop daemon and remote MCP servers, and none describes a vendor CLI reached through Code Mode. The `transport-axis` extension records why the provider forces it.
- `hub-router.json` (v1.1.4.0 → v1.2.0.0): `magicpath-aliases` vocabulary class, `routerSignals` entry at weight 4, and a `routerPolicy.tieBreak` entry.
- `leaf-manifest.json`: regenerated by `ci-skill-root-metadata.cjs --fix`; four leaf resources.
- `SKILL.md`, `README.md`, `description.json` (v1.5.2.0 → v1.6.0.0): the member is named and the transport axis reads four rather than three.
- `graph-metadata.json`: causal summary updated, and six MagicPath trigger phrases added — every other provider had them and MagicPath had none.
- `feature-catalog/`, `manual-testing-playbook/`: mode counts corrected to nine, and scenario `MT-011` added for MagicPath component lookup.

The mode is read-only by design. MagicPath's CLI can write `.tsx` files into the calling project, install npm packages, and create remote projects and component revisions; none of those commands is registered, so `mutatesWorkspace: false` holds for the same reason it holds for the remote-MCP transports, and the destructive half is unreachable from a tool call rather than merely discouraged.

## Corrections Carried

The hub's own catalog and playbook claimed seven modes while eight existed — `mcp-notion` was added without updating them. Writing an accurate sentence that includes MagicPath required fixing that too, so both now read nine and enumerate the axes correctly. Holdout coverage is stated honestly as 7/9: neither `mcp-notion` nor `mcp-magicpath` has a blind holdout scenario.

## Upgrade

None for existing modes. Sibling routing was exercised after the registry change and is unchanged. An operator wanting MagicPath must authenticate the CLI separately (`magicpath-ai login`, or `MAGICPATH_TOKEN` wired through the dotenv loader as `magicpath_MAGICPATH_TOKEN`); without a credential every tool returns a structured `NOT_AUTHENTICATED` object rather than failing opaquely.

## Known Gap

Hub-level resolution is verified: replaying `hub-router.json` resolves MagicPath phrasings to this mode and leaves every sibling unchanged. Advisor-level precedence is not. A cold MagicPath request that names neither the hub nor the mode has been observed returning no recommendation at all, and adding the missing trigger phrases did not change it. That behaviour belongs to the advisor's scoring, not to this registration.

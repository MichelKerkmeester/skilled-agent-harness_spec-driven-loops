# mcp-tooling gains a transport whose provider ships no MCP server

mcp-tooling now routes a provider's component and design-system surface through the hub.

## Why This Release

Every other bridge in the hub binds to an MCP server. All thirteen manuals registered in `.utcp_config.json` used `call_template_type: "mcp"`. The new provider publishes no MCP server. Its published integration is a Node CLI plus vendor-authored instruction files. Those files are dropped into three runtime directories. That integration bypasses the hub, registry and advisor. Every other tool bridge routes through them.

The `@utcp/cli` transport was already installed beside `@utcp/mcp`. It was unused. Registering the provider through it avoids standing up a protocol surface. It also avoids owning one. The vendor does not ship that surface.

## What's New at a Glance

- **The release adds the hub's ninth mode.** A UTCP `cli` manual reaches it.
- **`mode-registry.json` adds `backendKind: "code-mode-cli"`.** The registry moves from v1.0.2.0 to v1.1.0.0.
- **At the hub level, the provider's phrasings resolve to the new mode.** Sibling routing is unchanged after the registry change.
- **`graph-metadata.json` adds six trigger phrases for the new mode.** Its causal summary also changes.
- **`feature-catalog/` and `manual-testing-playbook/` now report nine modes.** The playbook adds scenario `MT-011` for component lookup through the new transport.
- **The hub descriptions now name the new transport.** The transport axis reads four rather than three.
- **The new transport is read-only by design.** The `.tsx`-writing, package-installing, remote-project and component-revision commands listed below are unregistered.
- **Advisor-level precedence is not established.** Adding trigger phrases did not alter the advisor-level outcome.

## The CLI Transport

#### The First CLI Manual

The new mode is the hub's first member reached through a UTCP `cli` manual rather than an MCP server. The manual is called through Code Mode. A mode packet describes it.

&nbsp;

#### A Backend for Vendor CLIs

The existing `backendKind` values cover a local desktop daemon and remote MCP servers. Neither describes a vendor CLI reached through Code Mode. So the `transport-axis` extension records why `code-mode-cli` is needed.

---

## Routing and Discovery

#### Routing Signals for the New Mode

`hub-router.json` moves from v1.1.4.0 to v1.2.0.0. It adds a vocabulary class for the provider's aliases. It adds a `routerSignals` entry at weight 4. A `routerPolicy.tieBreak` entry also joins the update.

&nbsp;

#### Trigger Phrase Coverage

Every other provider had trigger phrases. The new provider had none.

&nbsp;

#### Advisor Scoring Gap

A cold request names neither the hub nor the mode. Such a request for the new provider has been observed returning no recommendation at all. That behavior belongs to advisor scoring, not the registration.

---

## Hub Documentation

#### Corrected Mode Counts

The `feature-catalog/` and `manual-testing-playbook/` had claimed seven modes. Eight existed after `mcp-notion` was added without updating them. Both now enumerate the axes correctly. Holdout coverage is stated as 7/9. That is because neither `mcp-notion` nor the new transport has a blind holdout scenario.

&nbsp;

#### Member Descriptions and Leaf Resources

`SKILL.md`, `README.md` and `description.json` move from v1.5.2.0 to v1.6.0.0. `leaf-manifest.json` was regenerated. It has four leaf resources.

---

## Workspace Safety

#### Write Commands Stay Unregistered

The provider's CLI can write `.tsx` files into the calling project. It can install npm packages. It can create remote projects and component revisions. None of those commands is registered. So `mutatesWorkspace: false` holds for the same reason it holds for the remote-MCP transports. The destructive half is unreachable from a tool call. It is not merely discouraged.

---

## Upgrade Notes

- **Existing modes.** No upgrade is needed for existing modes.
- **Provider credentials.** Authenticate its CLI separately, or wire its token through the dotenv loader.
- **Missing credentials.** Without a credential every tool returns a structured `NOT_AUTHENTICATED` object. It does not fail opaquely.

# mcp-obsidian v0.2.0.0, Plugin Knowledge Deepening

mcp-obsidian v0.2.0.0 deepens guidance for Beancount Ledger, Obsidian Tables and BRAT with focused plugin references and copyable file-layer examples. It also separates named-plugin routing, adds plugin cards to the feature catalog and expands the playbook for Tables and BRAT workflows.

## Why This Release

A finance request should not load unrelated plugin references, while a bare plugin request still needs a usable catch-all.

---

## What's New at a Glance

- **Three community plugins gain deep reference families.** Beancount Ledger, Obsidian Tables and BRAT now have plugin-specific references.
- **Copyable assets support file-layer workflows.** The examples cover ledger and settings data, a Tables fixture and a BRAT policy fixture.
- **The finance target is Beancount Ledger (`beancount-finance`).** This replaces the stale Flat Financing framing.
- **Named plugin intents separate finance, Tables and BRAT requests.** Generic plugin requests retain a catch-all route.
- **The feature catalog grows from 20 to 23 entries.** A plugins category adds cards for the three plugins.
- **Two new deterministic scenarios bring the playbook from 17 to 19.** They cover Tables rendering and headless BRAT beta installation.

---

## Plugin Knowledge

#### Focused Reference Families

The deep reference families are at `references/plugins/beancount-finance/`, `references/plugins/obsidian-tables/` and `references/plugins/obsidian42-brat/`. Each covers its plugin's data model, workflows and troubleshooting.

&nbsp;

#### Copyable File Examples

The Beancount Ledger assets include an example ledger and a complete settings payload. The other assets are an Obsidian Tables `.table.md` fixture and a BRAT `data.json` policy fixture, all for file-layer workflows.

&nbsp;

#### Correct Finance Identity

The target plugin is Beancount Ledger (`beancount-finance`) from `mkshp-dev/obsidian-finance-plugin`. The tagged manifest and inspected source define its current plugin identity and data contract, replacing the stale Flat Financing framing.

## Skill Routing

#### Named Plugin Routes

`SKILL.md` is version `0.2.0.0`. The coarse `PLUGINS` route was replaced by `PLUGIN_FINANCE`, `PLUGIN_TABLES` and `PLUGIN_BRAT`, while generic `PLUGINS` remains the catch-all. Each specific intent maps only to its plugin-operation logic, slim index and three deep reference documents.

`TROUBLESHOOT` and `INSTALL` priority boosts are preserved. A specific-plugin tie preference makes a named plugin route beat generic plugin wording. Every deep plugin document is listed in the resource-loading block and Section 8 references.

The `feature-catalog/plugins/` category contains `beancount-finance.md`, `obsidian-tables.md` and `obsidian42-brat.md`. Each card documents file-layer operations, and the root inventory grows from 20 to 23 entries.

## Manual Testing Playbook

#### Tables and BRAT Scenarios

`OBS-012` creates or edits an Obsidian Tables `.table.md` and verifies its rendered round-trip. `OBS-013` covers headless BRAT staging, registration and activation of a tagged beta plugin.

The scenario tables, wave plan, automated cross-reference and feature-catalog cross-reference are updated for the added scenarios.

## Adopted Surface Set

#### Headless and App-Backed CLIs

Yakitrak `notesmd-cli` is the headless CLI and operates directly on the vault filesystem with no running app. The app-backed CLI is the official Obsidian CLI in Obsidian desktop v1.12.4+, which remote-controls a live desktop app after in-app registration.

&nbsp;

#### MCP and Plugin Data

The default MCP is `cyanheads obsidian-mcp-server@3.2.9`, a Code Mode stdio server using Local REST API v4.0.0+ and a bearer token. Community plugin data covers Beancount Ledger, Tables and BRAT files edited at the file layer, followed by a plugin or app reload when rendering or activation must be observed.

&nbsp;

#### File and App Boundaries

Plugin operations edit the files each plugin reads rather than drive command palettes or dashboards. Parse and verify the files, then reload when a visible render or activation check is required. A valid file proves persistence, while the app proves the plugin can consume the changed data.

The Tables render check still requires an Obsidian app with the Tables plugin enabled, since file parsing alone does not prove the visible view. BRAT staging requires a real or captured GitHub release, exact asset selection, `curl` and `jq`. No token value belongs in `data.json`.

Beancount validation and price/query operations depend on the local `bean-check`, `bean-query` and `bean-price` executables. The official `obsidian` CLI action syntax remains a local VERIFY boundary when a scenario requests an app reload or open action.

## Upgrade Notes

Existing slim plugin indexes remain the front door. Named finance, Tables or BRAT requests load the corresponding deep subfolder documents, while generic plugin requests load only the shared operation logic and three indexes.

The two new playbook scenarios require controlled vault fixtures and preserve the existing PASS/FAIL/SKIP evidence rules.

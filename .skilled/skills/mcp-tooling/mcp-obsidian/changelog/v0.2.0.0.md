# mcp-obsidian v0.2.0.0, Plugin Knowledge Deepening

mcp-obsidian v0.2.0.0 deepens guidance for three community plugins.

- It covers Beancount Ledger, Obsidian Tables and BRAT.
- It adds focused plugin references.
- It adds copyable file-layer examples.

The release also separates named-plugin routing.

- It adds plugin cards to the feature catalog.
- It expands the playbook for Tables and BRAT workflows.

&nbsp;

## Why This Release

This release closes two gaps in plugin guidance.

- A finance request should not load unrelated plugin references.
- A bare plugin request still needs a usable catch-all.

## Plugin Knowledge

Three community plugins gain deep reference families here.

#### Focused Reference Families <a id="c-focused-reference-families"></a>

- The deep reference families are at `references/plugins/beancount-finance/`, `references/plugins/obsidian-tables/` and `references/plugins/obsidian42-brat/`.
- Each covers its plugin's data model, workflows and troubleshooting.

#### Copyable File Examples <a id="c-copyable-file-examples"></a>

- The Beancount Ledger assets include an example ledger and a complete settings payload.
- The other assets are an Obsidian Tables `.table.md` fixture and a BRAT `data.json` policy fixture.
- All are for file-layer workflows.

#### Correct Finance Identity <a id="c-correct-finance-identity"></a>

- The target plugin is Beancount Ledger (`beancount-finance`) from `mkshp-dev/obsidian-finance-plugin`.
- The tagged manifest and inspected source define its current plugin identity and data contract.
- They replace the stale Flat Financing framing.

## Skill Routing

This area controls how requests reach plugin operations.

#### Named Plugin Routes <a id="c-named-plugin-routes"></a>

- `SKILL.md` is version `0.2.0.0`.
- The coarse `PLUGINS` route was replaced by `PLUGIN_FINANCE`, `PLUGIN_TABLES` and `PLUGIN_BRAT`.
- Generic `PLUGINS` remains the catch-all.
- Each specific intent maps only to its plugin-operation logic, slim index and three deep reference documents.
- `TROUBLESHOOT` and `INSTALL` priority boosts are preserved.
- A specific-plugin tie preference makes a named plugin route beat generic plugin wording.
- Every deep plugin document is listed in the resource-loading block and Section 8 references.

## Adopted Surface Set

This area records the tools the workflows use.

#### Headless and App-Backed CLIs <a id="c-headless-and-appbacked-clis"></a>

- Yakitrak `notesmd-cli` is the headless CLI.
- It operates directly on the vault filesystem with no running app.
- The app-backed CLI is the official Obsidian CLI in Obsidian desktop v1.12.4+.
- It remote-controls a live desktop app after in-app registration.

#### MCP and Plugin Data <a id="c-mcp-and-plugin-data"></a>

- The default MCP is `cyanheads obsidian-mcp-server@3.2.9`.
- It is a Code Mode stdio server using Local REST API v4.0.0+ and a bearer token.
- Community plugin data covers Beancount Ledger, Tables and BRAT files edited at the file layer.
- A plugin or app reload follows when rendering or activation must be observed.

#### File and App Boundaries <a id="c-file-and-app-boundaries"></a>

- Plugin operations edit the files each plugin reads.
- They do not drive command palettes or dashboards.
- Parse and verify the files.
- Then reload when a visible render or activation check is required.
- A valid file proves persistence.
- The app proves the plugin can consume the changed data.
- The Tables render check still requires an Obsidian app with the Tables plugin enabled.
- That is because file parsing alone does not prove the visible view.
- BRAT staging requires a real or captured GitHub release, exact asset selection, `curl` and `jq`.
- No token value belongs in `data.json`.
- Beancount validation and price/query operations depend on the local `bean-check`, `bean-query` and `bean-price` executables.
- The official `obsidian` CLI action syntax remains a local VERIFY boundary.
- That applies when a scenario requests an app reload or open action.

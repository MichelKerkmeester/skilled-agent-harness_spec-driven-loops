# v1.0.0.0, First Release

The first `mcp-magicpath` release delivered MagicPath as a read-only transport in the `mcp-tooling` hub. It documented the registered Code Mode manual, its tools and their calling and credential conventions.

## Why This Release

The registered surface was read-only on purpose. The CLI's write commands were deliberately left unregistered so an agent could not reach them through a tool call.

## What's New at a Glance

- **`mcp-magicpath` delivers the MagicPath transport.** It uses the existing `magicpath` Code Mode manual.
- **`SKILL.md` defines discovery-first execution.** It names MagicPath-specific activation signals and a guarded multi-intent router.
- **Fourteen read-only tools cover six themes.** They are registered in the `magicpath` manual.
- **Tools use the `magicpath.<tool>(...)` callable form.** The same dotted names appear during discovery.
- **Phase 002 establishes the `MAGICPATH_TOKEN` credential and synchronous call conventions.** Browser-based `magicpath-ai login` is the other credential route.
- **The write boundary includes safe component inspection.** `inspect_component` can read a component without installation.
- **`feature-catalog/` maps the registered surface.** Its overviews follow the six tool themes.
- **Reader documentation covers use and limits.** It includes the manual snapshot, reference guides and `README.md`.

## MagicPath Transport

#### The Existing Manual Powers the Bridge

The transport metadata set `packetKind: transport` and `mutatesWorkspace: false`, with no design or workspace-mutation authority. It used the existing `magicpath` Code Mode manual through a UTCP `cli` transport. The manual command ran `node .opencode/bin/magicpath-utcp-manual.cjs`, and tool calls ran `node .opencode/bin/magicpath-utcp-exec.cjs`, which shelled out to the `magicpath-ai` binary.

MagicPath ships no MCP server. The bridge was the `magicpath-ai` Node CLI, installed version `2.6.1`. The registered manual was preserved as a verify-only asset instead of editing `.utcp_config.json` or creating a second manual.

&nbsp;

#### Discovery Guides Read Calls

`SKILL.md` defined MagicPath-specific activation signals and a guarded multi-intent router. It defined discovery-first execution and the read funnel, which put reachability first, search or list next, inspect or get after that and share last. It also defined read-only safety rules.

## Registered Tool Surface

#### Six Themes Cover Fourteen Tools

Session tools were `info` and `whoami`. Component tools were `search_components`, `inspect_component` and `list_components`. Project tools were `list_projects`, `active_project` and `share_link`. Team tools were `list_teams` and `list_members`. Theme tools were `list_themes` and `get_theme`. Local and canvas tools were `list_installed` and `selection`. Every registered tool was read-only.

&nbsp;

#### Callable Names and Input Limits

Code Mode applied its `{manual}.{tool}` rule once to produce `magicpath.<tool>(...)`, because the tool names had no `magicpath_` prefix of their own. Discovery names appeared dotted. Per-session `tool_info` confirmation stayed mandatory. The packet failed closed on drift.

`limit` was declared as a `string`, not a number. `list_components` paginated by cursor (`after`), not page number. `share_link` accepted a component generated name or numeric project id in one `identifier`.

---

## Calls and Credentials

#### Calls Return Synchronous Values

`SKILL.md` defined the synchronous calling convention established by phase 002. Inside `call_tool_chain`, tools were synchronous, with no `await`, top-level `await` or returned Promise. A returned Promise silently marshalled as `{}`. TypeScript type annotations failed to parse, so calls used plain JavaScript.

A failing command did not throw. It returned error text or a JSON error object as an ordinary value, so callers had to inspect the result rather than rely on `try`/`catch`.

&nbsp;

#### Credentials Follow Phase 002

The credential path was browser-based `magicpath-ai login` or the `MAGICPATH_TOKEN` environment variable. Code Mode prefixed environment variables with the manual name, so `.env` used `magicpath_MAGICPATH_TOKEN`.

Without a credential, a call returned structured JSON `{"error":"Not authenticated. Set MAGICPATH_TOKEN or run \`magicpath-ai login\`.","code":"NOT_AUTHENTICATED","suggestion":"..."}`. `info` was the only tool that answered without credentials.

&nbsp;

#### Help and the Manual Set the Surface

`magicpath-ai info -o json` reported a stale `cli.commands` list that under-reported the real CLI surface. `magicpath-ai --help` was authoritative for CLI commands, while the registered manual defined what an agent could call.

## Read-Only Boundaries

#### CLI Write Commands Are Unregistered

The CLI could write `.tsx` files into the calling project, install npm packages and create remote projects and component revisions through `add`, `code`, `image`, `create-project` and `clone`. The packet refused to invoke, document as reachable or route to any unregistered write command.

Write requests were escalated to the operator or to a workflow that runs the CLI directly outside a tool call.

&nbsp;

#### Component Inspection Avoids Installation

`inspect_component` read source, dependencies and imports without installing anything and without a package manifest. It was the only way to read a component into a non-React project.

&nbsp;

#### Minimal Runtime Authority

Runtime authority stayed minimal. It allowed Read, Bash, Grep, Glob and Code Mode calls. Write, Edit and Task were forbidden.

## Documentation and Scope

#### The Catalog Maps Every Theme

`feature-catalog/` supplied a root inventory and six domain overviews. There was one overview per theme and one leaf for each of the fourteen tools. Catalog entries covered call forms, argument bounds, cursor pagination, the `share_link` identifier union, credential split, mutation class and cross-links to canonical references.

The per-tool leaf count equaled the fourteen registered tools. The catalog treated any live drift from those tools as a fail-closed escalation.

&nbsp;

#### References and Assets Carry the Contract

`references/tool-surface.md` carried the fourteen-tool contract, read funnel, stale `cli.commands` warning, calling convention and open questions. `references/credential-setup.md` carried the registered manual, env-var wiring, unauthenticated failure shape, callable naming rule and discovery-first contract. `references/mutation-boundary.md` carried the registered read-only surface, unregistered write surface and escalation path for write requests.

`assets/utcp-magicpath-manual.md` preserved the registered manual snapshot, env-var wiring and exec-wrapper behavior, including placeholder stripping and structured JSON errors.

&nbsp;

#### The README Describes Current Use

`README.md` described current-state use, the read funnel, the wiring, mutation boundary, troubleshooting and verification. All packet paths used kebab-case.

&nbsp;

#### Hub Files Wait for Phase 004

No hub files or live configuration belonged to this packet's release. The packet created no hub-root `description.json`, `graph-metadata.json`, `mode-registry.json` or `hub-router.json`. Those hub-root-only files were left for phase 004.

No undocumented tools, arguments, limits or authentication results were claimed. No capability from the MagicPath website or README beyond the registered manual's output was documented.

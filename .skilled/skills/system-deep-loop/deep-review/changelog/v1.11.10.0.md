# v1.11.10.0, A File You Were Already Editing Is Reported as Contested

The review loop protocol said to write containment files. It said to do this for every new dirty path outside the lineage folder. It said to write them under the lineage. So a file you were already editing read as the reviewer's own write. That happened while a review ran. The protocol now treats that file as contested. It also says where each kind of run reports it.

&nbsp;

## What's New at a Glance

- **A file that already had changes is contested, not the lineage's.** A path was dirty before the lineage started. If it changed again during the run, the run makes no quarantine copy, patch or revert. Its pre-dispatch bytes stay in the lineage's `containment/baseline/` folder.
- **Every run tells you about it.** A fan-out run records a `containment_contested` ledger event. It also records a `containmentContested` field on the lineage output. A single-lineage run appends the same event to its state log. The dispatch step prints the paths beside any violations.
- **Everything else is attributed as before.** A path that was clean when the lineage started still counts as the lineage's. A lane that produced its review artifacts still settles as complete. Opt-in restore mode still puts an already-dirty file back to its pre-dispatch bytes. That mode is meant for a checkout with one writer.

&nbsp;

## Upgrade

No migration required. Before you trust a contested file, compare it with its copy in `containment/baseline/`. The tree shows that the bytes changed. It does not show who wrote them.

# v1.11.10.0, A File You Were Already Editing Is Reported as Contested

The review loop protocol said write containment files every new dirty path outside the lineage folder under the lineage. So a file you were already editing while a review ran read as the reviewer's own write. The protocol now treats that file as contested and says where each kind of run reports it.

> Spec folder: `specs/system-deep-loop/043-fanout-resume-and-containment` (Level 2)

&nbsp;

## What's New at a Glance

- **A file that already had changes is contested, not the lineage's.** When a path was dirty before the lineage started and changed again during it, the run makes no quarantine copy, patch or revert. Its pre-dispatch bytes stay in the lineage's `containment/baseline/` folder.
- **Every run tells you about it.** A fan-out run records a `containment_contested` ledger event and a `containmentContested` field on the lineage output. A single-lineage run appends the same event to its state log, and the dispatch step prints the paths beside any violations.
- **Everything else is attributed as before.** A path that was clean when the lineage started still counts as the lineage's, and a lane that produced its review artifacts still settles as complete. Opt-in restore mode, meant for a checkout with one writer, still puts an already-dirty file back to its pre-dispatch bytes.

&nbsp;

## Upgrade

No migration required. Before you trust a contested file, compare it with its copy in `containment/baseline/`, because the tree shows that the bytes changed but not who wrote them.

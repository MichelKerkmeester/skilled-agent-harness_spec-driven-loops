# v1.13.0.0, Expansive Depth Mode for Review

Deep review can now split its target into sub-targets and work through them. This release adds an opt-in expansive depth mode for that.

- Reviews propose sub-targets while they work.
- Each proposal passes fixed checks before it joins the frontier.

Runs without the flag keep their behavior.

- Nothing changes unless the flag is passed.
- The one difference is one paragraph in CLI lineage prompts.

&nbsp;

## Why This Release

A review that checks its target in one pass can look finished too early. Nothing could split a sub-target out once the review began. So a large target could stop before each part got its own look.

- A narrow pass looked the same as a thorough one.
- The new mode lets the review widen within fixed bounds.

## Turning It On

Turning the mode on takes one flag. Without the flag, a review keeps its old behavior, and its dashboard gains no section.

#### Widen a review with one flag <a id="c-widen-a-review-with-one-flag"></a>

- Pass `--depth-mode=expansive` to a `/deep:review` run.
- Leave the flag out, or pass `--depth-mode=default`, to keep the old behavior.
- `rg -n -- '--depth-mode' .skilled/commands/deep/review.md` finds the setup line and the flag row.

#### Default runs keep their output <a id="c-default-runs-keep-their-output"></a>

- A default run writes the same registry, dashboard, Next Focus, prompt pack and stop config as before.
- The mode key appears only on expansive runs.
- CLI lineage prompts gain one paragraph in the agent persona.
- That paragraph has no effect on a default run.
- The paragraph applies only when an iteration prompt holds a `FRONTIER` block.

#### See the frontier on the dashboard <a id="c-see-the-frontier-on-the-dashboard"></a>

- An expansive review adds a `## 10B. FRONTIER` section to its dashboard.
- The section shows frontier size, pruned sub-targets, revisits and budget spent at each depth.
- A default dashboard has no such section.

## Admitting Sub-Targets

A review splits its target into sub-targets before it starts. Each proposal passes fixed checks before it joins the frontier.

#### Sub-targets exist before the first pass <a id="c-start-from-depth-one-sub-targets"></a>

- The review splits its target into depth-one sub-targets before iteration one.
- Each sub-target gets a scope and a question.
- A repeated launch adds no second set of sub-targets.
- A review writes its sub-targets to its own store and never to an inbox.

#### Every proposal passes six fixed checks <a id="c-every-proposal-passes-six-fixed-checks"></a>

- The checks run in one fixed order.
- Relevance comes first, then dedupe, depth, fan-out, budget and cycle.
- Relevance needs evidence, a scope inside the review target and a parent that exists.
- Dedupe refuses a question the review already holds.
- Depth stops at three levels.
- Fan-out caps each parent at six children, caps the root at eight on a review and caps the total count.
- A child cannot hold more budget than its parent.
- A cycle is refused.

#### Pruned proposals name their reason <a id="c-pruned-proposals-name-their-reason"></a>

- The first failing check decides the reason.
- A sub-target that arrives with a reason is settled at seed time.
- Two seed reasons exist. `merge-no-own-diff` marks a merge with no diff of its own. `generated-artifact` marks a generated index rebuild.
- A pruned proposal keeps its reason in the store.
- Only an admitted proposal joins the frontier.

## Steering and Stopping

Once sub-targets exist, the review works the active node's next uncovered dimension. It stops only when no sub-target stays open.

#### Each sub-target needs every dimension <a id="c-each-sub-target-needs-every-dimension"></a>

- A sub-target answers once every dimension in its universe has evidence behind it.
- The universe holds the four canonical dimensions plus any custom name. A run configured with a subset still needs all four on each sub-target.
- The active sub-target's next uncovered dimension steers the next iteration.
- Next Focus picks the blocked-stop recovery first, then the pivot, then the active sub-target.
- The leaf's own focus comes after that, and the first uncovered dimension comes last.

#### Open sub-targets hold a clean stop <a id="c-open-sub-targets-hold-a-clean-stop"></a>

- While a sub-target stays open, a review stop candidate becomes `CONTINUE` with `frontierOpen`.
- The hold covers the clean stop, which is a hard stop, as well as the composite stop.
- The iteration cap, consecutive failures, stuck recovery, pause, the max-duration stop, the off setting and the max-iterations policy still decide first.
- The review floor still decides first as well.
- Stuck recovery closes the active sub-target as `exhausted`. A sub-target the review cannot fund then stops holding it open.
- Once every sub-target is closed and at least one was answered, a review that forms no other stop candidate gets `frontier_drained`. The legal-stop gates still decide it, so a review whose sub-targets are done stops before its cap.

#### Budget splits across three depth bands <a id="c-budget-splits-across-three-depth-bands"></a>

- The iteration budget splits 50, 35 and 15 percent across depths one, two and three.
- Unused budget rolls down only after its band has no open sub-target, and it never rolls up.
- A band that spends its share closes its open sub-targets as `exhausted` with reason `budget`.
- With `--max-iterations` left at its default, the review sizes its budget from the seed. The formula is `min(24, max(7, 2 × D × (S + maxDepth − 1)))` iterations. S is the seeded sub-targets. D is the four canonical dimensions plus each custom name.
- D is never below four, so the ceiling of 24 binds from the first seed. A wide review is better split with fan-out.
- A fan-out lineage sizes its own budget from its share of the seed, with D fixed at four. A lineage dealt no seed runs at its default. That is 12 iterations native and 7 on a CLI.
- An explicit `--max-iterations`, marker, setup answer or fan-out matrix `iterations` value is kept as given.

#### The pivot waits for a closed frontier <a id="c-the-pivot-waits-for-a-closed-frontier"></a>

- The divergent review pivot refuses to run while a sub-target stays open.
- It seeds one revisit direction for each sub-target the frontier closed as `exhausted` or `blocked`.
- A default run keeps its pivot unchanged.

## Fan-Out Runs

A fan-out review deals its depth-one sub-targets across its lineages. The merge then checks the split.

#### Lineages share the sub-targets <a id="c-lineages-share-the-sub-targets"></a>

- Open depth-one sub-targets deal round-robin across the lineages, in node-id order.
- Each lineage writes its share to its own store before it spawns.
- A review lineage has no inbox.
- The orchestration summary records which lineage holds which sub-target.

#### The merge names a missing sub-target <a id="c-the-merge-names-a-missing-sub-target"></a>

- The merge checks that every dealt sub-target reached a lineage.
- A sub-target that no lineage reports gets a warning on stderr, named `frontier_partition_guard_failed`.
- The merged output carries `frontier_partition_guard` with the missing identifiers.
- The merge still completes.

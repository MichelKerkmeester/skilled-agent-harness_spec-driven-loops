# v1.9.13.0, An Interrupted Lineage Resumes and an Operator Edit Is No Longer Quarantined

Two faults showed up in one interrupted fan-out run. Resuming a lineage named its new dispatch exactly like the first one. So the effect gateway replayed the old result. The executor never ran. The lane failed. And the write-containment guard filed a file the operator was already editing under the lane. That was as if the lane had written it.

> Spec folder: `specs/system-deep-loop/043-fanout-resume-and-containment` (Level 2)

&nbsp;

## What's New at a Glance

- **A resumed lineage runs its executor again.** Each dispatch after the first gets a fresh effect id. It ends in `:redispatch-<count>`. The count comes from the dispatches the ledger already holds. So a resume is a new dispatch, not a replay.
- **A file that was already dirty is contested, not quarantined.** A path was dirty before the lane started. It changes again during the lane. Then the guard reports it as a `containment_contested` ledger event. It also adds a `containmentContested` field on the lineage output. It makes no quarantine copy, patch or revert.
- **The rest of containment is unchanged.** A path that was clean before the lane started is still a violation. A path the lane quarantined on an earlier pass stays the lane's. Restore mode keeps its single-owner reading.

&nbsp;

## Upgrade

No migration required. A contested file keeps its pre-dispatch bytes in the lineage's `containment/baseline/` folder. So compare against them before trusting either writer.

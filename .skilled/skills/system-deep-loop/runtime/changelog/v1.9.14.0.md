# v1.9.14.0, A Contested Path Reaches the State Log

A contested path, one that was already dirty before the dispatch and changed during it, gets no quarantine copy, no patch and no violation event. So when a caller ignored the result's `contested` field, nothing recorded the path at all. The guard now writes one record for it itself.

> Spec folder: `specs/system-deep-loop/043-fanout-resume-and-containment` (Level 2)

&nbsp;

## What's New at a Glance

- **A contested path is logged where violations are.** When the caller passes `stateLogPath` and some path was contested, `enforceWriteContainment` appends a `containment_contested` event with severity `warning`, the paths and their note. The `paths` and `note` match the fan-out runner's ledger event.
- **The violation event is unchanged.** It still names only the lane's own paths, and the result's `event` field still describes it alone.
- **A guard covers the workflow call sites.** A new test fails when any `/deep` workflow call to `enforceWriteContainment` stops passing a state log or stops printing contested paths.
- **The references name files that exist.** The integration risks and source anchors point the MCP-free boundary at the hub `SKILL.md`, the script contract cites `README.md` for the supported consumer path, and the test helper registers each redaction once.

&nbsp;

## Upgrade

No migration required. The fan-out runner passes no `stateLogPath`, so its ledger still carries one `containment_contested` event per contested pass.

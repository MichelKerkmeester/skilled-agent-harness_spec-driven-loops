# v1.10.0.0, The Frontier Store and the Gates Around It

Expansive runs keep their frontier in the shared runtime.

- `frontier-admit.cjs` seeds each depth-1 node and admits later proposals.
- Six checks decide admission, and a prune names the check that failed.
- The stop decision reads the store on every pass.

Fan-out splits that frontier across lineages.

- Each lineage gets its own share and its own store.
- Each lineage writes its own coverage graph.
- The merge names any dealt node that no lineage reports.

The iteration gates got stricter.

- A landed iteration is no longer dispatched twice.
- A pivot retry carries its attempt number through the CLI.

Smaller changes tighten the executor and the records.

- A research run on Claude honors the configured config dir.
- Research sources carry a class derived from their path.
- A torn store row is reported with its file and line.

&nbsp;

## Why This Release

Expansive depth shipped in deep-research and deep-review. The runtime behind it had no entry in its own line. Readers of `deep-loop-runtime` saw nothing from the hub releases v2.1.0.0 to v2.1.7.0.

- The frontier store, its checks and its stop veto.
- The fan-out partition, its per-lineage store and its merge.
- The pivot retry and the iteration gates.
- The config dir, the source class and the record fixes.

## Frontier Store

The frontier store records every question an expansive run may work. It seeds the first level, checks each proposal and closes nodes as answers land.

#### The Frontier Store Owns Every Node <a id="c-the-frontier-store-owns-every-node"></a>

- `runtime/scripts/frontier-admit.cjs` holds the node store.
- It seeds depth-1 nodes at the start of a run.
- It admits or prunes each proposal and closes nodes.
- It renders the prompt block and projects the graph.

#### Six Checks Decide Admission <a id="c-six-checks-decide-admission"></a>

- The order is relevance, dedupe, depth, fan-out, budget and cycle.
- A pruned proposal names the check that failed.
- A pruned node never returns as live work.
- A child of a pruned node is pruned on relevance.

&nbsp;

## Stop Decision

The stop decision reads the frontier on every pass. An open node keeps the run alive, and a drained frontier gives a review its own stop.

#### An Open Node Keeps the Run Going <a id="c-an-open-node-keeps-the-run-going"></a>

- `convergence.cjs` turns a stop candidate into `CONTINUE`.
- The verdict carries `frontierOpen` while a node stays open.
- The veto never creates a stop of its own.
- The iteration cap, a stuck recovery and a manual stop still win.

#### A Drained Frontier Can Stop a Review <a id="c-a-drained-frontier-can-stop-a-review"></a>

- Every node closed and one answered gives the `frontier_drained` candidate.
- The candidate is a hard stop.
- A frontier that closed with nothing answered forms no candidate.

&nbsp;

## Fan-Out

Fan-out splits the seeded frontier across lineages. Each lineage works its share, and the merge rejoins the parts.

#### Each Lineage Gets Its Share <a id="c-each-lineage-gets-its-share"></a>

- `fanout-run.cjs` deals the seeded nodes round-robin.
- Each lineage gets its share and its own frontier store.
- An unsized lineage is sized from that share.

#### Each Lineage Keeps Its Coverage Graph <a id="c-each-lineage-keeps-its-coverage-graph"></a>

- Each lineage writes its own coverage graph in `graph-db/`.
- `fanout-run.cjs` sets `DEEP_LOOP_COVERAGE_DB_DIR` to that folder.
- The shared database sits outside the lineage's write surface.
- A default fan-out run of either loop can stop before its cap.

#### The Merge Rejoins the Parts <a id="c-the-merge-rejoins-the-parts"></a>

- `fanout-merge.cjs` merges the lineage frontiers.
- A partition guard names any dealt node no lineage reports.
- A merged review keeps each lineage's coverage.
- Dimension, traceability, search and candidate surfaces carry through.

&nbsp;

## Iteration Gates

An iteration gate decides what a failed pass costs. A landed iteration keeps its files, and a pivot gets one more council round.

#### A Landed Iteration Skips Redispatch <a id="c-a-landed-iteration-skips-redispatch"></a>

- Three verify failures skip the redispatch.
- They are `executor_missing`, `findings_not_enumerated` and `ledger_backing_missing`.
- Those failures appear only after the narrative, state record and delta exist.
- Every other failure still gets one redispatch.

#### A Pivot Gets One Retry <a id="c-a-pivot-gets-one-retry"></a>

- `maxCouncilSeatOutputs` means three seats per council attempt.
- A first-attempt quorum miss reopens the pivot as attempt 2.
- A second miss ends the pivot.
- `divergent-pivot.cjs` carries the attempt number through `prepare` and `finalize`.

&nbsp;

## Runtime Surface

The executor and the records gained smaller changes. The flags stay opt-in, and a default run behaves as before.

#### Research Runs Use the Config Dir <a id="c-research-runs-use-the-config-dir"></a>

- Research accepts `--claude-config-dir` on `cli-claude-code`.
- The dir reaches the child and the executor audit row.
- An empty value means no config dir is set.
- Review still requires the flag on `cli-claude-code`.

#### Research Sources Carry a Class <a id="c-research-sources-carry-a-class"></a>

- `upsert.cjs` sets `quality_class` on each SOURCE node.
- The class comes from the path, name, label or id, in that order.
- Source diversity counts the distinct classes a question cites.
- A question answered only from code still blocks.

#### Review Evidence Reaches the Graph <a id="c-review-evidence-reaches-the-graph"></a>

- `upsert.cjs` derives one FINDING node per review finding and one EVIDENCE_FOR edge to its FILE node when the finding carries a `path:line` ref.
- A prefixed leaf finding id folds onto the stored `finding:<id>` node.
- An edge to a node that neither the batch nor the stored graph declares is skipped and listed in `rejectedOrphanEdges` instead of rolling back the batch.

## How It Was Checked

Each change was checked against the workflow and the runtime code. The table shows the behavior before and after.

#### Before and After <a id="c-before-and-after"></a>

| Check | Before | After |
|---|---|---|
| An expansive run with a node still open | a stop candidate ended the run | `CONTINUE` with `frontierOpen` |
| An expansive review with every node closed and one answered | the run went to its cap | stops on `frontier_drained` |
| A pivot whose first council round misses quorum | the pivot failed | one retry as attempt 2 |
| A verify failure after an iteration landed | one redispatch, then an error | no second dispatch |
| A `run_extended` event with an unmatched cap | accepted | refused |

## Upgrade Notes

No migration required. The frontier code runs only under `--depth-mode=expansive`.

#### Before You Start <a id="c-before-you-start"></a>

1. Run the runtime suite as before, with no change to a default run.
2. Pass `--depth-mode=expansive` only when you want a frontier.

# v1.6.29.0, Verification and Containment Rows Survive the Refresh

The last three diagnostic writers now go through the append gateway on a ledger-backed state log, so a degraded verification and a write containment finding stay in the log after a refresh. With `v1.6.27.0` and `v1.6.28.0`, every row the deep loop writes into a ledger-backed state log now reaches the ledger.

&nbsp;

## What's New at a Glance

- **`verification_degraded` reaches the ledger.** `validateIterationOutputs` writes it through the shared failure row helper, and each post-dispatch validation step passes the run's session id.
- **Containment rows reach the ledger.** `containment_violation` and `containment_contested` go through the same helper, and all twelve containment calls in the four review and research workflows pass the session id.
- **Research gains three stems.** `deep_research.verification_degraded`, `deep_research.containment_violation` and `deep_research.containment_contested` carry the rows field for field. Review carries them whole under its iteration stem.
- **The executor check reads the opening row.** On a ledger-backed log, `executor_missing` accepts an executor on the iteration's `iteration_start` row.
- **The docs say where the executor lands.** The research prompt pack and the review loop protocol now name the opening `iteration_start` row.
- **The hub reads v1.6.29.0.** Four routing files carry the new version.

&nbsp;

## Upgrade

No migration is required. A diagnostic row on a ledger-backed log now costs one gateway call, paid only when verification degrades or containment finds a path. A log with no ledger gets the same rows as before.

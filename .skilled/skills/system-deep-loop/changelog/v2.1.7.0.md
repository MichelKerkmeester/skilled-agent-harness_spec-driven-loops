# v2.1.7.0, The Expansive Frontier Runtime and Its Routing

Expansive runs keep their frontier in the shared runtime.

- `frontier-admit.cjs` seeds, admits and closes frontier nodes.
- Six checks decide whether a proposal enters the frontier.

The stop decision reads that store.

- An open node keeps the run going.
- A drained frontier can stop a review.

Fan-out splits the frontier and rejoins it.

- Each lineage gets its own share and its own coverage graph.
- The merge names any dealt node that went missing.

Expansive wording reaches the hub.

- The research and review aliases gained new phrasings.
- The advisor gained one too.

&nbsp;

## Why This Release

Expansive depth mode shipped in deep-research v1.16.0.0 and deep-review v1.13.0.0. The shared runtime behind it carried no hub entry.

- The frontier store, its checks and its stop veto had no hub record.
- The fan-out partition and its merge had no hub record.
- A default fan-out lineage had no coverage graph it could write.

## Frontier Store

The frontier store records every question an expansive run may work. It seeds the first level, checks each proposal and closes nodes as answers land. The store also renders the prompt block and projects the graph.

#### The Frontier Store Owns Every Node <a id="c-the-frontier-store-owns-every-node"></a>

- `runtime/scripts/frontier-admit.cjs` holds the node store.
- It seeds depth-1 nodes at the start of a run.
- It admits or prunes each proposal and closes nodes.
- It renders the prompt block and projects the graph.

#### Six Checks Decide Admission <a id="c-six-checks-decide-admission"></a>

- The order is relevance, dedupe, depth, fan-out, budget and cycle.
- A pruned proposal names the check that failed.
- Admission checks review scope against the review target.

#### A Pruned Node Stays Pruned <a id="c-a-pruned-node-stays-pruned"></a>

- A pruned node never returns as live work.
- A close cannot revive it.
- A child of a pruned node is pruned on relevance.

#### Review Scope Accepts Named Lists <a id="c-review-scope-accepts-named-lists"></a>

- Admission reads one scope list or one list per kind.
- The terminal gates read the same shapes.

&nbsp;

## Stop Decision

The stop decision reads the frontier. An open node vetoes a stop candidate, and a drained frontier gives a review its own stop reason.

#### An Open Node Vetoes a Stop <a id="c-an-open-node-vetoes-a-stop"></a>

- `convergence.cjs` turns a stop candidate into `CONTINUE`.
- The verdict carries `frontierOpen` while a node stays open.

#### A Drained Frontier Can Stop a Review <a id="c-a-drained-frontier-can-stop-a-review"></a>

- Every node closed and one answered gives the `frontier_drained` candidate.
- The candidate is a hard stop.

&nbsp;

## Fan-Out

Fan-out splits the seeded frontier across lineages. Each lineage works its share, and the merge rejoins the parts.

#### Fan-Out Deals the Seeded Nodes <a id="c-fan-out-deals-the-seeded-nodes"></a>

- `fanout-run.cjs` deals the seeded nodes round-robin.
- Each lineage gets its share and its own frontier store.
- An unsized lineage is sized from that share.

#### The Merge Rejoins the Frontiers <a id="c-the-merge-rejoins-the-frontiers"></a>

- `fanout-merge.cjs` merges the lineage frontiers.
- A partition guard names any dealt node no lineage reports.

#### Each Lineage Keeps Its Coverage Graph <a id="c-each-lineage-keeps-its-coverage-graph"></a>

- Each fan-out lineage keeps its own coverage graph in `graph-db/`.
- `fanout-run.cjs` sets `DEEP_LOOP_COVERAGE_DB_DIR` to that folder.
- The shared database sits outside the lineage's write surface.
- A default fan-out run of either loop can stop before its cap.

&nbsp;

## Ledger and Reducers

The reducers and the ledger reject a damaged record. A torn row is skipped with its location, and a mismatched extension cap is refused.

#### A Torn Store Row Is Reported <a id="c-a-torn-store-row-is-reported"></a>

- Both reducers skip a torn store row.
- The reducer prints the row's file and line.

#### An Extension Ceiling Must Match Its Run <a id="c-an-extension-ceiling-must-match-its-run"></a>

- The ledger refuses a `run_extended` event with an unmatched cap.
- The new cap must equal the continued run plus the added iterations.

&nbsp;

## Routing

Expansive-depth wording reaches the hub. The research and review aliases gained the phrases a request uses, and the advisor gained one of its own.

#### Expansive Requests Reach the Hub <a id="c-expansive-requests-reach-the-hub"></a>

- Research aliases gained "this research run" and the follow-up frontier phrasings.
- Review aliases gained "review target" and "sub-targets".
- The advisor gained "depth-capped frontier".

&nbsp;

## How It Was Checked

The frontier, stop-decision, fan-out, ledger and reducer suites pass. The golden tests keep a default run's output byte for byte. They strip the expansive-only persona paragraph from the lineage prompt before they compare.

&nbsp;

## Upgrade Notes

No migration required. The frontier code runs only under `--depth-mode=expansive`. The extension check applies to every run, and the extend step already writes a matching ceiling.

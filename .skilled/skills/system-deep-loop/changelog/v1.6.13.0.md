# v1.6.13.0, The Containment Docs Name the Contested Path

The research and review loop protocols said one thing. Write containment attributes every new dirty path to the lineage. That stopped being true when the runtime began reporting a file an operator was already editing as contested. The docs now say so. So do the command contracts built from them.

> Spec folder: `specs/system-deep-loop/043-fanout-resume-and-containment` (Level 2)

&nbsp;

## What's New at a Glance

- **The protocols name the one exception to attribution.** A path was dirty before the lane started. It changed again during the lane. That path is reported as contested. There is no quarantine copy or revert. A path that was clean at the start is still attributed.
- **The feature catalog states the trade-off.** A lane writes to a file an operator already had open. That write is reported only as contested. A brand-new file a second session creates mid-run still counts as a preserved advisory.
- **The deep research and deep review command contracts match.** They were recompiled from the updated protocols. So the contract a run loads carries the same rule.

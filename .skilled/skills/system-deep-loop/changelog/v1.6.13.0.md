# v1.6.13.0, The Containment Docs Name the Contested Path

The research and review loop protocols said that write containment attributes every new dirty path to the lineage. That stopped being true when the runtime began reporting a file an operator was already editing as contested. The docs and the command contracts built from them now say so.

> Spec folder: `specs/system-deep-loop/043-fanout-resume-and-containment` (Level 2)

&nbsp;

## What's New at a Glance

- **The protocols state the one exception to attribution.** A path dirty before the lane started and changed again during it is reported as contested, with no quarantine copy or revert, while a path that was clean at the start is still attributed.
- **The feature catalog states the trade-off.** A lane write to a file an operator already had open is reported only as contested, and a brand-new file a second session creates mid-run still counts as a preserved advisory.
- **The deep research and deep review command contracts match.** They were recompiled from the updated protocols, so the contract a run loads carries the same rule.

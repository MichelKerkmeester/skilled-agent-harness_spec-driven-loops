# v1.6.27.0, The Executor Row Survives the State Log Refresh

A review or research iteration run by a CLI executor now keeps its executor identity in the state log. Before this release the pre-dispatch audit wrote that row straight into the state log. The next projection refresh rebuilt the log from the ledger and dropped it. `v1.6.26.0.md` shipped with this gap open.

&nbsp;

## What's New at a Glance

- **The executor row goes through the append gateway.** On a state log with a ledger beside it, `writeFirstRecordExecutor` hands the gateway the `iteration_start` row with the run's ids. So the projection writes it back on every refresh.
- **Review carries the row whole.** The gateway records it under `deep_review.iteration_recorded`. That is the same stem the iteration record uses.
- **Research upcasts it to `deep_research.iteration_started`.** The stem gains an optional `executor` field. The projection writes it back on the opening row.
- **A redispatch adds no second row.** The audit skips an iteration whose row already names an executor.
- **A state log with no ledger is unchanged.** It keeps the direct write. Native runs still skip the audit.
- **The hub reads v1.6.27.0.** Four routing files carry the new version.

&nbsp;

## Upgrade

No migration is required. The four review and research workflows now pass the run's session id to the audit step. A gateway refusal of the executor row stops the pre-dispatch step. The direct write could not fail there.

# v1.6.15.0, Single-Lineage Runs Report a Contested Path

The write-containment guard holds a path that was already dirty before a dispatch out of its violations and reports it as contested. Only the fan-out runner read that report. The ten dispatch steps in the `/deep:research` and `/deep:review` workflows printed violations alone, so in a single-lineage run a lane write to a file the operator had open was reported nowhere. Each step now prints the contested paths with their note.

> Spec folder: `specs/system-deep-loop/043-fanout-resume-and-containment` (Level 2)

&nbsp;

## What's New at a Glance

- **Every dispatch step prints contested paths.** Beside any violations, the step prints each contested path and the note that the tree shows the bytes changed, not who wrote them.
- **The state log records them.** The runtime appends a `containment_contested` event to the run's state log, so the record survives the terminal output.
- **The protocols and the playbook match.** The research and review loop protocols say a single-lineage run reports the path in its state log. The shared-checkout playbook scenario now expects the contested path in `containmentContested` and the clean one in `containment.violations`. The command contracts were recompiled from both.

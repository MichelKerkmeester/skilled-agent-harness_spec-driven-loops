# v1.15.8.0, A File You Were Already Editing Is Reported as Contested

The research loop protocol said to write containment files under the lineage. That covered every new dirty path outside the lineage folder. So a file you were already editing when the run started read as the lineage's own write. The protocol now treats that file as contested. It says where each kind of run reports it.

&nbsp;

## What's New at a Glance

- **A file that already had changes is contested, not the lineage's.** A path was dirty before the lineage started. It changed again during the lineage. So the run makes no quarantine copy, patch or revert. Its pre-dispatch bytes stay in the lineage's `containment/baseline/` folder.
- **Every run tells you about it.** A fan-out run records a `containment_contested` ledger event. It also records a `containmentContested` field on the lineage output. A single-lineage run appends the same event to its state log. The dispatch step prints the paths beside any violations.
- **Everything else is attributed as before.** A path that was clean when the lineage started still counts as the lineage's. Opt-in restore mode is meant for a checkout with one writer. It still puts an already-dirty file back to its pre-dispatch bytes.

&nbsp;

## Upgrade

No migration required. Before you trust a contested file, compare it with its copy in `containment/baseline/`. That is because the tree shows that the bytes changed. It does not show who wrote them.

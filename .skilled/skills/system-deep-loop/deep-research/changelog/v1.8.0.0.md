Research iterations can now run through `codex exec`. You choose the model, reasoning effort and service tier. Before, they relied only on the native research agent with Claude Opus. The YAML workflow continues to own state tracking, convergence detection, lifecycle events and the reducer. The CLI runs inside that workflow. It is not a replacement. This release ships as a symmetric pair with `deep-review` v1.5.0.0.

## What's New at a Glance

- **Choose an executor for each iteration.** `executor.kind` selects `native` or `cli-codex`. `native` is the default and keeps the same agent dispatch as before. The `cli-codex` branch runs `codex exec` with the model and flags from config. It pipes the iteration prompt through stdin.
- **Render both executor prompts from one template.** The iteration context used to live inline in the YAML. That covers its state summary, focus area, constraints and file paths. It is now extracted into `assets/prompt-pack-iteration.md.tmpl`. That is because a CLI executor needs a file it can read. Before, the YAML runtime could pass the inline string straight into the native agent's context. Now both dispatch paths render the same template. They see the same content. So no implicit context gap is left between the native agent path and the CLI path.
- **Configure executor settings in one block.** `deep_research_config.json` adds `executor.kind`, `model`, `reasoningEffort`, `serviceTier`, `sandboxMode` and `timeoutSeconds`. `kind: "native"` is the default. The other fields default to null. Invalid combinations produce typed errors at config load. One example is `cli-codex` without a model. Another is an unwired reserved executor.
- **Set up executor choices with flags.** The `deep-research.md` command doc at `.opencode/commands/deep/research.md` adds `--executor`, `--model`, `--reasoning-effort`, `--service-tier` and `--executor-timeout`. Flags take precedence over config. Config takes precedence over the schema default. Setup asks one optional question in one case. That case is no flags set and no executor named in the topic. The question lets you choose `native` or `cli-codex`.
- **Record non-native executor details per iteration.** The JSONL record gains `executor: {kind, model, reasoningEffort, serviceTier}`. So readers can identify the executor for each iteration. Native runs omit the audit. That is because the YAML identifies their executor.
- **Check iteration outputs after dispatch.** Each executor must produce a markdown narrative file. It must also produce a JSONL delta record with required fields. Several faults emit a canonical `schema_mismatch` conflict event. They are missing or empty iteration output, a missing delta or missing required fields. Three consecutive validation failures trigger the existing stuck-recovery path.
- **Document the executor contract.** `SKILL.md` replaces a forward-looking note. The new text covers the shipped and reserved kinds, executor invariants, failure detection and recovery. It also covers the locations of the config and template.
- **Explain executor recovery in the loop protocol.** Section 3 of `references/loop-protocol.md` describes how branch selection interacts with `schema_mismatch` and stuck recovery. Branch selection does not change recovery semantics. The existing flow handles CLI failures like agent failures.

## Upgrade

No migration required. The `native` default preserves the same agent dispatch, iteration file and JSONL record. Existing config files need no changes.

To opt into `cli-codex` dispatch, invoke:

```
/deep:research :auto "topic" \
  --executor=cli-codex \
  --model=gpt-5.4 \
  --reasoning-effort=high \
  --service-tier=fast
```

Requires `codex` on PATH. Reserved kinds `cli-copilot` and `cli-claude-code` are declared in the config enum. They throw `ExecutorNotWiredError` at config load. The error points to future specs.

# v2.4.0.0, A CI Surface for GitHub Actions Workflows

A request about a GitHub Actions workflow reached the hub with no surface to bundle. So it reviewed as an unknown surface. It loaded none of the repository's workflow rules. The hub now has a second read-only surface, `sk-code-ci`. It holds those rules next to the file and line that prove each one.

&nbsp;

## What's New at a Glance

- `sk-code-ci` is a surface packet.
  - It is read-only and advisor-invisible.
  - It is bundled beside a workflow mode.
  - Its tool surface is `Read`, `Bash`, `Grep` and `Glob`.
- Four references carry the rules.
  - They are the rule index, the trigger and filter rules, the job shape rules and the protected set.
- Two scaffold templates.
  - A whole-workflow template and a job template start with the switch condition, permissions, concurrency, a timeout and SHA-pinned steps.
- message-contract's every-branch push is a recorded exception.
  - The trigger is correct as written.
  - So the workflow file is unchanged.
  - The exception is a labelled row in the trigger rules.
- The hub registration lists the new surface.
  - `mode-registry.json`, `hub-router.json`, `description.json`, `ROUTER.md`, the leaf manifest and the router-sync guard all name it.
  - The hub prose counts two surfaces.
- A CI prompt resolves to the surface.
  - "review the github actions workflow yaml" resolves to `[sk-code-review, sk-code-ci]`.
  - A canary case and a compiled-route test cover it.
  - Each CI phrase counts once against the review keyword.
  - The runtime keywords `build matrix`, `branch ruleset` and `actions cache key` keep a test matrix out of the CI surface.
  - The runtime keywords also keep a scorer ruleset or a loader cache key out of the CI surface.

&nbsp;

## Upgrade

No migration required. The registration is additive. It removes no mode or surface.

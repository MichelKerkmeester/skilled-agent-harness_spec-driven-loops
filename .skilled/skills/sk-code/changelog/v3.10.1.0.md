# v3.10.1.0, The Hub Reads in the Order Its Templates Prescribe

The sk-code hub now reads the way its own templates say a hub should. Related resources sit where a router expects them, the skill body keeps one job per section, and the shared workflow references orient a reader before they state a governing principle.

> Spec folder: `specs/sk-code/018-frontend-upstream-proposals/010-reference-readability-research` (Level 2)

&nbsp;

## Why This Release

A reader moving through the hub met the maintenance step and the implement, debug and verify doctrine inside WHEN TO USE, and met RELATED RESOURCES before the two sections a router reader needs. Both placements made the section names untrue. The router now matches the parent-skill template, and each overview opens with the orientation a reader needs before the principle behind it.

&nbsp;

## What's New at a Glance

- **Related resources close the router.** They move from section 8 to section 10, after HOW TO READ THIS and directly before MACHINE ROUTER, and the machine-readable router becomes section 8.
- **Every section citation follows.** The hub README setup steps, the ALWAYS tier row and the router prose now point at section 8 for the machine-readable block.
- **WHEN TO USE holds only triggers.** The `/doctor:sk-code setup` step moves to a Maintenance subsection in HOW IT WORKS, and the implement, debug and verify doctrine moves there too, beside the shared backend it belongs to.
- **Stack detection opens with orientation.** Purpose and When to Use precede Core Principle, so a reader learns what the reference decides before the principle behind it.
- **Shared workflow doctrine orients first.** The implement, debug and verify references, and the universal quality standards, now put When to Use before Core Principle or Iron Law.

&nbsp;

## Upgrade

Repoint any local citation that used the old numbers: related resources was section 8 and is now section 10, and the machine-readable router was section 9 and is now section 8.

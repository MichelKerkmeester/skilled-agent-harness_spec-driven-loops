# v3.10.1.0, The Hub Reads in the Order Its Templates Prescribe

The sk-code hub now reads the way its own templates say a hub should. Related resources sit where a router expects them. The skill body keeps one job per section. The shared workflow references orient a reader before they state a governing principle.

&nbsp;

## Why This Release

A reader moving through the hub met the maintenance step inside WHEN TO USE. They also met the implement, debug and verify doctrine there. They met RELATED RESOURCES before the two sections a router reader needs. Both placements made the section names untrue. The router now matches the parent-skill template. Each overview opens with the orientation a reader needs. That comes before the principle behind it.

&nbsp;

## What's New at a Glance

- **Related resources close the router.** They move from section 8 to section 10. They sit after HOW TO READ THIS and directly before MACHINE ROUTER. The machine-readable router becomes section 8.
- **Every section citation follows.** The hub README setup steps now point at section 8 for the machine-readable block. So do the ALWAYS tier row and the router prose.
- **WHEN TO USE holds only triggers.** The `/doctor:sk-code setup` step moves to a Maintenance subsection in HOW IT WORKS. The implement, debug and verify doctrine moves there too. It sits beside the shared backend it belongs to.
- **Stack detection opens with orientation.** Purpose and When to Use come before Core Principle. So a reader learns what the reference decides before the principle behind it.
- **Shared workflow doctrine orients before the principle.** The implement, debug and verify references now put When to Use before Core Principle or Iron Law. So do the universal quality standards.

&nbsp;

## Upgrade

Repoint any local citation that used the old numbers. Related resources was section 8 and is now section 10. The machine-readable router was section 9 and is now section 8.

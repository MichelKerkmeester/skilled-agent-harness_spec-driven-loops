# v1.1.6.0, The CI Docs Describe the Repository Profile

The CI routes learned to read a repository profile. The packet's README still said the toggle turns a `SKILLED_CI*` switch. The playbooks still called the six names the only valid ones. They now say those values belong to the repository's profile. A new scenario proves the doctor reads another repository's conventions, not this one's.

&nbsp;

## What's New at a Glance

- **The README has a section on the profile.** It gives the lookup order (`--profile`, the git config value, `.sk-code/ci.json`, a generic default). It says which values come from the profile. It says which rules stay universal. It points at the profile template. The reference map, the verification table and the related documents name the template. They also name the doctor script tests and the committed profile.
- **The skill file lists the template.** The reference map names `assets/ci-profile.template.json`. It says what `references/protected-set.md` now holds. The router table in the hub says the same.
- **A foreign-repository scenario was added.** A fresh repository has `ACME_CI` switches and three workflows. It reads clean in `/doctor:ci report` with a mocked `gh`. The scaffold prints no Skilled text. The toggle plans `ACME_CI_TESTS`. It refuses the variable behind the required check. It refuses the master switch above it. It refuses a name no workflow uses. The scenario was run. The stub's call log shows no write.
- **The hub playbook scenarios match the toggle.** The CI report scenario expects the profile key in its JSON. The toggle scenario expects the protected-workflow list and the second confirmation. It no longer limits the valid names to six.

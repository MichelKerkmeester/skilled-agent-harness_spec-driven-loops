# v1.1.6.0, The CI Docs Describe the Repository Profile

The CI routes learned to read a repository profile, but the packet's README still said the toggle turns a `SKILLED_CI*` switch and the playbooks still called the six names the only valid ones. They now say that those values belong to the repository's profile, and a new scenario proves the doctor reads another repository's conventions and not this one's.

> Spec folder: `specs/sk-code/017-portable-code-modes/010-docs-and-doctor-alignment` (Level 2)

&nbsp;

## What's New at a Glance

- **The README has a section on the profile.** It gives the lookup order (`--profile`, the git config value, `.sk-code/ci.json`, a generic default), says which values come from the profile and which rules stay universal, and points at the profile template. The reference map, the verification table and the related documents name the template, the doctor script tests and the committed profile.
- **The skill file lists the template.** The reference map names `assets/ci-profile.template.json` and says what `references/protected-set.md` now holds, and the router table in the hub says the same.
- **A foreign-repository scenario was added.** A fresh repository with `ACME_CI` switches and three workflows reads clean in `/doctor:ci report` with a mocked `gh`, the scaffold prints no Skilled text, and the toggle plans `ACME_CI_TESTS` and refuses the variable behind the required check, the master switch above it and a name no workflow uses. The scenario was run, and the stub's call log shows no write.
- **The hub playbook scenarios match the toggle.** The CI report scenario expects the profile key in its JSON, and the toggle scenario expects the protected-workflow list and the second confirmation, and no longer limits the valid names to six.

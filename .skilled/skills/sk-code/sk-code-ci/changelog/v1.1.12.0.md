# v1.1.12.0, Every Shipped Rule Reference Has Its Own Scenario

The playbook proved one route and little else. So a rule file could drift with nothing to catch it. Each rule reference the packet ships now has a scenario. It drives the rule against a fixture that breaks it. It also drives the rule against this repository, where it holds. The profile that decides which protections a doctor reads gets the same treatment. A prompt can mention a workflow without asking for CI help. That prompt is shown to stay away from the packet.

&nbsp;

## What's New at a Glance

- Each rule reference is exercised, not just routed to.
  - The document defaults, the trigger rules, the job shape rules and the profile rules each carry a scenario.
  - Each scenario has its own expected-result table.
- The profile and the flag surface are covered.
  - The four profile sources and three profile errors are walked.
  - The report, scaffold and toggle flags are driven to every exit code they can return.
  - That includes the non-zero one a step may legitimately report.
- A CI word no longer routes the packet.
  - A prompt that names a workflow without asking for CI help stays out.
  - A failure there blocks a release the way the routing one does.
- The routing expectation cites where the machine data lives.
  - The intent signals and the resource map sit in the `MACHINE ROUTER` section.
  - The expected signals name the titles the rule files carry.
- Two kinds of scenario carry two verdict rules.
  - A routing scenario is graded on its resolved paths and its route.
  - A behavioural one is graded on its own expected-result table.
  - So neither is failed for a declaration it never makes.
- The timeout ledger matches the workflows.
  - `changed-packet-validation` is listed at 20 minutes.
  - The floor count reads 35, with 9 jobs above it.

# v1.1.12.0, Every Shipped Rule Reference Has Its Own Scenario

The playbook proved one route and little else, so a rule file could drift with nothing to notice it. Each rule reference the packet ships now has a scenario that drives it against a fixture that breaks the rule and against this repository, where it holds. The profile that decides which protections a doctor reads gets the same treatment, and a prompt that mentions a workflow without asking for CI help is shown to stay away from the packet.

> Spec folder: `specs/sk-doc/072-skill-routing-and-clarity/012-alignment-remediation` (Level 2)

&nbsp;

## What's New at a Glance

- **Each rule reference is exercised, not just routed to.** The document defaults, the trigger rules, the job shape rules and the profile rules each carry a scenario with its own expected-result table.
- **The profile and the flag surface are covered.** The four profile sources and three profile errors are walked, and the report, scaffold and toggle flags are driven to every exit code they can return, including the non-zero one a step may legitimately report.
- **A CI word no longer routes the packet.** A prompt that names a workflow without asking for CI help stays out, and a failure on that scenario blocks a release the way the routing one does.
- **The routing expectation cites where the machine data lives.** The intent signals and the resource map sit in the `MACHINE ROUTER` section, and the expected signals name the titles the rule files carry.
- **Two kinds of scenario carry two verdict rules.** A routing scenario is graded on its resolved paths and its route, and a behavioural one on its own expected-result table, so neither is failed for a declaration it never makes.
- **The timeout ledger matches the workflows.** `changed-packet-validation` is listed at 20 minutes, the floor count reads 35 and 9 jobs sit above it.

# v1.13.9.0, The Quality Config Lives Inside the Skill Folder

A repository's quality config names the commands the gate runs. It also names the checklists it applies. It sat at the repository root as `.sk-code/quality.json`. It now travels with the mode that reads it. The new path is `repository/quality.json` in the `sk-code-quality` packet. So an install under `.opencode/` keeps the same path.

&nbsp;

## What's New at a Glance

- **Discovery reads the skill-folder file.** The order is `--config`, the stored `skcode.qualityConfig`, then `repository/quality.json` in the packet. That path resolves under `.skilled/` or `.opencode/`. After that comes none. `init` writes the same path. It refuses a skill folder that resolves outside the repository.
- **A config names the repository it was written for.** A `repository` field of `<owner>/<name>` applies only where the checkout matches. It is read from `GITHUB_REPOSITORY` in CI. Otherwise it is read from the origin remote. A copy that names another repository is reported as `ignored`. The gate and the doctor report it. It is applied to nothing.
- **A config at the old root path is refused.** `.sk-code/quality.json` exits 3 with `CONFIG_LEGACY_LOCATION`. It also prints a repair line that names the move. So a stale copy cannot look configured while the gate reads nothing. A `--config` or git config path inside `.sk-code/` is refused the same way. The quality reference, the README, the playbook and the runner tests name the new path.

&nbsp;

## Upgrade

A repository that committed `.sk-code/quality.json` moves it to `.skilled/skills/sk-code/sk-code-quality/repository/quality.json`. Or it names the new path with `--config` or `skcode.qualityConfig`. A repository with no config needs nothing.

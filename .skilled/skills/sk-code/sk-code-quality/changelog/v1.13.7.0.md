# v1.13.7.0, The Gate Applies Rule Overrides and the Doctor Shows Them

A repository could write a `## Rule overrides` section in its checklist. Only `--explain` read it. A run ignored the section. So a refused row passed unseen, and an accepted one left no record. `/doctor:sk-code quality` showed the config and its tools. It never showed what the gate would apply.

&nbsp;

## What's New at a Glance

- **A run reads every override section it loads.** The shared linter can refuse a section. One example is a section that names a hard-floor rule. That ends the run `ERROR` with `CONFIG_INVALID`, exit 3. The same happens for a row whose rule id no declaring document carries. That id is read from the hub's new rule id registry. The error names the checklist and every reason.
- **Accepted rows are recorded.** The verdict gains `rule_overrides`. The envelope's `p0_p1_p2_decisions` lists each row that applies. Each is written as `override <rule id> <none|replace> from <checklist file>`. These come ahead of `PENDING_AGENT_JUDGMENT`. That entry stays for the agent's own dispositions.
- **Conflicts keep the default.** Two checklists can sit at the same precedence level. If they disagree on one rule for one file, both are listed in `rule_conflicts`. They also appear as `override-conflict` in the decisions. The rule keeps its default and joins `summary.unverified`. So the gate reads `UNVERIFIED`. Rows that give the same action and text agree. `--explain` gains a per-file `rule_conflicts` field from the same pass.
- **The doctor lists what the gate would apply.** Status names each checklist with its seat. The seats are `default`, `repo-config`, `hub-surface` or `outside-skill`. It also names its override rows or refusal reasons. It names each `override-conflict` a sampled file reaches. It names the hygiene rules in force. It reads them through `quality-gate.cjs --explain` over a sample of the tree. It runs no check.
- **Every repository checklist is checked.** A `checklists[]` row the sample did not reach is listed as declared. Its file must exist. Its section must lint and name known rules. A missing file or a refused section fails the status. It fails with the code a gate run would give.
- **The docs name the outside-repository limit.** A surface skill in another repository is never discovered. `SKILL.md` and `references/quality-config.md` say how such a repository declares its rules. It declares them in `.sk-code/quality.json` instead.

&nbsp;

## Upgrade

No migration is required in a repository whose checklists carry no `## Rule overrides` section. A checklist with a refused section now stops every run that loads it. So check one with `node .skilled/skills/sk-code/shared/scripts/check-rule-overrides.cjs <checklist.md>`. Do that before the config names it.

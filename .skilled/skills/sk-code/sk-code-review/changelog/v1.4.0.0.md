sk-code-review v1.4.0.0 folds the sk-code-review slice of packet 146's ponytail-based refinement into the review baseline. It adds reusable teachings transplanted from an external reference. It moves none of the existing contract's floors. The theme is restraint and durability.

The reviewer now looks for reinvention and unneeded code. It now honors a concrete deliberate-shortcut note. Callers can now name and persist the review depth they want. It now ships a CI canary. That canary fails loudly when the verdict vocabulary drifts out of agreement. It also fails when the cross-document Iron Law wording drifts out of agreement. All five additions land in the review references plus one new script.

&nbsp;

## What's New at a Glance

- The checklist flags reinvention reviewers used to wave through.
  - Reviews used to wave through code that re-implemented behavior the language or platform gives for free.
  - Two new §6 Maintainability checks in `references/code-quality-checklist.md` name the smell directly.
  - The first is hand-rolled standard-library behavior.
  - A clear, readable primitive already exists there, and its behavior and edge cases match.
  - The second is custom code or a dependency that duplicates a native platform or runtime capability.
  - No current requirement exists that the native feature cannot satisfy.
  - Both recommend the standard or native API instead of a bespoke copy.
- The §7 KISS pass asks whether unneeded code should exist.
  - It used to ask whether code could be simpler.
  - It never asked whether it should exist.
  - New code that traces to no current requirement now earns a removal recommendation.
  - That covers a feature, parameter, branch or config nothing in the stated scope asked for.
  - It is not only a simplification suggestion.
  - It cross-references `removal_plan.md`.
  - It asks whether the code was requested.
  - It asks whether dropping the requirement would break anything.
  - Findings default to P2.
  - Findings rise to P1 only when unneeded code adds attack surface, contract obligations or regression and maintenance risk.
  - The §2 safe-to-remove-now table in `references/removal-plan.md` adds a `Replacement` field.
  - That field names what takes the removed code's place.
  - The options are nothing, a standard-library API, a native platform feature or a shorter equivalent expression.
- A concrete `ceiling:` comment can mark a shortcut as intentional.
  - A deliberate shortcut used to read like an oversight.
  - So reviewers flagged both.
  - The new §7 rule treats a comment as evidence.
  - That comment names the shortcut, its known ceiling and the upgrade path or trigger.
  - The evidence says a too-simple or missing-feature KISS or YAGNI finding was a choice.
  - The rule then downgrades or suppresses that P2.
  - This narrow exception never applies to security, authentication, persistence, sandboxing, public-contract or correctness findings.
  - Those are judged on their own contract, no matter what any comment says.
- Callers can persist review depth with `SK_CODE_REVIEW_DEPTH=lite|full|ultra`.
  - Callers who wanted a consistently deep or light review used to repeat "comprehensive" or "full review" each run.
  - §9.3 names and persists routing that already existed.
  - It resolves environment over config over default.
  - That is the same idiom as `SK_CODE_REVIEW_MIN_CHANGED_LINES`.
  - `full` is the unset default for normal ALWAYS plus CONDITIONAL plus ON_DEMAND routing.
  - `ultra` biases intent selection toward the existing ON_DEMAND deep-dive reference set for the session.
  - `lite` maps to the existing M-2 conservative skip.
  - The alias adds no new tier and relaxes no floor.
  - `lite` never lowers the ALWAYS tier, baseline security and correctness minimums or the P0/P1/P2 contract.
  - It never skips a review on a sensitive path (auth, config, persistence, dependencies, sandbox or public-response).
- A rule canary guards shared review wording against drift.
  - When an editor updated one copy and forgot the others, documents silently disagreed.
  - The guarantee rotted.
  - So `scripts/check-rule-copies.js` checks the exact `Review status:` verdict triplet in `SKILL.md` and `README.md`.
  - Downstream PR-state dedup keys on that triplet.
  - It also checks the `COMMENTED` status in the v1.3.0.0 changelog and dedup reference.
  - It also asserts that an Iron Law line still exists in sk-code `SKILL.md`, the root `CLAUDE.md` and `AGENTS.md`.
  - That line carries both "completion claim" and "verification".
  - The Iron Law forbids completion claims without verification.
  - It validates every Iron Law line in all three files.
  - So a tampered duplicate cannot hide behind a clean leading line.
  - It fails loudly when any copy drifts.
  - The canary is a checker, not a generator.
  - It never rewrites anything.
  - A `scripts/check-rule-copies.test.sh` self-test and the `.github/workflows/rule-canary-sync.yml` workflow wire it into CI.
  - The workflow fails closed if the canary is ever deleted or moved.
  - The workflow runs the canary on pull requests to `main`.

&nbsp;

## Upgrade

No migration required. None of the five additions changes the public review API. None relaxes a baseline minimum. The new review rows and prompts change what a reviewer looks for. They do not change the output contract. The depth alias is opt-in. It preserves prior behavior when unset. The canary only runs in CI and as an explicit local check. Every review keeps emitting the same `Review status:` final line.

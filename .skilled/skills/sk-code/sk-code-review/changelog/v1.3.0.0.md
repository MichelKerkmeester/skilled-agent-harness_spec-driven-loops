This release lands the sk-code-review portion of the packets 108 plus 110 auto-review uplift program. It applies 5 reusable teachings. Those teachings come from a deep-research pass over the upstream `dzianisv/opencode-plugins` auto-review package. The resulting review surface emits a parseable verdict on its final line. It refuses to repeat findings across iterations. It short-circuits reviews on already-reviewed pull-request state or low-evidence diffs. It does this without skipping sensitive changes. Implementation followed via `cli-opencode + deepseek-v4-pro --pure`. All five mechanisms land as prompt-rule and dispatcher-config changes. There are no source-code changes and no changes to the public review API.

## What's New at a Glance

- **Reviews now end with a plain-text verdict.** Reviews used to end with prose. That left downstream consumers to guess at approved, changes requested or commented. It also made retry and gating logic unreliable. So prompts now require one of these exact plain-text lines rather than Markdown bold: `Review status: APPROVED`, `Review status: REQUESTED_CHANGES` or `Review status: COMMENTED`. The `SKILL.md` NEVER section forbids any other final line. That lets consumers grep the last line for a deterministic verdict.
- **The dispatcher YAML injects a `CODE-REVIEW` marker at the start of the rendered-prompt boundary.** Reviewers occasionally drifted out of role. That happened when a long rendered prompt scrolled the role banner off-screen. The marker places the role banner where the reviewer is guaranteed to see it. A marker scan fails fast if the marker is missing after rendering. The marker is not placed in reference resources that carry YAML frontmatter. A stray marker there would corrupt parsing.
- **The review refuses to repeat findings across iterations.** Multi-iteration reviews used to surface the same finding under slightly different wording. That inflated finding counts and hid genuine new evidence. The `SKILL.md` NEVER section now prohibits restating an issue. That covers any issue already reported in an earlier iteration of the same review. So reviewers either omit the finding or extend the existing entry with new evidence. This is a prompt rule, not post-processing.
- **Unchanged pull requests reuse cached verdicts.** Re-running a review on a pull request that has not changed used to spend tokens. It re-derived the same findings. So the cache rooted at `.opencode/.sk-code-review-cache/` keys verdicts by `sha256(repo + pr_number + head_sha + base_sha + changed_files_digest)`. It short-circuits the review with the prior verdict and its provenance. Any keying-input change automatically invalidates the cache. A force-push or rebase therefore produces a fresh review. The new `references/pr-state-dedup.md` reference gives the full keying and invalidation rules.
- **The minimum-evidence gate short-circuits reviews of small diffs.** Reviewers used to apply the same depth to a one-line whitespace fix. They did the same for a 500-line refactor. So the gate short-circuits a review when the diff is too small. Such a diff does not warrant deep analysis. It never skips changes to any of the seven sensitive classes. These are security, authentication, configuration, persistence, dependencies, sandbox boundaries or public-facing paths. That holds even below the threshold.

## Upgrade

No migration required. The cache is created on its first hit. It is safe to delete at any time. The minimum-evidence gate must be explicitly enabled by the caller via `SK_CODE_REVIEW_MIN_CHANGED_LINES`. Leaving it unset preserves prior behavior. Reviewers picking up the new prompts will start emitting the final-line verdict immediately. Consumers that ignore the final line continue to work unchanged.

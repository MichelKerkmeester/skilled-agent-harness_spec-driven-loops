This release lands the sk-code-review portion of the packets 108 plus 110 auto-review uplift program, applying 5 reusable teachings distilled from a deep-research pass over the upstream `dzianisv/opencode-plugins` auto-review package. The resulting review surface emits a parseable verdict on its final line and refuses to repeat findings across iterations, while short-circuiting reviews on already-reviewed pull-request state or low-evidence diffs without skipping sensitive changes. Implementation followed via `cli-opencode + deepseek-v4-pro --pure` while all five mechanisms land as prompt-rule and dispatcher-config changes with no source-code changes or changes to the public review API.

> Spec folder: `.opencode/specs/skilled-agent-orchestration/108-auto-review-quick-wins-verdict-markers-logging` and `.opencode/specs/skilled-agent-orchestration/110-auto-review-stretch-config-dedup-gates` (Level 3)

## What's New at a Glance

- **Reviews now end with a plain-text verdict.** Reviews used to end with prose, leaving downstream consumers to guess at approved, changes requested or commented and making retry and gating logic unreliable, so prompts now require one of these exact plain-text lines rather than Markdown bold: `Review status: APPROVED`, `Review status: REQUESTED_CHANGES` or `Review status: COMMENTED`. The `SKILL.md` NEVER section forbids any other final line, allowing consumers to grep the last line for a deterministic verdict.
- **The dispatcher YAML injects a `CODE-REVIEW` marker at the start of the rendered-prompt boundary.** Reviewers occasionally drifted out of role when a long rendered prompt scrolled the role banner off-screen, and the marker places the role banner where the reviewer is guaranteed to see it. A marker scan fails fast if the marker is missing after rendering, and the marker is not placed in reference resources that carry YAML frontmatter, where a stray marker would corrupt parsing.
- **The review refuses to repeat findings across iterations.** Multi-iteration reviews used to surface the same finding under slightly different wording, which inflated finding counts and hid genuine new evidence. The `SKILL.md` NEVER section now prohibits restating an issue already reported in an earlier iteration of the same review, so reviewers either omit the finding or extend the existing entry with new evidence, by prompt rule rather than post-processing.
- **Unchanged pull requests reuse cached verdicts.** Re-running a review on a pull request that has not changed used to spend tokens re-deriving the same findings, so the cache rooted at `.opencode/.sk-code-review-cache/` keys verdicts by `sha256(repo + pr_number + head_sha + base_sha + changed_files_digest)` and short-circuits the review with the prior verdict and its provenance. Any keying-input change automatically invalidates the cache, and a force-push or rebase therefore produces a fresh review. The new `references/pr-state-dedup.md` reference gives the full keying and invalidation rules.
- **The minimum-evidence gate short-circuits reviews of small diffs.** Reviewers used to apply the same depth to a one-line whitespace fix and a 500-line refactor, so the gate short-circuits a review when the diff is too small to warrant deep analysis. It never skips changes to any of the seven sensitive classes: security, authentication, configuration, persistence, dependencies, sandbox boundaries or public-facing paths, even below the threshold.

## Upgrade

No migration required. The cache is created on its first hit and is safe to delete at any time. The minimum-evidence gate must be explicitly enabled by the caller via `SK_CODE_REVIEW_MIN_CHANGED_LINES`. Leaving it unset preserves prior behavior. Reviewers picking up the new prompts will start emitting the final-line verdict immediately. Consumers that ignore the final line continue to work unchanged.

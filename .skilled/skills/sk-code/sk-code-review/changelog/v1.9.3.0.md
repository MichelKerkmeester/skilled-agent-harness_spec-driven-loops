# v1.9.3.0, A Blocker Must Name a Reachable Input

A review could block on a failure that only a broken caller could ever trigger, because nothing in the severity rules asked whether the bad input was reachable. A P0 or P1 finding must now name an input the code's contract allows or a real caller that sends it, so blocking effort lands on defects a user can hit.

> Spec folder: `specs/sk-code/016-review-mode-followups` (Level 2)

&nbsp;

## What's New at a Glance

- **A blocker must name its reach.** The stated contract is whatever the signature, types, doc comment, name and existing checks promise, so input outside it is P2 hardening unless the code claims to validate that input.
- **A guard claims only the class it checks.** A range check that rejects an inverted range says nothing about `NaN`, so the unchecked class sits outside the contract rather than in a hole in the guard. A trust boundary is the exception, because data crossing it is always in reach, which keeps security findings as wide as they were.
- **Low confidence can no longer lift an unreachable finding.** The escalation rule raises only a finding whose reach is named, so the two rules cannot contradict each other.
- **Every copy of the mode states the rule.** The reference, the skill file, the README and the review agent with its runtime copies all carry it. The clean control now records a `NaN` or non-number hardening note as an allowed P2.
- **Measured on a live rerun.** Three runs per scenario on one model found the seeded injection and the seeded off-by-one at blocker severity every time. The clean control raised no blocker in any run. With the clean control's range guard removed, the review still flagged the inverted range, at P2.

&nbsp;

## Upgrade

A review that used to block on out-of-contract input now reports it as P2 hardening. Nothing else is required, because the report format is unchanged.

# v1.9.3.0, A Blocker Must Name a Reachable Input

A review could block on a failure that only a broken caller could ever trigger. Nothing in the severity rules asked whether the bad input was reachable. A P0 or P1 finding must now name an input the code's contract allows. Or it must name a real caller that sends it. So blocking effort lands on defects a user can hit.

&nbsp;

## What's New at a Glance

- **A blocker must name its reach.** The stated contract is whatever the signature, types, doc comment, name and existing checks promise. So input outside it is P2 hardening. That holds unless the code claims to validate that input.
- **A guard claims only the class it checks.** A range check that rejects an inverted range says nothing about `NaN`. So the unchecked class sits outside the contract. It is not a hole in the guard. A trust boundary is the exception. Data crossing it is always in reach. That keeps security findings as wide as they were.
- **Low confidence can no longer lift an unreachable finding.** The escalation rule raises only a finding whose reach is named. So the two rules cannot contradict each other.
- **Every copy of the mode states the rule.** The reference, the skill file, the README and the review agent all carry it. So do its runtime copies. The clean control now records a `NaN` or non-number hardening note as an allowed P2.
- **Measured on a live rerun.** Three runs per scenario on one model found the seeded injection. They also found the seeded off-by-one. Both came at blocker severity every time. The clean control raised no blocker in any run. With the clean control's range guard removed, the review still flagged the inverted range, at P2.

&nbsp;

## Upgrade

A review that used to block on out-of-contract input now reports it as P2 hardening. Nothing else is required. That is because the report format is unchanged.

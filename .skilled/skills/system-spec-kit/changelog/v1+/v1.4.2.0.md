# v1.4.2.0, The Comment Rule Gets Teeth, and the Review Backlog Closes

The sk-code rule finally has a machine that enforces it.

- The rule bans ephemeral-artifact pointers in code comments.
- The machine immediately proved the rule had been ignored.
- The guard found 274 violations across 116 files.
- The scale was roughly ten times what anyone thought.

The same release closes the actionable findings from the embedding-stack deep review.

- The coordinated single-writer and durability cluster lands together.
- The review flagged that cluster as must-fix-together.
- The release also repairs the memory database.
- That database had been failing every write since session start.

Three habits run through the work.

- Build the detector before you trust the cleanup.
- Re-validate every finding against HEAD before you touch it.
- Verify a fix through the path that actually failed.
- Do not verify it through the layer that was always fine.

## The Comment Rule, Now Enforced

The sk-code rule is simple. A code comment may keep its durable WHY. It must never embed an ephemeral-artifact pointer. Examples are a spec folder or number, a task/checklist/requirement id, a review-finding id, an ADR id or a ticket.

Those get renamed or archived on their own schedule. So they rot into dangling pointers. An earlier pass cleaned 27 files using hand-written grep patterns. This release built the detector that should have come first.

#### A Precision-First Detector <a id="c-a-precisionfirst-detector"></a>

- `scripts/validation/ephemeral-pointer-audit.mjs` is a standalone Node ESM script.
- `ephemeral-pointer-audit.mjs` is a dependency-free detector for sk-code §4.
- It flags ephemeral-artifact pointers in code comments.
- It inspects comment regions only.
- It never inspects string or code content.
- So it never flags a runtime path constant or a test fixture value.
- Each forbidden pattern is narrowed to the shape of a real tracking id.
- That covers spec numbers, `T###`, `CHK-###` and `REQ-###` ids, and ADR or ticket ids.
- Each pattern is paired with an explicit allow-list.
- The list holds HTTP status codes, embedding dimensions and token-budget tiers.
- It holds rolling-window sizes, schema-version tags and JSDoc example shapes.
- It holds externally-versioned standards.
- It holds the runtime `.opencode/specs/` paths the code actually reads.
- The script exits nonzero on any hit.
- So CI, pre-commit or an sk-code verification step can gate on it.

#### The Cleanup It Forced <a id="c-the-cleanup-it-forced"></a>

- The prior hand-rolled cleanup had caught roughly 10%.
- The guard found the rest.
- Its hand patterns missed several classes.
- They were `P0-`/`P1-`/`P2-` review-finding ids and two-digit and hyphenated task ids.
- They were no-hyphen checklist ids, `#NN` issue refs and `NNN-NNN` spec pairs.
- They were `SPRINT N` labels.
- A parallel sweep brought the whole tree to zero.
- A sweep with zero behavior change fixed every one.
- Fan-out agents made 261 fixes across 119 files.
- An orchestrator pass closed eight stragglers in directories the batching had missed.
- Every edit kept the explanatory text.
- It dropped only the perishable id.
- The diff touches comment and string text only.

## Review Backlog and Documentation Truth

The embedding-stack deep review left a backlog. This release works it.

#### Documentation Reconciled and Refreshed <a id="c-documentation-reconciled-and-refreshed"></a>

- Three documentation findings landed first.
- The 005 file-change matrix was attributing idle-eviction to the wrong file.
- It lives in `model-server-supervision.cjs`, not `hf-model-server.cjs`.
- ENV_REFERENCE had been missing `EMBEDDER_REINDEX_BATCH_SIZE`, `EMBEDDING_DIM` and `HF_EMBEDDINGS_PREFIX_QUERY`/`DOC`.
- Four embedding env knobs are now documented.
- Four daemon-reliability packet ledgers (009/010/012/013) had verification tables left open.
- Their summaries claimed "implemented".
- Their open items are now marked done with real evidence.
- Every session-touched code folder now documents its current source files.
- It documents its entry points and the new guard.
- Three folder READMEs were created.
- Ten were refreshed through the sk-doc template.

#### Three Fixes, Two Honest No-Changes <a id="c-three-fixes-two-honest-nochanges"></a>

- Three correctness edges are closed.
- The execution-router adapter cache now includes the resolved dimension in its invalidation check.
- So a `dimensionsOverride` can never silently reuse a wrong-dimension adapter.
- The bootstrap auto-selector now moves an explicit `EMBEDDINGS_PROVIDER` to the front of the local-first cascade.
- The retention TOCTOU is closed.
- The sweep re-validates `delete_after` inside the delete transaction.
- A concurrent writer can un-expire a row between select and delete.
- That can no longer cause a wrong deletion.
- That closes a multi-process data-loss window.
- Two findings were dispositioned rather than patched.
- One described a function that does not exist.
- The real lock fallback is an intentional graceful degradation to an in-process queue.
- So failing closed would have been a regression.
- The other was already fixed at HEAD.
- Re-validation is what caught both.

## The Single-Writer and Durability Cluster

The deep review flagged a cluster of launcher and durability defects. They share resources: a respawn lock, a root-liveness authority, lease files and a shutdown marker. It warned they must land together. Otherwise piecemeal fixes would re-collide.

Eight launcher and durability findings land as one change set. The corruption incident came from the launcher surface. That surface is now hardened.

#### Locks, Listeners and Eviction <a id="c-locks-listeners-and-eviction"></a>

- The respawn lock now bounds staleness to listener liveness.
- So a live demand listener cannot have its lock declared stale by wall-clock alone.
- The lazy listener re-arms on a failed spawn instead of stranding.
- Idle eviction now reaps the root process, not just its descendants.
- It does this through the shared root-liveness authority.

#### Safer Shutdown, Reindex, Startup and Leases <a id="c-safer-shutdown-reindex-startup-and-leases"></a>

- The clean-shutdown marker is deleted only after a confirmed-successful close.
- So a failed detach or close can no longer leave the next open wrongly trusting the DB.
- Same-dimension reindex writes to a staging shard.
- It atomic-swaps on success.
- So a mid-loop failure can no longer half-overwrite the live shard.
- The worker also re-reads its cancel flag mid-run.
- Direct startup applies the same socket-ownership and live-resident perimeter guard the supervised path uses.
- tcp targets enforce loopback or auth.
- The standalone-save lease honors a live recorded child pid in a stale-looking launcher lease.
- So a second writer is not admitted.
- The review listed an owner-lease election race.
- It was re-validated as already O_EXCL-remediated at HEAD.
- So it needed verification, not a change.

## Memory Database Repair

Every write to the spec-memory MCP failed with `SQLITE_CONSTRAINT_PRIMARYKEY`. That blocked `memory_save`, `memory_index_scan` and `memory_match_triggers`. The spec-memory daemon could not index or save.

#### A Premature Fix, Corrected <a id="c-a-premature-fix-corrected"></a>

- The investigation root-caused it to the FTS5 shadow desyncing after an unclean shutdown.
- An honest correction belongs in the record.
- The first repair attempt verified at the SQLite-CLI layer.
- It declared success prematurely.
- The MCP write path was never exercised.
- That path is the one that actually failed.
- On re-examination the on-disk database was healthy at rest.
- `quick_check` came back ok.
- The `memory_index` and `memory_fts` row counts matched.
- The failing daemon had already died.
- The real fault was a stale, unclean daemon lifecycle over a healthy DB.
- It was not fresh or standing corruption.

#### Verified Through the Failing Path <a id="c-verified-through-the-failing-path"></a>

- After the restart, `memory_health` shows FTS integrity ok and zero constraint errors.
- This time the repair was verified through real MCP writes.
- `memory_index_scan` succeeded across the session's new packets with zero errors.
- The memory database accepts writes again.
- A clean daemon restart cleared the failure.
- `memory_health` now reports HEALTHY.
- The packet docs had diagnostic-only `/doctor memory` references.
- Those were corrected to point at the guarded `memory_health` autoRepair path.
- Three packet docs had drifted into mutual contradiction.
- They were reconciled to the verified outcome.

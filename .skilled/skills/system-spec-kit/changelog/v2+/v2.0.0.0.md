This release moves the system spec kit from JavaScript to TypeScript to make the codebase easier to maintain without changing how the runtime behaves for existing users.

## Why This Release

The project had grown large enough that stronger type checks were worth the migration effort.

## What's New at a Glance

- **The system spec kit moved from JavaScript to TypeScript.** The conversion gives the project a more consistent foundation.
- **The migration was divided into phases.** Breaking up the large change lowered migration risk.
- **TypeScript build support was added.** Project references support multi-workspace builds.
- **Runtime compatibility was preserved.** Existing startup commands stayed in place.
- **The tests and documentation moved with the code.** Example code and file references were updated.
- **Dedicated type support files were added.** Shared types and vector-extension declarations support the new code.

---

## TypeScript Migration

#### TypeScript Covers the Kit

The conversion included the shared code, MCP server, scripts, tests and supporting documentation. It helps catch mistakes earlier during development.

&nbsp;

#### Work Moves in Phases

The work covered infrastructure, shared utilities, core server code, handlers, scripts, tests and documentation, with each area updated in sequence. This made it easier to validate each part before moving on.

&nbsp;

#### Builds Support Workspaces

A TypeScript codebase needs its own build rules and project-level settings. The release added TypeScript configuration files, generated type declarations and source maps. These additions keep the build process predictable and make cross-project imports easier to understand.

&nbsp;

#### Runtime Compatibility Holds

The compiled output stayed compatible with the existing CommonJS runtime, and the generated JavaScript behavior stayed aligned with the earlier version. Teams can adopt the new source format without having to relearn or rewire the runtime setup.

&nbsp;

#### Tests and Docs Follow Along

A language migration is hard to trust if the tests and documentation still describe the old setup. The release converted the test suite and updated example code. Documentation references changed from `.js` files to `.ts` files where needed, keeping the written guidance in sync with the actual code and making the migration easier to follow.

&nbsp;

#### Shared Types Have a Home

Some parts of the TypeScript setup needed dedicated support files. The release introduced shared type definitions and vector-extension type declarations so the new code could compile cleanly across workspaces. These additions remove guesswork around shared interfaces and give the migration a cleaner long-term base.

---

## Upgrade Notes

- Pull the latest changes and rebuild the project as usual.
- Existing startup commands stay in place, so no runtime migration is required.
- If you maintain local docs or examples, update any remaining `.js` source references to `.ts`.

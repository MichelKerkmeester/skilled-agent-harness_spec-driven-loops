This release makes concurrent access to the memory index more reliable and completes database maintenance. It explains the results more clearly, giving the team clearer proof that the maintenance worked and making the workflow easier to follow and trust.

## What's New at a Glance

- **Concurrent readers wait for the WAL lock.** When multiple MCP server processes access the WAL-mode database concurrently, the `busy_timeout = 10000` PRAGMA lets readers wait 10 seconds instead of failing immediately. This avoids intermittent `"no such table: memory_index"` errors that occurred when `sqlite3_prepare()` could not obtain the lock during schema loading and the database fell back to a stale main database file with an empty schema.
- **The memory index was cleaned.** Maintenance removed 67 test artifact entries (`spec_folder='T'`) and 2 temporary-tier entries.
- **The old stale-conflict entries were no longer needed.** Cleanup removed 9,626 orphaned records from `memory_conflicts`.
- **Missing phrases were supplied.** Title- and path-based extraction generated trigger phrases for 1,463 memories that had none.
- **The post-maintenance index contained 2,909 memories.** It had zero test artifacts, temporary entries, stale conflicts and missing trigger phrases.
- **The incremental scan completed.** It indexed 23 new files, updated 30 and skipped 1,485 unchanged files using mtime-based skip.

## Upgrade

The `busy_timeout` PRAGMA is applied automatically on database open. Restart any running MCP server processes to pick up the fix. No migration required.

This release fixes the MCP server's SQLite "no such table" errors in `/memory:manage`. The fix works in four layers: tool access, a health-check guard, schema resilience and actionable error messages.

A code review pass also cleaned up variable naming, shared error handling, stale section references and the health table list.

## Why This Release

The errors hit the `memory_index` and `checkpoints` tables when the LLM fell back to raw `sqlite3` Bash commands against uninitialized databases.

## What's New at a Glance

- **`/memory:manage` drops Bash from its allowed tools.** The LLM loses the fallback that led to the errors.
- **`/memory:manage` adds two error handling rows.** They give actionable guidance when a tool or the database is not ready.
- **`handleMemoryHealth()` now awaits `checkDatabaseUpdated()`.** It was the only handler missing this standard guard.
- **Companion table setup is extracted into `ensureCompanionTables()`.** The companion tables are now always created, even when `memory_index` already exists.
- **Error messages suggest specific recovery actions.** Four null-database responses are also aligned with each other.
- **Local variables move from snake_case to camelCase.** `spec_folder` becomes `specFolder` and `checkpoint_name` becomes `checkpointName`.
- **Checkpoints share one error helper.** `toErrorMessage()` replaces all eight inline error patterns.
- **`requireDb()` returns a standard `NonNullable<>` type.** The health handler response also uses ES2015 property shorthand.

---

## The Manage Command

#### Tool Rules and Recovery Rows

The command gains an explicit tool enforcement block that prohibits direct database access. The two new error handling rows are "MCP tool unavailable" and "Database not initialized".

&nbsp;

#### References and Tables Brought Current

Seven stale section number references in the command's routing tree are fixed, such as a Section 5 reference that now reads Section 7. The health check output template now includes the `memory_history`, `checkpoints` and `memory_conflicts` tables. It no longer lists `session_state`, which is managed by session-manager, not companion tables.

---

## Database Safety

#### Health Checks Report a Missing Schema

A missing table used to leave the health check silently reporting a "degraded" status. The handler now detects "no such table" and returns `E_SCHEMA_MISSING` with recovery instructions.

&nbsp;

#### Companion Tables on Both Paths

`ensureCompanionTables()` carries TSDoc and holds idempotent `CREATE TABLE IF NOT EXISTS` statements for `memory_history`, `checkpoints` and `memory_conflicts` plus their indexes. `create_schema()` calls it from both its existing-database early-return path and its new-database path.

&nbsp;

#### Errors That Name a Fix

The improved messages cover the null-database responses in `requireDb()`, `checkpoints.getDatabase()`, `handleMemoryList()` and `handleMemoryStats()`. The checkpoints module also drops its module prefix from the error it throws.

---

## Code Cleanup

#### Consistent camelCase Names

The rename covers all snake_case local variables in `handleMemoryDelete`, `handleMemoryUpdate`, `handleMemoryList` and `handleMemoryStats`, including `allow_partial_update` to `allowPartialUpdate`. The backward-compatible snake_case alias block gains a comment with removal guidance.

&nbsp;

#### One Shared Error Helper

The checkpoints module imports `toErrorMessage()` from the db helpers. Each replaced pattern had the form `error instanceof Error ? error.message : String(error)`.

&nbsp;

#### Standard Types and Shorthand

The `NonNullable<>` utility type replaces the `and {}` intersection trick in the `requireDb()` return type. The property shorthand applies to `embeddingModelReady` and `memoryCount`.

---

## Upgrade Notes

- Restart the MCP server after updating to apply the schema changes.
- On the next startup, `ensure_companion_tables()` will auto-create any missing companion tables. No manual migration is needed.

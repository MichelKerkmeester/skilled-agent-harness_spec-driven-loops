# v3.4.2.0, The Comment Rule Gets Teeth, and the Review Backlog Closes

v3.4.2.0 is a hardening-and-honesty release. The sk-code rule that bans ephemeral-artifact pointers in code comments finally has a machine that enforces it. That machine immediately proved the rule had been ignored at roughly ten times the scale anyone thought.

The same release closes the actionable findings from the embedding-stack deep review. It lands the coordinated single-writer and durability cluster the review flagged as must-fix-together, and it repairs the memory database that had been failing every write since session start.

The throughline is three habits. Build the detector before you trust the cleanup. Re-validate every finding against HEAD before you touch it. Verify a fix through the path that actually failed, not the layer that was always fine.

## Why This Release

v3.4.1.0 shipped the substrate. This release follows it with hardening and honesty: a machine behind the comment rule, the fixes the deep review called for and a working memory database.

## The Comment Rule, Now Enforced

The sk-code rule is simple: a code comment may keep its durable WHY but must never embed an ephemeral-artifact pointer, such as a spec folder or number, a task/checklist/requirement id, a review-finding id, an ADR id or a ticket. Those get renamed or archived on their own schedule and rot into dangling pointers. An earlier pass cleaned 27 files using hand-written grep patterns, and this release built the detector that should have come first.

#### A Precision-First Detector

`scripts/validation/ephemeral-pointer-audit.mjs` is a standalone Node ESM script. It inspects comment regions only, never string or code content, so it never flags a runtime path constant or a test fixture value.

Each forbidden pattern, from spec numbers to `T###`, `CHK-###` and `REQ-###` ids and ADR or ticket ids, is narrowed to the shape of a real tracking id. Each is paired with an explicit allow-list: HTTP status codes, embedding dimensions, token-budget tiers, rolling-window sizes, schema-version tags, JSDoc example shapes, externally-versioned standards and the runtime `.opencode/specs/` paths the code actually reads. The script exits nonzero on any hit, so CI, pre-commit or an sk-code verification step can gate on it.

&nbsp;

#### The Cleanup It Forced

The prior hand-rolled cleanup had caught roughly 10%, and the guard found the rest. The classes its hand patterns missed were `P0-`/`P1-`/`P2-` review-finding ids, two-digit and hyphenated task ids, no-hyphen checklist ids, `#NN` issue refs, `NNN-NNN` spec pairs and `SPRINT N` labels.

A parallel sweep brought the whole tree to zero. Fan-out agents made 261 fixes across 119 files, and an orchestrator pass closed eight stragglers in directories the batching had missed. Every edit kept the explanatory text and dropped only the perishable id, and the diff touches comment and string text only.

## Review Backlog and Documentation Truth

The embedding-stack deep review left a backlog, and this release works it. Each finding was re-validated against the current HEAD before any edit, because line numbers had shifted under the comment sweep and several findings turned out to be already-fixed or mis-located.

#### Documentation Reconciled and Refreshed

Three documentation findings landed first. The 005 file-change matrix was attributing idle-eviction to the wrong file: it lives in `model-server-supervision.cjs`, not `hf-model-server.cjs`. ENV_REFERENCE had been missing `EMBEDDER_REINDEX_BATCH_SIZE`, `EMBEDDING_DIM` and `HF_EMBEDDINGS_PREFIX_QUERY`/`DOC`.

The four daemon-reliability packet ledgers (009/010/012/013) had verification tables left open while their summaries claimed "implemented". Their open items are now marked done with real evidence. Every session-touched code folder now documents its current source files, entry points and the new guard.

&nbsp;

#### Three Fixes, Two Honest No-Changes

The execution-router adapter cache now includes the resolved dimension in its invalidation check, so a `dimensionsOverride` can never silently reuse a wrong-dimension adapter. The bootstrap auto-selector now moves an explicit `EMBEDDINGS_PROVIDER` to the front of the local-first cascade. The retention TOCTOU is closed: the sweep re-validates `delete_after` inside the delete transaction, so a concurrent writer that un-expires a row between select and delete can no longer cause a wrong deletion. That closes a multi-process data-loss window.

Two findings were dispositioned rather than patched. One described a function that does not exist. The real lock fallback is an intentional graceful degradation to an in-process queue, so failing closed would have been a regression. The other was already fixed at HEAD. Re-validation is what caught both.

## The Single-Writer and Durability Cluster

The deep review flagged a cluster of launcher and durability defects that share resources: a respawn lock, a root-liveness authority, lease files and a shutdown marker. It warned they must land together or piecemeal fixes would re-collide.

#### Locks, Listeners and Eviction

The respawn lock now bounds staleness to listener liveness, so a live demand listener cannot have its lock declared stale by wall-clock alone. The lazy listener re-arms on a failed spawn instead of stranding. Idle eviction now reaps the root process, not just its descendants, through the shared root-liveness authority.

&nbsp;

#### Safer Shutdown, Reindex, Startup and Leases

The clean-shutdown marker is deleted only after a confirmed-successful close, so a failed detach or close can no longer leave the next open wrongly trusting the DB. Same-dimension reindex writes to a staging shard and atomic-swaps on success, so a mid-loop failure can no longer half-overwrite the live shard. The worker also re-reads its cancel flag mid-run.

Direct startup applies the same socket-ownership and live-resident perimeter guard the supervised path uses, and tcp targets enforce loopback or auth. The standalone-save lease honors a live recorded child pid in a stale-looking launcher lease, so a second writer is not admitted.

The owner-lease election race the review listed was re-validated as already O_EXCL-remediated at HEAD, so it needed verification, not a change.

## Memory Database Repair

Every write to the spec-memory MCP failed with `SQLITE_CONSTRAINT_PRIMARYKEY`, which blocked `memory_save`, `memory_index_scan` and `memory_match_triggers`. The spec-memory daemon could not index or save.

#### A Premature Fix, Corrected

The investigation root-caused it to the FTS5 shadow desyncing after an unclean shutdown. An honest correction belongs in the record: the first repair attempt verified at the SQLite-CLI layer and declared success prematurely, while the MCP write path, the one that actually failed, was never exercised.

On re-examination the on-disk database was healthy at rest. `quick_check` came back ok, and the `memory_index` and `memory_fts` row counts matched. The failing daemon had already died. The real fault was a stale, unclean daemon lifecycle over a healthy DB, not fresh or standing corruption.

&nbsp;

#### Verified Through the Failing Path

After the restart, `memory_health` shows FTS integrity ok and zero constraint errors. This time the repair was verified through real MCP writes: `memory_index_scan` succeeded across the session's new packets with zero errors.

The diagnostic-only `/doctor memory` references in the packet docs were corrected to point at the guarded `memory_health` autoRepair path. The three packet docs that had drifted into mutual contradiction were reconciled to the verified outcome.

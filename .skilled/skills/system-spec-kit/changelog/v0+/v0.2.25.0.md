This release makes concurrent access to the memory index more reliable. It also completes database maintenance. It explains the results more clearly. The team gets clearer proof that the maintenance worked. The workflow is easier to follow and trust.

&nbsp;

## What's New at a Glance

- Concurrent readers wait for the WAL lock.
  - Multiple MCP server processes can access the WAL-mode database at once.
  - The `busy_timeout = 10000` PRAGMA lets readers wait 10 seconds instead of failing at once.
  - This avoids intermittent `"no such table: memory_index"` errors.
  - Those errors came when `sqlite3_prepare()` could not get the lock during schema loading.
  - The database then fell back to a stale main database file with an empty schema.
- The memory index was cleaned.
  - Maintenance removed 67 test artifact entries (`spec_folder='T'`).
  - Maintenance also removed 2 temporary-tier entries.
- The old stale-conflict entries were no longer needed.
  - Cleanup removed 9,626 orphaned records from `memory_conflicts`.
- Missing phrases were supplied.
  - Title- and path-based extraction generated trigger phrases for 1,463 memories.
  - Those memories had none.
- The post-maintenance index contained 2,909 memories.
  - It had zero test artifacts, temporary entries, stale conflicts and missing trigger phrases.
- The incremental scan completed.
  - It indexed 23 new files and updated 30.
  - It skipped 1,485 unchanged files using mtime-based skip.

&nbsp;

## Upgrade

The `busy_timeout` PRAGMA is applied automatically on database open. Restart any running MCP server processes to pick up the fix. No migration required.

# v1.5.0.0, dispatch to OpenCode 1 or 2

cli-opencode now dispatches to OpenCode 1 (1.19.3) or OpenCode 2 (2.0.32) from one skill, and it reads the version from parsed `--version` output rather than the binary name. The dispatch guard audits both versions, and a new setup helper and install reference cover the side-by-side layout, because both packages claim the `opencode` name and share the same default database.

> Spec folder: `specs/cli-external-orchestration/082-opencode-v1-v2-dual-compat` (Level 2)

&nbsp;

## What's New at a Glance

- **The dispatch resolves its binary first.** `$OPENCODE_BIN` wins when it is set, and otherwise a `PATH` walk prefers `opencode2` over `opencode` inside each directory.
- **The guard audits both versions.** Every hard rule declares the versions it applies to, so an `opencode2` run is checked instead of passing unaudited. When the version cannot be read, version-specific rules drop to a warning rather than blocking a dispatch they cannot prove wrong.
- **OpenCode 2 changes the flags.** The reasoning level rides on the model id (`-m provider/model#level`) and the dispatch starts in the target directory, with `--standalone` on every OpenCode 2 child dispatch. `--variant`, `--dir` and `--command` are OpenCode 1 only, and an OpenCode 2 slash prompt goes through `session.command` instead.
- **Install has a helper and a reference.** `scripts/opencode-setup.sh` builds the side-by-side, OpenCode 1-only or OpenCode 2-only layout and refuses to shadow the other version. `references/install-and-versions.md` covers the `opencode2` launcher, the shared config folder and the `upgrade --major` warning.

&nbsp;

## Upgrade

No migration required. The OpenCode 1 dispatch line is unchanged. With both versions installed, a dispatch with no `OPENCODE_BIN` pin follows `PATH` order, where an earlier directory wins and `opencode2` comes first only within a directory, so set `OPENCODE_BIN=opencode` to keep it on OpenCode 1.

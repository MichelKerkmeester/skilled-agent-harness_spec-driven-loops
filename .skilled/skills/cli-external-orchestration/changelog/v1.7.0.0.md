The Jev judgment transport now has a separate `cli-jev` hub. The executor dispatch hub keeps its seven workflow modes.

## What's New at a Glance

- **The former `cli-jev` mode is now `cli-usage`.** It is the first mode in its own `cli-jev` hub at `.skilled/skills/cli-jev/`. The rule that a judgment is not an authorization moved with the mode, which the `cli-jev` hub now states.
- **The `transport-axis` extension now belongs to `cli-jev`.** Its `transports` list names `cli-usage`, while this hub's `mode-registry.json` no longer declares `extensions["transport-axis"]`. The per-hub gate refuses a transport whose packet does not resolve, so the axis moved with its packet instead of staying here without one.
- **Jev requests resolve to the `cli-jev` hub.** `hub-router.json` drops the `cli-jev` signal and the `cli-jev-aliases` and `jev-dispatch` vocabulary classes. It also removes the `cli-jev` entry in `tieBreak`.
- **The hub's descriptions and docs no longer advertise Jev transport.** `description.json` and `graph-metadata.json` no longer carry transport keywords or docs while the `SKILL.md` mode table lists seven modes with no second axis. The `README.md` describes one packet kind while the `ROUTER.md` maps no Jev intent or leaf.
- **The `jev` judgment command still resolves to `cli-jev` in the audit.** Enforcement guards now read `cli-jev/cli-usage/SKILL.md`.
- **The seven executor modes keep `packetKind: "workflow"` and their behavior.** They still classify intent and choose a provider while their dispatched sessions write in this repository. Their contracts, invariants and evidence stay unchanged.

# v1.6.0.0 — cli-jev transport mode

## Added

- **`cli-jev` — the hub's eighth mode and its first `packetKind: "transport"`.** It bridges the Jev
  CLI/MCP surface: `noul`, `choice`, `score` and `run` return one typed value from a state, and the
  mode writes nothing into this workspace. `Write`, `Edit` and `Task` are forbidden and
  `mutatesWorkspace` is `false`, so a transport selects while a workflow acts.
- **The `transport-axis` extension.** `mode-registry.json` now declares
  `extensions["transport-axis"].transports: ["cli-jev"]`, so the axis is registered rather than
  ad-hoc, and the per-hub gate enforces the whole contract (routingClass `metadata`,
  `mutatesWorkspace: false`, the forbidden tool set, and membership in the axis).
- **`cli-jev` packet** at `cli-jev/`: `SKILL.md` with eight declared hard rules, four references
  (`cli-reference.md`, `providers-and-models.md`, `integration-patterns.md`, `mcp-server.md`), a
  question-shaping card, a feature catalog, a 22-scenario manual testing playbook, a benchmark
  baseline and a changelog.
- **Dispatch enforcement.** The audit resolves `jev noul|choice|score|run` and `jev-mcp` to
  `cli-jev` from the command's structure, and eight implemented checks back the packet's rules:
  availability, stdin bounding, `choice` cardinality, `score` cardinality, `--value` against `run`,
  the `custom` endpoint requirement, inline credentials, and the `jev-mcp` host-only rule. Each
  carries a satisfied/violated fixture pair under the existing bijection guard.
- **Routing surfaces.** `hub-router.json` gains the `cli-jev` signal with its two vocabulary
  classes; `ROUTER.md` gains the `JEV` intent row and its two-lead `RESOURCE_MAP`; `leaf-manifest.json`
  registers the five leaves; the hub `SKILL.md` carries the transport row, the second axis and the
  layout; `ROUTER.md` and the hub registry prose name the transport throughout.

## Changed

- **`packetKind` prose in `mode-registry.json`** and the hub `SKILL.md` now describe two axes and one
  extension instead of asserting zero. The previous text said no mode here could be a transport, which
  the eighth mode disproves; the discriminator prose is the registry's own contract, so it moved with
  the registry.
- **`description.json`, `mode-registry.json`, `hub-router.json`, `ROUTER.md` and the hub `SKILL.md`**
  all carry `1.6.0.0`, keeping the single release value the hub's version authority requires.
- **The executor-delegation note** states explicitly that the scorer reads the `workflow` modes and
  that `cli-jev` is deliberately absent: an executor there means "a CLI that can take a task", and
  the transport runs nothing.

## Not Changed

- **No deep-loop `ExecutorKind`.** Jev has no file tools, no iteration model and no stop policy, so it
  cannot run a lineage and no `ExecutorKind` was added.
- **No MCP registration.** `jev-mcp` ships in the same package and is documented, but no repository
  MCP config carries it. Wiring a host is an operator step.
- **The seven existing modes.** No workflow mode's behavior, contract, rules or routing changed; the
  registry edits are additive apart from the version and the prose that the new mode falsified.

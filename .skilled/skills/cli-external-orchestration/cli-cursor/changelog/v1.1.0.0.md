This release gives cli-cursor one dedicated catalog. It holds the provider, model, effort and dispatch facts. Readers can find them in one place. The hard-enforced 10-id allowlist already matched the intended keep-set. That set is Composer, Grok-4.5 and GLM-5.2. So no roster curation was needed. The work was purely catalog, trim and restructure.

&nbsp;

## Why This Release

The model facts were split between `SKILL.md` and `cli-reference.md`. So answering which model, which effort and how dispatch works meant stitching fragments together. That made the safety-critical 10-id allowlist easy to miss.

&nbsp;

## What's New at a Glance

- One catalog covers provider and model details.
  - `references/providers-and-models.md` records cli-cursor's one backing provider.
  - That provider is Cursor via `cursor-agent`.
  - The catalog also records the default model, the suffix-baked effort model and the dispatch shape.
  - The mode has no `--effort` flag.
  - That is because the tier lives in the model ID.
- The advisor can surface the catalog directly.
  - The catalog mirrors the full hard-enforced 10-id allowlist.
  - That list scopes dispatch as a safety contract.
  - The catalog links to `CURSOR_SUPPORTED_MODELS` in `executor-config.ts`.
  - The catalog says code wins if documentation differs.
- The duplicate notes now point to the catalog.
  - `cli-reference.md` §5 and the `SKILL.md` roster hold compact residues.
  - Those residues point there.
  - The enforced list stays inline in `cli-reference.md`.
  - So the safety contract remains visible in the primary reference.
  - The effort explanation, ID-form pitfall and dispatch envelope live only in the catalog.
- The model list is grouped by provider.
  - Section 2 uses a `### Cursor` heading and table per provider.
  - The table makes the enforced allowlist scannable.
  - The table shows family, default and per-ID notes.
  - The table replaces an inline paragraph.

&nbsp;

This release gives cli-cursor one dedicated catalog for its provider, model, effort and dispatch facts, so readers can find them in one place. The hard-enforced 10-id allowlist already matched the intended keep-set of Composer, Grok-4.5 and GLM-5.2, so no roster curation was needed. The work was purely catalog, trim and restructure.
> Spec folder: `.opencode/specs/cli-external-orchestration/033-per-mode-provider-model-reference/`

## Why This Release

The model facts were split between `SKILL.md` and `cli-reference.md`, so answering which model, which effort and how dispatch works meant stitching fragments together. That made the safety-critical 10-id allowlist easy to miss.

## What's New at a Glance

- **One catalog covers provider and model details.** `references/providers-and-models.md` records cli-cursor's one backing provider, Cursor via `cursor-agent`, the default model, suffix-baked effort model and dispatch shape. The mode has no `--effort` flag because the tier lives in the model ID.
- **The advisor can surface the catalog directly.** It mirrors the full hard-enforced 10-id allowlist that scopes dispatch as a safety contract, links to `CURSOR_SUPPORTED_MODELS` in `executor-config.ts` and says code wins if documentation differs.
- **The duplicate notes now point to the catalog.** `cli-reference.md` §5 and the `SKILL.md` roster hold compact residues that point there. The enforced list stays inline in `cli-reference.md` so the safety contract remains visible in the primary reference, while the effort explanation, ID-form pitfall and dispatch envelope live only in the catalog.
- **The model list is grouped by provider.** Section 2 uses a `### Cursor` heading and table per provider. The table makes the enforced allowlist scannable by family, default and per-ID notes instead of an inline paragraph.
